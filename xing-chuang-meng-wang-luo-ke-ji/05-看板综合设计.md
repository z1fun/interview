# 看板综合设计｜15 分钟

用时：读 5 分钟，脱稿讲两遍共 10 分钟。以下是练习方案，不代表个人生产经历。

## 题目

按日期、游戏、渠道查看收入、活跃和付费趋势，支持明细与导出。

## 1. 先确认六件事

指标口径、数据量、刷新频率、查询范围、响应目标、租户权限。没有容量信息时先给基本架构，说明后续通过代表性负载验证。

## 2. 一条完整链路

业务事件 → 幂等接入/清洗 → PostgreSQL 明细及必要汇总 → Go 查询 API（Redis 缓存）→ Vue 图表和明细。

| 层次 | 核心职责 |
|---|---|
| 数据 | 明确支付/登录粒度、去重、迟到及退款修正 |
| Go API | 鉴权、校验指标维度、超时、有限查询并发 |
| PostgreSQL | 正确聚合、索引、汇总及结果核验 |
| Redis | 复用可接受过期的结果，区分权限与筛选 |
| Vue | 筛选联动、请求竞态、状态和更新时间 |

接口可接收指标 ID、维度 ID、时间范围和筛选值。租户访问范围由服务端认证上下文决定；值参数化，列名/表达式白名单映射，不能直接执行客户端 SQL。

## 3. 三种故障怎样回答

**数字不对**：固定筛选、时区和权限 → 查缓存 → 查 SQL/汇总 → 对源事件。重点看口径不一致、重复、漏数据及迟到。

**查询很慢**：拆连接池等待与 SQL 时间，分析计划；索引/预聚合/缓存优化，并限制查询范围和并发。大量导出异步分批，不占住交互请求。

**部分图失败**：约定部分成功协议，成功图继续展示，失败图可重试；所有结果带相同筛选版本，避免静默混用旧数据。

## 4. 上线验收

小样本手算对账；测试重复事件、退款、空数据和跨租户访问；用代表性数据验证耗时和超时；监控 API P95、错误率、数据库等待和数据延迟，准备回滚。

现有方案持续不满足目标后再评估 OLAP，考虑同步延迟和维护成本。本轮不展开选型细节。

## 两分钟答题顺序

**确认需求 → 指标与模型 → 数据链路 → API/权限 → 性能与页面 → 验证上线。**

项目表达另读[补充准备](补充准备.md)：POS 数据贯通主讲数据，商云前台主讲页面，数字人幂等作为可靠性补充。
