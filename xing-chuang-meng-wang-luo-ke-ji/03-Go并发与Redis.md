# Go 并发、Redis 与消息｜50 分钟

用时：Go 20 分钟，缓存与消息 20 分钟，脱稿复述 10 分钟。

## 1. 并发首先保护资源

goroutine 轻量，但数据库连接和下游容量有限。看板同时发出大量 SQL 时，无限并发只会把压力变成排队、内存增长和超时。

可用固定 worker 或信号量限制执行数量，同时限制等待队列；排队超时就拒绝或取消。**先启动无限 goroutine 再让它们等信号量，仍会堆积 goroutine。** 并发上限应结合数据库容量和压测确定。

GMP：G 是 goroutine，M 是线程，P 提供执行 Go 代码所需的调度资源；GOMAXPROCS 不限制 goroutine 总数。

## 2. 同步与退出

| 手段 | 用途 | 易错点 |
|---|---|---|
| Mutex | 保护共享状态 | 持锁期间做慢 I/O 会放大等待 |
| channel | 任务/结果交接 | 没人接收时可能一直阻塞 |
| WaitGroup | 等待一组任务结束 | 本身不传错误，也不取消任务 |
| context | 传播超时和取消 | 被调用方必须响应 |

请求的 context 应继续传给数据库/HTTP 调用，派生超时后及时调用 cancel 释放资源。取消不是强行杀死 goroutine。[Go context 文档](https://pkg.go.dev/context)

泄漏排查：看 goroutine 数量趋势和堆栈，找无法结束的收发、等待或后台循环。channel 关闭应由明确的所有者负责，通常由发送方在所有发送结束后关闭。

基础追问：普通 map 并发读写需要同步；接口包含动态类型和值，因此装入 nil 指针后接口可能不等于 nil。

## 3. 消费幂等：处理重投，不假设只投一次

推荐设计思路：

1. 以业务事件 ID/版本作为幂等键，数据库唯一约束兜底。
2. 幂等记录和业务变更在同一事务提交，重复事件不重复产生副作用。
3. 提交后 ACK；ACK 失败可能重投，下一次安全跳过已完成事件。

乱序按业务版本判断；失败使用有上限的退避重试，无法处理的消息隔离排查。外部调用不受本地数据库事务保护，需要对方幂等键或额外补偿设计。

联系 POS 项目时，把以上“设计思路”替换成自己的真实实现，不直接说项目采用了该方案。

## 4. 报表缓存

基本流程：读缓存 → 未命中查数据库 → 写缓存；数据修改提交后失效相关缓存，并为失效失败设计重试/补偿。

Key 至少区分租户、有效权限范围/版本、指标版本、时间范围和标准化筛选。缓存命中不等于可以跳过当前权限校验。

| 问题 | 含义 | 常见处理 |
|---|---|---|
| 穿透 | 不存在的数据反复回源 | 参数校验、适当短暂缓存空结果 |
| 击穿 | 热点缓存失效，大量请求回源 | 请求合并、限制回源并发 |
| 雪崩 | 大批缓存同时失效或缓存服务故障 | TTL 抖动、限流、降级 |

缓存允许多旧必须由业务决定，页面展示数据更新时间。单进程请求合并不会自动合并其他实例的请求。

## 5. 分布式锁的边界

获取锁使用唯一持有者标识和有效期；释放时原子比较标识再删除，避免删掉新持有者的锁。租约到期后旧任务仍可能运行，关键写入还需要幂等或资源端版本保护。[Redis 锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

## 自测

用真实项目回答一个问题：消息处理成功但 ACK 失败会怎样？再口述：如何限制看板 SQL 并发？锁过期后旧任务为什么仍危险？

线上排障顺序：先确认影响和发布变更，必要时回滚/限流，再拆应用、数据库、下游耗时，检查 CPU、GC、连接池等待及锁。
