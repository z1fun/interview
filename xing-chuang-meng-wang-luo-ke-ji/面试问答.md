# 面试问答｜17 道核心题

每题按“结论 → 做法 → 一个边界”回答，控制在 30—60 秒。技术方案不代表个人已做过的项目。

## BI 与 PostgreSQL｜70 分钟

### 1. BI 的指标、维度、事实粒度是什么？

指标是收入、付费人数等计算结果；维度是日期、渠道、游戏等分析角度；粒度是一行数据代表什么，例如一笔支付。先定粒度与口径，再写 SQL，避免重复统计。

常用口径，需与产品确认：

- DAU：一天内指定活跃行为的去重用户数。
- ARPU：统计期收入 / 该口径下的用户数；采用活跃用户口径时分母为活跃人数。
- ARPPU：统计期收入 / 付费用户数。
- 次日留存：某日新增用户中，次自然日仍活跃的人数 / 该日新增人数。

**易错点**：统一时区、币种、退款与用户范围；月活不能累加日活，比率不能直接平均，分母为零需单独处理。

### 2. 为什么 JOIN 后金额翻倍？

订单关联多条明细后，一笔订单出现多次，订单金额被重复相加。按正确粒度先聚合再 JOIN，或分开算指标。不能用 SUM(DISTINCT amount) 补救，因为不同订单可能金额相同。

### 3. 手写每天收入最高的三个渠道

练习表：`orders(tenant_id, order_id, channel_id, paid_at timestamptz, amount numeric, status)`；一行一笔订单，同币种，统计已支付毛收入，不含退款修正。

```sql
WITH daily AS (
  SELECT (paid_at AT TIME ZONE 'Asia/Shanghai')::date AS day,
         channel_id, SUM(amount) AS revenue
  FROM orders
  WHERE tenant_id = $1 AND status = 'paid'
    AND paid_at >= $2 AND paid_at < $3
  GROUP BY 1, 2
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY day ORDER BY revenue DESC, channel_id
  ) AS rn
  FROM daily
)
SELECT day, channel_id, revenue
FROM ranked WHERE rn <= 3
ORDER BY day, rn;
```

记住：**先聚合，再排名，最后筛选**。ROW_NUMBER 每天最多三行；要前三个收入档位且保留并列，用仅按收入排序的 DENSE_RANK。

追问速答：GROUP BY 合并行，窗口函数保留输入行；CTE 组织查询，不保证更快。环比用 LAG，但先补日期，且用 NULLIF 防止除零。

练习：读懂后关掉文档手写一遍。示例尚未连接 PostgreSQL 执行。

### 4. PostgreSQL 慢查询如何排查？

固定参数和范围 → 看执行计划 → 找扫描、JOIN、排序瓶颈 → 调整 SQL/索引 → 对比正确性和性能。重点看估算与实际行数差异、循环次数、缓冲访问和排序落盘。EXPLAIN ANALYZE 会实际执行语句。[官方说明](https://www.postgresql.org/docs/current/using-explain.html)

### 5. 联合索引怎么设计？

围绕常用过滤与排序。租户等值、时间范围查询可评估 `(tenant_id, paid_at)`；渠道也是常用等值条件时再评估加入渠道。用实际计划验证收益，同时考虑写入和存储成本。大范围聚合不一定走索引更快。

### 6. 数据多了怎么优化报表？

先优化 SQL 和索引，再考虑汇总表、缓存、限制查询范围；大导出改异步分批。持续的大范围分析瓶颈再评估 OLAP，并考虑同步延迟和维护成本。不要一上来就换数据库。

## Go、Redis 与消息｜50 分钟

### 7. goroutine 为什么要限并发？

数据库连接、CPU 和下游容量有限，无限并发会让排队和内存失控。用有限 worker/信号量限制执行数量，同时限制等待队列；超载拒绝或转异步，等待也要能取消。

GMP 速记：G 是 goroutine，M 是线程，P 是执行 Go 代码所需的调度资源；GOMAXPROCS 不是 goroutine 上限。

### 8. channel、锁和 context 怎么用？

channel 协调任务和结果，锁保护共享状态；普通 map 并发读写要同步。context 传播超时/取消，但工作代码必须响应。阻塞收发没有退出路径容易泄漏，可查看 goroutine profile 定位。[Go 取消机制示例](https://go.dev/blog/pipelines)

追问：接口包含动态类型和值，装入 nil 指针后接口本身可能不为 nil。

### 9. 消息重复消费怎么办？

用业务事件 ID/版本作为幂等键，数据库唯一约束兜底；幂等记录与业务写入放同一事务，提交成功再 ACK。提交后 ACK 失败可能重投，所以必须支持重复处理。乱序按业务版本判断，迟到数据修正对应汇总。

这是一种回答方案，POS 项目的实际实现要按本人经历说明。

### 10. 报表缓存如何设计？

Key 包含租户、有效权限范围/版本、指标、规范化筛选和时间范围，不能只用报表 ID。设置 TTL、更新后失效；热点请求合并，限制回源并发。权限仍需校验，页面展示数据更新时间，失效失败要能补偿。

### 11. Redis 锁如何安全释放？

获取锁设置唯一标识与过期时间；释放时原子比较标识再删除，避免误删别人的锁。锁过期后旧任务仍可能执行，关键写入还需幂等或资源端版本保护。[Redis 官方说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 12. 接口上线后突然变慢，怎么查？

先看影响范围和近期发布，必要时回滚/限流；再拆分应用、数据库、下游耗时，检查 CPU、GC、连接池等待、锁和慢查询。用监控和 profile 定位，不盲目扩容或加重试。

## Vue 与看板｜40 分钟

### 13. computed、watch、Pinia 分别做什么？

computed 做派生值，watch 做变化后的副作用，如重新请求数据。Pinia 放跨组件共享状态，局部 loading 不必全局化；切换租户和退出时清理相关状态。[Vue 侦听器说明](https://vuejs.org/guide/essentials/watchers.html)

补充：ref 可包装基础值或对象，脚本通过 `.value` 访问；reactive 用于对象，直接解构基础类型属性可能失去响应式关联。

### 14. 快速切换筛选，旧请求覆盖新结果怎么办？

取消旧请求，并用递增请求编号，只允许当前编号更新数据和 loading。防抖只减少次数，不能保证返回顺序。多个图表也要对应同一份筛选条件。

### 15. ECharts 页面越用越卡怎么办？

检查重复初始化和未清理监听；复用实例更新数据，容器变化时 resize，卸载时 dispose。大量点位先做服务端聚合，大表格用分页或虚拟滚动。

### 16. Vite 要注意什么？

区分开发代理与生产路由配置；本地能调通不代表线上鉴权和跨域正确。交付到浏览器的配置都是可见的，数据库密码等秘密只能留在服务端。

### 17. 如何设计一个游戏运营看板？

按以下顺序回答，约两分钟：

1. **需求**：指标口径、时区、实时性、数据量、租户权限。
2. **数据**：事件去重 → 明细 → 必要汇总，明确退款和迟到修正。
3. **后端**：Go 接口 + PostgreSQL 查询；指标/列名白名单、值参数化，服务端校验权限。
4. **性能**：Redis 缓存、超时、有限并发，昂贵导出异步化。
5. **页面**：Vue 筛选、图表、明细；处理竞态、空数据、错误和更新时间。
6. **验证**：小样本手算对账、租户隔离、代表性数据性能、上线监控与回滚。

记住三个检查点：**数字算对、权限隔离、查询受控**。
