## 3.1 🥇 王牌：LoveSpouse 数字人

### 3.1.1 90 秒标准讲述 🎤

> **背景**：这是一个面向成人智能玩具配套 App 的虚拟角色陪伴系统，用户可以创建和选择虚拟角色，进行多语言聊天、剧情互动、实时语音通话，还有一些付费的媒体内容解锁。技术栈是 Go + Gin + GORM + MySQL + Redis，实时语音用的 Gemini Live，消息走腾讯 IM。
>
> **我的职责**：我负责数字人后端的整条对话链路，具体包括四块——**对话流程编排、分层记忆系统、实时语音接入、计费和跨实例控制**。
>
> **难点我讲三个：**
>
> **第一个是记忆。** 大模型的上下文窗口有限，但陪伴类产品要求角色能记住几个月前聊过的东西。我做了一套**分层记忆**：最近的对话原文保留，更早的按会话做摘要，再往上是长期摘要，最顶层是「稳定事实」——比如用户的称呼、喜好、重要经历这种不该忘的信息。每层有不同的生成时机和检索策略，拼装 Prompt 的时候按预算往里塞。
>
> **第二个是实时语音的跨实例控制。** 用户打语音电话时，WebSocket 连接可能落在任意一个实例上，但通话状态需要全局唯一——不能出现两个实例同时给一个用户推语音。我用 Redis 做了分布式状态和抢占，保证同一时刻只有一个实例持有通话。
>
> **第三个是计费。** 语音通话是按时长扣金币的，这就必须保证**不多扣也不漏扣**。我在计费的各个环节都做了幂等，扣费记录带唯一业务 ID，同时有对账机制兜底。
>
> **收获**：这套东西做下来，我对「**怎么把大模型能力做成一个稳定的线上服务**」理解比较深了——不只是调 API，还有上下文管理、状态一致性、成本控制、降级这些工程问题。

### 3.1.2 必被追问的 8 个问题 ⭐

**Q1：分层记忆为什么分四层？摘要什么时候生成？**

> 分层的本质是**在有限的 Token 预算里放最有价值的信息**。
> - **近期对话**：原文保留，保证多轮对话的连贯性和语气一致——摘要会丢细节，而陪伴类产品对细节很敏感。
> - **会话摘要**：一次会话结束时生成，压缩掉闲聊，保留事件。
> - **长期摘要**：定期把多个会话摘要再往上聚合，比如每周或每 N 次会话。
> - **稳定事实**：这一层是**结构化**的，不是摘要——比如"用户叫小明""养了一只猫""在深圳工作"。它由模型在对话中抽取出来，单独存表，每次拼 Prompt 都带上，**不受摘要漂移影响**。
>
> **生成时机**：会话结束或达到轮次阈值时异步生成，不阻塞用户请求。**检索策略**：按时间倒序 + 关键词/向量召回，在总 Token 预算内从低层往高层填。

> 💡 **如果追问"摘要怎么做不丢信息"**：摘要的 Prompt 我会明确要求保留「人物、事件、情绪、承诺」四类信息，并且**摘要是有损的，所以关键事实走结构化抽取那条路**，两条路互补。

**Q2：跨实例通话控制具体怎么做的？**

> 通话是有状态的，但服务是无状态的，所以状态必须外置。我用 **Redis 存通话会话状态**，key 是用户 ID，value 是通话信息 + 当前持有的实例 ID，带 TTL。
> 用户发起通话时**用 SETNX 抢占**，抢到的实例负责建立和上游的语音连接；抢不到说明已有通话，走「加入」逻辑。
> 实例挂了的话，TTL 到期后 key 自动释放，用户重连就能重新抢占——**用 TTL 换掉了复杂的心跳和故障检测**。
> 通话中的状态（比如已用时长）定期回写 Redis，避免实例崩溃时丢太多。

> 💡 **追问"两个实例同时抢怎么办"**：SETNX 是原子的，只有一个能成功。**真正的风险是脑裂**——旧实例以为自己还持有，但 TTL 已经过期被新实例抢走了。所以旧实例每次写状态都要校验自己的持有者标识，写不进去就主动断开自己。

**Q3：语音是按什么计费的？怎么保证不超扣不多扣？**

> 按**通话时长**扣金币。做法是：通话建立时先**预扣**一个最小单位或者做额度校验，通话过程中定期按心跳上报时长累加扣费，结束时做**最终结算**（补扣或退还）。
> **幂等**上，每次扣费都带一个唯一业务 ID（通话 ID + 序号），数据库加唯一索引，重复提交直接被挡掉。
> **兜底**上，每天有一轮对账，把计费流水和通话记录做比对，不一致的进人工核查队列。

> ⚠️ **注意**：如果你实际没做到这个程度，就诚实说「**我们的实现是** XXX，我理解更严谨的做法是 YYY」。**不要编造细节**——这类问题面试官一追问实现细节就露馅。

**Q4：Gemini Live 断线了怎么办？**

> 分几层：
> - **客户端侧**：检测到断线后自动重连，带上会话 ID 恢复上下文。
> - **服务侧**：维护会话状态，重连时把最近的对话上下文重新注入。
> - **兜底**：如果在超时时间内恢复不了，**降级成文本对话**，先让用户能继续用，而不是直接报错。
>
> 实时语音这类长连接，**断线不是异常而是常态**，必须按常态设计。

**Q5：意图识别是怎么做的？**

> **分场景**：简单意图（闲聊、查询角色信息）用规则和小模型就够了，成本和延迟都低；复杂意图（付费推荐、剧情分支、情绪判断）走大模型 + 结构化输出。
> **关键是用结构化输出把模型的判断变成可靠的代码分支**——让模型返回 JSON，指定 schema，解析失败就重试或走默认分支，**绝不让模型直接决定业务流程**。

**Q6：为什么用 Gemini 不用国内模型？**

> 主要是产品面向海外用户，多语言和语音能力是硬需求。另外我们没有自建推理的想法，走 API 更快。
> **如果追问"如果让你换成国产模型或私有化"**：瓶颈主要在语音链路的实时性——私有化要考虑推理延迟和并发吞吐，如果量不大，vLLM 起一个实例够用；量大就要做多实例 + 负载均衡，以及流式首包延迟的优化。

> 💡 **这题是陷阱**：问"为什么用 X"时，**真正在问的是"你有没有做过技术选型的思考"**。答"选型依据 + 转换成本"就够了，不要贬低任何一方。

**Q7：并发量多大？**

> ⚠️ **备考时填上真实数字**。如果没有准确数据，用这个口径：
> 「**我没有拿过全量的准确数字，我说我确定的部分：我们当时的日活是【】量级，同时在线语音通话峰值大概在【】路。**」——**给一个你有把握的量级，比编一个漂亮数字安全。**

**Q8：如果让你重做，你会改什么？**

> **这题是送分题，也是加分题**——面试官想看你的反思能力。准备好一个真实答案，比如：
> 「记忆这块我当初四层是写死的，现在我会做成**可配置的**，因为不同角色的记忆需求不一样；另外摘要生成是串行的，我会改成**异步任务 + 失败重试**，避免影响主链路。」

## 3.2 🥈 第二张：AI 漏洞研判系统

### 3.2.1 90 秒标准讲述 🎤

> **背景**：这是面向 SRC 运营的漏洞审核平台。传统流程里，安全研究员提交漏洞报告后要人工判断信息是否完整、复现 POC、定级定价、再复测，非常耗人力。我们这个系统是用多 Agent 把这条链路自动化，同时保留人工审批介入。
>
> **我的职责**：我负责用 **LangGraph 搭多 Agent 工作流**，设计信息完整性评估和漏洞定级定价这两个节点的 Prompt；另外用 FastAPI 做专家经验知识库，底层是 **PostgreSQL + pgvector 的 RAG 检索链路**；还对接了飞书审批卡片，在自动化流程里接入人工审核。
>
> **难点讲三个：**
>
> **第一个是多 Agent 的编排**。我没有做成自由对话式的 Agent，而是做成**有向图的状态机**——每个节点是一个明确的处理步骤（评估完整性、验证 POC、定级定价），节点之间通过共享状态传递数据，条件边决定下一步走向哪。**好处是流程可控、可观测、可复现**，这对审核类业务很重要——同一个漏洞报告，今天跑和明天跑不应该得出完全不同的结论。
>
> **第二个是 Prompt 和输出稳定性**。定级定价是核心输出，我用结构化输出约束模型，指定 JSON schema，包含漏洞等级、评分、定价建议和推理依据。同时把专家经验通过 RAG 检索出来塞进 Prompt 作为参考——**让模型基于我们自己的历史案例判断，而不是凭它自己的通用认知**。
>
> **第三个是人工介入**。全自动处理风险太高，所以关键节点会通过飞书审批卡片把决策权交给人，人确认后流程继续。**这里的关键是流程的可中断和可恢复**——审批可能等几小时，状态必须持久化。
>
> **收获**：这个项目让我理解了**做 AI 应用最难的不是调模型，而是让整个流程可靠、可观测、可干预**。

### 3.2.2 必被追问的 6 个问题

**Q1：为什么用 LangGraph 而不是自己写状态机？**

> 主要三个原因：**一是** LangGraph 原生支持状态图和条件路由，比自己写状态机省事；**二是**它有 checkpointer，能把流程状态持久化，这对"审批可能等几小时"的场景是刚需；**三是**人工介入（human-in-the-loop）是它的原生能力。
> **如果追问"那你觉得它的缺点是什么"**：抽象层比较厚，调试的时候要理解它的状态合并机制，另外版本升级有破坏性变更。**如果流程简单，我其实更倾向于自己写状态机——依赖更少，可控性更强。**

> 💡 **这题是这次面试的高频题**，因为它能同时考察「技术选型能力」和「批判性思维」。**一定要准备"缺点"那一半。**

**Q2：多 Agent 是流水线还是对话式协作？**

> 是**流水线式的图结构**，不是自由对话。原因：审核业务需要**确定性**——同一个输入应该得到可复现的输出，自由对话式的 Agent 每次跑结果都可能不一样，这在审核场景不可接受。
> 我们的节点有明确的输入输出契约，共享状态里存中间结果，**可观测性好**——出问题能定位到具体是哪个节点。

**Q3：RAG 的检索效果怎么保证？**

> 几层：
> - **切分**：按语义切，不是按固定长度硬切，保证每块信息完整。
> - **向量化**：用 embedding 模型，pgvector 建索引。
> - **检索**：先向量召回 Top-K，再用关键词做混合检索补充——**纯向量检索对专有名词和漏洞编号召回很差**。
> - **Rerank**：召回后做重排，把最相关的放前面。
> - **Prompt 里加引用要求**：让模型基于检索到的内容回答，检索不到就明确说"无历史参考"，**不要让它编**。

**Q4：怎么防止模型胡说（幻觉）？**

> **分几层防**：
> - **输入侧**：Prompt 里明确"基于给定材料判断，没有依据就说没有依据"。
> - **输出侧**：结构化输出 + schema 校验，格式不对直接重试。
> - **流程侧**：关键结论（定级定价）走人工审批，**模型只是给建议，最终决策权在人**。
> - **兜底**：记录每次调用的输入输出和依据，出问题可以回溯。
>
> **我的观点是：在审核这类高风险场景，不要指望 Prompt 消除幻觉，而是要在流程设计上让人能兜住。**

**Q5：人工审批怎么接入的？状态怎么持久化？**

> 流程走到审批节点时，调飞书开放接口发一张交互卡片，然后**流程挂起**，状态存到数据库（LangGraph 的 checkpointer）。用户在飞书点按钮后，飞书回调我们的接口，我们根据回调里的 ID 恢复对应的流程继续执行。
> **关键点是**：回调可能重复、可能乱序、可能用户不点——所以回调要**幂等**，还要有**超时兜底**（超时就默认走保守分支或转人工）。

**Q6：这个项目有什么量化结果？**

> ⚠️ **备考时填**。没有硬数据就用这个口径：
> 「**坦白说我们没做严格的 A/B 量化。可观测的提升是：过去一份报告从提交到定级平均要 X 小时，系统上线后大部分能自动给出结论，人工只需要处理系统标记为不确定的那部分。**」

# 第 4 部分：技术速答（25 分钟）

> 这一部分**不看全，重点看 4.1 和 4.2**——这两节直接对应 JD 的第 1、2 条职责，也是你区别于普通 Go 候选人的地方。

## 4.1 ⭐⭐⭐ 大模型 API 对接（JD 职责第 2 条，必考）

> JD 原文：「对接大模型/多模态/检测模型 API，完成**鉴权、限流、重试、结果落库与服务封装**」——**这五个词就是出题范围**，逐个准备。

### 4.1.1 鉴权

**要做到什么**：API Key 不能硬编码、不能进日志、支持多租户多 Key、能轮换。

> **答法**：密钥统一走配置中心或环境变量注入，代码里只拿引用。多租户场景下每个租户可能有自己的 Key 或配额，我在数据库里存租户和 Key 的映射，调用时按租户取。**Key 绝对不能落到日志里**——这需要专门处理，比如日志中间件里对 Authorization 头做脱敏。
>
> 另外出网的请求统一走一个 Client，方便做统一鉴权、统一埋点、统一超时。

> 💡 **加分句**：「如果是私有化部署或者内网模型服务，鉴权就变成内网网关的事了，业务侧只认网关地址——**这样模型换了业务代码不用动**。」

### 4.1.2 限流 ⭐

**三层限流，答全就是高分：**

> **第一层是调用方的自我保护**——用信号量或者令牌桶限制自己对上游的并发，防止把上游打挂。
> **第二层是上游 429 的响应处理**——收到 429 不能傻等，要**退避重试**，同时把这个信息反馈给限流器，动态降低自己的发送速率。
> **第三层是业务侧的配额**——按租户或用户限，这是产品需求，比如免费用户每分钟几次。
>
> 实现上我用 Redis 做分布式限流（令牌桶或滑动窗口），本地再加一层单实例的限流兜底，**因为 Redis 挂了不能导致限流完全失效**。

### 4.1.3 重试 ⭐

**关键在"哪些错误该重试"，这是区分度所在：**

> **可重试**：网络超时、连接失败、5xx、429。
> **不可重试**：400（请求本身有问题，重试还是一样）、401/403（鉴权问题）、**内容审核拒绝**（重试无意义）。
>
> 策略上：**指数退避 + 抖动**，比如 1s、2s、4s 加随机抖动，避免多个请求同时重试形成惊群。重试次数控制在 2-3 次，总耗时不能超过上游调用的超时预算。
>
> **还有一个坑是幂等**——重试的请求必须能安全重复。如果模型调用有副作用（比如已经计费），就要带幂等 ID。

> 💡 **流式场景的重试是特殊难点**（主动讲出来是加分项）：
> 「**流式请求重试要小心**——如果已经开始往客户端推数据了才发现上游断，这时候重试会导致客户端收到重复内容。我们的做法是：**首包之前失败可以透明重试，首包之后失败就不能重试了**，只能把错误通过流里的特殊事件告诉客户端，或者降级到备用模型重开。」

### 4.1.4 结果落库

> 每次模型调用我都会记一条调用日志：**租户、模型、Prompt 版本、输入输出 Token 数、耗时、状态、错误信息**。
> 几个用途：**成本核算**（按 Token 计费）、**问题排查**（用户投诉时能查到当时到底喂了什么）、**效果分析**（改 Prompt 前后对比）。
>
> **注意两点**：一是**异步落库**，不要阻塞主链路，一般走消息队列或者异步写；二是**脱敏**，用户隐私和密钥不进日志。

### 4.1.5 服务封装 ⭐⭐（JD 明确要求，重点答）

**这题问的是"你怎么设计一个模型调用层"，答好直接拉满：**

> 我的做法是**定义一个统一的 Provider 接口**，把不同模型的差异收敛在适配器里：
>
> ```
> type LLMProvider interface {
>     Chat(ctx, req) (resp, error)
>     ChatStream(ctx, req) (<-chan Chunk, error)
> }
> ```
>
> 上层业务只依赖这个接口，具体是 Gemini、OpenAI 还是私有化的 vLLM，在配置里选。**这样做的好处是：换模型、加模型、做灰度、做降级，业务代码都不用改。**
>
> 接口之上再包一层**统一的能力层**：限流、重试、超时、日志、计费、降级，这层是横切的，用中间件或者装饰器的方式组装。
>
> **降级策略**：主模型不可用时切备用模型，或者降低能力（比如从大模型切到小模型，或者从实时语音降级到文本）。降级要有开关，能人工介入。

## 4.2 ⭐⭐⭐ Prompt 编排与模型调用链路（JD 职责第 3 条，必考）

> JD 原文：「设计并实现 **Prompt 编排与模型调用链路**（**上下文管理、工具调用、结构化输出**）」＋任职要求第 5 条「**角色设定、Few-shot、结构化输出、流式响应**；了解**超时、截断、限流**」——**这些词就是题库**。

### 4.2.1 上下文管理 ⭐

> **核心问题**：上下文窗口有限，但对话可能很长，还要塞知识库和系统提示。
>
> **我的做法是按 Token 预算分配**：系统提示（角色设定）固定占一块，检索到的知识占一块，剩余留给对话历史。对话历史放不下时，**从最旧的开始压缩**——先摘要，摘要还放不下就丢。
>
> **优先级**：稳定事实（用户画像）> 系统提示 > 近期对话 > 长期摘要 > 更早的对话。**因为陪伴类产品里，用户最不能忍的是"你忘了我是谁"。**
>
> **实操细节**：Token 数是**估算**的，不是精确值——一般按字符数或词数估，留 10-20% 的安全余量，**因为超限请求会被上游直接拒绝**。

### 4.2.2 工具调用（Function Calling）⭐

> **流程**：把工具的 schema 一起发给模型 → 模型返回要调用的工具和参数 → **后端校验参数并真正执行** → 把结果作为一条消息回灌给模型 → 模型生成最终回复。
>
> **几个关键点**：
> - **参数必须校验**：模型给的参数不可信，要当成外部输入来校验，尤其是会改数据的工具。
> - **执行要幂等 + 超时**：工具执行可能失败，失败要把错误信息回灌给模型，让它自己决定重试还是换方案。
> - **要有轮次限制**：防止模型陷入工具调用的死循环，一般设最多 N 轮。
> - **权限控制**：不是所有用户都能调所有工具，工具列表要按用户和场景动态生成。

### 4.2.3 结构化输出 ⭐

> **做法**：用 JSON Schema 约束输出格式，能走原生 structured output 就走原生（更可靠），不行就在 Prompt 里给 schema 和示例，再用解析器兜。
>
> **容错很重要**：模型偶尔会输出带 markdown 代码块包裹的 JSON、或者多一段解释文字。所以要**做容错解析**——剥掉代码块标记、提取第一个完整 JSON 对象。
>
> **解析失败怎么办**：一次重试（把错误信息一起喂回去让它纠正），还失败就走默认分支或者降级。**绝不能让解析失败直接抛异常给用户。**

### 4.2.4 流式响应（SSE）⭐

> **为什么流式**：大模型首包延迟可能好几秒，流式能让用户**立刻看到字在往外蹦**，体感快很多。
>
> **实现**：HTTP SSE，`Content-Type: text/event-stream`，服务端持续往连接里写 event。Go 里需要注意 **flusher**——写完要主动 flush，否则会被缓冲住，用户看到的还是"卡住然后一次性出全文"。
>
> **几个坑**：
> - **代理和网关可能缓冲**：Nginx 要关掉 buffering，否则流式失效。
> - **客户端断开**：要监听 `ctx.Done()`，用户关了页面就及时取消上游请求，**不然白烧 Token**。
> - **首包之后不能重试**（见 4.1.3）。
> - **结束标记**：要有明确的结束事件，客户端才知道是正常结束还是断了。

### 4.2.5 超时与截断

> **超时分三层**：连接超时（建连）、首包超时（TTFB，等第一个 token）、总超时（整个请求）。**流式场景下总超时不能设太短**，因为生成长文本本来就要久，一般靠首包超时 + 空闲超时来兜。
>
> **截断**：输入侧是上下文超限（靠预算管理解决），输出侧是 `max_tokens`——要注意**输出被截断时返回的 JSON 是不完整的**，解析会失败，所以要判断结束原因（finish_reason），是长度截断的话要能识别并处理。

## 4.3 ⭐ 多模态 / 检测模型（对口宠智灵业务）

> **这题你大概率会被问**，因为公司做宠物视觉识别。**核心是讲清它和文本 LLM 的不同：**

> **文本调用是同步的，多模态检测往往是异步的**：
> - **图片/视频太大**，一般不直接走 API body，而是**先传到对象存储，再把 URL 给模型服务**。
> - **检测类任务耗时长**，常见的模式是**提交任务 → 返回 task_id → 回调或轮询拿结果**。
>
> **所以后端要处理的问题变成了**：
> - **回调的幂等**——回调可能重复、可能乱序，要用 task_id 做幂等键。
> - **任务状态机**：待处理 / 处理中 / 成功 / 失败 / 超时，要能查、能重试、能取消。
> - **超时兜底**：回调可能永远不来，所以要有**轮询兜底和超时标记**，不能一直挂着。
> - **结果落库**：检测结果（比如品种、置信度、检测框）结构化存储，方便后续检索和统计。
>
> **如果追问"检测模型和 LLM 怎么配合"**（宠智灵问诊的真实场景）：
> 「典型是**检测模型先出结构化结果**（比如识别出宠物品种、皮肤异常区域），**再把这些结果作为上下文喂给 LLM 生成问诊建议**。这样 LLM 不用处理图像，只做推理和表达，职责清晰，成本也低。」

## 4.4 ⭐ 私有化部署：Ollama / vLLM / 内网网关（JD 第 6 条）

> **这题你没做过，策略是：承认没落地过，但把原理和选型讲清楚。**

**四种方案对比（能说出这张表就够）：**

| 方案 | 定位 | 特点 |
| --- | --- | --- |
| **Ollama** | 开发/小规模 | 部署极简，一条命令拉起。适合本地开发和量小的场景。**性能和并发能力一般**，不适合生产高并发 |
| **vLLM** | 生产推理服务 | **吞吐量高**，是私有化部署的主流选择。核心是 PagedAttention 和连续批处理 |
| **其他本地推理**（llama.cpp / TensorRT-LLM 等） | 特定场景 | llama.cpp 适合 CPU/边缘；TensorRT-LLM 适合 NVIDIA 卡上榨性能 |
| **内网网关** | 统一出口 | 业务不直连模型，走一层网关做鉴权、限流、审计、路由。**国内常用 one-api / new-api 这类开源方案**，或者自研 |

**vLLM 为什么快（说这两点就够）：**

> **一是 PagedAttention**：传统做法给每个请求预分配一整块连续的 KV Cache 显存，浪费严重。PagedAttention 借鉴操作系统的**分页**思想，把 KV Cache 切成固定大小的块，按需分配、可以不连续，**显存利用率大幅提升，能塞下更多并发请求**。
>
> **二是连续批处理（Continuous Batching）**：传统批处理要等一个 batch 里所有请求都生成完才能接下一批，短请求要等长请求。连续批处理是**每生成一个 token 就重新组批**，完成的请求立刻退出、新请求立刻进来，**GPU 利用率大幅提高**。

**选型时要考虑什么（这题是送分的思考题）：**

> - **数据合规**：数据不能出内网 → 必须私有化。
> - **成本**：调用量大的话，自建比按 Token 付费便宜；量小反而自建更贵（要占卡）。
> - **延迟**：内网部署省掉公网往返，首包更快。
> - **运维成本**：私有化要自己管显存、管并发、管扩缩容、管模型版本，**这是真实成本**。
> - **模型能力**：开源模型和头部闭源模型还有差距，要看业务能不能接受。
>
> **我的判断**：**先调 API 快速验证业务，量起来或合规要求硬的时候再私有化**。如果是混合模式，可以在统一 Provider 接口下同时挂 API 和私有化实例，按租户或场景路由。

## 4.5 Go 并发速答（你是 5 年 Go，扫读即可）

- **GMP 模型**：G 是 goroutine，M 是内核线程，P 是处理器（携带本地运行队列）。**P 的数量由 `GOMAXPROCS` 决定**，M 必须绑定 P 才能执行 G。**核心价值是 work-stealing**：P 的本地队列空了会去偷别的 P 的，也支持从全局队列拿。
- **为什么要有 P**：如果没有 P，每个 M 都要自己去抢全局队列，锁竞争严重。P 提供了**无锁的本地队列**，绝大多数调度在本地完成。
- **channel 底层**：有缓冲的是一个**环形队列 + 两个等待队列**（sendq / recvq）。发送/接收时如果对面有等待者，直接把数据交给它并唤醒（**handoff，避免了一次调度**）。
- **`select`**：随机选一个就绪的 case，**这是刻意设计**，避免某个 case 饿死。
- **`sync.Mutex`**：正常模式是自旋 + 排队，**饥饿模式**下（等待超过 1ms）直接把锁交给队首，保证公平。
- **`context`**：树形传播，父取消子跟着取消。**`ctx.Done()` 一定要监听**，这是 Go 里做超时和取消的标准姿势——**尤其是调大模型 API 的时候，客户端断开要立刻取消上游请求**。
- **内存逃逸**：变量被外部引用、或者大小在编译期不确定时，会从栈逃到堆。**`go build -gcflags=-m` 可以看逃逸分析**。
- **pprof**：`net/http/pprof` 挂上，看 CPU、heap、goroutine。**goroutine 泄漏是 Go 服务最常见的线上问题**——一般是 channel 阻塞或者忘了取消 context。

## 4.6 MySQL / Redis 速答

**MySQL：**
- **索引**：B+ 树，非叶子节点只存键、叶子节点存数据且用链表相连 → **树矮（3-4 层就能存千万级）+ 范围查询快**。
- **最左前缀**：联合索引 (a,b,c)，`where b=1` 用不上索引。**范围查询后面的列会失效**。
- **事务隔离**：读未提交 / 读已提交 / 可重复读（**MySQL 默认**）/ 串行化。RR 下 MVCC + 间隙锁解决了大部分幻读。
- **MVCC**：每行有隐藏的版本信息（trx_id、rollback pointer），通过 undo log 找回历史版本。**RC 和 RR 的区别就在 ReadView 的生成时机**——RC 每次查询都生成，RR 只在第一次查询生成。
- **慢查询**：开 slow log，`explain` 看执行计划，重点看 **type（避免 ALL 全表扫描）**、**key（实际用的索引）**、**rows（扫描行数）**。
- **分库分表**：**先优化 SQL 和索引，再考虑读写分离，最后才分库分表**——分表会带来跨表查询、分布式事务、全局 ID 一堆问题。

**Redis：**
- **缓存三问**：**穿透**（查不存在的数据）→ 布隆过滤器 / 空值缓存；**击穿**（热点 key 过期）→ 互斥锁重建 / 逻辑过期；**雪崩**（大量 key 同时过期）→ 过期时间加随机。
- **持久化**：RDB 快照（快、可能丢数据）vs AOF 日志（安全、文件大）。**生产一般混合用**。
- **分布式锁**：`SET key value NX EX`，**value 放唯一标识**（删锁时要校验是自己的，否则可能删了别人的锁）。生产环境更推荐 Redisson 看门狗续期，或者直接用 Redis 官方建议的 Redlock 替代方案。
- **大 key / 热 key**：大 key 会阻塞（比如 `keys *`、`del` 大集合），要拆；热 key 要加本地缓存或多副本。

## 4.7 Kafka / RabbitMQ / MQTT（**缺口，重点看**）

**Kafka vs RabbitMQ（必答）：**

| | Kafka | RabbitMQ |
| --- | --- | --- |
| 模型 | **分布式日志**，消息按 partition 追加，消费靠 offset | **消息队列**，broker 负责投递和删除 |
| 吞吐 | 极高（百万级/秒） | 万级/秒 |
| 顺序性 | **partition 内有序** | 单队列有序 |
| 消费 | **拉模式**，消费组 + offset，**能回溯重放** | 推模式为主，消费完删除 |
| 适用 | 日志、埋点、流处理、大数据管道 | 业务解耦、任务分发、复杂路由 |

> **你的口径**：「**生产上我用 RabbitMQ 做过 POS 数据中台的业务数据消费，Kafka 我没在生产用过，但原理我理解——它的核心是分区和消费组，partition 内保证顺序，消费组内一个 partition 只被一个消费者消费，所以扩容消费者最大到 partition 数。另外 offset 可以重置，所以能重放历史数据，这是它和传统 MQ 最大的区别。**」

**MQTT（IoT 场景必问）：**

> **为什么 IoT 用 MQTT 不用 HTTP**：设备数量可能几十万，HTTP 短连接的开销撑不住；MQTT 是**长连接 + 发布订阅**，开销极小，**非常适合弱网和低功耗设备**。
>
> **QoS 三档**：0 = 最多一次（可能丢，不管），1 = 至少一次（**可能重复，所以消费侧必须幂等**），2 = 恰好一次（四次握手，开销最大）。
>
> **遗嘱消息（LWT）**：设备可以预先注册一条遗嘱，**设备异常断线时 broker 自动发布**——这是做**设备离线检测**的标准做法。
>
> **Topic 设计**：用 `/` 分层，比如 `device/{productId}/{deviceId}/status`，支持通配符 `+`（单层）和 `#`（多层）。
>
> **落地要点**：设备认证（一机一密）、连接数限制、离线消息、消息积压监控。**如果追问"设备离线怎么判断"**：靠心跳超时 + 遗嘱消息双重判定，**因为心跳超时判定有延迟，遗嘱是即时的**。

## 4.8 幂等 / 降级 / 限流（JD 职责第 5 条，必考）

**幂等——JD 明确提了，一定要答得漂亮：**

> **幂等的本质是"同一个请求执行多次，结果和执行一次一样"**。几个层次：
> - **数据库唯一索引**：最可靠的一道防线，用业务唯一键（订单号、消息 ID）建唯一索引，重复插入直接失败。
> - **状态机**：状态只能单向流转，比如订单从"待支付"到"已支付"，重复支付请求会因为状态不匹配被拒绝。
> - **幂等表 / 去重表**：记录已处理过的请求 ID，处理前先查。
> - **分布式锁**：并发场景下先用锁串行化，再查幂等表。
>
> **我的实践**：LoveSpouse 里对接腾讯 IM 消息和金币计费都做了幂等——**IM 消息会重复推送，计费不能重复扣**，都用业务唯一 ID + 唯一索引兜底。

**降级：**
> **降级是"牺牲非核心能力，保住核心链路"**。做法：预先定义降级开关（配置中心下发，能热更新），出问题手动或自动触发。
> **例子**：大模型不可用时，语音降级成文本、AI 回复降级成预设话术、推荐降级成热门兜底。**关键是降级要提前设计好，不能等出事现想。**

**限流：**
> - **算法**：计数器（简单但有临界问题）、**滑动窗口**（平滑）、**令牌桶**（允许突发）、漏桶（恒定速率）。
> - **位置**：网关层做全局限流，业务层做细粒度限流，**两层都要有**。
> - **分布式限流**：Redis + Lua 保证原子性。
> - **被限流了怎么办**：返回明确的状态码和重试建议，**不要直接报 500**。

4. **「咱们在模型这块是调用云端 API 还是有私有化部署的规划？」**
   → 直接对应 JD 第 6 条。**回答能透露他们的技术成熟度。**

**🥈 加分——展示你的思考：**

## 6.2 薪资口径（**练手为主，20K+ 可考虑**）

**先说清楚你的处境：**
- 岗位 12-18K，你目标 25-30K，**落差大**。
- 但你是**超配**的（JD 要 3 年，你有 5 年，而且 AI 应用经验比 JD 要求更深）。
- 定位：**练手 + 探行情**。给到 20K+ 且业务对口可以考虑；给不到就轻松结束，不用勉强。

**被问期望薪资怎么答：**

> ### 🎤 标准答法
> 「我目前的期望是 **25K 左右**，不过**我更看重岗位和业务方向是否匹配**。
> 我看咱们这边是做 AI 数字人和多模态方向，这块正好是我最近两年在做的，**所以薪资上是有弹性的**。
> **我想了解一下，咱们这个岗位的薪资区间有上浮空间吗？**」

**这段的设计意图：**
- **先报数字（25K）**：守住锚点。不报数字会让对方按最低给。
- **再说弹性**：给台阶，避免因为数字直接谈崩。
- **把球踢回去**：**「有上浮空间吗」是关键句**——让他们先亮牌。这一步能让你立刻判断这是不是认真的机会。

**根据对方回答的应对：**

| 对方反应 | 你的应对 | 判断 |
| --- | --- | --- |
| 「我们预算就是 12-18K」 | 「**那我理解这个岗位的定位和我目前的期望有差距。不过今天聊下来我对咱们的业务挺感兴趣的，我想多了解一下再做判断。**」 | 继续聊，当练手，**最后大概率不去** |
| 「可以谈，最高到 20K」 | 「**20K 可以接受，但我希望确认一下职责范围**」——顺便把反问那几条问全 | **认真评估**，看业务是否真对口、团队是否有 mentor |
| 「你期望多少？」（不亮牌） | 坚持先给区间：「**我期望 25K 左右，但具体可以结合岗位职责和咱们的薪酬结构再谈。**」 | 不要被套出底线 |
| 「你上一份多少？」 | 「**上一份是 XX，不过我这次看机会更看重方向和成长。**」 | 如实说，**但立刻把话题拉回方向** |

**⚠️ 三个禁忌：**
1. ❌ **不要报一个低于你真实预期的数字然后心里不甘** —— 报了就是你的承诺。
2. ❌ **不要因为对方压价就自我怀疑** —— 12-18K 是他们的预算，不是你的市场价。
3. ❌ **不要在面试一开始就谈薪资** —— 等对方问，或者放到反问环节。

## 6.3 收尾

> 「**今天聊得挺有收获的，特别是【聊到的某个具体点】。我回去会把今天提到的【某个技术点】再深入看一下。后续如果有进展，随时联系我。**」

**收尾的三个动作：**
1. **提一个你今天听到的具体内容** —— 证明你在认真听，不是背稿。
2. **表达持续兴趣但不卑微** —— 你在评估他们，不是求 offer。
3. **确认后续流程** —— 「大概什么时候会有反馈？」
