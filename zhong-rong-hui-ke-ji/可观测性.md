## 一、可观测性三大支柱

```
┌──────────────────────────────────────────────────────┐
│                    可观测性                           │
│                                                      │
│  ┌──────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │ Metrics  │  │   Tracing    │  │   Logging    │  │
│  │  指标     │  │   追踪       │  │   日志       │  │
│  ├──────────┤  ├──────────────┤  ├──────────────┤  │
│  │ 宏观     │  │ 请求级       │  │ 事件级       │  │
│  │ 聚合数据 │  │ 链路上下文   │  │ 详细上下文   │  │
│  │ 趋势     │  │ 瓶颈定位     │  │ 问题排查     │  │
│  └──────────┘  └──────────────┘  └──────────────┘  │
│         Prometheus    OpenTelemetry      ELK/Loki    │
│         + Grafana     + Jaeger          + Grafana   │
└──────────────────────────────────────────────────────┘
```

### 三者关系

```
Metrics 告诉你"出问题了"（告警触发 → QPS突然下降）
  ↓
Tracing 告诉你"哪里出了问题"（追踪发现 → 支付服务调用超时）
  ↓
Logging 告诉你"为什么出问题"（日志显示 → 第三方通道返回timeout）
```

## 二、Metrics（指标）

### 2.1 核心概念

```
数据模型：指标名 + 标签(tags/labels) + 值 + 时间戳

http_requests_total{method="POST", endpoint="/pay", status="200"} 1453 @1712345678
│                   │                    │                       │     │
│                   标签(维度)            │                       值    时间戳
│                                       标签(维度)
指标名                                   标签(维度)
```

### 2.2 指标类型

| 类型 | 含义 | Prometheus示例 | 适用场景 |
|------|------|---------------|----------|
| **Counter** | 只增不减的计数器 | `http_requests_total` | 请求数、错误数、处理量 |
| **Gauge** | 可增可减的瞬时值 | `cpu_usage_percent` | CPU、内存、连接数 |
| **Histogram** | 分布统计（分桶） | `http_request_duration_seconds` | P50/P90/P99延迟 |
| **Summary** | 分位数统计 | 客户端计算分位数 | 延迟分位数（不聚合） |

### 2.3 RED方法（服务监控）

```
Rate      — 每秒请求数 → 判断流量是否正常
Errors    — 每秒错误数 → 判断服务是否健康
Duration  — 请求延迟分布 → 判断性能是否退化

这就是面试中最常问的服务监控维度！
```

### 2.4 USE方法（资源监控）

```
Utilization  — 资源利用率 → CPU、内存、磁盘使用率
Saturation   — 资源饱和度 → 排队任务数、连接等待数
Errors       — 错误数 → 磁盘IO错误、网络丢包
```

### 2.5 支付业务核心指标

```
业务指标：
  - 支付成功率：payment_success_rate
  - 支付延迟P99：payment_duration_p99
  - 单笔交易金额：transaction_amount
  - 对账差异数：reconciliation_diff_count

技术指标：
  - 接口QPS、错误率、P99延迟（RED）
  - 数据库连接池利用率、慢查询数
  - 消息队列堆积量（Lag）
  - Redis命中率、内存使用率
```

### 2.6 Go + Prometheus 集成

```go
import (
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

// 定义指标
var (
    httpRequestsTotal = prometheus.NewCounterVec(
        prometheus.CounterOpts{
            Name: "http_requests_total",
            Help: "Total number of HTTP requests",
        },
        []string{"method", "endpoint", "status"}, // 标签维度
    )

    httpRequestDuration = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "http_request_duration_seconds",
            Help:    "HTTP request latency",
            Buckets: prometheus.DefBuckets, // .005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10
        },
        []string{"method", "endpoint"},
    )

    paymentAmount = prometheus.NewCounter(
        prometheus.CounterOpts{
            Name: "payment_amount_total",
            Help: "Total payment amount processed",
        },
    )
)

// 注册（在init或main中）
func init() {
    prometheus.MustRegister(httpRequestsTotal, httpRequestDuration, paymentAmount)
}

// 中间件中使用
func MetricsMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()

        c.Next() // 执行实际handler

        // 记录请求指标
        duration := time.Since(start).Seconds()
        status := strconv.Itoa(c.Writer.Status())

        httpRequestsTotal.WithLabelValues(c.Request.Method, c.FullPath(), status).Inc()
        httpRequestDuration.WithLabelValues(c.Request.Method, c.FullPath()).Observe(duration)
    }
}

// 暴露 /metrics 端点
func main() {
    r := gin.Default()
    r.Use(MetricsMiddleware())
    r.GET("/metrics", gin.WrapH(promhttp.Handler()))
    // ...
}
```

### 2.7 Grafana 仪表盘

```
常用面板：
  - QPS曲线（Rate of http_requests_total[1m]）
  - 错误率 = rate(errors[1m]) / rate(total[1m])
  - P99延迟 = histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
  - 4xx/5xx状态码分布
  - GC耗时、goroutine数量、内存分配速率
```

## 三、Tracing（分布式追踪）

### 3.1 核心概念

```
Trace(追踪)：
  └── Span A（HTTP /api/pay）                         ← 根Span
       ├── Span B（gRPC → 用户服务：查询账户）          ← 子Span
       │    └── Span C（MySQL：SELECT balance）         ← 子Span
       └── Span D（gRPC → 支付通道：发起扣款）
            └── Span E（Redis：SET idempotent_key）    ← 子Span

关键属性：
  - TraceID：全局唯一，贯穿所有Span
  - SpanID：当前操作唯一ID
  - ParentSpanID：父操作ID
  - 时间戳 + 耗时(Duration)
  - Tags：附属信息（http.status_code, db.statement等）
```

### 3.2 追踪上下文传播

```
W3C Trace Context 标准（HTTP头部）：
  traceparent: 00-{trace-id}-{span-id}-{trace-flags}
  tracestate: vendor-specific-info

gRPC 中使用 metadata：
  "grpc-trace-bin" 二进制格式传播

传播路径：
  前端 → Nginx → 网关(Inject) → 服务A(Extract) → gRPC → 服务B(Extract) → DB
                   ↑                                           ↑
              生成Span                                    继承TraceID
```

### 3.3 OpenTelemetry + Go 实践

```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/jaeger"
    "go.opentelemetry.io/otel/sdk/trace"
    "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
)

// 初始化
func initTracer(serviceName string) (*trace.TracerProvider, error) {
    // Jaeger exporter
    exp, err := jaeger.New(jaeger.WithCollectorEndpoint(
        jaeger.WithEndpoint("http://localhost:14268/api/traces"),
    ))
    if err != nil {
        return nil, err
    }

    tp := trace.NewTracerProvider(
        trace.WithBatcher(exp),
        trace.WithSampler(trace.TraceIDRatioBased(1.0)), // 100%采样(生产环境降低)
        trace.WithResource(resource.NewWithAttributes(
            semconv.ServiceNameKey.String(serviceName),
        )),
    )
    otel.SetTracerProvider(tp)
    return tp, nil
}

// Gin中间件中使用
func TracingMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        // 提取上游context中的traceID
        tracer := otel.Tracer("payment-service")
        ctx, span := tracer.Start(c.Request.Context(), c.FullPath())
        defer span.End()

        // 设置span属性
        span.SetAttributes(
            attribute.String("http.method", c.Request.Method),
            attribute.String("http.url", c.Request.URL.String()),
        )

        c.Request = c.Request.WithContext(ctx)
        c.Next()

        span.SetAttributes(attribute.Int("http.status_code", c.Writer.Status()))
    }
}

// 业务代码中使用
func (s *PaymentService) Pay(ctx context.Context, req *PayRequest) error {
    tracer := otel.Tracer("payment-service")
    ctx, span := tracer.Start(ctx, "PayService.Pay")
    defer span.End()

    // 调用下游服务时，ctx自动传播traceID
    span.AddEvent("validating_account")
    if err := s.validateAccount(ctx, req.UserID); err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, err.Error())
        return err
    }

    span.AddEvent("executing_payment")
    // gRPC调用会自动携带trace信息
    return s.executePayment(ctx, req)
}
```

### 3.4 采样策略

```
固定采样（生产常用）：
  - 100%采样：开发/测试环境
  - 10%采样：一般生产环境（控制存储成本）
  - 1%采样：超大流量

自适应采样（推荐）：
  - 正常请求：采样1%
  - 错误请求：采样100%
  - 慢请求(>1s)：采样100%

面试话术：
"追踪数据量很大，我们一般不会100%采样。
通常的策略是：正常请求低采样率(1-10%)减少开销，
错误和慢请求100%采样确保问题可追溯。"
```

## 四、Logging（日志）

### 4.1 结构化日志

```go
// ❌ 非结构化日志——无法检索、无法聚合
log.Printf("User %s paid %d yuan for order %s", userID, amount, orderID)

// ✅ 结构化日志——可以按字段检索、告警
import "go.uber.org/zap"

logger, _ := zap.NewProduction()
defer logger.Sync()

logger.Info("payment_processed",
    zap.String("user_id", userID),
    zap.Int64("amount", amount),
    zap.String("order_id", orderID),
    zap.String("channel", "wechat"),
    zap.Duration("latency", latency),
)

// 输出JSON格式（生产标准）：
// {"level":"info","ts":1712345678.123,"msg":"payment_processed",
//  "user_id":"123","amount":10000,"order_id":"ORD456","channel":"wechat",
//  "latency":0.235}
```

### 4.2 日志级别规范

```
FATAL   — 灾难性错误，服务无法启动
ERROR   — 业务错误、外部依赖调用失败
WARN    — 潜在问题（慢查询、接近限流阈值、重试成功）
INFO    — 关键业务节点（请求到达、支付成功、状态变更）
DEBUG   — 开发调试信息

实践：
- INFO 级别记录业务关键节点 → 用于业务对账、用户行为分析
- ERROR 记录所有外部调用失败 → 用于告警
- 禁止在循环内打INFO日志，避免日志爆炸
```

### 4.3 日志串联Tracing

```go
// 关键：日志中携带TraceID，实现Logging与Tracing的联动
import "go.opentelemetry.io/otel/trace"

func LogWithTrace(ctx context.Context, logger *zap.Logger, msg string, fields ...zap.Field) {
    spanCtx := trace.SpanContextFromContext(ctx)
    if spanCtx.IsValid() {
        fields = append(fields,
            zap.String("trace_id", spanCtx.TraceID().String()),
            zap.String("span_id", spanCtx.SpanID().String()),
        )
    }
    logger.Info(msg, fields...)
}

// 在Jaeger中看到某个Trace有问题 → 用TraceID在Loki/ELK中搜索该请求所有日志
```

### 4.4 日志最佳实践

```
1. 敏感信息脱敏（手机号中间4位、银行卡号仅显示后4位）
   手机号 138****1234
   卡号   **** **** **** 7890

2. 大对象/文件内容不要全部打印日志
   只记录hash/大小/摘要

3. 日志采集使用异步写入
   通过 stdout → filebeat/fluent-bit → Kafka → Elasticsearch/Loki
   不要直接写磁盘 → 阻塞业务线程

4. 日志保留策略
   热数据：ES（7天）
   冷数据：对象存储（90天）
   法规要求：离线归档（3-5年）
```

```

│                    可视化与告警层                          │

```
