## 一、Go 语言基础

### Q1: Go的GMP调度模型是什么？为什么Go能支持百万并发？

**答**：
Go的GMP模型将goroutine的调度分为三层：
- **G（Goroutine）**：用户态轻量级协程，初始栈仅2KB（OS线程初始1MB），创建和切换成本极低。
- **M（Machine）**：操作系统线程，真正执行计算的载体，由OS内核调度。
- **P（Processor）**：逻辑处理器，G和M之间的调度中介，数量由`GOMAXPROCS`决定（默认CPU核数）。每个P维护一个本地G队列（256容量），还有一个全局G队列。

**调度机制**：
1. **work stealing**：当P的本地队列空了，会从其他P的队列尾偷一半G来执行，实现负载均衡。
2. **hand off**：当G发生阻塞系统调用时，M会带着阻塞的G离开，P会绑定新的M继续执行其他G，保证CPU不闲置。
3. **抢占式调度**：Go 1.14起基于信号的抢占，防止单个G霸占CPU。

**为什么能百万并发**：因为goroutine是用户态调度，100万goroutine只需要约2GB内存（100万×2KB），而100万OS线程需要约1TB。实际工作中，goroutine的创建和切换不需要陷入内核态，开销远小于线程。

### Q2: Go的Channel底层实现原理？

**答**：
Channel底层是`runtime.hchan`结构体，包含：
- `buf`：环形队列缓冲区（有缓冲channel用）
- `sendx`/`recvx`：发送/接收索引
- `sendq`/`recvq`：等待发送/接收的goroutine队列（双向链表）
- `lock`：互斥锁，保证并发安全

**工作流程**：
- **无缓冲Channel**：发送方goroutine直接阻塞在recvq等待接收方，接收方阻塞在sendq等发送方，双方就绪后内存直接拷贝，无需经过buf。
- **有缓冲Channel**：buf未满时发送直接写入buf；buf满时发送方加入sendq等待。buf不空时接收方直接从buf读取；buf空时接收方加入recvq等待。
- **关闭的Channel**：永远不阻塞，读取返回零值+false。向已关闭channel发送会panic。

### Q3: Go的defer执行顺序和执行时机？

**答**：
- **执行顺序**：LIFO（后进先出），类似栈。后声明的defer先执行。
- **执行时机**：函数return之前（更准确地说，在设置返回值之后、函数返回给调用者之前）。
- **参数求值**：defer声明时就对参数求值（不是执行时），所以：

```go
func demo() {
    x := 1
    defer fmt.Println(x) // 此时x=1已被"快照"，最终打印1
    x = 2
}
```

- **1.14+的性能优化**：Go 1.14+对`defer`做了内联优化，大部分场景下defer开销接近0。
- **recover必须在defer中调用**才能捕获panic，在非defer的goroutine中无效。

### Q4: Go的nil interface和nil的区别？

**答**：这是一个经典坑！

```go
func getError() error {
    var p *MyError = nil
    return p  // 返回的error != nil！
}

err := getError()
fmt.Println(err == nil) // false！
```

原因：interface由两部分组成——`(type, value)`。当`p`被赋值给error接口时，type是`*MyError`（非nil），value是`nil`，所以err整体不为nil。**interface为nil必须type和value同时为nil**。

**正确写法**：
```go
func getError() error {
    if something {
        return &MyError{} // 明确有错误时返回非nil
    }
    return nil // 直接返回nil，不要返回typed nil
}
```

### Q5: Go中slice的扩容机制？

**答**：
- Go 1.18前：容量<1024 → 扩容为2倍；≥1024 → 扩容约1.25倍。
- Go 1.18后：容量<256 → 2倍；[256,512] → 约1.63倍；[512,1024] → 约1.44倍；更大 → 约1.25倍。
- 扩容后会分配新内存并拷贝数据，**原slice和扩容后的slice底层数组不同**。
- **最佳实践**：如果可以预估容量，用`make([]T, 0, capacity)`预分配，避免多次扩容导致的内存分配和GC压力。

## 二、分布式系统

### Q6: 什么是幂等性？在支付系统中如何保证？

**答**：
幂等性指同一个操作执行一次和执行多次的效果相同。支付系统中，用户可能因为网络重试、前端重复点击等导致同一笔支付请求被多次发送，必须保证不会重复扣款。

**实现方案**（从简单到严格）：

1. **数据库唯一索引**：为订单号+操作类型建唯一索引，利用DB约束天然防重。
2. **Redis令牌**：支付前先SET NX（原子操作），key为幂等令牌，value为状态，带TTL。处理完成后更新状态。
3. **状态机**：数据库记录状态字段（INIT→PROCESSING→SUCCESS/FAILED），用`UPDATE ... WHERE status='INIT'`做乐观锁，受影响行数为0即表示已处理。
4. **上游预先生成**：由前端/网关生成全局唯一的业务流水号，后端根据流水号做幂等校验。

**最推荐**：方案1（数据库唯一索引）+ 方案3（状态机）组合使用，因为数据库保证是最终的防线。

### Q7: 分布式事务的解决方案有哪些？各自优缺点？

**答**：

| 方案 | 描述 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **2PC** | 两阶段提交，协调者先PREPARE再COMMIT | 强一致，ACID | 同步阻塞、单点故障、性能差 | 传统数据库内部 |
| **TCC** | Try预留→Confirm提交→Cancel回滚 | 业务可控、不锁资源 | 代码侵入大、需实现3个接口 | 支付金融核心 |
| **Saga** | 长事务拆为多个本地事务+补偿 | 无锁、高并发、适合长事务 | 弱隔离、需补偿设计 | 跨服务订单流程 |
| **本地消息表** | 业务+消息在同一本地事务写入 | 实现相对简单、可靠性高 | 需定时扫表、消费端需幂等 | 最终一致性场景 |
| **RocketMQ事务消息** | MQ提供半消息+事务回查 | 不用自己扫表 | 依赖MQ特性 | 异步解耦 |
| **Seata AT模式** | 自动生成回滚SQL | 对业务代码无侵入 | 性能损耗、隔离性弱 | Java生态 |

**支付场景推荐**：TCC（核心转账）+ 本地消息表（通知/对账等非核心链路）

### Q8: 消息队列如何保证消息不丢失？

**答**：
消息可靠投递需要**生产、Broker、消费**三层保障：

**生产端**：
- 使用Confirm模式（同步发送等待Broker确认ACK）
- 发送失败重试+N次后落库人工处理

**Broker端（RabbitMQ为例）**：
- 开启持久化：`deliveryMode=2`（消息持久化） + durable queue（队列持久化）
- 镜像队列策略（集群节点宕机自动切换）

**消费端**：
- **手动ACK**（不是autoAck），业务处理完成后再确认
- 消费失败：NACK + 重新入队，或发送到死信队列
- 幂等处理：防止重复消费导致数据错误

**你的项目经验话题**：
> "在POS数据贯通项目中，我们使用RabbitMQ做数据异步处理。消费端使用手动ACK，只有数据成功加工并上传后才确认消息。超过3次重试失败的消息进入死信队列，由运维定时人工排查。这样保证了消息不丢失。"

### Q9: CAP定理在支付系统中如何权衡？

**答**：

支付系统的核心要求是**资金安全**，所以选CP（牺牲可用性保证一致性）：

**为什么不用AP？**
- AP允许短暂不一致 → 可能看到余额不准 → 用户可能超支 → 资金风险
- 银行/支付公司宁可短时间不可用，也不能出现账务错误

**实际架构策略**：
- **核心账务链路**：CP模型，用强一致性数据库+分布式锁保证
- **非核心链路**（通知、报表、积分）：AP模型，最终一致性即可
- **应对网络分区**：用多机房部署+主备切换，降低P发生的概率

> "实际上，CAP给我们的启示不是'三选二'，而是'分区发生时如何在C和A之间取舍'。
> 支付系统优先保证C，同时通过冗余部署尽可能提高A。"

## 三、MySQL

### Q10: MySQL索引底层原理？B+树为什么比B树更适合数据库？

**答**：

**B+树 vs B树**：
| 比较维度 | B树 | B+树 |
|----------|-----|------|
| 数据存储 | 所有节点存数据 | 仅叶子节点存数据 |
| 叶子节点 | 无链表 | 双向链表连接 |
| 范围查询 | 需中序遍历 | 遍历链表即可 |
| IO次数 | 随机 | 非叶子节点小，更多在内存 |

**B+树优势**：
1. **非叶子节点不存数据**，一个磁盘页能存更多索引key → 树更矮 → IO次数更少
2. **叶子节点有序链表** → 范围查询（`BETWEEN`、`ORDER BY`、`GROUP BY`）效率极高
3. **查询稳定**：任何查询都要到叶子节点，效率一致

**面试加分项—覆盖索引**：
```sql
-- 如果idx_name_age覆盖了SELECT所需的列（name, age），
-- 则不需要回表（不需要再根据主键去聚簇索引查完整行）
EXPLAIN会显示Extra: Using index → 说明走了覆盖索引
```

### Q11: MySQL慢查询怎么排查和优化？

**答**：

**排查流程**：
```
1. 开启慢查询日志 → 找到慢SQL
   SET GLOBAL slow_query_log = ON;
   SET GLOBAL long_query_time = 1;  -- 超过1秒记录

2. EXPLAIN分析执行计划 → 看type/rows/Extra/possible_keys/key
   - type从好到差：const > eq_ref > ref > range > index > ALL
   - Extra中的Using filesort / Using temporary 是危险信号

3. 分析索引使用情况
   - key列是否使用了预期的索引
   - 是否有索引但没命中（possible_keys有，key为NULL）

4. PROFILING诊断
   SHOW PROFILES; SHOW PROFILE FOR QUERY 2;
```

**常见优化手段**：
- **索引优化**：为WHERE/JOIN/ORDER BY列建索引，使用联合索引最左前缀
- **查询改写**：避免SELECT \*，用LIMIT控制返回量，用EXISTS替代IN（某些场景）
- **表结构优化**：字段类型尽量小，避免NULL（额外1字节标记），适当冗余减少JOIN
- **参数调优**：innodb_buffer_pool_size设为内存的60%-80%，调整连接数
- **架构优化**：读写分离（主写从读）、分库分表（按业务/用户拆分）

### Q12: MySQL事务隔离级别有哪些？各自问题？

**答**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 |
|----------|:----:|:----------:|:----:|----------|
| READ UNCOMMITTED | ✅ | ✅ | ✅ | 无锁 |
| READ COMMITTED | ❌ | ✅ | ✅ | MVCC+每次读最新快照 |
| REPEATABLE READ | ❌ | ❌ | ✅(部分❌) | MVCC+事务级别一致快照 |
| SERIALIZABLE | ❌ | ❌ | ❌ | 所有读加共享锁 |

**MySQL InnoDB**默认REPEATABLE READ，通过**MVCC（多版本并发控制）+ 间隙锁（Gap Lock）**在RR级别下也解决了部分幻读问题。

**支付系统选哪个**？
> "大多数场景用REPEATABLE READ足够。对于核心转账，通过`SELECT ... FOR UPDATE`显式加行锁，在RR级别下配合唯一索引已能防止大部分问题。极端场景可用SERIALIZABLE或通过业务层锁（Redis分布式锁）补充。"

### Q14: Redis的缓存策略？如何保证缓存与数据库一致？

**答**：

**最常用：Cache-Aside（旁路缓存）**
```
读：先查缓存 → miss → 查DB → 写回缓存
写：先写DB → 删缓存（不是更新缓存！）

为什么删除而不是更新？
→ 并发写可能导致缓存与DB顺序不一致（先写的后更新缓存）
→ 删除避免了并发写的问题
→ 如果缓存删除失败，用binlog异步重试删除（Canal方案）
```

**延迟双删策略**（更严格的方案）：
```
1. 先删缓存
2. 写DB
3. 延时（如500ms）
4. 再次删缓存

目的：避免在写DB期间，其他请求读到旧数据并写入缓存
```

**缓存更新选择的结论**：常规80%场景用「先写DB→删缓存」即可。对一致性要求极高的场景（如支付），不走缓存直接读DB。

## 五、系统设计场景

### Q16: 设计一个秒杀系统？

**答**：

```
全链路设计（自上而下）：

1. 前端层
   - 按钮置灰+倒计时（减少80%无效请求）
   - 验证码/滑块（防脚本刷单）

2. 网关层
   - Nginx限流（limit_req_zone 令牌桶）
   - 黑名单/白名单过滤

3. 服务层
   - Redis预减库存（lua脚本保证原子性）
   - 下单请求入MQ削峰
   - 后续异步处理+返回结果

4. 数据库层
   - 库存扣减SQL带条件：UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0
   - 利用行锁+库存条件，天然防超卖

5. 补偿
   - 超时未支付 → 库存回补
   - 对账补偿机制
```

**核心思路**：尽量在前置层拦截无效流量，DB是最后一道防线。

### Q17: 设计一个支付回调系统？

**答**（针对这家公司重点准备）：

```
1. 支付通道回调接入
   - 验签（验证回调确实来自第三方支付通道）

4. 对账
   - T+1日账单文件与本地订单比对
   - 差异自动标记+人工复核
```

## 六、Go 代码实战题

### Q18: 实现并发安全的限流器（手写代码可能性高）

```go
type RateLimiter struct {
    mu       sync.Mutex
    tokens   float64
    lastTime time.Time
    rate     float64 // 每秒产生token数
    burst    float64 // 桶容量
}

func (l *RateLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()

    now := time.Now()
    // 计算新增的token
    elapsed := now.Sub(l.lastTime).Seconds()
    l.tokens += elapsed * l.rate
    if l.tokens > l.burst {
        l.tokens = l.burst // 不超过桶容量
    }
    l.lastTime = now

    if l.tokens >= 1 {
        l.tokens--
        return true
    }
    return false
}
```

### Q19: 使用两个goroutine交替打印奇偶数

```go
func main() {
    ch1 := make(chan struct{})
    ch2 := make(chan struct{})
    var wg sync.WaitGroup

    wg.Add(2)
    go func() {
        defer wg.Done()
        for i := 1; i <= 100; i += 2 {
            <-ch1
            fmt.Println("奇数:", i)
            ch2 <- struct{}{}
        }
        <-ch1 // 接收最后一个信号后退出
    }()

    go func() {
        defer wg.Done()
        for i := 2; i <= 100; i += 2 {
            <-ch2
            fmt.Println("偶数:", i)
            ch1 <- struct{}{}
        }
    }()

    ch1 <- struct{}{} // 启动
    wg.Wait()
}
```
