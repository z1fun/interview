## 一、核心理论

### 1.1 CAP 定理

```
分布式系统设计原则

CAP = Consistency(一致性) + Availability(可用性) + Partition Tolerance(分区容错)

现实：P 不可避免（分布式网络分区一定会发生），所以实际是 CP vs AP 的选择
```

| 类型 | 说明 | 适用场景 | 示例 |
|------|------|----------|------|
| **CP** | 发生分区时牺牲可用性，保证一致性 | 金融交易、支付 | ZooKeeper、etcd |
| **AP** | 发生分区时牺牲一致性，保证可用性 | 社交、CDN | Eureka、Cassandra |

> **面试重点**：支付系统必须选CP或通过业务手段在AP之上构建一致性保证。

### 1.2 BASE 理论

```
BASE = Basically Available(基本可用) + Soft State(软状态) + Eventually Consistent(最终一致性)

这是AP系统的实践延伸——允许短暂不一致，但保证最终达成一致。
```

**ACID 事务特性**：

ACID 是传统关系型数据库事务的四个基本属性，保证事务的可靠处理：

| 特性 | 全称 | 说明 | 举例 |
|------|------|------|------|
| **A** | Atomicity（原子性） | 事务是一个不可分割的最小单元，要么全部成功，要么全部回滚 | 转账：扣款和入账必须同时成功或同时失败 |
| **C** | Consistency（一致性） | 事务前后数据必须满足所有约束规则（主键、外键、触发器、业务规则） | 转账前后，A+B 的总余额不变 |
| **I** | Isolation（隔离性） | 并发事务之间互不干扰，每个事务看起来是串行执行的 | 两人同时买最后一张票，只有一人能成功 |
| **D** | Durability（持久性） | 事务一旦提交，即使系统崩溃数据也不会丢失 | 提交后断电，重启后余额仍是转账后的值 |

> **Go 中如何保证**：数据库驱动（如 `database/sql` + `go-sql-driver/mysql`）通过 `tx.Begin()` → `tx.Exec()` → `tx.Commit()` / `tx.Rollback()` 实现事务的原子性。隔离级别通过 `tx.QueryContext(ctx, "SET TRANSACTION ISOLATION LEVEL ...")` 设置。

**与 ACID 对比**：
| ACID | BASE |
|------|------|
| 强一致性（C） | 最终一致性 |
| 隔离性（I）保证 | 无隔离保证 |
| 关注提交（事务一致性） | 关注可用 |
| 传统 RDBMS（MySQL、PostgreSQL） | 分布式系统（NoSQL、微服务） |

### 1.3 一致性模型

```
强一致性 → 顺序一致性 → 因果一致性 → 最终一致性
   ↑                                    ↑
 支付转账                           点赞/浏览数
```

**支付场景要求**：账户余额必须强一致，流水记录可以最终一致。

## 二、分布式事务

### 2.1 2PC (两阶段提交)

```
协调者                    参与者A                  参与者B
  |                         |                        |
  |--- PREPARE ------------>|                        |
  |--- PREPARE ------------------------------------>|
  |<-- YES ----------------|                        |
  |<-- YES -----------------------------------------|
  |                         |                        |
  |--- COMMIT ------------->|                        |
  |--- COMMIT ------------------------------------->|
  |<-- ACK ----------------|                        |
  |<-- ACK -----------------------------------------|
```

**缺点**：同步阻塞、单点故障(协调者)、数据不一致风险。

**Go实践**：一般不直接使用，而是通过框架封装。
```go
// 伪代码：XA事务在Go中的形态
// 通常由数据库驱动或分布式事务框架提供
// 支付场景更推荐TCC或Saga
```

### 2.2 TCC (Try-Confirm-Cancel)

**支付场景最常用的事务方案！**

```
业务场景：A给B转账100元

Try阶段（预留资源）：
  - A账户：冻结100元，可用余额-100
  - B账户：预增加100元（不可用状态）

Confirm阶段（提交）：
  - A账户：扣除冻结的100元
  - B账户：确认到账100元

Cancel阶段（回滚）：
  - A账户：解冻100元，可用余额+100
  - B账户：取消预增加的100元
```

**Go实现要点**：
```go
type TccAction interface {
    Try(ctx context.Context, req *TccRequest) error
    Confirm(ctx context.Context, txID string) error
    Cancel(ctx context.Context, txID string) error
}

// 关键设计：空回滚、防悬挂、幂等性
type TccService struct {
    db    *sql.DB
    cache *redis.Client // 用于记录Try/Cancel状态，防止悬挂
}

func (s *TccService) Try(ctx context.Context, req *TccRequest) error {
    // 1. 检查是否已被Cancel（防悬挂）
    if s.isCancelled(ctx, req.TxID) {
        return ErrCancelled
    }
    // 2. 执行业务冻结
    // 3. 记录Try状态
    return nil
}

func (s *TccService) Cancel(ctx context.Context, txID string) error {
    // 1. 检查是否已Try（空回滚：未Try直接返回成功）
    if !s.isTryDone(ctx, txID) {
        // 记录Cancel状态，防止后续Try执行
        s.markCancelled(ctx, txID)
        return nil
    }
    // 2. 执行业务回滚
    // 3. 幂等保证：已Cancel则直接返回成功
    return nil
}
```

### 2.3 Saga

```
两种实现方式：
1. 编排模式（Orchestration）：协调者驱动，类似2PC但无资源锁定
2. 协同模式（Choreography）：事件驱动，各服务自治

适合长事务、跨服务多的场景
```

**Go + 消息队列实践（你的RabbitMQ经验可以直接套用）**：
```go
// Saga 协同模式：利用RabbitMQ实现事件驱动
// 正向流程：order.created → payment.deducted → inventory.reserved
// 补偿流程：payment.failed → order.cancelled（补偿已执行的步骤）

type OrderSaga struct {
    mq *amqp.Channel
}

func (s *OrderSaga) Start(ctx context.Context, order *Order) error {
    // 发布"订单已创建"事件
    return s.publishEvent(ctx, "order.created", order)
}

func (s *OrderSaga) handlePaymentFailed(ctx context.Context, msg *Event) error {
    // 执行补偿：取消订单
    return s.compensateOrder(ctx, msg.OrderID)
}
```

### 2.4 本地消息表 + 消息队列（最实用方案）

```
核心思想：将业务操作和消息发送放在同一个本地事务中

步骤：
1. 开启本地事务
2. 执行业务SQL（如：用户下单）
3. 插入消息表（同一事务内，状态=待发送）
4. 提交事务
5. 定时任务扫描消息表→发送MQ→标记已发送
6. 消费端做幂等处理

这就是你在POS数据贯通中做的事（RabbitMQ消费+数据加工+上传）的理论升级版！
```

## 三、幂等性（支付核心必备）

### 3.1 为什么需要幂等性

```
场景：用户点击"支付"按钮
→ 前端loading，用户又点了一次
→ 两次HTTP请求到达后端
→ 如果没有幂等保护 → 扣两次钱 💸

金融系统每个写操作都必须幂等！
```

### 3.2 实现方案

```go
// 方案1：唯一索引（最简单可靠）
// 使用订单号+操作类型建唯一索引
CREATE UNIQUE INDEX idx_idempotent ON payment_records(order_id, operation_type);

func (s *PaymentService) Pay(ctx context.Context, orderID, operationType string) error {
    // 尝试插入，冲突即已处理过，直接返回成功
    _, err := s.db.Exec(
        "INSERT INTO payment_records(order_id, operation_type, status) VALUES(?, ?, ?)",
        orderID, operationType, "processing",
    )
    if isDuplicateKeyError(err) {
        return nil // 幂等：已处理
    }
    // ... 实际扣款逻辑
}

// 方案2：Redis幂等令牌
func (s *PaymentService) PayV2(ctx context.Context, req *PayRequest) error {
    key := fmt.Sprintf("pay:idempotent:%s", req.IdempotentKey)
    // SET NX + 过期时间，原子操作
    ok, err := s.redis.SetNX(ctx, key, "1", 24*time.Hour).Result()
    if err != nil {
        return err
    }
    if !ok {
        return nil // 已处理
    }
    // ... 实际扣款逻辑
}

// 方案3：状态机（最严格）
// 支付状态：INIT → PROCESSING → SUCCESS / FAILED
func (s *PaymentService) PayV3(ctx context.Context, orderID string) error {
    // UPDATE + WHERE 条件做状态检查，利用数据库行锁
    result, err := s.db.Exec(
        "UPDATE payment SET status='PROCESSING' WHERE order_id=? AND status='INIT'",
        orderID,
    )
    if rowsAffected, _ := result.RowsAffected(); rowsAffected == 0 {
        return nil // 非INIT状态，已处理过
    }
    // ... 实际扣款逻辑
}
```

## 四、分布式最终一致性

### 4.1 消息队列异步解耦

```
同步调用：                   异步解耦：
A → B → C → D              A → MQ ──→ B
   ↓                         ↓         ↓
  调用链长                    MQ       MQ
  故障传播                   ↓         ↓
  RT累积                     C         D
                         各消费者独立，故障隔离
```

### 4.2 消息可靠性保证

```go
// 生产端：Confirm模式（你RabbitMQ用过）
// 消费端：手动ACK + 重试 + 死信队列

func (c *Consumer) Consume(ctx context.Context, msg amqp.Delivery) error {
    // 1. 反序列化
    var event PayEvent
    json.Unmarshal(msg.Body, &event)

    // 2. 业务处理（带幂等）
    if err := c.processPayment(ctx, event); err != nil {
        // 3. 重试逻辑
        retryCount := getRetryCount(msg)
        if retryCount < 3 {
            // NACK + 重新入队
            msg.Nack(false, true)
            return nil
        }
        // 4. 超过重试次数，进入死信队列
        return c.sendToDLQ(ctx, msg)
    }

    // 5. 手动ACK
    msg.Ack(false)
    return nil
}
```

```
MySQL Binlog → Canal → Kafka → 下游服务（搜索索引/缓存更新/数据仓库）

适合：缓存一致性、多系统数据同步、审计日志
```

## 五、分布式锁

```go
// Redis分布式锁（适合非严格场景）
func (s *Service) WithRedisLock(ctx context.Context, key string, fn func() error) error {
    lockKey := fmt.Sprintf("lock:%s", key)
    token := uuid.New().String() // 唯一标识，防误删

    // 加锁
    ok, err := s.redis.SetNX(ctx, lockKey, token, 30*time.Second).Result()
    if err != nil || !ok {
        return ErrLockFailed
    }

    // Lua脚本原子释放（确保只有锁持有者才能释放）
    defer s.redis.Eval(ctx, `
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            return redis.call("DEL", KEYS[1])
        else
            return 0
        end
    `, []string{lockKey}, token)

    // 续期：watchdog goroutine
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()
    go s.watchDog(ctx, lockKey, token, 30*time.Second)

    return fn()
}

// etcd分布式锁（强一致性场景，如选主） — go-zero中通过etcd实现服务注册
// 你的POS数据贯通项目就用了etcd！
```

## 六、分库分表与读写分离

### MySQL分库分表策略

```
分库分表维度选择 → 优先选择查询最频繁的字段

支付系统推荐：用户ID + 商户ID 双维度
- 按 userId 分库（用户维度查询）
- 按 merchantId 分表（商户维度查询）
- 订单号冗余映射表（通过订单号先查userId，再定位库表）
```

### 读写分离下的数据一致性

```go
// go-zero框架中通过配置实现读写分离
```
