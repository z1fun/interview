# 02｜Go 并发与性能

## context 是请求生命周期的主线

入口创建或接收 `context.Context`，向数据库、RPC、模型调用、goroutine 一路传递；所有 I/O 设置 deadline。客户端断开或上游超时后，下游必须收到取消信号。不要把 context 存入结构体长期复用，也不要用它传业务必填参数。

```go
ctx, cancel := context.WithTimeout(parent, 8*time.Second)
defer cancel()
go func() {
    select {
    case <-ctx.Done(): return
    case jobs <- job:
    }
}()
```

## channel、锁与 worker pool

- channel 用于所有权转移、任务编排和信号；关闭由发送方负责，接收方不应随意关闭。
- `Mutex` 保护共享可变状态；`RWMutex` 仅在读远多于写且临界区不长时有益。
- `WaitGroup` 等待任务结束，不承担取消；取消仍靠 context。
- 有限 worker pool 保护模型、数据库等稀缺下游，队列满时应明确拒绝、短暂等待或降级，不能无限堆积。

## 常见故障与排查

**goroutine 泄漏**：无退出条件的 for-select、向无人接收的 channel 发送、无超时 I/O、ticker 未 Stop。检查 goroutine dump/pprof，关注数量是否随流量后不回落。

**数据竞争**：多个 goroutine 未同步读写 map/字段。用 `go test -race`；不要用“偶尔不报错”判断安全。

**死锁**：锁顺序不一致、持锁调用外部函数、channel 双方互等。缩短临界区，统一锁顺序，不在持锁状态做网络调用。

## 高并发链路的控制点

入口按用户/IP/业务做限流；服务内限制并发请求数；下游调用设置 timeout、熔断和有限重试；队列积压有长度和等待时间告警。对 Agent 而言，排队时间也属于用户延迟，不能只盯模型耗时。

## 性能回答模板

先定义问题（QPS、P95、CPU、GC、连接数或错误率），再用 pprof、trace、慢日志和指标分层定位。优化后重复压测验证，并说明收益与副作用。例如缓存能降数据库压力，但需处理一致性和穿透；增加并发能提吞吐，但可能击穿模型配额。

## GC 与逃逸

逃逸不是错误，关键是高频路径上减少不必要分配。通过 `go build -gcflags=-m` 观察，结合 benchmark/pprof 决策；复用 buffer 或对象池前先评估竞争和复杂度。面试中避免承诺“关闭 GC”这类不可取方案。
