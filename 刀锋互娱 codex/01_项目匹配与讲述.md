# 01｜项目匹配与讲述

## 面试表达公式

每个项目按“业务目标 → 我的职责 → 关键决策 → 难点与取舍 → 结果/复盘”讲述。先讲自己做了什么，避免把团队成果笼统归为个人；没有可验证数字时，说监控口径与改善方向，不编造指标。

## LoveSpouse 数字人：3 分钟版本

这是为成人智能玩具 App 做的虚拟角色陪伴系统，目标是让用户获得角色一致、能记住长期偏好、支持实时语音并能完成付费互动的体验。我负责后端对话链路：意图识别、场景路由、付费推荐和结构化回复；还设计并实现了近期对话、会话摘要、长期摘要、稳定事实组成的分层记忆。

实时交互上，我接入腾讯 IM，按业务消息 ID 保证幂等，避免回调重试造成重复回复或重复扣费；语音侧接入 Gemini Live，并处理会话生命周期、金币计费与跨实例通话控制。工程上我会给模型调用加超时和取消传播，用户断开后及时停止下游请求，避免无效消耗。

这个项目让我对 AI 陪伴产品的核心矛盾有了实战理解：不能只追求模型回答，而要同时控制实时性、角色一致性、成本、内容安全和业务正确性。这与该岗位的 Agent 实时交互、会话管理和稳定性需求高度一致。

## 可画出的链路

```text
客户端 / 腾讯 IM
  → 鉴权、限流、幂等校验
  → 会话编排（意图、场景、权益）
  → 记忆检索与上下文组装
  → 模型 / 工具调用（流式）
  → 结构化结果、计费、消息投递
  → 日志、指标、Trace
```

**追问：为什么分层记忆？** 原始历史保真但占 Token；摘要压缩阶段性语境；长期摘要保存有价值事件；稳定事实保存相对不变的偏好。请求时按当前意图选择少量相关内容，而非全量拼接。

**追问：跨实例通话怎么保证？** 先说明实际实现，再补充通用原则：通话会话有全局 ID 与 owner/lease；状态进入 Redis 或数据库等共享存储；抢占使用原子操作并带 TTL；实例故障后可超时接管；关键消息用序号或幂等键防重复处理。

## AI 漏洞研判系统：2 分钟版本

系统将信息完整性评估、POC 验证、定级定价、复测等环节建成 LangGraph 多 Agent 工作流。我负责工作流节点和 Prompt，并用 PostgreSQL + pgvector 建设 RAG 知识库；当低置信度或高风险结论出现时，通过飞书审批卡片转人工审核。

关键不在于“Agent 越多越好”，而在于把可控的业务步骤显式建模：每个节点有输入、输出 schema、状态变更和失败路径；检索结果带来源；人工决策回写流程状态，便于审计和回归评估。

## POS 数据贯通：补足后端深度

该项目用 Go、go-zero、gRPC、RabbitMQ、MySQL、Redis、ETCD 统一接入多产品线销售、商品、发票数据。我负责接口和消息消费加工。讲重点是：消费端按至少一次投递设计，用唯一业务键保证幂等；失败分级重试、死信和告警；接口版本和字段兼容；用指标定位积压或下游瓶颈。

## 真实数据准备表

面试前补齐下列事实：日活/并发连接、平均与 P95 响应、首 Token 时间、模型成功率、Token 或成本、IM 重复率、通话成功率、消费吞吐和历史故障案例。数字不完整时可说“当时没有建设该指标，若现在重做会补充 X 口径”。
