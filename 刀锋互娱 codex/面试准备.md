## 项目讲述主线

### 1. LoveSpouse 数字人（优先讲）

**背景与目标**：面向成人智能玩具 App 的虚拟角色陪伴系统。用户需要多角色、多语言、跨会话记忆、实时语音和可控的付费互动；难点是角色体验、实时性与业务闭环要同时成立。

**你的职责**：负责后端对话流程与实时交互链路，覆盖意图识别、场景路由、付费推荐、结构化回复、分层记忆、腾讯 IM 对接、Gemini Live 语音、金币计费及跨实例会话控制。

**可展开的技术亮点**：

- 以“近期原始对话 → 会话摘要 → 长期摘要 → 稳定事实”管理记忆。回答前按场景检索和拼装，避免无节制堆历史造成延迟与成本上升。
- IM 消息按业务消息 ID 做幂等键；重复回调只返回已有处理结果，关键状态落库或 Redis，避免重复回复、重复扣费。
- 对实时语音建立会话归属与生命周期控制；跨实例状态统一存储或通过消息协调，避免同一通话被多实例同时处理。
- 对模型调用设置 deadline、失败重试和降级路径；流式输出要能感知客户端断开并及时取消 context，避免无效 Token 消耗。

**结果表达原则**：如有真实数据，请用“平均响应时间、首 Token 时间、通话成功率、模型成本、重复消息率、异常率、付费转化”等指标替换泛泛描述；没有数据时，坦诚说明监控口径和改善方向，不虚构数字。

## 高频问答

### 为什么适合这个岗位？

岗位需要 Go 服务端、实时会话、Agent 工程化和稳定性经验。我的数字人项目直接覆盖了会话管理、记忆、腾讯 IM、Gemini Live 实时语音、模型调用、计费和分布式会话控制；同时我做过 gRPC、RabbitMQ、Redis 的 Go 微服务。相比从零转向 Agent，我已经在用户实时交互业务中踩过消息幂等、长连接和模型成本的工程问题，能更快形成产出。

### 怎样设计一个 Agent 会话服务？

先把入口、会话编排、模型网关、工具服务、记忆服务、异步任务和观测体系解耦。入口负责鉴权、限流和连接；会话服务负责状态机与上下文；模型网关统一处理供应商差异、流式输出、超时、重试和成本记录；工具调用必须做 schema 校验、权限校验和审计。会话状态应有明确的持久化和幂等边界，耗时任务走队列，链路贯穿 trace ID。MVP 阶段可先模块化单体，随着连接数和团队边界增长再拆服务。

### 记忆如何设计，如何避免上下文无限膨胀？

短期保留当前窗口的原始轮次，超过阈值后异步摘要；长期记忆保存稳定偏好、关系事件和明确的用户事实，并记录来源、时间和置信度。每次请求不拼接全部历史，而是根据当前意图召回少量相关记忆，并保留固定 Token 预算。冲突信息以时间、显式用户修正和可信来源为优先级；敏感数据必须最小化存储、支持删除和脱敏。

### WebSocket 与 SSE 如何选？

仅需要服务端把 LLM token 单向推给客户端时，SSE 实现更轻量，天然适合 HTTP 流式响应；需要语音控制、客户端事件、打断、状态同步或双向实时互动时选 WebSocket。无论哪种都要有鉴权、心跳/断连感知、超时、序号或幂等 ID，并在客户端断开后取消下游模型请求。

### 如何保证 IM 消息不重复处理？

以平台消息 ID 或业务幂等键建立唯一约束，先原子地抢占处理权，再执行副作用；已处理消息直接返回既有结果。消息处理、回复记录、扣费等关键动作要各自可幂等。对于“写库成功但发消息失败”的跨系统场景，可以用 Outbox/重试任务保证最终投递，而不是依赖一次 RPC 成功。

### Agent 调用模型失败或变慢怎么办？

区分不可重试的参数/安全错误与可重试的网络、限流、5xx；为每层设置 deadline，有限次数指数退避，不做无限重试。为不同模型或功能准备降级，例如切换备用模型、返回基于缓存的简短结果或让用户稍后重试。记录首 Token、总耗时、错误码、输入输出 Token 和重试次数，才能判断是模型、网络、Prompt 还是自身排队造成问题。

### Go 中如何避免 goroutine 泄漏？

所有 goroutine 都需要明确退出条件：接收 `context.Done()`，channel 由明确的一方关闭，不在无人消费的 channel 上永久阻塞。外部调用必须有 timeout；worker pool 要有关闭和等待机制。用 `go test -race` 查数据竞争，用 pprof、goroutine dump 和压测观察数量是否持续增长。

### RabbitMQ 消费者如何应对重复、失败和积压？

消费端按至少一次投递设计，业务以唯一键保证幂等；成功后再 ack。可恢复错误有限重试，持续失败进入死信队列并告警；毒消息不能无限 requeue。积压时先确认生产速度、消费者吞吐和下游瓶颈，再增加消费者或分片，但要注意单 key 顺序要求与下游承载能力。

### 如何控制模型成本？

最先建立每次调用的 Token、模型、功能、用户与结果质量口径。然后控制上下文：摘要、检索、裁剪和缓存；按任务复杂度路由模型，简单分类不使用昂贵模型；流式断连立即取消；对高频确定性问题做缓存。成本优化不能只看单价，也要看失败重试和低质量回复带来的二次调用。

### 如果陪聊 Agent 输出不当内容，如何处理？

做分层防护：入口识别高风险输入，系统 Prompt 明确能力和边界，工具白名单和参数校验防止越权，输出再做安全审核和必要的替换/拒答。高风险场景留存可审计事件但遵守最小化与脱敏原则。对未成年人、隐私、诱导付费、违法违规等设置更严格策略，并建立人工复核与规则迭代闭环。
