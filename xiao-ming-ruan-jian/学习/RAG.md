## 一、RAG全景图

### 1.1 什么是RAG？为什么需要RAG？

**RAG = Retrieval-Augmented Generation（检索增强生成）**

核心思想：**在LLM生成答案之前，先从外部知识库中检索相关信息，把检索结果和问题一起送给模型，让模型基于素材来回答。**

```
┌─────────────────────────────────────────────────────────────────────┐
│                          RAG 全链路                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  【离线入库链路】                                                      │
│  原始文档 → 文档解析 → 文本切片 → Embedding向量化 → 向量数据库存储       │
│                                                                     │
│  【在线问答链路】                                                      │
│  用户提问 → (查询改写) → 向量检索 → (重排序) → Prompt组装 → LLM生成 → 返回 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 RAG解决的三个核心问题

| 问题 | 说明 | 例子 |
|------|------|------|
| **知识截止** | LLM训练数据有截止日期 | GPT-4训练数据到2023年12月，之后的事不知道 |
| **幻觉** | LLM在不知道时会编造 | 问"公司2025年财报"→模型编一个数字 |
| **私有数据** | 企业内部数据没在公开训练集里 | 问"我们公司的报销流程"→RAG检索内部制度文档 |

### 1.3 RAG vs 微调：什么时候用哪个？

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 即时（更新文档即可） | 需要重新训练 |
| 成本 | 低（检索+推理） | 高（GPU训练） |
| 可解释性 | 高（能追溯引用来源） | 低（知识融在参数里） |
| 适用场景 | 知识检索、问答、事实查询 | 风格学习、领域特化、格式遵循 |
| 幻觉风险 | 低（有参考素材约束） | 中高 |

> **口述话术**："大部分企业AI场景首选RAG——成本低、见效快、知识好更新。只有当前RAG搞不定（比如需要模型学会特定的推理模式或者风格）时才考虑微调。两者也可以结合——RAG检索+微调过的模型生成。"

## 二、模块1：文档解析

### 2.1 常见文档类型与解析工具

| 文档类型 | 推荐工具 | 注意事项 |
|---------|---------|---------|
| PDF（文本层） | PyPDF2 / pdfplumber | 提取文本+保留页码等元数据 |
| PDF（扫描件） | PaddleOCR / Tesseract | 需要OCR识别，准确率取决于扫描质量 |
| Word (.docx) | python-docx | 需要处理表格、页眉页脚 |
| Markdown | markdown-it / Python markdown | 保留标题层级信息 |
| HTML | BeautifulSoup | 去除标签保留文本，注意去噪 |
| Excel/CSV | pandas | 表格数据需要特殊处理保留结构 |

### 2.2 复杂文档的处理难点

- **表格**：通用文本解析会把表格结构打散。解决：用专门的表格解析器（如unstructured的table模块），保留表格的Markdown格式或JSON结构。
- **版式复杂**（双栏PDF、图文混排）：需要layout分析，识别阅读顺序。
- **去噪**：页眉页脚、水印、页码——这些会被切成碎片污染知识库。
- **图片/图表**：多模态RAG——把图片描述文本也向量化（CLIP等多模态Embedding）。

### 2.3 你的项目结合

> "在AI漏洞研判系统里，知识库文档主要是结构化的漏洞修复记录——字段固定（漏洞类型、影响组件、修复方案等），不需要复杂的文档解析。但如果要做企业知识库问答，PDF和Word的解析就是一个不小的工程——文档格式千奇百怪，解析质量直接影响后续检索效果。"

## 三、模块2：切片策略

### 3.1 为什么切片很重要？

切片是RAG里**最影响效果的环节之一**。

- 切太大：一段里包含多个话题，语义被稀释，检索精度下降
- 切太小：语义不完整，缺少上下文，LLM看到碎片化的信息
- 切得太随意：把一个完整的概念切成两半，检索时各一半都匹配不到

### 3.2 四种切片策略对比

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **固定长度** | 按字符数切，如每512字符一块 | 简单快速 | 可能在句子中间切断 | 格式规整的文档 |
| **递归字符** | 按分隔符优先级（段落→句子→词）递归切??? | 尽量保持语义完整 | 忽略文档结构 | 通用场景，性价比最高 |
| **按文档结构** | 按Markdown标题层级（H1/H2/H3）切 | 保留层级关系 | 各块大小不均 | 结构化好的文档 |
| **语义切片** | 用模型判断句子间语义相似度来分块 | 语义最连贯 | 慢、成本高 | 质量要求极高的场景 |

### 3.3 关键参数

| 参数 | 建议值 | 说明 |
|------|--------|------|
| chunk_size | 256-1024 | 中文建议512字符，英文建议1000字符 |
| chunk_overlap | chunk_size的10-20% | 防止关键信息刚好落在边界被切断 |
| 元数据绑定 | 每块绑定：来源文档、章节标题、页码、时间戳 | 这是检索过滤和引用标注的基础 |

### 3.4 特殊场景的切片处理

- **代码**：按函数/类切，用AST解析器识别边界
- **表格**：保留表格格式+添加上下文标题作为向量化文本
- **FAQ**：每对QA独立成一个chunk
- **长文档摘要**：先对长文档做摘要，把摘要和原文都向量化

### 3.5 中文切片注意事项

> 中文不像英文有空格分词，分词效果会影响切片质量。建议：用langchain的RecursiveCharacterTextSplitter并设置中文标点（。！？；）作为高层级分隔符。如果文档结构好（有标题层级），优先按标题切。

## 四、模块3：Embedding向量化

### 4.1 Embedding是什么？

Embedding是把文本转成一个固定维度的向量（如768维的浮点数数组）。**语义相近的文本，向量距离近**。

比如：
- "Python怎么安装" → [0.12, -0.34, 0.56, ...]（768维）
- "如何配置Python环境" → [0.13, -0.32, 0.55, ...]（向量很接近）
- "今天天气怎么样" → [-0.45, 0.78, -0.23, ...]（向量距离很远）

### 4.2 中文Embedding模型选型

| 模型 | 维度 | 最大输入长度 | 特点 | 推荐场景 |
|------|------|------------|------|---------|
| **bge-m3** | 1024 | 8192 | 多语言、支持稀疏+稠密向量、效果好 | 中文首选推荐 |
| **bge-large-zh** | 1024 | 512 | 中文效果好，但输入长度短 | 短文本中文场景 |
| **m3e-base/large** | 768/1024 | 512 | 中文社区主流，轻量 | 中小规模，资源有限 |
| **text-embedding-3-large** | 3072 | 8191 | OpenAI的，效果最好但成本高 | 对质量要求极高 |
| **text-embedding-3-small** | 512 | 8191 | OpenAI的轻量版，性价比高 | 英文为主 |
| **jina-embeddings-v2** | 768 | 8192 | 支持中英双语，8K输入 | 长文档嵌入 |

### 4.3 相似度计算方法

| 方法 | 公式 | 说明 |
|------|------|------|
| **余弦相似度 (Cosine)** | cos(θ) = A·B/(\|A\|×\|B\|) | 值域[-1,1]，1=完全相同，最常用 |
| **内积 (Dot Product)** | A·B | 向量归一化后等价于余弦相似度 |
| **欧氏距离 (L2)** | sqrt(Σ(Aᵢ-Bᵢ)²) | 越小越相似，对向量长度敏感 |
| **曼哈顿距离 (L1)** | Σ\|Aᵢ-Bᵢ\| | 很少在语义搜索中使用 |

> **实践**：用余弦相似度最普遍。如果向量已经做了L2归一化，内积 = 余弦相似度，可以用内积（更快，pgvector支持inner product索引）。

### 4.4 Embedding的工程实践

- **批量向量化**：避免逐条调用Embedding API，100条一起发效率高得多
- **缓存**：相同文本不重复向量化——用文本哈希做key
- **维度选择**：维度高→表达力强但存储和检索成本大，768/1024维是平衡点
- **更新策略**：文档更新后需要重新向量化对应chunk并更新向量库

## 五、模块4：向量数据库

### 5.1 向量数据库的核心：ANN近似最近邻搜索

向量数据库的核心能力是ANN（Approximate Nearest Neighbor）——在海量向量中快速找到最相似的K个。不是逐个比较（太慢），而是用索引结构加速。

**主流ANN索引算法**：
- **HNSW**（Hierarchical Navigable Small World）：分层图索引，查询快，构建慢，内存占用大
- **IVFFlat**：先聚类再在最近的几个聚类里搜索，速度快但精度略低
- **PQ**（Product Quantization）：向量压缩，大幅减少内存但精度有一定损失

### 5.2 主流向量数据库对比

| 数据库 | 类型 | 规模 | 优势 | 劣势 | 适用场景 |
|--------|------|------|------|------|---------|
| **FAISS** | 内存库 | 百万-亿级 | 速度极快，Meta出品 | 不持久化，无分布式 | 离线实验、嵌入缓存 |
| **Chroma** | 嵌入式 | 万-十万级 | 上手极简，自带持久化 | 规模有限，生产弱 | 原型、小型项目 |
| **Milvus** | 分布式 | 亿级+ | 分布式、混合检索、GPU加速 | 运维复杂，资源消耗大 | 大规模生产 |
| **pgvector** | PG扩展 | 十万-百万级 | 与业务库一体、SQL查询、运维简单 | 超大规模不如Milvus | 中小规模，想少运维 |
| **Qdrant** | 独立服务 | 百万-亿级 | Rust实现高性能，过滤能力强 | 独立部署 | 中等规模 |
| **Weaviate** | 独立服务 | 百万-亿级 | 内置混合搜索和Reranker | 资源消耗较大 | 需要开箱即用 |

### 5.3 pgvector深度（你的实战经验重点展开）

**为什么你选pgvector是对的**：

1. **规模匹配**：历史漏洞记录几千条，不需要分布式
2. **运维简单**：和业务数据一个PostgreSQL实例，不用多维护一套服务
3. **联合查询**：向量检索+元数据过滤（时间、类型、状态）一个SQL搞定
4. **成本低**：不需要额外的服务器资源

**pgvector关键操作**：

```sql
-- 安装扩展
CREATE EXTENSION vector;

-- 创建向量字段（768维）
ALTER TABLE vulnerability_records ADD COLUMN embedding vector(768);

-- 创建HNSW索引（比IVFFlat更快，构建更慢）
CREATE INDEX ON vulnerability_records USING hnsw (embedding vector_cosine_ops);

-- 向量相似度查询 + 元数据过滤（一个SQL搞定）
SELECT content, 1 - (embedding <=> query_embedding) AS similarity
FROM vulnerability_records
WHERE vuln_type = 'SQL注入'
  AND created_at > '2025-01-01'
ORDER BY embedding <=> query_embedding
LIMIT 10;
```

**索引参数调优**：
- `m`（HNSW每层连接数）：默认16，加大→召回更准但索引更大更慢
- `ef_construction`（构建时搜索深度）：默认64，加大→索引质量更好但构建更慢

## 六、模块5：检索优化（面试最高频话题）

### 6.1 检索效果诊断框架

当面试官问"检索不准怎么办"，先诊断再开方：

```
检索不准 → 是召回问题还是精排问题？

【召回问题】该召回的不在结果里
├── 切片不合理（太大/太小/割裂）
├── Embedding模型不适合你的领域
├── 查询太口语化，和文档风格不匹配
└── 单一检索方式覆盖不全（需要混合检索）

【精排问题】召回了但不排在前面
├── 缺少重排序
├── 仅靠向量相似度不够精细
└── 缺少元数据/规则过滤
```

### 6.2 混合检索（Hybrid Search）⭐⭐⭐⭐⭐

**原理**：同时做语义检索（向量）和关键词检索（BM25），结果融合。

- **向量检索**：擅长找意思相近的——"电脑坏了"能匹配到"笔记本故障"
- **关键词检索**：擅长找精确匹配的——搜索"SQL注入"不会召回"XSS攻击"
- **融合后**：各取所长，覆盖更全

**RRF融合算法**（Reciprocal Rank Fusion）：

```
RRF(文档d) = Σ 1/(k + rank_i(d))
每个检索通路的排名取倒数求和，k是常数（通常取60）
排第一 = 1/61，排第十 = 1/70，差距不太大
```

**工程实践**：
```
向量检索 top-20 + BM25检索 top-20 → 去重 → RRF融合 → 取 top-10
```

### 6.3 查询改写（Query Rewriting）

用户的问题往往不适合直接用于检索：
- "这个怎么弄" → 缺少上下文
- "上个月那个问题又出现了" → 指代不明确

**多轮对话改写**（最重要）：
```
对话历史：用户"Python怎么装" → 助手"..."
当前问题："那Mac上呢"
改写后："如何在Mac上安装Python"
```

**查询扩展**（提升召回）：
```
原始问题："怎么提升检索准确率"
扩展查询：
  - "RAG检索优化方法"
  - "向量检索重排序方案"
  - "混合检索改进召回率"
→ 多个查询分别检索，结果合并去重
```

### 6.4 重排序（Reranking）⭐⭐⭐⭐⭐

**原理**：向量检索用bi-encoder（query和doc分别编码再算相似度），速度快但交互不够精细。Reranker用cross-encoder（query和doc拼接在一起打分），能捕捉细粒度语义匹配，但速度慢。

**典型用法**（二阶段检索）：
```
粗排：向量检索 top-100（快但不够准）
精排：Reranker重排 top-5（准但慢）
生成：送top-5给LLM
```

**Reranker选型**：
| 模型 | 说明 |
|------|------|
| bge-reranker-v2-m3 | 开源，多语言，效果很好 |
| bge-reranker-large | 中文效果好 |
| Cohere Rerank | 商业API，效果好但收费 |

### 6.5 元数据过滤

在检索时加上粒度过滤，缩小召回范围：
- 时间过滤：只要最近一年的文档
- 类型过滤：只要技术文档不要新闻
- 权限过滤：员工只能看自己部门的文档
- 标签过滤：按预先打好的标签过滤

pgvector天然支持这种联合查询——向量检索WHERE条件可以带任意业务字段过滤。

### 6.6 其他检索优化技术

| 技术 | 说明 | 适用场景 |
|------|------|---------|
| **HyDE** | 先让LLM生成假设答案，用答案向量去检索 | 短问题搜长文档 |
| **Small-to-Big** | 检索小块，返回大块（含上下文） | 语义碎片化场景 |
| **Multi-Query** | 从多个角度改写查询分别检索 | 查询意图不明确 |
| **Self-Query** | LLM自动从问题中提取过滤条件 | 需要元数据过滤时 |
| **语义缓存** | 相似问题直接返回缓存答案，不调模型 | 高频重复问题 |

### 6.7 你的项目实战

> "在AI漏洞研判系统中，检索不准的表现是：语义检索会召回'语义相似但类型不同'的历史漏洞。比如一个SQL注入和一个XSS漏洞，描述里都写了'用户输入未过滤'——语义上相似，但实际上是完全不同的漏洞类型，参考价值为零。我的解法是混合策略——向量语义检索做初筛+漏洞类型和影响组件的精确规则过滤做精排。"

## 七、模块6：答案生成

### 7.1 Prompt模板设计

```
你是一个{角色设定}。请严格基于以下参考文档回答用户问题。

【参考文档】
{检索到的文档片段，带编号和来源}

【回答要求】
1. 仅基于上述参考文档回答，不要补充文档中没有的信息
2. 如果参考文档不足以回答问题，请明确说"根据现有资料无法回答"
3. 回答时标注引用来源 [文档编号]
4. 回答简洁清晰，不要罗列无关信息

【用户问题】
{用户问题}
```

### 7.2 关键设计点

- **引用标注**：让模型标注每句话的来源（[文档1]、[文档2]），增强可信度
- **拒答机制**：检索结果置信度低于阈值时，说"我不知道"而不是编造
- **Temperature**：RAG场景设0.1-0.3，减少模型"自由发挥"
- **max_tokens**：根据业务场景设上限，避免回答过长

### 7.3 多轮对话 + RAG

多轮对话场景需要注意上下文管理：
1. 当前问题可能是对上一轮回答的追问
2. 检索时需要结合对话历史（查询改写）
3. 上下文窗口需要合理分配：对话历史 + 检索文档 + 生成回复

## 八、模块7：幻觉与评估

### 8.1 幻觉的四大成因

| 原因 | 说明 | 缓解手段 |
|------|------|---------|
| 检索缺失 | 知识库里没有相关信息 | 加拒答机制、扩展知识库 |
| 切片割裂 | 相关信息被切在不同片段里 | 优化切片策略、增大overlap、small-to-big |
| 模型编造 | 模型即使有参考文档也会编 | Prompt约束（"仅基于文档"）、降低temperature |
| 指令冲突 | Prompt指令和检索文档信息冲突 | 优化Prompt设计，明确优先级 |

### 8.2 评估指标体系

**检索侧**：
| 指标 | 含义 | 计算方式 |
|------|------|---------|
| Recall@K | 正确答案在top-K中的比例 | 命中数/总查询数 |
| MRR | 第一个正确答案的平均排名倒数 | 1/rank的平均 |
| Hit Rate | 至少召回一个正确答案的比例 | 命中查询数/总查询数 |

**生成侧**：
| 指标 | 含义 |
|------|------|
| Faithfulness（忠实度） | 回答是否完全基于检索文档，有无编造 |
| Answer Relevance | 回答是否直接回应了问题 |
| Context Relevance | 检索到的文档是否和问题相关 |

**评估框架**：RAGAS——用LLM当Judge，自动对上述三个指标打分，不需要人工标注。

### 8.3 线上监控指标

- 无答案率（用户问题知识库无法回答的比例）
- 引用率（回答中有文档引用的比例）
- 用户反馈（点赞/踩/转人工的比例）
- 平均检索延迟（P50/P99）

## 九、模块8：高级RAG趋势（了解即可）

### GraphRAG
微软提出的方案。传统RAG把文档当独立片段，GraphRAG先构建知识图谱（实体+关系+社区），检索时除了找相关文档，还能理解实体关系和全局主题。适合需要全局理解的复杂问题，代价是构建成本高。

### Agentic RAG
让Agent自主决定检索策略——什么时候检索、检索什么、要不要多轮检索、检索结果不好时要不要换个方式重新检索。比固定流程的RAG更灵活。

### Self-RAG
模型在生成过程中自我反思——检索到的内容相关吗？生成的内容忠于检索结果吗？不需要就跳过检索，不相关就重新检索。

### Corrective RAG
检索后用评估模型检查文档相关性，不相关时自动触发网络搜索或其他知识源补充。
