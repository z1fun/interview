## 一、为什么这是胜负手

JD 写了这样一句话：

> 「无独立负责ai全栈项目经验的勿扰」

你简历上的项目描述偏向"模块负责人"口吻（"主要负责..."、"参与..."），面试官天然会怀疑你是否有独立交付能力。

**但事实上**，AI漏洞研判系统你做了工作流设计、Prompt调优、RAG检索链路、飞书审批对接——这就是端到端全链路。你只是**没有按"独立交付"的方式来讲述**。

本章的目标：**完成叙事重写，把"我负责其中几个模块"变成"我主导了从0到1的全链路交付"。**

## 二、从0到1的标准回答模板

当面试官问"给你一个AI产品需求，你怎么做？"时，按以下框架回答：

### 方法论六步法

```
需求调研 → MVP定义 → 技术选型 → 迭代开发 → 测试上线 → 持续运营
```

### 口述模板（可直接背诵）

> "我的方法分六步。第一步需求调研，我会先跟业务方聊清楚痛点，把需求收敛到可用AI解决的核心问题上——不是所有需求都适合用AI，做减法很重要。
>
> 第二步是MVP定义，我会画一个最小可行产品的范围：哪些功能必须有，哪些可以后面再加，定一个2-4周能上线的时间节点。
>
> 第三步技术选型，我会评估是用现成的平台（比如Dify）快速验证，还是需要代码级方案（比如LangGraph）做更灵活的控制。模型方面我会优先评估API调用 vs 私有化部署的成本和延迟。
>
> 第四步是迭代开发，我会把RAG链路、Agent工作流、前后端接口按优先级分批次交付，每批次都做验收。
>
> 第五步是测试上线，我会做功能测试、边界case测试、还有RAG的检索准确率评估，确认没问题再灰度上线。
>
> 最后一步是持续运营，我会建监控（响应延迟、无答案率、用户反馈），根据数据持续迭代知识库和Prompt。"

## 三、三大项目叙事重写

### 项目1：AI漏洞研判系统（核心王牌）

#### STAR版本（口述脚本）

**S — Situation（背景与痛点）**

> "我在诚迈科技负责的这个项目，背景是SRC安全应急响应中心的运营场景。每天有大量白帽子提交漏洞报告，运营人员需要逐一审核：判断漏洞信息是否完整、构造POC验证漏洞是否真实存在、评估危害等级、给出合理的赏金定价、修复后还要人工复测。这个过程非常耗时，而且不同运营人员判定的标准不统一，赏金定价主观性强。我主导了这个项目的技术方案，目标是把整个审核流程用AI Agent自动化。"

**T — Task（我的任务）**

> "我需要设计一个多Agent协作系统，实现漏洞从提交到复测的全链路自动化。核心挑战有三个：一是5个环节各自需要不同的判断逻辑和工具能力，不能用一个通用Prompt搞定；二是需要引入历史漏洞知识库做RAG检索，为定价提供参考依据；三是必须保留人工审批节点，不能让AI全自动做敏感决策——安全领域要可控。"

**A — Action（我做了什么）**

> "我选型了LangGraph做Agent编排，因为它的StateGraph天然支持多节点、条件分支和状态持久化，比LangChain的线性Chain更适合这种有分支的工作流场景。
>
> 我设计了5个Agent节点：第一个做信息完整性评估，检查白帽子提交的漏洞描述是否完整；第二个做POC构造与风险评估，根据漏洞类型生成验证脚本并评估潜在危害；第三个做POC自动验证，在沙箱环境中执行验证脚本；第四个做漏洞定级定价，结合RAG检索的历史相似漏洞数据给出定级和赏金建议；第五个做自动复测，在漏洞修复后自动重新验证。
>
> 节点间通过共享的State传递上下文。关键节点设置了条件边——比如信息不完整就走驳回分支，不需要经过后续节点。人工审批通过LangGraph的interrupt机制实现，在定级定价节点暂停等待飞书审批卡片的结果再继续。
>
> RAG部分我用了pgvector做向量数据库，把历史漏洞修复记录向量化，检索时做语义匹配+定级规则过滤的混合策略。飞书审批我用的是卡片消息API，审批人能直接在卡片上点通过/驳回/转交。"

**R — Result（结果）**

> "系统上线后在日常运营中使用。最直接的效果是审核效率提升了数倍——以前一个人一天审十几条，现在系统自动筛掉信息不全的，只把需要决策的推给人工。赏金定价也有了数据依据而不是拍脑袋。另外我加了凭证自动失效检测，防止用过期凭证执行验证导致误报。"

#### 面试官追问预案

| 追问 | 回答要点 |
|------|---------|
| "为什么用LangGraph不用LangChain？" | LangChain的Chain是线性的，不适合有分支、有条件跳转的工作流。LangGraph的StateGraph支持条件边、循环和状态持久化，适合多步骤有决策分支的场景。另外LangGraph的checkpointer天然支持中断和恢复，方便做人工审批介入。 |
| "5个Agent怎么通信？" | 通过共享的State字典传递，每个节点读取上游节点的输出字段，写入自己的结果。State的结构是TypedDict，LangGraph会自动合并各节点的输出。 |
| "pgvector为什么不用Milvus？" | 项目规模不需要分布式向量数据库，pgvector和业务库同一个PostgreSQL实例，减少了运维复杂度。而且我们的漏洞数据本身就在PostgreSQL里，向量存在一起方便做元数据过滤的联合查询。 |
| "检索不准怎么办？" | 我做了两层优化：一是检索时加了元数据过滤（漏洞类型、时间范围），缩小召回范围；二是召回后加了规则层做精排。如果效果还不好，会考虑加Reranker做重排序。 |
| "飞书审批怎么做的？" | 用飞书卡片消息API，当Agent走到定级定价节点时，发送审批卡片给指定审批人。卡片上有通过/驳回/转交按钮，点击后飞书回调我们的FastAPI接口，接口拿到结果后通过LangGraph的interrupt resume机制继续工作流。 |
| "最大的技术挑战？" | 一是POC验证的安全隔离问题——在沙箱里执行不确定的验证脚本有风险；二是RAG检索的准确率——历史漏洞数据量不大但类型分散，语义检索容易召回不相关的。第一个问题通过容器化沙箱+超时+资源限制解决，第二个通过混合检索（语义+规则过滤）逐步优化。 |
| "如果重新做，会怎么改进？" | 一是RAG加Reranker重排序提升精排准确率；二是Agent评估体系——现在靠人工反馈，应该加自动化评测（任务完成率、定价偏差率）；三是考虑引入MCP协议让工具调用更标准化。 |

### 项目2：AI助理（Dify方案）

#### STAR版本（口述脚本）

**S — Situation**

> "在思迅软件，我们服务的是零售商户。商户老板每天要看销售数据、调价格、管库存，但数据散在不同的报表里，他们缺的不是数据，是把数据变成行动建议的能力。"

**T — Task**

> "我需要快速搭建一个AI助手，让商户能用自然语言问'最近什么商品卖得好？''这个价格合理吗？'然后得到直接的建议。关键是快速验证，不能花几个月做完美方案。"

**A — Action**

> "我选择用Dify快速搭建，因为当时团队资源有限，Dify的可视化工作流可以省掉大量前端和编排代码的开发时间。模型用的是DeepSeek。
>
> 我设计了两个核心工作流：智能定价——输入商品信息和历史销售数据，输出定价建议和调价幅度；爆款商品雷达——分析销售趋势，自动识别增长最快的商品。Prompt调优上，我用了CoT的思路让模型先分析数据再给建议，并且约束输出格式让前端好渲染。
>
> 知识库部分我整理了公司的零售行业数据——历史定价策略、品类销售特征、促销效果记录——作为RAG的参考素材注入到工作流中。
>
> 上线策略是做限时限量开放——先给一部分商户试用，收集反馈，验证了需求真实存在再扩大。"

**R — Result**

> "通过最小可行性验证，证明了商户对AI辅助决策有真实需求。智能定价的建议采纳率不错，爆款商品雷达帮助商户发现了他们自己没注意到的增长品类。这个项目的价值在于用最小的成本验证了AI在零售场景的可行性。"

#### 面试官追问预案

| 追问 | 回答要点 |
|------|---------|
| "为什么选Dify而不是自己写？" | 当时的目标是最快验证需求。Dify的工作流拖拽 + 内置RAG能力 + DeepSeek接入，几天就能出MVP。如果自己从零搭FastAPI+LangChain+前端，至少几周。等需求验证通过后，如果有更复杂的需求Dify满足不了，再考虑代码级方案。 |
| "Dify的局限性？" | 一是复杂条件分支不如代码灵活，二是知识库切片策略是内置的黑盒不能完全自定义，三是多Agent协作支持较弱。所以后来做漏洞系统时，需求复杂度高了就选了LangGraph。|
| "Prompt怎么调的？" | 核心是让模型先分析再建议（CoT），而不是直接给结论。比如定价工作流，我先让它分析历史价格区间、竞品价格、销量趋势，再基于这些分析给定价建议。另外加了输出格式约束，用JSON Schema确保前端能直接渲染。 |

### 项目3：商云前台（全栈证据）

#### STAR版本（口述脚本）

**S — Situation**

> "商云前台是思迅的收银POS桌面应用，功能覆盖市面上常见收银软件的全部模块——秤重、AI商品识别、会员、促销、支付、打印、外卖等等。"

**T — Task**

> "我需要负责多个核心模块的全栈开发，包括自助模式、微信电子小票、打印钱箱、RabbitMQ消息推送、权限控制等。技术挑战是桌面应用要在离线模式下正常运行，联网时再同步数据。"

**A — Action**

> "技术栈是 Wails + Vue3 + TypeScript + Go。Wails框架让Go后端和前端通过JS Bridge直接通信，不需要HTTP服务。Go端负责业务逻辑、串口通信（秤、钱箱）、加解密（AES/RSA）、本地SQLite缓存、RabbitMQ消息消费。前端Vue3 + TypeScript + Pinia + Vue Router做UI和状态管理。
>
> 离线模式的设计思路是：所有数据先写本地SQLite，在线模式下定时通过RabbitMQ上传到云端，云端有变更也通过RabbitMQ推下来更新本地。加密信息（比如支付密钥）用RSA非对称加密保护。"

**R — Result**

> "商云前台是公司面向商户的主力收银产品，在多个客户门店部署使用。我负责的模块从Go后端到Vue3前端都是独立完成，经历了从开发、测试、上线到线上问题排查的完整链路。"

#### 面试官追问预案

| 追问 | 回答要点 |
|------|---------|
| "Wails和Electron有什么区别？" | Wails用Go替代了Node.js做后端，打包体积小（几十MB vs 上百MB），内存占用低。而且Go的并发处理串口通信和RabbitMQ消息比Node.js更高效。但对前端来说开发体验差不多，都是写Vue/React然后通过Bridge调后端。 |
| "离线模式数据一致性怎么保证？" | 本地SQLite是唯一写入口，上传是异步的。用时间戳+版本号做冲突检测，云端以本地数据为准（因为POS是数据源头）。RabbitMQ消费端做幂等处理，防止重复消费。 |

## 五、质疑应对话术

### "你没有独立做过AI产品"

> "其实我最核心的AI漏洞研判系统，从技术方案设计、Agent工作流编排、RAG检索链路、Prompt调优到飞书审批集成、上线部署，都是我主导完成的。虽然是在团队协作的背景下，但AI核心链路是我一个人从头写到尾的。包括技术选型——为什么用LangGraph不用LangChain、为什么用pgvector不用Milvus——都是我做的决策。从这个意义上说，我确实经历了AI产品从0到1的全过程。
>
> 如果您有具体的场景需求，我也可以现场讲讲我的设计思路。"

### "你5年经验AI只占1年"

> "是的，我的职业路径是先从Go后端做起，这是我的底座。前3年我积累了扎实的工程能力——微服务、高并发、数据库、Docker运维。近两年我主动往AI方向转型，因为在实际业务中看到了AI能解决的真实问题：零售商户需要数据解读、安全运营需要自动化审核。这个转型是业务驱动的，不是跟风。
>
> 而且我发现在AI工程化方向，Go的高并发能力其实很稀缺——比如做推理网关、高并发API封装、限流熔断这些，大部分AI团队缺这样的人才。所以这5年的积累不是在浪费，而是在AI浪潮中找到了一个差异化的位置。"

### "你TypeScript/Vue3熟悉到什么程度？"

> "在商云前台项目中，我用Vue3 + TypeScript + Pinia + Vue Router做了完整的前端开发，包括组件通信、状态管理、路由守卫这些常规操作都会。TypeScript方面，interface泛型、工具类型这些日常在用。
>
> 但如果跟专职前端比，我的深度肯定不如。我现在的水平是'能独立完成AI产品的前端交互开发'——做对话界面、管理后台、数据可视化这些没问题，但复杂的前端性能优化或组件库开发还需要再深入。React我也在系统学习，能写函数组件和Hooks。"

### "为什么从Go转AI？"

> "三个原因。第一是兴趣，我觉得让程序能理解和推理是个很有意思的方向。第二是业务驱动——在思迅做POS时发现商户没有数据分析能力，我想用AI帮他们；在诚迈看到安全运营的人效瓶颈，AI能规模化处理审核任务。第三是我发现Go在AI工程化里也有独特价值——大模型服务的高并发API网关、推理请求的调度和限流，这些恰恰是Go擅长的。我不是抛弃Go，而是把Go和AI结合起来。"

## 六、现场演示预案

如果面试官说"你给我现场设计一个AI问答系统"，用以下框架回答（5分钟版）：

> "我以'企业IT帮助台问答系统'为例，快速过一下设计思路。
>
> **需求**：员工问IT问题——比如'VPN连不上怎么办''怎么申请新电脑'——系统能自动回答，减少IT人员重复工作。
>
> **方案**：用标准RAG架构。核心链路是：员工提问→查询改写（把'连不上'改成具体环境）→向量检索（从IT知识库召回相关文档）→重排序（精排top5）→答案生成（带引用标注）。如果检索置信度低，走拒答策略，让员工转人工。
>
> **技术选型**：知识库用内部的IT文档、常见问题FAQ。文档解析用unstructured处理PDF和Markdown。切片用递归字符分割，512字符一块、overlap 50。Embedding用bge-m3。向量库用pgvector和业务库放一起。检索用混合策略：向量语义检索 + BM25关键词检索，通过RRF融合。Reranker用bge-reranker-v2-m3做精排。生成用DeepSeek或者公司指定的模型。
>
> **工程化**：FastAPI + SSE流式输出。前端对话界面Vue3，展示引用来源。日志记录每次问答的检索结果和用户反馈，用于后续优化。
>
> **迭代计划**：第一版只覆盖VPN和账号问题，跑通链路验证效果。第二版加更多知识类别和用户反馈闭环。"
