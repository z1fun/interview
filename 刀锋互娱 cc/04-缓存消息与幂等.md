# 缓存、消息与幂等｜50 分钟

用时：缓存 20 分钟，消息与幂等 20 分钟，数据库 10 分钟。POS 数据贯通（RabbitMQ）与数字人（IM 幂等、Redis）是直接经验。

## 1. 缓存三问题

| 问题 | 含义 | 常见处理 |
|---|---|---|
| 穿透 | 不存在的数据反复回源 | 参数校验、短暂缓存空结果 |
| 击穿 | 热点 key 失效，大量请求同时回源 | 请求合并/互斥重建、限制回源并发 |
| 雪崩 | 大批 key 同时失效或缓存服务故障 | TTL 抖动、限流、降级 |

- **更新策略（旁路缓存）**：读未命中回源并写缓存；更新先写 DB 再失效缓存，失败要有重试/补偿，TTL 兜底一致性。
- Key 设计：业务前缀 + 版本 + 参数标准化；缓存命中不等于跳过权限校验。
- 缓存允许多旧由业务决定，页面可展示数据更新时间。

## 2. Redis 数据结构选型

| 类型 | 场景 |
|---|---|
| string | 缓存值、计数器、限流计数、分布式锁 |
| hash | 对象的多个字段（用户档案） |
| list | 简单队列、最近消息 |
| set | 去重、在线成员、标签 |
| zset | 排行榜、按时间排序的消息 |

## 3. 分布式锁的边界

- 获取：`SET key 唯一持有者 NX PX 过期`；释放：Lua 脚本原子比较持有者再删除，避免删掉新持有者的锁。
- **过期风险**：任务执行时间可能超过锁 TTL → 锁续期（watchdog）或把关键写入做成幂等/资源端版本保护兜底。
- Redlock 有争议：多数场景单实例 + 主从切换有风险，重数据用 DB 唯一约束兜底更可靠。

## 4. 消息与消费幂等：处理重投，不假设只投一次

- RabbitMQ：交换机/队列/绑定；消费手动 ACK，处理成功后 ACK；失败 nack 重投 → **至少一次投递**，消费必须幂等。
- 幂等设计三步（数字人 IM 幂等、POS 数据贯通同思路）：

1. 以业务事件 ID（IM 消息 ID、业务流水号）作为幂等键，**数据库唯一约束兜底**。
2. 幂等记录与业务变更**同一事务**提交，重复事件不重复产生副作用。
3. 提交后 ACK；ACK 失败重投时，下一次安全跳过已完成事件。

- **乱序**：按业务序列号/版本判断，旧消息跳过。
- 失败处理：有上限的退避重试；超限进死信队列隔离排查。
- 外部调用不受本地事务保护：调用支付、发消息等要给对方幂等键或设计补偿。

## 5. MySQL 基础

- 慢查询排查：定位慢 SQL → `EXPLAIN` 看扫描类型与行数 → 调索引/SQL → 验证正确性与性能。
- 联合索引遵循最左前缀，围绕常用过滤 + 排序设计（如 `(user_id, created_at)` 查聊天记录）。
- InnoDB 默认可重复读 + 间隙锁，防幻读；了解脏读/不可重复读/幻读定义。
- 连接池最大连接数与并发控制联动（呼应 01 篇：池耗尽 = 排队超时）。
