# 高并发与稳定性｜20 分钟

用时：阅读 15 分钟，脱稿复述 5 分钟。岗位职责明确要求监控、压测、容灾，多数题按“思路 + 项目印证”回答。

## 1. 限流

| 算法 | 特点 |
|---|---|
| 固定窗口 | 简单，窗口边界有突刺 |
| 滑动窗口 | 平滑，实现略重 |
| 令牌桶 | 允许突发，按速率补充令牌 |
| 漏桶 | 匀速流出，削峰 |

- 单机用 `golang.org/x/time/rate`；分布式用 Redis 计数/脚本；网关层统一拦截更省事。
- 维度：用户/接口/IP；超限返回 429 或降级排队。
- 限流要与降级配合：核心链路（聊天、通话）保底，非核心（推荐、统计）先限。

## 2. 压测

- **目标先行**：定 QPS、延迟分位（P50/P99）、错误率指标再动手。
- 方法：压测环境与生产隔离；阶梯加压找到拐点；观察 CPU、内存、GC、连接池、数据库、下游耗时；记录数据对比优化前后。
- 常见瓶颈：连接池耗尽、数据库慢查询/锁竞争、下游无超时、goroutine 堆积、GC 停顿。

## 3. 监控与日志

- **指标**：QPS、延迟分位、错误率、goroutine 数、GC 停顿、连接池使用率、MQ 积压、模型调用耗时与 token 用量（Agent 特有）。
- **日志**：结构化，trace ID 贯穿 请求 → RPC → MQ → 模型调用，一条链路能串起来。
- **告警**：分级、收敛、避免告警疲劳；错误率、P99、积压这些可行动的指标才告警。

## 4. 容灾与降级

- **超时**：每层都设超时，ctx 传播（01 篇）。
- **重试**：只对幂等操作重试，指数退避 + 随机抖动，防重试风暴（04 篇幂等前提）。
- **熔断**：下游故障快速失败，不再等待（go-zero breaker 这类实现）。
- **降级**：模型挂了切备用模型/缓存兜底回复；非核心功能关停。
- **发布**：灰度、可回滚；出问题先看最近变更。

## 5. 任务调度

- 定时任务多实例部署会重复执行 → 分布式锁、DB 唯一约束或分片解决。
- 异步任务走 MQ + 重试 + 死信队列（04 篇）。
- 数字人例子：会话摘要生成是会话结束后的异步任务，失败可重试、不影响主链路——这就是"任务调度"的真实经验素材。

## 6. 故障排查顺序

先确认影响面与时间点 → 看发布/变更 → 看监控（资源、错误率、下游、积压）→ 按链路逐层拆（网关→服务→DB/缓存/MQ/模型）→ 必要时回滚/限流止损 → 复盘。排查讲方法，不背流程。

## 自测

1. 口述一次压测的完整做法：指标怎么定、怎么加压、瓶颈怎么定位？
2. 定时任务在多实例部署下有什么问题？几种解法？
3. 线上响应突然变慢，你的排查顺序？
