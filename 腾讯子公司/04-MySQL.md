## 1. 索引原理（重点，占面试 1/3 时间）

### 1.1 从磁盘 IO 说起：索引到底在解决什么问题

数据库的三大存储介质速度量级（这是所有索引设计的出发点，一定要能脱口而出）：

| 介质 | 访问耗时 | 相对量级 |
|---|---|---|
| CPU 寄存器 / L1 缓存 | ~1 ns | 1x |
| 内存（随机访问） | ~100 ns | 100x |
| SSD 随机读 | ~50~150 μs | 10 万倍 |
| 机械磁盘随机读（含寻道+旋转） | ~10 ms | **1000 万倍** |

结论：**内存比磁盘快 10 万倍，所以数据库索引设计的唯一目标是——把随机磁盘 IO 的次数降到最低**。

这引出了一切的核心概念：**磁盘预读与页（Page）**。操作系统从磁盘读数据不是按字节读，而是按块（block，通常 4KB）读；InnoDB 更进一步，以 **16KB 的页（`innodb_page_size`，默认 16KB）** 为最小 IO 单位。也就是说：**你只查 1 行数据，InnoDB 也要把这一行所在的 16KB 整页读进内存**。

所以索引结构的设计目标变成了：**让每一次磁盘 IO 都能"顺带"排除掉尽可能多的数据**。这就决定了必须用一种**矮胖（多叉、低层高）**的树，而不是二叉的树。

一次 IO 读一页，一页能装多少个索引项，就决定了这棵树有多"胖"。InnoDB 索引页的内部结构（源码层，`storage/innobase/include/page0page.h`）：

```
+--------------------------------------------------+
| File Header (38B)  FIL_PAGE_PREV / FIL_PAGE_NEXT |  <- 页之间双向链表（范围查询关键）
+--------------------------------------------------+
| Page Header (56B)  PAGE_N_DIR_SLOTS / PAGE_LEVEL |
+--------------------------------------------------+
| Infimum + Supremum 记录（虚拟最小/最大记录）        |
+--------------------------------------------------+
| User Records（真正的索引记录，单向链表串起来）        |
|    ... 按主键/索引列有序排列 ...                    |
+--------------------------------------------------+
| Free Space                                       |
+--------------------------------------------------+
| Page Directory（槽 slot，稀疏目录，每 6 条记录 1 槽）|  <- 页内二分查找
+--------------------------------------------------+
| File Trailer (8B)  校验和，防止页损坏               |
+--------------------------------------------------+
```

页内查找用的是 **Page Directory + 二分查找**：先在槽数组里二分定位到大致范围（槽是稀疏的，每 4~8 条记录一个槽），再沿记录的单向链表顺序找。所以**页内查找是 O(log n) 定位 + O(槽间距) 遍历**，不是纯二分。

### 1.2 B+ 树结构详解（面试必背的核心）

#### 结构定义

InnoDB 的 B+ 树有两个必须记住的特征：

1. **只有叶子节点存数据**，非叶子节点（内节点）只存「索引列 + 子页页号」，纯粹是"目录"。
2. **所有叶子节点用双向链表连接**，且同一层的页之间也通过 `FIL_PAGE_PREV/FIL_PAGE_NEXT` 串起来。

```
                         [根页 root]
                    /        |        \
              [内节点]     [内节点]    [内节点]         <- 只存 key + page_no
             /    \       /    \      /    \
          [叶子] [叶子]  [叶子] [叶子] [叶子] [叶子]      <- 存完整行数据 or 主键值
            <->    <->     <->    <->    <->    <->      <- 双向链表（范围查询的关键）
```

#### 三层 B+ 树能存多少行？（面试超高频追问）

这是推导题，面试官就是看你能不能算，而不是背结论。

**前提假设**：InnoDB 页 16KB；主键为 `BIGINT`（8 字节）；一个页号（page no）占 6 字节；假设一行数据 1KB。

**非叶子节点能放多少个目录项**：
```
单条目录项 = 主键 8B + 页号 6B = 14B
可用空间 ≈ 16KB = 16384B（还要减去 File Header 38B、Page Header 56B、
                          Infimum/Supremum、Page Directory 等约 100+ 字节开销）
16384 / 14 ≈ 1170 个目录项
```

**叶子节点能放多少行**：
```
一页 16KB / 一行 1KB = 16 行
```

**三层 B+ 树容量**：
```
第 1 层（根）    : 1 个页
第 2 层（内节点）: 1170 个页
第 3 层（叶子）  : 1170 × 1170 = 1,368,900 个页
总行数          : 1,368,900 × 16 ≈ 2190 万行
```

**结论（直接背）：一棵三层 B+ 树大约可以存 2000 万行数据，而查询任意一行最多只需要 3 次磁盘 IO**。而且根节点常驻内存（Buffer Pool），实际上通常只有 2 次甚至 1 次物理 IO。

**追问：那 2000 万行以上的表怎么办？** → 树变成 4 层，多一次 IO。这正是"单表千万级建议分表"的经验值的由来，但要注意**这个经验值的前提是"每行 1KB + 主键 BIGINT"**。如果你的表一行只有 100 字节，4 层 B+ 树能存几个亿。所以面试时一定要说：**"单表多少行要分表，取决于单行大小和访问模式，不能只看行数"**——这句话能直接把你和背八股的候选人区分开。

#### 范围查询为什么快

`SELECT * FROM t WHERE id BETWEEN 100 AND 500`：

1. 从根节点二分找到 id=100 所在的叶子页（3 次 IO）；
2. 在叶子页内二分定位到 100；
3. **沿着叶子节点的双向链表向右顺序扫描**，直到遇到 id > 500。

因为叶子节点是**有序 + 链表相连**的，所以范围查询是**顺序 IO**，而不是每行都回根节点重新查。这是 B+ 树相对 B 树的核心优势之一。

### 1.3 为什么是 B+ 树？——B 树 / 哈希 / 红黑树 / 跳表逐个对比

这是 MySQL 最经典的"为什么"题，答题结构应该是**先建立评价标准，再逐个对比**：

> **评价标准**：① 磁盘 IO 次数（树高）；② 是否支持范围查询与排序；③ 页内/节点内查找效率；④ 增删时的维护成本。

#### 对比表（背这张表就够）

| 数据结构 | 树高/查找复杂度 | 磁盘 IO | 范围查询 | 排序 | 结论 |
|---|---|---|---|---|---|
| **B+ 树** | 3~4 层（多叉） | 2~4 次 | ✅ 叶子链表顺序扫描 | ✅ | **胜出** |
| B 树 | 3~4 层（多叉） | 2~4 次，但**非叶也存数据** | ⚠️ 需中序遍历、跨层跳转 | ⚠️ | 淘汰 |
| 哈希表 | O(1) | 1 次 | ❌ 完全不支持 | ❌ | 只适合等值 |
| 红黑树/AVL | O(log₂n) ≈ 24 层(2000万) | **24 次随机 IO** | ✅ 但需中序遍历 | ✅ | 淘汰 |
| 跳表 | O(log n) ≈ 24 层 | 24 次随机 IO | ✅ | ✅ | 内存场景用（Redis ZSet） |
| B* 树 | 类似 B+ | 略优 | ✅ | ✅ | 实现复杂，未采用 |

#### 逐个说清楚

**① 为什么不用 B 树？**

B 树（B-Tree）的特点是**每个节点既存 key 也存 data**：

```
B 树节点（16KB）: [key1|data1|ptr1|key2|data2|ptr2|key3|data3|ptr3]
                    ↑ data 占了大量空间，导致一页能放的 key 少得多
```

三个致命问题：

1. **单页能放的 key 更少 → 树更高 → IO 更多**。假设 data 1KB，一页只能放十几条，树高迅速膨胀到 5~6 层。
2. **范围查询低效**。B 树的数据分散在所有层，做 `BETWEEN` 需要**中序遍历整棵树**（从叶子爬到根再下到另一个叶子），产生大量随机 IO；B+ 树只需要定位到起点然后顺着叶子链表扫。
3. **查询性能不稳定**。B 树查根节点命中就是 1 次 IO，查叶子要 4 次 IO，**性能抖动**；B+ 树任何查询都必须走到叶子，IO 次数恒定，**性能可预测**。（这一点面试时说出来很加分，很多资料不谈。）

**② 为什么不用哈希索引？**

哈希索引（如 Memory 引擎的 HASH 索引）等值查询 O(1)，确实快，但：

- **不支持范围查询**：`WHERE id > 100` 只能全表扫描，因为哈希值是散列的，顺序和原值无关。
- **不支持排序**：`ORDER BY` 必然 filesort。
- **不支持最左前缀**：联合索引 (a,b) 的哈希值必须 a、b 全给才能算出来，`WHERE a = 1` 完全用不上。
- **哈希冲突**：冲突多了退化成链表，O(1) 变 O(n)。

**注意一个加分点**：InnoDB 实际上**有哈希索引**——叫 **自适应哈希索引（Adaptive Hash Index，AHI）**。它会自动监控索引页的访问模式，如果发现某些索引值被频繁等值查询，就自动在 **Buffer Pool 内存中** 为这些页建立哈希索引，把 B+ 树的 3 次查找降为 1 次。用 `SHOW ENGINE INNODB STATUS` 可以看到 `Hash table size ... node heap` 相关输出，参数 `innodb_adaptive_hash_index`。**它是内存态的，不落盘，重启即失效，所以不能替代 B+ 树**。

**③ 为什么不用红黑树 / 跳表？**

核心就是**树高 = 磁盘 IO 次数**：

```
红黑树是二叉树，n = 2000 万时高度 ≈ 2 × log₂(2000万) ≈ 2 × 24 = 48 层
最坏情况下需要 48 次磁盘随机 IO，每次 10ms → 单次查询 0.5 秒
```

而 B+ 树是**多叉**的，一个节点（页）能放 1170 个分叉，所以 3 层就够了。**"多叉"是唯一的解药，而多叉的前提是节点要足够大（16KB 页）**。

顺带说一句 Redis 的 ZSet 用了跳表（skiplist），面试官可能追问"为什么 Redis 用跳表而 MySQL 用 B+ 树"：**因为 Redis 是纯内存数据库，不存在磁盘 IO 的问题，跳表实现更简单、范围查询同样友好、内存占用可调（层高概率 p=0.25）；而 MySQL 的数据在磁盘上，必须减少 IO，所以要用多叉的 B+ 树**。这个对比答出来非常漂亮。

**④ 为什么 InnoDB 页是 16KB？**

`innodb_page_size` 可配 4KB/8KB/16KB/32KB/64KB，默认 16KB：

- 太小 → 一页放的索引项少 → 树高增加 → IO 增多；
- 太大 → 一次 IO 读取过多无用数据、Buffer Pool 中单页管理成本上升、写入放大（InnoDB 写页是整页写，哪怕只改一个字节）；
- 16KB 是**磁盘块大小（4KB）的整数倍**（避免一次逻辑 IO 拆成多次物理 IO），同时与 SSD 的页大小和文件系统的块大小匹配得较好，是经验最优值。

**如果面试官问"改大页会怎样"**：改大后单页容纳更多行，树变矮，但**写入放大更严重、并发写入时页锁竞争更激烈、Buffer Pool 内存碎片化**。这个参数一般不动。

### 1.4 聚簇索引与二级索引

#### 聚簇索引（Clustered Index）

**定义**：索引和数据存在一起，叶子节点直接存放**完整的一行数据**。

InnoDB 的聚簇索引**就是主键索引**。它的选取规则（源码层 `row_sel_build_clust_index`）：

1. 如果表定义了**主键**（PRIMARY KEY），用主键做聚簇索引；
2. 否则选**第一个所有列都 NOT NULL 的唯一索引**（UNIQUE NOT NULL）当聚簇索引；
3. 都没有 → InnoDB 自动生成一个 **6 字节的隐藏列 `DB_ROW_ID`** 当主键，用它建聚簇索引（此时你的 SQL 查不到这一列，但它真实存在）。

**重要推论**：**一张 InnoDB 表，数据只存一份，就在聚簇索引的叶子里**（这句话是"表就是索引，索引就是表"的来源）。

#### 二级索引（Secondary Index，也叫辅助索引/非聚簇索引）

**定义**：叶子节点存放「索引列的值 + 主键值」，**不存完整行**。

```
聚簇索引（主键 idx_id）:  [id=1 | 完整行1] [id=2 | 完整行2] [id=3 | 完整行3]
                                  ↑ 叶子即数据

二级索引（idx_name）    :  [name='a'|id=1] [name='b'|id=3] [name='c'|id=2]
                                  ↑ 叶子只存 name + 主键 id
```

**为什么二级索引要存主键值？** 因为通过二级索引找到记录后，还需要拿主键去聚簇索引里把整行取出来，这个动作叫**回表**。

**回表（Bookmark Lookup / Row Lookup）**：

```sql
SELECT * FROM user WHERE name = 'b';
-- 执行过程：
-- 1. 在 idx_name 上找到 name='b' 的记录 → 得到 id=3
-- 2. 拿 id=3 回到主键 B+ 树查找 → 得到完整行
-- 这就是回表，如果第一步命中 1000 行，就要回表 1000 次
```

回表的代价是：**每一条命中记录都意味着一次（或多次，若聚簇索引有 4 层）额外的 B+ 树查找**。虽然每次都走 Buffer Pool，但这是纯粹的随机访问，是慢查询最常见的元凶。

#### 主键为什么推荐自增？（页分裂 / 页合并）

这是聚簇索引的超高频追问，答不出来会显得很"背"：

**自增主键**：新行总是追加到 B+ 树**最右边的叶子页**，如果该页满了就**申请一个新页**，不需要移动已有数据 → **顺序写入，无随机 IO**。

**随机主键（如 UUID）**：新行的位置是随机的，可能落在任意一个已有的叶子页中间：

- 如果目标页**已满** → 触发**页分裂（Page Split）**：把一页拆成两页，并把父节点加一条目录项，父节点满了还要继续向上分裂（甚至增加树高）。页分裂后，**两个新页都只有约 50% 的空间利用率**，浪费磁盘、Buffer Pool 和 IO。
- 分裂后，新页可能落在磁盘的任意位置 → **顺序写入变成随机写入**。
- 删除数据时大量页变空，会触发**页合并（Page Merge）**，同样带来性能抖动。

**但要注意面试官的反问："那为什么有些公司还是用 UUID 做 MySQL 主键？"** 标准答法：
- 分布式场景下自增主键无法全局唯一（分库分表后各库自增会冲突）；
- 单库单表场景，自增主键必胜；
- 如果业务需要一个不暴露 ID 规则的外部标识，正确做法是：**内部仍用 BIGINT 自增（或雪花 ID）做聚簇索引，另外加一个 UNIQUE 的业务编号列**，而不是把 UUID 当主键；
- 如果一定要用无序 ID（如雪花 ID 的机器位不规则、或 UUIDv4），可以考虑 **UUIDv7 / ULID / 有序雪花** 这类"趋势递增"的方案，把随机写变成近似顺序写。

**结合项目话术**：FlashRoot 项目涉及多级客户和结算流水，这类表我在设计时用 `BIGINT AUTO_INCREMENT` 做聚簇索引，另外给结算流水加了 `biz_no`（业务单号）唯一索引，这样做的好处是：主键保证写入顺序性和页利用率，业务单号又有唯一约束兜底、支持用户按单号查。这个"双键设计"的思路在任何订单/工单/流水类表里都通用。（可结合 **FlashRoot 返点结算**、**POS 数据贯通上传流水** 作答）

### 1.5 覆盖索引（Covering Index）

**定义**：如果一个查询**需要返回的所有列**，都能在二级索引的叶子节点上拿到，就不需要回表。此时 `EXPLAIN` 的 `Extra` 会显示 **`Using index`**。

```sql
-- 表 user(id PK, name, age, city)，有索引 idx_name_age(name, age)

-- ① 不覆盖：需要 city，索引上没有 → 回表
SELECT name, age, city FROM user WHERE name = 'tom';
-- Extra: Using index condition / NULL（有回表）

-- ② 覆盖：需要的列 name, age, id 全在 idx_name_age 叶子上（id 是主键，天然带在二级索引里）
SELECT id, name, age FROM user WHERE name = 'tom';
-- Extra: Using index   ← 不需要回表
```

**注意一个关键细节（很多人答错）**：**任何二级索引的叶子节点上都带着主键值**，所以 `SELECT 主键, 索引列...` 天然是覆盖索引，**即使没有显式把主键写进索引**。

**怎么用覆盖索引优化？**

1. **把 SELECT 的列缩到最小**，或者把高频查询涉及的列加进联合索引（代价是索引变大、写入变慢）。
2. **延迟关联（深分页神器，见 4.6）**：先用覆盖索引查出主键，再用主键回表取其他列。
3. 区分 **`Using index`（真覆盖，不回表）** vs **`Using index condition`（索引下推，仍需回表）** —— 这是 EXPLAIN 里最容易混的两个值，**面试经常拿它俩做陷阱题**。

**覆盖索引的代价**：每个额外索引都要单独维护一棵 B+ 树，写入时要更新多棵树的页（**写放大**），并占用 Buffer Pool。所以**不能为了覆盖而无限加索引**，一般单表索引控制在 5~6 个以内。

**结合项目话术**：POS 数据贯通里我做过商品档案的批量查询接口，原来 `SELECT *` 走二级索引回表，QPS 上来以后 DB 的 CPU 打满；后来把列表页需要的列做成了联合索引实现覆盖索引，同时在代码层用 GORM 的 `Select("id, sku, name, price")` 明确指定列而不是 `Find(&list)` 全字段，回表次数降为 0，这个接口的 P99 从 200ms 降到了 20ms 以内。（可结合 **POS 数据贯通** 作答；如果面试官追问 GORM 细节，见下面的小贴士）

> **GORM 小贴士（面试官爱问"你用 GORM，那你怎么控制 SQL"）**：
> ```go
> // ❌ 全字段查询，容易破坏覆盖索引
> db.Where("sku = ?", sku).Find(&products)
>
> // ✅ 明确指定列，命中覆盖索引
> db.Select("id, sku, name, price").Where("sku = ?", sku).Find(&products)
>
> // ✅ 看真实执行的 SQL（面试时说出来显得你真的用过）
> stmt := db.Session(&gorm.Session{DryRun: true}).Where(...).Find(&p)
> fmt.Println(stmt.Statement.SQL.String(), stmt.Statement.Vars)
> // 生产环境开日志：db.Debug() 或 logger 配置 SlowThreshold
> ```
> GORM 的 `logger.Config{SlowThreshold: 200 * time.Millisecond}` 可以把慢 SQL 打出来，我们线上就是用它 + 慢查询日志双保险定位问题的。

### 1.6 最左前缀原则（原理，不是背诵）

#### 原理：联合索引在 B+ 树里怎么排序？

建一个联合索引 `idx_abc (a, b, c)`，它在 B+ 树中的排序规则是：

> **先按 a 排序；a 相等时按 b 排序；b 相等时按 c 排序。**（本质是**字典序**）

对应的索引记录长这样：

```
叶子节点中的数据（按 a,b,c 字典序排列）:
(a=1, b=1, c=1)  → id=5
(a=1, b=1, c=3)  → id=8
(a=1, b=2, c=1)  → id=2
(a=2, b=1, c=1)  → id=9
(a=2, b=1, c=4)  → id=3
(a=3, b=2, c=2)  → id=7
```

**看这张图就能理解一切**：
- `WHERE a=1 AND b=2 AND c=1` → 能精确定位 ✅
- `WHERE a=1 AND b=2` → 定位到 (1,2,*) 的一段连续区间 ✅
- `WHERE a=1` → 定位到 (1,*,*) 的连续区间 ✅
- `WHERE b=2` → **b 的值在全局是无序的**（a=1 下面有 b=2，a=2 下面也有 b=2，它们不相邻）❌ 无法定位
- `WHERE c=1` → 同理 ❌

**所以"最左前缀"不是 MySQL 的规则，而是 B+ 树这种有序结构的数学必然**。这样答，面试官会觉得你懂原理而不是背规则。

#### 几条必须记准的细则

| SQL 条件 | 联合索引 (a,b,c) 使用情况 | 说明 |
|---|---|---|
| `a=1` | 用到 a | |
| `a=1 AND b=2` | 用到 a,b | |
| `a=1 AND b=2 AND c=3` | 用到 a,b,c | 全部用上 |
| `b=2 AND c=3` | **完全不用** | 缺 a，不满足最左 |
| `a=1 AND c=3` | 只用到 a | b 断了，c 用不上（但可能被 ICP 过滤） |
| `a=1 AND b>2 AND c=3` | 只用到 a,b | **范围查询会让后面的列失去索引定位能力** |
| `a>1 AND b=2` | 只用到 a | 同上 |
| `a=1 AND b=2 ORDER BY c` | 用到 a,b + 排序也用索引 | 顺序天然满足 |
| `a=1 ORDER BY c` | 用到 a，排序 filesort | c 在 a 相同时才有意义？不，b 没给，c 无序 → filesort |

**重点解释「范围查询后的列失效」**：

`WHERE a=1 AND b>2 AND c=3` 中，索引定位只能到 `a=1 AND b>2` 这个区间。在这个区间内，记录是按 b 有序的，但 **c 只有在 (a,b) 都相同时才有序**。因为 b 是一个范围（b=3,4,5...），不同的 b 值下面 c 都是各自有序的，全局无序 → **c 无法用于索引定位**。

但 c=3 这个条件不会浪费：MySQL 5.6+ 会在**存储引擎层**用 c 做过滤（**索引下推 ICP**，见 1.7），`Extra` 显示 `Using index condition`。

**实战推论（很重要）**：设计联合索引时，**等值查询的列放前面，范围查询的列放最后**。例如"查某个用户某时间段的订单"：`idx(user_id, created_at)` 而不是 `idx(created_at, user_id)`。

**MySQL 8.0 的补充：索引跳跃扫描（Index Skip Scan，8.0.13+）**

在特定条件下（a 的基数很小），`WHERE b=2` 也可能用上 (a,b) 索引：优化器会把 a 的每个不同值都当成一次独立的等值查询，做多次区间扫描（类似"跳跃"）。**但这是优化器的补充手段，不是常规能力，代价高、基数大时不会启用，所以不能依赖**。面试时提一句"8.0 有 skip scan，但依赖基数，不能作为设计依据"是很好的加分项。

### 1.7 索引下推（Index Condition Pushdown，ICP）

**背景：MySQL 5.6 引入**。"下推（pushdown）"指的是：**把本应在 Server 层做的过滤，下推到存储引擎层做**。

#### 没有 ICP 时（5.5 及以前）

```sql
SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
-- 索引 idx_name_age(name, age)
```

执行流程：

```
Server 层（优化器/执行器）
    ↓ 只有 name 这一个条件下推
存储引擎层（InnoDB）
    1. 在 idx_name_age 上扫描 name LIKE '张%' → 假设命中 10000 条
    2. 每条都回表（10000 次回表！）
    3. 把 10000 条完整行返回给 Server 层
Server 层
    4. 再逐行过滤 age = 20 → 假设只剩 10 条
```

**浪费点**：age 明明就在索引里，却要回表 10000 次才把它过滤掉。

#### 有 ICP 时（5.6+）

```
存储引擎层（InnoDB）
    1. 在 idx_name_age 上扫描 name LIKE '张%'
    2. 在索引上直接判断 age = 20，不满足的直接跳过（不过滤出 10000 条，只留 10 条）
    3. 只对满足全部索引条件的 10 条回表
Server 层
    4. 收到 10 条，无需再过滤
```

**回表次数从 10000 降到 10**，这就是 ICP 的价值。

**`EXPLAIN` 上怎么看**：`Extra` 列出现 **`Using index condition`**。

**ICP 的适用条件**：
- 只适用于**二级索引**（聚簇索引本身就是全行，无需下推）；
- 适用于 `range`、`ref`、`eq_ref`、`ref_or_null` 等访问类型；
- 条件下推的是**索引中存在的列**（如上面的 age），索引上没有的列无法下推；
- **不适用于子查询**、触发器等场景。

**易错点（面试陷阱）**：
- `Using index condition` = 用到了 ICP，**仍然要回表**；
- `Using index` = 覆盖索引，**不需要回表**；
- 两者可能**同时出现**（某些列覆盖、某些条件下推）。

### 1.8 为什么 `LIKE '%xxx'` 不走索引？

**根本原因**：B+ 树是**按列的完整值有序**的（本质是按字典序比较），所以可以二分定位。而 `LIKE '张%'` 是**前缀匹配**，它能确定"从'张'开始，到'张'后面最后一个 Unicode 字符为止"这个连续区间，所以能用二分定位到起点 → **走 range 扫描**。

`LIKE '%张'` 或 `LIKE '%张%'` 则是"包含"语义，**它匹配的值在整个 B+ 树里是离散的**：

```
name 索引叶子: '李四' ... '张三' ... '小张' ... '张伟' ... '老张'
                    ↑匹配      ↑匹配     ↑匹配      ↑匹配
             命中的记录散布在整棵树上，无法确定扫描起点
```

既然无法确定起点，**只能从头到尾把整棵索引扫一遍**（全索引扫描），或者干脆全表扫描。于是走索引没有任何好处，反而多一次回表，**优化器基于成本（Cost）会主动放弃它**。

**追问：那 `LIKE '%张%'` 怎么优化？**（这是真正体现工程能力的地方）

1. **倒排/全文索引**：MySQL 5.6+ 的 `FULLTEXT`（中文需 ngram 分词器 `ngram_token_size`）或用 **Elasticsearch**（推荐，尤其日志/检索类）；
2. **反转存储 + 前缀匹配**：存一列 `name_reverse`（如"张三"→"三张"），把 `LIKE '%张'`（后缀匹配）变成 `LIKE '张%'`（前缀匹配）走索引。适合"按手机号后四位查"这类固定后缀场景；
3. **如果一定要走索引**：`LIKE '%张%'` 但 SELECT 的列全在索引里 → 会是 `Using index` 的**全索引扫描**（比全表扫描快，因为索引小、无需回表），可以作为兜底;
4. **业务侧限制**：限制搜索字数、加时间范围缩小扫描区间（`WHERE created_at > '2026-01-01' AND name LIKE '%张%'`，先用其他索引把范围缩小）；
5. **搜索引擎兜底**：真正的模糊搜索需求交给 ES，MySQL 只做精确查询。

**结合项目话术**：AI 漏洞研判系统里做专家经验知识库检索时，我们没有用 `LIKE '%关键词%'`，而是走了 PostgreSQL 的 pgvector 向量检索 + 全文索引的混合方案，因为模糊匹配在大数据量下必然全表扫描。如果回到 MySQL 场景，同样的思路就是**能用前缀绝不用中缀，中缀检索交给 ES**。（可结合 **AI 漏洞研判系统** 作答）

### 1.9 索引失效场景全汇总（面试最爱问"你说说有哪些情况索引会失效"）

先纠正一个认知：**"索引失效"其实有两种完全不同的原因**，能分清这个，回答的层次立刻不一样：

- **A 类：结构上用不了**（B+ 树的有序性被破坏）—— 确定失效；
- **B 类：优化器基于成本主动放弃**（能用但"不划算"）—— 可能"看起来失效"。

#### A 类：结构上无法使用

| # | 场景 | 例子 | 原因 |
|---|---|---|---|
| 1 | **不满足最左前缀** | 索引 (a,b)，`WHERE b=1` | 见 1.6 |
| 2 | **范围条件后面的列** | 索引 (a,b,c)，`WHERE a=1 AND b>2 AND c=3`，c 不用于定位 | 见 1.6 |
| 3 | **在索引列上做运算/函数** | `WHERE YEAR(created_at)=2026`、`WHERE id+1=10` | 索引里存的是**原值**，不是函数结果 |
| 4 | **隐式类型转换（列侧）** | `phone` 是 `VARCHAR`，写 `WHERE phone = 13800000000` | 等价于 `CAST(phone AS INT)`，触发函数运算 |
| 5 | **`LIKE '%x'`** | `WHERE name LIKE '%张%'` | 无法确定扫描起点 |
| 6 | **`OR` 两侧有未索引列** | `WHERE a=1 OR d=2`（d 无索引） | 必须全表扫描才能保证语义 |
| 7 | **排序/分组列与索引顺序不一致** | 索引 (a,b)，`ORDER BY b`；或 `WHERE a=1 ORDER BY c`（索引 (a,b,c)） | 索引不保证该列全局有序 → filesort |
| 8 | **排序方向不一致** | 索引 (a ASC, b ASC)，`ORDER BY a ASC, b DESC`（8.0 前） | 8.0+ 支持降序索引 `(a ASC, b DESC)` |
| 9 | **字符集/排序规则不一致的 JOIN** | `t1.utf8mb4 JOIN t2.utf8` | 需要转换后才能比较 |

**重点讲透第 3、4 条（面试最高频）**：

```sql
-- ❌ 反面教材：索引列上做函数运算
SELECT * FROM orders WHERE YEAR(created_at) = 2026;
-- ✅ 改成范围查询，把函数移到常量侧
SELECT * FROM orders WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- ❌ 隐式转换：phone 是 VARCHAR(11)
SELECT * FROM user WHERE phone = 13800000000;
-- MySQL 会把 phone 转成数字再比较：CAST(phone AS SIGNED) = 13800000000 → 索引失效
-- ✅ 加引号，或者用参数化查询时确保 Go 传的是 string
SELECT * FROM user WHERE phone = '13800000000';
```

**Go/GORM 中的对应坑（非常有实战感，面试说出来很加分）**：

```go
// ❌ GORM 里写原生 SQL 片段，最容易踩函数坑
db.Where("DATE(created_at) = ?", date).Find(&orders)

// ✅ 用范围
db.Where("created_at >= ? AND created_at < ?", start, end).Find(&orders)

// ❌ 用了 sql.NullString / 空字符串，导致隐式转换
// ✅ 参数化查询本身没问题，问题是列类型和参数类型不一致
```

> **注意反例说明（避免被面试官反杀）**：`WHERE int_col = '123'` 是**不会**失效的——因为常量侧转换不影响列的有序性（`123` 转成数字后仍然能用索引定位）。**只有"列被转换"才失效，"常量被转换"不失效**。这个细节一定要说清楚。

**MySQL 8.0 的补救：函数索引（Functional Index）**

```sql
-- 8.0.13+ 可以为函数表达式建索引
ALTER TABLE orders ADD INDEX idx_year ((YEAR(created_at)));
-- 此时 WHERE YEAR(created_at) = 2026 就能走索引了
-- 本质是建了一个隐藏的虚拟生成列（Generated Column）+ 索引
```

#### B 类：优化器基于成本主动放弃

**这是"为什么我建了索引却不走"的常见答案**，很多人答不上来：

优化器（`best_access_path` → `Cost_model`）会比较"走索引 + 回表"和"全表扫描"的成本：

- **走二级索引的成本** ≈ 扫描索引页的成本 + **回表次数 × 回表成本**（随机 IO）；
- **全表扫描的成本** ≈ 扫描聚簇索引全部页的成本（顺序 IO，且有预读优化）。

**当查询要返回的行占全表的比例很高（经验值 20%~30% 以上）时，回表带来的随机 IO 成本会超过全表扫描**，优化器就会选择全表扫描。此时 `EXPLAIN` 的 `type=ALL`、`key=NULL`。

**典型场景**：
```sql
-- status 只有 0/1 两个值，查 status=1 命中 80% 的行 → 优化器选全表扫描
SELECT * FROM orders WHERE status = 1;
```
**解决**：这种**低基数列单独建索引意义不大**，应该建**联合索引**（如 `(status, created_at)`）让索引本身有更强的过滤能力，或者用**覆盖索引**消除回表成本。

**"索引区分度/基数（Cardinality）"**：可以用 `SHOW INDEX FROM t` 看 `Cardinality` 列（近似值，由采样统计得出，不是精确值）。区分度 = 不同值数量 / 总行数，越接近 1 越好。**性别、状态、是否删除这类低基数列，不适合单独建索引**。

> **`EXPLAIN` 的 rows 估算不准怎么办？** → `ANALYZE TABLE t` 重新采集统计信息；`innodb_stats_persistent=ON` 让统计信息持久化（8.0 默认开启），避免重启后统计信息丢失导致执行计划突变。

### 1.10 本节高频 Q&A

**Q1：一张表建了很多索引，会有什么问题？**

> **参考回答**：索引不是免费的，代价有三块。第一是**空间**：每个二级索引都是一棵独立的 B+ 树，叶子存索引列 + 主键，我的经验是一张表索引总大小经常超过数据本身。第二是**写入性能**：INSERT 要改 1 棵聚簇索引 + N 棵二级索引，UPDATE 如果改了索引列，还要先删后插，等于写放大 N 倍；同时索引页的变更也进 redo log，磁盘 IO 和锁竞争都会增加。第三是**优化器负担**：可选的索引越多，优化器估算执行计划的成本越高，还可能选错。所以我的实践原则是：**单表索引控制在 5 个左右；联合索引优先于多个单列索引（能用 (a,b) 覆盖 a 和 a,b 两种查询）；写多读少的表要极其克制地加索引；上线前用 `pt-index-usage` 或慢查询日志复盘，把没用到的索引 drop 掉**。在 FlashRoot 的结算流水表上我就踩过这个坑——早期为了方便查询给每个维度都加了单列索引，后来写入 QPS 一上来，插入延迟明显上升，最后合并成了两个联合索引。（可结合 **FlashRoot 结算** 作答）

**Q2：`Select *` 有什么问题？**

> **参考回答**：三个问题。① 破坏覆盖索引：哪怕索引里已经有查询需要的列，`SELECT *` 也会强制回表；② 多传输无用数据、多一次网络往返和内存拷贝，宽表尤其明显；③ 表结构变更（加字段）时，`SELECT *` 会让程序行为隐式改变。我们线上代码规范里是禁止 `SELECT *` 的，GORM 里也是显式 `Select(...)`。（可结合 **POS 数据贯通** 作答）

**Q3：`CHAR` 和 `VARCHAR` 的区别？**

> **参考回答**：`CHAR(N)` 是定长，不足部分用空格补齐，读取时会去掉尾部空格；`VARCHAR(N)` 是变长，用 1~2 字节记录实际长度。选择上：长度固定的（如 MD5 值 32 位、手机号、身份证、性别）用 CHAR，读取不需要额外计算长度，且定长不会产生页内碎片；长度变化大的用 VARCHAR。注意 `VARCHAR(N)` 里的 N 是**字符数**不是字节数，`utf8mb4` 下一个字符最多 4 字节，所以 `VARCHAR(255)` 最坏占 1020 字节，**建索引时要算这个长度，索引列总长度超过 3072 字节（`innodb_large_prefix` + DYNAMIC 行格式）会建不上**。

**Q4：`COUNT(*)`、`COUNT(1)`、`COUNT(字段)` 的区别？**

> **参考回答**：语义上，`COUNT(*)` 和 `COUNT(1)` 都是统计行数（包括 NULL 行），`COUNT(字段)` 只统计该字段非 NULL 的行数。性能上，在 InnoDB 中**三者都需要遍历**——因为 InnoDB 有 MVCC，每个事务看到的行数可能不同，**无法像 MyISAM 那样维护一个精确的行数计数器**。InnoDB 会选择最小的可用索引来扫描，所以 `COUNT(*)` 和 `COUNT(1)` 性能基本一致，`COUNT(字段)` 如果字段上有索引会快一点，没索引就只能扫聚簇索引。补充：`COUNT(*)` 是 SQL 标准语法，优化器会做专门处理，所以**官方推荐用 `COUNT(*)`**。大数据量场景的替代方案是维护计数表（用 `INSERT ... ON DUPLICATE KEY UPDATE cnt = cnt + 1` 原子更新），或者用 Redis 计数器（但要接受不一致）。

**Q5：`UNIQUE` 索引和普通索引的区别？（问的是 change buffer）**

> **参考回答**：查询性能上两者几乎没差别（都能精确定位，唯一索引还能提前终止）。写入时差别很大：**普通索引可以用 change buffer，唯一索引不行**。change buffer 是 Buffer Pool 里的一块内存，作用是缓存"对非唯一二级索引页的修改"——因为非唯一索引不要求唯一，插入顺序无所谓，所以可以先记在 change buffer 里，等之后读到该页时再 merge 进去（一次 merge 可能合并多个操作，把多次随机 IO 变成一次），从而**避免每次写都要把索引页从磁盘读进内存**。而唯一索引的插入必须立即读页判断是否唯一，没法延迟，所以用不上 change buffer。**结论：在业务能接受的前提下，普通索引在写多场景更优**。用 `innodb_change_buffering` 控制（8.0 默认 `all`），`SHOW ENGINE INNODB STATUS` 的 `INSERT BUFFER AND ADAPTIVE HASH INDEX` 段可以看到当前缓冲的记录数和合并情况。

**Q6：讲讲索引的"区分度/基数"，怎么判断一个索引该不该建？**

> **参考回答**：区分度 = `COUNT(DISTINCT col) / COUNT(*)`，越接近 1 表示过滤能力越强。可以用这条 SQL 快速评估：
> ```sql
> SELECT COUNT(DISTINCT col) / COUNT(*) FROM t;
> ```
> 经验值：区分度 > 0.1 的列才有单独建索引的价值。低基数列（性别、状态、逻辑删除标记）不要单独建索引，但可以放到联合索引的**中间或后面**（比如 `(user_id, status, created_at)`，user_id 已经过滤到很少行了，status 作为辅助过滤仍然有意义）。另外注意 `SHOW INDEX` 里的 `Cardinality` 是**采样估算**的，可能不准，`ANALYZE TABLE` 可以刷新。

**Q7：`ORDER BY` 什么时候会 `Using filesort`？怎么避免？**

> **参考回答**：当 MySQL 无法利用索引的有序性来满足排序时，就会 `Using filesort`。要利用索引排序，需要满足两个条件：① `ORDER BY` 的列顺序与索引的最左前缀一致；② 排序方向一致（8.0 之前）；③ `WHERE` 中的等值条件列不破坏排序的有序性。举例，索引 `(a,b,c)`：
> - `WHERE a=1 ORDER BY b,c` ✅ 用索引有序性
> - `WHERE a=1 ORDER BY c` ❌ b 没给等值，c 在全局无序
> - `WHERE a>1 ORDER BY b` ❌ a 是范围，b 全局无序（多个 a 值下各自有序）
> - `WHERE a=1 ORDER BY b DESC, c ASC` ❌ 方向不一致（除非建降序索引）
>
> 另外，`filesort` 有两种算法：**全字段排序**（把所有查询列放进 sort buffer 排序，内存不够就用磁盘临时文件）和 **rowid 排序**（只排 sort buffer 里的"排序键 + 主键"，排完再回表）。MySQL 会自己选，但你可以通过 `max_length_for_sort_data` 影响它。真正的优化建议是：**能让索引天然有序，就不要 filesort；实在不行，控制排序的数据量（先 WHERE 缩小范围再排）**。

**Q8：`IN` 和 `EXISTS` 怎么选？`IN` 会不会导致索引失效？**

> **参考回答**：`IN` 的量少时（几十到几百）会走索引 range 扫描，不会失效；量很大（几千以上）时优化器可能改判成全表扫描，因为回表次数太多。`IN` 和 `EXISTS` 的选择经验：**当子查询结果集小、外表的表大时用 `IN`**（先算出小集合，再驱动大表）；**反之用 `EXISTS`**（对外表每行做一次存在性判断）。不过 MySQL 8.0 优化器已经能把很多 `IN` 子查询自动改写成半连接（semi-join），实际差别不大，**真正该做的是用 `EXPLAIN` 验证，而不是凭经验选**。

**Q9：什么是"索引合并（index merge）"？**

> **参考回答**：当 `WHERE` 里是 `OR` 连接或者多个不同列的条件时，优化器可能会对多个索引分别扫描，然后求交集/并集——`Extra` 显示 `Using union(...)`、`Using intersect(...)`。`type` 是 `index_merge`。它的性能通常不如一个设计良好的联合索引（因为要额外做集合运算），**所以我一般把它当成"索引设计不合理的信号"**：看到 index_merge，通常意味着应该建一个覆盖这些条件的联合索引。可以在优化器开关里关掉它验证：`SET optimizer_switch='index_merge=off'`。

**Q10：为什么主键不建议用业务字段（比如身份证号、手机号）？**

> **参考回答**：四个原因。① **二级索引会膨胀**：所有二级索引的叶子都存主键值，主键多长，每个二级索引就多占多少空间，18 位身份证比 8 字节 BIGINT 大了 2 倍多，所有索引一起膨胀；② **写入随机**：业务字段基本无序，会导致页分裂和随机写；③ **业务可变**：手机号可能会换、身份证号可能出现录入错误需要更正，而主键一旦被二级索引引用，改主键代价极大；④ **安全性**：主键会暴露在 URL、接口返回值里。**正确做法是代理主键（Surrogate Key）= 无业务含义的自增 BIGINT 或雪花 ID，业务唯一键用 UNIQUE 索引约束**。

## 2. 事务与 MVCC

### 2.1 ACID 与它的实现依赖（"ACID 靠什么实现"是必问题）

| 特性 | 含义 | **InnoDB 靠什么实现** |
|---|---|---|
| **A 原子性** (Atomicity) | 事务内的操作要么全成功要么全回滚 | **undo log**（回滚日志）+ 事务回滚段 |
| **C 一致性** (Consistency) | 事务前后数据满足业务约束（唯一键、外键、CHECK） | 是 A/I/D 共同保障的**目的**，不是手段；由约束 + 业务代码保证 |
| **I 隔离性** (Isolation) | 并发事务互不干扰 | **锁（行锁/间隙锁）+ MVCC** |
| **D 持久性** (Durability) | 提交后即使断电也不丢 | **redo log**（WAL，Write-Ahead Logging）+ 双写缓冲 + 刷盘 |

**面试加分答法**：把 C 单独拎出来说——"严格说一致性不是靠某个机制实现的，它是 A、I、D 三个机制共同作用的结果，再加上数据库的完整性约束（唯一索引、外键、CHECK、NOT NULL）和应用层的业务校验。如果面试官问'ACID 里哪个最重要'，我会答一致性，因为它是目的，其他三个是手段。"

**顺带把三种日志的区别讲清楚（高频追问，也解释"为什么有了 binlog 还要 redo log"）**：

| 日志 | 层级 | 内容 | 作用 | 写入时机 |
|---|---|---|---|---|
| **redo log** | InnoDB 引擎层 | 物理逻辑日志（页号 + 偏移 + 修改内容），**循环写**，固定大小（`innodb_log_file_size`） | **崩溃恢复**（crash-safe），保证 D | 事务执行中持续写，**prepare 阶段就写盘** |
| **undo log** | InnoDB 引擎层 | 逻辑日志（反向操作，如 INSERT 对应 DELETE） | **回滚 + MVCC 版本链** | 事务执行中写 |
| **binlog** | MySQL Server 层 | 逻辑日志（statement / row / mixed 格式），**追加写**，不覆盖 | **主从复制 + 数据恢复（PITR）** | 事务**提交时**写 |

**为什么需要两份日志？（超高频）** 因为 redo log 是 InnoDB 独有的，而 binlog 是 Server 层的（MyISAM 也有）。早期 InnoDB 不是 MySQL 默认引擎；另外两者职责不同——redo log 是**崩溃恢复**用的物理日志、循环写容量有限；binlog 是**归档与复制**用的逻辑日志、需要长期保留全量。

**两阶段提交（2PC）**（事务提交流程，必背）：

```
1. InnoDB 写 redo log，标记为 prepare 状态
2. Server 层写 binlog
3. InnoDB 把 redo log 改成 commit 状态
```

**为什么需要 2PC？** 为了保证 redo log 和 binlog 的**逻辑一致**，否则主从/备份恢复会出现数据不一致：

- 若先写 redo 再写 binlog，redo 写完但 binlog 没写时崩溃 → 本机数据是新的，但从库/备份恢复出来的数据是旧的 → **主从不一致**；
- 若先写 binlog 再写 redo，binlog 写完但 redo 没写时崩溃 → 从库重放 binlog 得到了新数据，本机却是旧的 → **不一致**。

**崩溃恢复规则**：
- redo log 里是 **commit** → 直接提交；
- redo log 里是 **prepare**，检查对应 binlog **是否存在且完整** → 是则提交，否则回滚。

> 追问：**prepare 状态的 redo log 写完之后，事务算提交了吗？** —— 不算，此时事务还没真正完成，还需要 binlog 落盘 + redo 状态改为 commit。这也是为什么 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1` 被称为"双 1 配置"（金融级持久性保证），代价是每次提交都要 fsync 两次，性能下降明显。**生产环境的常见折中是 `innodb_flush_log_at_trx_commit=2`（写 OS cache，不 fsync）+ `sync_binlog=1`**（binlog 必须 fsync，因为它还承担复制职责），这是很多大厂的标准配置，面试说出来很加分。

### 2.2 ACID 的 I：四种隔离级别与三种读现象

#### 三种"读"现象的精确定义（面试问的是定义，别答混）

| 现象 | 定义 | 例子 |
|---|---|---|
| **脏读** (Dirty Read) | 事务 A **读到了事务 B 未提交**的修改 | B 把余额 100 改成 200（未提交），A 读到 200；B 回滚 → A 读到了从不存在的值 |
| **不可重复读** (Non-Repeatable Read) | **同一事务内，两次读同一行结果不同**，因为中间有其他事务**提交了 UPDATE/DELETE** | A 第一次读余额 100；B 改成 200 并提交；A 再读得到 200 |
| **幻读** (Phantom Read) | **同一事务内，两次执行同样的范围查询，结果集的行数变了**，因为其他事务**提交了 INSERT** | A 查 `WHERE age > 20` 得 3 行；B 插入一行 age=25 并提交；A 再查得 4 行 |

**关键区别（面试常用来分辨你是否真懂）**：
- 不可重复读针对 **UPDATE/DELETE**，关注的是**同一行的值变了**；
- 幻读针对 **INSERT**，关注的是**结果集多了/少了行**。

#### 四种隔离级别对照表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | MySQL 默认 | 实现 |
|---|---|---|---|---|---|
| **READ UNCOMMITTED** (读未提交) | ❌ 可能 | ❌ 可能 | ❌ 可能 | | 直接读最新数据，无 MVCC |
| **READ COMMITTED** (读已提交) | ✅ 解决 | ❌ 可能 | ❌ 可能 | Oracle/PG 默认 | **每次 SELECT 都生成新 ReadView** |
| **REPEATABLE READ** (可重复读) | ✅ 解决 | ✅ 解决 | ✅ **基本解决**（靠间隙锁+MVCC） | **✅ MySQL 默认** | **只在第一次 SELECT 生成 ReadView 并复用** |
| **SERIALIZABLE** (串行化) | ✅ | ✅ | ✅ | | 读也加共享锁，事务串行 |

**查看和设置**：

```sql
-- 查看当前会话/全局隔离级别
SELECT @@transaction_isolation;          -- MySQL 8.0（5.7 是 @@tx_isolation）
-- 设置（会话级）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 设置（全局，需重启或对新连接生效）
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 配置文件标准写法（my.cnf）
-- [mysqld]
-- transaction-isolation = READ-COMMITTED
```

#### 用两个会话演示（面试白板题，务必能画出来）

**准备**：

```sql
CREATE TABLE account (
  id      BIGINT PRIMARY KEY AUTO_INCREMENT,
  name    VARCHAR(32),
  balance DECIMAL(18,2)
) ENGINE=InnoDB;
INSERT INTO account(name, balance) VALUES ('tom', 100);
```

**① 脏读（READ UNCOMMITTED）**

```sql
-- 会话 A                                    -- 会话 B
SET SESSION TRANSACTION ISOLATION
  LEVEL READ UNCOMMITTED;
BEGIN;
SELECT balance FROM account
  WHERE name='tom';  -- 100
                                             BEGIN;
                                             UPDATE account SET balance=200
                                               WHERE name='tom';
                                             -- 未提交！
SELECT balance FROM account
  WHERE name='tom';  -- ⚠️ 读到 200（脏读）
                                             ROLLBACK;
-- 会话 A 读到的 200 从未真实存在过
```

**② 不可重复读（READ COMMITTED 下会发生，RR 下不会）**

```sql
-- 会话 A（RR 或 RC）                        -- 会话 B
BEGIN;
SELECT balance FROM account
  WHERE name='tom';  -- 100
                                             BEGIN;
                                             UPDATE account SET balance=200
                                               WHERE name='tom';
                                             COMMIT;
SELECT balance FROM account
  WHERE name='tom';
-- RC 下: ⚠️ 200（不可重复读）
-- RR 下: ✅ 100（MVCC 快照，可重复读）
COMMIT;
```

**③ 幻读（RR 下 MVCC 也挡不住的经典场景）**

```sql
-- 表: t(id INT PRIMARY KEY, c INT, d INT)
-- 会话 A（RR）                              -- 会话 B
BEGIN;
SELECT * FROM t WHERE d > 10;  -- 3 行（快照读）
                                             BEGIN;
                                             INSERT INTO t VALUES (15, 15, 15);
                                             COMMIT;
-- ① 再快照读：仍然是 3 行（MVCC 挡住，不幻读）
SELECT * FROM t WHERE d > 10;  -- 3 行 ✅
-- ② 做一次当前读的 UPDATE
UPDATE t SET c = 100 WHERE d > 10;
-- ⚠️ 提示 "Rows matched: 4" —— 更新到了"不存在"的第 4 行！
-- ③ 再快照读：变成 4 行，且新行的 c 已被改成 100
SELECT * FROM t WHERE d > 10;  -- ⚠️ 4 行（幻读！）
COMMIT;
```

**这个例子的意义（面试必讲）**：**InnoDB 的 RR 只在"快照读"下解决了幻读；一旦事务里出现"当前读"（UPDATE/DELETE/`SELECT ... FOR UPDATE`），它就会看到其他事务新插入的行**——因为当前读必须读最新版本，而且会给自己看到的所有行加上 next-key lock。所以严格说，**InnoDB 的 RR 没有完全解决幻读，而是"通过间隙锁阻止了其他事务在本事务的查询范围内插入"来间接防止**——但前提是本事务**先**做过一次当前读把间隙锁住。上面这个例子里，A 的第一次当前读发生在 B 插入提交之后，间隙锁已经来不及阻止了。

**面试官如果追问"那生产上到底该用 RC 还是 RR？"**：
> **参考回答**：MySQL 默认 RR，但**互联网大厂普遍把默认隔离级别改成 RC**（阿里、美团等），理由是：① RC 下没有间隙锁，锁的范围小很多，并发插入的性能明显更好，死锁概率大幅降低；② RC 配合 ROW 格式的 binlog 是安全的主从复制配置，不存在 RR 时代的历史负担；③ RC 的"不可重复读"在业务上往往不是问题——因为业务通常每个事务只读一次（读-改-写模式），不像报表事务需要重复读同一行。代价是：报表类、需要多次读同一数据保证快照一致的事务要自己加 `SELECT ... FOR UPDATE` 或者拆成单条 SQL。**注意改 RC 一定要确认 `binlog_format = ROW`**，否则 statement 格式在 RC 下可能导致主从不一致。

### 2.3 MVCC 原理（本节是全篇技术含量最高的部分）

MVCC = Multi-Version Concurrency Control（多版本并发控制）。一句话概括：**InnoDB 通过"版本链 + 一致性视图"让读操作不加锁就能读到事务开始时的数据快照，从而实现"读不加锁、读写不冲突"**。

它由三样东西构成：**隐藏字段 → undo log 版本链 → ReadView**。

#### 第一块积木：行记录的隐藏字段

InnoDB 每一行记录都有几个用户看不见的隐藏列（源码 `row0mysql.h` / `rem0rec`）：

| 隐藏列 | 长度 | 含义 |
|---|---|---|
| `DB_TRX_ID` | 6 字节 | **最近一次修改该行的事务 ID**（事务 id 是全局递增的） |
| `DB_ROLL_PTR` | 7 字节 | **回滚指针**，指向 undo log 中该行的上一个版本（版本链的链针） |
| `DB_ROW_ID` | 6 字节 | 隐式行 ID，**仅在无主键且无非空唯一索引时存在**，用于构建聚簇索引 |

#### 第二块积木：undo log 版本链

每次修改一行，InnoDB 都会把**旧值**写入 undo log，并让当前行的 `DB_ROLL_PTR` 指向它。多个事务依次修改同一行，就形成一条**版本链**：

```
当前行（最新版本）
┌─────────────────────────────────────────┐
│ id=1  name='C'  age=30                  │
│ DB_TRX_ID = 300  DB_ROLL_PTR ───────────┼──┐
└─────────────────────────────────────────┘  │
                                             ↓
undo log: 版本2  name='B' age=25  TRX_ID=200 ──┐
                                             ↓
undo log: 版本1  name='A' age=20  TRX_ID=100 ──┐
                                             ↓
                                          (链表头，最早版本)
                    ↑ 链头是"最新的旧版本"，越往后越旧
```

**undo log 的两种类型**（源码层 `trx_undo`）：

- **insert undo log**：INSERT 产生的，只在事务回滚时需要（其他事务看不到未提交的插入，因为 MVCC 会把 `DB_TRX_ID` 判断为不可见），**事务提交后可以立即删除**；
- **update undo log**：UPDATE/DELETE 产生的，**提交后不能立即删**，因为 MVCC 后续可能还要用它读旧版本 → 由 **purge 线程**在确认没有更早的 ReadView 需要它之后才清理。

> **延伸面试题**：**"长事务有什么危害？"** 标准答案就藏在这里——长事务会导致 undo log 版本链**无法被 purge**：
> 1. **undo 表空间暴涨**：版本链越来越长，磁盘占用持续增长（`ibdata` / `undo_001` 文件）；
> 2. **purge 跟不上**，History list length 持续增长（`SHOW ENGINE INNODB STATUS` 里的 `History list length`）；
> 3. **锁持有时间长**：行锁一直不释放，阻塞其他事务，**死锁概率大增**；
> 4. **MDL 锁不释放**：阻塞 DDL，进而让后续所有访问该表的查询排队（经典生产事故）；
> 5. **主从延迟**：大事务在从库重放时间长。
>
> **排查**：`SELECT * FROM information_schema.innodb_trx WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;`
> **规避**：把大事务拆小、控制事务内不做 RPC/IO、设置 `innodb_lock_wait_timeout`。

#### 第三块积木：ReadView（一致性视图）

ReadView 是"**事务在某个时刻对全局事务状态拍的一张快照**"，用来判断版本链上哪个版本对该事务可见。核心 4 个字段（源码 `read0types.h` 的 `ReadView` 类）：

| 字段 | 含义 |
|---|---|
| `m_ids` | 生成 ReadView 时，**当前活跃（未提交）的事务 ID 列表** |
| `min_trx_id` | `m_ids` 中的**最小值**（即活跃事务里最小的 id） |
| `max_trx_id` | 生成 ReadView 时**系统应该分配给下一个事务的 ID**（注意：是"下一个"，等于当前最大已分配 id + 1） |
| `creator_trx_id` | **创建这个 ReadView 的事务自己的 ID** |

#### 可见性判断算法（背下来，面试直接手推）

对于版本链上的某个版本，设它的 `DB_TRX_ID = trx_id`：

```
① trx_id == creator_trx_id
   → 这是本事务自己改的，可见 ✅

② trx_id < min_trx_id
   → 该版本由"已经提交的事务"产生（因为它不在活跃列表里，且比最小活跃 id 还小）
   → 可见 ✅

③ trx_id >= max_trx_id
   → 该版本由"ReadView 生成之后才开始的事务"产生，肯定还没提交
   → 不可见 ❌

④ min_trx_id <= trx_id < max_trx_id
   → 落在活跃区间里，需要查 m_ids：
      - trx_id 在 m_ids 中  → 该事务还没提交 → 不可见 ❌
      - trx_id 不在 m_ids 中 → 该事务已提交   → 可见 ✅

⑤ 若当前版本不可见 → 顺着 DB_ROLL_PTR 找上一个版本，重复 ①~④
   直到找到可见版本，或者走到链尾（说明该行对本事务"不存在"）
```

#### RR vs RC 的本质区别（一句话说清，面试最爱的对比）

> **RC 和 RR 在 MVCC 上的唯一区别是：ReadView 的生成时机。**
> - **RC**：**每次**执行快照读（每条 SELECT）都**重新生成**一个 ReadView → 所以能读到别人刚提交的数据 → **不可重复读**；
> - **RR**：只在事务中**第一次**快照读时生成一个 ReadView，**之后整个事务复用这一个** → 所以整个事务看到的是同一个快照 → **可重复读**。

配合上面的可见性算法：RR 下，即使在事务执行中途有其他事务提交了，由于 ReadView 的 `m_ids` 里始终记着那个事务（当时它还活跃），新版本永远被判为不可见 → 实现可重复读。

#### 快照读 vs 当前读（必须能区分）

| | **快照读（一致性读）** | **当前读（锁定读）** |
|---|---|---|
| 读什么 | 走 MVCC，读 ReadView 对应的**历史快照** | 读**最新已提交版本**，并且**加锁** |
| 是否加锁 | 不加锁 | 加锁（S/X 锁、间隙锁） |
| 语句 | 普通 `SELECT` | `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`（8.0: `FOR SHARE`）、`UPDATE`、`DELETE`、`INSERT`、`INSERT ... ON DUPLICATE KEY UPDATE` |
| 隔离级别影响 | RC/RR 差异体现在这 | 各隔离级别都要加锁 |

**面试陷阱题**：**"`UPDATE` 语句里没有索引条件时会怎样？"** → `UPDATE` 是当前读，会扫聚簇索引（无索引 → 全表扫描），并且**给扫描到的每一行都加上 next-key lock**（不是只给匹配的行加！因为扫描过程中访问到的行都会被锁住）。这会导致**锁表级别的效果**，是生产上最危险的场景之一。所以**UPDATE/DELETE 语句的 WHERE 条件一定要走索引**——这不只是性能问题，更是并发安全问题。

### 2.4 本节高频 Q&A

**Q1：请说说 MVCC 的实现原理。**

> **参考回答**（结构化，60 秒讲完）：MVCC 由三部分组成。**第一，行上的隐藏字段**：每行有 6 字节的 `DB_TRX_ID`（最后修改它的事务 id）和 7 字节的 `DB_ROLL_PTR`（指向 undo log 里的上一个版本）。**第二，undo log 版本链**：每次修改都把旧值写进 undo log，用回滚指针串成一条从新到旧的链表。**第三，ReadView**：事务做快照读时生成一个视图，里面有 `m_ids`（当时活跃的事务 id 列表）、`min_trx_id`、`max_trx_id` 和 `creator_trx_id` 四个字段。判断可见性时，拿版本链上每个版本的 `DB_TRX_ID` 去和 ReadView 比：小于 `min_trx_id` 的可见，大于等于 `max_trx_id` 的不可见，落在中间的查 `m_ids` 是否包含它。如果当前版本不可见，就顺着回滚指针找上一个版本，直到找到可见的或链条走完。**RC 和 RR 的区别就在 ReadView 的生成时机：RC 每条 SELECT 都重新生成，RR 只在第一次生成并全程复用**，这就是 RR 能可重复读的原因。（可结合 **POS 数据贯通数据加工** 作答："数据中台做统计加工时，我用 RC 隔离级别并在单个事务里只读一次，避免长事务导致 undo 版本链无法回收。"）

**Q2：为什么 RR 隔离级别下，我明明没读到别人插入的数据，但 UPDATE 却影响了它？**

> **参考回答**：这就是 MVCC 的"快照读"和"当前读"的差异。普通 `SELECT` 是快照读，读的是 ReadView 对应的历史快照，所以看不到后来插入的行；而 `UPDATE`/`DELETE`/`SELECT FOR UPDATE` 是当前读，必须读最新版本才能正确修改，所以能看到。这是 InnoDB RR 没有完全消除幻读的体现。要避免这个问题，就是要让"第一次当前读"尽早发生（间隙锁才会生效），或者干脆接受 RC 隔离级别 + 业务层用唯一约束兜底。

**Q3：为什么 InnoDB 要用 MVCC，不用"读写锁"一套搞定？**

> **参考回答**：如果只有锁，读要加 S 锁、写要加 X 锁，**读会阻塞写、写会阻塞读**，并发度极低——这在"读多写少"的业务里是不可接受的。MVCC 让**读不加锁**，读和写互不阻塞，只有写-写之间才需要锁，并发度提升一个量级。代价是：① 需要额外的存储和维护（undo log + purge 线程）；② 只能保证"读到自己该看到的快照"，对于"必须读最新值"的场景（比如扣库存）还得用当前读 + 锁。**这就是典型的"用空间和版本管理换并发度"的工程权衡**。

**Q4：什么是"一致性读"（consistent read）？它和 MVCC 是一回事吗？**

> **参考回答**：基本是一回事。一致性读指"在 RC/RR 下，普通的 SELECT 会基于一个一致性快照返回数据，不需要加锁"。它由 MVCC 实现。需要注意一个细节：**RR 下，一致性快照是在事务第一次 SELECT 时建立的，而不是 BEGIN 时**——这意味着如果你 `BEGIN` 之后什么也不做，过了 5 分钟才做第一次 SELECT，那么这 5 分钟内提交的数据你是能看到的。这个细节面试时说出来非常加分，因为很多人会答错。

**Q5：`SELECT ... FOR UPDATE` 和 `LOCK IN SHARE MODE` 的区别？**

> **参考回答**：都是当前读、都会加锁，区别在锁的类型：`FOR UPDATE` 加**排他锁（X 锁）**，其他事务既不能读（当前读）也不能写；`LOCK IN SHARE MODE`（8.0 里叫 `FOR SHARE`）加**共享锁（S 锁）**，其他事务可以读但不能写。**用途不同**：`FOR UPDATE` 用于"读-改-写"的悲观锁场景（扣库存、抢单），`FOR SHARE` 用于"我要保证这行在我读的时候不会变"的场景（比如计算依赖多行的报表）。**实际项目里 `FOR SHARE` 用得很少**，因为 S 锁容易和别处的 X 锁形成死锁，收益不明显。

**Q6：`UPDATE` 的执行流程是怎样的？（超高频，把日志串起来）**

> **参考回答**：以 `UPDATE t SET c=c+1 WHERE id=2` 为例：
> 1. **执行器**调用 InnoDB 引擎接口取 id=2 这一行（如果该页在 Buffer Pool 里就直接返回，否则从磁盘读入）；
> 2. 判断是否加锁（当前读，加 X 锁）；
> 3. **写 undo log**（记录旧值，用于回滚和 MVCC）；
> 4. **修改 Buffer Pool 中的页**（内存中的页成为"脏页"）；
> 5. **写 redo log**（标记 prepare）；
> 6. 写 **binlog**；
> 7. **提交事务**，redo log 状态改为 commit。
> 注意：此时**数据文件可能还没更新**（脏页由后台线程异步刷盘）——这就是 WAL 的意义：**先用顺序写日志保证持久性，再慢慢随机写数据页**，把随机写变成了顺序写。如果崩溃，靠 redo log 重放恢复。

**Q7：WAL 是什么？为什么能提升性能？**

> **参考回答**：WAL = Write-Ahead Logging，先写日志再写数据页。性能提升来自两个方面：① **顺序写替代随机写**：redo log 是顺序追加的，而数据页的修改是随机的（要找到对应的页），顺序写磁盘快得多；② **写操作只需一次 fsync**：一个事务可能修改多个页，如果直接刷数据页就要多次随机 IO，而 redo log 只需要一次顺序 fsync 就能保证持久性（配合 `innodb_flush_log_at_trx_commit=1`）。代价是：**崩溃后需要恢复过程**（用 redo log 重放未刷盘的修改），恢复时间与脏页数量相关。

**Q8：什么是 Checkpoint？为什么不把 redo log 设得无限大？**

> **参考回答**：redo log 是**循环写**的（`ib_logfile0`、`ib_logfile1`...），有两个关键指针：**write pos**（当前写到哪）和 **checkpoint**（已经刷盘、可以覆盖的位置）。两者之间的部分就是"还没落盘的日志"。如果 write pos 追上 checkpoint，就必须**停下来先推进 checkpoint（把脏页刷盘）**，这就是一次性能抖动。redo log 不能无限大的原因是：**崩溃恢复时间与 redo log 大小正相关**（要重放的日志更多），而且大文件的管理成本高。所以 `innodb_log_file_size` 是个权衡参数，一般设为 1~2GB（8.0.30+ 用 `innodb_redo_log_capacity` 直接指定总容量，默认 100MB，生产建议调大到几个 GB）。

### 2.5 本节「结合项目」话术提示

- **被问"你们项目用什么隔离级别"** → "MySQL 默认 RR。POS 数据贯通里消费 RabbitMQ 消息写库的场景，我会特别注意两点：一是把 `UPDATE`/`DELETE` 的 WHERE 条件保证走索引，避免当前读导致的大范围 next-key 锁；二是事务里绝不做 RPC 和长耗时操作，把事务边界压到最小。"（**POS 数据贯通**）
- **被问"有没有遇到过幻读"** → "业务的并发插入场景我用唯一索引来兜底而不是依赖间隙锁，因为唯一约束是数据库层面的强保证，不依赖隔离级别的实现细节。"（**LoveSpouse IM 消息幂等 / POS 消费幂等**）
- **被问"长事务怎么排查"** → 直接给 `information_schema.innodb_trx` 的 SQL 和 `innodb_lock_wait_timeout` 的处理策略。

## 3. 锁机制

### 3.1 全局锁

**是什么**：对整个数据库实例加读锁。

```sql
FLUSH TABLES WITH READ LOCK;   -- 简称 FTWRL
-- 此时：其他所有线程的 数据更新（DML）、DDL 全部阻塞
--      其他线程的 普通查询 可以继续
UNLOCK TABLES;
```

**典型用途**：**全库逻辑备份**。备份时如果不用全局锁，会出现"备份了订单表但没备份到对应的支付流水"这种跨表不一致。

**但 InnoDB 有更好的方案**：

```bash
# 官方推荐：利用 RR 隔离级别的一致性快照做备份，全程不需要加全局锁
mysqldump --single-transaction -u root -p dbname > backup.sql
```

> `--single-transaction` 的原理：开启一个 RR 事务，**整个备份过程读到的是同一个一致性快照**（MVCC），因此备份期间业务可以正常读写。**限制**：只对 InnoDB 有效（MyISAM 表仍需要 FTWRL），且不能与 DDL 并发（DDL 会被 MDL 挡住）。

**面试延伸**：如果要求"备份期间业务完全不停"且表很大，可以用 **XtraBackup**（物理备份，通过复制 InnoDB 数据页 + redo log 实现热备）。

### 3.2 表级锁

#### ① 普通表锁

```sql
LOCK TABLES t1 READ, t2 WRITE;
UNLOCK TABLES;
```

- `LOCK TABLES ... READ`：本线程只能读 t1，其他线程也只能读；
- `LOCK TABLES ... WRITE`：只有本线程能读写 t2，其他线程全阻塞。

**注意**：`LOCK TABLES` 与事务的关系很微妙——`LOCK TABLES` 会**隐式提交当前事务**，且 `InnoDB` 中不建议使用（因为 InnoDB 有更好的行锁）。**除了特殊的批量导入场景，生产代码里不应出现 `LOCK TABLES`**。

#### ② 元数据锁（MDL，Metadata Lock）——**生产事故王者**

**不需要显式使用**：访问一个表时自动加，用于保证「表结构」与「表中数据」的一致性：

- 执行 **DML**（SELECT/INSERT/UPDATE/DELETE）→ 加 **MDL 读锁**；
- 执行 **DDL**（ALTER TABLE / DROP 等）→ 加 **MDL 写锁**。

**MDL 读锁之间不互斥**（所以并发的查询/写入不受影响），**读锁和写锁互斥**。

**经典生产事故（一定要能讲出这个故事）**：

```
时刻 1  会话 A：SELECT * FROM t;  （长事务开始，持有 MDL 读锁，事务未提交）
时刻 2  会话 B：ALTER TABLE t ADD COLUMN x INT;  （请求 MDL 写锁 → 被 A 阻塞，排队等待）
时刻 3  会话 C：SELECT * FROM t;  （请求 MDL 读锁 → 被 B 的写锁请求阻塞！）
时刻 4  会话 D、E、F...：全部阻塞，连接池迅速耗尽，整个服务不可用
```

**关键点**：**MDL 的请求是"排队"的，写锁请求会阻塞后续所有的读锁请求**（即使读锁之间不互斥）。所以**一个长事务 + 一个 ALTER 就能让整张表不可用**。

**防护措施**：
1. **DDL 前先检查长事务**：`SELECT * FROM information_schema.innodb_trx WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 10;`
2. **给 DDL 设置等待超时**：`ALTER TABLE t ADD COLUMN x INT, ALGORITHM=INPLACE, LOCK=NONE;`，或在执行前 `SET SESSION lock_wait_timeout = 3;`（宁可 DDL 失败，也不要阻塞业务）；
3. **用 gh-ost / pt-online-schema-change** 做在线 DDL（它们先建影子表、通过 binlog 同步增量、最后原子切换）；
4. **控制事务长度**（这是根治手段）。

> **MySQL 8.0 的升级**：`performance_schema.metadata_locks` 表可以直接查到 MDL 的持有者和等待者，比 5.7 只能靠 `SHOW PROCESSLIST` + `sys.schema_table_lock_waits` 方便很多。

#### ③ 意向锁（Intention Lock，IS / IX）——**表级，但服务于行锁**

**问题背景**：假设事务 A 给表 t 的某一行加了行锁，事务 B 想给整张表加表锁，B 怎么知道表里有没有行锁？**总不能一行一行去扫吧**（那太慢了）。

**解决方案**：**意向锁**。规则是：

- 在给某一行加 **S 锁**之前，必须先给表加 **IS 锁**（意向共享锁）；
- 在给某一行加 **X 锁**之前，必须先给表加 **IX 锁**（意向排他锁）；
- **意向锁之间互相兼容**（IS 和 IX 不冲突，因为不同行可以各自加锁）；
- **意向锁与表锁互斥**：表级的 `S` 锁与 `IX` 互斥，表级的 `X` 锁与 `IS`/`IX` 都互斥。

于是加表锁时只需要**检查表上有没有意向锁**（一次判断，O(1)），不用扫全表。

**兼容性矩阵（背这张表）**：

| 已持有 ↓ / 请求 → | IS | IX | S（表锁） | X（表锁） |
|---|---|---|---|---|
| **IS** | ✅ | ✅ | ✅ | ❌ |
| **IX** | ✅ | ✅ | ❌ | ❌ |
| **S（表锁）** | ✅ | ❌ | ✅ | ❌ |
| **X（表锁）** | ❌ | ❌ | ❌ | ❌ |

**记忆口诀**：`IS/IX` 之间全兼容；意向锁和表锁的 S/X 按"共享兼容、排他互斥"的常规规则；`IX` 和表 `S` 互斥是因为"表级共享锁"通常意味着要读全表，和行级的写意图冲突。

#### ④ AUTO-INC 锁（自增锁）

**用途**：保证 `AUTO_INCREMENT` 生成的 id 连续且不冲突。

**三种模式**（`innodb_autoinc_lock_mode`）：

| 模式 | 名称 | 行为 | 说明 |
|---|---|---|---|
| 0 | traditional | 语句级表锁，**语句执行完才释放** | 保证连续，并发差 |
| 1 | consecutive（5.7 默认） | 普通 INSERT 用轻量互斥量（分配完即释放）；**批量插入（`INSERT ... SELECT`、`LOAD DATA`）仍用表锁** | 保证单语句内连续 |
| 2 | interleaved（**8.0 默认**） | **全部用轻量互斥量**，不用表锁 | 并发最高，但批量插入的 id 可能不连续 |

**为什么 8.0 默认改成 2？** 因为 8.0 默认 `binlog_format=ROW`，**从库重放的是具体的行数据而不是 SQL 语句，所以不需要主从的 id 一致**，可以放心用 interleaved 模式。而 statement 格式的 binlog 下必须保证主从自增 id 一致，所以只能用 0 或 1。

### 3.3 行锁：Record / Gap / Next-Key

**前提**：**行锁是加在索引上的**（这是一个核心认知）。如果你 `UPDATE` 的 WHERE 条件没有用到索引，InnoDB 会**扫描聚簇索引的全部记录并逐行加锁**（等效于锁全表）。

#### 三种行锁

| 锁类型 | 加在哪 | 作用 |
|---|---|---|
| **Record Lock**（记录锁） | 索引记录本身 | 锁住一条索引记录 |
| **Gap Lock**（间隙锁，**RR 独有**） | 索引记录之间的**开区间** | 锁住一个范围，**阻止其他事务在间隙中插入**（注意：只阻止 INSERT，不阻止其他事务在间隙里的记录上加锁） |
| **Next-Key Lock**（临键锁） | 记录 + 它前面的间隙，**左开右闭** `(prev, cur]` | **行锁的默认加锁单位** |

**用图说明**（假设索引上有值 5, 10, 15, 20）：

```
符号:  (-∞,5)  (5,10)  (10,15)  (15,20)  (20,+∞)
              ↑       ↑        ↑        ↑         ← 这些是间隙（Gap）
       5       10      15       20
       ↑       ↑       ↑        ↑                   ← 这些是记录（Record）

Next-Key Lock on 15  =  (10, 15]  ← 左开右闭：包含间隙 (10,15) 和记录 15
Gap Lock on (10,15)  =  只锁间隙，不锁两端的记录
Record Lock on 15    =  只锁记录 15
```

**为什么需要间隙锁？** 为了**防止幻读**。事务 A 执行 `SELECT * FROM t WHERE id > 10 FOR UPDATE`（当前读），如果只锁住已有的记录，事务 B 就能在 (10,+∞) 里插入新记录，A 再查就"多"了行（幻读）。Gap Lock 直接把"可能插入的区间"锁住，B 的插入就会阻塞。

**间隙锁的"可重入"特性**：两个事务可以同时对**同一个间隙**加 Gap Lock（间隙锁之间不互斥），因为间隙锁的唯一目的是阻止插入，而插入才是互斥的。这意味着**间隙锁本身不会造成死锁，但插入意向锁（Insert Intention Lock）会和间隙锁互斥**。

#### 加锁规则（林晓斌《MySQL 45 讲》总结的 5 条，面试官很吃这套）

> **前提**：以下规则基于 RR 隔离级别、`next-key lock` 为默认加锁单位。

1. **加锁的基本单位是 next-key lock**，它是**前开后闭区间**；
2. **查找过程中访问到的对象才会加锁**（所以索引很重要——扫到的行才锁）；
3. **唯一索引上的等值查询，命中记录时，next-key lock 退化为 record lock**；
4. **唯一索引上的等值查询，未命中（`WHERE id = 8` 但表里没有 8），next-key lock 退化为 gap lock**；
5. **唯一索引上的范围查询，会访问到不满足条件的第一个值为止**（多锁一个）。

**举例实战**（表 t，id 主键，有 5,10,15,20；c 列有普通索引，值 5,10,15,20）：

```sql
-- 例1: 唯一索引等值命中 → 退化为 Record Lock
BEGIN;
SELECT * FROM t WHERE id = 10 FOR UPDATE;
-- 加锁: Record Lock on id=10（只锁这一行）
-- 因为主键等值查询，其他事务不可能插入 id=10（已存在），无幻读风险

-- 例2: 唯一索引等值未命中 → 退化为 Gap Lock
BEGIN;
SELECT * FROM t WHERE id = 8 FOR UPDATE;
-- 加锁: Gap Lock on (5, 10)
-- 阻止其他事务插入 id 在 (5,10) 之间的记录，防止幻读

-- 例3: 唯一索引范围查询
BEGIN;
SELECT * FROM t WHERE id >= 10 AND id < 15 FOR UPDATE;
-- 加锁: Record Lock on id=10 + Gap Lock on (10,15) + Record Lock on id=15（多锁一个！）
-- 为什么锁了 15？因为规则5：要"访问到第一个不满足条件的值为止"

-- 例4: 普通（非唯一）索引等值查询
BEGIN;
SELECT * FROM t WHERE c = 10 FOR UPDATE;
-- 加锁: next-key lock on (5,10] + Gap Lock on (10,15)
-- 为什么多一个 gap？因为 c=10 记录后面要扫到下一个记录（c=15）才能确认"没有更多 c=10 的了"，规则4

-- 例5: 无索引（最危险！）
BEGIN;
UPDATE t SET d = d + 1 WHERE d = 100;   -- d 列无索引
-- 结果: 全表扫描，聚簇索引上所有记录 + 所有间隙都被加锁 → 等效锁全表
-- 其他事务的任何插入/更新全部阻塞
```

**最后一个例子是面试的"送命题"**：面试官问"给没有索引的列做 UPDATE 会怎样"，你要能答出**"会加全表的 next-key lock，线上表现为整表写阻塞"**。

### 3.4 死锁

#### 怎么产生的

**死锁的四个必要条件**（操作系统课的内容，数据库同样适用）：互斥、持有并等待、不可剥夺、循环等待。

**经典场景 1：相反顺序更新**

```sql
-- 会话 A                            -- 会话 B
BEGIN;                               BEGIN;
UPDATE t SET v=1 WHERE id=1;  -- 持有 id=1 的锁
                                     UPDATE t SET v=2 WHERE id=2;  -- 持有 id=2 的锁
UPDATE t SET v=1 WHERE id=2;         -- ⚠️ 等待 B 释放 id=2
                                     UPDATE t SET v=2 WHERE id=1;  -- ⚠️ 等待 A 释放 id=1
                                     -- 💥 死锁！
```

**经典场景 2：间隙锁导致的死锁（RR 下特有的，面试高频）**

```sql
-- 表 t 有 id=5, id=10
-- 会话 A                                -- 会话 B
BEGIN;                                   BEGIN;
SELECT * FROM t WHERE id=8 FOR UPDATE;   -- 拿到 Gap Lock (5,10)
                                         SELECT * FROM t WHERE id=8 FOR UPDATE;  -- ✅ 间隙锁兼容，也拿到了
INSERT INTO t VALUES (8);                -- 等待 B 的间隙锁
                                         INSERT INTO t VALUES (9);  -- ⚠️ B 也要插入，
                                         -- B 的插入意向锁被 A 的间隙锁阻塞，A 的插入被 B 的间隙锁阻塞
                                         -- 💥 死锁！
```

**这个例子说明**：间隙锁之间不互斥（所以两个事务都能拿到），但**插入意向锁（Insert Intention Lock）与间隙锁互斥**，形成循环等待 → 死锁。**这是 RR 隔离级别下死锁率明显高于 RC 的根本原因**，也是大厂改用 RC 的核心理由之一。

#### 死锁的处理：InnoDB 的自动检测

InnoDB 有**死锁检测机制**（`innodb_deadlock_detect`，默认 ON）：每次加锁前检查是否会形成环路，如果形成，**主动回滚"代价最小"的那个事务**（通常是修改行数少的），并报错：

```
ERROR 1213 (40001): Deadlock found when trying to get lock;
try restarting transaction
```

**应用层的标准处理（Go 代码）**：

```go
// 死锁是"预期内"的错误，必须捕获并重试，而不是抛给用户
func WithRetry(db *gorm.DB, fn func(tx *gorm.DB) error) error {
    const maxRetry = 3
    for i := 0; i < maxRetry; i++ {
        err := db.Transaction(fn)
        if err == nil {
            return nil
        }
        // MySQL 死锁错误码 1213；锁等待超时 1205
        var mysqlErr *mysql.MySQLError
        if errors.As(err, &mysqlErr) && (mysqlErr.Number == 1213 || mysqlErr.Number == 1205) {
            time.Sleep(time.Duration(i+1) * 50 * time.Millisecond) // 退避
            continue
        }
        return err
    }
    return errors.New("transaction failed after retries")
}
```

> **面试加分点**：主动说出"`innodb_deadlock_detect=ON` 在高并发下本身有成本——每次加锁都要做环路检测，如果锁等待链很长，检测会成为 CPU 瓶颈，所以有些高并发场景会**关闭死锁检测 + 依赖 `innodb_lock_wait_timeout` 超时兜底**"。这是阿里《Java 开发手册》里提到的知名调优案例。

#### 死锁排查的标准流程（面试直接讲这套）

```sql
-- ① 看最近一次死锁现场
SHOW ENGINE INNODB STATUS\G
--    找 "LATEST DETECTED DEADLOCK" 段
--    重点看: 两个事务分别在执行什么 SQL、各自持有/等待什么锁、最后回滚了谁

-- ② 开启全量死锁日志（默认只记录最近一次）
SET GLOBAL innodb_print_all_deadlocks = ON;   -- 日志会写到 error log

-- ③ MySQL 8.0：实时查看锁等待

-- ④ 定位到具体 SQL
SELECT trx_id, trx_state, trx_started, trx_query
FROM information_schema.innodb_trx;
```

#### 怎么避免（面试要给出可落地的清单）

1. **固定访问顺序**：所有事务按同一顺序访问资源（比如都按 id 升序更新），这是**最有效的手段**；
2. **缩短事务**：事务里不写 RPC/HTTP/文件 IO，把"先查再算再写"的耗时操作移出事务；
3. **减小锁范围**：UPDATE/DELETE 的 WHERE 必须走索引（否则锁全表）；用 `LIMIT` 限制批量更新的行数；
4. **降低隔离级别到 RC**：消除间隙锁，可以大幅降低死锁概率（需配合 `binlog_format=ROW`）；
5. **批量操作排序**：批量插入/更新前对 id 排序（如 `INSERT INTO t VALUES (1,...),(3,...),(2,...)` 改成按主键排序）；
6. **避免热点行**：把 `UPDATE counter SET c = c + 1` 这种单行热点改成"分片累加 + 定时汇总"，或改用 Redis 计数（**金币计费场景的经典解法**）；
7. **超时兜底**：`innodb_lock_wait_timeout`（默认 50s，太长）调小到 5~10s，配合应用层重试；
8. **唯一索引防幻读**：用 `INSERT ... ON DUPLICATE KEY UPDATE` 或唯一约束代替"先查再插"（后者在 RR 下会加间隙锁）。

### 3.5 本节高频 Q&A

**Q1：InnoDB 的行锁是加在什么上的？**

> **参考回答**：加在**索引**上的，不是加在数据行上。这是理解 InnoDB 锁的关键。如果一条 `UPDATE` 的 WHERE 条件没有走索引，InnoDB 会扫描整个聚簇索引，给**访问到的每一条记录**都加上 next-key lock，实际效果等同于锁全表。所以"WHERE 条件必须走索引"不只是性能问题，更是并发安全问题——我在写 `UPDATE`/`DELETE` 时一定会先 `EXPLAIN` 一下。（可结合 **POS 数据贯通批量更新** 作答）

**Q2：为什么 RR 要间隙锁，RC 不要？**

> **参考回答**：间隙锁的唯一目的是**防止其他事务在本事务的查询区间内插入新记录**，也就是防幻读。RC 隔离级别本来就允许幻读（隔离级别定义如此），所以不需要间隙锁。而 RC 下因为没有间隙锁，**并发插入的性能更好、死锁概率大幅降低**——这就是互联网公司普遍把生产库改成 RC 的原因。代价是 RC 下如果要防幻读，只能靠应用层的唯一约束或者串行化。

**Q3：什么是插入意向锁（Insert Intention Lock）？**

> **参考回答**：它是一种**特殊的间隙锁**，在 INSERT 之前由事务加上，表示"我打算在这个间隙的某个位置插入记录"。它的作用不是阻止别人，而是**让多个事务在同一个间隙的不同位置插入时不需要互相等待**（比如一个插 6、一个插 8，它们不冲突）。但是**插入意向锁与普通的 Gap Lock 互斥**（间隙锁存在的意义就是阻止插入），这也是间隙锁场景下死锁的来源。

**Q4：`SELECT ... FOR UPDATE` 加了锁，为什么还读到旧数据？**

> **参考回答**：`FOR UPDATE` 是当前读，一定是读最新已提交的数据。如果读到旧数据，可能的原因有：① **锁没锁到你以为的行**——比如 WHERE 条件没走索引，走的是全表扫描，而你观察的行不在扫描范围内；② 用的是 `FOR SHARE`（共享锁），其他事务仍能读到；③ 在 `REPEATABLE READ` 下，如果这条 `FOR UPDATE` 语句**在此之前**本事务已经做过快照读，`FOR UPDATE` 仍然会读最新版本（当前读不受快照影响）——所以这种情况基本不存在；④ 最可能的是**读的其实是另一个事务还没提交的数据被别的事务写入了**。排查时用 `performance_schema.data_locks` 确认到底锁了哪些记录。

**Q5：什么是"锁等待"和"锁超时"？**

> **参考回答**：当一个事务请求的锁被其他事务持有，它会进入等待队列，这就是锁等待。如果等待时间超过 `innodb_lock_wait_timeout`（默认 50 秒），会报 `ERROR 1205 (HY000): Lock wait timeout exceeded`，事务被回滚（但只回滚这一条语句，不是整个事务——这点和死锁不同，死锁是回滚整个事务）。**注意超时的默认值 50 秒对在线业务太长**，建议调小到 5~10 秒，让失败快速暴露而不是拖垮整个服务。排查用 `information_schema.innodb_trx` + `sys.innodb_lock_waits` 找到阻塞源头，`KILL` 掉那个连接（**KILL 前一定确认它是不是关键事务**）。

### 4.1 `EXPLAIN` 逐字段解读（面试必考，要能"看图说话"）

#### 用法

```sql

-- 8.0.19+ 可以看更多信息（如是否用了 ICP、实际使用的索引）
EXPLAIN FORMAT=JSON SELECT ...;

-- 查看优化器代价（诊断"为什么没走索引"的终极武器）

SELECT * FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace="enabled=off";
```

#### 输出示例

```

| id | select_type | table  | partitions | type | possible_keys    | key     | key_len | ref   | rows | filtered | Extra                 |
+----+-------------+--------+------------+------+------------------+---------+---------+-------+------+----------+-----------------------+

#### 逐个字段讲透

**① `id`**

- 查询的序号。**id 相同 → 从上往下顺序执行；id 不同 → id 越大越先执行**（子查询先执行）；
- `id` 为 `NULL` 表示这是一个结果集（如 `UNION` 的合并结果）。

**② `select_type`（查询类型）**

| 值 | 含义 |
|---|---|
| `SIMPLE` | 简单查询，不含子查询/UNION |
| `PRIMARY` | 有子查询时，最外层的查询 |
| `SUBQUERY` | SELECT 列表或 WHERE 里的**非相关**子查询（只执行一次） |
| `DEPENDENT SUBQUERY` | **相关**子查询（依赖外部查询，**每行执行一次，性能杀手**） |
| `DERIVED` | FROM 子句里的子查询（派生表，可能被物化） |
| `UNION` / `UNION RESULT` | UNION 的各分支 / 合并结果 |
| `MATERIALIZED` | 被物化的子查询 |

> **面试点**：看到 `DEPENDENT SUBQUERY` 就要警惕——它是"相关子查询"，外层每扫一行就要执行一次子查询。**优化手段**：改写成 `JOIN` 或 `EXISTS`，或者用临时表先算出结果集。

**③ `type`（访问类型）——最重要的字段**

**从好到坏排序**（背下来，面试直接能说）：

```
system > const > eq_ref > ref > fulltext > ref_or_null > index_merge
       > unique_subquery > index_subquery > range > index > ALL
```

| type | 含义 | 例子 |
|---|---|---|
| `system` | **表只有一行**（系统表），const 的特例 | 极少见 |
| `const` | **通过主键或唯一索引等值查询，最多匹配一行**，优化器在编译期就能确定值 | `WHERE id = 1` |
| `eq_ref` | **JOIN 时被驱动表用主键/唯一索引等值匹配，每行只匹配一条** | `JOIN ... ON t1.id = t2.t1_id`（t2.t1_id 唯一） |
| `ref` | **普通索引等值查询，可能匹配多行** | `WHERE user_id = 100`（user_id 有普通索引） |
| `range` | **索引范围扫描** | `WHERE id > 100`、`BETWEEN`、`IN`、`LIKE 'x%'` |
| `index` | **全索引扫描**（遍历整棵索引树，但比全表快，因为索引小） | `SELECT id FROM t`（覆盖索引但没有过滤条件） |
| `ALL` | **全表扫描**（扫聚簇索引所有页） | 无索引可用 |

**面试要点**：
- 至少要到 **`range`**，**出现 `index` 或 `ALL` 就要审视**；
- **`index` 不一定是坏事**：如果它是"覆盖索引的全索引扫描"（`Extra: Using index`），可能比 `ALL` 快很多，因为索引页比数据页小得多；
- **`type=ALL` 且行数大** → 必须优化。

**④ `possible_keys` / `key` / `key_len`**

- `possible_keys`：**理论上可能用到的索引**（可能为 NULL，表示没有可用索引）；
- `key`：**实际用的索引**（为 NULL 表示没用索引）；
- `key_len`：**实际使用的索引字节长度**。**这是判断"联合索引用到了几列"的关键**。

**`key_len` 计算规则（面试常考）**：

| 类型 | 占用字节 |
|---|---|
| `TINYINT` | 1 |
| `SMALLINT` | 2 |
| `INT` | 4 |
| `BIGINT` | 8 |
| `DATE` | 3 |
| `DATETIME` | 5（8.0 之前是 8） |
| `TIMESTAMP` | 4 |
| `CHAR(N)` | N × 字符集字节数 |
| `VARCHAR(N)` | N × 字符集字节数 + 2（长度前缀） |
| **可为 NULL 的列** | **额外 +1**（用 1 字节标识 NULL） |

**举例**（`utf8mb4` = 4 字节/字符）：

```sql
-- 索引 idx_age_name (age INT NOT NULL, name VARCHAR(50) NOT NULL)
-- 查询: WHERE age = 25 AND name = 'tom'
-- key_len = 4 (age) + 50*4+2 (name) = 4 + 202 = 206

-- 查询: WHERE age = 25
-- key_len = 4   ← 只用到 age 一列

-- 如果 name 允许为 NULL: 50*4+2+1 = 203
```

**面试用法**：**"我通过 `key_len` 判断联合索引实际用到了哪几列，如果比预期短，就说明有列没走上索引，需要检查最左前缀或隐式类型转换。"**

**⑤ `ref`**

显示索引的哪一列被用来做等值匹配，可能的值：`const`（常量）、`func`（函数）、`库名.表名.列名`（JOIN 时的驱动列）。

**⑥ `rows`（重要）**

优化器**预估**需要扫描的行数（**不是精确值**，基于统计信息 + 索引基数估算）。

**面试要点**：
- 这是判断"扫描量大不大"的核心指标；
- **估算可能严重不准**，特别是 UPDATE/DELETE 频繁的表（统计信息不更新）→ `ANALYZE TABLE t` 刷新；
- 8.0 可以用 `EXPLAIN ANALYZE` 看**实际**行数，两者差距大说明统计信息失真。

**⑦ `filtered`**

表示**存储引擎返回的行中，再经过 Server 层条件过滤后，剩余的行所占的百分比**。`filtered = 100` 表示没有额外过滤。`rows × filtered%` 才是"真正参与后续操作的行数估算"。

**⑧ `Extra`（信息量最大，面试最爱问）**

| 值 | 含义 | 好坏 |
|---|---|---|
| **`Using index`** | **覆盖索引**，不需要回表 | ✅ 优 |
| **`Using index condition`** | 用了**索引下推（ICP）**，仍要回表 | ✅ 优 |
| `Using where` | Server 层还要过滤（说明索引没能完全覆盖 WHERE） | ⚠️ 中性 |
| **`Using filesort`** | **无法用索引排序，需要额外排序** | ❌ 差（数据量小时可接受） |
| **`Using temporary`** | **用了临时表**（常见于 GROUP BY、DISTINCT、UNION） | ❌ 差 |
| `Using join buffer (Block Nested Loop / hash join)` | 被驱动表没有索引，用了 JOIN BUFFER | ❌ 差 |
| `Impossible WHERE` | WHERE 条件永远为假（如 `WHERE 1=0`） | ✅ 好（不用扫） |
| `Select tables optimized away` | 优化器直接用索引统计信息返回（如 `SELECT MIN(id) FROM t` 走索引） | ✅ 优 |
| `Using MRR` | 用了 Multi-Range Read，把随机回表改成按主键排序后的顺序回表 | ✅ 优 |
| `Using index for group-by` | 用了松散索引扫描优化 GROUP BY | ✅ 优 |

> **`Using filesort` 与 `Using temporary` 同时出现**是典型的"该重写 SQL"的信号，常见于 `GROUP BY` 非索引列 + `ORDER BY` 非索引列。

### 4.2 慢查询日志与工具链

#### 开启配置（my.cnf）

slow_query_log_file = /var/log/mysql/slow.log

# 记录没有使用索引的查询（慎用，全表扫描的小表也会被记，日志会爆）
log_queries_not_using_indexes = 0
# 记录扫描行数超过 N 行的（比 long_query_time 更能反映"慢"的本质）
min_examined_row_limit = 100
# 日志输出到文件还是表（TABLE 会占用 mysql.slow_log 表空间，一般用 FILE）
log_output = FILE
# 记录管理语句（ALTER/ANALYZE 等）

# 记录从库的慢查询

```

**运行时动态开启（不重启）**：

```sql

SET GLOBAL long_query_time = 1;    -- 注意：只对新连接生效
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
```

> **面试点**：`long_query_time` 的判断依据是**实际执行时间**，不包含等待锁的时间（`lock_time` 单独记录）。所以"锁等待导致的慢"不会出现在慢日志里，要单独看锁等待。

#### 日志内容解读

```
# Time: 2026-09-17T10:23:45.123456Z
# User@Host: app[app] @ [10.0.0.5]  Id: 12345
# Query_time: 3.204512  Lock_time: 0.000123  Rows_sent: 10  Rows_examined: 1580000
SET timestamp=1758100000;
SELECT * FROM orders WHERE DATE(created_at) = '2026-09-17' LIMIT 10;
```

**关键指标**：
- `Query_time`：总执行时间；
- `Lock_time`：等锁时间；
- `Rows_sent`：返回行数；
- **`Rows_examined`：扫描行数 ← 最重要的指标**。

**面试话术**："我看慢查询日志的习惯是先看 `Rows_examined / Rows_sent` 的比值，如果这个比值很大（比如 158000 倍），说明扫描了大量无用数据，问题一定在索引上；如果比值接近 1 但 Query_time 还是很高，可能是锁等待或者返回数据量太大。"

#### 分析工具

```bash
# ① mysqldumpslow（MySQL 自带，轻量）
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log     # 按总耗时排序，取前 10
mysqldumpslow -s at -t 10 -g "SELECT" slow.log       # 按平均耗时排序，只看 SELECT
mysqldumpslow -s c -t 10 slow.log                    # 按出现次数排序

# 排序参数:
#   t  = 按总查询时间   at = 按平均查询时间   c = 按次数
#   r  = 按返回行数     ar = 按平均返回行数  l = 按锁时间
#   al = 按平均锁时间   s  = 按扫描行数
# 附加: -g 正则过滤   -t N 取前 N 条   -a 不把数字抽象成 N

# ② pt-query-digest（Percona Toolkit，功能强大，生产首选）
pt-query-digest /var/log/mysql/slow.log > report.txt
pt-query-digest --since='2026-09-17 00:00:00' --until='2026-09-17 12:00:00' slow.log
# 输出包含: 每条 SQL 的执行次数、总耗时占比、平均耗时、扫描行数分布、执行计划
```

**pt-query-digest 输出的关键解读**：

```

# ==== ================== =============== ====== ======= ===== ==========
#    1 0xABCDEF...1234     1820.5000 45.2%   10000 0.18205 0.02 SELECT orders
#      ↑ 总耗时占比最高的 SQL 优先优化
```

> **面试加分**：说一句"我们线上是**慢查询日志 + APM 链路追踪**结合的，因为慢查询日志只有 SQL 层面的耗时，定位不到是哪个接口、哪个用户触发的；我们会把 `trace_id` 通过 SQL 注释打进去（`/* trace_id=xxx */`），这样从慢日志能直接关联到具体的请求链路。"（这个技巧很实战，说出来面试官会觉得你真的做过生产运维）

### 4.3 常见优化手段清单（背下来，问"你会怎么优化"直接报）

#### A. 索引层面

| 手段 | 说明 |
|---|---|
| **加合适的索引** | 联合索引优先于多个单列索引；等值列在前、范围列在后 |
| **利用覆盖索引** | 减少回表，把 SELECT 列缩到索引里 |
| **最左前缀对齐** | 把高频查询条件放在联合索引最左 |
| **删除无用索引** | 减少写放大和优化器负担 |
| **前缀索引** | 长字符串列（如 URL、UUID）用 `INDEX(url(20))`，牺牲一点精确性换空间 |
| **避免索引失效** | 不在索引列上做函数/运算/隐式转换 |

#### B. SQL 语句层面

| 手段 | 反例 → 正例 |
|---|---|
| **避免 `SELECT *`** | `SELECT *` → `SELECT id, name, price` |
| **避免函数作用于索引列** | `WHERE YEAR(created_at)=2026` → `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| **避免隐式类型转换** | `WHERE phone = 13800000000` → `WHERE phone = '13800000000'` |
| **`OR` 改写为 `UNION ALL`** | `WHERE a=1 OR b=2` → 两个走各自索引的查询 `UNION ALL` |
| **大 `IN` 拆小** | `IN (1000 个值)` → 分批 200 个查，或改成 JOIN 临时表 |
| **`COUNT(*)` 优化** | 维护计数表 或 用近似值 |
| **`LIMIT` 限制返回** | 所有列表查询必须分页 |
| **批量操作** | 1000 次单条 INSERT → 一次批量 INSERT（减少网络往返和事务开销） |
| **`JOIN` 小表驱动大表** | 确保被驱动表（大表）的关联列有索引，让优化器用 Index Nested Loop |
| **减少 `JOIN` 表数** | 超过 3 张表的 JOIN 考虑拆成多次查询或冗余字段 |
| **`GROUP BY`/`ORDER BY` 走索引** | 让分组/排序列与索引顺序一致，避免临时表和 filesort |
| **`UNION ALL` 替代 `UNION`** | `UNION` 要额外去重（用临时表），能用 `UNION ALL` 就用 |

#### C. 表结构与架构层面

| 手段 | 说明 |
|---|---|
| **合适的字段类型** | 能用 `INT` 不用 `BIGINT`；能用 `TINYINT` 不用 `INT`；状态用 `TINYINT` 不用 `VARCHAR` |
| **`NOT NULL` + 默认值** | 避免 NULL 判断，节省 1 字节（`key_len` 会小），也避免 `IS NULL` 无法用索引的情况 |
| **大字段拆表** | `TEXT`/`BLOB` 拆到扩展表（避免主表行变大，一页放的行数变少） |
| **分区表** | 按时间 RANGE 分区，查询能分区裁剪（注意：分区键必须在所有唯一索引里） |
| **归档历史数据** | 冷数据定期迁移到历史表 |
| **读写分离** | 主库写、从库读（注意主从延迟，写后立即读要强制走主库） |
| **加缓存** | Redis 缓存热点数据（**但要注意缓存一致性，见 05-Redis**） |
| **分库分表** | 单表数据量或写入量到达瓶颈时的最后手段 |

### 4.4 深分页（Deep Pagination）——面试高频场景题

#### 问题

```sql
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;
```

**为什么慢？** MySQL 的执行过程是：**取出满足条件的 1000010 行，然后丢弃前 1000000 行，返回最后 10 行**。也就是说，**扫描了 100 万行只为了返回 10 行**，`Rows_examined` 巨大，而且如果有回表（`SELECT *`），这 100 万次回表更致命。

#### 优化方案 1：延迟关联（子查询 / JOIN 覆盖索引）

```sql
-- 原 SQL
SELECT * FROM orders WHERE status = 1 ORDER BY id LIMIT 1000000, 10;

-- 优化：先用覆盖索引把"要返回的 10 个主键"找出来，再回表取其余列
SELECT o.*
FROM orders o
INNER JOIN (
    SELECT id FROM orders WHERE status = 1 ORDER BY id LIMIT 1000000, 10
) AS t ON o.id = t.id;
```

**为什么快？** 子查询里的 `SELECT id` 是**覆盖索引查询**（`(status, id)` 索引的叶子直接有 id），不需要回表，扫描虽然还是 100 万行，但都是**索引页的顺序扫描**（比数据页小得多、还能用预读）；真正回表的只有最后 10 行。

**代价**：扫描行数没变，只是"扫描"的成本降低了。**页数越深，效果越有限**。

#### 优化方案 2：游标 / 书签（Seek Method）—— **推荐方案**

```sql
-- 原 SQL：第 100001 页
SELECT * FROM orders WHERE status = 1 ORDER BY id LIMIT 1000000, 10;

-- 优化：记住上一页的最后一条记录的 id（前端传 last_id），用 WHERE 定位起点
SELECT * FROM orders WHERE status = 1 AND id > 1000000 ORDER BY id LIMIT 10;
```

**为什么快？** 用 `id > last_id` 直接**通过索引定位到起点**，不需要扫描并丢弃前面的行，**扫描行数从 100 万降到 10 行**。复杂度从 O(offset + limit) 降到 O(limit)。

**代价**：**不支持"跳页"**（不能直接跳到第 100 页，只能"下一页"），所以适合**无限滚动的信息流**（点赞列表、消息列表、日志列表）。

**Go 实现（游标分页的通用封装）**：

```go
type CursorPage struct {
    LastID int64 `json:"last_id"`
    Limit  int   `json:"limit"`
}

func ListOrders(db *gorm.DB, p CursorPage) ([]Order, error) {
    if p.Limit <= 0 || p.Limit > 100 {
        p.Limit = 20   // 一定要限制上限，防止 limit=100000 拖垮 DB
    }
    var orders []Order
    q := db.Where("status = ?", 1)
    if p.LastID > 0 {
        q = q.Where("id > ?", p.LastID)   // ← 关键：用索引定位起点
    }
    err := q.Order("id ASC").Limit(p.Limit).Find(&orders).Error
    return orders, err
}
```

#### 优化方案 3：业务层面限制

- **不允许跳到太深的页码**（如"最多只能看前 100 页"），Google/Bing 都是这么做的；
- **限制 `LIMIT` 的最大值**（在 DAO 层强制校验，`limit > 1000` 直接拒绝）；
- **总数缓存**：`COUNT(*)` 本身可能很慢 → 用近似值、或者只在必要时才算，或者维护计数表。

#### 方案 4（冷门但加分）：按时间分区 + 预聚合

对日志/流水类海量数据，按天分区，查询时**强制带上时间范围**（如"只能查最近 30 天"），让分区裁剪发挥作用。

> **结合项目话术**：POS 数据贯通里做销售流水的列表查询，数据量大且是"无限滚动"的场景，我采用的是**游标分页（`id > last_id`）+ 强制时间范围**的组合：既避免了深分页的扫描，也让分区/索引裁剪生效。如果是后台管理需要跳页的表格，就用**延迟关联 + 限制最大页数**。**这个"按场景选方案"的答法比背一种方案要好得多。**

### 4.5 大表优化与分库分表

#### 先问"多大算大表"

不是看行数，而是看**是否出现瓶颈**：

| 信号 | 说明 |
|---|---|
| 单表数据文件 > 几十 GB | 备份恢复时间长、DDL 困难 |
| 查询出现 4 层 B+ 树 | 每查一次多一次 IO |
| 加索引/改结构需要数小时 | DDL 窗口不可接受 |
| 单库 QPS / 连接数打满 | 单机写入瓶颈 |
| 主从延迟持续增长 | 大事务/高写入 |

#### 优化路径（**按代价从低到高，依次尝试**，这个顺序很重要）

```
① SQL 与索引优化（成本最低，收益最高）
        ↓ 还不够
② 加缓存（Redis 挡读）
        ↓ 还不够
③ 读写分离（主写从读）
        ↓ 还不够
④ 垂直拆分（大字段拆表、冷热数据拆表、按业务拆库）
        ↓ 还不够
⑤ 水平分表（同库分表 → 分库分表）
        ↓
⑥ 换存储（TiDB / ClickHouse / ES 等）
```

**面试要点**：一定要强调 **"分库分表是最后的手段，因为它引入的复杂度（分布式 ID、跨片查询、分布式事务、扩容）非常高，能靠前面几步解决就不要分"**。这是有经验的工程师和背八股的人的区别。

#### 水平分表的关键设计

**① 分片键（Sharding Key）的选择**

原则：**查询频率最高、离散度高、能覆盖大部分查询场景**。

- 订单/工单类 → `user_id` 或 `customer_id`（因为查询总是"某用户的订单"）；
- 如果同时要按"商家维度"查 → 要么冗余一份（用 binlog 同步到另一个分片维度的表），要么走 ES 做多维度检索；
- **千万不要用时间做分片键**（除非是按月分表），否则热点全在最新的分片上。

**② 分片算法**

| 算法 | 优点 | 缺点 |
|---|---|---|
| `hash(key) % N` | 分布均匀 | **扩容要重新分布所有数据**（N 变成 N+1 时几乎全部要迁移） |
| **`hash(key) % 2^n`（成倍扩容）** | 扩容时只需迁移一半数据 | 需要预先规划 |
| **一致性哈希** | 扩容只影响邻近节点 | 实现复杂，可能有数据倾斜 |
| **范围分片**（按 id 区间） | 扩容简单（加新片即可） | 热点集中在最新的分片（新数据总是写最后一片） |
| **预分片**（一开始就分 1024 片，映射到少量物理库） | 扩容只需改映射关系，**不用迁数据** | 需要提前规划 |

> **预分片（Pre-sharding）** 是实践中最推荐的方案：一开始就按 1024/4096 个逻辑分片建表，路由表单独存"逻辑分片 → 物理库"的映射，扩容时只需把部分逻辑分片迁到新库 + 改映射。**面试时能说出"预分片"这个词，直接体现你考虑过扩容问题**。

**③ 引入的复杂问题与解法**

| 问题 | 解法 |
|---|---|
| **全局唯一 ID** | 雪花算法（Snowflake）、号段模式（美团 Leaf）、Redis INCR、数据库序列 |
| **跨分片查询** | ① 冗余分片键；② 异构索引表（用 binlog/Canal 同步到另一个维度的表）；③ 走 ES；④ 广播查询 + 内存归并 |
| **跨分片分页/排序** | 各分片取前 N 条，内存归并再取前 N（内存排序大时性能差） |
| **跨分片聚合（COUNT/SUM）** | 各分片算完再汇总；实时性要求不高的走离线数仓 |
| **分布式事务** | 尽量避免跨片事务（把强关联的数据放同一分片）；必要时用本地消息表 / TCC / Seata |
| **扩容** | 预分片 / 成倍扩容 / 双写迁移 |

**④ 常用中间件**

- **ShardingSphere-JDBC**（Java 生态主流，客户端分片）；
- **Vitess**（YouTube 开源，K8s 友好）；
- **TiDB**（分布式 NewSQL，**不用改业务代码**，但对 SQL 有兼容性限制、成本高）；
- Go 生态：**ShardingSphere-Proxy**（代理模式，对 Go 友好）或**业务层手写分片路由**（Go 项目里很常见，因为简单可控）。

> **结合项目话术**：POS 数据贯通的数据是"按产品线 + 门店"维度查询的，如果未来数据量上来，我会选 `shop_id` 作为分片键，因为绝大多数查询都是"某门店的流水"；同时用预分片 + 映射表的方式避免以后扩容要迁数据。分片键的选择一定是**从查询模式倒推**，而不是拍脑袋选主键。（**POS 数据贯通** —— 展示"有架构思考"）

### 4.6 一个完整的慢 SQL 排查案例（面试可以完整讲的故事）

> **面试官问："讲一个你优化慢 SQL 的经历"** → 用这个结构化的故事，STAR 法：

**S（背景）**：FlashRoot 的渠道商后台有个"结算明细列表"，随着刷机记录积累到几百万行，运营反馈页面加载要十几秒。

**T（任务）**：要在不影响线上业务的前提下把接口响应降到 500ms 以内。

**A（行动）**：
1. **定位**：先看慢查询日志，找到 `Rows_examined = 400 万，Rows_sent = 20` 的 SQL，确认是全表扫描 + 深分页；
2. **分析**：`EXPLAIN` 显示 `type=ALL`、`key=NULL`。原因是查询条件写成了 `WHERE DATE(created_at) = ?`，函数作用在索引列上导致索引失效；同时 SQL 用了 `LIMIT 200000, 20` 的深分页；还需要 JOIN 客户表取渠道商名称；
3. **改造**：① 把 `DATE(created_at) = ?` 改成 `created_at >= ? AND created_at < ?` 的半开区间，让 `(customer_id, created_at)` 联合索引生效；② 深分页改成游标分页（前端本来就是"加载更多"的交互）；③ JOIN 客户表改为在应用层批量查（`WHERE id IN (...)`）后内存拼装，消除 JOIN；
4. **验证**：灰度发布，对比优化前后的 `Rows_examined` 和 P99。

**R（结果）**：`Rows_examined` 从 400 万降到 200 行以内，接口 P99 从 8 秒降到 80ms 左右。

**（可结合 FlashRoot 结算 / POS 数据贯通作答）**

### 4.7 本节高频 Q&A

**Q1：怎么定位一条慢 SQL？**

> **参考回答**：分四步。**① 发现**：慢查询日志（`long_query_time`）+ `pt-query-digest` 排序找 TOP SQL，或者 APM 监控发现接口 P99 高；**② 拿到真实 SQL**：注意 ORM 生成的 SQL 往往不是你以为的那条，用 `DryRun` 或者开 GORM 的慢日志把真实 SQL 打出来；**③ 分析**：`EXPLAIN` 看 `type`、`key`、`rows`、`Extra`，重点找 `ALL`/`index`（扫描类型差）、`Using filesort`/`Using temporary`（额外开销）、`rows` 远大于返回行数（索引不精准）；**④ 优化并验证**：改索引或 SQL，重新 `EXPLAIN` 确认，压测对比。如果 `EXPLAIN` 看不出问题，我会用 `OPTIMIZER_TRACE` 看优化器的成本计算过程，确认它为什么放弃了某个索引。

**Q2：`EXPLAIN` 的 `rows` 估算不准怎么办？**

> **参考回答**：`rows` 是基于**索引基数（Cardinality）**和统计信息估算的，不是精确值。不准的常见原因：① 统计信息过期（大量增删后）→ `ANALYZE TABLE` 刷新；② 索引基数采样不准（`innodb_stats_persistent_sample_pages` 默认 20 页，大表可以调大）；③ 多列条件的相关性被忽略（优化器假设列之间独立，实际可能强相关）。**8.0 的 `EXPLAIN ANALYZE` 会给出实际执行的行数和耗时**，是验证估算是否准确的最好工具。如果统计信息和实际差很远导致优化器选错索引，可以用 `FORCE INDEX` 强制指定（但这是下策，治标不治本）。

**Q3：一张表可以建多少个索引？**

> **参考回答**：InnoDB 单表最多 64 个二级索引，联合索引最多 16 列。但**这是上限不是建议值**。实践原则是：**单表索引不要超过 5~6 个**，因为每个索引都要占空间、每次写都要维护。真正该做的是把多个单列索引合并成联合索引——比如有 `(a)`、`(a,b)`、`(b)` 三个索引，其实 `(a,b)` 一个就能覆盖前两个。

**Q4：`JOIN` 的算法有哪些？为什么小表要驱动大表？**

> **参考回答**：三种算法。**① Index Nested Loop Join（INLJ）**：驱动表的每行去被驱动表的索引上查一次，**这是最优的**，前提是被驱动表的关联列有索引；**② Simple Nested Loop Join**：被驱动表没有索引，每行都要全表扫描，**性能灾难**；**③ Block Nested Loop Join（BNL，5.6+）**：把驱动表的数据放进 `join_buffer`，然后扫一遍被驱动表做匹配，减少被驱动表的扫描次数（但仍然是全表扫描）。**8.0.18+ 引入了 Hash Join**：对被驱动表建哈希表，适合等值 JOIN 且被驱动表没索引的场景，比 BNL 快得多。
>
> **"小表驱动大表"的原因**：在 INLJ 里，驱动表的行数 = 对被驱动表的查找次数，所以驱动表越小，总查找次数越少。**注意"小表"指的是参与 JOIN 的列经过 WHERE 过滤后结果集小的表**，不是物理行数少的表。

**Q5：`WITH` / 临时表 / 派生表 有什么性能坑？**

> **参考回答**：派生表（FROM 里的子查询）在 MySQL 5.7 会被**物化成临时表**（没有索引），外层查询对临时表做过滤会全表扫描；MySQL 8.0 引入了**派生表合并（Derived Merge）**优化，能把简单的派生表合并进外层查询，但如果派生表里有 `GROUP BY`、`DISTINCT`、`LIMIT` 等就无法合并，仍会物化。所以实践中**能用 JOIN 就别写派生表**，实在要用的话，注意物化后的临时表是没有索引的。

**Q6：主从延迟怎么排查和解决？**

> **参考回答**：先确认延迟现状：`SHOW SLAVE STATUS\G`（8.0 是 `SHOW REPLICA STATUS`）看 `Seconds_Behind_Master` 和 `Relay_Log_Pos`。**常见原因和处理**：
> - **大事务**（一个事务改了百万行）→ 拆成小批次，每批 500~1000 行；
> - **从库单线程重放**（5.6 之前）→ 开并行复制 `slave_parallel_workers` + `slave_parallel_type=LOGICAL_CLOCK`（基于组提交的并行复制，8.0 默认）；
> - **从库硬件差/有其他查询压力** → 从库只做读，避免跑大报表；
> - **DDL 阻塞** → 用 gh-ost。
>
> **业务侧兜底**：写后立即读的场景（比如下单后跳订单详情）强制走主库；或者用"半同步复制"（`rpl_semi_sync_master_wait_for_slave_count=1`，至少一个从库确认收到才返回）；或者在缓存里放个标记，短时间内的读走主库。

## 5. 数据库设计与 OA 业务建模

> 这一节是**本岗位的差异化重点**。JD 明确写了"有 OA 系统开发经验者优先，熟悉审批流、表单引擎、组织权限等典型 OA 业务场景更佳"，而对应的要求是"具备数据库设计……的实际经验"。所以面试官很可能直接问：**"如果让你设计一个审批流的表结构，你怎么设计？"** 这是本节要准备的核心。

### 5.1 三大范式与反范式

#### 三大范式

| 范式 | 定义 | 违反的例子 |
|---|---|---|
| **第一范式 1NF** | 每一列都是**原子**的，不可再分 | `contact` 列存 "手机:138...,邮箱:a@b.com" |
| **第二范式 2NF** | 在 1NF 基础上，**非主键列完全依赖主键**（消除部分依赖） | 联合主键 `(order_id, product_id)` 的表里放 `product_name`（只依赖 product_id） |
| **第三范式 3NF** | 在 2NF 基础上，**非主键列不传递依赖主键** | 订单表里放 `customer_name`（依赖 customer_id，而 customer_id 依赖 order_id） |

**记忆**：1NF 管"列能不能拆"，2NF 管"依赖主键的全部还是部分"，3NF 管"依赖主键还是依赖非主键"。

#### 反范式（Denormalization）

**为什么要反范式**：范式化的本质是**用 JOIN 换空间和一致性**，但 JOIN 是查询性能的杀手（尤其是分库分表后无法 JOIN）。

**常见的反范式手段**：

| 手段 | 例子 | 代价 |
|---|---|---|
| **冗余字段** | 订单表冗余 `customer_name`、`shop_name` | 客户改名后要同步更新历史订单（或接受历史快照语义） |
| **冗余统计值** | 订单表冗余 `item_count`、`total_amount` | 需要事务保证一致，或用触发器/异步任务 |
| **预计算** | 日结表、月结表 | 需要定时任务维护，实时性差 |
| **宽表** | 数仓里的宽表，把所有维度拍平 | 存储放大，更新困难 |

**面试标准答法（很重要）**：
> "我的原则是**先按三范式设计**（保证数据一致性和可维护性），**只在有明确性能和查询模式证据时才反范式**，并且必须想清楚**冗余数据的一致性怎么保证**。举个例子，OA 的审批单列表要显示申请人姓名和部门名，如果每次都 JOIN 用户表和部门表，在数据量大时很慢；我会选择在审批实例表上冗余 `applicant_name` 和 `dept_name`。**这里的语义要明确：这是"提单时刻的快照"** —— 申请人后来改名或调岗，历史审批单显示的仍然是当时的名字和部门，这在 OA 业务里恰恰是**正确的**（审计要求还原当时的状态），所以这个冗余不仅不牺牲一致性，反而更符合业务语义。而如果是"商品价格"这种必须实时的，就绝不能冗余。"

### 5.2 OA 审批流表设计（**核心中的核心**）

#### 先讲清楚：审批流引擎的通用模型

任何审批流引擎都包含三个层次：

```
【定义层】（Design Time，流程设计器写入，读多写极少）
   流程定义 → 节点定义 → 连线定义
        ↓ 发布（版本化快照）
【运行层】（Runtime，每发起一次审批就产生一条）
   流程实例 → 任务（待办）→ 操作日志
        ↓
【数据层】（业务数据 + 表单数据）
   表单定义 → 表单数据
```

**核心设计原则（面试直接讲这几条，立刻显得专业）**：

1. **定义与实例分离**：流程定义（模板）和流程实例（一次具体的审批）分开存，一个定义对应 N 个实例；
2. **实例引用定义的版本快照**：流程定义一旦被实例引用，就**不能修改**，只能发布新版本（`version` 字段）→ 否则改了流程会让正在跑的审批"变异"；
3. **运行态与历史态分离**：待办表（`approval_task`）只存**待处理的**，办完的移到历史表（`approval_task_history`）或者用 `status` 字段区分 —— **待办表的查询频率极高（每次打开 App 都要查），必须保持在千万级以内**；
4. **表单数据与流程数据解耦**：流程引擎不关心表单里有什么字段，只存 `business_key` 和 JSON 数据；
5. **所有状态变更都落操作日志**：OA 系统是审计系统，任何操作的"谁、何时、做了什么、为什么"都必须可追溯。

#### 设计要点讲解（面试时讲这些，一句顶十句）

**① 为什么 `approval_instance` 要冗余 `applicant_name`、`dept_id`、`dept_name`？**

> 两个原因。**一是语义正确**：OA 是审计系统，审批单上的"申请人/部门"应该是**提单时刻的快照**，员工后来改名或调岗，历史单据不该跟着变。**二是性能**：待办列表和审批列表是最高频的查询，如果每次都要 JOIN 用户表和部门表，在数据量大时开销明显；冗余后单表可查。同时 `dept_id` 还承担**数据权限**的职责——"部门经理只能看本部门的审批单"这个过滤条件要能走索引，所以 `dept_id` 必须落在索引里。

**② 待办列表的索引为什么是 `(tenant_id, assignee_id, status, created_at)`？**

> 因为最高频的查询是"查我的待办，按提交时间倒序"：
> ```sql
> SELECT * FROM approval_task
> WHERE tenant_id = ? AND assignee_id = ? AND status = 0
> ORDER BY created_at DESC LIMIT 20;
> ```
> 这个联合索引的列顺序完全匹配查询：**三个等值条件（tenant_id、assignee_id、status）在前，范围/排序列（created_at）在最后**，所以能同时满足"过滤"和"排序"，`Extra` 里既不会有 `Using filesort`，也不会有回表（如果只需要索引里的列）。这就是 1.6 讲的最左前缀原则在真实业务里的应用。

**③ 待办表为什么不能无限增长？**

> 因为它是**读多写多且查询要求极快**的表（用户每次打开 OA 首页都要查）。**设计上要做的是"任务生命周期结束时把它从待办表移走"**：一种做法是加 `status` 字段区分（简单，但表会持续增长）；更好的做法是**归档**——审批完成后把记录搬到 `approval_task_history`，待办表只保留 `status IN (0)` 的数据。这样待办表永远只有"当前待处理的量级"（通常是万级到十万级），索引小、全内存，查询极快。

**④ 会签（and）和或签（or）怎么实现？**

> 在节点定义上用 `multi_mode` 字段区分，运行时在任务表里生成多条 `approval_task` 记录（每个审批人一条）：
> - **或签**：任意一个人处理完，就把同节点的其他任务置为"已跳过"（`status=5`）；
> - **会签**：所有人处理完（且都同意）才流转到下一节点；只要有一个人驳回，整个实例驳回。
>
> **注意并发**：两个人同时点"同意"，会同时去判断"是不是所有人都同意了"，这就是典型的**并发更新问题**。解法是：**在同一个事务里用 `SELECT ... FOR UPDATE` 锁住实例行**，或者在实例表上维护一个"已完成人数"的计数并使用 `UPDATE ... SET done_count = done_count + 1 WHERE id = ? AND done_count < total` 的原子更新来判断。**这是一个非常好的面试亮点**——它把 OA 业务和 3.x 的锁知识串起来了。

**⑤ 流程定义改了怎么办？**

> 流程定义**版本化，不允许原地修改**。已经发起但未完成的实例，继续按它发起时的版本走（因为 `approval_instance.process_def_id` 指向的是**具体某个版本**的定义，而不是 `process_key`）。新版本只对**新发起**的实例生效。如果业务要求"老单据也要按新流程走"，那属于**流程迁移**，需要单独设计（一般是让运维介入，或者提供一个"流程重定向"的管理功能），不能靠改定义表实现。

**⑥ "撤回 / 驳回 / 加签 / 转办"怎么建模？**

| 动作 | 语义 | 实现 |
|---|---|---|
| **同意 agree** | 当前任务完成，流转到下一节点 | 更新 task 状态 + 生成下一节点的 task + 写日志 |
| **驳回 reject** | 退回 | 有两种语义：**驳回到发起人**（实例状态=驳回，结束）或**驳回到指定节点**（重新激活该节点的 task）；**必须在流程定义里明确配置**，不能各流程各写一套 |
| **撤回 revoke** | 申请人主动撤销 | 只有"还没被人处理过"的实例才能撤回；撤回后实例状态=撤回 |
| **加签 add_sign** | 在**当前节点**增加审批人 | 新增一条 task 记录，`multi_mode` 变成会签语义 |
| **转办 transfer** | 把自己的待办转给别人 | 修改 task 的 `assignee_id`，但要**在日志里记录原审批人**（审计要求） |
| **抄送 cc** | 只是通知，不阻塞流程 | 单独一张 `approval_cc` 表或复用 task 表（`node_type='cc'`，不参与流转） |

**⑦ 超时自动审批怎么实现？**

> 用**定时任务扫描** `approval_task` 的 `due_at`（走 `idx_due` 索引），把超时的任务按定义里的 `timeout_action` 处理（自动通过/自动驳回/提醒）。**注意**：定时任务要**幂等**（用 `UPDATE ... WHERE status = 0 AND due_at < NOW()` 的原子更新抢占，避免多实例部署时重复处理），并且要**分批处理**（一次 500 条）避免大事务。生产中更常见的做法是**延迟消息**（RabbitMQ 的延迟队列 / 定时消息），到点触发，比轮询精准。**（结合 POS 数据贯通的 RabbitMQ 经验：我们用 RabbitMQ 做过延迟消息处理超时未支付的订单，思路完全一样。）**

### 5.3 表单引擎（动态表单）表设计

**需求**：不同审批流程需要不同的表单（请假单有"开始时间/结束时间/事由"，报销单有"金额/发票号/费用类型"）。**不能为每种表单建一张物理表**（那样加一个新流程就要 DDL）。

#### 方案对比（面试要能说出权衡）

| 方案 | 表结构 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **JSON 列**（推荐） | `form_data JSON` | 灵活、读写简单、8.0 支持 JSON 索引 | 无法强约束字段类型、复杂查询难 | **主流方案** |
| **EAV**（实体-属性-值） | `(instance_id, field_key, field_value)` 一行一个字段 | 可以按字段查（`WHERE field_key='amount' AND value > 1000`） | **行数爆炸**（一个表单 20 个字段 = 20 行）、查询要自连接、类型都是字符串 | 字段极少或需要按字段检索 |
| **动态建表** | 每种表单建一张物理表 | 查询最灵活 | DDL 成本高、表数量爆炸、运维灾难 | ❌ 不推荐 |
| **宽表 + 预留列** | 预建 50 个 `field_1..field_50` | 简单 | 浪费、语义不清、扩展性差 | ❌ 不推荐 |

**MySQL 8.0 的 JSON 能力（面试加分）**：

>
> **结合项目话术**：AI 漏洞研判系统里我用 PostgreSQL + pgvector 存漏洞向量和专家经验，思路是一样的——**结构化的元数据（等级、状态、时间）用普通列 + 索引，非结构化的内容（报告正文、向量）用 JSON/扩展类型**，这样既能灵活扩展，又能保证查询性能。（**AI 漏洞研判系统**）

#### 部门树：三种存储方案对比（**面试高频**）

**需求**：查"某部门及其所有下级部门的员工"（数据权限过滤的核心）。

| 方案 | 表结构 | 查子树 | 查祖先 | 移动子树 | 评价 |
|---|---|---|---|---|---|
| **邻接表** `parent_id` | `dept(id, parent_id, name)` | ❌ 递归（MySQL 8.0 前无 CTE，要应用层循环查） | ❌ 递归 | ✅ O(1) | 简单，但查询痛苦 |
| **路径枚举** `path` | `dept(id, path VARCHAR(255))` 存 `0/1/5/12/` | ✅ `WHERE path LIKE '0/1/5/%'` 一条 SQL | ✅ 解析字符串 | ⚠️ 要更新所有子孙的 path | **推荐**，兼顾查询与简单 |
| **闭包表** | `dept_path(ancestor_id, descendant_id, depth)` 存所有祖先-后代对 | ✅ 一次 JOIN | ✅ 一次 JOIN | ✅ 只改受影响的行 | 查询最灵活，但表会膨胀 |
| **嵌套集** `lft/rgt` | `dept(id, lft, rgt)` | ✅ `WHERE lft BETWEEN ? AND ?` | ✅ | ❌ 移动节点要更新半棵树 | 查询快，写入极慢，不推荐 |

**推荐方案：路径枚举 + 冗余父级链**

```sql
CREATE TABLE `sys_dept` (
  `id`        BIGINT       NOT NULL AUTO_INCREMENT,
  `name`      VARCHAR(64)  NOT NULL,
  `parent_id` BIGINT       NOT NULL DEFAULT 0,
  `path`      VARCHAR(255) NOT NULL DEFAULT '' COMMENT '祖先路径，如 0/1/5/12/',
  `level`     TINYINT      NOT NULL DEFAULT 1 COMMENT '层级',
  `sort`      INT          NOT NULL DEFAULT 0,
  `leader_id` BIGINT       NOT NULL DEFAULT 0 COMMENT '部门负责人（审批流取审批人用）',
  `tenant_id` BIGINT       NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_parent` (`parent_id`),
  KEY `idx_path` (`path`(64))   -- 前缀索引，path LIKE '0/1/%' 可用
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ★ 核心查询：某部门及其所有下级的 ID 列表（数据权限过滤用）
SELECT id FROM sys_dept WHERE path LIKE '0/1/5/%' OR id = 5;

-- 用于 IN 子句
SELECT * FROM approval_instance
WHERE dept_id IN (SELECT id FROM sys_dept WHERE path LIKE '0/1/5/%');
```

**这个设计如何支撑"数据权限"？**

```sql
-- 部门经理（data_scope = 2 本部门及以下）看审批列表：
SELECT i.* FROM approval_instance i
WHERE i.tenant_id = ?
  AND i.dept_id IN (
      SELECT id FROM sys_dept WHERE path LIKE CONCAT(?, '%')
  )
  AND i.status = ?
ORDER BY i.created_at DESC LIMIT 20;
```

> **面试要点**：`path LIKE '0/1/5/%'` 是**前缀匹配，能走索引**（这正是 1.8 讲的"LIKE '%x' 不走索引但 LIKE 'x%' 走"的正面应用）。**但要注意**：如果部门树很深、子部门很多，`IN` 子句会很大 → 解法是**限制层级（如最多 5 级）**，或者把权限过滤结果在**用户登录时算好放进 Redis**（部门树变更频率低，非常适合缓存）。**这个"树形结构 + 前缀索引 + 缓存"的组合是 OA 数据权限的标准解法。**

> **MySQL 8.0 的替代方案：递归 CTE**
> ```sql
> WITH RECURSIVE dept_tree AS (
>     SELECT id, name, parent_id FROM sys_dept WHERE id = 5
>     UNION ALL
>     SELECT d.id, d.name, d.parent_id
>     FROM sys_dept d INNER JOIN dept_tree dt ON d.parent_id = dt.id
> )
> SELECT * FROM dept_tree;
> ```
> **注意**：递归 CTE **无法使用索引优化**，每层都要扫，深度大时性能差；而且需要 `cte_max_recursion_depth`（默认 1000）限制。所以**能用在低频场景，不能用在列表查询的 WHERE 里**。

### 5.5 金额字段设计（**结合返点结算项目，高价值**）

#### 结论先行（面试直接说）

> **金额字段用 `DECIMAL`，绝不用 `FLOAT`/`DOUBLE`。**

#### 为什么不用 FLOAT/DOUBLE？

浮点数是**二进制**表示，无法精确表示大多数十进制小数：

```sql
-- 经典演示
SELECT 0.1 + 0.2 = 0.3;                    -- 返回 0（false）
SELECT 0.1 + 0.2;                          -- 0.30000000000000004
SELECT * FROM t WHERE amount = 0.3;        -- 可能查不到原本存 0.3 的记录！

-- 更糟糕的是累加
SELECT SUM(amount) FROM t;                 -- 浮点累加误差会放大
```

**原理**：`0.1` 在二进制里是无限循环小数（就像十进制的 1/3），`float`（4 字节）/`double`（8 字节）只能存近似值。金额计算一旦有误差，**对账就永远对不平**，这在结算系统里是事故。

#### DECIMAL 原理

`DECIMAL(M, D)`：`M` 是总位数（最大 65），`D` 是小数位数（最大 30）。

- **InnoDB 中的存储**：`DECIMAL` 是**以二进制编码的十进制定点数**（BCD 压缩存储，每 9 个十进制位用 4 字节），**精确无误差**；
- **运算规则**：MySQL 中 `DECIMAL` 的算术运算是精确运算（`DECIMAL` 与 `DECIMAL` 运算结果是 `DECIMAL`），但**除法的精度规则**要注意：`DECIMAL` 除法的结果精度 = `DIV_PRECISION_INCREMENT`（`div_precision_increment`，默认 4），即结果的小数位 = 被除数小数位 + 4，需要显式 `ROUND()`。

#### 字段设计建议

```sql
-- 订单/结算金额：DECIMAL(18,2) 或 (18,4)
`amount`      DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '金额，单位元，2 位小数'

-- 单价（可能需要更高精度）：DECIMAL(18,4)
`unit_price`  DECIMAL(18,4) NOT NULL DEFAULT 0.0000

-- 返点比例（可能到万分之一甚至更细）：DECIMAL(9,6) 表示最大 999.999999（即百分比）
`rebate_rate` DECIMAL(9,6) NOT NULL DEFAULT 0.000000 COMMENT '返点比例，如 0.035000 = 3.5%'

-- 也可以用「万分比/基点」存整数，避免比例的小数运算
`rebate_rate_bp` INT NOT NULL DEFAULT 0 COMMENT '返点比例，单位万分比（bp），350 = 3.5%'
```

**两种比例存法的取舍（面试能讲出这个层次非常好）**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| `DECIMAL(9,6)` 存比例 | 直观、可读性好 | 参与乘法运算时有精度舍入问题 |
| `INT` 存万分比/基点（bp） | **运算全是整数，绝对精确**；`金额 * bp / 10000` 中除法是唯一失精点 | 可读性差，需要转换 |

> **实际建议**：如果返点比例是**离散的固定档位**（3.5%、5%、7.5%），用 bp 存整数最安全；如果是**自由输入的比例**，用 `DECIMAL` 但要明确约定精度和舍入规则。

#### 舍入策略（结算系统的核心）

```sql
-- 推荐：由数据库统一用 ROUND 四舍五入到分
SELECT ROUND(amount * rate, 2) FROM ...;

-- 注意 MySQL 的 ROUND 是"四舍五入"，不是"银行家舍入"
SELECT ROUND(2.5);   -- 3
SELECT ROUND(3.5);   -- 4
```

> **在 Go 里怎么处理金额（面试很可能追问）**：
> ```go
> // ❌ 绝对不要用 float64 做金额计算
> var amount float64 = 0.1
> amount += 0.2   // 0.30000000000000004
>
> // ✅ 方案一：用最小单位的整数（分），推荐用于支付/结算核心链路
> type Money int64 // 单位：分
> func (m Money) Yuan() string { return fmt.Sprintf("%.2f", float64(m)/100) } // 仅用于展示
> // 运算：sum := a + b  // 整数加法，绝对精确
> // 乘法：total := Money(int64(price) * int64(qty))  // 整数乘法
> // 分润（按比例）：share := Money(int64(total) * int64(bp) / 10000)
> //   ⚠️ 整数除法会截断，需要明确：截断还是四舍五入？分润的"尾差"归谁？
> //   实践：最后一个人用"总额 - 其他人之和"计算，保证分润之和 == 总额（对账关键）
>
> // ✅ 方案二：用 shopspring/decimal 库（任意精度十进制）
> import "github.com/shopspring/decimal"
> price := decimal.NewFromString("19.99")
> rate  := decimal.NewFromString("0.035")
> total := price.Mul(rate).Round(2)   // 精确十进制运算
>
> // ✅ GORM 扫描 DECIMAL 字段的坑（一定要讲，非常实战）
> // ❌ 用 float64 接收 DECIMAL → 精度丢失（GORM 默认把 DECIMAL 扫成 float64 或 string）
> type Order struct {
>     Amount float64 `gorm:"column:amount"`   // ⚠️ 有精度风险
> }
> // ✅ 用 decimal.Decimal（实现 Scanner/Valuer 接口）或 string 接收
> type Order struct {
>     Amount decimal.Decimal `gorm:"column:amount;type:decimal(18,2)"`
> }
> ```
>
> **一句话总结**："金额在**存储层**用 `DECIMAL`，在**传输层**用字符串（避免 JSON 的 float 转换），在**计算层**用整数分或 decimal 库——**全链路都不出现 `float64`**。"

#### 返点结算的完整设计要点（**FlashRoot 项目的核心话术**）

> **面试官问："讲讲你的返点结算功能怎么设计的？"** → 用这个结构：

**① 数据模型**：

```sql
-- 结算流水（每笔刷机记录产生的返点明细）
CREATE TABLE `settlement_detail` (
  `id`            BIGINT        NOT NULL AUTO_INCREMENT,
  `biz_no`        VARCHAR(64)   NOT NULL COMMENT '业务单号（刷机记录号）——幂等键',
  `customer_id`   BIGINT        NOT NULL COMMENT '渠道商',
  `customer_path` VARCHAR(255)  NOT NULL DEFAULT '' COMMENT '渠道商层级路径，用于多级分成',
  `level`         TINYINT       NOT NULL DEFAULT 1 COMMENT '渠道层级',
  `device_id`     VARCHAR(64)   NOT NULL COMMENT '设备标识',
  `model`         VARCHAR(64)   NOT NULL DEFAULT '',
  `base_amount`   DECIMAL(18,2) NOT NULL COMMENT '计费基数（元）',
  `rebate_rate`   DECIMAL(9,6)  NOT NULL COMMENT '返点比例',
  `rebate_amount` DECIMAL(18,2) NOT NULL COMMENT '返点金额（元）',
  `settle_status` TINYINT       NOT NULL DEFAULT 0 COMMENT '0=待结算 1=已结算 2=已冻结',
  `settle_batch`  VARCHAR(64)   NOT NULL DEFAULT '' COMMENT '结算批次号',
  `created_at`    DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_biz_customer` (`biz_no`, `customer_id`) COMMENT '★ 幂等：同一设备对同一渠道商只结算一次',
  KEY `idx_customer_status` (`customer_id`, `settle_status`, `created_at`),
  KEY `idx_batch` (`settle_batch`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='返点结算明细';

-- 渠道商账户（余额）
CREATE TABLE `customer_account` (
  `id`             BIGINT        NOT NULL AUTO_INCREMENT,
  `customer_id`    BIGINT        NOT NULL,
  `balance`        DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '可用余额',
  `frozen_balance` DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '冻结金额',
  `total_rebate`   DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '累计返点（统计用）',
  `version`        INT           NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
  `updated_at`     DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_customer` (`customer_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='渠道商账户';
```

**② 多级返点怎么算（多级客户数据结构）**：

> 渠道商是**树形结构**（总代 → 省代 → 市代 → 门店），一笔刷机记录要**向上逐级分成**。设计上我用的是**路径枚举**（`customer_path = '0/12/45/103/'`），这样：
> - 一笔业务发生，**一条 SQL 就能拿到所有需要分成的上级**：`WHERE path LIKE '0/12/45/%'`；
> - 每级的分成比例在客户表上配置（不同层级、不同产品线比例不同）；
> - 结算明细表里**每个层级一行**（`UNIQUE(biz_no, customer_id)` 保证幂等），而不是一行存所有层级的 JSON —— 因为**结算和提现是按渠道商维度查的**，一行一渠道商才能走 `idx_customer_status` 索引。
>
> **面试官可能追问："如果层级很深，一笔业务要写很多行怎么办？"** → 答："我们限制了最大层级（业务上不超过 5 级），并且这个写入是**异步的**（通过消息队列），不在业务主链路上。"

**③ 幂等与对账（结算系统的生命线）**：

> - **幂等**：`UNIQUE(biz_no, customer_id)` 唯一索引兜底。消费消息时用 `INSERT ... ON DUPLICATE KEY UPDATE id = id`（或者 `INSERT IGNORE`）来保证"重复消费不重复结算" —— **把幂等交给数据库唯一约束，而不是靠应用层判断"是否处理过"**，这是最可靠的（避免并发下的检查-插入竞态）；
> - **金额一致性**：`UPDATE customer_account SET balance = balance + ?, total_rebate = total_rebate + ? WHERE customer_id = ?` —— **用数据库的原子更新，而不是"先查余额再算再写回"**（后者在并发下会丢更新，除非加锁或用乐观锁）；
> - **对账**：每天定时跑一次"明细汇总 vs 账户余额"的核对，不一致就告警。对账 SQL 用 `SUM(rebate_amount)` 按 `customer_id` 分组，全程 `DECIMAL` 精度，不用浮点；
> - **可追溯**：每笔结算都有 `biz_no`、`settle_batch`，任何金额都能反查到原始业务。

**④ 面试官可能追问的坑**：

| 追问 | 参考回答 |
|---|---|
| 用户提现了怎么办？ | 用"冻结 + 确认"两阶段：提现时 `balance -= x, frozen_balance += x`（一个事务），提现成功后 `frozen_balance -= x`，失败则回滚。**永远不要在提现时就减 balance 而不冻结**，否则重复提现会出错 |
| 比例改了，历史单据要重算吗？ | **不重算**。结算明细里**存的是"计算时刻的比例快照"**（`rebate_rate` 字段），这样才能复现历史。改比例只影响**新产生**的结算。这就是 5.1 讲的"快照语义"的冗余字段 |
| 怎么防止重复结算？ | 唯一索引 + 结算批次号 + 幂等消费（三重保险） |
| 大促期间结算压力大？ | 明细表**只插入**（写为主，按时间归档）；汇总计算异步化；账户余额更新用行锁 + 短事务；热点渠道商的余额更新可以做"批量合并"（累积 N 笔一次性更新） |

### 5.6 通用建表规范 Checklist（面试可以主动说"我们团队的规范是……"）

| 项 | 规范 | 原因 |
|---|---|---|
| **引擎** | 一律 `InnoDB` | 事务、行锁、崩溃恢复、外键 |
| **字符集** | 一律 `utf8mb4` + `utf8mb4_general_ci`（或 `_0900_ai_ci`） | `utf8` 存不了 emoji（3 字节）；`utf8mb4` 才是真正的完整 UTF-8 |
| **主键** | `BIGINT UNSIGNED AUTO_INCREMENT`，**必须有主键** | 无主键会用隐藏 6 字节 ROW_ID；且自增保证顺序写 |
| **主键类型** | 用 `BIGINT` 不用 `INT` | `INT UNSIGNED` 上限 42 亿，业务增长快时容易耗尽；改主键类型是灾难性 DDL |
| **时间字段** | `created_at` / `updated_at`，用 `DATETIME(3)` 或 `TIMESTAMP` | `DATETIME` 不受时区影响（推荐）；`TIMESTAMP` 有 2038 问题、受时区影响。**毫秒精度用 `DATETIME(3)`** |
| **金额字段** | `DECIMAL(18,2)` / `(18,4)`，`NOT NULL DEFAULT 0.00` | 见 5.5 |
| **状态字段** | `TINYINT` + 注释说明枚举含义 | 比 `VARCHAR` 省空间、可索引；**枚举含义一定写进 COMMENT** |
| **布尔字段** | `TINYINT(1)` 或 `TINYINT`，用 `is_xxx` 命名 | MySQL 没有真正的 BOOLEAN |
| **NULL 处理** | 尽量 `NOT NULL DEFAULT ''`/`0` | NULL 占额外 1 字节（影响 key_len）、`IS NULL` 无法用索引、四则运算结果是 NULL、`COUNT(列)` 不算 NULL 行 |
| **字符串长度** | 按需给足，不要一律 `VARCHAR(255)` | 影响索引长度和内存分配 |
| **大字段** | `TEXT`/`BLOB` 拆到扩展表 | 主表行越大，一页放的行越少，索引效率越低 |
| **逻辑删除** | `deleted_at DATETIME(3) NULL`（推荐）或 `is_deleted TINYINT` | **注意坑**：逻辑删除的列**必须放进唯一索引**，否则"删除后重名不能复用"的问题。**更好的做法是物理删除 + 归档** |
| **索引命名** | `uk_xxx`（唯一）/ `idx_xxx`（普通） | 可读性 |
| **外键** | **互联网场景一般不用物理外键** | 外键会导致**跨表加锁**（容易死锁）、影响写入性能、DDL 困难、分库分表后无法使用；改为**应用层保证 + 定期对账** |
| **单表大小** | 控制在 2000 万行以内（经验值） | 见 1.2 的推导 |
| **表注释/字段注释** | **必须写** | OA 系统的表往往要交接给他人维护 |

> **逻辑删除的坑（面试高频追问）**：
> ```sql
> -- ❌ 逻辑删除 + 唯一索引的冲突
> UNIQUE KEY uk_username (username)
> -- 用户 'tom' 被逻辑删除后，无法再注册 'tom'（唯一索引还在）
>
> -- ✅ 解法：把删除标记放进唯一索引
> UNIQUE KEY uk_username (username, deleted_at)
> -- 但 deleted_at 为 NULL 时，MySQL 认为 NULL != NULL，唯一性判断会失效！
> -- 所以更常用：用 is_deleted TINYINT + 删除时置为 id（或时间戳）
> UNIQUE KEY uk_username (username, is_deleted)
> -- 删除时 is_deleted = id（唯一），未删除时 is_deleted = 0
> ```
> **我的建议是**：**能用物理删除 + 归档就不要逻辑删除**。逻辑删除的代价是——所有查询都要带 `deleted_at IS NULL`（容易漏，漏了就是数据泄露），索引选择性变差，表持续膨胀。如果业务确实需要"可恢复"（OA 系统常见），那就把逻辑删除**做在业务层明确的"回收站"表**里，而不是给每张表加 `is_deleted`。

### 5.7 本节高频 Q&A

**Q1：设计一张表，你会考虑哪些点？**

> **参考回答**：我会按这个顺序想。**① 业务语义**：这张表是什么、生命周期多长、读写比例如何；**② 字段**：类型选择（能用小的不用大的）、是否 NOT NULL、金额用 DECIMAL、状态用 TINYINT、大字段拆出去；**③ 主键**：自增 BIGINT 做聚簇索引，业务唯一键用 UNIQUE 索引；**④ 索引**：从查询模式倒推（哪些等值、哪些范围、哪些排序），联合索引的列序遵循"等值在前、范围在后"；**⑤ 容量估算**：单行多大、一年多少行、什么时候需要考虑归档或分表；**⑥ 一致性要求**：哪些字段是同事务强一致，哪些可以异步（决定是否加缓存/消息队列）；**⑦ 安全与合规**：手机号/身份证这类敏感字段是否要加密或脱敏存储。**第 ⑤ 步的容量估算是我觉得最容易被忽略但最重要的**——很多表设计的时候没想清楚数据量，上线半年就要重构。

**Q2：单表数据量多大要分表？**

> **参考回答**：不能只看行数，要看**单行大小 + 访问模式**。我的判断标准是：**B+ 树层高超过 3 层（即树高变 4 层，多一次 IO），或者单表数据文件超过几十 GB，或者 DDL/备份窗口不可接受，或者写入 QPS 打满单机**。用 1.2 的推导，主键 BIGINT + 单行 1KB 时大约是 2000 万行到 4 层。但**分表是最后的手段**——先做 SQL/索引优化 → 缓存 → 读写分离 → 垂直拆分，都不够才水平分表。而且分表前一定要想清楚**分片键**和**扩容方案**（预分片、成倍扩容），否则后期迁移数据的代价极大。

**Q3：为什么互联网公司不推荐用外键？**

> **参考回答**：三个原因。① **性能**：每次插入/更新子表，InnoDB 都要去父表加共享锁做检查，这个锁是跨表的，**并发写入时容易造成锁等待和死锁**；② **运维**：有外键的表做 DDL、数据迁移、归档都极其困难，还需要按依赖顺序处理；③ **架构**：分库分表后外键根本不可能跨库生效，所以从设计之初就不该依赖它。**取而代之的是**：应用层保证引用完整性（先插父记录再插子记录，同一个事务）、定期对账任务扫描孤儿数据、必要时用触发器兜底（但触发器同样不推荐）。

**Q4：`TIMESTAMP` 和 `DATETIME` 怎么选？**

> **参考回答**：`TIMESTAMP` 占 4 字节，存储的是 **UTC 时间戳**，读取时按会话时区转换；范围是 `1970-01-01 ~ 2038-01-19`（**2038 问题**）。`DATETIME` 占 5~8 字节（8.0 之前 8 字节，8.0 起 5 字节 + 小数位），存的是**字面时间**，不受时区影响，范围到 9999 年。**我的选择**：业务表统一用 `DATETIME(3)`（毫秒精度，不受时区影响，跨时区部署时行为可预测），**`created_at`/`updated_at` 用 `DEFAULT CURRENT_TIMESTAMP(3)` 自动维护**。只有需要严格按 UTC 存储并依赖数据库做时区转换时才用 `TIMESTAMP`。**注意**：跨时区业务（比如我们的数字人项目面向海外用户）一定要在应用层统一用 UTC 存储和传输，展示时再转本地时区，不要依赖数据库的时区设置。

**Q5：`id` 用自增还是雪花？**

> **参考回答**：单库单表用自增（顺序写、无页分裂、占空间小）。**分库分表或需要提前生成 ID（比如要在插入前就把 ID 给到前端）时用雪花算法**。雪花 ID 是 64 位（1 位符号 + 41 位毫秒时间戳 + 10 位机器 ID + 12 位序列号），**趋势递增但非严格递增**，所以作为聚簇索引时写入位置基本在右侧，页分裂远少于 UUID，是可以接受的。**注意两个坑**：① **时钟回拨**会导致 ID 重复，必须有检测和处理机制（等待或抛错）；② 雪花 ID 是 19 位数字，**前端 JS 的 Number 精度只有 53 位，会丢失精度**，所以 API 返回给前端时要用 **string 类型**（这也是为什么很多大厂的接口 ID 都是字符串）。

**Q1：一条 SQL 的执行流程是怎样的？（从连接器到存储引擎）**

> **参考回答**：MySQL 的逻辑架构分两层：**Server 层**和**存储引擎层**。一条 `SELECT` 的流程是：
> ① **连接器**：TCP 握手 + 认证（用户名密码、权限），建立连接后权限就固定了（中途改权限不影响已有连接）；
> ② **查询缓存**（8.0 已废弃）：8.0 之前会用 SQL 文本做 key 查缓存，命中直接返回；**因为"任何更新都会清空整表缓存"导致命中率极低，8.0 彻底移除了**；
> ③ **解析器**：词法分析 + 语法分析，生成语法树；
> ④ **预处理器**：检查表/列是否存在、展开 `SELECT *`、处理权限；
> ⑤ **优化器**：基于**成本模型**决定用哪个索引、JOIN 的顺序，生成执行计划（`EXPLAIN` 看到的就是这一步的结果）；
> ⑥ **执行器**：调用存储引擎接口，逐行取数据，做 WHERE 过滤、排序、聚合，返回结果集。
> **存储引擎层**：InnoDB 通过 Buffer Pool 访问数据，缓存未命中就从磁盘读页。
>
> 而 `UPDATE` 的流程多了几个关键步骤（这也是高频追问）：取数据加锁 → 写 undo log → 改 Buffer Pool → 写 redo log（prepare）→ 写 binlog → 提交（redo 改 commit），即**两阶段提交**。

**Q2：`WHERE a = 1 AND b = 2 ORDER BY c` 建立什么索引最优？**

> **参考回答**：建 `(a, b, c)`。因为 `a` 和 `b` 是等值条件（放最左），`c` 是排序列。索引 `(a,b,c)` 在 `a=1 AND b=2` 确定后，`c` 天然有序，所以排序可以直接利用索引，避免 `Using filesort`。
>
> **追问："那如果查询是 `WHERE a = 1 AND c = 2 ORDER BY b` 呢？"** → 这时候应该建 `(a, c, b)`。**原则是：等值条件的列放前面（顺序可交换），排序列放最后。**
>
> **追问："如果 a、b 都是范围条件呢？"** → 那么只有第一个范围列能用于索引定位。所以应该**把选择性更高（过滤后行数更少）的范围列放在前面**，让索引扫描的行数更少。这个"选择性"的判断要基于实际的基数估算，不能想当然。

**Q3：`LIMIT 1` 和 `LIMIT 0,1` 有区别吗？**

> **参考回答**：功能上没区别，都是取第一行。**性能上，`LIMIT 1` 更优**——`LIMIT 0, 1` 里的 `0` 表示 offset，MySQL 需要先"跳过 0 行"，虽然逻辑上等价，但历史上某些版本对带 offset 的写法会多一层处理。**不过这个差异微乎其微，真正重要的是另一个点**：`LIMIT 1` 在**确认唯一性**或**存在性判断**时是重要的性能优化——比如"判断是否存在"用 `SELECT 1 FROM t WHERE ... LIMIT 1` 而不是 `SELECT COUNT(*)`，前者找到一条就返回，后者要扫全部。**这个"存在性判断用 LIMIT 1"的技巧我在实际项目里用得很多。**

**Q4：`UPDATE` 的时候发现"锁等待超时"，怎么处理？**

> **参考回答**：按这个顺序处理。**① 确认现象**：`SELECT * FROM information_schema.innodb_trx` 看有没有长时间运行的事务；`SELECT * FROM sys.innodb_lock_waits` 找出阻塞的源头（谁在等谁）。**② 定位根因**：常见三类——(a) **有长事务没提交**（应用忘了 commit，或者事务里做了 RPC/IO）；(b) **跨事务的加锁顺序不一致**导致循环等待（那就是死锁了，会报 1213 而不是 1205）；(c) **WHERE 条件没走索引**导致锁了太多行，和别的请求冲突。**③ 立即处置**：如果是阻塞了业务的连接，先 `KILL` 掉源头事务的连接（**但一定要确认它是否在关键路径上**，KILL 会造成回滚）。**④ 根治**：缩短事务、固定加锁顺序、WHERE 走索引、把 `innodb_lock_wait_timeout` 从默认的 50 秒调小到 5~10 秒让问题快速暴露、应用层对 1205/1213 做退避重试。

**Q5：什么叫"回表"？怎么避免？**

> **参考回答**：在二级索引上查到主键值后，需要回到聚簇索引（主键索引）里取出完整的行，这个动作叫回表。**每一条命中的记录都要回表一次**，所以当命中行数多时，回表会产生大量随机 IO，是慢查询最常见的根因。
>
> **避免的方式**：① **覆盖索引**——让查询需要的所有列都在二级索引的叶子上（`Extra: Using index`）；② **延迟关联**——先用覆盖索引把主键查出来，再回表取其余列，把回表次数从"扫描行数"降到"返回行数"；③ **减少返回列**（不用 `SELECT *`）；④ **索引下推（ICP）**——在存储引擎层过滤掉不满足条件的记录，减少回表次数。
>
> **追问："回表一定是坏的么？"** → 不是。如果回表的行数很少（比如 `type=ref` 只命中 10 行），回表的成本可以接受，此时为了覆盖而把索引建得很宽反而更糟（写放大）。**判断标准是"回表的次数 × 单次回表成本" vs "索引变宽的代价"**。

**Q6：什么是 Buffer Pool？它的 LRU 有什么特别之处？**

> **参考回答**：Buffer Pool 是 InnoDB 在内存中缓存数据页和索引页的区域（`innodb_buffer_pool_size`，**生产环境建议设置为物理内存的 50%~70%**），是 InnoDB 性能的核心。读写数据时先看 Buffer Pool，命中就直接在内存操作，未命中才从磁盘读入。
>
> **它的 LRU 和普通 LRU 不一样**，因为要解决两个问题：**① 全表扫描污染缓存**（一个 `SELECT * FROM 大表` 会把整个 Buffer Pool 冲掉）；**② 预读失效**（InnoDB 会预读相邻页，如果预读的页根本用不到，会挤掉热点页）。
>
> **解法是把 LRU 链表分成两段**：
> - **young 区（约 5/8）**：真正热的数据；
> - **old 区（约 3/8）**：新读进来的页**先放在 old 区的头部**（而不是整个链表的头部）。
>
> 一个页要在 old 区**停留超过 `innodb_old_blocks_time`（默认 1000ms）**，并且**再次被访问**，才能被移到 young 区。这样全表扫描读进来的页在 1 秒内就被淘汰了，不会污染 young 区的热点数据。
>
> **查看命中率**：
> ```sql
> SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
> -- 命中率 = 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests
> ```
> 命中率应该保持在 99% 以上。另外 8.0 支持**多个 Buffer Pool 实例**（`innodb_buffer_pool_instances`），减少并发访问的锁竞争。

**Q7：什么是 Change Buffer？它解决什么问题？**

> **参考回答**：Change Buffer 是 Buffer Pool 里的一块内存（**5.5 之前叫 Insert Buffer，只支持 INSERT；5.5 起支持 INSERT/DELETE/UPDATE 的标记操作，改名 Change Buffer**），用来缓存"**对非唯一二级索引页的修改**"。
>
> **它解决的问题**：修改一条记录时，聚簇索引的页通常已经在 Buffer Pool 里了（因为你是先查到它才改），但**二级索引页可能不在内存**——如果每次都要把二级索引页从磁盘读进来再改，就是一次随机 IO。Change Buffer 的做法是：**把修改先记在内存里，不立即读页**；等到之后有查询需要读这个页时，再把缓冲的修改 merge（合并）进去——**一次 merge 可能合并多个操作，把多次随机 IO 变成一次**。
>
> **为什么只有非唯一索引能用？** 因为唯一索引插入时必须立即读页判断"是否已存在"，无法延迟。
>
> **相关参数**：`innodb_change_buffering`（8.0 默认 `all`）、`innodb_change_buffer_max_size`（默认占 Buffer Pool 的 25%）。
> **什么时候它特别有用**：**写多读少的表**（比如日志、流水表），因为二级索引页读得少，merge 的机会就少，缓冲的收益就大。**什么时候没用**：如果二级索引页很快就被读到，change buffer 还没来得及攒就 merge 了。
>
> **查看**：`SHOW ENGINE INNODB STATUS` 的 `INSERT BUFFER AND ADAPTIVE HASH INDEX` 段，看 `size`（已缓冲的操作数）和 `merges`（合并次数）。

**Q8：什么是"索引覆盖扫描"和"松散索引扫描"（Loose Index Scan）？**

> **参考回答**：**覆盖索引扫描**就是 `Using index`，不回表。**松散索引扫描**（`Extra: Using index for group-by`）是 GROUP BY 的一种优化：当 `GROUP BY` 的列是索引的最左前缀时，MySQL 不需要扫描所有记录，**只需要"跳跃"地读每个分组的第一条记录**就能得到分组结果。比如索引 `(a,b)`，`SELECT a, MIN(b) FROM t GROUP BY a` 就可以用松散索引扫描，因为它只需要每个 a 的第一条记录。
>
> **对应的还有"紧凑索引扫描"**（`Using index for group-by` 的完整形式），它需要扫描所有记录但不需要临时表。

**Q9：Redis 和 MySQL 双写不一致怎么解决？（**跨模块高频题**）**

> **参考回答**：这是**缓存一致性问题**，核心结论是"**无法做到绝对强一致（除非用分布式锁串行化），只能做到最终一致 + 把不一致窗口控制到业务可接受**"。主流方案是 **Cache Aside（旁路缓存）**：
>
> **读**：先读缓存，命中返回；未命中，读数据库，然后**写回缓存**。
> **写**：**先更新数据库，再删除缓存**（不是更新缓存）。
>
> **为什么是"删除"而不是"更新"？** ① 更新缓存的成本更高（可能需要复杂计算）；② 并发写时，两次更新缓存的顺序可能和数据库相反，导致缓存里是旧值；而删除操作是幂等的。
>
> **为什么是"先写库再删缓存"？** 反过来（先删缓存再写库）在并发下更容易出问题：请求 A 删了缓存，还没写库；请求 B 读缓存未命中，读到**旧值**并写回缓存；A 才写库 → **缓存里是旧值，长期不一致**。而"先写库再删缓存"的极端情况是：A 写库成功，A 删缓存**失败**了 → 缓存里也是旧值，但概率低得多，而且可以用**重试 + TTL 兜底**。
>
> **三种加强手段**：
> - **延迟双删**：写完库后删缓存，**延迟 500ms~1s 再删一次**（为了覆盖"读请求在删缓存前就已经读到旧值并准备写回"的情况）；
> - **订阅 binlog 异步删缓存（Canal）**：业务代码只管写库，Canal 订阅 binlog 变更去删缓存。**优点**：业务无侵入、不受业务代码 bug 影响、天然支持重试；**缺点**：引入中间件、有延迟；
> - **TTL 兜底**：所有缓存都设置过期时间（哪怕一致性要求高也设一个较长的，如 1 小时），保证"最终一定会一致"。
>
> **最强保证（不常用）**：读写都加分布式锁（性能差）、或者用 **Redis + Lua 做原子操作**、或者干脆不让缓存承担一致性要求（缓存只做降级和加速，正确性由数据库保证）。
>
> **我的实践**：LoveSpouse 的金币余额我用的是 **Redis 做准实时扣减 + MySQL 做异步落账**，这里的"不一致"是**设计上接受的**——因为 Redis 是权威的实时余额，MySQL 的流水是**账本**用于对账，两者通过**定时对账任务**兜底。**关键是业务上要明确"谁是权威数据源"**。（**LoveSpouse 金币计费**）

**Q10：你会怎么设计一个"客服工单系统"的数据库？（**岗位核心场景题**）**

> **参考回答**：我会分成四块来设计。
>
> **① 工单主体表 `ticket`**：`id`、`ticket_no`（业务单号，UNIQUE）、`title`、`content`、`status`（待受理/处理中/待客户确认/已解决/已关闭）、`priority`、`channel`（电话/在线/邮件/IM）、`creator_id`、`assignee_id`（当前处理人）、`team_id`（所属技能组）、`created_at`、`resolved_at`、`closed_at`。索引按查询模式建：`(team_id, status, created_at)` 用于"某技能组的待处理工单"，`(assignee_id, status, created_at)` 用于"我的工单"。
>
> **② 工单流转记录表 `ticket_flow`**：每次状态变更、转派、回复、升级都写一条，`(ticket_id, created_at)` 索引。**这是审计和 SLA 计算的基础**，只增不改，量大时按月分表。
>
> **③ 会话消息表 `ticket_message`**：工单可能对应一个 IM 会话。`(ticket_id, id)` 索引，支持游标分页拉历史消息。如果是 IM，消息量会非常大，考虑**冷热分离**（最近 3 个月在 MySQL，更早的进归档表/对象存储）。
>
> **④ 组织与权限**：复用 RBAC + 部门树（路径枚举），加**技能组**（`team`）和坐席的关联表。
>
> **关键设计点**：
> - **数据权限**：坐席只能看自己/本组的工单，用 `team_id IN (...)` 过滤，索引里必须包含 `team_id`；
> - **分配策略**：轮询/最少工单数/技能匹配，分配动作要**幂等**（用 `UPDATE ... WHERE assignee_id = 0` 的原子更新抢占，避免两个坐席同时被分配同一工单）；
> - **SLA**：工单表上冗余 `first_response_due_at`、`resolve_due_at`，定时任务扫描超时（走 `idx_due`），**和审批流的超时提醒是同一套机制**；
> - **统计报表**：不要直接在工单主表上跑 `COUNT`/`GROUP BY`（会拖慢在线业务），而是**异步聚合到日结表**或者走数仓。
>
> 这套设计和 OA 审批流是同构的——**都是"主体 + 状态机 + 流转日志 + 待办队列"**，只是业务语义不同。**（结合 AI 漏洞研判系统的"研判 → 人工审批 → 复测"流程** —— 这就是一个工单状态机的实践）

**Q11：`SELECT ... FOR UPDATE` 锁不住数据是什么原因？**

> **参考回答**：几个常见原因。① **WHERE 条件没走索引** —— 那它会锁全表，你以为只锁了一行，实际上锁了很多（也会阻塞别人）；② **RR 下的快照读混淆** —— `FOR UPDATE` 是当前读，一定读最新值，如果你观察到的结果和预期不符，多半是**别的语句**（普通 SELECT）在快照读；③ **锁的粒度问题** —— 在 RR 下 `WHERE id = 8` 且 id=8 不存在时，加的是**间隙锁**（锁住 (5,10) 的间隙），它阻止插入但不锁任何已存在的行，所以"看不到锁住了哪一行"；④ **唯一索引等值命中时退化为记录锁**，此时确实只锁一行；⑤ **主从读写分离** —— 你在从库上查，从库根本没有主库的锁！**这是最隐蔽的坑**，`FOR UPDATE` 必须走主库。
>
> **排查方法**：`SELECT * FROM performance_schema.data_locks WHERE OBJECT_NAME = '你的表'` 直接看锁了什么。

**Q12：什么是"半一致性读"（semi-consistent read）？**

> **参考回答**：这是 **RC 隔离级别下 UPDATE 的一个优化**。在 RC 下执行 `UPDATE` 时，InnoDB 会先把记录的最新版本读出来，**判断它是否满足 WHERE 条件**：如果不满足，就**释放锁**，继续读下一条（不加锁）。这样能减少锁的持有，降低冲突。
>
> **注意**：这个优化**只在 RC 下生效**（`innodb_locks_unsafe_for_binlog` 在 5.6 后已废弃，8.0 无此参数），RR 下 UPDATE 一律要加锁（因为要保证可重复读的语义）。

**Q13：`TRUNCATE`、`DELETE`、`DROP` 的区别？**

> **参考回答**：
>
> | | `DELETE` | `TRUNCATE` | `DROP` |
> |---|---|---|---|
> | 类型 | DML | DDL | DDL |
> | 删除粒度 | 可以带 WHERE 删部分 | 清空整表 | 连表结构一起删 |
> | 事务 | 可以回滚 | **隐式提交，不可回滚** | 不可回滚 |
> | 速度 | 慢（逐行删 + 写 undo/redo） | 快（重建表/段） | 快 |
> | 自增计数器 | **不重置** | **重置为 1** | — |
> | 触发器 | 会触发 | 不触发 | 不触发 |
> | 锁 | 行锁（走索引时） | MDL 写锁 | MDL 写锁 |
>
> **生产注意**：**清空大表绝不要用 `DELETE FROM t`（会产生巨大的 undo log 和 binlog，主从延迟，还可能导致磁盘打满）**，用 **`TRUNCATE`** 或者**分批删除**（`DELETE FROM t WHERE id < ? LIMIT 1000` 循环，每批之间 sleep 一下给主从复制留时间）。**注意 `TRUNCATE` 在 8.0 之前是不可回滚且会隐式提交的**，且它需要 DROP 权限。

**Q14：`utf8` 和 `utf8mb4` 的区别？**

> **参考回答**：MySQL 的 `utf8`（别名 `utf8mb3`）**每个字符最多 3 字节**，**存不了 4 字节的字符**——包括 emoji、一些生僻汉字（如"𠮷"）、部分少数民族文字。`utf8mb4` 才是真正的完整 UTF-8（最多 4 字节）。
>
> **实践建议**：**一律用 `utf8mb4`**。历史上 `utf8` 很流行是因为 MySQL 5.5 之前索引长度限制为 767 字节，`utf8mb4` 的 `VARCHAR(255)` 需要 1020 字节建不了索引；后来 `innodb_large_prefix`（5.7.7+ 默认开启）+ DYNAMIC 行格式把限制提到了 3072 字节，这个问题就不存在了。**迁移注意**：`utf8` → `utf8mb4` 时，**连接、表、列、排序规则**都要改，还要检查索引长度是否会超限。**而且这个转换在数据量大时是重量级 DDL**，要用 gh-ost 在线做。

**Q15：怎么用 MySQL 实现"分布式锁"？和 Redis 分布式锁比呢？**

> **参考回答**：MySQL 实现分布式锁有两个常用方案。
> **① 唯一索引**：建一张锁表 `CREATE TABLE t_lock (lock_key VARCHAR(64) PRIMARY KEY, holder VARCHAR(64), expire_at DATETIME)`。加锁就是 `INSERT INTO t_lock VALUES(...)`，成功即拿到锁，**INSERT 失败（主键冲突）说明别人持有**。释放就是 `DELETE WHERE lock_key = ? AND holder = ?`（防止删掉别人的锁）。
> **② `SELECT ... FOR UPDATE`**：把一个"锁行"存在表里，加锁就在事务里 `SELECT ... FOR UPDATE`，事务结束自动释放（**优点是不会像 Redis 那样有"锁过期但任务没跑完"的问题**，因为锁的生命周期和事务绑定）。
>
> **和 Redis 对比**：
>
> | | MySQL 锁 | Redis 锁 |
> |---|---|---|
> | 性能 | 低（有磁盘 IO） | **高** |
> | 可靠性 | **高**（有事务、持久化） | 中（主从切换可能丢锁） |
> | 自动续期 | 不需要（事务/连接断开即释放） | 需要 watch 狗 |
> | 适用 | **低频、强一致**的关键操作（如结算批次生成） | **高频、短临界区**（如防重复提交、限流） |
>
> **我的选择**：FlashRoot 的"结算批次生成"我用的是**唯一索引 + 状态机**的方式——因为这是个低频但绝不能重复执行的操作，MySQL 的强一致性和"唯一索引天然幂等"更让我放心；而防重复提交、接口限流这种高频短操作就用 Redis。**核心思路是：锁的可靠性要求和操作的重要性匹配，不要为了性能牺牲正确性。**（**FlashRoot 结算 + LoveSpouse 防重**）

---

**Q16：你们线上是怎么做数据库备份和恢复的？**

> **参考回答**：分三层。
> **① 备份**：每天凌晨低峰期用 `mysqldump --single-transaction`（或 **XtraBackup** 做物理热备）做**全量备份**，同时保证 **binlog 一直开启并归档**（`expire_logs_days` / `binlog_expire_logs_seconds`，一般保留 7~30 天），这样能做到 **PITR（Point-In-Time Recovery）** —— 恢复到任意时间点。
> **② 高可用**：主从复制 + 半同步（`rpl_semi_sync`）保证至少一个从库有数据；MHA / Orchestrator / 云厂商的 RDS 高可用版做自动故障转移。
> **③ 演练**：**定期做恢复演练**（这个最容易被忽略但最重要）——把备份恢复到一台新实例，验证数据完整性和恢复时间（RTO）。没演练过的备份等于没有备份。
>
> **面试加分**：说一句"**误删数据的恢复流程**：① 立刻停掉业务写入（或把从库提为主库）；② 用最近的全量备份恢复到新实例；③ 把 binlog 从备份时间点重放到误操作前一刻；④ 从新实例把误删的数据导回生产。**关键是第 ① 步要快——因为 binlog 重放的时间窗口越短越好**。"

**Q17：大表加字段/加索引怎么做才安全？**

> **参考回答**：**绝对不能直接 `ALTER TABLE`**，因为会锁表阻塞业务（尤其是在 MySQL 5.6 之前，加字段会重建整张表）。现在的手段：
> **① MySQL 5.6+ 的 Online DDL**：`ALTER TABLE t ADD COLUMN x INT, ALGORITHM=INPLACE, LOCK=NONE` —— 支持不锁表地加字段/加索引（加索引时 InnoDB 会用一个"临时文件"记录增量，最后 merge）。**但不是所有操作都支持**（改字段类型、改字符集通常还是要重建表）。
> **② gh-ost / pt-online-schema-change**：原理是**建一张影子表（结构是新的），把老数据分批拷过去，同时用 binlog/触发器同步增量，最后原子地 rename 换表**。**优点**：可控（限速、可暂停）、对主库压力小（pt-osc 要建触发器有一定开销，gh-ost 用 binlog 无触发器，更推荐）。**这是大表 DDL 的标准做法**。
> **③ 业务层方案（零 DDL）**：加字段可以用"**扩展表**"（新建一张 `t_ext` 存新字段，用主键关联）或者"**JSON 列**"（`ALTER` 加一个 JSON 列在 8.0 是 instant 操作）—— 8.0.12+ 支持 **INSTANT ADD COLUMN**（只改元数据，毫秒级完成）。
> **执行纪律**：① **先检查长事务**（MDL 冲突会导致整表不可用）；② 在**低峰期**执行；③ 设置 `lock_wait_timeout` 避免长时间等待；④ **先在从库演练**。

**Q18：如果线上出现"数据库 CPU 100%"，你的排查思路是什么？**

> **参考回答**：按"从外到内、从现象到根因"的思路：
> **① 确认现象和影响面**：是完全不可用还是部分慢？看监控的 QPS、连接数、慢查询数量、主从延迟。
> **② 快速止血**（先恢复业务，再找根因）：如果是某条 SQL 引起的，先 KILL 掉相关连接（`SELECT id, user, time, state, info FROM information_schema.processlist WHERE time > 60`）；如果是流量突增，先限流/降级；如果有恶意/异常 SQL 来源，先从入口阻断。
> **③ 定位**：
>   - `SHOW PROCESSLIST` / `information_schema.processlist` 找**运行时间长、状态异常**的线程（`Waiting for table metadata lock` → MDL 问题；`Sending data` → 大结果集或全表扫描；`Waiting for row lock` → 锁冲突）；
>   - `SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`、`History list length`（长事务）；
>   - 慢查询日志 + `pt-query-digest` 找 TOP SQL；
>   - 系统层：`top -H` 看 MySQL 线程的 CPU 分布、`iostat` 看 IO、`vmstat` 看上下文切换。
> **④ 常见根因清单**：新上线的 SQL 没走索引、某接口被刷（流量突增）、统计信息过期导致执行计划突变、`prepare` 语句泄漏或连接池配置不当、备份/DDL 任务在跑、主从延迟导致从库压力反噬。
> **⑤ 根治与复盘**：加索引/改 SQL、加缓存、加限流、把慢查询和 MDL 检查纳入上线卡点（**这个"卡点"很重要：上线前用 pt-query-digest 过一遍新增的 SQL**）。

### 7.2 一句话结论速记（面试"抢答"用）

- **为什么 B+ 树**：多叉 → 树矮 → 磁盘 IO 少；叶子链表 → 范围查询快。
- **回表**：二级索引拿到主键，回聚簇索引取整行。
- **覆盖索引**：`Using index`，不回表。
- **索引下推**：`Using index condition`，在引擎层过滤，**还是要回表**。
- **最左前缀**：B+ 树按联合索引列字典序排序的必然结果。
- **LIKE '%x'**：无法确定扫描起点 → 全表/全索引扫描。
- **MVCC 三要素**：隐藏字段 + undo 版本链 + ReadView。
- **RC vs RR**：ReadView 的生成时机（每条 SELECT vs 首次 SELECT）。
- **RR 没完全解决幻读**：快照读不幻读，当前读（UPDATE）会幻读。
- **间隙锁的目的**：阻止插入 → 防幻读。
- **行锁加在索引上**：WHERE 不走索引 → 锁全表。
- **死锁排查**：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`。
- **深分页**：游标分页（`id > last_id`）> 延迟关联 > 限制页数。
- **金额**：`DECIMAL`，绝不用 `FLOAT`/`DOUBLE`；Go 里用整数分或 decimal 库。
- **逻辑删除**：能物理删除 + 归档就别逻辑删除。
