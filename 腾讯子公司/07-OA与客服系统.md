## 7.1 审批流引擎设计（本章重点）

### 7.1.1 为什么审批流引擎难

一个「请假审批」看起来很简单：员工提交 → 主管审批 → HR 审批 → 结束。写几个 `if-else` 就完了。

难的是**当它要变成一个通用产品的时候**：

- 每个部门的请假流程不一样，有的要三级审批，有的两级；
- 金额超过 5000 要加一个总监节点；
- 审批人要支持「发起人的直属主管」「部门的 HRBP」「角色为财务的任意一人」这些**动态解析**规则；
- 审批人休假了要能**委托**给别人；
- 需要**会签**（三个人都要同意）和**或签**（三个人任一个同意就行）；
- 提交后发现有错要能**撤回**，审批人发现不对要能**驳回**（驳回上一步还是驳回到发起人？）；
- 审批过程中流程定义改版了，正在跑的流程不能乱；
- 每一步都要有**留痕**，出了事要能查是谁批的。

把这些需求都满足，就是一个流程引擎了。**核心难点在于：把「流程」从代码里抽出来变成数据，再用一个通用的执行器去跑它。**

### 7.1.2 流程定义模型

#### （1）BPMN 概念速览

BPMN（Business Process Model and Notation）是流程建模的国际标准。我们不需要实现完整的 BPMN（那是个巨大的工程），但**面试时必须知道这些概念对应的中文和用途**，因为面试官默认你听过：

| BPMN 元素 | 中文 | 在审批流里的含义 |
| --- | --- | --- |
| StartEvent | 开始事件 | 流程起点，一般对应「发起人提交表单」 |
| EndEvent | 结束事件 | 流程终点，实例状态变为已通过 |
| UserTask | 用户任务 | **审批节点**，需要人参与，产生待办 |
| ServiceTask | 服务任务 | 系统自动执行，如调用接口、发通知、更新业务表 |
| ExclusiveGateway | 排他网关 | **条件分支**，XOR，只走满足条件的第一条路 |
| ParallelGateway | 并行网关 | **并行分支**，所有分支都走，全部到达后汇聚 |
| InclusiveGateway | 包容网关 | 满足条件的分支都走（OR） |
| SequenceFlow | 顺序流 | **连线**，节点之间的箭头，可带条件表达式 |
| BoundaryEvent | 边界事件 | 挂在节点上的事件，如**超时定时器** |
| SubProcess | 子流程 | 流程里嵌套流程 |
| CallActivity | 调用活动 | 调用另一个流程定义 |

**面试要点**：能说出「我们的引擎支持 UserTask、ExclusiveGateway、ParallelGateway 和 BoundaryEvent（超时），不追求完整 BPMN 兼容」——这种「知道标准但做了裁剪」的表达，比假装实现了完整 BPMN 要可信得多，也体现了工程判断力。

#### （2）流程定义的数据结构（JSON）

流程定义的本质是**一张有向图**：`nodes`（节点）+ `edges`（连线）+ `variables`（变量定义）。

**两种建模风格的选择（面试加分点）**：
- **前端画布风格（nodes + edges 分离）**：节点和连线各自是数组，和前端拖拽画布的数据结构一致，新增连线类型（如条件标签）方便。**推荐**。
- **邻接表风格（每个节点带 next 数组）**：结构紧凑，但条件分支表达不自然（要么 next 是对象数组，要么条件挂在节点上）。这是很多简单引擎的做法（如 go-workflow 类库）。

#### （3）审批人规则（ApproverRule）

这是 OA 引擎里最容易做复杂的一块，因为「谁来审批」有非常多种表达：

| 规则类型 | 说明 | 实现要点 |
| --- | --- | --- |
| `user` | 指定具体的人 | 直接存 userId，简单但流程不通用 |
| `role` | 指定角色（如财务、HR） | 运行时查 `user_role` 表，**可能返回多个人**（需要决定是或签还是会签） |
| `dept` | 指定部门的负责人 | 查部门表的 `leader_id` |
| `leader` | 发起人的第 N 级主管 | 沿组织树的汇报链向上找 N 层，**要处理「找不到」的兜底** |
| `initiator` | 发起人自己 | 用于「发起人确认」节点 |
| `form_field` | 表单里选的某个人 | 如「指定审批人」字段，动态性强 |
| `sql` / `script` | 自定义 SQL 或脚本 | 最灵活但最危险，**生产环境慎用**（性能和安全） |
| `node_approver` | 前序节点的审批人 | 用于「同上」场景 |

**动态解析的关键设计**：
1. **解析时机**：在**任务生成时**解析，不是流程定义时。因为组织结构会变，定义时必须存「规则」而不是「人」。
2. **兜底策略（Fallback）**：`leader` 规则如果发起人没有上级（比如就是 CEO），必须有兜底——指定固定的人、或者跳到上一个有效节点、或者直接跳过该节点。**这是面试官爱问的细节，因为它体现你有没有处理过真实的组织数据**。
3. **多人时的默认行为**：`role` 规则解析出 5 个人时，默认应该是「或签」（任一人处理即可），因为把 5 个人都拉进会签会让流程卡住。规则里要能配置。
4. **去重**：解析出的人可能重复（既是主管又是 HR），要按 userId 去重。

```go
// 审批人解析器
type ApproverResolver interface {
    Resolve(ctx context.Context, rule ApproverRule, inst *Instance) ([]int64, error)
}

func (r *LeaderResolver) Resolve(ctx context.Context, rule ApproverRule, inst *Instance) ([]int64, error) {
    userID := inst.InitiatorID
    level := rule.Level
    if level <= 0 { level = 1 }

    // 沿汇报链向上找 level 层
    for i := 0; i < level; i++ {
        leader, err := r.orgSvc.GetLeader(ctx, userID)
        if err != nil { return nil, err }
        if leader == 0 {
            // 找不到上级：走兜底策略
            return r.resolveFallback(ctx, rule.Fallback, inst)
        }
        userID = leader
    }
    return []int64{userID}, nil
}

// 兜底：指定人 / 指定角色 / 跳过
func (r *LeaderResolver) resolveFallback(ctx context.Context, fb []string, inst *Instance) ([]int64, error) {
    for _, f := range fb {
        switch {
        case strings.HasPrefix(f, "user:"):
            id, _ := strconv.ParseInt(strings.TrimPrefix(f, "user:"), 10, 64)
            return []int64{id}, nil
        case strings.HasPrefix(f, "role:"):
            return r.orgSvc.GetUsersByRole(ctx, strings.TrimPrefix(f, "role:"))
        case f == "skip":
            return nil, ErrSkipNode // 特殊信号：跳过该节点
        }
    }
    return nil, errors.New("无法解析审批人且无有效兜底")
}
```

### 7.1.3 流程实例与任务

**三个核心概念必须分清**（面试时混淆这三个概念会直接暴露你没做过）：

| 概念 | 说明 | 类比 |
| --- | --- | --- |
| **流程定义（Definition）** | 模板，如「请假流程 v3」 | 类（Class） |
| **流程实例（Instance）** | 一次具体的运行，如「张三 2026-09-17 请 2 天假」 | 对象（Object） |
| **任务（Task）** | 实例在某个节点上产生的待办，如「李四需要审批这条请假」 | 方法调用 |

**关键规则**：
- **实例启动时固化的不是「流程定义的引用」，而是「版本」**——`instance.def_id` 指向具体那一版的定义。这样流程定义改版后，运行中的实例仍按老版本跑完，不会中途错乱。**这是版本管理的基础，一定要讲出来。**
- 一个实例在某个时刻可能有**多个活跃任务**（并行网关、会签），所以实例和任务是一对多。
- 任务的状态只有三个：`pending`（待处理）、`done`（已处理）、`canceled`（已取消）。**取消是必须有的状态**——驳回、撤回、或签被别人抢了，都会产生「任务被取消」的情况，不能直接删记录（要留痕）。

### 7.1.4 实例状态机设计

```
        ┌────────┐
        │  草稿   │  （可选：先保存不提交）
        │ draft  │
        └───┬────┘
      提交    │
            ▼
        ┌────────┐
        │ 审批中  │◄──────────────────┐
        │running │                   │
        └─┬──┬──┬┘                   │
          │  │  │                    │
   全部通过│  │  │被驳回             │撤回后重新提交
          │  │  └──────────┐         │
          │  │             ▼         │
          │  │        ┌────────┐     │
          │  │        │ 已驳回  │─────┘
          │  │        │rejected│
          │  │        └────────┘
          │  │
          │  └── 发起人撤回 ──► ┌────────┐
          │                    │ 已撤回  │
          │                    │canceled│
          │                    └────────┘
          ▼
        ┌────────┐
        │ 已通过  │
        │approved│
        └────────┘

   另外：running → terminated（管理员强制终止）
```

**状态设计要点**：
- 状态用**字符串枚举**而不是数字（可读性优先，`status = 'running'` 比 `status = 1` 在排查问题时省太多事）；
- 每次状态变更都要**写审批记录表**，形成完整的审计链路；
- 状态变更用 **CAS**（`UPDATE ... WHERE id = ? AND status = 'running'`），防止并发下的状态错乱——比如审批通过的同一瞬间发起人撤回了。

### 7.1.5 驳回：驳回到上一步 vs 驳回到任意节点

**这是面试官最爱问的 OA 问题之一**，因为它的实现差异很大，能考察你是否真的实现过。

#### 方案 A：驳回到上一步（简单）

**实现**：找到当前节点的**前驱节点**，取消当前活跃任务，在前驱节点上重新生成任务。

```go
// 驳回到上一节点
func (e *Engine) RejectToPrev(ctx context.Context, task *Task, comment string) error {
    node := e.def.GetNode(task.NodeKey)

    // 1. 找前驱节点（单前驱的情况简单，多前驱要按策略选）
    prevKey := e.findPrevNode(node)
    if prevKey == "" || prevKey == "start" {
        // 上一节点就是发起人，等于「驳回到发起人」，实例回到可编辑状态
        return e.rejectToInitiator(ctx, task, comment)
    }

    return e.db.Transaction(func(tx *gorm.DB) error {
        // 2. 取消当前节点的所有活跃任务（会签场景下可能有多条）
        tx.Model(&Task{}).
            Where("instance_id = ? AND node_key = ? AND status = 'pending'", task.InstanceID, task.NodeKey).
            Updates(map[string]interface{}{"status": "canceled", "finish_time": time.Now()})

        // 3. 在前驱节点生成新任务（审批人重新解析，因为人可能已经变了）
        prevNode := e.def.GetNode(prevKey)
        approvers, err := e.resolver.Resolve(ctx, prevNode.ApproverRule, inst)
        if err != nil { return err }
        for _, uid := range approvers {
            tx.Create(&Task{
                InstanceID: task.InstanceID,
                NodeKey:    prevKey,
                NodeName:   prevNode.Name,
                AssigneeID: uid,
                Status:     "pending",
                Round:      task.Round + 1, // 轮次 +1，用于区分同一节点的多次执行
            })
        }

        // 4. 更新实例的当前节点
        tx.Model(&Instance{}).Where("id = ?", task.InstanceID).
            Updates(map[string]interface{}{"current_node": prevKey})

        // 5. 记录审批留痕
        tx.Create(&Record{
            InstanceID: task.InstanceID, NodeKey: task.NodeKey,
            OperatorID: task.AssigneeID, Action: "reject",
            Comment: comment, TargetNode: prevKey,
        })
        return nil
    })
}
```

**注意 `Round` 字段的设计**：同一个节点可能被执行多次（驳回后重走），必须用 `round` 区分，否则查询「我要审批的任务」时会查出历史任务。**这是一个很容易踩的坑，主动说出来是加分项。**

#### 方案 B：驳回到任意节点（复杂，有两种策略）

**策略 B1：回滚式（回退并保留历史）**

做法：把目标节点**之后的所有活跃任务全部取消**，在目标节点重新生成任务；历史记录（`record` 表）**全部保留**，但标注本轮为「已失效」。

```
原路径：发起 → A(已批) → B(已批) → C(当前) 
驳回 C 到 A：
  → 取消 C 的活跃任务
  → 在 A 生成新任务（round+1）
  → 实例 current_node = A
  → B 的记录保留但标记 superseded = 1（用于展示「曾经批过，但已被本次驳回覆盖」）
  
新路径：发起 → A(待办, round=2) → B → C
```

- **优点**：历史完整可追溯，实现相对直接。
- **缺点**：重走时 B 又要重新审批一次，用户体验差（「刚批过的怎么又要批」）。

**策略 B2：跳回式（只重走目标节点之后的部分）**

做法：把目标节点之后**未处理**的任务取消，目标节点重新生成任务，但**已通过的节点可以选择跳过**（配置项）。

```
驳回 C 到 A（skipApproved = true）：
  → 取消 C 的任务，在 A 生成新任务（round=2）
  → A 审批通过后，因为 B 在本轮已批过且 skipApproved = true，直接跳过 B
  → 直接到 C
```

- **优点**：用户少批一次。
- **缺点**：跳过意味着 B 没有看到 A 修改后的新内容（万一 A 改了金额，B 应该重新判断）。**所以这个配置要谨慎，涉及金额、风险类的审批不能跳过。** 这个 trade-off 的分析能大幅加分。

#### 方案 C：驳回到发起人（最常见的实际选择）

很多公司的流程引擎**只支持两种驳回**：驳回到上一节点、驳回到发起人。因为「驳回到任意节点」的边界情况太多（跨并行分支怎么办？跨会签怎么办？），维护成本极高。

**面试话术**：「我们当时只实现了驳回到上一节点和驳回到发起人两种，因为驳回到任意节点在跨并行网关、跨会签节点这些场景下语义不清晰——比如一个并行分支的两个节点，其中一个被驳回了，另一个分支的任务要不要取消？我们评估后认为收益不值这个复杂度，就用「驳回到发起人重新提交」覆盖了这类场景。如果要做得更细，我倾向于用 B2 的跳回式，但必须给「已通过节点是否重新审批」做成配置项，并且金额类流程强制重审。」

**这个回答的杀伤力在于：它展示了「知道怎么做但不做」的架构判断力，而不是「不会做」。**

#### 驳回后重新提交的关键细节

1. **驳回后的数据可编辑性**：驳回到发起人时，实例状态要变成 `rejected` 或专门的 `returned`，发起人修改表单后**重新提交**。重新提交时是**同一个实例**（ID 不变，`round+1`）还是**新建实例**？推荐**同一个实例 + round 递增**，因为业务单据是同一个，新建实例会导致单据重复。但要注意：重新提交时**重新计算条件分支**（因为表单可能改了，`days` 从 2 变成 5，路由应该变）。
2. **驳回链路的记录**：`record` 表要能还原出「批了 → 被驳 → 改了 → 又批了」的完整时间线，所以 `round`、`action`、`create_time` 三个字段缺一不可。
3. **通知**：驳回必须通知到发起人（站内信 + 企微/飞书），否则流程会卡住没人知道。

### 7.1.6 撤回

**撤回的语义**：发起人提交后反悔了，把流程收回来。

**关键约束（面试必答）**：**撤回只能在没有后续审批动作时进行**。也就是说：
- 只有**第一个节点还没被处理**时可以撤回（最常见、最安全）；
- 或者更宽松的：**所有已产生的任务都还没被处理**时可以撤回；
- 一旦有人批过了，就不能「撤回」，只能走「撤销/作废」流程（因为已经有审批意见产生了，直接撤回会让审批人的工作「消失」，审计上说不通）。

```go
func (e *Engine) Withdraw(ctx context.Context, instanceID, operatorID int64) error {
    inst := e.getInstance(ctx, instanceID)

    // 1. 只有发起人能撤回
    if inst.InitiatorID != operatorID {
        return errors.New("只有发起人可以撤回")
    }
    // 2. 只有运行中的实例能撤回
    if inst.Status != "running" {
        return errors.New("当前状态不可撤回")
    }
    // 3. 关键约束：不能有任何已完成的审批任务
    var doneCount int64
    e.db.Model(&Task{}).
        Where("instance_id = ? AND status = 'done'", instanceID).
        Count(&doneCount)
    if doneCount > 0 {
        return errors.New("已有审批人处理，无法撤回，请联系审批人驳回")
    }

    return e.db.Transaction(func(tx *gorm.DB) error {
        // 4. 取消所有活跃任务
        tx.Model(&Task{}).
            Where("instance_id = ? AND status = 'pending'", instanceID).
            Update("status", "canceled")
        // 5. 实例状态改为已撤回
        tx.Model(&Instance{}).Where("id = ? AND status = 'running'", instanceID).
            Updates(map[string]interface{}{"status": "canceled", "end_time": time.Now()})
        // 6. 留痕
        tx.Create(&Record{
            InstanceID: instanceID, NodeKey: inst.CurrentNode,
            OperatorID: operatorID, Action: "withdraw",
            Comment: "发起人撤回",
        })
        return nil
    })
}
```

**撤回后能不能重新提交？** 两种产品设计：
- **可以重新提交**：实例状态回到 `draft` 或提供「重新发起」按钮，用户改完再提交（推荐，体验好）；
- **必须新建**：撤回即终结，用户要重新走一遍（审批留痕更清晰）。

**注意点**：撤回用 CAS（`WHERE status = 'running'`）保证不会和审批人的「同意」操作并发冲突。

### 7.1.7 会签（Countersign）

**会签 = 一个节点有多个审批人**。这是 OA 引擎里复杂度陡增的地方。

#### 四种策略（必须能全说清）

| 策略 | 英文/标识 | 规则 | 适用场景 |
| --- | --- | --- | --- |
| **会签（全票通过）** | `all` / `sequential` | **所有人**都同意才算通过；任一人拒绝则节点拒绝 | 重要决策，需要所有人背书 |
| **或签（抢占）** | `any` / `or` | **任一人**处理即节点完成，其他人的任务自动取消 | 日常审批，找谁都行（如「HR 组任意一人审批」） |
| **一票否决** | `veto` | 只要有一人拒绝，节点立即判定为拒绝（不等其他人） | 风控、合规 |
| **按比例通过** | `ratio` | 同意人数 / 总人数 ≥ 阈值（如 2/3） | 董事会、评委会 |

**`all` 和 `veto` 的区别**（很多人答不上来，一定要说清）：
- `all`（全票通过）：所有人都必须处理完。如果 3 个人里 1 人拒绝、2 人还没处理，节点**不会立即失败**，要等另外 2 人处理完才判定为拒绝。**好处是留痕完整**（每个人的意见都有）。
- `veto`（一票否决）：1 人拒绝**立即**判定为拒绝，取消其余人的任务。**好处是响应快**，坏处是后面的人没机会表达意见。

#### 判断逻辑的实现

```go
// 会签判定：在每次任务完成后调用
func (e *Engine) evalCountersign(ctx context.Context, tx *gorm.DB, inst *Instance, node *Node, nodeKey string) (bool, string, error) {
    var tasks []Task
    tx.Where("instance_id = ? AND node_key = ? AND round = ?", inst.ID, nodeKey, inst.Round).
        Find(&tasks)

    total   := len(tasks)
    done    := 0
    approve := 0
    reject  := 0
    for _, t := range tasks {
        if t.Status != "done" { continue }
        done++
        switch t.Result {
        case "approve": approve++
        case "reject":  reject++
        }
    }

    switch node.Countersign {
    case "any": // 或签：任一人处理即完成（同意或拒绝都算节点结论）
        if done >= 1 {
            if reject > 0 { return false, "rejected", nil }
            return true, "approved", nil
        }
        return false, "pending", nil

    case "veto": // 一票否决：立即失败
        if reject > 0 { return false, "rejected", nil }
        if approve == total { return true, "approved", nil }
        return false, "pending", nil

    case "ratio": // 按比例：同意数 / 总数 >= 阈值
        if float64(approve)/float64(total) >= node.CountersignRatio {
            return true, "approved", nil
        }
        // 剩余未处理的人即使全同意也达不到阈值 → 提前判定失败
        if float64(approve+ (total-done))/float64(total) < node.CountersignRatio {
            return false, "rejected", nil
        }
        return false, "pending", nil

    case "all": // 默认：全票通过（所有人都处理完才判定）
        if done < total {
            return false, "pending", nil
        }
        if reject > 0 { return false, "rejected", nil }
        return true, "approved", nil
    }
    return false, "pending", nil
}
```

**`ratio` 策略里那个「提前判定失败」的逻辑非常关键**：比如 5 人需要 3 票同意，如果已经有 3 人拒绝，那剩下 2 人即使全同意也只有 2 票 < 3，可以**立即判定失败**，不用等所有人。这个优化能体现你考虑过真实的效率问题。

**会签的加签/减签**：会签过程中可能要临时加人（比如主管觉得这事需要法务看看）。加签后 `total` 会变，要注意**比例策略下的阈值重算**——是固定人数还是动态计算？一般用动态（`ratio × 当前总人数`），但会签中途加人会导致「已达标又变成不达标」，需要在产品上定义清楚。

### 7.1.8 加签、转办、委托

这三个词面试官经常混着问，一定要能清晰区分：

| 操作 | 发起人 | 效果 | 原审批人 | 适用场景 |
| --- | --- | --- | --- | --- |
| **加签** | 当前审批人 | 在流程里**插入**新的审批人 | **任务还在，处理权不变** | 拿不准，找个人一起看 |
| **转办** | 当前审批人 | 把任务**移交**给别人 | **任务没了，永久转出** | 这事不归我管 |
| **委托** | 审批人预先设置 | **一段时间内**所有任务自动转给代理人 | 任务来时自动改派 | 休假、出差 |

**加签的两种形式（重点）**：
- **前加签**：在我审批**之前**加人。实现上要先把我的任务挂起（状态改为 `waiting` 或用一个 `pending_pre` 标记），生成加签人的任务；加签人处理完后，流程**回到我这里**。**关键点：加签人的结论对我的影响**——是「加签人同意=我这边自动同意」，还是「加签人只是给意见，我还要自己批」？产品上通常是后者（加签人给意见，原审批人拍板）。
- **后加签**：我审批**之后**加人。实现上是在当前节点生成新任务，原任务标记为已处理但节点不推进，等加签人处理完再推进。**前加签更常用**（「先问问法务的意见」），后加签用于「我批了，但需要老板再确认一下」——这种情况其实更适合用「新增节点」或者干脆下一个节点就是老板。

```go
// 前加签
func (e *Engine) AddSignBefore(ctx context.Context, task *Task, addedUserIDs []int64, comment string) error {
    return e.db.Transaction(func(tx *gorm.DB) error {
        // 1. 原任务挂起，不是完成
        tx.Model(&Task{}).Where("id = ? AND status = 'pending'", task.ID).
            Update("status", "waiting")

        // 2. 生成加签任务
        for _, uid := range addedUserIDs {
            tx.Create(&Task{
                InstanceID: task.InstanceID,
                NodeKey:    task.NodeKey,
                NodeName:   task.NodeName + "(加签)",
                AssigneeID: uid,
                Status:     "pending",
                Round:      task.Round,
                TaskType:   "addsign",       // 标记为加签任务
                ParentTaskID: task.ID,        // 关联原任务，处理完要唤醒它
            })
        }

        tx.Create(&Record{
            InstanceID: task.InstanceID, NodeKey: task.NodeKey,
            OperatorID: task.AssigneeID, Action: "add_sign_before",
            Comment: comment, Ext: toJSON(map[string]interface{}{"added": addedUserIDs}),
        })
        return nil
    })
}

// 加签人处理完后，唤醒原任务（在任务完成的逻辑里判断）
func (e *Engine) onTaskDone(ctx context.Context, tx *gorm.DB, t *Task) error {
    if t.TaskType == "addsign" && t.ParentTaskID > 0 {
        var siblings []Task
        tx.Where("parent_task_id = ? AND status = 'pending'", t.ParentTaskID).Find(&siblings)
        if len(siblings) == 0 {
            // 所有加签人都处理完了，恢复原任务为待处理
            tx.Model(&Task{}).Where("id = ? AND status = 'waiting'", t.ParentTaskID).
                Update("status", "pending")
            // 通知原审批人「加签已完成，请您审批」
        }
    }
    return nil
}
```

**转办 vs 委托的实现差异**：
- **转办**改的是**当前这一条任务**的 `assignee_id`，并记录一条转办日志（谁转给谁、为什么）。任务本身只有一条，不产生新任务。
- **委托**是**规则**：单独一张 `oa_delegate` 表存 `(委托人, 代理人, 开始时间, 结束时间, 生效流程范围)`。任务生成时先解析审批人，然后检查这个人有没有生效的委托规则，有就把 `assignee_id` 换成代理人，同时**用 `original_assignee_id` 字段保留原审批人**（审计要用）。
- **委托链**：A 委托给 B，B 又委托给 C，要不要支持？一般**只支持一级**（避免循环委托）。要检测循环（A 委托 B，B 委托 A）。

### 7.1.9 超时自动审批

**配置项**：
```json
"timeout": {
  "duration": 86400,          // 超时时长（秒）
  "action": "auto_approve",   // auto_approve / auto_reject / transfer_leader / notify_only
  "notifyBefore": 3600,       // 超时前多久提醒
  "maxLevel": 3               // 逐级升级的最大层级
}
```

**四种超时动作**：
| 动作 | 说明 | 风险 |
| --- | --- | --- |
| `auto_approve` | 自动通过 | **有风险**，等于给了「拖着不批就能过」的口子，只适合低风险流程 |
| `auto_reject` | 自动拒绝 | 保守，但可能因为审批人不在而误伤业务 |
| `transfer_leader` | 转交给上级 | 最常用的生产选择 |
| `notify_only` | 只提醒不处理 | 最安全，但流程可能永远卡住 |

**实现方式：用延迟队列，不要用定时扫全表**。

```go
// 任务创建时，投递一个延迟消息
func (e *Engine) scheduleTimeout(ctx context.Context, t *Task, node *Node) error {
    if node.Timeout == nil { return nil }
    msg := TimeoutMsg{
        TaskID:   t.ID,
        InstanceID: t.InstanceID,
        NodeKey:  t.NodeKey,
        Action:   node.Timeout.Action,
        Level:    1,
    }
    // 到期时间 = 现在 + duration
    return e.delayQueue.Publish(ctx, msg, time.Duration(node.Timeout.Duration)*time.Second)
}

// 超时消费者
func (e *Engine) onTimeout(ctx context.Context, msg TimeoutMsg) error {
    // 幂等：任务可能已经被处理了
    t := e.getTask(ctx, msg.TaskID)
    if t.Status != "pending" && t.Status != "waiting" {
        return nil // 已处理，直接忽略
    }

    switch msg.Action {
    case "notify_only":
        e.notify(ctx, t.AssigneeID, "您有审批即将超时")

    case "transfer_leader":
        leader := e.orgSvc.GetLeader(ctx, t.AssigneeID)
        e.transfer(ctx, t, leader)   // 转办给上级
        e.notify(ctx, leader, "有一条超时审批转交给您")

    case "auto_approve":
        // 走正常的审批完成逻辑，保证状态机一致
        return e.approve(ctx, t, "系统超时自动通过", SystemOperator)

    case "auto_reject":
        return e.reject(ctx, t, "系统超时自动拒绝", SystemOperator)
    }
    return nil
}
```

**三个工程细节（面试加分）**：
1. **超时任务要能被取消**：如果任务在超时前被处理了，延迟消息仍然会到达，必须靠「幂等校验」忽略它。**不能依赖「取消延迟消息」**——大多数 MQ 不支持取消已投递的延迟消息。
2. **服务重启后延迟消息要能恢复**：如果用的是内存延迟队列（如 Go 的 `time.AfterFunc`），进程重启就丢了。所以要么用 MQ 的持久化延迟队列，要么用**定时扫表**（`WHERE status='pending' AND due_time <= NOW()`），后者最可靠。
3. **提醒要分阶段**：超时前 1 小时提醒本人、超时后提醒上级、再超时提醒上上级。这种「逐级升级」比一刀切自动通过要合理得多，也是真实 OA 产品的做法。

### 7.1.10 版本管理

**核心问题**：流程定义改了（加了一个审批节点），正在跑的实例怎么办？

**答案：实例启动时固化版本，改版只影响新实例。**

**做到这一点的三个要点**：
1. 流程定义表用 **`(tenant_id, process_key, version)` 唯一**，每次编辑生成新版本，旧版本不删（标记为「历史版本」）；
2. 实例表存 **`def_id`**（指向具体那一版的定义记录），而不是只存 `process_key`；
3. 引擎执行时，**从实例的 `def_id` 加载定义**，绝不从「当前最新版本」加载。

```sql
-- 流程定义表（一个 key 多个版本）
CREATE TABLE `oa_process_def` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `tenant_id`    BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `process_key`  VARCHAR(64)  NOT NULL COMMENT '流程标识，同一 key 多版本',
  `name`         VARCHAR(128) NOT NULL,
  `version`      INT          NOT NULL DEFAULT 1,
  `status`       TINYINT      NOT NULL DEFAULT 0 COMMENT '0草稿 1已发布 2已停用',
  `node_config`  JSON         NOT NULL COMMENT '节点与连线定义（完整图）',
  `form_id`      BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `remark`       VARCHAR(500) NOT NULL DEFAULT '' COMMENT '版本变更说明',
  `created_by`   BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_key_version` (`tenant_id`, `process_key`, `version`),
  KEY `idx_key_status` (`tenant_id`, `process_key`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='流程定义表（多版本）';
```

**版本管理的进阶问题（面试可以用来展示深度）**：
- **能不能「迁移」运行中的实例到新版本？** 理论上可以（改 `def_id`），但**工程上强烈不建议**——因为新版本的节点结构可能完全不同，实例的 `current_node` 可能在新版本里不存在，会出现「实例卡在一个不存在的节点上」。非要做的话，必须定义清晰的迁移规则（节点 key 映射表 + 只允许「加节点」这类兼容性变更）。
- **已停用的流程还能发起吗？** 不能。停用后新的实例不能再启动，但存量实例要能跑完（所以停用≠删除）。
- **草稿版本能被引用吗？** 不能。只有 `status = 1（已发布）` 的版本可以被实例固化。

**索引设计说明（会被追问，要能讲清每个索引服务的查询）**：
- `idx_assignee_todo`：服务「我的待办」——最高频查询，`(assignee_id, status)` 定位，`create_time` 排序，避免 filesort；
- `idx_instance + round`：服务「流程详情的时间线」和「会签判定」（要按 round 捞出同一轮所有任务）；
- `idx_timeout`：服务超时扫描，`status` 在前是因为大部分记录是 `done`，能大幅缩小扫描范围；
- `idx_business` 唯一键：防重复发起（同一个业务单据不能发起两次），**这也是幂等的实现**；
- `idx_dept_status`：服务数据权限——「我部门的审批单」需要按部门过滤。

**分表策略**：审批记录表（`oa_approve_record`）是 append-only 且增长最快的（一个流程平均产生 5-10 条记录），建议**按月分表**或按 `instance_id` 哈希分表；实例表和任务表数据量中等，先按 `tenant_id` 分库，单表超过 2000 万再考虑分表。

### 7.1.12 代码层面：节点流转的实现

```go
// ========== 引擎核心：从当前节点推进到下一个节点 ==========
type Engine struct {
    defRepo      DefinitionRepo
    instRepo     InstanceRepo
    taskRepo     TaskRepo
    orgSvc       OrgService
    resolver     ApproverResolver
    exprEngine   *expr.Engine     // 条件表达式求值
    eventBus     EventBus         // 发事件（通知/统计）
}

// MoveNext 是引擎的核心：给定实例和刚完成的节点，推进流程
func (e *Engine) MoveNext(ctx context.Context, inst *Instance, fromNodeKey string) error {
    def, err := e.defRepo.GetByID(ctx, inst.DefID) // 注意：用实例固化的 def_id，不是最新版本
    if err != nil { return err }

    fromNode := def.GetNode(fromNodeKey)
    if fromNode == nil { return fmt.Errorf("节点不存在: %s", fromNodeKey) }

    // 1. 找到所有出边
    edges := def.GetOutEdges(fromNodeKey)
    if len(edges) == 0 {
        // 没有出边 = 流程结束
        return e.finishInstance(ctx, inst, "approved")
    }

    // 2. 根据节点类型决定走哪些边
    var nextEdges []Edge
    switch fromNode.Type {
    case NodeExclusiveGateway:
        // 排他网关：按顺序求值，走第一条满足条件的（default 边兜底）
        for _, edge := range edges {
            if edge.Condition == "" {
                nextEdges = append(nextEdges, edge) // 无条件 = default
                break
            }
            ok, err := e.exprEngine.EvalBool(edge.Condition, inst.FormData)
            if err != nil {
                return fmt.Errorf("条件表达式求值失败: %s, err=%w", edge.Condition, err)
            }
            if ok {
                nextEdges = append(nextEdges, edge)
                break
            }
        }
        if len(nextEdges) == 0 {
            return errors.New("没有满足条件的路由，请检查流程定义")
        }

    case NodeParallelGateway:
        // 并行网关：所有出边都走（分叉）
        nextEdges = edges

    default:
        // 普通节点：单出边（或多出边但都要走，如抄送）
        nextEdges = edges
    }

    // 3. 处理每个目标节点
    // 注意：如果目标节点是网关，需要递归/循环处理，直到抵达用户任务或结束
    for _, edge := range nextEdges {
        if err := e.enterNode(ctx, inst, def, edge.To); err != nil {
            return err
        }
    }
    return nil
}

// enterNode 进入一个节点：按类型分发处理，网关节点需要继续往下走
func (e *Engine) enterNode(ctx context.Context, inst *Instance, def *Definition, nodeKey string) error {
    node := def.GetNode(nodeKey)
    if node == nil { return fmt.Errorf("节点不存在: %s", nodeKey) }

    var err error
    switch node.Type {
    case NodeStart:
        // 开始节点：直接推进
        err = e.MoveNext(ctx, inst, nodeKey)

    case NodeApproval:
        // 审批节点：解析审批人，生成任务
        err = e.createApprovalTasks(ctx, inst, node)

    case NodeCC:
        // 抄送节点：生成抄送记录，然后继续往下（无人为阻塞）
        err = e.createCCRecords(ctx, inst, node)
        if err == nil {
            err = e.MoveNext(ctx, inst, nodeKey)  // 抄送不阻塞，直接推进
        }

    case NodeExclusiveGateway, NodeParallelGateway:
        // 网关：继续往下走（由 MoveNext 处理分支逻辑）
        err = e.MoveNext(ctx, inst, nodeKey)

    case NodeEnd:
        err = e.finishInstance(ctx, inst, "approved")

    case NodeServiceTask:
        // 服务任务：调用外部接口/执行系统动作
        err = e.executeServiceTask(ctx, inst, node)
        if err == nil {
            err = e.MoveNext(ctx, inst, nodeKey)
        }

    default:
        err = fmt.Errorf("未知节点类型: %s", node.Type)
    }

    // 更新实例的当前节点
    if err == nil {
        e.instRepo.UpdateCurrentNode(ctx, inst.ID, nodeKey)
    }
    return err
}

// createApprovalTasks 创建审批任务（含会签、委托、审批人解析）
func (e *Engine) createApprovalTasks(ctx context.Context, inst *Instance, node *Node) error {
    // 1. 解析审批人
    approvers, err := e.resolver.Resolve(ctx, node.ApproverRule, inst)
    if err != nil { return err }
    if len(approvers) == 0 {
        // 没有审批人：按配置跳过或报错
        if node.AllowSkip {
            return e.MoveNext(ctx, inst, node.Key)
        }
        return fmt.Errorf("节点 %s 解析不到审批人", node.Name)
    }

    // 2. 去重
    approvers = dedup(approvers)

    // 3. 应用委托规则
    approvers = e.applyDelegate(ctx, inst, approvers)

    // 4. 只有一个审批人时，会签配置无意义，强制当作单人处理
    countersign := node.Countersign
    if len(approvers) == 1 { countersign = "any" }

    // 5. 创建任务
    err = e.db.WithTx(ctx, func(tx *gorm.DB) error {
        for _, uid := range approvers {
            t := &Task{
                InstanceID: inst.ID,
                NodeKey:    node.Key,
                NodeName:   node.Name,
                Round:      inst.Round,
                AssigneeID: uid,
                Status:     "pending",
                Countersign: countersign,
            }
            if node.Timeout != nil {
                t.DueTime = ptr(time.Now().Add(time.Duration(node.Timeout.Duration) * time.Second))
            }
            if err := tx.Create(t).Error; err != nil { return err }
        }
        return tx.Create(&Record{
            InstanceID: inst.ID, NodeKey: node.Key, NodeName: node.Name,
            Round: inst.Round, Action: "arrive",
            Comment: fmt.Sprintf("进入节点：%s", node.Name),
        }).Error
    })
    if err != nil { return err }

    // 6. 发事件：通知审批人 + 安排超时
    for _, uid := range approvers {
        e.eventBus.Publish(ctx, TaskCreatedEvent{InstanceID: inst.ID, NodeKey: node.Key, Assignee: uid})
    }
    e.scheduleTimeoutForNode(ctx, inst, node)
    return nil
}

// ========== 审批人处理任务（同意/拒绝） ==========
func (e *Engine) Approve(ctx context.Context, taskID, operatorID int64, comment string) error {
    return e.db.WithTx(ctx, func(tx *gorm.DB) error {
        // 1. CAS 抢占任务：防止并发重复审批（幂等）
        res := tx.Model(&Task{}).
            Where("id = ? AND assignee_id = ? AND status = 'pending'", taskID, operatorID).
            Updates(map[string]interface{}{
                "status": "done", "result": "approve",
                "comment": comment, "finish_time": time.Now(),
            })
        if res.RowsAffected == 0 {
            return errors.New("任务已处理或无权处理")
        }

        task := e.taskRepo.GetByID(ctx, taskID)
        inst := e.instRepo.GetByID(ctx, task.InstanceID)
        def  := e.defRepo.GetByID(ctx, inst.DefID)
        node := def.GetNode(task.NodeKey)

        // 2. 留痕
        tx.Create(&Record{
            InstanceID: inst.ID, TaskID: task.ID, NodeKey: task.NodeKey,
            NodeName: task.NodeName, Round: task.Round,
            OperatorID: operatorID, Action: "approve", Comment: comment,
        })

        // 3. 如果是或签/一票否决，取消同节点其他任务
        if node.Countersign == "any" || node.Countersign == "veto" {
            tx.Model(&Task{}).
                Where("instance_id = ? AND node_key = ? AND round = ? AND id != ? AND status = 'pending'",
                    inst.ID, task.NodeKey, task.Round, taskID).
                Updates(map[string]interface{}{"status": "canceled", "finish_time": time.Now()})
        }

        // 4. 会签判定：节点是否已完成
        done, result, err := e.evalCountersign(ctx, tx, inst, node, task.NodeKey)
        if err != nil { return err }
        if !done {
            return nil // 节点还没批完，等其他人
        }
        if result == "rejected" {
            return e.handleNodeRejected(ctx, tx, inst, node, task)
        }

        // 5. 节点通过 → 推进流程
        return e.MoveNextInTx(ctx, tx, inst, task.NodeKey)
    })
}
```

**代码里的四个关键设计（面试可以主动讲）**：
1. **`ApproverResolver` 用接口抽象**，每种规则一个实现，新增规则类型不用改引擎——**策略模式**；
2. **任务抢占用 CAS**（`WHERE status = 'pending'`），并发下只有一个人能成功，返回 0 行就是「已被处理」，天然幂等；
3. **会签判定抽成独立函数**，遵循「节点是否完成」的语义，让主流程保持清晰；
4. **网关的处理是递归的**（`enterNode` → `MoveNext` → `enterNode`），因为网关后面可能还是网关，不能假设「网关后面一定是审批节点」。

**死循环防护**：如果流程定义里画了一个环（A → B → A），递归会栈溢出。防护手段是**限制单次推进的最大步数**（如 100 步），超过就报错。**这个细节能体现你真写过引擎。**

### 7.1.13 审批流高频面试 Q&A

**Q1：你们的审批流引擎是怎么设计的？**

> 我分四层来说。
> **第一层是流程定义**，它本质上是一张有向图，用 JSON 存 `nodes` 和 `edges`。节点有开始、审批、条件网关、并行网关、抄送、结束这几种类型，连线可以带条件表达式。审批节点上挂三类配置：审批人规则（直属主管/角色/指定人/表单字段）、会签策略、超时策略。流程定义是按 `process_key + version` 多版本管理的。
> **第二层是流程实例**，用户发起一次审批就产生一个实例。关键在于**实例启动时会固化 `def_id`**——也就是锁定当时那个版本的定义，之后流程改版不影响正在跑的实例，这是版本管理的基础。
> **第三层是任务**，实例到达审批节点时为每个审批人生成一条待办任务。会签就是这个节点上有多条任务。
> **第四层是引擎执行器**，核心是一个 `MoveNext` 函数：从当前节点找出边，按节点类型决定走哪几条（排他网关走第一条满足条件的，并行网关全走），然后进入目标节点——审批节点就生成任务，网关就继续递归往下，结束节点就终结实例。
> 还有个设计我比较满意的是**审批人解析用策略模式抽象成接口**，`leader`、`role`、`form_field` 各是一个实现，新增规则类型不用改引擎。而且解析是在**任务生成时**做的，不是定义时——因为组织架构会变，定义里必须存规则而不是人。

**Q2：驳回是怎么实现的？驳回到上一步和驳回到任意节点有什么区别？**

> 驳回到上一步相对简单：找到当前节点的前驱节点，把当前节点的活跃任务批量置为 `canceled`，在前驱节点重新生成任务，同时更新实例的 `current_node`。
> 驳回到任意节点复杂得多，有两条实现路线。
> **回滚式**是取消目标节点之后所有活跃任务，在目标节点重建任务，历史记录全部保留但把被覆盖的记录标记 `superseded = 1`。它的好处是审计链完整，坏处是用户要重批一遍已经批过的节点。
> **跳回式**是让已通过的节点在重新走的时候自动跳过，用户只重走目标节点之后的部分。体验好，但有个隐患——如果前序审批人修改了内容（比如把金额从 5000 改成 5 万），原本批过的节点其实是基于旧内容批的，跳过就不合理了。所以这个开关必须按流程类型配置，金额、风险类的流程强制重审。
> 我们实际只实现了「驳回到上一节点」和「驳回到发起人」两种，因为驳回到任意节点在跨并行网关、跨会签这些场景下语义不清晰——比如并行分支里一个节点的任务被驳回了，另一个分支要不要取消？我们评估后觉得收益不值这个复杂度，就用「驳回到发起人重新提交」覆盖了。**我的判断是：能做但要克制，流程引擎最怕的就是规则组合爆炸导致没人能说清它到底怎么跑。**

**Q3：会签怎么实现？一票否决和全票通过有什么区别？**

> 会签就是一个节点上有多个审批任务。数据上靠三样东西支撑：任务表里同一 `instance_id + node_key + round` 下有多条记录；节点配置里存会签策略；每次有人处理完就调一次「节点判定」函数。
> 判定函数按策略分四种：`all` 全票通过，要等所有人处理完，有一个人拒绝就整体拒绝；`any` 或签，任一人处理即完成，其他任务立即取消；`veto` 一票否决，任一人拒绝立即失败，不等其他人；`ratio` 按比例，同意数除以总数达到阈值就通过。
> **一票否决和全票通过的区别在于「提前终止」**：全票通过必须等所有人处理完才判定，即使第一个人就拒绝了，后面两个人还是要有机会表达意见，好处是留痕完整；一票否决是拒绝的瞬间就判定失败并取消其他人的任务，好处是响应快，适合风控场景。
> 还有一个优化点：按比例策略下可以**提前判定失败**——比如 5 人需要 3 票同意，已经有 3 人拒绝了，那剩下 2 人全同意也只有 2 票，达不到阈值，就可以立即判定失败不用等。
> 会签的坑主要在**加签导致的人数变化**上：会签中途加人会让总数变，比例策略下的阈值是按固定人数算还是动态算？我们用的是动态（当前总人数 × 比例），但这就可能出现「已经达标了，加完人又变成不达标」，所以产品上要定义清楚加签的语义。

**Q4：审批人是怎么确定的？「发起人的直属主管」怎么找？**

> 审批人规则做成配置项，支持几种类型：指定人、角色、部门的负责人、发起人的第 N 级主管、表单里选的字段、以及前序节点的审批人（用于「同上」）。
> 「直属主管」的实现是沿组织架构的汇报链向上找 N 层：用户表上有 `leader_id` 或者部门表上有 `leader_id`，从发起人开始逐级往上。这里有几个必须处理的边界：
> 一，**找不到上级怎么办**——比如发起人就是 CEO。必须有兜底策略，可以是「转给指定的人」「转给某个角色（如 HRBP）」「跳过这个节点」。没有兜底的话流程会直接卡死，这是生产事故。
> 二，**多人时的默认行为**——角色规则可能解析出 5 个人，默认应该是「或签」而不是「会签」，否则流程很容易卡在某个没登录的人身上。
> 三，**去重**——如果一个人既是直属主管又是 HRBP，不能给他生成两条任务。
> 四，**人员离职或调岗**——任务已经生成了，但审批人离职了怎么办？要么检测到离职自动转交给上级，要么支持管理员「改派」。这个我们当时是做了个兜底的定时任务，检测长期停留在一个节点上的实例并告警。
> 另外**解析时机很关键**，必须在任务生成时解析，不能在流程定义时。定义里存的是规则（「直属主管」），不是具体的人。

**Q5：审批过程中流程定义改了怎么办？**

> 核心原则是：**实例在启动时固化版本，改版只影响新实例**。
> 具体做法是流程定义表用 `(tenant_id, process_key, version)` 做唯一键，每次编辑生成一个新版本，老版本不删除只标记为历史。实例表里存的不是 `process_key` 而是一个具体的 `def_id`，引擎执行时从实例的 `def_id` 去加载定义，绝不加载「最新版本」。这样正在跑的实例完全不受影响。
> 补充几点：**草稿版本不能被引用**，只有已发布的版本才能启动实例；**停用不等于删除**，停用后新实例不能发起，但存量实例必须能跑完；**编辑已发布的流程要生成新版本**而不是原地修改，否则正在跑的实例会读到被改过的节点配置。
> 至于「能不能把运行中的实例迁移到新版本」，技术上改个 `def_id` 就行，但**工程上我不建议**——新版本的节点结构可能完全不同，实例的 `current_node` 在新版本里可能根本不存在，会直接卡死。真要做迁移，必须定义清楚迁移规则，比如只允许「在末尾追加节点」这类兼容性变更，并且要做节点 key 的映射表。

**Q6：审批流怎么防止重复提交和并发审批？**

> 有三个层次。
> **防重复发起**：实例表上有 `uk(tenant_id, process_key, business_key, round)` 唯一索引，同一个业务单据比如一个采购申请单，只能发起一次流程。用户重复点提交会撞唯一键，直接返回「已发起」。
> **防并发审批**：用 CAS。`UPDATE oa_task SET status='done' WHERE id=? AND assignee_id=? AND status='pending'`，看受影响行数。为 0 就说明任务已经被处理过或不是你的任务。这一条 SQL 同时解决了并发安全和权限校验两个问题，比先查再改可靠得多。
> **防消息重复消费**：审批完成后的通知、同步到业务系统这些动作是异步的，消息会重复投递，所以消费端要用「实例 ID + 节点 + 轮次」做幂等。我们用的是唯一索引兜底。
> 还有一类更隐蔽的并发问题是**实例状态和任务状态不一致**：比如审批通过的同一瞬间发起人点了撤回，或者管理员点了终止。解决办法是所有状态变更都带 `WHERE status = ?` 的前置条件，谁先成功谁生效，后到的会拿到 0 行然后提示用户「状态已变更，请刷新」。这比加分布式锁简单也可靠。

**Q7：如果让你重新设计这套引擎，你会怎么改进？**

> 这个问题是考反思能力，我会讲三点。
> **第一，条件表达式的求值要更安全**。我们当时用的是自己实现的简单表达式解析，只支持比较和逻辑运算。更好的做法是用成熟的表达式引擎（比如 expr-lang），但要限制可用的函数集合，禁止它执行任意代码，因为流程定义是用户配的，这是个注入风险点。
> **第二，超时处理从定时扫表改成延迟队列 + 扫描双保险**。定时扫表实现简单但精度受扫描间隔限制，扫得太频对数据库有压力；延迟队列精度高但服务重启可能丢消息。两者结合是最好的。
> **第三，也是最想改的——把「流程推进」做成显式的状态机而不是递归调用**。递归的 `MoveNext` 写起来简洁，但出了问题很难排查，而且不好做「执行到一半失败后的事务一致性」。更好的做法是把「待执行的节点」放进一张 `oa_execution_queue` 表，用一个 worker 循环消费，每一步都是独立的数据库事务，天然支持断点续跑和重放。这其实就是**用「状态机 + 队列」替代「递归调用」**，是我从 POS 项目用消息队列做异步化里得到的启发。

### 7.1.14 结合项目的话术提示

> **【可结合 AI 漏洞研判系统的飞书审批卡片作答 —— 这是最强映射，务必背熟】**
>
> 「虽然我没有做过传统 OA 的审批流引擎，但我做过一个本质相同的事情——AI 漏洞研判系统里的人工审批环节。
> 那个系统的多 Agent 工作流跑到「漏洞定级定价」这一步时会停下来，把研判结果通过飞书审批卡片推给安全专家，等专家点了同意或驳回之后，工作流才继续往下走。**这其实就是流程引擎里最核心的「人工任务节点 + 外部事件唤醒」模式**：
> 第一，**状态挂起**——工作流执行到这里要保存完整的上下文快照并暂停，不能占着资源空转；
> 第二，**幂等**——用户在飞书上可能重复点击、可能几小时后才点，中间服务可能重启过，所以我们的审批记录是落库的，用状态机 CAS 保证「只有状态还是待审批时才能被审批」，重复点击直接返回成功但不重复执行；
> 第三，**超时处理**——卡片长时间没人处理要有提醒和兜底；
> 第四，**审计留痕**——谁在什么时候批的、批的意见是什么，全部落库，因为 SRC 运营是有合规要求的。
> 这四个问题，正好就是审批流引擎里人工节点要解决的全部问题。所以我觉得转到 OA 审批流上，我缺的只是「节点类型更多、配置项更细」这部分业务知识的积累，而核心的机制设计我是有实践经验的。」

> **【可结合商云前台权限控制作答】**
>
> 「商云前台那个收银系统里我做过权限控制模块，虽然比 OA 的权限体系简单，但基本的模型是一致的：用户关联角色，角色关联权限点，前端根据权限点控制按钮和菜单的显示，后端接口层做二次校验。当时踩过一个坑让我印象很深——只在前端做权限控制是不够的，我们测试的时候直接用 Postman 绕过前端调接口，发现后端没校验，普通收银员能调管理员的接口。后来补上了后端的统一拦截。这个经验让我明白**权限必须在服务端做最终校验，前端控制只是体验优化**。」

## 7.2 表单引擎设计

### 7.2.1 为什么需要表单引擎

审批流是「怎么走」，表单是「填什么」。如果每个流程的表单都硬编码一个 Vue 页面：

- 新增一个「报销单」要前端写页面、后端写接口和表，两周过去了；
- 表单字段加一个要发版；
- 字段的显示/隐藏规则、必填规则散落在代码里，改一处影响多处。

表单引擎的目标是**把表单变成配置**：运营在后台拖拽出表单，绑定到流程节点上，不同节点看到的字段和权限可以不一样。

### 7.2.2 动态表单建模

#### （1）表单定义的结构

#### （2）字段类型清单

| 分类 | 类型 | 说明 | 后端存储 |
| --- | --- | --- | --- |
| 基础 | `text` / `textarea` / `number` / `money` | 文本、多行文本、数字、金额（**用分为单位存整数，避免浮点误差**） | string / int64 |
| 选择 | `select` / `radio` / `checkbox` / `multiSelect` | 单选、多选 | string / []string |
| 日期 | `date` / `datetime` / `dateRange` | 日期时间 | string（ISO8601）或 int64 时间戳 |
| 组织 | `userPicker` / `deptPicker` / `rolePicker` | 选人、选部门、选角色 | []int64 |
| 附件 | `upload` / `image` | 文件、图片 | []string（URL 列表） |
| 关联 | `relation` | 关联其他业务单据（如关联采购单） | {type, id, snapshot} |
| 高级 | `subtable`（明细表/子表单） | 一对多的明细行 | []map[string]interface{} |
| 高级 | `formula` | 计算字段（如总金额 = 单价 × 数量） | 计算得出，不存 |
| 展示 | `divider` / `label` / `richText` | 分隔线、说明文字 | 不存 |

**金额为什么用「分」存**：`float64` 表示 `0.1 + 0.2` 会得到 `0.30000000000000004`，金额计算用浮点必然出错。所以统一用「分」为单位的 `int64`，展示时除以 100。**这是一个必答的细节。**

**明细表（subtable）的存储**：JSON 里直接存数组（`[{"item":"打车","amount":5000}]`）最简单，适合行数少的场景（<100 行）。如果明细行数多或者需要按明细统计，就应该存到独立的子表（`oa_form_subtable_row(instance_id, field_key, row_no, data JSON)`）。

#### （3）校验规则

**三层校验**（缺一不可）：
1. **前端校验**：即时反馈，用户体验。（**但不能作为安全边界**——用 Postman 可以绕过。）
2. **后端通用校验**：根据字段定义自动校验（必填、类型、长度、范围、正则、枚举合法性）。**这是必须做的，因为字段定义本来就在后端**。
3. **业务校验**：跨字段、跨系统的规则（如「请假天数超过 5 天必须有附件」「报销金额不能超过预算余额」），需要单独配置或写代码。

```go
// 后端通用校验引擎
func (v *FormValidator) Validate(formDef *FormDef, data map[string]interface{}) error {
    errs := make([]string, 0)
    for _, f := range formDef.Fields {
        // 1. 显示条件：不可见的字段不校验，也不存
        if f.VisibleWhen != "" {
            visible, _ := v.expr.EvalBool(f.VisibleWhen, data)
            if !visible { continue }
        }

        val, exists := data[f.Key]

        // 2. 必填
        if f.Required && (!exists || isEmpty(val)) {
            errs = append(errs, fmt.Sprintf("%s 不能为空", f.Label))
            continue
        }
        if !exists { continue }

        // 3. 类型与长度
        if err := v.checkType(f, val); err != nil {
            errs = append(errs, fmt.Sprintf("%s 格式错误: %v", f.Label, err))
            continue
        }

        // 4. 数值范围
        if f.Type == "number" || f.Type == "money" {
            num := toFloat(val)
            if f.Min != nil && num < *f.Min {
                errs = append(errs, fmt.Sprintf("%s 不能小于 %v", f.Label, *f.Min))
            }
            if f.Max != nil && num > *f.Max {
                errs = append(errs, fmt.Sprintf("%s 不能大于 %v", f.Label, *f.Max))
            }
        }

        // 5. 自定义规则（正则、枚举、自定义消息）
        for _, rule := range f.Rules {
            if err := v.applyRule(rule, val, data); err != nil {
                errs = append(errs, err.Error())
            }
        }

        // 6. 子表：递归校验每一行
        if f.Type == "subtable" {
            rows := toSlice(val)
            if f.MaxRows > 0 && len(rows) > f.MaxRows {
                errs = append(errs, fmt.Sprintf("%s 最多 %d 行", f.Label, f.MaxRows))
            }
            for i, row := range rows {
                for _, col := range f.Columns {
                    if col.Required && isEmpty(row[col.Key]) {
                        errs = append(errs, fmt.Sprintf("%s 第 %d 行 %s 不能为空", f.Label, i+1, col.Label))
                    }
                }
            }
        }
    }
    if len(errs) > 0 {
        return &ValidationError{Errors: errs}
    }
    return nil
}
```

**表达式求值的错误处理要格外小心**：`visibleWhen` 引用的字段可能不存在（表单定义改过），求值会失败。此时**应该保守处理**（比如按「可见」处理并记日志），而不是直接报错让用户无法提交。这类「配置错误不能导致业务不可用」的思考是加分项。

#### （4）字段权限：可见 / 可编辑

**为什么需要**：同一个表单，发起人填的时候「审批意见」字段是隐藏的；主管审批时「金额」字段可以改但「申请人」不能改；HR 只能看不能改。

**实现：字段权限配置在「流程节点」上**（不是表单上），因为权限是随节点变化的。

```json
{
  "key": "n1",
  "type": "approval",
  "name": "主管审批",
  "fieldPermissions": {
    "days":     "readonly",   // 只读
    "amount":   "editable",   // 可编辑
    "reason":   "hidden",     // 隐藏
    "attachment": "editable"
  },
  "defaultPermission": "readonly"   // 未列出的字段默认只读
}
```

**三种权限值**：`hidden`（不可见，**且提交时不接收该字段的值**）、`readonly`（可见不可改）、`editable`（可改）。

**后端必须强制校验**（这一点一定要讲）：前端会根据权限渲染，但**后端在处理任务提交时必须过滤字段**——只有当节点配置为 `editable` 的字段才允许更新 `form_data`，其他字段一律忽略。否则用户可以绕过前端改任意字段。

```go
// 按节点权限过滤提交的字段
func (e *Engine) mergeFormData(inst *Instance, node *Node, submitted map[string]interface{}) map[string]interface{} {
    merged := deepCopyMap(inst.FormData)
    for key, val := range submitted {
        perm := node.FieldPermissions[key]
        if perm == "" { perm = node.DefaultPermission }
        if perm == "editable" {
            merged[key] = val
        }
        // readonly / hidden 一律忽略，不写入
    }
    return merged
}
```

**另一个常见需求：字段权限按角色/条件动态变化**。比如「金额小于 1 万时主管可以改，超过 1 万只能看」。这就在 `fieldPermissions` 的值上支持条件表达式：
```json
"fieldPermissions": {
  "amount": {"editable": "amount <= 10000", "readonly": "amount > 10000"}
}
```

#### （5）表单版本与历史数据兼容

**核心矛盾**：表单定义会改（删字段、改类型、加校验），但**已经提交的历史单据必须能正常展示**。

**三种方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **快照式** | 实例存 `form_data` 的完整 JSON 快照 + `form_version` | 数据完全自包含，展示不依赖定义；改定义不影响历史 | 存储冗余；无法统一改历史数据的展示 |
| **引用式** | 只存字段值，展示时用「当前版本」的定义渲染 | 存储省；改定义能全局生效 | **删了字段历史数据就丢了**；类型改了渲染会错乱 |
| **混合式（推荐）** | 存 `form_version` + `form_data` 快照；展示时优先用历史版本的字段定义，定义已被删除的字段则从快照里「兜底渲染」 | 兼顾两者 | 实现略复杂 |

**推荐做法**：
```go
// 实例表里存两个东西
type Instance struct {
    FormID      int64                  `gorm:"column:form_id"`
    FormVersion int                    `gorm:"column:form_version"`   // 固化表单版本
    FormData    datatypes.JSON         `gorm:"column:form_data"`      // 数据快照
}

// 详情页渲染
func (s *FormService) Render(ctx context.Context, inst *Instance) (*RenderResult, error) {
    // 1. 优先加载「当时的版本」的定义
    def, err := s.repo.GetByKeyAndVersion(ctx, inst.FormID, inst.FormVersion)
    if err != nil {
        // 版本已不存在（被清理），退化为「用数据反推字段」
        def = s.inferFieldsFromData(inst.FormData)
    }

    // 2. 用定义渲染 + 用 form_data 填充值
    fields := def.Fields
    values := inst.FormData

    // 3. 关键：定义里已经没有、但数据里存在的字段，也要展示出来（用 key 当 label 并标注）
    for k, v := range values {
        if !def.HasField(k) {
            fields = append(fields, Field{
                Key: k, Label: k + "(历史字段)", Type: guessType(v),
                Deprecated: true,
            })
        }
    }
    return &RenderResult{Fields: fields, Values: values}, nil
}
```

**表单定义变更的兼容性规则（重要）**：
- **删除字段**：不要物理删除，标记 `deleted = 1`，历史数据仍能渲染；
- **改字段类型**：危险操作。`text` → `number` 会让历史数据渲染异常。应该**新增字段**而不是改类型；
- **改字段 key**：等于删了旧的加了个新的，历史数据会丢。**key 一旦使用就不可变**，这要写进规范；
- **改枚举选项**：删掉的选项在历史数据里会出现「未知值」，渲染时要能兜底显示原始值；
- **加校验规则**：只对新提交生效，不能影响已提交的数据（否则会出现「历史单据现在校验不过」）。

**版本发布的流程**：表单定义也应该是「草稿 → 发布」的模式，发布后生成新版本，实例启动时固化版本号。**和流程定义的版本管理是同一套逻辑**——这个一致性可以主动说出来。

### 7.2.3 表单与流程的绑定

**绑定关系**：
```
流程定义（process_key） ──1:1──► 表单定义（form_id，可指定版本）
        │
        └── 每个审批节点可以配置：
              ├─ fieldPermissions：本节点的字段权限
              ├─ requiredFields：本节点要求补充的必填字段（如主管必须填「审批意见」）
              └─ allowModify：本节点是否允许修改表单数据
```

**一个流程能不能绑多个表单？** 能，但复杂度高。常见场景是「不同条件走不同表单」，实现方式是在流程定义里把表单绑在**节点**上而不是流程上，或者用条件网关分流到不同的表单节点。**大多数系统选择「一个流程一个主表单 + 节点级的字段权限」，简单可维护。**

### 7.2.4 表单引擎高频面试 Q&A

**Q1：动态表单怎么设计？数据怎么存？**

> 表单定义用 JSON 存字段数组，每个字段有 `key`、`label`、`type`、校验规则、显示条件和顺序。字段类型覆盖文本、数字、金额、日期、下拉、选人、选部门、附件、明细表这些。
> 数据存储上有两种主流方案：**一种是 JSON 存进实例表的 `form_data` 字段**，配合 MySQL 5.7+ 的 JSON 类型和生成列索引；**另一种是 EAV 模型**（一张 `form_value(instance_id, field_key, value)` 竖表）。我倾向于用 JSON 存，理由是：EAV 模型的查询要大量自连接，字段一多 SQL 就没法看了，而且类型安全差（所有值都得存成字符串）；JSON 存储天然对应表单的数据结构，读取是一次性的，配合虚拟列 + 索引也能支持按字段查询。
> JSON 方案的代价是**无法做复杂的跨字段统计查询**。如果某个字段需要频繁参与统计分析（比如「按部门统计报销金额」），我会在实例表上给它单独建一个冗余列并加索引，写入时同步维护——这就是**用冗余列换查询性能**。
> 还有一个细节：金额字段一定要用**分**为单位的整数存，不能用浮点，否则 `0.1 + 0.2` 会算出 `0.30000000000000004`。

**Q2：表单改了，历史数据怎么兼容？**

> 核心是**实例启动时固化表单版本**，展示历史数据时用当时的版本渲染，而不是用最新版本。
> 具体是实例表存三个字段：`form_id`、`form_version`、`form_data` 快照。详情页渲染时先按 `form_id + form_version` 找当时的定义；如果那个版本已经被清理了，就退化成「从 form_data 反推字段」——用 JSON 的 key 当 label 展示出来，并且标注为「历史字段」。
> 另外字段定义有几个兼容性铁律：**字段的 `key` 一旦使用就不能改**（改了等于删旧加新，历史数据全丢）；**删除字段用逻辑删除**不物理删；**不要改字段类型**（`text` 改 `number` 会让历史数据渲染错乱），需要的话新增字段；**新增的校验规则只对新提交生效**，不能影响已提交的单据，否则会出现「历史单据现在校验不过，用户连重新提交都做不到」。
> 表单定义本身也要版本化管理，用「草稿 → 发布」的模式，和流程定义是同一套逻辑。

**Q3：字段权限怎么做？**

> 字段权限配置在**流程节点**上而不是表单上，因为同一个表单在不同节点看到的权限不一样。三种权限值：`hidden` 不可见、`readonly` 可见不可改、`editable` 可改。还有一个 `defaultPermission` 兜底，没列出的字段默认取它。
> **最关键的一点是后端必须强制校验**。前端会根据权限渲染，但用户完全可以用 Postman 绕过前端提交任意字段。所以后端在处理任务提交时要按节点权限过滤——只有 `editable` 的字段才允许合并进 `form_data`，其他一律忽略。我在商云前台做权限模块时踩过这个坑：只在前端做了按钮级的权限控制，结果测试时绕过前端调接口，普通收银员能调管理员接口。**权限的最终校验必须在服务端，前端控制只是体验优化。**
> 再进阶一点，权限还可以是动态的，比如「金额小于 1 万主管能改，超过 1 万只能看」，那就把权限值也做成条件表达式，在提交时按当前数据求值。

## 7.3 组织权限体系

### 7.3.1 RBAC 模型

#### （1）经典 RBAC 的四要素

```
    用户(User) ──多对多──► 角色(Role) ──多对多──► 权限(Permission) ──► 资源(Resource)
      张三                   部门主管                  dept:edit         部门模块
```

**为什么要引入角色而不是直接给用户配权限**：如果直接「用户-权限」多对多，1000 个用户每个配 50 个权限就是 5 万条关系，新人入职要抄一遍别人的配置，权限调整要改 N 个用户。引入角色后，配置的是「角色的权限」（几十条），用户的权限通过角色继承——**这是把「变化的用户」和「稳定的权限集合」解耦**。

**权限的粒度设计（面试常问）**：
- **页面/菜单级**：`ticket:list`（能不能看到「工单管理」菜单）
- **按钮/操作级**：`ticket:create`、`ticket:delete`、`ticket:export`
- **数据级**：能看哪些工单（见下一节数据权限）
- **字段级**：能不能看到工单里的「客户手机号」（脱敏）

**权限编码规范**：`{模块}:{资源}:{操作}`，如 `oa:process:approve`、`ticket:assign`。**用字符串而且是稳定可读的编码**，不要用自增 ID——因为代码里要硬编码判断，ID 变了代码就错了。

#### （2）表结构

#### （3）RBAC 的扩展：角色继承与角色组

真实的组织里角色是**有层次的**（总监 > 经理 > 主管），权限应该是向下继承的。两种实现：
- **角色继承**：`sys_role` 加 `parent_id`，计算权限时递归向上合并。**简单但要注意环检测。**
- **权限组**：把权限打包成「权限组」，角色关联权限组。适合权限项很多（几百个）时降低配置成本。

**面试建议**：如果被问到「权限项太多怎么管理」，答「先按业务模块分组，角色配置时按组批量勾选，再支持角色继承减少重复配置」——这体现了你对配置成本的敏感。

### 7.3.2 数据权限（部门树 + 可见范围）

**功能权限**解决「能不能点这个按钮」，**数据权限**解决「能看到哪些数据」。这是 OA 系统里最容易被低估、也最容易出安全事故的地方——一个普通员工能查到全公司的薪资审批单，就是重大事故。

#### （1）五种数据范围

| 范围 | 编码 | 含义 | 典型角色 |
| --- | --- | --- | --- |
| 全部 | `1` | 所有数据 | 系统管理员、CEO |
| 本部门及下级 | `2` | 自己部门 + 所有子部门 | 总监、分管副总 |
| 本部门 | `3` | 只有自己所在部门 | 部门经理 |
| 本人 | `4` | 只有自己创建的 | 普通员工 |
| 自定义 | `5` | 指定若干部委 | 特殊授权，如 HRBP 负责几个事业部 |

#### （2）部门树的设计与子树查询

**两种存法**：

**方案 A：邻接表（`parent_id`）**
- 优点：结构简单，移动部门只改一个字段；
- 缺点：查子树要递归（MySQL 8.0 支持 CTE `WITH RECURSIVE`，但性能一般），查「某人的所有下级」要循环 N 次。

**方案 B：路径枚举（`path` 字段存 `/1/12/123/`）**
- 优点：查子树一条 SQL：`WHERE path LIKE '/1/12/%'`；
- 缺点：移动部门要批量更新所有后代的 path（但部门树很少变动，可以接受）。

**生产环境通常是两者结合**：存 `parent_id` 保证结构正确，同时冗余 `path` 用于快速子树查询，移动部门时异步重建 path。**这个「主结构 + 冗余索引」的思路可以主动说出来，是很典型的工程权衡。**

```sql
-- 查「本部门及下级」的所有用户
-- 部门表 path 形如 /1/12/123/
SELECT u.* FROM sys_user u
JOIN sys_dept d ON u.dept_id = d.id
WHERE d.path LIKE CONCAT((SELECT path FROM sys_dept WHERE id = ?), '%')
  AND u.tenant_id = ? AND u.status = 1;
```

#### （3）数据权限的实现方式

**方式一：SQL 拼接（最常用）**

```go
// 数据权限拦截器：在 DAO 层统一注入 where 条件
type DataScope struct {
    Scope     int      // 1全部 2本部门及下级 3本部门 4本人 5自定义
    UserID    int64
    DeptIDs   []int64  // 解析好的可见部门列表
}

func (d *DataScope) Apply(query *gorm.DB, column string) *gorm.DB {
    switch d.Scope {
    case 1: // 全部，不加条件
        return query
    case 2: // 本部门及下级
        return query.Where(column+" IN ?", d.DeptIDs)
    case 3: // 本部门
        return query.Where(column+" = ?", d.DeptIDs[0])
    case 4: // 本人
        return query.Where("initiator_id = ?", d.UserID)
    case 5: // 自定义部门
        return query.Where(column+" IN ?", d.CustomDeptIDs)
    }
    return query.Where("1 = 0") // 兜底：不认识的 scope 一律不给数据
}

// 使用
func (r *InstanceRepo) List(ctx context.Context, q *ListQuery) ([]Instance, error) {
    db := r.db.Model(&Instance{}).Where("tenant_id = ?", q.TenantID)
    if q.Keyword != "" {
        db = db.Where("title LIKE ?", "%"+q.Keyword+"%")
    }
    // 统一注入数据权限
    db = q.DataScope.Apply(db, "initiator_dept")
    var list []Instance
    return list, db.Order("create_time DESC").Limit(q.Size).Find(&list).Error
}
```

**实现要点**：
1. **必须在 DAO 层统一注入**，不能让每个业务方法自己写——漏一个就是一个越权漏洞；
2. **「本部门及下级」的部门列表要预先解析好**（在请求进入时查一次部门树，放进 context），不要在 SQL 里做子查询（性能差且难维护）；
3. **兜底必须安全**：`switch` 的 default 分支应该是「不给数据」而不是「给全部数据」——**配置错误时必须往安全的方向失败（fail-safe）**；
4. **列表和详情都要校验**：列表做了过滤，但详情接口 `GET /instance/{id}` 如果只按 ID 查，用户猜到 ID 就能越权查看。**详情必须校验数据权限，这是最常见的越权漏洞来源。**

**方式二：数据权限表（更灵活，用于复杂场景）**

对于「谁对哪些数据有权限」变化很大的场景（如销售系统中每个销售只能看自己的客户，但转岗后客户要交接），可以用一张关系表：

```sql
CREATE TABLE `data_permission` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `tenant_id`   BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `subject_type` TINYINT NOT NULL COMMENT '1用户 2角色 3部门',
  `subject_id`  BIGINT UNSIGNED NOT NULL,
  `resource_type` VARCHAR(64) NOT NULL COMMENT '资源类型，如 ticket',
  `resource_id` BIGINT UNSIGNED NOT NULL,
  `permission`  VARCHAR(32) NOT NULL COMMENT 'read/write/admin',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_all` (`tenant_id`, `subject_type`, `subject_id`, `resource_type`, `resource_id`),
  KEY `idx_resource` (`resource_type`, `resource_id`)
) COMMENT='数据权限关系表';
```
- 优点：粒度最细，能做到「这条工单只有张三和李四能看」；
- 缺点：数据量会很大（每份数据 × 每个有权限的人），适合权限对象少的场景。

**面试建议**：主推「角色数据范围（SQL 注入）」方案，把关系表方案作为「更细粒度时的补充」——**分层设计，大部分场景用简单方案，少数特殊场景用灵活方案**，这个表达很加分。

### 7.3.3 ABAC 简介

**RBAC 的局限**：RBAC 是静态的、基于身份的（「你是主管所以你能看」）。但很多场景需要**基于属性**的动态决策：

- 「工作时间内可以访问，非工作时间不行」（环境属性）
- 「金额小于 1 万的自己批，超过 1 万需要上级批」（资源属性）
- 「只有本部门的工单才能操作，且不能操作自己提交的工单」（主体+资源+环境）

**ABAC = 属性基访问控制**，用四类属性做决策：
```
主体属性（Subject）：用户ID、部门、角色、职级、在职状态
资源属性（Resource）：资源类型、所有者、部门、金额、密级
动作属性（Action）：读、写、审批、导出
环境属性（Environment）：时间、IP、设备、地理位置

策略（Policy）：IF 主体.department == 资源.department AND 环境.time 在工作时间内 THEN ALLOW
```

**实现方式**：
- **策略引擎**：OPA（Open Policy Agent，用 Rego 语言写策略）、Casbin（Go 生态最流行，支持 RBAC/ABAC/RESTful 模型）
- **Casbin 示例**：
```go
e, _ := casbin.NewEnforcer("model.conf", "policy.csv")

// model.conf
// [request_definition]
// r = sub, obj, act
// [policy_definition]
// p = sub, obj, act
// [matcher]
// m = r.sub.department == r.obj.department && r.act == p.act

if ok, _ := e.Enforce(user, ticket, "read"); ok {
    // 允许
}
```

**RBAC vs ABAC 的取舍**：

| 维度 | RBAC | ABAC |
| --- | --- | --- |
| 配置成本 | 低，配角色即可 | 高，要写策略 |
| 灵活度 | 低，只能表达「角色能做什么」 | 高，任意属性组合 |
| 性能 | 高（查缓存即可） | 较低（每次要算策略） |
| 可解释性 | 好（「因为你是主管」） | 差（策略复杂后没人说得清） |
| 适用 | **95% 的场景** | 合规要求高、规则复杂的场景 |

**实践建议（面试话术）**：「我的建议是**RBAC 为主，ABAC 为辅**。主体权限（能不能进这个模块、能不能点这个按钮）用 RBAC，因为它简单直观、性能好、可解释；只有少量动态规则（如时间限制、金额分级、密级控制）才用 ABAC 兜底。全盘 ABAC 的问题是策略会膨胀到没人能说清系统的权限行为，反而容易出漏洞。」

### 7.3.4 多租户方案

如果这套 OA 系统要卖给多个企业客户，就需要多租户隔离。三种方案：

| 方案 | 隔离级别 | 成本 | 适用 |
| --- | --- | --- | --- |
| **独立数据库** | 最高（物理隔离） | 最高（每租户一套库，运维成本 × N，升级要跑 N 次） | 大客户、金融/医疗等强合规要求 |
| **共享库 + 独立 Schema** | 中（逻辑隔离） | 中（一个库多 Schema，连接池和迁移管理复杂） | 中等规模、数量不多的租户 |
| **共享表 + `tenant_id` 字段** | 低（行级隔离） | 最低（一套表全租户共用） | **SaaS 最常用**，租户数多但单租户数据量小 |

**共享表方案的实现要点（重点，也是最常考的）**：
1. **所有表都要有 `tenant_id` 且必须在索引的最左列**——否则跨租户查询会全表扫描；
2. **所有查询自动注入 `tenant_id`**，在 ORM 层做（GORM 的 `Scopes` 或插件），**不能让业务代码自己写**，漏一个就是跨租户数据泄露；
```go
// GORM 全局租户插件
func TenantScope(tenantID int64) func(db *gorm.DB) *gorm.DB {
    return func(db *gorm.DB) *gorm.DB {
        if tenantID <= 0 {
            // 兜底：没有租户上下文，拒绝查询而不是查全表
            return db.Where("1 = 0")
        }
        return db.Where("tenant_id = ?", tenantID)
    }
}
db.Scopes(TenantScope(ctxTenantID)).Find(&tickets)
```
3. **唯一索引要带上 `tenant_id`**：`UNIQUE KEY uk_username (tenant_id, username)`，否则 A 租户的 `admin` 会挡住 B 租户的 `admin`；
4. **缓存 key 要带租户前缀**：`ticket:{tenant_id}:{id}`，否则缓存会串租户——**这是最隐蔽的跨租户泄露**；
5. **数据量大时按 `tenant_id` 分库**：大客户单独一个库，小客户共享，这就是「混合模式」，兼顾成本和大客户体验；
6. **跨租户的运营后台**要单独设计（平台管理员需要跨租户统计），用一个特殊的超级权限通道，且**必须有审计日志**。

### 7.3.5 登录认证与 SSO

#### （1）Session vs JWT

| 维度 | Session | JWT |
| --- | --- | --- |
| 状态 | 服务端存储（内存/Redis），有状态 | 无状态，信息在 token 里 |
| 横向扩展 | 需要会话共享（Redis 或粘滞） | 天然支持（服务端不存） |
| 主动失效 | 容易（删 session） | **困难**（签发后无法撤销直到过期） |
| 跨服务/跨域 | 需要共享 session 存储 | 天然支持 |
| 体积 | 小（只有一个 sessionId） | 大（每次带完整 claims） |
| 适用 | 单体、传统 Web | 微服务、前后端分离、开放 API |

**JWT 的结构**：`Header.Payload.Signature` 三段 Base64URL。Header 说明算法（`{"alg":"HS256","typ":"JWT"}`），Payload 放 claims（`sub`、`exp`、`iat`、自定义的 `uid`、`tenant_id`、`roles`），Signature 是对前两段用密钥签名。

**JWT 必须注意的安全点**（面试加分）：
1. **不要放敏感信息**：Payload 只是 Base64 编码，不是加密，任何人都能解开看；
2. **`alg: none` 攻击**：库如果接受 `none` 算法就等于没有签名，必须显式校验算法；
3. **密钥要够强**，且**不能泄露**（泄露后可以伪造任意用户）；
4. **无法主动失效**是硬伤。解决方案：
   - **短过期 + Refresh Token**：access token 15 分钟，refresh token 7 天，refresh 存在服务端（Redis）可以撤销；
   - **黑名单**：登出/改密码时把 token 的 `jti` 加入 Redis 黑名单，过期时间 = token 剩余有效期。代价是每次请求要查一次 Redis（可以用本地缓存优化）；
   - **版本号**：用户表存 `token_version`，JWT 里带上，改密码时 version+1，所有老 token 自动失效。
5. **`exp` 必须校验**，且服务端时间要同步（NTP）。

#### （2）OAuth2 与 OIDC

**OAuth2 是「授权」框架，不是「认证」框架**——这点一定要说清楚，很多人搞混。

**四种授权模式**（面试必须能说出前两种）：
| 模式 | 流程 | 适用 |
| --- | --- | --- |
| **授权码模式（Authorization Code）** | 前端跳转到授权服务器 → 用户登录并同意 → 回调带上 code → 后端用 code 换 token | **最安全，Web 应用标准做法**。配合 PKCE 用于移动端/SPA |
| **简化模式（Implicit）** | 直接返回 token 在 URL fragment 里 | 已废弃（token 暴露在浏览器历史），改用授权码 + PKCE |
| **密码模式（Password）** | 客户端直接拿用户名密码换 token | 仅用于高度信任的第一方客户端，OAuth 2.1 已移除 |
| **客户端凭证（Client Credentials）** | 服务端对服务端，没有用户 | 内部服务间调用 |

**授权码模式的完整流程（企业微信/飞书扫码登录就是这个）**：
```
1. 前端跳转：https://open.work.weixin.qq.com/wwopen/sso/qrConnect?appid=xx&redirect_uri=yy&state=zz
2. 用户在企微扫码确认
3. 企微回调你的 redirect_uri?code=abc&state=zz
4. 后端用 code + appsecret 调企微接口换 access_token
5. 用 access_token 拿用户信息（userid）
6. 用 userid 查本地用户表 → 建立本地会话（签发自己的 JWT 或建 session）
7. 返回给前端，登录完成
```
**关键点**：`state` 参数用于防 CSRF（回调时要校验 state 和发起时一致）；`code` 只能用一次且有短有效期；**appsecret 绝不能放在前端**。

**OIDC（OpenID Connect）= OAuth2 + 身份认证层**。它在 OAuth2 之上加了一个 `id_token`（就是一个 JWT），里面标准化了用户身份字段（`sub`、`name`、`email`、`picture`），还定义了 `/.well-known/openid-configuration` 发现端点和 `userinfo` 接口。**简单说：OAuth2 给你一张「能进门的门禁卡」，OIDC 额外告诉你「你是谁」。** 企业 SSO 应该用 OIDC。

#### （3）OA 系统的登录实践

真实 OA 系统的登录一般是：
```
用户 → OA 登录页 → 跳转企业微信/飞书扫码（OIDC）→ 拿到用户身份
     → 匹配本地用户（首次登录自动创建）→ 签发本地 JWT + 建立会话
     → 后续请求带 JWT → 网关校验签名和过期 → 解析出 uid/tenant_id 放进 context
     → 业务层从 context 取用户身份做权限判断
```

**关键设计**：
- **用户信息不放在 JWT 里全部带上**（角色多的时候 token 会很大），只放 `uid` + `tenant_id`，权限在服务端查缓存；
- **权限缓存**：用户权限列表（角色 + 权限点 + 数据范围）缓存在 Redis，key 是 `perm:{tenant}:{uid}`，用户角色变更时**主动删除缓存**；
- **多租户下的登录**：要么用不同的域名/子域名区分（`acme.oa.com` vs `beta.oa.com`），要么让用户先输企业码再登录。

### 7.3.6 组织权限高频面试 Q&A

**Q1：RBAC 怎么设计？权限粒度到什么程度？**

> RBAC 是四要素：用户、角色、权限、资源。核心是两张关联表：用户-角色、角色-权限。引入角色的价值在于**把「变化的用户」和「相对稳定的权限集合」解耦**——如果直接给用户配权限，1000 个用户每人 50 个权限就是 5 万条关系，新人入职要抄配置，调整一个权限要改一批用户。
> 权限粒度我一般分四层：**菜单级**（能不能看到这个模块）、**操作级**（能不能点新增/删除/导出按钮）、**数据级**（能看到哪些数据，这是数据权限的范畴）、**字段级**（像客户手机号这种敏感字段要不要脱敏）。
> 权限编码用 `模块:资源:操作` 这样的字符串，比如 `oa:process:approve`，**不用自增 ID**，因为代码里要做判断，ID 变了代码就错了。
> 补充两点实践：一，权限项多了之后要有**权限分组**，角色配置时按组批量勾选，降低配置成本；二，如果角色有明显的层级（总监 > 经理 > 主管），可以支持**角色继承**，权限向下继承，减少重复配置，但要做环检测。
> 还有一个容易忽略的：**权限变更后要主动清缓存**。用户的权限列表一般是缓存在 Redis 里的，管理员改了角色权限后如果不清缓存，用户要等缓存过期才生效——这在「紧急收回某人权限」的场景下是安全事故。

**Q2：数据权限怎么做？「本部门及下级」怎么实现？**

> 数据权限和功能权限要分开看：功能权限管「能不能操作」，数据权限管「能看到哪些数据」。
> 标准做法是**给角色配一个数据范围**，通常是五种：全部、本部门及下级、本部门、本人、自定义部门。实现分三步：
> 第一步，**解析可见范围**。用户登录或请求进入时，根据他的角色算出「可见的部门 ID 列表」。如果是「本部门及下级」，就要查部门树拿到所有子部门。
> 第二步，**在 DAO 层自动注入条件**。这是关键——必须在 ORM 层统一做（GORM 的 Scopes 或插件），不能让每个业务方法自己拼 where，因为漏一个就是一个越权漏洞。注入时兜底要安全，遇到不认识的范围值应该返回空数据而不是全部数据。
> 第三步，**详情接口也要校验**。列表过滤了但详情接口如果只按 ID 查，用户猜到 ID 就能越权看别人的数据——**这是最常见的越权漏洞来源**。
> 部门树的实现我倾向「`parent_id` 保证结构 + 冗余 `path` 字段加速子树查询」：`path` 存 `/1/12/123/` 这样的祖级路径，查子树就是 `WHERE path LIKE '/1/12/%'` 一条 SQL。代价是移动部门要批量更新后代的 path，但部门树很少变动，这个代价可以接受。
> 还有一点：**「本部门及下级」的部门列表要预先解析好放进 context**，不要在每条 SQL 里做子查询，那样性能很差。

**Q3：多租户怎么实现？**

> 三种方案：独立数据库、共享库独立 Schema、共享表加 `tenant_id` 字段。隔离性从高到低，成本从高到低。
> 独立库隔离最好，但运维成本是乘 N 的——每加一个租户就要建一套库、跑一次迁移，升级要跑 N 遍，所以只适合大客户或强合规要求（金融、医疗）。共享表加 `tenant_id` 是 SaaS 最常用的，成本最低，但**有六个坑必须处理**：
> 一，**所有表的 `tenant_id` 必须在索引最左列**，否则跨租户查询会全表扫描；
> 二，**所有查询必须自动注入 `tenant_id`**，在 ORM 层做统一插件，绝不能靠业务代码自觉——漏一个就是跨租户数据泄露；
> 三，**唯一索引要带 `tenant_id`**，否则 A 租户的 `admin` 会把 B 租户的 `admin` 挡住；
> 四，**缓存 key 要带租户前缀**，这是最隐蔽的泄露——A 租户查出来的数据被缓存后，B 租户查同一个 key 就读到了；
> 五，**兜底要 fail-safe**，租户上下文缺失时应该拒绝查询，而不是查全表；
> 六，**数据量大时按租户分库**，做成混合模式：大客户独占库，小客户共享库，兼顾成本和大客户体验。
> 另外平台级的运营后台需要跨租户查询，这个要走特殊的超级权限通道，并且必须有审计日志——因为这是权限体系的最高危操作。

**Q4：企业微信/飞书扫码登录是怎么实现的？**

> 标准做法是走 OAuth2 的授权码模式，企微和飞书都支持。流程是：前端跳转到企微的扫码页面，带上 `appid`、`redirect_uri` 和一个随机的 `state`；用户扫码确认后，企微回调我们的 `redirect_uri` 并带上 `code`；后端拿 `code` 加上 `appsecret` 去调企微接口换 `access_token`，再用 token 拿用户的 `userid`；然后用 `userid` 匹配本地用户表，首次登录可以自动创建账号；最后签发我们自己的 JWT 返回给前端，登录完成。
> 几个安全细节：**`state` 参数必须校验**，回调时对比发起时的值，防 CSRF；**`code` 只能用一次**且有很短的有效期；**`appsecret` 绝对不能放前端**，只能在服务端使用。
> 另外要区分 OAuth2 和 OIDC：**OAuth2 是授权框架不是认证框架**，它只解决「你能访问什么」，不解决「你是谁」。OIDC 是在 OAuth2 之上加了身份层，多返回一个 `id_token`（是个 JWT），里面标准化了 `sub`、`name`、`email` 这些身份字段，还有标准的发现端点。企业 SSO 应该用 OIDC。企微和飞书都提供 OIDC 兼容的接口。
> 落地到 OA 系统里，我们自己的会话用的是 JWT，但只放 `uid` 和 `tenant_id`，**不把角色权限也塞进去**——因为角色多的时候 token 会很大，而且权限变更后老 token 里的权限是过期的。权限应该服务端查缓存。

**Q5：JWT 怎么主动失效？**

> 这是 JWT 的固有短板——它是无状态的，签发后在过期前一直有效，服务端没有地方「撤销」它。有三种解法：
> **一，短过期 + Refresh Token**：access token 设 15 分钟，refresh token 设 7 天且存在服务端（Redis），登出或封号时删掉 refresh token。这样最多 15 分钟后生效。这是最常见的方案。
> **二，黑名单**：登出时把 token 的唯一标识 `jti` 加入 Redis 黑名单，过期时间是 token 的剩余有效期。缺点是每次请求都要查一次 Redis——可以用本地缓存加短 TTL 优化，但要接受几秒的不一致窗口。
> **三，版本号机制**：用户表加一个 `token_version` 字段并写进 JWT，改密码或强制下线时把 version 加一，所有老 token 校验时因为版本不匹配直接失效。这个方案的好处是**一次操作让该用户所有设备的 token 全部失效**，很适合「改密码后踢掉所有登录」的场景，而且只需要查一次用户信息（本来就要查，可以合并）。
> 我们实践里是方案一和三结合：短过期的 access token + 服务端可撤销的 refresh token，外加版本号做强制下线。
> 另外提醒几个 JWT 的安全点：Payload 只是 Base64 编码不是加密，**不能放敏感信息**；库必须显式校验算法，防 `alg: none` 攻击；签名密钥要够强且严格保密，泄露了就能伪造任意用户。

### 7.3.7 结合项目的话术提示

> **【可结合商云前台的权限控制模块作答】**
>
> 「我在商云前台做过权限控制模块。那是个桌面收银应用，权限模型是简版的 RBAC——用户关联角色，角色关联权限点，前端根据权限点控制菜单和按钮的显示。
> 当时有个坑我印象很深：我们一开始只在前端做了权限控制，因为收银端的界面比较定制化，觉得前端控制就够了。结果测试的时候有人用 Postman 直接绕过前端去调管理员的接口，发现后端完全没校验，普通收银员能调管理员的功能。后来我们补上了后端的统一拦截——每个接口声明需要的权限点，在中间件里统一校验。
> **这件事让我形成了一个认知：权限的最终校验必须在服务端，前端控制只是体验优化。** 所以我特别能理解为什么 OA 系统里数据权限要在 DAO 层统一注入而不能靠每个业务方法自己写——因为「靠自觉」的方案一定会漏。
> 另外那个项目还有个细节是多级客户的数据结构，渠道商下面有分销商、分销商下面有门店，每级只能看到自己下属的数据。这其实就是「本部门及下级」数据权限的一个变体，我们用路径枚举的方式实现了子树查询。」

> **【可结合 AI 漏洞研判系统作答】**
>
> 「AI 漏洞研判系统里也有权限相关的设计。那个系统是给 SRC 运营和安全专家用的，不同角色能做的事差别很大——普通运营只能提交和查看自己的报告，专家才能做漏洞定级定价，管理员才能改配置。我们的实现是接口级的权限点校验，每个接口声明需要的权限码。
> 有一点和 OA 很像：**漏洞报告的可见范围是有数据权限的**。一个漏洞报告可能涉及某个业务线，那这个业务线的负责人应该能看到，其他业务线的不应该看到。我们的做法是在查询层注入业务线的过滤条件，而不是在应用层过滤——因为应用层过滤意味着数据已经查出来了，万一某个接口忘了过滤就直接泄露了。」

### 7.4.1 工单生命周期

#### （1）完整的状态流转

```
   ┌──────────┐
   │  待受理   │◄──────────────┐
   │ pending  │               │
   └────┬─────┘               │
        │ 分配/认领            │
        ▼                     │
   ┌──────────┐   转办/升级    │
   │  处理中   │───────┐       │
   │processing│◄──────┘       │
   └────┬─────┘               │
        │ 解决(resolve)        │ 重开(reopen)
        ▼                     │
   ┌──────────┐               │
   │  待确认   │───────────────┘
   │ resolved │
   └────┬─────┘
        │ 客户确认 / 超时自动关闭
        ▼
   ┌──────────┐    ┌──────────┐
   │  已关闭   │    │  已取消   │  （用户撤销或重复工单合并）
   │  closed  │    │ canceled │
   └──────────┘    └──────────┘
```

**每一步的语义（面试要能说清）**：
| 状态 | 谁触发 | 说明 |
| --- | --- | --- |
| **待受理** | 用户创建 | 还没有人负责，可能在被分配或在排队 |
| **处理中** | 坐席认领或系统分配 | 有明确负责人，SLA 开始计时 |
| **待确认** | 坐席点击「解决」 | 等用户确认问题是否真的解决了。**这个状态非常重要**——它是防止坐席「为了 KPI 草率关单」的机制 |
| **已关闭** | 用户确认 / 超时自动 | 用户 N 天不确认就自动关闭（一般 3-7 天） |
| **已取消** | 用户 / 系统 | 用户自己撤销，或者被合并到另一个工单 |
| **重开** | 用户 | 关闭后一段时间内（如 7 天）用户还能重开，重开后回到处理中并关联原坐席 |

**「重开」的设计要点**：重开不是把状态改回去那么简单——要保留**原处理人和完整的沟通历史**，并且**重新计算 SLA**（但要用新的 SLA 周期，不能沿用旧的，否则一重开就超时）。同时要**记录重开次数**，重开率高说明坐席解决问题不彻底，这是质检指标。

**SLA 的「工作时间」是个大坑**（能主动说出来是加分项）：客户提工单是周六晚上，但客服周一才上班，如果按自然时间算，SLA 一开始就超时了。所以 SLA 必须支持**工作日历**：`首次响应截止时间 = 从当前时间开始，按工作日历累加 N 分钟`。实现上要写一个「工作日历计算器」，跳过非工作时间和节假日。

```go
// 按工作日历计算截止时间
func (c *Calendar) AddMinutes(start time.Time, minutes int, cal *WorkCalendar) time.Time {
    cur := start
    remain := minutes
    for remain > 0 {
        if !cal.IsWorkingTime(cur) {
            cur = cal.NextWorkingTime(cur)  // 跳到下一个工作时间点
            continue
        }
        // 当前工作时段剩余时长
        segEnd := cal.CurrentSegmentEnd(cur)
        avail := int(segEnd.Sub(cur).Minutes())
        if avail >= remain {
            cur = cur.Add(time.Duration(remain) * time.Minute)
            remain = 0
        } else {
            remain -= avail
            cur = cal.NextWorkingTime(segEnd)
        }
    }
    return cur
}
```

### 7.4.2 IM 在线会话

> **这是求职者最有优势的部分**——数字人项目里做过腾讯 IM 对接、消息幂等、跨实例通话控制。要讲出「我不是只会调 SDK，我懂底层的连接管理和消息可靠性」。

#### （1）长连接接入方案

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **直接 WebSocket** | 简单可控 | 要自己处理鉴权、心跳、重连、集群路由 | 自建，团队有经验 |
| **WebSocket + 网关** | 网关统一处理连接管理，业务服务无状态 | 多一跳 | **推荐**，主流做法 |
| **第三方 IM（腾讯云 IM / 融云 / 环信）** | 快速上线，消息可靠性有保障 | 成本、定制受限、数据在别人那 | 中小企业、非核心业务 |
| **SSE（Server-Sent Events）** | 简单，浏览器原生支持 | **单向**，只能服务端推 | 只需服务端推送的场景（如工单状态变更通知） |
| **长轮询** | 兼容性最好 | 延迟高、服务端压力大 | 兜底方案（WebSocket 不通时降级） |

**推荐架构（自建）**：
```
客户端 ──WebSocket──► 长连接网关集群（Go）
                      ├─ 连接管理：一个 uid 一个连接（或一个 uid 多端连接）
                      ├─ 心跳：30s ping / 90s 无 pong 断开
                      ├─ 鉴权：连接建立时校验 JWT
                      └─ 消息路由：查 Redis 找出接收方在哪个节点，本节点直投，否则 gRPC 转发
                              │
                              ▼
                      消息服务（收到消息 → 落库 → 投递）
                              │
                              ▼
                      RabbitMQ（异步：通知、统计、离线推送、工单联动）
```

#### （2）消息可靠性的四个机制

**对标求职者在 LoveSpouse 里做的腾讯 IM 集成**：

1. **客户端 ACK**：服务端投递消息后，客户端必须回 ACK 表示收到。服务端维护「已发送未确认」的消息，超时未 ACK 就重推（客户端可能断线了），重推上限 N 次。
2. **服务端 ACK + 客户端重发**：客户端发的消息，服务端**落库成功后**才回 ACK。客户端超时没收到 ACK 就重发——**所以服务端必须做幂等**，用客户端生成的 `client_msg_id` 作为幂等键。
3. **序号（seq）机制**：每个会话维护一个单调递增的 `seq`，服务端按 seq 顺序分配。客户端按 seq 排序展示，**发现 seq 不连续就主动调接口拉取缺失的消息**。这是解决「消息乱序和丢消息」最有效的机制。
4. **离线消息**：接收方不在线时存离线消息（Redis List 存最近 N 条 + MySQL 全量），上线后按「本地最大 seq」增量拉取。

```go
// 消息幂等处理（参考数字人项目对接腾讯 IM 的做法）
func (s *MessageService) HandleIncoming(ctx context.Context, msg *IncomingMessage) error {
    // 1. 幂等：用 clientMsgID + 会话ID 做唯一键
    dedupKey := fmt.Sprintf("im:dedup:%d:%s", msg.ConversationID, msg.ClientMsgID)
    ok, err := s.redis.SetNX(ctx, dedupKey, "1", 24*time.Hour).Result()
    if err != nil {
        return err // Redis 异常，让上游重试
    }
    if !ok {
        // 已处理过，直接返回成功（让上游停止重发）
        return nil
    }

    // 2. 分配会话内的序号（Redis INCR 保证原子且连续）
    seq, err := s.redis.Incr(ctx, fmt.Sprintf("im:seq:%d", msg.ConversationID)).Result()
    if err != nil { return err }

    // 3. 落库（唯一索引 uk(conversation_id, client_msg_id) 兜底）
    record := &Message{
        ConversationID: msg.ConversationID,
        ClientMsgID:    msg.ClientMsgID,
        Seq:            seq,
        FromUID:        msg.FromUID,
        Content:        msg.Content,
        ContentType:    msg.ContentType,
        Status:         "sent",
        CreateTime:     time.Now(),
    }
    if err := s.db.Create(record).Error; err != nil {
        if isDuplicateKey(err) {
            return nil // 唯一索引冲突 = 已处理
        }
        return err
    }

    // 4. 更新会话的最后消息（用于会话列表展示，用 CAS 保证 seq 单调）
    s.db.Exec("UPDATE cs_conversation SET last_msg_id = ?, last_msg_seq = ?, "+
        "last_msg_preview = ?, update_time = NOW() "+
        "WHERE id = ? AND last_msg_seq < ?",
        record.ID, seq, truncate(msg.Content, 50), msg.ConversationID, seq)

    // 5. 异步投递（不阻塞 ACK）
    s.mq.Publish(ctx, "im.message.new", record)
    return nil
}
```

**代码里的四个关键点**：
- **Redis SETNX 做快速去重 + 数据库唯一索引兜底**——和 POS 项目的幂等方案完全一致，可以互相印证；
- **seq 用 Redis INCR**，保证原子且连续；更新会话的 `last_msg_seq` 用 CAS（`WHERE last_msg_seq < ?`），防止乱序更新导致会话列表显示旧消息；
- **先落库再 ACK**，不能反过来；
- **投递走异步**，ACK 不被投递耗时拖慢。

#### （3）多端同步与会话列表

- **多端在线**：同一个 uid 在 App 和 Web 都登录了，消息要投给所有端（推给每个连接）；
- **已读同步**：用「最大已读 seq」而不是「每条消息的已读状态」——只同步一个数字，成本极低。A 端读了消息，把 `max_read_seq` 同步给服务端，服务端推给 B 端，B 端本地把 seq ≤ max_read_seq 的都标记为已读；
- **会话列表**：需要展示「每个会话的最后一条消息 + 未读数」，如果每次查列表都去 count 未读，N 个会话就是 N 次查询。优化做法是**冗余字段**：会话表上存 `last_msg_id`、`last_msg_preview`、`unread_count`，发消息时维护；未读数用 Redis 的 Hash 存（`HINCRBY unread:{uid} {convID} 1`），读取时一次性 `HMGET` 拿全部。

### 7.4.3 坐席分配策略

#### （1）四种策略详解

| 策略 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **轮询（Round Robin）** | Redis `INCR` 取模，或环形队列 | 绝对均匀，实现最简单 | **不考虑当前负载**，手上压着 20 个会话的人和空闲的人分到一样多 | 流量小、处理时长均匀的场景 |
| **最少会话数（Least Active）** | Redis ZSet，score = 当前会话数，取最小的 | 负载均衡效果好，**生产最常用** | 老坐席会持续被分派（因为他们处理快），可能过载 | 处理时长差异大的场景 |
| **技能组路由（Skill-based）** | 工单先按类型路由到技能组，组内再选人 | 专业问题给专业的人，**解决率大幅提升** | 需要维护技能矩阵，组间忙闲不均时无法互相支援 | 客服系统标配 |
| **加权分配（Weighted）** | 按权重比例分配（新手 0.5、老手 1.5） | 可以给新人少分单，也可以给骨干多分单 | 权重需要人工维护 | 有新人培养需求的团队 |
| **空闲时长优先** | 记录坐席最近一次会话结束时间，最久空闲的优先 | 让每个人都有活干，避免有人一直闲着 | 需要维护时间戳 | 团队氛围敏感的场景 |

#### （2）实现代码

```go
type AssignStrategy interface {
    Select(ctx context.Context, candidates []Agent) (*Agent, error)
}

// 最少活跃会话数 + 在线过滤 + 超载保护
type LeastActiveStrategy struct {
    redis *redis.Client
}

func (s *LeastActiveStrategy) Select(ctx context.Context, candidates []Agent) (*Agent, error) {
    if len(candidates) == 0 { return nil, ErrNoAgent }

    best := (*Agent)(nil)
    bestLoad := math.MaxInt32
    for i := range candidates {
        a := &candidates[i]
        // 1. 硬性过滤：离线、休息、超载的一律跳过
        if !a.Online || a.Status != "available" { continue }
        if a.CurrentSessions >= a.MaxSessions { continue }

        // 2. 取实时负载（Redis Hash 里的值，比数据库实时）
        load := s.getLoad(ctx, a.ID)
        // 3. 归一化：把负载换算成「饱和度」，避免 MaxSessions 不同导致不公平
        //    比如 A 上限 5 当前 4（80%），B 上限 20 当前 10（50%）→ 应该选 B
        saturation := float64(load) / float64(a.MaxSessions)
        if saturation < float64(bestLoad)/float64(1) {
            best = a
            bestLoad = int(saturation * 100)
        }
    }
    if best == nil { return nil, ErrNoAgent }
    return best, nil
}

// 分配入口：技能组路由 → 组内选人 → 失败进排队
func (s *AssignService) Assign(ctx context.Context, ticket *Ticket) error {
    // 1. 技能组路由：按工单类型找到匹配的技能组（可能匹配多个，按优先级排）
    groups, err := s.routeToGroups(ctx, ticket)
    if err != nil { return err }

    for _, g := range groups {
        candidates, err := s.getAvailableAgents(ctx, g.ID)
        if err != nil || len(candidates) == 0 { continue }

        agent, err := s.strategy.Select(ctx, candidates)
        if err != nil { continue }

        // 2. 原子占位：用 Lua 保证「检查 + 占用」原子，防并发超卖
        ok, err := s.tryOccupy(ctx, g.ID, agent.ID, agent.MaxSessions)
        if err != nil || !ok { continue } // 被别人抢了，试下一个

        // 3. 更新工单
        return s.db.Model(&Ticket{}).
            Where("id = ? AND status = 'pending'", ticket.ID).
            Updates(map[string]interface{}{
                "assignee_id": agent.ID, "group_id": g.ID,
                "status": "processing", "assign_time": time.Now(),
            }).Error
    }

    // 4. 没有可用坐席 → 进入排队池
    return s.enqueue(ctx, ticket)
}
```

```lua
-- tryOccupy: 原子地检查并占用坐席名额（防止并发超卖）
-- KEYS[1] = agent:load:{groupID}   (ZSet, member=agentID, score=当前会话数)
-- ARGV[1] = agentID  ARGV[2] = maxSessions
local load = redis.call('ZSCORE', KEYS[1], ARGV[1])
if not load then return 0 end                    -- 坐席不在池子里（已下线）
if tonumber(load) >= tonumber(ARGV[2]) then return 0 end  -- 已超载
redis.call('ZINCRBY', KEYS[1], 1, ARGV[1])
return 1
```

**「归一化饱和度」这个细节非常加分**：如果坐席的 `maxSessions` 配置不同（有人能同时接待 5 个，有人能接待 20 个），单纯比较绝对会话数是不公平的——一个上限 5 现在 4 个的人（80% 饱和）其实比上限 20 现在 10 个的人（50%）更忙。**应该比较饱和度而不是绝对值。这个思考能立刻和其他候选人拉开差距。**

**并发超卖问题**：多个分配请求同时选到同一个坐席，都看到「当前 4 个，没到上限 5」，然后都分配 → 变成 6 个，超载。解决办法是**用 Lua 脚本把「检查 + 占用」做成原子操作**。**这个坑非常真实，一定要讲。**

#### （3）分配失败与排队

```go
// 排队池：Redis ZSet，score = 优先级权重 * 10^13 + 入队时间戳
// 这样先按优先级排，同优先级内按等待时间排（FIFO）
func (s *QueueService) enqueue(ctx context.Context, ticket *Ticket) error {
    score := float64(ticket.PriorityWeight())*1e13 + float64(time.Now().UnixMilli())
    return s.redis.ZAdd(ctx, "queue:"+strconv.FormatInt(ticket.GroupID, 10),
        redis.Z{Score: score, Member: strconv.FormatInt(ticket.ID, 10)}).Err()
}

// 坐席释放时（会话结束/工单关闭）触发排空
func (s *QueueService) dispatch(ctx context.Context, groupID int64) error {
    for {
        // ZPOPMIN 原子取出最高优先级的一条
        res, err := s.redis.ZPopMin(ctx, "queue:"+strconv.FormatInt(groupID, 10), 1).Result()
        if err != nil || len(res) == 0 {
            return nil // 队列空了
        }
        ticketID, _ := strconv.ParseInt(res[0].Member.(string), 10, 64)
        ticket := s.getTicket(ctx, ticketID)
        if err := s.assigner.Assign(ctx, ticket); err != nil {
            // 还是没坐席，重新入队（score 保持原值，不会插队）
            s.redis.ZAdd(ctx, "queue:"+strconv.FormatInt(groupID, 10),
                redis.Z{Score: res[0].Score, Member: res[0].Member})
            return nil
        }
    }
}
```

**排队的几个产品细节**：
- **超时兜底**：排队超过 N 分钟（如 3 分钟）还没排上，要给用户提示「当前咨询人数较多，预计等待 X 分钟」，或者提示留手机号等待回拨——**主动告知比让用户干等体验好得多**；
- **放弃排队**：用户等不了可以取消排队；
- **跨技能组支援**：A 组排队很长而 B 组空闲时，可以让 B 组的人支援（但 B 组的人要先能看到 A 组的知识库）。这是高级功能，主动提出来是加分项。

### 7.4.4 排队与超时转人工

**机器人接待 → 转人工**的完整流程：

```
用户进线
  ▼
机器人接待（RAG 检索知识库）
  ├─ 高置信度命中 → 直接回答
  │     └─ 用户满意 → 会话结束，标记「机器人解决」
  │     └─ 用户不满意 / 点了「转人工」→ 转人工流程
  ├─ 低置信度 → 直接提示「我帮您转接人工客服，请稍等」
  └─ 识别到负面情绪 / 投诉关键词 → 立即转人工（不再尝试机器人应答）
  ▼
转人工流程：
  1. 生成转人工事件，带上完整上下文（用户问题、机器人尝试过的回答、用户身份、订单信息）
  2. 按技能组 + 优先级进入排队池
  3. 分配坐席
     ├─ 成功 → 推送给坐席（含上下文摘要），通知用户「XXX 为您服务」
     └─ 失败 → 排队等待，每 30s 重试，超过 3 分钟提示用户
  4. 坐席接入后，机器人退出，但会话历史全部保留给坐席
  ▼
坐席服务 → 解决 → 会话结束 → 满意度评价
         → 解决不了 → 一键转工单（携带完整会话记录）
```

**「带上下文转人工」是关键体验点**：用户在转人工之前已经和机器人说了 5 句话，如果坐席接进来后问「请问您遇到什么问题」，用户会崩溃。所以转人工时必须把**上下文摘要**推给坐席——这正是 LLM 擅长的（可以用模型生成一段 50 字的摘要：用户咨询的是「XXX 订单未收到货」，已尝试的回答是「物流查询指引」，用户表示已经查过但没有结果）。

**超时转人工的几种触发条件**：
| 触发条件 | 实现 | 说明 |
| --- | --- | --- |
| 用户主动点「转人工」 | 前端按钮事件 | 最常见 |
| 机器人连续 N 轮未解决 | 计数 | 如连续 3 轮回答都是「抱歉我没理解」 |
| 识别到负面情绪 | 关键词 + 情绪模型 | 「投诉」「曝光」「消协」这类词直接转 |
| 会话超时无响应 | 定时任务 | 用户长时间不说话，先问「还在吗」，再无响应则结束 |
| 机器人置信度低 | 检索分数阈值 | 检索 Top-1 的相似度低于阈值 |

### 7.4.5 会话与工单的关联

**为什么要关联**：客服场景里，一次会话可能解决一个小问题（不用建工单），也可能需要跨部门协作（必须建工单）。两者是「即时沟通」和「流程协作」的关系。

**关联设计**：
```sql
-- 会话表
CREATE TABLE `cs_conversation` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `tenant_id`     BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `conv_no`       VARCHAR(32) NOT NULL COMMENT '会话号',
  `customer_id`   BIGINT UNSIGNED NOT NULL,
  `agent_id`      BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '当前坐席，0 表示机器人接待中',
  `bot_id`        BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `group_id`      BIGINT UNSIGNED NOT NULL DEFAULT 0,
  `ticket_id`     BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '关联工单（双向关联）',
  `status`        VARCHAR(32) NOT NULL DEFAULT 'active'
                  COMMENT 'active/queuing/transferred/closed',
  `queue_enter_at` DATETIME DEFAULT NULL COMMENT '进入排队的时间，算等待时长',
  `first_reply_at` DATETIME DEFAULT NULL,

  KEY `idx_agent_active` (`tenant_id`, `agent_id`, `status`, `update_time`),
  KEY `idx_customer` (`tenant_id`, `customer_id`, `start_time`),
  KEY `idx_ticket` (`ticket_id`)
) COMMENT='客服会话表';

-- 会话消息表（按 conversation_id 分表 or 按天分表）
CREATE TABLE `cs_message` (

  `conversation_id` BIGINT UNSIGNED NOT NULL,

  `client_msg_id`   VARCHAR(64) NOT NULL DEFAULT '' COMMENT '客户端生成的消息ID，用于幂等',

  `content_type`    TINYINT NOT NULL DEFAULT 1 COMMENT '1文本 2图片 3文件 4语音 5视频 6卡片',

  UNIQUE KEY `uk_conv_client` (`conversation_id`, `client_msg_id`) COMMENT '幂等键',
  UNIQUE KEY `uk_conv_seq` (`conversation_id`, `seq`) COMMENT '保证序号唯一，防并发乱序',
  KEY `idx_conv_time` (`conversation_id`, `create_time`)
) COMMENT='会话消息表';
```

**双向关联的价值**：
- 会话 → 工单：坐席一键把会话转成工单，**完整聊天记录作为工单内容**，客户不用重新描述问题；
- 工单 → 会话：工单处理中需要和客户确认细节，一键发起会话，**坐席能看到完整工单上下文**；
- **质检和追溯**：出了问题能查到「客户说了什么 → 坐席怎么答的 → 工单怎么处理的」，形成完整证据链。

### 7.4.6 知识库与智能应答（结合 RAG 经验）

> **这是求职者的强项，要重点讲**。数字人项目的分层记忆系统 + AI 漏洞研判的 RAG 检索链路，都可以直接映射到智能客服。

#### （1）知识库设计

| 知识类型 | 存储 | 检索方式 |
| --- | --- | --- |
| **FAQ 问答对** | MySQL | 关键词 + 向量混合检索 |
| **产品文档 / 操作手册** | 对象存储 + 切片入向量库 | 向量检索（语义匹配） |
| **历史工单的解决方案** | MySQL（工单表） | 向量检索（相似工单）+ 结构化过滤（产品线、版本） |
| **结构化业务数据**（订单状态、物流） | 业务库 | 工具调用（Function Calling），不是检索 |
| **话术模板 / 规范** | MySQL | 按场景标签 |

#### （2）RAG 智能应答的完整链路

```
用户提问：「我的订单为什么还没发货」
   ▼
1. 查询理解（Query Understanding）
   ├─ 意图分类：物流咨询 / 退款 / 产品使用 ……
   ├─ 实体抽取：订单号、商品名、时间
   └─ 改写：把「这个怎么弄」结合上下文改成完整问题
   ▼
2. 检索（Retrieval）
   ├─ 向量检索：embedding 相似度 Top-K（语义匹配，「发货慢」能匹配到「配送时效」）
   ├─ 关键词检索：BM25/ES（精确匹配，订单号这种必须精确）
   └─ 混合排序（RRF 或加权）：两路结果融合，取 Top-N
   ▼
3. 重排（Rerank）
   └─ 用 Cross-Encoder 模型对 Top-N 精排，取 Top-3（精度提升明显，成本可控）
   ▼
4. 生成（Generation）
   └─ Prompt = 系统指令 + 检索到的知识 + 用户问题 + 对话历史
   └─ 要求：只基于提供的知识回答，知识里没有就说不知道
   ▼
5. 后处理与兜底
   ├─ 置信度评估：检索分数低 / 生成内容与知识不相关 → 不直接回答，转人工
   ├─ 引用溯源：回答里带上「依据：XX 文档第 3 节」，用户和坐席能核实
   └─ 敏感校验：涉及退款金额、承诺时效的内容要审核（合规）
   ▼
6. 效果闭环
   └─ 坐席对 AI 回答的采纳/修改/否定全部回流，作为评估集和优化语料
```

#### （3）RAG 在客服场景的四个关键设计（面试重点）

1. **混合检索不是可选项而是必须项**：纯向量检索在「订单号 `SO20260917001`」这种精确查询上表现很差（embedding 会把不同的订单号编码到很近的位置），必须搭配关键词检索。**这个细节能证明你真的用过 RAG，而不只是看过文章。**

2. **必须可溯源**：客服场景涉及承诺（「3 天内发货」），如果 AI 编造了一个时效承诺，就是法律风险。所以回答必须附上知识来源，并且**只允许基于检索到的内容回答**。这也是求职者在 AI 漏洞研判项目里做 RAG 时的同一个要求——研判结论必须能追溯到历史漏洞案例和专家经验。

3. **置信度兜底**：低置信度不硬答，直接转人工。**「宁可转人工也不要答错」是客服场景的铁律**——答错的成本（客户投诉、错误承诺）远高于转人工的成本。

4. **效果闭环**：这是最容易被忽略但价值最高的。要记录「AI 回答了什么问题、用户是否满意、坐席是否采纳」，形成评估集。没有闭环的 RAG 系统无法迭代——**你永远不知道改 Prompt 之后是变好了还是变差了**。这可以直接引用求职者在数字人项目里做「Prompt 调优」的经验。

**（4）AI 客服的落地节奏建议**（体现工程判断力）：

> 「我建议 AI 客服分三步走：**第一步先做「辅助」而不是「替代」**——AI 给坐席推荐回答，坐席确认后发送。这样风险可控，而且能收集到「AI 建议 vs 坐席实际发送」的对比数据，这是最有价值的训练数据。**第二步做「机器人独立接待简单问题」**——只开放高置信度的 FAQ 场景（如「营业时间」「退换货政策」），其余全部转人工。**第三步才是全场景智能应答**。一上来就让 AI 直面客户，问题答错了直接影响客户体验和品牌，而且你连回滚的手段都没有——因为客户已经看到了。」

### 7.4.7 客服系统高频面试 Q&A

**Q1：工单的生命周期是怎么设计的？**

> 核心状态有六个：待受理、处理中、待确认、已关闭、已取消，加上重开这个动作。
> 有几个设计点我想强调。**第一是「待确认」这个状态**——坐席点了「已解决」之后不是直接关闭，而是进入待确认，等用户确认。这个状态的价值是防止坐席为了 KPI 草率关单。用户 N 天不确认（一般 3-7 天）才自动关闭，这是体验和效率的平衡。
> **第二是重开的设计**，它不是简单把状态改回去：要保留原处理人和完整的沟通历史，但 **SLA 必须重新计算**——用新的截止时间，不能沿用旧的，否则一重开就处于超时状态，坐席会直接放弃。同时要记录重开次数，因为重开率高说明坐席解决问题不彻底，这是质检指标。
> **第三是 SLA 的工作日历问题**，这个坑很真实：客户周六晚上提的工单，客服周一才上班，如果按自然时间算 SLA，一开始就超时了。所以 SLA 的截止时间必须按工作日历累加——跳过非工作时间和节假日。实现上要写一个日历计算器，把「在工作时间内累加 N 分钟」这个逻辑封装好。
> **第四是状态流转用 CAS**：`UPDATE ... WHERE id = ? AND status = ?`，因为工单会被多方同时操作（坐席、客户、系统定时任务），必须防止并发下的状态错乱。

**Q2：坐席分配怎么做？怎么防止并发问题？**

> 策略上主推**技能组路由 + 组内最少活跃会话数**。技能组解决「专业问题给专业的人」——退款问题只有退款组能处理，这个对解决率的影响最大。组内用最少活跃数是为了负载均衡。
> 但有个细节我想特别说一下：**比较负载的时候不能比绝对值，要比饱和度**。因为坐席的 `maxSessions` 配置可能不同——一个上限是 5 现在接待 4 个的人已经 80% 饱和了，另一个上限 20 现在接待 10 个的人只有 50%，这时候应该分给后者。直接比绝对会话数会做出错误的决策。
> **并发超卖是个真实的坑**：两个分配请求同时选到同一个坐席，都读到「当前 4 个，上限 5」，然后都分配，结果变成 6 个超载了。解决办法是用 **Redis Lua 脚本把「检查负载 + 占用名额」做成原子操作**，检查不过就换下一个候选。
> 分配失败（没有可用坐席）就进排队池。排队池我用 Redis ZSet，score 设计成 `优先级权重 × 10^13 + 入队时间戳`，这样一个 ZSet 同时实现了「优先级优先 + 同优先级 FIFO」两个排序条件，`ZPOPMIN` 一条命令原子取出最该处理的。
> 排队还要有**兜底体验**：等待超过 3 分钟要主动提示用户「当前咨询量大，预计还要等 X 分钟」，或者提供「留手机号等回拨」的选项。让用户干等是最差的体验。

**Q3：IM 消息怎么保证不丢不重？**

> 三个机制配合。
> **不丢**靠三段：客户端发消息时，服务端**落库成功后**才回 ACK，客户端超时没收到 ACK 就重发；服务端投递后，客户端要回 ACK，没收到就重推；接收方不在线时存离线消息，上线后按「本地最大 seq」增量拉取。
> **不重**靠幂等：客户端生成一个 `client_msg_id`，服务端用 `(conversation_id, client_msg_id)` 做唯一索引，重复插入直接捕获冲突当成功处理。这和我在 POS 数据贯通项目里的做法完全一致——**Redis 快速去重挡大部分，数据库唯一索引做最终兜底**，因为可靠性不能建立在缓存之上。
> **不乱**靠会话内的 seq 序号：Redis `INCR` 保证原子且连续，客户端按 seq 排序，**发现 seq 不连续就主动拉取缺失的消息**。这是最实用的机制，因为它同时解决了乱序和丢消息两个问题。
> 还有一个细节是**会话列表的更新要用 CAS**：`UPDATE conversation SET last_msg_seq = ? WHERE id = ? AND last_msg_seq < ?`。因为并发下消息可能乱序处理完，如果不用 CAS，一条旧消息可能会把 `last_msg_seq` 覆盖成一个更小的值，导致会话列表显示错误。
> 这些机制我在数字人项目对接腾讯 IM 的时候都实践过，包括幂等、消息顺序和跨实例的消息路由。

**Q4：一个用户的消息怎么路由到他所在的长连接服务器？**

> 关键是要维护「用户在哪个节点」的映射。连接建立时，网关把 `uid → 本节点` 写入 Redis（`route:uid:{uid} = node_id`）；连接断开时删除这个 key（用租约或心跳续期防止残留）。
> 消息投递时，消息服务先查 Redis 拿到接收方所在的节点：如果就在本节点，直接找到连接写入；如果在其他节点，通过 gRPC 转发过去。转发时目标节点也要校验连接是否还在（可能刚好断线了），不在就转存离线消息。
> 有几个细节：**一个 uid 可能多端在线**（手机 + 电脑），所以路由表应该是 `uid → []node` 或者用 Hash 存每个端的连接；**路由表要有 TTL 或心跳续期**，否则节点崩溃后路由信息残留，消息会一直往一个死节点发；**跨节点转发的失败要能降级**——转发失败就当离线消息处理，让客户端重连后拉取。
> 集群规模大了之后可以考虑**一致性哈希**：按 uid 哈希决定用户连到哪个网关节点，这样消息路由不用查表，直接算出来。代价是节点扩缩容时会有大量用户重连。所以小规模用 Redis 路由表更灵活，规模大了再考虑哈希。

**Q5：智能客服（AI 客服）你会怎么设计？**

> 我的思路是「**先做辅助，再做替代**」。第一版不做让 AI 直接面对客户，而是给坐席推荐回答——AI 检索知识库生成候选答案，坐席确认或修改后发送。这样做风险可控，而且能收集到「AI 建议 vs 坐席实际发送」的对比数据，这是最有价值的优化素材。
> 技术上链路的五个环节：**查询理解**（意图分类、实体抽取、多轮改写）→ **检索**（向量 + 关键词混合）→ **重排**（Cross-Encoder 精排）→ **生成**（基于检索内容生成，不允许自由发挥）→ **兜底**（置信度低就转人工）。
> 有三个设计我认为是客服场景特有的、不能省的：
> **一是混合检索**。纯向量检索在订单号这类精确查询上表现很差，因为 embedding 会把不同的订单号编码到很接近的位置。必须配关键词检索。
> **二是可溯源**。客服回答涉及承诺（「3 天内发货」「可以退款」），AI 编一个就是法律风险。所以回答必须带上知识来源，而且 Prompt 上要强约束「只基于提供的资料回答」。我在 AI 漏洞研判项目里做 RAG 时也是同样的要求——研判结论必须能追溯到历史案例。
> **三是效果闭环**。要记录 AI 回答了什么问题、坐席是否采纳、用户是否满意，形成评估集。没有闭环的 RAG 系统没法迭代，你改完 Prompt 都不知道是变好还是变差。
> 最后是落地节奏：先 FAQ 这类高置信度场景开放机器人独立接待，其余全部转人工，跑稳了再逐步放开。**一上来就全场景 AI 接待，答错了你连回滚都做不到——客户已经看到了。**

## 7.5 OA / 客服场景设计题与参考架构

### 7.5.1 设计题：企业 OA 审批系统

> **答题框架复用模块 06 的 6.5.0 节：需求澄清 → 容量估算 → 架构图 → 数据模型 → 关键流程 → 扩展高可用。**

#### 第 1 步：需求澄清（话术）

> 「我先确认几个问题。**功能上**，是一个通用审批平台（各业务线自己配流程），还是固定几个审批场景？需要支持哪些节点类型——审批、抄送、条件分支、并行、会签？流程是管理员配还是业务人员也能配？**规模上**，多少员工、多少租户、日审批量大概多少？**集成上**，要不要对接企业微信/飞书做登录和消息通知？要不要和 HR 系统同步组织架构？
> 我今天重点讲**流程引擎的设计**，因为它是最核心也最难的部分，可以吗？」

假设答案：通用审批平台，5000 员工，单租户，日审批 1 万条，对接企微做登录和通知，组织架构从 HR 系统同步。

#### 第 2 步：容量估算

```
日审批 1 万条 → 平均 0.12 QPS，峰值（工作时间集中，按 20 倍）≈ 2.5 QPS
任务数：每条流程平均 4 个节点 × 2 个审批人 = 8 条任务 → 日 8 万条任务
审批记录：每条流程平均 10 条 → 日 10 万条 → 年 3650 万条 → 需要按月分表

待办查询 QPS：5000 人，每人每小时刷新 10 次 → 1.4 万次/小时 ≈ 4 QPS（峰值 20）
组织架构：5000 用户 + 200 部门，全量缓存在内存（几 MB）

结论：这是个**低并发、高复杂度**的系统。瓶颈不在 QPS，而在
  1. 流程定义的复杂度（节点组合、条件分支的正确性）
  2. 组织架构的实时性（人员变动、委托、离职）
  3. 待办列表的查询性能（多表关联 + 数据权限）
```

**这个结论非常重要**：OA 系统不是高并发系统，**面试时主动说出「这是低并发高复杂度系统，难点在模型设计和正确性而非性能」**，会显得你很有判断力——很多候选人会盲目地给 OA 系统上分库分表、缓存集群，反而暴露了对业务的误解。

#### 第 4 步：数据模型

见 7.1.11 的完整 DDL（流程定义表、实例表、任务表、审批记录表、抄送表、委托表）+ 7.2 的表单定义表 + 7.3 的组织权限表。

#### 第 5 步：关键流程

**流程发起**：
```
1. 用户填写表单，前端按表单定义渲染 + 校验
2. 后端二次校验（必填、类型、范围、业务规则）
3. 解析流程定义（取已发布的最新版本）
4. 创建实例：固化 def_id + form_version + form_data 快照
5. 引擎推进到第一个用户任务节点
6. 解析审批人（走委托规则）→ 生成任务
7. 事务提交后发事件：通知审批人 + 安排超时
8. 返回实例 ID
```

**审批处理**：
```
1. 校验：任务是否存在、是否属于当前用户、状态是否 pending
2. CAS 更新任务状态（WHERE status='pending'）
3. 记录审批意见（审批记录表）
4. 会签判定（如果是会签节点）
5. 节点通过 → 引擎推进；节点拒绝 → 按驳回策略处理
6. 发事件：通知下一节点审批人 / 通知发起人
```

**组织架构同步**（容易被忽略但很重要）：
```
HR 系统 → 定时全量同步 + 增量变更事件 → 组织服务更新用户/部门
   ├─ 人员离职：检测该人名下是否有待办任务 → 自动转交给其主管 + 告警
   ├─ 部门调整：受影响的是数据权限（部门树变了）→ 清权限缓存
   └─ 汇报关系变更：影响后续节点的审批人解析（已生成的任务不受影响）
```

#### 第 6 步：扩展与高可用

| 挑战 | 方案 |
| --- | --- |
| **审批记录表膨胀**（年 3650 万条） | 按月分表；超过 1 年的归档到冷库，详情页从冷库查 |
| **待办列表慢** | `idx(tenant_id, assignee_id, status, create_time)` 覆盖索引；待办数量用 Redis 计数器 |
| **流程定义解析频繁** | 定义加载后缓存在本地内存（进程内），定义发布时通过 MQ 广播失效——**定义是读多写少，非常适合本地缓存** |
| **组织架构查询频繁** | 用户/部门/角色全部缓存在 Redis + 本地内存，变更时 MQ 广播失效 |
| **定时任务重复执行** | 多实例部署时定时任务要加分布式锁（Redis 或 ETCD 选主），否则超时提醒会发 N 遍 |
| **引擎执行失败** | 关键操作都在数据库事务里；跨服务的动作（通知）走 MQ + 重试，失败不影响主流程 |
| **流程定义错误导致死循环** | 保存定义时做**静态校验**（必须有开始和结束节点、必须有出边、环检测、条件表达式语法校验）；运行时限制最大推进步数 |
| **数据权限越权** | DAO 层统一注入；详情接口也要校验；写单元测试专门覆盖越权场景 |

#### 亮点加分项（主动说出来）

1. **流程定义的可视化校验**：保存时静态检查（孤立节点、无出口节点、条件不完整、环），把错误挡在配置阶段而不是运行阶段——**这是流程引擎产品化程度的重要标志**。
2. **审批人解析的兜底链路**：`直属主管 → 上级主管 → 部门负责人 → 指定兜底人 → 抄送管理员并跳过`，**每一层都有兜底**，保证流程不会因为组织数据缺失而卡死。
3. **流程的「模拟运行」**：发布前可以用测试数据试跑一遍，看路径是否符合预期。这个功能对复杂流程（多层条件分支）价值极大。
4. **审批效率分析**：统计每个节点的平均耗时、哪个审批人是瓶颈、哪些流程经常被驳回，反哺流程优化。**这是从「做功能」上升到「做业务价值」的表达。**

### 7.5.2 设计题：企业客服工单系统

**完整设计见模块 06 的 6.5.1 节**，这里补充客服特有的部分：

#### 与 OA 审批系统的异同（面试可以主动对比，展示抽象能力）

| 维度 | OA 审批系统 | 客服工单系统 |
| --- | --- | --- |
| **流程确定性** | 流程在发起时**完全确定**（按定义走） | 流程**动态**（坐席可以自己决定转给谁、要不要升级） |
| **驱动方式** | 流程引擎驱动（按定义推进） | 状态机驱动（人工决定下一步） |
| **参与人** | 固定的审批人（按规则解析） | 技能组 + 抢单 + 分配 |
| **时间要求** | SLA 大致要求 | SLA **严格**（首次响应、解决时长都有硬指标） |
| **渠道** | 单一（系统内） | 多渠道（Web/App/IM/电话/邮件） |
| **会话** | 无 | **有 IM 实时会话**，这是最大的差异 |
| **数据量** | 小（日万级） | 大（日消息可能百万级） |

**面试话术**：「这两个系统我都会用状态机 + 流转记录的模式来做，但它们有个本质区别：**OA 审批的流程在发起时就由流程定义确定了，引擎是「照着图走」；客服工单的流程是动态的，坐席可以自己决定转给谁、要不要升级，系统更多是提供规则和约束而不是强制执行路径。** 所以工单不需要流程引擎，一个设计良好的状态机就够了——**用流程引擎去做工单是过度设计**，这是我在评估技术方案时会特别警惕的。」

### 7.5.3 设计题：多租户 SaaS 版 OA

**需求澄清**：卖給多个企业，租户数量可能几百到几千，每个租户的员工数从几十到几万不等。

**关键决策：租户隔离方案**
```
租户分层：
  ├─ 大客户（>5000 员工，如 20 家）→ 独立数据库（物理隔离，满足合规，性能可控）
  ├─ 中型客户（500-5000 员工，如 200 家）→ 共享库 + 独立 Schema
  └─ 小客户（<500 员工，如 2000 家）→ 共享表 + tenant_id（成本最低）

路由层：根据请求的域名/子域名 → 查租户配置 → 决定连哪个库/Schema
```
**「分层混合」这个答案是加分项**——它承认了「没有一种方案适合所有租户」，而这正是真实 SaaS 的做法（Salesforce、钉钉都是这么做的）。

**多租户特有的技术点**：
1. **元数据隔离**：流程定义、表单定义、权限配置都要带 `tenant_id`，且租户之间不能互相引用；
2. **连接池管理**：独立库的方案下，几百个租户就是几百个连接池，必须有**懒加载 + 空闲回收**（租户久不访问就释放连接池），否则数据库连接数会爆；
3. **数据迁移**：租户从小客户升级成大客户时要能**在线迁移**（双写 + 校验 + 切流），这是 SaaS 的关键能力；
4. **定制化**：不同租户可能要改字段、改流程。方案是**配置驱动**（用流程定义和表单定义的配置能力覆盖 90% 需求）+ **插件扩展点**（少数特殊需求走扩展点，代码隔离）；**绝不能给租户改代码**——那样就没法统一升级了；
5. **版本升级**：多租户的升级要灰度（先升级内部租户 → 再升几个愿意尝鲜的 → 再全量），且独立库的租户要能分批升级；
6. **资源隔离**：一个租户的大量请求不能拖垮其他租户（**吵闹邻居问题**），需要在网关上做**按租户的限流**。

### 7.5.4 OA/客服设计题的通用答题模板

```
【万能结构】
1. 需求澄清（2-3 分钟）
   - 功能范围、规模量级、集成需求、明确今天的重点
2. 关键判断（30 秒，非常重要）

```

## 7.6 话术指导：如何回答「你没有 OA 经验」

> **这一节是本章最重要的部分，请务必背熟并内化成自己的话。**

### 7.6.1 心态建设

首先明确三点：

1. **不要慌，也不要编**。面试官问「你有没有 OA 经验」时，他心里清楚大多数候选人没有——否则不会写「有 OA 系统开发经验者**优先**」而不是「必须」。这是个**加分项**，不是**门槛项**。
2. **编造一定露馅**。OA 的细节特别多（会签策略、驳回语义、委托与转办的区别），随便挑一个追问三层就编不下去了，而且一旦被发现说谎，整场面试的可信度归零。
3. **正确的策略是「承认 + 映射 + 展示学习能力」**。承认没做过 OA，但证明**你做过同类复杂度的事情**，并且**已经理解了 OA 的核心模型**（这一章的内容就是你的弹药）。

### 7.6.2 标准回答话术（三段式）

**第一段：坦诚承认，但马上给出「能力等价物」**

> 「我先坦诚说，我没有做过传统意义上的 OA 系统——没有交付过一个完整的审批流引擎产品。**但我想说明一下，OA 里最核心的几块能力，我在别的项目里都实践过，我可以具体讲讲。**」

**第二段：逐条映射（这是核心，要讲得具体）**

> 「**第一块是人工审批节点，这个我在 AI 漏洞研判系统里做过。**那个系统是多 Agent 工作流跑漏洞研判，跑到「定级定价」这一步必须由安全专家介入，我们把研判结果通过飞书审批卡片推给专家，专家确认或驳回之后工作流才继续。
> 这其实就是审批流引擎里**最难的那个部分——「人工任务节点 + 外部事件唤醒」**：工作流要挂起并保存上下文快照；用户可能重复点击或者几小时后才点，所以要靠落库 + 状态机 CAS 保证幂等；长时间没人处理要有超时提醒和兜底；每一步都要留痕因为 SRC 运营有合规要求。**这四个问题正好就是流程引擎里人工节点要解决的全部问题**，我缺的只是「节点类型更多、配置项更细」这部分业务知识的积累，机制设计我是有实践经验的。
>
> **第二块是权限体系，我在商云前台做过权限控制模块。**用户关联角色、角色关联权限点、前端按权限点控制菜单按钮、后端接口层统一拦截。当时踩过一个印象很深的坑：一开始只在前端做了权限控制，结果测试时用 Postman 绕过前端调接口，普通收银员能调管理员的功能。**这件事让我形成了一个很强的认知——权限的最终校验必须在服务端，前端控制只是体验优化。**所以我特别能理解为什么 OA 的数据权限要在 DAO 层统一注入。「本部门及下级」那种子树查询我也做过类似的，用的是路径枚举。
>
> **第三块是 IM 会话，这个是我最近在数字人项目里的主要工作。**我负责对接腾讯 IM，做了消息幂等、离线消息、跨实例的消息路由和通话控制。客服系统里的在线会话、坐席分配、消息可靠性，用的就是这套东西。
>
> **第四块是微服务架构，POS 数据贯通项目里用的是 go-zero + ETCD + gRPC + RabbitMQ**，服务拆分、注册发现、消息可靠性这些都踩过坑。OA 和客服系统的技术底座和这个是一样的。」

**第三段：表达学习路径，展示主动性（关键收尾）**

> 「至于 OA 的业务知识，我在准备这个岗位的时候专门研究过审批流引擎的设计——流程定义怎么用有向图建模、实例和任务怎么分、会签的四种策略（全票、或签、一票否决、按比例）、驳回是驳回到上一步还是任意节点、这两个方案在跨并行分支时的语义差异、流程定义的版本管理要怎么做才能不影响运行中的实例。**这些我理解得比较透了，只是还缺真实的业务场景来验证。**
>
> 我的判断是，**流程引擎的难点不在代码量，而在模型设计的正确性和对业务语义的理解**。我过去做 POS 数据贯通时，面对五六条产品线各不相同的字段格式，我抽象了一套统一的 Protobuf 模型 + 适配器模式，让接入新产品线时核心链路零改动——**这种「把变化抽出来做成配置」的思路，和流程引擎把流程抽出来做成定义，本质上是同一个问题**。所以我有信心能比较快地上手。」

### 7.6.3 常见追问与应对

**追问 1：「那你觉得流程引擎最难的地方是什么？」**（考察你是不是真的想过）

> 「我认为是**边界情况的语义定义**，而不是技术实现。举几个例子：
> 会签节点中途有人加签，按比例通过的阈值是按加签前的人数算还是加签后的？如果按加签后算，可能出现「已经达标了，加完人又变成不达标」的荒谬情况。
> 驳回如果支持「驳回到任意节点」，在跨并行网关时语义就不清晰了——一个并行分支的任务被驳回了，另一个分支要不要取消？如果取消，那个分支上已经审批过的人的工作算白做了吗？
> 流程定义改版后，正在跑的实例怎么办？我们固化版本是对的，但用户会问「为什么我的流程还是老的」。这时候要不要支持「迁移到新版本」？迁移的技术实现很简单（改个 def_id），但新版本的节点结构可能完全不同，实例的 current_node 在新版本里可能根本不存在。
> **这些问题的共同点是：技术上都能做，但业务语义上说不清，而说不清的东西上线后一定会出问题。**所以我做的判断是宁可功能少一点，也要保证每个功能的语义是清晰的。」

**追问 2：「如果让你一周内上线一个简单的审批功能（比如请假审批），你怎么做？」**（考察务实程度）

> 「我会**先不上流程引擎**。一周的时间做不出一个可靠的通用引擎，硬做出来也是个玩具。
> 我的方案是**用一个简单的状态机 + 配置表**：请假单表上加 `current_step` 字段，一张审批步骤配置表定义「第几步、谁审批、审批不过怎么办」，审批时按步骤推进。这样支持三级审批、支持配置调整，代码量很小，一周肯定能上线。
> 同时我会**留好演进路径**：把审批步骤的配置做成 JSON（而不是硬编码的表结构），把「找审批人」抽成一个独立的函数（将来换成规则解析器）。这样等业务复杂到状态机撑不住的时候，可以平滑迁移到流程引擎，而不是推翻重来。
> **这里我的判断是：不要为了「技术完备性」而上重型方案。**流程引擎的复杂度很高，维护成本也高，如果只有两三个固定流程，用状态机是完全正确的选择。」

**追问 3：「你之前没接触过 OA，怎么快速上手我们的系统？」**

> 「我会分三步。
> **第一周看代码和文档**，重点搞清三件事：流程定义的数据结构（是 BPMN 还是自定义的图模型）、实例和任务的状态机（有哪些状态、怎么流转）、组织权限的模型（RBAC 怎么设计的、数据权限怎么注入的）。这三块是 OA 的骨架，搞清楚了其他都是细节。
> **第二周从修 bug 和小需求入手**。因为 OA 系统的 bug 往往出现在边界情况上（某个节点审批人解析不到、驳回后状态不对），修 bug 是理解系统最好的方式，比看文档有效得多。而且这类 bug 的修复能快速建立我在团队里的可信度。
> **第三周开始接完整的需求**。我会主动挑一个涉及流程配置的需求，因为它会逼我把定义、实例、任务、权限这几块串起来理解。
> 另外我有一个习惯是**边看边写文档**——把我理解的流程引擎执行逻辑、状态流转图画下来，一来验证我理解得对不对（给同事 review），二来对团队也是贡献。我在上个项目里也这么干过。」

## 7.7 精选 12+ 道业务高频面试题与参考回答

**Q1：审批流引擎怎么设计？核心表和核心流程是什么？**

> 四层结构：**流程定义**（有向图，JSON 存 nodes 和 edges，按 `process_key + version` 多版本管理）、**流程实例**（一次运行，启动时固化 `def_id` 锁版本）、**任务**（实例到达审批节点时为每个审批人生成的待办）、**引擎执行器**（`MoveNext`：找出边 → 按节点类型和条件选边 → 进入目标节点 → 审批节点生成任务 / 网关继续递归 / 结束节点终结实例）。
> 核心表五张：流程定义表、实例表、任务表、审批记录表（留痕，append-only）、抄送表。
> 有三个设计点我认为最关键：
> 一，**实例固化定义版本**。实例存 `def_id` 而不是 `process_key`，引擎执行时从实例的 def_id 加载定义，绝不用「当前最新版本」。这样流程改版不影响运行中的实例。
> 二，**审批人规则在任务生成时解析**，不在定义时。定义里存的是规则（「直属主管」），因为组织架构会变，存具体的人会失效。而且每一级都要有兜底，否则组织数据缺失会让流程卡死。
> 三，**所有状态变更用 CAS**（`WHERE status = ?`），因为审批、驳回、撤回、超时可能是并发的，必须防止状态错乱。

**Q2：会签怎么实现？四种策略的区别是什么？**

> 会签就是同一个节点上有多条任务（同一 `instance_id + node_key + round`）。数据上靠「任务多条 + 节点配置会签策略 + 每次任务完成后调一次节点判定」来实现。
> 四种策略：**全票通过**（`all`，所有人处理完且无拒绝才算通过）、**或签**（`any`，任一人处理即完成，其他任务取消）、**一票否决**（`veto`，任一人拒绝立即失败并取消其他人）、**按比例**（`ratio`，同意数/总数达到阈值）。
> **全票通过和一票否决的区别在于「提前终止」**：全票通过即使第一个人就拒绝了，也要等所有人处理完才判定——好处是每个人都能表达意见，留痕完整；一票否决是拒绝的瞬间就失败并取消其他人——好处是响应快，适合风控。
> 按比例还有个优化：**提前判定失败**。5 人需要 3 票同意，如果已经有 3 人拒绝，剩下 2 人全同意也只有 2 票，达不到阈值，可以立即失败不用等。
> 会签的坑主要在加签：**中途加人会改变总人数**，比例策略下的阈值是固定还是动态？动态算的话可能出现「已经达标了，加完人又不达标」。这个必须在产品上定义清楚。

**Q3：驳回怎么实现？驳回上一步和驳回到任意节点有什么区别？**

> 驳回上一步：取消当前节点的活跃任务，在前驱节点重新生成任务（审批人重新解析，因为人可能变了），更新实例的 `current_node`。
> 驳回到任意节点有两条路线：**回滚式**是取消目标节点之后的所有活跃任务，在目标节点重建，历史记录保留但标 `superseded`（用户要重批已经批过的节点）；**跳回式**是让已通过的节点自动跳过（体验好，但如果前序审批人改了内容，跳过的节点其实是基于旧内容批的，不合理）。
> 我倾向**只实现「驳回上一步」和「驳回到发起人」**。理由是驳回到任意节点在跨并行网关、跨会签时语义不清晰——并行分支里一个节点被驳回了，另一个分支要不要取消？取消的话那批过的人的工作算白做吗？**技术上都能实现，但业务语义说不清的东西上线后一定会出问题。**所以宁可功能少，也要保证每个语义是清晰的。如果一定要支持，就用跳回式 + 「已通过节点是否重审」做成配置项，金额和风险类的流程强制重审。
> 还有一个细节：驳回后重走需要 **`round` 轮次字段**区分同一节点的多次执行，否则「我的待办」会查出历史任务。

**Q4：表单引擎怎么设计？数据怎么存？**

> 表单定义用 JSON 存字段数组，每个字段有 `key`、`label`、`type`、校验规则、显示条件、顺序。字段类型覆盖文本、数字、金额、日期、下拉、选人、选部门、附件、明细表。
> 数据存储我倾向**用 JSON 存在实例表的 `form_data` 字段**，而不是 EAV 竖表。EAV（`form_value(instance_id, field_key, value)`）的问题是查询要大量自连接，字段一多 SQL 就没法看，而且所有值都得存成字符串丢了类型。JSON 存储天然匹配表单的数据结构，配合 MySQL 5.7+ 的虚拟列 + 索引也能支持按字段查询。代价是复杂统计不方便——如果某个字段要频繁参与统计，我会在实例表上给它单独加冗余列和索引，用冗余换性能。
> **金额字段一定用「分」为单位的整数存**，不能用浮点，否则 `0.1 + 0.2 = 0.30000000000000004`。
> 版本兼容是重点：实例存 `form_id + form_version + form_data 快照`，展示时用当时的版本渲染。字段定义的铁律是 **key 不可变、删除用逻辑删除、不要改字段类型、新增校验只对新提交生效**。

**Q5：字段权限怎么做？**

> 字段权限配在**流程节点**上而不是表单上（同一个表单在不同节点权限不同）。三种权限值：`hidden`（不可见且提交时忽略）、`readonly`（可见不可改）、`editable`（可改），外加 `defaultPermission` 兜底。
> **最关键的是后端必须强制校验**。前端按权限渲染，但用户可以绕过前端直接调接口，所以后端处理提交时要按节点权限过滤——只有 `editable` 的字段才允许合并进 `form_data`。
> 我在商云前台踩过这个坑：只在前端做了权限控制，结果测试时用 Postman 绕过前端，普通收银员能调管理员接口。**这让我形成了一个很强的认知：权限的最终校验必须在服务端。**
> 进阶一点，权限还可以是动态的（「金额小于 1 万主管能改，超过 1 万只能看」），那权限值也做成条件表达式，在提交时按当前数据求值。

**Q6：RBAC 和数据权限怎么设计？**

> RBAC 是用户-角色-权限三要素加两张关联表。引入角色的价值是**把「变化的用户」和「相对稳定的权限集合」解耦**。权限粒度分四层：菜单级、操作级、数据级、字段级。权限编码用 `模块:资源:操作` 的字符串，不用自增 ID。
> 数据权限独立于功能权限：**功能权限管「能不能操作」，数据权限管「能看到哪些数据」**。做法是给角色配数据范围（全部/本部门及下级/本部门/本人/自定义），请求进来时解析出「可见部门列表」放进 context，然后在 **DAO 层统一注入 where 条件**。
> 三个关键点：
> 一，**必须在 DAO 层统一做**，不能靠每个业务方法自觉，因为漏一个就是越权漏洞。
> 二，**兜底必须 fail-safe**——遇到不认识的范围值应该返回空数据而不是全部数据，配置错误要往安全的方向失败。
> 三，**详情接口也要校验**。列表做了过滤但详情接口只按 ID 查的话，用户猜到 ID 就能越权——这是最常见的越权漏洞来源。
> 部门树我倾向「`parent_id` 保证结构 + 冗余 `path` 字段加速子树查询」，`path` 存 `/1/12/123/`，查子树就是一条 `LIKE '/1/12/%'`。

**Q7：工单的生命周期怎么设计？**

> 六个状态：待受理、处理中、待确认、已关闭、已取消，加上重开这个动作。
> 三个设计点：**「待确认」状态**是为了防止坐席为了 KPI 草率关单，退回让用户确认，用户 N 天不确认才自动关闭；**重开不是简单改状态**——要保留原处理人和沟通历史，但 SLA 必须重新计算（用新的截止时间，否则一重开就处于超时状态），同时记录重开次数作为质检指标；**SLA 要支持工作日历**——客户周六提的工单，客服周一才上班，按自然时间算一开始就超时了，所以截止时间要按「工作时间累加 N 分钟」计算。
> 状态流转用 CAS（`WHERE status = ?`），因为工单会被坐席、客户、系统定时任务多方同时操作。

**Q8：坐席分配怎么做？**

> 主推**技能组路由 + 组内最少活跃会话数**。技能组解决「专业问题给专业的人」，对解决率影响最大；组内最少活跃做负载均衡。
> 一个关键细节：**比较负载要比饱和度而不是绝对值**。坐席的 `maxSessions` 可能不同——上限 5 现在 4 个（80% 饱和）比上限 20 现在 10 个（50% 饱和）更忙，应该分给后者。
> **并发超卖是真实的坑**：两个分配请求同时选到同一个坐席，都读到「4 个、上限 5」，都分配就变成 6 个超载。解决办法是用 Redis Lua 脚本把「检查 + 占用」做成原子操作，检查不过就换下一个候选。
> 分配失败进排队池，我用 Redis ZSet，score = `优先级权重 × 10^13 + 入队时间戳`，一个 ZSet 同时实现「优先级优先 + 同优先级 FIFO」，`ZPOPMIN` 原子取出。坐席释放时触发排空。
> 排队要有兜底体验：超过 3 分钟主动提示用户预计等待时间，或者提供「留电话等回拨」，让用户干等是最差的体验。

**Q9：IM 消息怎么保证可靠、不重、不乱？**

> **不丢**：客户端发消息，服务端落库成功才回 ACK（客户端超时重发）；服务端投递后客户端要回 ACK（没收到就重推）；接收方不在线就存离线消息，上线后按「本地最大 seq」增量拉取。
> **不重**：客户端生成 `client_msg_id`，服务端用 `(conversation_id, client_msg_id)` 唯一索引，重复插入直接当成功。**Redis 快速去重挡大部分 + 数据库唯一索引做最终兜底**——和我在 POS 项目里的做法完全一致，可靠性不能建立在缓存之上。
> **不乱**：会话内维护单调递增的 `seq`（Redis INCR 保证原子连续），客户端按 seq 排序，**发现 seq 不连续就主动拉取缺失消息**——这一个机制同时解决了乱序和丢消息。
> 还有个细节：更新会话的「最后一条消息」要用 CAS（`WHERE last_msg_seq < ?`），否则并发下一条旧消息可能把 `last_msg_seq` 覆盖成更小的值，导致会话列表显示错误。

**Q10：客服系统的「排队转人工」怎么设计？**

> 触发条件有五种：用户主动点转人工、机器人连续 N 轮未解决、识别到负面情绪或投诉关键词、机器人检索置信度低于阈值、会话超时无响应。
> 转人工的**关键是带上完整上下文**：用户已经和机器人聊了 5 句，坐席接进来还问「请问您遇到什么问题」，用户会崩溃。所以转人工时要生成上下文摘要推给坐席——这正是 LLM 擅长的，可以把「用户问题 + 机器人尝试过的回答 + 用户身份和订单信息」压缩成 50 字的摘要。
> 排队用 Redis ZSet 按优先级和等待时长排序，分配成功就推送坐席、通知用户「XXX 为您服务」。排队超过 N 分钟要主动告知预计等待时间，或者提供留电话等回拨。
> 高级功能是**跨技能组支援**——A 组排队很长而 B 组空闲时让 B 组支援，但 B 组的人要能看到 A 组的知识库。

**Q11：智能客服的 AI 应答怎么做？**

> 我的思路是「**先做辅助再做替代**」。第一版是给坐席推荐回答，坐席确认或修改后发送——风险可控，而且能收集「AI 建议 vs 坐席实际发送」的对比数据，这是最有价值的优化素材。
> 技术链路五步：查询理解（意图分类、实体抽取、多轮改写）→ 混合检索（向量 + 关键词）→ 重排（Cross-Encoder 精排）→ 生成（基于检索内容，不允许自由发挥）→ 兜底（低置信度转人工）。
> 三个客服场景特有的设计：**一是混合检索不能省**——纯向量检索在订单号这种精确查询上表现很差，embedding 会把不同订单号编码到很接近的位置；**二是必须可溯源**——客服回答涉及承诺（「3 天内发货」），AI 编一个就是法律风险，所以回答要带知识来源，Prompt 上强约束「只基于提供的资料回答」，这和我在 AI 漏洞研判项目里的要求是一致的；**三是必须有效果闭环**——记录 AI 回答了什么、坐席是否采纳、用户是否满意，形成评估集，否则改完 Prompt 都不知道是变好还是变差。

**Q12：多租户怎么做？有哪些坑？**

> 三种方案：独立库、共享库独立 Schema、共享表加 `tenant_id`。隔离性和成本是反向的。**真实 SaaS 应该是分层的**：大客户独立库（满足合规、性能可控），中型客户独立 Schema，小客户共享表——因为**没有一种方案适合所有租户**。
> 共享表方案的六个坑：
> 一，所有表的 `tenant_id` 必须在**索引最左列**，否则跨租户查询全表扫描；
> 二，所有查询**自动注入 `tenant_id`**，在 ORM 层做统一插件，不能靠业务代码自觉——漏一个就是跨租户泄露；
> 三，**唯一索引要带 `tenant_id`**，否则 A 租户的 `admin` 会把 B 租户的 `admin` 挡住；
> 四，**缓存 key 要带租户前缀**，这是最隐蔽的泄露途径；
> 五，**兜底要 fail-safe**，租户上下文缺失时拒绝查询而不是查全表；
> 六，**按租户限流**，防吵闹邻居——一个租户的流量高峰不能拖垮其他租户。
> 另外独立库方案下，几百个租户就是几百个连接池，必须做**连接池懒加载 + 空闲回收**，否则数据库连接数会爆。

**Q13：如果你的系统要对接企业微信/飞书，登录和消息通知怎么做？**

> 登录走 **OAuth2 授权码模式 + OIDC**。流程是：前端跳转企微扫码页（带 `appid`、`redirect_uri`、随机 `state`）→ 用户扫码 → 企微回调带 `code` → 后端用 `code + appsecret` 换 token → 拿 `userid` → 匹配本地用户（首次登录可自动建号）→ 签发本地 JWT。安全细节：`state` 必须校验防 CSRF，`code` 只能用一次，`appsecret` 绝不能放前端。
> 注意 **OAuth2 是授权框架不是认证框架**，它解决「能访问什么」不解决「你是谁」；OIDC 在它之上加了 `id_token`（JWT），标准化了身份字段，企业 SSO 应该用 OIDC。
> 本地会话用 JWT，但**只放 `uid` 和 `tenant_id`，不放角色权限**——角色多的时候 token 会很大，而且权限变更后老 token 里的权限是过期的。权限服务端查缓存。
> 消息通知走企微的应用消息接口或飞书的卡片消息。**异步发送**（走 MQ），失败重试 + 死信兜底，因为通知失败不应该影响审批主流程。飞书还支持**交互式卡片**，可以直接在卡片上点同意/拒绝，回调到我们的接口——这就是我在 AI 漏洞研判项目里做的，本质上就是一个「移动端的待办处理入口」。

**Q14：线上有个用户反馈「我的待办里有一条审批，点进去提示无权处理」，你怎么排查？**

> 这是个很好的排查题，我会按链路一步步缩小范围。
> **第一步，确认现象**：让用户提供工单/流程的编号，先查这条任务在数据库里的真实状态——`assignee_id` 是不是这个用户？`status` 是不是 `pending`？
> **第二步，分情况判断**：
> - 如果 `assignee_id` 不是他 → 可能是**委托或转办**导致的：任务生成时检测到原审批人有生效的委托规则，把任务改派给了代理人，但用户还是从旧的通知里点进来的。查 `oa_delegate` 表确认。
> - 如果 `status` 不是 `pending` → 任务已经被处理了（可能是别人代批的，或者超时自动通过的），但用户的待办列表是缓存里的旧数据。这是**缓存一致性问题**：待办列表缓存没在任务状态变更时失效。
> - 如果 `assignee_id` 是对的、`status` 也是 `pending` → 那问题在权限校验逻辑，可能是**数据权限**把他挡住了（比如他调岗了，部门变了，而数据权限是按当前部门过滤的）。
> **第三步，看日志**：查这个请求的 TraceID，看校验是在哪一步返回的「无权处理」，是任务归属校验、还是数据权限校验。
> **第四步，修复与预防**：如果是缓存问题，检查所有任务状态变更的地方是否都做了缓存失效——**这是我们最容易漏的地方，应该把它收敛到一个统一的「任务状态变更」函数里**。如果是数据权限问题，要考虑「历史任务不该受当前组织架构变更影响」——任务的 `assignee_id` 是快照，不应该再叠加数据权限过滤。
> 最后我要加一个动作：**这个问题不是个例，要查一下有多少用户受影响**（比如查一下最近有多少条「无权处理」的错误日志），如果量大就要按线上故障处理而不是个案。

**Q15：你觉得 OA 系统和客服系统，技术上最大的区别是什么？**

> 我认为最大的区别是**流程的确定性**。
> **OA 审批的流程在发起时就由流程定义完全确定了**——引擎是「照着图走」，每一步走到哪、谁来审批都是定义好的。所以它需要的是一个**流程引擎**，核心能力是流程建模、条件路由、会签、驳回。
> **客服工单的流程是动态的**——坐席可以自己决定转给谁、要不要升级、要不要建工单。系统更多是提供规则和约束（技能组、SLA、升级策略），而不是强制执行一条固定路径。所以工单**不需要流程引擎，一个设计良好的状态机就够了**。
> 这个区别带来的技术选型差异是：**用流程引擎去做工单是过度设计**，会引入大量不必要的复杂度；反过来用状态机去做审批也不行，因为审批的流程是配置出来的，写死在代码里的状态机没法支持「业务人员自己配流程」。
> 另一个区别是**规模和实时性**：OA 是低并发高复杂度，难点在模型正确性；客服系统有 IM 长连接，是真正的高并发（几万长连接、消息百万级），难点在连接管理和消息可靠性。所以客服系统的技术挑战更多在网络层和消息层。

**Q16：如果让你从零开始设计这套系统，你会怎么保证质量？**

> 我会从四个方面入手。
> **第一，模型层面先想清楚边界情况**。流程引擎的复杂度都在边界上（会签加签、跨并行分支驳回、组织数据缺失），我会先把这些场景列出来，明确每一个的语义，写成设计文档给产品和技术一起确认。**语义不清的功能上线后一定会出问题**——与其后期打补丁，不如前期想清楚。
> **第二，静态校验前置**。流程定义保存时做静态检查：必须有开始和结束节点、不能有孤立节点、不能有环、条件表达式的语法和字段引用要合法。**把错误挡在配置阶段，而不是运行阶段**——运行阶段发现错误意味着线上有实例卡住了。
> **第三，测试要覆盖并发和边界**。除了正常流程，必须测：并发审批同一任务、审批和撤回并发、组织架构变更后已生成任务的表现、超时和处理的竞态。这些用单元测试 + 集成测试覆盖，关键路径做压测。
> **第四，可观测**。流程引擎最怕的是「实例卡住了没人知道」，所以必须有监控：**长时间停留在同一节点的实例数**、**超时任务数**、**死信队列消息数**、**引擎执行失败率**。这几个指标能提前发现大部分问题。另外全链路 TraceID 要透传，出问题能快速定位。
> 还有个工程习惯：**流转记录表是 append-only 的，任何状态变更都必须留痕**。这样出问题时可以完整还原「谁在什么时候做了什么」，这是 OA 系统排查问题的最大依仗。

**Q17：你怎么理解「全栈」在这个岗位上的价值？**

> 我理解这个岗位强调全栈，**不是要求前后端都写得很深，而是要求能独立把一个功能从需求到上线完整交付**。
> 具体体现在三个场景：**一是需求评审时**，懂前端就知道「这个交互要改三个组件的状态」，能提前识别出成本，而不是等前端说「这个做不了」；**二是接口设计时**，懂前端就知道该一次性返回哪些字段，避免前端为了一个列表页调五个接口；**三是排查线上问题时**，能自己看前端日志、看 Network 面板，判断是前端渲染问题还是接口数据问题，不用等前端同事有空。
> 我在商云前台项目里就是全栈交付的——用 Wails（Go + Vue 3）做桌面收银应用，后端服务、RabbitMQ 消息、权限模块、部分前端界面都是我做。那段经历最大的收获是**建立了端到端的视角**：一个功能从数据存储到用户点击的完整链路我都走过一遍，所以设计接口时会自然地考虑「前端拿到这个数据好不好用」。
> 另外我对前端不是「了解」的水平——简历上写的是 Vue 3 + TypeScript，我在商云前台里是实际写业务页面的，包括状态管理和组件封装。所以如果团队需要，我是能顶上前端工作的。

### 审批流引擎

| 概念 | 一句话记忆 |
| --- | --- |
| 流程定义 | 有向图，`nodes + edges`，按 `process_key + version` 多版本 |
| 流程实例 | 一次运行，**启动时固化 `def_id` 锁版本** |
| 任务 | 节点上的待办，一对多（会签就是多条） |
| 引擎推进 | `MoveNext`：找出边 → 按类型/条件选边 → 进目标节点（网关要递归） |
| 审批人规则 | **任务生成时解析**（不是定义时）；每级都要有兜底 |
| 驳回 | 上一步简单；任意节点有「回滚式」和「跳回式」，跨并行/会签语义不清，慎用 |
| 撤回 | **只能在没有已完成审批时**；用 CAS 防和审批并发 |
| 会签四策略 | 全票(all，等齐)、或签(any，抢)、一票否决(veto，立即)、按比例(ratio，可提前判定失败) |
| 加签 | **前加签**（原任务挂起 waiting，加签完唤醒）、后加签（原任务完成后再加） |
| 转办 vs 委托 | 转办改单条任务；委托是规则表，任务生成时改派，保留 `original_assignee_id` |
| 超时 | 延迟队列或定时扫表；**动作要能被幂等忽略，不能依赖取消延迟消息** |
| 关键细节 | `round` 轮次字段区分同一节点多次执行；状态变更全用 CAS |
| 版本管理 | 定义多版本、实例固化版本；**不建议迁移运行中实例**（current_node 可能不存在） |

| 概念 | 一句话记忆 |

| 表单定义 | 字段数组 JSON（key/label/type/rules/visibleWhen） |

### 组织权限

| 概念 | 一句话记忆 |
| --- | --- |
| RBAC | 用户-角色-权限 + 两张关联表；价值是解耦「变化的人」和「稳定的权限集」 |
| 数据权限 | 5 种范围；**DAO 层统一注入**；兜底 fail-safe；**详情接口也要校验** |
| 部门树 | `parent_id` 保证结构 + 冗余 `path` 加速子树查询（`LIKE '/1/12/%'`） |
| RBAC vs ABAC | RBAC 为主（简单、快、可解释），ABAC 为辅（动态规则，如时间/金额分级） |
| 多租户 | 独立库 / 独立 Schema / `tenant_id` 字段；**分层混合**是最优解 |
| 多租户六坑 | 索引最左列、自动注入、唯一索引带租户、缓存 key 带前缀、fail-safe、按租户限流 |
| SSO | OAuth2 授权码 + PKCE 是主流；**OAuth2 管授权，OIDC 管身份** |
| JWT | Payload 不加密；无法主动失效 → 短过期+refresh / 黑名单 / 版本号 |

### 客服系统

| 概念 | 一句话记忆 |
| --- | --- |
| 工单状态 | 待受理→处理中→**待确认**→已关闭；待确认是防草率关单的机制 |
| 重开 | 保留原坐席和历史，但 **SLA 要重新计算** |
| SLA | 必须支持**工作日历**（跳过非工作时间和节假日） |
| 坐席分配 | 技能组路由 + 组内最少活跃；**比饱和度不比绝对值** |
| 并发超卖 | 用 **Lua 脚本把「检查 + 占用」做成原子操作** |
| 排队池 | Redis ZSet，score = `优先级 × 10^13 + 时间戳`，一个 ZSet 两个排序条件 |
| IM 三保证 | 不丢（落库后 ACK + 离线消息）、不重（client_msg_id 唯一索引）、不乱（seq + 缺号拉取） |
| 消息路由 | Redis 存 `uid → node`，本节点直投、跨节点 gRPC 转发、失败转离线 |
| 会话关联工单 | 转工单时带上完整会话上下文；双向关联便于质检追溯 |
| AI 客服 | 先辅助后替代；混合检索（向量+关键词）、可溯源、置信度兜底、效果闭环 |

### 话术核心（最该背下来的一段）

> 「我没有做过传统 OA，但 OA 里最核心的三块能力我都实践过：
> **人工审批节点**——AI 漏洞研判的飞书审批卡片，做的就是流程挂起、外部事件唤醒、幂等、超时、留痕，这就是审批流里最难的人工节点；

> **IM 会话**——数字人项目对接腾讯 IM，消息幂等、离线消息、跨实例路由都做过，正好对应客服的在线会话。
> 至于 OA 的业务知识，我专门研究过流程引擎的设计（流程定义建模、实例与任务分离、会签四策略、驳回语义、版本管理），理解得比较透了，缺的只是真实业务场景的验证。而流程引擎的难点我认为不在代码量，在于模型设计的正确性和业务语义的清晰度——这和我做 POS 数据贯通时抽象统一模型 + 适配器、把变化做成配置的思路是同一个问题。」
