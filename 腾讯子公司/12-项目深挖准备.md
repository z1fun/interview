# 12 项目深挖准备

> 面试官对项目的追问是无限深的。本模块把 6 个项目逐个拆解：STAR 讲述稿、技术难点、可能被追问的问题和参考回答、与目标岗位的关联话术。
> 讲述原则：**先说结论（我做了什么、达成什么效果），再展开技术细节；每个技术点都要能经得起三层追问（怎么做 → 为什么这么做 → 有什么坑/怎么优化）。**

## 12.1 LoveSpouse 数字人（2026.01-2026.04）—— 与客服系统强相关，重点讲

**技术栈**：Go、Gin、GORM、MySQL、Redis、IM、Gemini Live、WebSocket、Agent Harness

### STAR 讲述稿（2 分钟版）

> 这个项目是面向智能硬件玩具的虚拟角色陪伴系统，支持多角色、多语言聊天、长期记忆、剧情互动、实时语音和付费媒体解锁。我负责数字人后端的对话流程核心模块。
> 具体做了三块：
> 第一，**对话流程编排**——设计意图识别 → 场景路由 → 对话生成 → 付费互动推荐 → 结构化回复的完整链路，负责 Prompt 调优；
> 第二，**分层记忆系统**——把角色记忆拆成近期对话、会话摘要、长期摘要和稳定事实四层，支持跨会话的上下文连贯，解决了"AI 角色记不住用户"的问题；
> 第三，**IM 与实时语音的稳定性**——对接腾讯 IM 消息并做了幂等处理，防止重复消息重复回复；接入 Gemini Live 实时语音，实现金币计费和跨实例通话控制。
> 这个项目让我完整走了一遍"AI 对话系统从 0 到 1"的设计，包括对话状态管理、消息可靠性和计费一致性。

### 三层追问准备（必被问）

**Q：分层记忆系统怎么设计的？为什么分四层？**
> - 单一的长上下文有两个问题：token 成本线性增长、大模型对长上下文的"中部遗忘"导致早期设定失效。
> - 设计：**近期对话**直接拼接进上下文（最近 N 轮）；**会话摘要**是每轮结束后异步增量摘要，跨会话时先加载；**长期摘要**是多个会话的周期聚合（跨会话话题演化）；**稳定事实**是从对话中抽取的固定属性（用户偏好、角色设定），走结构化存储，优先注入。
> - 工程细节：摘要有独立队列异步生成，防止阻塞主对话链路；稳定事实的抽取用少量样本 few-shot 保证抽取格式稳定；Redis 缓存近期对话，MySQL 持久化摘要。
> - 坑：异步摘要与对话轮次的一致性——用消息序号/会话版本号对齐，摘要落库时校验版本，过期丢弃。

**Q：IM 消息幂等怎么做的？**
> - 背景：腾讯 IM 的回调/推送在网络抖动时会重复投递，重复处理会导致角色重复回复甚至重复计费。
> - 方案：消息全局唯一 ID（服务端生成），处理前先查 Redis `SETNX msg:{msgID}` 占位并设置过期时间，占位成功才进入业务处理；业务处理完落库时再以 msgID 做 MySQL 唯一索引兜底（Redis 与 DB 双保险）。失败重试走占位过期后自然重入 + 业务侧状态检查。
> - 追问：为什么 SETNX 过期时间要大于业务处理时间？答：处理中崩溃时占位自动释放可重试，若业务已提交则 DB 唯一索引兜底。最终一致性由 DB 约束保证。

**Q：跨实例通话控制怎么做的？**
> - 背景：语音通话是长连接，部署多实例后，同一用户的通话可能落在不同实例。
> - 方案：Redis 维护"用户 → 通话实例"的路由表（`user:call:route`），通话开始注册（带租约心跳），结束时释放；控制指令（挂断、静音）先查路由表再转发到目标实例（内部 RPC/消息）；实例异常时租约过期，通话自动回收。
> - 追问：路由表是分布式锁的变体吗？答：类似，但强调租约续期和异常回收，避免死锁（实例挂了锁不释放）。

**Q：金币计费怎么做一致性？**
> - 背景：按分钟/按条计费，涉及用户金币扣减与订单记录。
> - 方案：Redis 原子扣减（`DECRBY` + Lua 校验余额充足）做实时校验，MySQL 异步落账（扣减流水）；用唯一订单号保证落账幂等；对账任务定期核对 Redis 快照与 DB 流水，差额告警。
> - 坑：Redis 与 DB 的最终一致窗口——用对账兜底而非强一致，对内部业务足够；讲清楚"为什么不用事务强一致"（高频计费场景性能优先，银行级场景才需要）。

**Q：Gemini Live 实时语音怎么接的？延迟怎么优化？**
> - 通过 Gemini Live 的 WebSocket API 接入，音频流式上传、文本增量返回；
> - 延迟优化：音频分片发送（攒够 ~100ms 一帧）、VAD 检测说话结束提前触发推理、TTS 流式播报（边合成边播）、中断机制（用户打断立即停止当前播报）；
> - 坑：网络抖动导致音频乱序——客户端带序号，服务端重排/丢帧策略。

### 与岗位的关联话术

> "这个项目本质上就是一个**AI 客服/陪伴的会话系统**：消息可靠性、幂等、计费、会话状态管理，和客服系统的 IM 会话、坐席管理是同一类技术问题。如果让我做客服系统，我还能把记忆系统改成用户画像，把意图识别改成智能路由——先 AI 应答，答不了转人工。"

## 12.2 AI 漏洞研判系统（2025.11-2026.02）—— 审批流映射，重点讲

**技术栈**：Python、LangGraph、FastAPI、PostgreSQL、Docker、飞书API、Jira API、RAG

### STAR 讲述稿（2 分钟版）

> 这是面向安全应急响应中心运营的多 Agent 漏洞审核平台，把原本纯人工的漏洞审核流程自动化：报告评估、POC 验证、漏洞定级定价、复测，全程支持人工审批介入。
> 我负责两块：
> 第一，**用 LangGraph 搭建多 Agent 工作流**——拆成信息完整性评估、漏洞定级、定价等节点，每个节点有独立 Prompt，节点间有状态流转，中间插入人工审批节点，审批通过才进入下一步；
> 第二，**RAG 检索链路**——用 FastAPI 建专家经验知识库，PostgreSQL + pgvector 做向量检索，为研判提供历史漏洞和专家经验参考，提升研判准确率。
> 另外对接了飞书审批卡片交互，让专家在飞书上直接审批。

### 三层追问准备

**Q：为什么用多 Agent 而不是一个大 Prompt 全做？**
> - 单 Agent 做全流程的问题：任务多（评估/验证/定价/复测），指令冲突，出错难定位，且无法在中间插入人工审批；
> - 多 Agent 按职责拆分后：每个节点 Prompt 短、职责单一、可独立调优；流程显式化成状态图，**人工审批节点（human-in-the-loop）是审批流的核心诉求**，单 Prompt 根本做不到流程中断；
> - 权衡：多 Agent 的 token 开销和延迟更大，我们靠节点间的结果压缩（结构化输出）控制成本。

**Q：LangGraph 的状态机和传统状态机有什么区别？**
> - 概念一样（节点 + 边 + 状态），LangGraph 的价值是状态天然被 LLM 输出驱动、支持条件边（模型输出决定下一跳）、支持 checkpoint 持久化（断点续跑/重试）；
> - 我们用它实现了：评估不通过 → 打回；通过 → 定级；定级争议 → 转人工；复测未修复 → 重新流转。

**Q：RAG 检索链路怎么做的？检索质量怎么保证？**
> - 知识库构建：专家经验文档切块（按语义边界而非固定长度）→ embedding → pgvector 存向量 + 原文；
> - 检索：向量相似度 top-k → 拼接到 Prompt 作为参考案例；
> - 质量优化：对切块做了重叠窗口防止语义断裂；Prompt 里要求"参考案例仅供参考，与当前漏洞无关时忽略"，降低检索噪音误导；
> - 追问 pgvector：HNSW 索引、IVFFlat 对比；答：规模几万条用 HNSW 即可，查询延迟毫秒级。

**Q：人工审批怎么接进自动化流程的？**
> - 飞书审批卡片：工作流在审批节点挂起 → 生成飞书审批卡片（结构化字段：漏洞信息、模型研判结论）→ 专家在飞书点通过/驳回 → 回调 webhook → LangGraph checkpoint 恢复继续执行；
> - 关键点：挂起期间状态持久化（不占进程内存），超时未审批走催办/自动流转策略。

### 与岗位的关联话术（这是 OA 短板的关键破解点）

> "这个项目里我做的人工审批流，和 OA 审批流的核心技术是一样的：**节点流转的状态机、审批人与权限、驳回/转办、审批过程的可视化和持久化**。飞书审批卡片本质上就是动态表单 + 审批流的结合。所以 OA 审批流的设计模式我是有实战的，只是业务场景从漏洞审核换成了请假报销。"

## 12.3 POS 数据贯通（2024.12-2025.04）—— 展示架构与数据能力，重点讲

**技术栈**：Go、go-zero、GORM、MySQL、Redis、RabbitMQ、ETCD、Docker、gRPC、Protobuf

### STAR 讲述稿（2 分钟版）

> 这是面向多条零售 POS 产品线的数据中台，统一接入销售流水、商品档案、电子发票等业务数据。
> 我负责销售流水、电子发票、商品档案的接口开发：不同产品线的数据格式不一样，我设计了统一的数据模型和接入适配层，各产品线差异在适配层消化，对上是统一接口；
> 数据接入走 RabbitMQ，我负责消费端的实现：数据校验、清洗、加工后上传/落库；同时持续接入存量产品线，把老系统的数据迁进来。
> 这个项目让我完整实践了 go-zero 微服务体系：ETCD 注册发现、gRPC 服务间通信、消息驱动的数据流。

### 三层追问准备

**Q：多产品线数据格式差异怎么统一？**
> - 设计统一的领域模型（如销售流水：门店/商品/金额/时间/渠道），每个产品线一个适配器，把异构字段映射到统一模型；产品线特有字段进扩展字段（JSON）；
> - 好处：下游消费方只认统一模型，新增产品线只加适配器不改下游；
> - 坑：字段语义不一致（如"金额"有的含税有的不含），靠适配层显式转换 + 数据字典记录口径。

**Q：RabbitMQ 消息可靠性怎么保证？**
> - 生产者：发布确认（publisher confirm）；
> - 消费端：手动 ACK，业务处理成功才确认；处理失败进入重试队列，重试 N 次后进死信队列人工处理；
> - 幂等：消息带唯一业务 ID（流水号），落库唯一索引防重复；
> - 顺序性：按产品线/门店做路由 key 分区，保证同一门店消息进同一队列。

**Q：数据量大吗？有没有性能问题？**
> - 销售流水日均量级（据实回答，若不大量就讲"内部零售业务，量级可控，但架构按可扩展设计"）；
> - 优化点：批量落库（攒批 + 事务）、消费端并发度控制、慢 SQL 优化（索引覆盖）、大字段（发票 JSON）单独存储。

**Q：为什么选 RabbitMQ？和 Kafka 的对比？**
> - 数据中台场景消息量可控，RabbitMQ 的灵活路由（交换机/队列/绑定）、死信、延迟队列能力够用且运维简单；Kafka 优势在超高吞吐的日志/事件流场景，我们的量级用不上，且 Kafka 的消费语义（分区顺序、重平衡）更复杂。

### 与岗位的关联话术

> "数据中台训练了我做**系统间集成和数据治理**的能力——客服/OA 系统也要和很多周边系统对接（HR、财务、消息中心），统一模型 + 适配层 + MQ 异步解耦这套打法直接复用。"

## 12.4 商云前台（2023.12-2025.04）—— 展示全栈能力，重点讲

**技术栈**：Go、Wails、Vue 3、TypeScript、SQLite、RabbitMQ、串口通信、AES、RSA

### STAR 讲述稿（1.5 分钟版）

> 这是基于 Wails 的桌面收银应用，覆盖收银、会员、促销、支付及外设集成，数据本地 SQLite 存储 + 云端同步。
> 我负责自助模式的后台模块、加密信息处理与通信：微信电子小票、打印钱箱（串口通信）、RabbitMQ 消息、权限控制和语音提示模块，也参与了登录、电子秤、外卖模块和部分前端界面开发。
> 这是一个真正的全栈项目：Wails 的架构是 Go 后端 + WebView 前端，Go 通过 IPC 调用 JS 接口、前端事件回传后端，我前后端都写。

### 三层追问准备

**Q：Wails 的通信机制？**
> - Wails 把 Go 函数绑定到 JS 环境，前端调用像调本地方法；后端可以 emit 事件推送到前端；底层是 WebView 的 JS bridge（JSON 序列化通信）；
> - 与 Electron 对比：Wails 用系统 WebView 而非打包 Chromium，包体小（几十 MB vs 几百 MB）、内存占用低，代价是 WebView 版本随系统、兼容性要处理。

**Q：本地 SQLite + 云同步的一致性怎么处理？**
> - 收银场景要求断网可用：本地先落库保证交易不丢，网络恢复后增量同步（变更日志 + 版本号/时间戳）；冲突用"最后写入优先 + 关键业务（库存/会员余额）以服务端为准"。

**Q：权限控制模块怎么设计的？**
> - 收银员/店长/管理员角色，按角色控制菜单和操作按钮可见性 + 后端接口校验（前端隐藏只是体验，后端鉴权兜底）；敏感操作（退货、改价）需要更高权限或密码验证；
> - 与 OA 岗位的关联：这就是 RBAC 的最小实践，权限模型思想直接复用。

**Q：串口通信踩过什么坑？**
> - 打印钱箱/电子秤走串口：波特率匹配、字节流协议解析（帧头/长度/校验）、并发写串口要加锁、外设断连重试；Windows 驱动兼容问题。

### 与岗位的关联话术

> "商云前台是我最完整的全栈交付：从串口硬件到前端页面。岗位要求的 Vue、Linux 部署、权限控制我都有实战，接手客服系统的前端模块没有障碍。"

## 12.5 FlashRoot 安卓刷机工具（2022.01-2023.11）—— 讲成长与业务建模

**技术栈**：Gin、GORM、MySQL、Redis、Docker

### STAR 讲述稿（1 分钟版）

> 面向非洲市场的安卓刷机工具，支持离线刷机、联网后信息上传，为渠道商提供刷机统计与结算支持。
> 我负责 ROM 管理与渠道后台接口开发；参与了多级客户数据结构设计（渠道商-门店-网点多级层级）、返点计算和结算功能。
> 这是我第一次独立设计业务数据结构和结算逻辑，踩了很多坑——比如返点规则的变更导致历史结算数据口径混乱，后来学会了**结算规则版本化 + 结算快照**的设计。

### 追问准备

**Q：多级客户结构怎么设计？**
> - 树形结构：渠道商下挂门店、门店下挂网点；用 parent_id 自关联 + 路径字段（物化路径）加速"某节点及所有下级"的查询；层级不固定用闭包表/递归 CTE 的取舍讨论。

**Q：返点结算怎么做？**
> - 每月按刷机量 × 返点规则计算；规则按时间版本化管理（规则表带生效时间区间）；结算单生成时固化快照，后续规则变更不影响历史单；金额用 DECIMAL 计算避免浮点误差。

### 与岗位的关联话术

> "这个项目的多级组织结构和 OA 的**部门树、数据权限（本部门及下级）**是同一类建模问题，返点结算的版本化和审批流的流程版本化思路一致。"

## 12.7 项目讲述通用规则

1. **每个项目都准备：一句话定位 + 2 分钟版本 + 30 秒版本**（面试官说"简单讲讲"用 30 秒）；
2. **主动讲坑和复盘**：只讲成功不讲坑 = 显得没深度。每个项目至少准备一个"踩过的坑 + 怎么解决的"；
3. **数据说话**：能量化就量化（响应时间、处理量、人力节省），实在没有就讲范围（几条产品线、几个节点）；
4. **落点到岗位**：每段结尾一句关联话术（各节已给出）；
5. **诚实边界**：没做过的部分（如前端界面只参与了部分）明确说"参与"而非"负责"，防止追问穿帮。
