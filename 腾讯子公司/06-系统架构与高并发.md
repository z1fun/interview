## 6.1 微服务架构

### 6.1.1 原理讲解

#### （1）服务拆分原则

微服务不是「越细越好」，拆分的本质是**降低变更的耦合半径**：一个需求变更最好只改一个服务、只发一次版。

| 拆分依据 | 说明 | 举例（客服系统） |
| --- | --- | --- |
| 业务能力（Business Capability） | 按「公司做什么事」拆，最稳定 | 工单服务、会话服务、知识库服务、通知服务 |
| DDD 限界上下文 | 同一术语在不同上下文含义不同，应分属不同服务 | 「客户」在 CRM 上下文是商机主体，在客服上下文是联系人 |
| 变更频率 | 变更频繁的与稳定的分开 | 营销活动规则常变，账号体系稳定 |
| 读写分离 / 性能特征 | 高并发写的与复杂查询的分开 | IM 消息写入 vs 报表统计 |
| 团队组织（康威定律） | 系统架构会映射团队沟通结构 | 两个团队各负责一块，就别硬塞一个服务 |

**拆分的反面代价（一定要能说出来）**：
- 分布式事务：原本一个 `BEGIN...COMMIT` 变成跨服务补偿；
- 调用链变长：多一跳网络，P99 延迟叠加；
- 运维复杂度：服务数 × 实例数 × 配置项爆炸；
- 排查难度：一个报错要跨 5 个服务查日志，必须上链路追踪；
- 数据一致性：无法跨库 JOIN，需要冗余字段 + 最终一致。

**判断粒度是否合理的经验法则**：
1. 两个功能是否总是一起变更？是 → 别拆。
2. 拆分后是否出现了「同步调用链超过 3 层」？是 → 拆细了。
3. 是否出现了「一个业务操作要改 3 个库还得强一致」？是 → 拆细了。
4. 团队里有没有人能独立负责这个服务的全部生命周期（开发 + 部署 + 值班）？没有 → 拆细了。

#### （2）注册与发现（ETCD）

**解决的核心问题**：服务实例的 IP 是动态的（扩容、缩容、发布、宕机），调用方不能把 IP 写死在配置里。

三种角色：**服务提供者（Provider）**、**服务消费者（Consumer）**、**注册中心（Registry）**。

**ETCD 的机制**：

- **Lease（租约）**：注册时创建一个 TTL 租约（如 10s），把 key 绑定到租约上。ETCD 内部有定时器，租约到期自动删除 key。这就是「服务下线自动摘除」的原理——实例宕机后不再续约，TTL 到期 key 消失。
- **KeepAlive（心跳续约）**：客户端启动一个后台 goroutine 定期续约（一般 TTL/3 的间隔）。`clientv3` 的 `KeepAlive` 返回一个 channel，续约失败会通知客户端，客户端应主动重建 lease。
- **Watch（监听）**：消费者 watch 某个前缀（如 `/pos/rpc/product`），ETCD 在服务列表变化时**主动推送**事件，消费者本地维护一份内存中的实例列表。这比「定时轮询拉取」实时性高、压力小。
- **Raft 共识**：ETCD 集群通常 3/5 节点，写要多数派确认。它是 **CP** 系统——网络分区时宁可不可用也不返回脏数据。
- **Revision + MVCC**：每次写产生全局递增 revision，Watch 可以指定 `WithRev(rev)` 从历史版本开始回放，天然支持「断线后增量补偿」。

**对比其他注册中心**：

| 组件 | 一致性 | 健康检查 | 特点 |
| --- | --- | --- | --- |
| ETCD | CP（Raft） | 客户端租约心跳 | K8s 生态标配，Watch 机制强，Go 客户端友好 |
| ZooKeeper | CP（ZAB） | 临时节点 + Session | 老牌，运维重，写性能一般 |
| Consul | CP（Raft，也支持 AP 模式） | 客户端 + 服务端探测 | 自带 DNS/健康检查，功能全 |
| Nacos | AP（Distro）+ CP 可切换 | 心跳 + 服务端探测 | 阿里生态，带配置中心，Java 系友好 |

**优雅上下线（高频追问）**：
```
下线：先从注册中心注销（或停止续约）→ sleep 一个「客户端本地缓存刷新周期 + 在途请求时间」→ 停止接收新请求 → 等在途请求处理完（graceful shutdown）→ 关闭进程
上线：先启动、健康检查通过 → 再注册到 ETCD → 开始接流量
```
如果不做「先注销再等待」，消费者本地还有旧缓存，会把请求打到一个已经关掉的实例上，产生一批 `connection refused`。

#### （3）RPC 原理：gRPC 的 HTTP/2 与 Protobuf

**一次 RPC 的完整链路**：
```
业务代码调用 stub.Method(req)
  → 序列化（Protobuf 编码）
  → 服务发现（从本地实例列表缓存拿 IP:Port）
  → 负载均衡（选一个实例，如 P2C / 加权轮询）
  → 连接池取一条 HTTP/2 连接
  → HTTP/2 分帧、发送
  —— 网络 ——
  → 服务端 HTTP/2 解帧
  → 反序列化
  → 按 path（/package.Service/Method）路由到注册的 handler
  → 反射/生成的代码调用真实方法
  → 同样的流程回包
```

**gRPC 为什么快——HTTP/2 的四个特性**：

1. **二进制分帧层（Binary Framing）**：HTTP/1.1 是文本协议，解析要处理换行、大小写、空格；HTTP/2 把所有内容切成 `HEADERS` / `DATA` / `SETTINGS` 等二进制帧，解析是定长读取，CPU 开销低。
2. **多路复用（Multiplexing）+ Stream**：HTTP/1.1 一条连接同时只能处理一个请求（管线化因队头阻塞基本没人用）；HTTP/2 把每个请求抽象成一个 **Stream（流 ID）**，同一 TCP 连接上跑成百上千个并发流，**应用层的队头阻塞被消除**。（注意：TCP 层的队头阻塞仍然存在，这是 HTTP/3 用 QUIC/UDP 的原因——这句话说出来是加分项。）
3. **HPACK 头部压缩**：静态表（61 个常用头）+ 动态表 + 哈夫曼编码。gRPC 的头（`:method`、`:path`、`content-type`、`grpc-timeout`）高度重复，动态表可以做到第二次只发索引号。
4. **流控（Flow Control）与服务端推送**：基于 Stream 和 Connection 两级的 WINDOW_UPDATE 窗口，防止接收方被压垮；服务端可以主动 PUSH（gRPC 里体现为 Server Streaming）。

**gRPC 的四种调用模式**：
- Unary（一元）：最常见，一问一答；
- Server Streaming：客户端发一次，服务端持续推（如进度推送、日志流）；
- Client Streaming：客户端持续发，服务端最后回一次（如批量上报）；
- Bidirectional Streaming：双向流（如实时语音、协同编辑）。**求职者做过的 Gemini Live 实时语音就是典型的双向流场景，可以直接类比。**

**Protobuf 编码原理**：
- 采用 **TLV（Tag-Length-Value）** 结构，Tag = `(field_number << 3) | wire_type`；
- **Varint** 变长编码：小的数字占更少字节（`1` 只占 1 字节），`int32` 存大数会退化成 5 字节，所以负数多时应用 `sint32/sint64`（ZigZag 编码）；
- **字段号是唯一标识**，字段名不进二进制。所以：
  - **绝不能改已有字段的编号**，改了就是线上事故；
  - 删除字段要 `reserved 5;` 防止后人复用编号导致数据错乱；
  - 新增字段用新编号，老客户端不认识会忽略（**向后兼容**）；
  - 默认值（0/""/false）不序列化，所以无法区分「未设置」和「设置为 0」，需要 `optional` 关键字 + `HasField`。

**与 JSON 的对比**：

| 维度 | Protobuf | JSON |
| --- | --- | --- |
| 体积 | 小 3~10 倍（字段名不进包、varint） | 大，文本冗余 |
| 序列化速度 | 快 5~100 倍 | 慢，要解析字符串 |
| 可读性 | 差，需要 .proto 或工具解码 | 好 |
| 契约 | 强类型，IDL 生成代码，天然文档 | 弱，靠约定 |
| 适用 | 内部服务间高频调用 | 对外 API、浏览器交互 |

#### （4）API 网关

**网关的职责**（一定要能分层说清）：
- **接入层**：TLS 卸载、HTTP/2、gzip、静态资源；
- **路由层**：按 path/host/header 路由到后端服务（由服务发现驱动动态更新）；
- **安全层**：鉴权（JWT 校验）、限流（IP/用户/接口维度）、黑白名单、防重放、参数校验；
- **流量治理**：灰度发布（按 header/uid 分流）、A/B 测试、熔断、重试、超时；
- **可观测**：全链路 TraceID 注入、访问日志、Metrics 埋点；
- **协议转换**：对外 REST/JSON，对内 gRPC（用 grpc-gateway 或网关自己做 Transcoding）。

**BFF（Backend For Frontend）**：为不同端（Web / App / 小程序）各建一个聚合层，做数据裁剪和编排。好处是端上的多次请求变一次、字段按需裁剪（移动端省流量）；代价是多了一层维护成本。**小团队慎用**——这句话能体现你的判断力。

**选型**：Nginx / OpenResty（性能最好，Lua 扩展）、Kong、APISIX（云原生，etcd 存储，插件丰富）、go-zero 自带的 `gateway`（理解成本低，适合内部系统）、K8s Ingress（网关能力弱，偏 L4/L7 转发）。

#### （5）服务治理：超时 / 重试 / 熔断 / 负载均衡

**超时（Timeout）**：
- 原则：**上游超时 > 下游超时**，否则上游已经放弃了，下游还在跑，白白浪费资源。
- 更进阶的是**超时预算传递（Deadline Propagation）**：客户端设置总预算 500ms，第一跳花了 100ms，第二跳就只剩 400ms，通过 `grpc-timeout` header 或 context metadata 逐跳传递。gRPC 原生支持——`context.WithTimeout` 的 deadline 会自动编码到 HTTP/2 的 `grpc-timeout` 头里。
- **一定要有超时**：没有超时的 RPC 是定时炸弹，下游一慢，上游 goroutine / 连接池 / 线程全被占满，形成雪崩。

**重试（Retry）**：
- 只重试**幂等**操作（GET、查询、带幂等键的写）；
- 只重试**可恢复错误**（网络抖动、超时、503），不要重试 400/401/业务校验失败；
- **指数退避 + 抖动（Jitter）**：`sleep = min(cap, base * 2^n) * rand(0.5, 1.5)`。没有抖动的重试会产生「重试风暴」——所有客户端在同一时刻重试，把刚恢复的服务再次打挂（thundering herd）。
- 限制重试次数（2~3 次）和重试预算（重试请求不超过总请求的 10%）；
- **重试放大问题**：A→B→C 三层各重试 3 次，C 承受的请求量是正常时的 3×3=9 倍。解决：只在最外层重试，或者用「重试预算」全局控制。

**熔断（Circuit Breaker）**：
三态机：
```
Closed（闭合，正常放行）
  │ 统计窗口内错误率 > 阈值（如 50%）或慢调用比例超阈值
  ▼
Open（打开，直接快速失败，不走网络）
  │ 冷却时间到（如 5s）
  ▼
Half-Open（半开，放行少量探测请求）
  ├─ 探测成功数达标 → Closed
  └─ 探测失败 → Open（重置冷却计时）
```
关键点：熔断是**保护调用方**（防止自己线程被慢下游耗光），限流是**保护自己**（防止被打挂），降级是**保证有损可用**。三者目标不同，面试官喜欢追问这个区别。

**负载均衡**：
- 简单策略：随机、轮询、加权轮询、一致性哈希（同 key 落同实例，便于本地缓存命中）；
- 进阶策略：**P2C（Power of Two Choices）**——随机挑两个实例，选「当前在途请求数 / 权重」更小的那个。go-zero 的 `zrpc` 默认就是 P2C + 指数加权移动平均（EWMA）延迟统计，比轮询更能抗慢节点。**这点非常加分，因为 go-zero 是简历上的技术栈**；
- 最小连接数、最快响应（需统计延迟）。

### 6.1.2 高频面试 Q&A

**Q1：微服务拆分粒度怎么把握？拆太细有什么问题？**

参考回答：
> 我的判断标准是「变更耦合半径」和「团队边界」。具体三条：
> 第一，看变更频率，总是一起改的功能不要拆——比如我们做 POS 数据贯通时，销售流水和商品档案虽然业务上不同，但共用一套产品线适配层和统一上传逻辑，我就把它们放在同一个数据接入服务里，只是拆成不同的 handler 和 consumer。
> 第二，看事务边界。拆完之后如果需要一个业务操作强一致地写三个库，那就是拆错了，应该用聚合根把它收回一个服务。
> 第三，看团队。康威定律是真实存在的，一个服务如果没人能独立负责它的部署和值班，它就不该独立存在。
> 拆太细的代价很具体：分布式事务成本、调用链变长导致 P99 叠加、无法跨库 JOIN 导致要冗余字段、排查问题需要跨服务查日志、运维复杂度指数上升。所以我的倾向是**「先单体模块化，等模块边界稳定、团队规模够大了再拆」**，而不是一上来就微服务。

**Q2：ETCD 是怎么实现服务注册与发现的？租约过期会发生什么？**

参考回答：
> ETCD 用 **Lease + Watch** 两套机制完成。服务启动时创建一个带 TTL 的租约（我们用 10 秒），把 `服务前缀/实例ID` 这个 key 绑定到租约上，然后起一个后台 goroutine 做 KeepAlive 续约。服务正常下线时主动撤销租约（Revoke），key 立即消失；服务宕机时心跳停了，租约到期 ETCD 自动删除 key。
> 消费方 watch 服务前缀，ETCD 通过长连接把变更事件推给消费方，消费方在内存里维护一份实例列表，调用时直接本地负载均衡。ETCD 是 CP 系统，底层 Raft 保证多数派写入。
> 需要注意的坑有两个：
> 一是**下线时要先 Revoke 再等一会儿再停进程**——因为消费方的本地缓存有刷新延迟，立刻停进程会有一批请求打到已经死掉的实例上，出现 connection refused。我们当时是在优雅停机里加了 3 秒的等待窗口。
> 二是**网络抖动会导致租约误过期**，服务其实活着但被摘除了。解决方式是把 TTL 设得比心跳间隔大 3 倍以上，并在 KeepAlive channel 返回失败时主动重建 lease 并重新注册。

**Q3：gRPC 为什么比 HTTP + JSON 快？**

参考回答：
> 分两层。**传输层是 HTTP/2**：二进制分帧让解析变成定长读取，比文本协议省 CPU；多路复用把每个请求抽象成 stream，一条 TCP 连接上跑几百个并发请求，消除了 HTTP/1.1 的应用层队头阻塞；HPACK 头压缩用静态表 + 动态表，重复的头只发索引，而 gRPC 的头（content-type、grpc-timeout、path）高度重复，压缩收益很大。
> **编码层是 Protobuf**：字段名不进二进制，只发字段编号和 varint 编码的值，体积通常比 JSON 小 3~10 倍；反序列化是直接按 schema 读二进制，不用解析字符串和数字转换，速度通常快一个数量级。
> 补充一个辩证的点：HTTP/2 解决的是应用层队头阻塞，**TCP 层的队头阻塞还在**（丢一个包，同连接所有 stream 都等重传），这也是 HTTP/3 改用 QUIC over UDP 的原因。
> 另外 Protobuf 的代价是可读性差，排查问题要工具解码，所以对外 API 我们仍然用 JSON，内部服务间才用 gRPC。

**Q4：服务间调用的超时和重试怎么设计？重试会有什么问题？**

参考回答：
> 超时的原则是**上游超时必须大于下游超时**，否则上游已经返回失败了，下游还在白跑，占着连接和 goroutine，等于自杀。更好的做法是超时预算传递：客户端设 500ms 总预算，第一跳用了 100ms，剩下 400ms 通过 gRPC 的 `grpc-timeout` header 传给下一跳，逐跳递减。gRPC 原生支持，因为 context 的 deadline 会自动编码进头部。
> 重试有三个铁律：一，**只重试幂等操作**，下单、扣款这种必须有幂等键才能重试；二，**只重试可恢复错误**，网络超时、503 可以重试，400 和业务校验失败重试一万次也没用，纯属放大故障；三，**必须指数退避加随机抖动**，`base * 2^n * rand(0.5,1.5)`，没有抖动的话所有客户端会在同一时刻重试，形成重试风暴，把刚恢复的服务二次打挂。
> 最容易被忽略的是**重试放大**：A→B→C 三层各重试 3 次，C 最坏要承受 9 倍流量。所以我们的做法是只在最外层网关做重试，内部 RPC 层默认不重试，或者用重试预算（重试流量不超过总流量的 10%）做全局熔断。

**Q5：熔断、限流、降级有什么区别？**

参考回答：
> 三者解决的不是同一个问题。
> **限流**是保护自己不被压垮，控制的是**入口流量速率**，手段有令牌桶、漏桶、滑动窗口，超了就拒绝或排队。
> **熔断**是保护调用方不被慢下游拖死，控制的是**对某个下游的调用**。它是个三态机：Closed 正常放行，错误率超阈值转 Open 直接快速失败，冷却后半开试探，成功就恢复。核心价值是「快速失败」——下游挂了的时候，与其让请求卡在超时上占满我的 goroutine 和连接池，不如立刻失败，把资源留给其他健康的下游。
> **降级**是保证有损可用，是在资源不足或依赖故障时，**主动关闭或简化非核心功能**，比如商品详情页的推荐模块挂了就返回空列表、大促时关闭实时排行榜改用一小时前的快照。降级是有损的，所以必须提前和产品定义好「哪些功能可以降、降成什么样、怎么一键开关」，通常是配置中心下发开关，出问题一键降级。

**Q6：一次 RPC 调用的完整流程是怎样的？**

参考回答：
> 完整链路是：业务代码调 stub 生成的方法 → Protobuf 序列化成二进制 → 从本地服务实例缓存里取列表 → 负载均衡选一个实例 → 从连接池拿一条 HTTP/2 连接 → 分帧发送 → 服务端解帧反序列化 → 按 `/package.Service/Method` 这个 path 找到注册的 handler → 调用真实方法 → 反向回包。
> 里面有几个容易被忽略的工程细节：**连接池**要控制最大连接数和空闲回收；**服务列表缓存**要有兜底，ETCD 挂了不能让调用方直接不可用，本地要有最后一版快照；**负载均衡**用 P2C 比轮询好，能自动避开慢节点；**超时要逐跳传递**；**TraceID 要透传**，否则跨服务排查就是灾难。
> go-zero 的 zrpc 把这些都封好了：内置 etcd resolver、P2C 负载均衡、自适应熔断（基于 Google SRE 的算法按成功率动态算丢弃概率）、超时和链路追踪，所以我们在 POS 项目里基本只写业务逻辑，不用自己造轮子。

**Q7：微服务的可观测性怎么做？**

参考回答：
> 三个支柱：**Metrics、Tracing、Logging**。
> Metrics 用 Prometheus + Grafana，关注四个黄金指标：延迟（P50/P95/P99，不要只看均值）、流量、错误率、饱和度（CPU/内存/连接池/队列长度）。服务端要暴露 RED 指标（Rate、Errors、Duration）。
> Tracing 用 OpenTelemetry 或 Jaeger，核心是 TraceID 全链路透传（HTTP header / gRPC metadata / MQ 消息属性），跨服务甚至跨 MQ 都要带上。我曾经排查过一个「消息消费延迟 30 秒」的问题，就是因为 TraceID 在发消息时丢了，只能靠业务 ID 反查日志，成本高很多。
> Logging 要结构化（JSON），带 TraceID、用户 ID、耗时、错误码，方便 ELK 检索。日志级别要能动态调整，出问题时不用重启就能开 DEBUG。
> 落地建议是先做「能定位问题」的最小集：统一 TraceID + 结构化日志 + 核心接口 P99 监控 + 错误率告警，不要一上来就追求大而全。

## 6.2 消息队列（RabbitMQ）

### 6.2.1 原理讲解

#### （1）核心模型与交换机类型

RabbitMQ 的核心模型：**Producer → Exchange → Binding → Queue → Consumer**。消息不直接进队列，而是先发给 Exchange，由 Exchange 根据**绑定规则**决定投递到哪些 Queue（**Routing Key** 是生产者的路由凭据，**Binding Key** 是队列的绑定规则）。

| 交换机类型 | 路由规则 | 典型场景 |
| --- | --- | --- |
| **direct** | Routing Key 精确匹配 Binding Key | 按业务类型分发，如 `order.paid` 只给订单队列 |
| **topic** | 通配符匹配：`*` 匹配一个单词，`#` 匹配零或多个单词 | POS 多产品线数据接入（`pos.{product}.{dataType}`） |
| **fanout** | 忽略 Routing Key，广播到所有绑定队列 | 配置刷新、缓存失效通知、事件广播 |
| **headers** | 按消息头键值对匹配（可 `x-match: all/any`） | 少见，性能差，一般用 topic 替代 |

**默认交换机**：名称为空字符串 `""`，每个队列自动绑定一个同名 Binding Key，所以 `Publish(routingKey="queueName")` 会直接进队列。

**备用交换机（Alternate Exchange, AE）**：给主交换机配置 `alternate-exchange`，当消息无法路由到任何队列时（而不是被丢弃）转发到 AE，用于兜底告警。**能在面试中主动提到 AE 是加分的**，说明你处理过「消息被静默丢弃」这个经典坑。

**topic 路由示例（POS 项目实战）**：
```
Exchange: pos.data (topic)
Queue: pos.sale.data        Binding: pos.*.sale       # 所有产品线的销售流水
Queue: pos.invoice.data     Binding: pos.*.invoice    # 所有产品线的电子发票
Queue: pos.product.data     Binding: pos.*.product    # 所有产品线的商品档案
Queue: pos.all.audit        Binding: pos.#            # 审计队列，收全部
生产者：Publish(routingKey="pos.retailA.sale")
```
这套设计的价值是：**接入新产品线时，生产者只改 Routing Key，消费端一行不改**——这正是开闭原则。

#### （2）消息可靠性：三个环节都不能丢

消息丢失可能发生在三个位置，必须逐个堵：

**① 生产者 → Broker**

- **Publisher Confirm**：把 channel 设为 confirm 模式，Broker 收到并持久化后会回 `basic.ack`（含投递序号），失败回 `basic.nack`。支持异步批量确认，性能损耗小。
- **Publisher Return**：处理「路由失败」——消息到了 Exchange 但没匹配到队列时会回调 `basic.return`（需设置 `mandatory=true`）。注意：Confirm 只管「Broker 收到了」，Return 才管「路由成功了」，**两者必须配合使用**，只开 Confirm 会漏掉路由失败的消息。
- **本地消息表 + 定时补偿**：本地事务和发消息无法原子。做法是在业务库里加一张 `local_message` 表，**业务写和消息记录在同一个本地事务**中提交，然后异步投递；投递成功则把记录标记为已发送，失败由定时任务扫表重投。（详见 6.4 分布式一致性）

**② Broker 内部持久化**
- Exchange 和 Queue 声明时设 `durable=true`（否则 Broker 重启后拓扑消失）；
- 消息发送时设 `DeliveryMode: amqp.Persistent`（2）落盘；
- 两者必须**同时满足**，只设一个都不可靠。
- 进阶：用 **Quorum Queue（仲裁队列）** 代替经典镜像队列，基于 Raft 复制，是 RabbitMQ 3.8+ 官方推荐的高可用方案（经典镜像队列有脑裂和同步阻塞问题，4.0 已移除）。
- 极端情况（磁盘损坏）仍需依赖多副本或异地容灾，RabbitMQ 不保证。

**③ Broker → 消费者**
- **关闭自动 ACK，改用手动 ACK**：自动 ACK 在消息一投出就确认，消费者崩溃或处理失败消息就永远丢了。手动 ACK 是「业务处理成功后」才 `Ack()`。
- **ACK 时机**：必须在业务逻辑（含 DB 写入）完成之后再 ACK，不能收到消息就 ACK 然后异步处理。
- **Nack / Reject**：处理失败时 `Nack(requeue=true)` 重新入队（要配合重试次数上限，否则无限循环）；或 `Nack(requeue=false)` 直接进死信队列。
- **prefetch / Qos**：`channel.Qos(prefetchCount, 0, false)` 限制每个消费者未 ACK 的消息数（一般设 10~50），防止一个消费者把队列里的消息全拉走但处理不过来（不公平分发 + 内存爆掉）。

#### （3）消费幂等

**为什么必须幂等**：网络抖动、消费者重启、ACK 丢失都会导致消息重复投递。RabbitMQ 的语义是 **at-least-once（至少一次）**，不是 exactly-once。

**四种方案**：

| 方案 | 实现 | 适用 |
| --- | --- | --- |
| **数据库唯一索引** | 业务表上加 `uk(biz_type, biz_id)`，重复插入报 1062 直接忽略 | 最常用的兜底方案，成本低、绝对可靠 |
| **去重表** | 单独一张 `msg_consume_log(msg_id, status, create_time)`，先插入再处理，唯一键冲突即已消费 | 需要对消息本身去重（如通知类） |
| **Redis SETNX** | `SET msg:{id} 1 NX EX 86400`，返回 false 说明已消费 | 性能最好，但 Redis 挂了或过期会失效，一般配合唯一索引双保险 |
| **状态机 CAS** | `UPDATE ticket SET status='处理中' WHERE id=? AND status='待处理'`，受影响行数为 0 说明已被处理 | 状态流转场景，天然幂等且能防并发 |

**关键细节**：
- 幂等键的选择决定了幂等的有效性。**优先用业务唯一键（订单号、流水号、发票号），而不是消息 ID**——因为生产者重发时 MessageID 会变，但业务单号不变。POS 项目里我们的幂等键就是 `产品线 + 门店号 + POS 流水号`。
- **「先查后插」有并发窗口**，必须靠数据库唯一约束兜底，不能只靠 `SELECT` 判断存在。
- 幂等要和去重的**TTL**权衡：Redis 去重一般保留 24 小时~7 天，超过窗口的重复消息就挡不住了。
- 如果消费逻辑涉及第三方调用（如上传到云端），第三方接口本身也要支持幂等（用业务单号作为 requestId）。

#### （4）顺序性

**RabbitMQ 何时会乱序**：
1. 一个队列有**多个消费者**——消息被轮询分发，谁先处理完不确定；
2. 消息**重新入队（requeue）**——会回到队头，但对其他消费者来说顺序已经破坏；
3. 消费端**异步/并发处理**（收到消息丢进 goroutine pool）；
4. 生产者**多线程发送**且未等待 Confirm。

**保证顺序的三种手段**：
- **单队列 + 单消费者 + 串行处理**：最简单的强顺序方案，代价是吞吐上不去（RabbitMQ 单队列单消费者大概几千 TPS）。**只在业务真的需要全局顺序时用**。
- **按业务 key 哈希分区**：把同一业务实体的消息路由到同一队列（如按门店号 hash 到 N 个队列），每个队列单消费者。这样既保证「同一实体的顺序」，又能横向扩展 N 倍吞吐。**这是最推荐的做法**。
- **消息内序号 + 消费端重排/丢弃**：消息带 `seq`，消费端维护已处理的最大序号，小于等于的直接丢弃；或缓存乱序消息等前序到达。复杂度高，慎用。

**面试关键点**：一定要反问「你说的顺序是全局顺序还是分区顺序？」——绝大多数业务只需要「同一订单/同一工单的局部顺序」，不需要全局顺序。这个反问能立刻体现你有实战经验。

#### （5）死信队列与延迟队列

**死信（Dead Letter）的三种来源**：
1. 消息被 `Nack(requeue=false)` 或 `Reject(requeue=false)`；
2. 消息 TTL 过期（队列级 `x-message-ttl` 或消息级 `expiration`）；
3. 队列达到最大长度 `x-max-length` 后溢出（默认丢弃队头）。

**死信交换机（DLX）配置**：
```go
// 队列声明时绑定死信交换机
args := amqp.Table{
    "x-dead-letter-exchange":    "pos.dlx",           // 死信转发到哪个交换机
    "x-dead-letter-routing-key": "pos.sale.dead",     // 转发时使用的 routing key
    "x-message-ttl":             int32(30000),        // 队列级 TTL，30 秒
    "x-max-length":              int32(100000),       // 队列最大长度，防内存爆
}
ch.QueueDeclare("pos.sale.data", true, false, false, false, args)
```

**死信队列的业务价值**：
- **隔离坏消息**，避免一条毒消息（poison message）无限重试阻塞整个队列；
- **人工介入**：进死信队列的消息可以落库，提供后台页面让运营重投；
- **延迟重试阶梯**：失败后进 10s 死信队列 → 再失败进 1min 队列 → 再失败进 10min 队列，符合「快速重试 + 长尾兜底」的策略。

**延迟队列的三种实现**：

| 方案 | 原理 | 优缺点 |
| --- | --- | --- |
| **TTL + DLX** | 消息进一个没有消费者的队列并设 TTL，过期后变成死信转发到真实消费队列 | 原生支持、无插件依赖；**坑**：RabbitMQ 只检查队头消息的 TTL，如果队头消息 TTL 很长会阻塞后面短 TTL 的消息，必须为每个延迟档位单独建队列 |
| **delayed_message_exchange 插件** | 官方社区插件，Exchange 内做了延迟投递 | 用起来最优雅，支持任意延迟时间；但需要装插件，部分云厂商不开放 |
| **定时任务扫表** | 业务表加 `next_retry_time` 字段，定时任务扫描到期记录 | 最可靠、可观测、可人工干预，延迟精度取决于扫描间隔；**生产环境我最推荐这个**，因为它不依赖中间件特性，出问题好排查 |

**另一个坑**：延迟队列的消息如果队列声明时没设 `durable`，Broker 重启后延迟消息全丢。

#### （6）消息积压与消费限流

**积压的原因与处置**：
- 消费慢于生产 → 先看是**消费者处理慢**（慢 SQL、下游超时）还是**消费者数量不够**；
- 应急扩容消费者（但注意顺序性会被破坏）；
- 极端情况：临时把消息转到更大容量的队列，或用「捞消息转发」的临时消费者程序快速转存到数据库/MQ，先把队列清空，再慢慢处理；
- 长期方案：**生产端限流**（令牌桶控制入队速率）、**批量消费**（一次拉多条批量写库）、**异步化**（消费只做落库，重逻辑交给下游）。

**监控指标**：队列 depth（积压量）、unacked 数、publish/deliver/ack rate、消费者数量。队列 depth 持续上涨必须告警。

### 6.2.2 高频面试 Q&A

**Q1：怎么保证消息不丢失？**

参考回答：
> 我把链路拆成三段分别堵。
> **生产端到 Broker**：开启 Publisher Confirm，Broker 持久化成功会回 ack，失败回 nack，我们的程序在 nack 时落库重投；同时开 `mandatory=true` 配合 Publisher Return 处理「路由失败」的情况——因为 Confirm 只保证 Broker 收到了，不保证路由到了队列，这两个机制必须一起用才完整。再进一步就是本地消息表，业务写和消息记录放在同一个本地事务里，彻底消除「业务成功但消息没发出去」的窗口。
> **Broker 内部**：Exchange 和 Queue 都声明 `durable=true`，消息设 `DeliveryMode=2` 持久化，这两个必须同时满足；高可用上我们用的是 Quorum Queue，基于 Raft 复制，比老的镜像队列更可靠。
> **Broker 到消费者**：关掉自动 ACK，用手动 ACK，而且必须在业务处理完成（包括数据库写入提交）之后才 Ack。失败的话用 Nack 加 requeue，但要配合重试次数字段或死信队列限制重试次数，否则毒消息会无限循环。
> 做过这三段之后，理论上还剩一种极端情况：消费者处理完了、数据库也提交了，但 Ack 的时候进程挂了，消息会重投——这就是为什么**消费端必须做幂等**，可靠性和幂等是一对搭档，缺一不可。

**Q2：怎么保证消息不被重复消费？**

参考回答：
> 首先纠正一个认知：RabbitMQ 的投递语义是 **at-least-once**，重复是必然的，不是 bug，所以幂等是消费端的必答题而不是附加题。
> 我们的做法是**分层去重**：第一层用 Redis 的 `SET msg_key 1 NX EX 86400` 做快速拦截，挡住 99% 的重复，成本低；第二层也是最关键的一层，是数据库唯一索引兜底——我们的销售流水表上有 `uk(product_line, store_no, pos_serial)` 这个联合唯一键，重复插入会报 1062，程序里捕获这个错误码当成功处理，这样即使 Redis 挂了或者过了 TTL 也不会产生脏数据。
> 幂等键的选择很关键：**要用业务唯一键，不能用消息 ID**，因为生产端重发时消息 ID 会变，但业务单号不变。
> 另外还有一个反模式要避免：不能「先 SELECT 判断存在再 INSERT」，这个有并发窗口，两个消费者同时查都说没有，然后都插入。必须直接 INSERT 靠数据库约束保证原子性。
> 对于状态流转类的场景，我们用**状态机 CAS** 更自然：`UPDATE ticket SET status='处理中' WHERE id=? AND status='待处理'`，看受影响行数是不是 1，为 0 说明已经被处理过了，直接返回成功。

**Q3：怎么保证消息的顺序性？**

参考回答：
> 我一般会先反问一句「需求上要的是全局顺序还是同一业务实体的顺序」，因为绝大多数场景只需要后者，而这两者的成本差一个数量级。
> 如果确实要顺序，RabbitMQ 有三个地方会破坏顺序：一个队列有多个消费者、消息 requeue 回队头、消费端异步并发处理。
> 所以最小的保证是「单队列 + 单消费者 + 串行处理」，但吞吐很低，单队列大概几千 TPS。
> 实践中更好的是**按业务 key 分区**：用一致性哈希把同一个门店、同一个订单的消息路由到同一个队列，每个队列单消费者。这样既保证了同一实体的严格顺序，又能通过增加队列数横向扩展吞吐，是我们 POS 项目里的实际做法。
> 如果既想并发又要顺序，就得在消费端做重排：消息带序号，维护已处理的最大序号，比它小的直接丢弃，比它大的先缓存等前序到达。但这个复杂度很高，还引入了内存和延迟问题，除非业务强要求，我不推荐。
> 另外顺序性和重试是冲突的——一条消息失败重试会打乱后续顺序，所以顺序队列里的失败消息一般直接进死信队列人工处理，而不是原地重试。

**Q4：消息积压了几百万条怎么处理？**

参考回答：
> 先定位原因再动手，因为不同原因的解法完全不同。看三个指标：生产速率有没有突增、消费速率是不是掉了、消费者实例数是不是不够。
> 如果是消费端变慢（下游超时、慢 SQL），先修消费逻辑，然后临时扩容消费者把积压追平。但扩容前要确认业务能不能接受乱序，如果要保序就只能扩队列数并重新分配分区，不能直接加消费者。
> 如果是生产突增（比如上游补数据），可以考虑临时用一批「搬运工」消费者，不做业务逻辑，只把消息原样转存到一个容量更大的队列或者直接落库，先把主队列清空恢复线上，再用离线任务慢慢处理存下来的数据。这个方案的好处是不阻塞主链路。
> 长期要做三件事：一是队列 depth 和 unacked 数必须监控告警；二是生产端加限流，不能让上游把 MQ 当无限缓冲池；三是消费端做批量消费和异步化，把重逻辑从消费链路里挪出去。
> 还有一个要提前设的防护是 `x-max-length`，防止内存被打爆拖垮整个 Broker——宁可丢消息也不能让 Broker 挂，因为 Broker 挂了影响的是所有业务线。

**Q5：RabbitMQ 和 Kafka 怎么选？**

参考回答：
> 核心差异在**模型定位**：RabbitMQ 是「消息队列」，面向消息投递，消息被消费后可以删除，强调灵活路由和低延迟；Kafka 是「分布式提交日志」，面向流式数据，消息按分区追加、按 offset 消费、可重放，强调高吞吐和持久化。
> 具体维度上：吞吐量 Kafka 高一个数量级（百万级 vs 十万级），因为它是顺序写 + 零拷贝 + 批量；RabbitMQ 延迟更低，单条几毫秒，Kafka 因为批量发送通常几十毫秒；路由能力 RabbitMQ 强得多（四种交换机 + 通配符），Kafka 只有 topic + 分区；顺序性 Kafka 天然按分区有序，RabbitMQ 要自己设计；消息重放 Kafka 支持（改 offset），RabbitMQ 消费完就删了。
> 选型上：业务解耦、任务分发、复杂路由、需要延迟队列和死信，选 RabbitMQ；日志采集、埋点、流式计算、需要重放和超高吞吐，选 Kafka。
> 我们 POS 项目选 RabbitMQ 主要就是因为 topic 交换机的多产品线路由能力刚好匹配「一条产品线一个 routing key」这个模型，而且数据量级在几十万条/天，RabbitMQ 完全够用，运维成本也更低。如果哪天量级涨到千万级，我会考虑换 Kafka。

**Q6：延迟队列怎么实现？**

参考回答：
> 三种方式，我按推荐度倒序说。
> **最推荐的是定时任务扫表**：业务表加 `next_retry_time` 和 `retry_count` 字段，定时任务每分钟扫一次到期未处理的记录。它不依赖任何中间件特性、可观测、能人工干预、能改延迟时间，出问题也最好排查。精度取决于扫描间隔，对绝大多数业务（如 30 分钟未处理自动升级）完全够用。
> **其次是 TTL + DLX**：建一个没有消费者的队列，设 `x-message-ttl`，消息过期后变成死信转发到真正的消费队列。这里有个**大坑**：RabbitMQ 只检查队头消息的 TTL，如果队头是一条 1 小时 TTL 的消息，后面的 10 秒消息要等 1 小时才被检查到。所以必须**为每个延迟档位单独建队列**（10s 队列、1min 队列、10min 队列）。
> **最优雅的是 `rabbitmq_delayed_message_exchange` 插件**，Exchange 内部维护延迟投递，支持任意延迟时间。但需要装插件，很多云厂商的托管 RabbitMQ 不开放插件安装权限，我们当时就没法用。
> 另外要提醒一点：延迟队列的消息也要做持久化，否则 Broker 重启延迟消息全丢，那些等着重试的任务就永远消失了。

## 6.3 高并发设计

### 6.3.1 原理讲解

#### （1）限流算法（含 Go 实现）

**① 固定窗口计数器（Fixed Window）**

思路：每秒钟一个窗口，一个计数器，到 1 就拒绝，下一个窗口清零。

```
|---- 窗口1 (0-1s) ----|---- 窗口2 (1-2s) ----|
     限流 100 次             限流 100 次
```

**致命缺陷——临界问题**：如果限流 100/s，在 0.9s 打 100 次，1.1s 再打 100 次，两个窗口各 100 次都合法，但 0.5s 内实际过了 200 次，是限额的 2 倍。所以固定窗口**只能用于精度要求不高的场景**。

```go
// 固定窗口计数器（单机版）
type FixedWindowLimiter struct {
    mu       sync.Mutex
    limit    int           // 窗口内最大请求数
    window   time.Duration // 窗口大小
    counter  int           // 当前窗口计数
    windowStart time.Time  // 当前窗口起始时间
}

func (l *FixedWindowLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    now := time.Now()
    if now.Sub(l.windowStart) >= l.window {
        l.windowStart = now
        l.counter = 0
    }
    if l.counter >= l.limit {
        return false
    }
    l.counter++
    return true
}
```

**② 滑动窗口（Sliding Window）**

解决临界问题。有两种实现：

- **滑动日志（Sliding Log）**：把每次请求的时间戳存下来（Redis ZSet），每次判断「当前时间往前推 1 秒内的请求数」是否超限。精度最高，但内存开销大（要存所有请求时间戳）。
- **滑动窗口计数（近似）**：把 1 秒切成 10 个 100ms 的小格，每格一个计数器，窗口滑动时累加最近 10 个格子的值。内存小，精度取决于格子粒度。**这是工程上最常用的方案**（Sentinel 用的就是这种）。

```go
// 滑动窗口计数（分片计数器，单机版）
type SlidingWindowLimiter struct {
    mu       sync.Mutex
    limit    int
    slots    []int       // 每个小格的计数
    slotDur  time.Duration
    lastSlot int64       // 当前所处的格子编号
}

func NewSlidingWindow(limit int, window time.Duration, slotCount int) *SlidingWindowLimiter {
    return &SlidingWindowLimiter{
        limit:   limit,
        slots:   make([]int, slotCount),
        slotDur: window / time.Duration(slotCount),
    }
}

func (l *SlidingWindowLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    now := time.Now().UnixNano() / int64(l.slotDur)
    // 把上一轮到现在之间跨过的格子清零
    if now != l.lastSlot {
        diff := now - l.lastSlot
        if diff >= int64(len(l.slots)) {
            for i := range l.slots { l.slots[i] = 0 }
        } else {
            for i := int64(1); i <= diff; i++ {
                l.slots[(l.lastSlot+i)%int64(len(l.slots))] = 0
            }
        }
        l.lastSlot = now
    }
    sum := 0
    for _, v := range l.slots { sum += v }
    if sum >= l.limit { return false }
    l.slots[now%int64(len(l.slots))]++
    return true
}
```

**Redis + Lua 版滑动窗口（分布式）**：
```lua
-- KEYS[1]: 限流 key
-- ARGV[1]: 当前时间戳(ms)  ARGV[2]: 窗口大小(ms)  ARGV[3]: 限流阈值
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

-- 移除窗口外的请求
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- 统计窗口内请求数
local count = redis.call('ZCARD', key)
if count >= limit then
    return 0
end
-- 记录本次请求，member 用 时间戳+随机 避免同毫秒覆盖
redis.call('ZADD', key, now, now .. '-' .. math.random(100000))
-- 设置过期，防止冷 key 常驻内存
redis.call('PEXPIRE', key, window)
return 1
```
**为什么必须用 Lua**：`ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` 三步如果分开执行，多个客户端会交叉执行产生竞态（check 完还没 add 别人也 check 通过）。Lua 脚本在 Redis 里是**原子执行**的，这是分布式限流的标准做法。

**③ 漏桶（Leaky Bucket）**

思路：请求像水一样倒进桶里，桶底有一个**恒定速率**的漏口。桶满了新请求就溢出（被限流）。
- 特点：**输出速率绝对恒定**，天然平滑流量，适合保护下游；
- 缺点：**不允许突发**——即使下游很闲，也不能一次放行一批。这在很多业务上是不可接受的（比如页面加载会同时发 10 个请求）。

**④ 令牌桶（Token Bucket）**

思路：以一个恒定速率往桶里放令牌，桶有容量上限。请求来了要先拿一个令牌，拿不到就拒绝或等待。
- 特点：**允许突发**（桶里攒了 N 个令牌就能瞬间放行 N 个请求），同时长期平均速率受限于放令牌的速度；
- 这是**工程上最常用的算法**，Go 的 `golang.org/x/time/rate` 就是令牌桶。

```go
import "golang.org/x/time/rate"

// 限流 100 QPS，突发允许 200
limiter := rate.NewLimiter(rate.Limit(100), 200)

// 方式一：非阻塞判断，不等待
if !limiter.Allow() {
    return errors.New("too many requests")
}

// 方式二：阻塞等待（可用于削峰，把请求排队而不是拒绝）
ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
defer cancel()
if err := limiter.Wait(ctx); err != nil {
    return errors.New("rate limit timeout")
}

// 方式三：一次性拿多个令牌（批量场景）
if !limiter.AllowN(time.Now(), 10) { return err }
```

**令牌桶的懒计算实现（面试常考）**：不需要后台 goroutine 定时加令牌，而是在每次请求时按时间差补算：
```go
type TokenBucket struct {
    mu         sync.Mutex
    capacity   float64   // 桶容量
    tokens     float64   // 当前令牌数
    rate       float64   // 每秒放入令牌数
    lastRefill time.Time
}

func (b *TokenBucket) Allow(n float64) bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    now := time.Now()
    // 按经过的时间补发令牌
    elapsed := now.Sub(b.lastRefill).Seconds()
    b.tokens = math.Min(b.capacity, b.tokens+elapsed*b.rate)
    b.lastRefill = now
    if b.tokens >= n {
        b.tokens -= n
        return true
    }
    return false
}
```

**四种算法对比**：

| 算法 | 允许突发 | 输出平滑 | 内存 | 精度 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 固定窗口 | 否 | 否 | 极小 | 差（临界 2 倍） | 粗粒度保护 |
| 滑动窗口 | 部分 | 中 | 小 | 好 | 通用 API 限流 |
| 漏桶 | 否 | 是（恒定） | 小 | 好 | 保护下游、流量整形 |
| 令牌桶 | **是** | 中 | 小 | 好 | **最通用**，网关限流 |

**限流维度与拒绝策略**：按 IP / 用户 ID / 接口 / 租户 / 全局；拒绝方式有「直接报错 429」「排队等待」「降级返回兜底数据（如返回缓存的老数据）」。**降级返回兜底数据往往比直接报错体验好**，这是加分回答。

#### （2）熔断（状态机）与 Go 实现

```go
type State int

const (
    StateClosed State = iota
    StateOpen
    StateHalfOpen
)

type CircuitBreaker struct {
    mu            sync.Mutex
    state         State
    failureCount  int
    successCount  int
    totalCount    int
    failureRate   float64       // 触发熔断的错误率阈值，如 0.5
    minRequests   int           // 统计窗口内最小请求数（样本太少不算）
    openTimeout   time.Duration // 熔断持续时间，如 5s
    halfOpenMax   int           // 半开放行的探测请求数
    openUntil     time.Time
}

func (cb *CircuitBreaker) Allow() error {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    switch cb.state {
    case StateOpen:
        if time.Now().Before(cb.openUntil) {
            return errors.New("circuit breaker is open")
        }
        // 冷却结束，进入半开，放行探测流量
        cb.state = StateHalfOpen
        cb.successCount, cb.failureCount = 0, 0
        return nil
    case StateHalfOpen:
        if cb.successCount+cb.failureCount >= cb.halfOpenMax {
            return errors.New("half-open probe limit reached")
        }
        return nil
    default:
        return nil
    }
}

func (cb *CircuitBreaker) Record(success bool) {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    switch cb.state {
    case StateHalfOpen:
        if success {
            cb.successCount++
            if cb.successCount >= cb.halfOpenMax {
                cb.state = StateClosed // 探测通过，恢复正常
                cb.failureCount, cb.totalCount = 0, 0
            }
        } else {
            cb.state = StateOpen // 探测失败，继续熔断
            cb.openUntil = time.Now().Add(cb.openTimeout)
        }
    case StateClosed:
        cb.totalCount++
        if !success {
            cb.failureCount++
        }
        if cb.totalCount >= cb.minRequests &&
            float64(cb.failureCount)/float64(cb.totalCount) > cb.failureRate {
            cb.state = StateOpen
            cb.openUntil = time.Now().Add(cb.openTimeout)
        }
    }
}
```

**工业级熔断的进阶点**（面试加分）：
- **滑动窗口统计**而不是累计计数，否则历史错误会永远影响判断；
- **慢调用比例**也要熔断，因为超时不算错误但同样拖垮上游；
- **自适应熔断**：go-zero 和 Sentinel 用的是 Google SRE 的算法，不用配阈值，而是根据成功率动态计算丢弃概率，成功率下降时按比例丢弃请求，恢复时按比例放行——`drop_ratio = max(0, (error_ratio - 0.5) / (1 - 0.5))`；
- **熔断粒度**：按下游服务 + 按接口分别熔断，不能一个大熔断器把所有接口都断了。

#### （3）降级

**降级的触发条件**：下游超时/熔断、自身资源耗尽（CPU/内存/连接池）、流量超阈值、依赖的第三方不可用。

**降级的层次**（从轻到重）：
1. **返回兜底数据**：推荐位返回空列表、商品详情返回缓存快照、个人主页返回默认头像；
2. **功能开关**：关闭非核心功能（实时排行榜、评论、点赞数实时刷新）；
3. **读降级**：读走缓存不走库、只返回部分字段、关闭分页深度限制；
4. **写降级**：写请求异步化（落 MQ 后立即返回）、关闭非关键写（浏览历史、埋点）；
5. **限流降级**：整站按比例放行，保住 VIP 用户/核心商户。

**落地要点**：
- 降级开关必须**放在配置中心**（ETCD/Nacos/Apollo），出问题一键切换，不能靠发版；
- 降级必须**有监控和告警**，降级发生后要立刻通知，否则会「静默降级」好几天没人发现；
- 降级方案要**提前演练**，混沌工程注入故障验证降级是否真的生效；
- 降级要**有损但可接受**，必须和产品达成一致——「关掉这个功能用户能接受吗？」

#### （4）超时控制（context）

```go
// 1. 基础超时
ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
defer cancel() // 必须 cancel，否则 context 泄漏（timer 不释放）

// 2. 超时预算逐跳递减
func handleRequest(ctx context.Context) error {
    deadline, ok := ctx.Deadline()
    if !ok {
        ctx, cancel = context.WithTimeout(ctx, time.Second)
        defer cancel()
    }
    // 给下游留 100ms 处理返回，其余传给下游
    rpcCtx, cancel := context.WithTimeout(ctx, time.Until(deadline)-100*time.Millisecond)
    defer cancel()
    return callDownstream(rpcCtx)
}

// 3. 并发调多个下游，任一失败即取消其他
ctx, cancel := context.WithCancel(ctx)
defer cancel()
g, ctx := errgroup.WithContext(ctx)
g.Go(func() error { return callA(ctx) })
g.Go(func() error { return callB(ctx) })
if err := g.Wait(); err != nil { return err }
```

**context 的四个关键认知**（面试考点）：
1. `context.WithTimeout` 的 deadline 会通过 gRPC 的 `grpc-timeout` header **自动跨进程传递**——这是超时预算的基础；
2. **必须 defer cancel()**，否则 context 挂载在父节点上直到父节点结束才释放，长生命周期父 context（如 `context.Background()` 派生后忘记 cancel）会导致内存泄漏；
3. context 应该**作为函数的第一个参数**传递，不要塞进 struct；
4. **context 只用于控制信号（取消/超时）和请求域数据（TraceID、用户身份）**，不要用它传业务可选参数。`WithValue` 的 key 要用自定义类型避免冲突。

**Go 里做超时的其他姿势与坑**：
- `http.Client` 一定要设 `Timeout`，或者更好的是用 `context` 控制单次请求，并给 `Transport` 配 `DialContext` 超时、`ResponseHeaderTimeout`、`IdleConnTimeout`；
- `database/sql` 用 `QueryContext`，不要用不带 context 的版本；
- **超时后服务端不一定停止执行**——客户端超时只是放弃等待，服务端还在跑。所以服务端也要有超时，并且长任务要支持「检查 context 是否已取消」。

#### （5）幂等设计

| 方案 | 实现 | 适用场景 |
| --- | --- | --- |
| **Token 机制** | 进入页面前先调 `GET /token` 拿一个一次性 token（存 Redis），提交时带上，服务端 `DEL` 成功才处理 | 表单提交、下单、支付等用户主动触发的写 |
| **唯一键 / 唯一索引** | `uk(业务维度)`，冲突即视为已处理 | MQ 消费、数据同步、外部回调 |
| **状态机** | `UPDATE ... WHERE status = '待处理'`，判断受影响行数 | 工单流转、订单状态变更 |
| **乐观锁版本号** | `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?` | 并发编辑同一记录 |
| **去重表** | 独立的 `idempotent_record` 表，先插入后处理 | 通用兜底 |
| **幂等中间件** | 框架层统一拦截，按「用户 + 接口 + 业务参数 hash」去重 | 统一治理，go-zero 的 `fx` 包就是干这个的 |

**关键工程细节**：
- **Token 的原子性**：`DEL` 返回 1 才算拿到执行权，`GET` 后 `DEL` 有竞态，应该用 `DEL` 的返回值判断或用 Lua；
- **处理中状态**：如果第一次请求还在处理（未完成），第二次请求应该返回「处理中」而不是重复执行。可以用 `SET key "processing" NX` 三态化（处理中/已完成）；
- **失败要能重试**：Token 被消费了但业务失败，用户重试会一直失败，所以要在业务失败时把 Token 还回去（`SET key 1`）或者用「处理中 + 超时释放」；
- **幂等窗口**：任何幂等都有时效，要明确业务能接受多长的窗口。

#### （6）高并发读写的通用手段

**高并发读**：
- 缓存（本地缓存 + Redis 多级），本地缓存用 `sync.Map` 或 `bigcache`（避免 GC 压力），注意**本地缓存的一致性**（靠 MQ 广播失效或短 TTL）；
- 读写分离（主从），注意主从延迟导致「写后立即读不到」——解决方案是写后一段时间内强制走主库；
- 数据库索引优化、覆盖索引、避免回表；
- 静态资源 CDN、HTTP 缓存头；
- 分页优化：不要 `LIMIT 100000, 20`，用游标（`WHERE id > last_id LIMIT 20`）。

**高并发写**：
- **异步化**：同步链路只做落库，重逻辑走 MQ；
- **批量合并（Batch）**：把 N 个小写入合并成一次批量写（如日志、埋点、计数器），`sqlx` 的批量插入比逐条快几十倍；
- **分库分表**：按用户 ID/租户 ID 哈希分片，注意跨片查询和分布式事务的代价；
- **消息队列削峰**：秒杀场景把请求写入 MQ，后端按自己的节奏消费；
- **锁优化**：缩小事务范围、乐观锁代替悲观锁、`UPDATE ... SET count = count + 1` 用数据库原子操作而不是「读-改-写」。

**容量评估（Little's Law，面试常考）**：
```
并发数 = QPS × 平均响应时间
```
例如 QPS 1000、RT 100ms，则需要的并发处理能力是 100 个。反过来说，如果线程/goroutine 池只有 50，那么理论最大 QPS 就是 `50 / 0.1 = 500`——这就是为什么超时和降级如此重要，RT 一涨，吞吐立刻塌方。

**压测要点**：明确目标（QPS/RT/错误率）、逐级加压找拐点、区分「压力机瓶颈」和「服务瓶颈」、关注 P99 而不是均值、压测环境要隔离、压测后清数据。

### 6.3.2 高频面试 Q&A

**Q1：你们系统做过限流吗？怎么选算法？**

参考回答：
> 做过。选算法的核心是看**要不要允许突发流量**。
> 如果业务本身需要突发（比如页面加载会同时发十几个请求，或者一个批量任务会瞬间调很多次），就必须用**令牌桶**——桶里攒够令牌就能一次性放行一批，同时长期平均速率仍然受控。Go 的 `x/time/rate` 就是标准实现，我们直接用它。
> 如果是要保护一个非常脆弱的下游，希望输出流量绝对平滑，就用**漏桶**，它恒定速率放出，不管上游多猛，下游看到的都是均匀的。
> 如果是简单的接口级限流，**滑动窗口**就够了，比固定窗口好——固定窗口有临界问题，0.9 秒打满 100 次、1.1 秒再打满 100 次，两个窗口都合法但实际 0.5 秒过了 200 次，是限额的两倍。
> 分布式场景下我们是用 Redis + Lua 实现滑动窗口的，把时间戳存 ZSet，脚本里做 `ZREMRANGEBYSCORE` 清理过期、`ZCARD` 计数、`ZADD` 记录，必须整个放在 Lua 里保证原子性，否则 check 和 add 之间有竞态窗口。
> 还有一个实践经验：限流的**拒绝策略**也很重要。直接返 429 用户体验很差，我们的做法是核心接口排队等待（用 `limiter.Wait(ctx)` 加一个短超时），非核心接口返回兜底的缓存数据，这样用户基本无感。

**Q2：熔断和限流的区别？降级怎么落地？**

参考回答：
> 三者目标不同，我习惯用一句话区分：**限流保护自己不被外部打垮，熔断保护自己不被下游拖死，降级保证故障时有损可用**。
> 熔断是个三态机：正常情况下 Closed 放行；统计窗口内错误率超过阈值就转 Open，之后的请求直接快速失败根本不发网络请求；冷却时间过后转 Half-Open，放少量请求探测，成功就恢复 Closed，失败就回到 Open 并重置冷却计时。它最大的价值是「快速失败」——下游挂了的时候最忌讳的是请求都卡在超时上，把上游的 goroutine 和连接池全占满，最后整条链路雪崩。
> 降级的落地我有三条硬性要求：一，**开关放配置中心**，出问题一键切，不能靠发版，发版要几分钟，故障几分钟可能就是几百万损失；二，**必须有告警**，最怕静默降级，功能偷偷降了两天没人知道；三，**方案要提前和产品定义清楚**，哪些功能可以降、降成什么样，技术上不能自己拍脑袋，因为降级是有损的，得业务方认。
> 我们还做过混沌演练来验证降级是否真的生效——手动把某个下游服务停掉，看熔断有没有触发、降级有没有生效、告警有没有发出来。不演练的降级方案基本等于没有。

**Q3：Go 里的 context 你是怎么用的？有什么坑？**

参考回答：
> context 主要用在三个地方：**超时控制、取消传播、请求域数据传递**。
> 超时上最重要的实践是**超时预算逐跳递减**：客户端设 500ms 总预算，第一跳花了 100ms，那传给下游就只剩 400ms，不能每层都设 500ms，否则上游早就放弃了下游还在白跑，占着资源。gRPC 原生支持这个，因为 context 的 deadline 会自动编码成 HTTP/2 的 `grpc-timeout` 头传过去。
> 取消传播上，用 `errgroup.WithContext` 并发调多个下游时，任何一个失败会自动取消其他，避免做无用功。
> 坑有好几个：第一，**`WithTimeout` 必须 defer cancel**，不 cancel 的话子 context 会一直挂在父节点上，定时器不释放，是典型的内存泄漏——这也是 `go vet` 会报的 `lostcancel` 问题。第二，context 要作为函数第一个参数显式传递，不要塞进 struct 里。第三，**`WithValue` 不要滥用**，它只应该传请求域的元数据（TraceID、用户身份）而不是业务可选参数，因为它是隐式的、没有类型安全，而且 key 要用自定义类型避免不同包之间字符串冲突。
> 还有一个容易误解的点：**客户端超时不代表服务端停止执行**。客户端只是不等了，服务端的 goroutine 还在跑。所以长任务一定要主动检查 `ctx.Done()`，在循环里定期判断是否已被取消。

**Q4：接口幂等怎么设计？**

参考回答：
> 我会先分类，不同场景用不同方案。
> **用户主动触发的写操作**（下单、支付、表单提交）用 **Token 机制**：进入页面时先调接口拿一个一次性 token 存 Redis，提交时带上，服务端用 `DEL` 的返回值判断——返回 1 说明是首次，返回 0 说明重复提交。这里有个细节，不能用 `GET` 再 `DEL`，有并发窗口，必须靠 `DEL` 的原子性。
> **MQ 消费和外部回调**用**唯一索引**兜底：我们的销售流水表上有 `uk(产品线, 门店号, POS 流水号)`，重复插入直接捕获 1062 当成功处理。绝不能「先查再插」，那有竞态。
> **状态机类的操作**用 **CAS** 最自然：`UPDATE ticket SET status='处理中' WHERE id=? AND status='待处理'`，看受影响行数是不是 1，为 0 就是已经处理过了。这个方案同时解决了幂等和并发控制两个问题。
> **并发编辑**用**乐观锁版本号**，前端带上查到的 version，更新时 `WHERE version=?`，冲突就让用户刷新重试。
> 另外还有两个容易被忽略的点：一是**Token 消费了但业务失败了怎么办**——用户重试会一直失败，所以业务失败时要把 token 还回去，或者设计成「处理中」这种中间态，超时自动释放；二是**幂等窗口**，任何幂等方案都有时效，Redis 去重一般存 24 小时，过了窗口就挡不住了，要和业务确认能接受多长的窗口。
> 我们 POS 项目里这些方案是组合用的：Redis 做第一层快速拦截，数据库唯一索引做最终兜底。因为可靠性不能建立在缓存之上，缓存的定位永远是性能优化而不是正确性保证。

**Q5：如何设计一个高并发系统？**

参考回答：
> 我会按「分层防御」的思路来答，从上到下六层：
> **第一层，客户端**：按钮防抖、合并请求、静态资源本地缓存、失败重试加退避。
> **第二层，接入层**：CDN 扛静态资源、网关做限流（按 IP/用户/接口多维）、WAF 防攻击、负载均衡。
> **第三层，应用层**：无状态化（会话外置到 Redis）才能水平扩容；服务降级开关；异步化，同步链路只做最必要的落库操作，重逻辑丢 MQ；批量合并减少下游调用次数；连接池和 goroutine 池限制资源上限。
> **第四层，缓存层**：多级缓存（本地 + Redis），热点数据预热，缓存三大问题（穿透用布隆过滤器或空值缓存、击穿用单飞或互斥锁、雪崩用随机过期时间 + 多级缓存）。
> **第五层，存储层**：读写分离、分库分表、索引优化、冷热分离。
> **第六层，容量与保障**：压测找拐点、监控四个黄金指标（延迟/流量/错误/饱和度）、全链路压测、预案演练。
> 另外我想强调一下**理论依据**，因为高并发说到底是资源问题：按 Little's Law，`并发数 = QPS × RT`。所以提升吞吐有两条路——要么加并发数（扩容），要么降低 RT。而 RT 一旦因为某个慢下游从 10ms 涨到 1s，即使并发数不变，吞吐也会掉 100 倍。**这就是超时和熔断在高并发系统里比扩容更重要的原因**。

### 6.3.3 结合项目的话术提示

> **【可结合 LoveSpouse 数字人项目的金币计费作答】**
>
> 「我在数字人项目里做过金币计费，这块天然要求幂等和高并发安全。**扣费绝对不能出现「读-判断-写」**，那样并发下一定超扣。我们的做法是把扣费逻辑收敛成一条数据库原子更新：`UPDATE wallet SET coins = coins - ? WHERE user_id = ? AND coins >= ?`，然后看受影响行数——为 0 说明余额不足，直接返回失败。这一条 SQL 同时解决了并发安全和余额校验两个问题，比先 `SELECT` 再 `UPDATE` 再加锁好得多。
> 另外计费的幂等键用的是「通话会话 ID + 时间片」——因为实时语音是按分钟扣费的，定时结算任务可能因为实例重启重复执行，这个幂等键保证同一分钟只扣一次。这就是典型的**业务唯一键做幂等**。
> 跨实例通话控制这块也有并发问题：用户可能在两台不同实例上发起操作，我们用 Redis 做了跨实例的状态协调和分布式锁，保证同一通会话的控制指令是串行的。」

> **【可结合 POS 数据贯通作答】**
>
> 「高并发这块 POS 项目里的实践是**异步化 + 批量**。数据接入是百万级的日增量，如果每条数据都同步走完整链路肯定扛不住。我们的做法是 MQ 削峰——上游只管往队列里发，消费端按自己的节奏处理；消费端用 prefetch 控制预取数量做自我保护；落库时把攒到的一批数据做批量插入，比逐条插入快一个数量级。这套组合本质上是「用队列把尖峰摊平，用批量把单位成本降下来」。」

> **【可引申到客服系统】**
>
> 「客服系统的高并发特点是**读多写少、且热点集中**。工单查询、知识库检索是高频读，适合多级缓存；工单创建和 IM 消息是高频写，适合异步化加 MQ。坐席分配这种强竞争的操作用 Redis 原子操作或分布式锁保证一致性。SLA 超时升级用延迟队列而不是定时扫全表，避免大表扫描。」

## 6.4 分布式一致性与分布式 ID

### 6.4.1 原理讲解

#### （1）CAP 与 BASE

- **CAP**：一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可兼得。分布式系统里 P 是客观存在的（网络一定会分区），所以真正的选择是 **CP 还是 AP**。
- **BASE**：Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）。这是 AP 系统的实践纲领——不追求强一致，追求最终一致。
- **我们的工程选择**：绝大多数互联网业务（订单、工单、审批）都用**最终一致性**，因为强一致（2PC）的性能和可用性代价太高。**但要注意：涉及钱的场景往往需要 TCC 或更严格的方案。**

#### （2）2PC / 3PC 为什么不用

- **2PC（两阶段提交）**：准备阶段所有参与者锁定资源并投票，提交阶段统一提交/回滚。
  - **同步阻塞**：准备阶段资源被锁定，其他事务要等，性能差；
  - **协调者单点**：协调者挂了，参与者会一直阻塞（数据库层面就是「事务未决」）；
  - **数据不一致**：提交阶段部分参与者网络失败，会出现部分提交部分回滚。
- **3PC**：加了 CanCommit 阶段和参与者超时自动提交，减少阻塞，但**无法解决网络分区导致的不一致**（超时提交可能和协调者的回滚决定冲突）。
- **结论**：XA/2PC 只在极少场景使用（如跨库强一致且并发极低），互联网业务基本都用柔性事务。

#### （3）本地消息表（最实用的方案）

**核心思想**：把「业务操作」和「消息记录」放进**同一个本地事务**，利用数据库的 ACID 保证两者原子，然后靠异步 + 重试保证消息最终投递成功。

```sql
-- 本地消息表
CREATE TABLE `local_message` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `biz_type`     VARCHAR(64)  NOT NULL COMMENT '业务类型',
  `biz_id`       VARCHAR(64)  NOT NULL COMMENT '业务ID（幂等键）',
  `payload`      JSON         NOT NULL COMMENT '消息内容',
  `status`       TINYINT      NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送 2发送失败 3已消费',
  `retry_count`  INT          NOT NULL DEFAULT 0,
  `next_retry_at` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '下次重试时间',
  `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_biz` (`biz_type`, `biz_id`),
  KEY `idx_status_retry` (`status`, `next_retry_at`)

```

```go
func (l *TicketLogic) CreateTicket(ctx context.Context, req *CreateReq) (*Resp, error) {
    var resp *Resp

        }

// 定时任务兜底：扫描待发送/失败的消息重投
func (l *MessageCron) ResendPending() {
    var msgs []model.LocalMessage
    l.db.Where("status IN (0,2) AND retry_count < 10 AND next_retry_at <= ?", time.Now()).
        Limit(200).Find(&msgs)
    for _, m := range msgs {
        if err := l.publish(m); err != nil {
            // 指数退避：10s, 20s, 40s ... 最大 10 分钟
            backoff := time.Duration(math.Min(600, math.Pow(2, float64(m.RetryCount))*10)) * time.Second
            l.db.Model(&m).Updates(map[string]interface{}{
                "status":        2,
                "retry_count":   gorm.Expr("retry_count + 1"),
                "next_retry_at": time.Now().Add(backoff),
            })
            continue
        }
        l.db.Model(&m).Update("status", 1)
    }
}
```

**优点**：不依赖 MQ 的高级特性，任何 MQ 都能用；消息可靠落库，可查可重投。
**缺点**：消息表和业务库耦合（同一个库）；定时任务有延迟（精度取决于扫描间隔）；消息量大时消息表会膨胀，需要定期归档。

#### （4）事务消息（RocketMQ 方案，理解即可）

流程：
1. 生产者发**半消息（Half Message）**给 Broker，消息对消费者不可见；
2. Broker 确认收到后，生产者执行**本地事务**；
3. 生产者根据本地事务结果发送 Commit 或 Rollback；
4. 如果生产者没回（进程挂了），Broker 会**回查**生产者（调用回查接口），生产者检查本地事务状态后回复；
5. Commit 后消息对消费者可见。

**RabbitMQ 没有原生事务消息**。如果非要在 RabbitMQ 上实现类似语义，只能靠**本地消息表 + Confirm**，或者 **RabbitMQ 的 TX 事务（性能极差，不推荐）**。面试时如果被问「RabbitMQ 怎么做事务消息」，正确回答是「RabbitMQ 不提供事务消息，我们用本地消息表实现等效语义，或者换 RocketMQ/Kafka（Kafka 用事务 + 幂等生产者也支持类似语义）」。

#### （5）TCC（Try-Confirm-Cancel）

**三个阶段**：
- **Try**：预留资源（不是直接扣减，而是冻结），如冻结账户 100 元；
- **Confirm**：确认执行，把冻结的钱真正扣除，**Confirm 必须成功且幂等**（要重试）；
- **Cancel**：取消执行，释放冻结的资源，**同样必须幂等**。

**TCC 的三个经典问题**（能答出来是高级信号）：
1. **空回滚**：Try 没执行（比如网络超时导致 Try 请求根本没到），但协调者发起了 Cancel。Cancel 时发现没有对应的冻结记录，此时应该**插入一条空的回滚记录**并返回成功，而不是报错。
2. **幂等**：Confirm/Cancel 会重试，必须靠「事务控制表 + 唯一键」保证只执行一次。
3. **悬挂**：Cancel 比 Try 先到（Try 因为网络延迟在 Cancel 之后才到达），导致资源被冻结但永远不会被释放。解决办法是 Cancel 时记录回滚标记，Try 执行前先检查该标记，有标记就拒绝执行。

**TCC 的适用场景**：涉及资金、库存这类必须严格一致的业务。**代价是业务侵入性极强**——每个参与方都要实现三个接口，还要处理三个经典问题，所以只在核心链路用。

#### （6）Saga 与最大努力通知

- **Saga**：把长事务拆成一串本地事务 `T1, T2, ..., Tn`，每个 `Ti` 有对应的补偿 `Ci`。任一失败就反向执行 `Ci-1 ... C1`。分**编排式（Orchestration，有一个中心协调器）**和**协同式（Choreography，各服务监听事件自行决定）**。适合长流程（如订单履约、审批流）。
- **最大努力通知**：适用于对端不保证可靠的场景（如通知第三方支付结果）。做法是**阶梯式重试 + 对账兜底**，通知不到就让对方来主动查询接口。

**方案选型总结**：

| 方案 | 一致性 | 侵入性 | 性能 | 场景 |
| --- | --- | --- | --- | --- |
| 本地消息表 | 最终一致 | 低 | 好 | **最通用，首选** |
| 事务消息 | 最终一致 | 低 | 好 | 用 RocketMQ 时 |
| TCC | 准强一致 | 极高 | 中 | 资金、库存 |
| Saga | 最终一致 | 中 | 好 | 长流程编排 |
| 最大努力通知 | 最终一致 | 低 | 好 | 对外通知 |

#### （7）分布式 ID

| 方案 | 有序性 | 性能 | 缺点 |
| --- | --- | --- | --- |
| UUID | 无序（v4） | 高 | 无序导致 B+ 树页分裂严重，占用空间大（36 字符），不可读 |
| 数据库自增 | 有序 | 低（单点） | 单库瓶颈，扩展困难；多主需设不同步长 |
| 号段模式（Leaf-segment） | 有序 | 高 | 依赖 DB，服务重启会浪费一段；**推荐** |
| Redis INCR | 有序 | 高 | 依赖 Redis 可用性，需持久化 |
| 雪花算法（Snowflake） | 趋势有序 | 极高 | **依赖时钟**，时钟回拨是硬伤 |
| 美团 Leaf-snowflake | 趋势有序 | 极高 | 用 ZK 管理 workerId + 解决时钟回拨 |

**雪花算法结构（64 位）**：
```
0 | 0000000000 0000000000 0000000000 0000000000 0 | 00000 00000 | 0000000000 00
▲ │                 41 位时间戳（毫秒）              │  10 位机器ID │  12 位序列号
符号位（恒为0，保证正数）
```
- **41 位时间戳**：相对于自定义起始纪元（epoch）的毫秒差，可用约 69 年；
- **10 位机器 ID**：最多 1024 个节点（可拆成 5 位数据中心 + 5 位机器）；
- **12 位序列号**：同一毫秒内最多 4096 个 ID，即单机 **409.6 万 ID/秒**。

```go
package snowflake

import (
    "errors"
    "sync"
    "time"
)

const (
    epoch          = int64(1700000000000) // 自定义起始纪元（毫秒）
    workerIDBits   = uint(10)
    sequenceBits   = uint(12)
    maxWorkerID    = int64(-1) ^ (int64(-1) << workerIDBits) // 1023
    maxSequence    = int64(-1) ^ (int64(-1) << sequenceBits) // 4095
    workerIDShift  = sequenceBits
    timestampShift = sequenceBits + workerIDBits
)

type Node struct {
    mu        sync.Mutex
    workerID  int64
    lastStamp int64 // 上次生成 ID 的时间戳
    sequence  int64
}

func NewNode(workerID int64) (*Node, error) {
    if workerID < 0 || workerID > maxWorkerID {
        return nil, errors.New("worker id out of range")
    }
    return &Node{workerID: workerID}, nil
}

func (n *Node) NextID() (int64, error) {
    n.mu.Lock()
    defer n.mu.Unlock()

    now := time.Now().UnixMilli()

    if now < n.lastStamp {
        // 时钟回拨：小回拨（<5ms）等待追平，大回拨直接报错，避免生成重复 ID
        offset := n.lastStamp - now
        if offset > 5 {
            return 0, errors.New("clock moved backwards")
        }
        time.Sleep(time.Duration(offset) * time.Millisecond)
        now = time.Now().UnixMilli()
    }

    if now == n.lastStamp {
        n.sequence = (n.sequence + 1) & maxSequence
        if n.sequence == 0 {
            // 当前毫秒序列号用尽，自旋等待下一毫秒
            for now <= n.lastStamp {
                now = time.Now().UnixMilli()
            }
        }
    } else {
        n.sequence = 0
    }

    n.lastStamp = now
    return (now-epoch)<<timestampShift | (n.workerID << workerIDShift) | n.sequence, nil
}
```

**时钟回拨的处理方式**（面试高频追问）：
1. **小回拨等待**：回拨几毫秒就 sleep 等追平（最常用）；
2. **大回拨报错**：拒绝服务，让上层重试或告警，绝不能生成可能重复的 ID；
3. **备用 workerId**：预留几个 workerId，回拨时切换（美团 Leaf 的做法）；
4. **记录最大时间戳**：持久化上次生成 ID 的最大时间戳，重启后对比，防止重启后时间倒退。

### 6.4.2 高频面试 Q&A

**Q1：分布式事务有哪些方案？你们怎么选的？**

参考回答：
> 我先说结论：**互联网业务九成场景用最终一致性就够了，首选本地消息表**，因为侵入性最低、不依赖特定中间件、可观测可重投。只有在涉及资金和库存这种不能有中间态的场景，才上 TCC 或更严格的方案。
> 本地消息表的做法是把「业务写」和「消息记录」放在同一个本地事务里提交，用数据库的 ACID 保证两者原子——要么都成功要么都失败。然后异步投递消息，投递失败由定时任务扫描重投，用指数退避控制重试频率。投递成功的消息标记为已发送，另外还有一个「已消费」状态由消费方回调更新，这样还能做对账。
> TCC 我也了解，它是 Try 预留资源、Confirm 确认、Cancel 补偿三阶段。业务侵入性很强，每个参与方都要实现三个接口。而且有三个经典坑必须处理：**空回滚**（Try 没到但 Cancel 到了，Cancel 要插入空记录并返回成功）、**幂等**（Confirm/Cancel 会重试）、**悬挂**（Cancel 比 Try 先到，导致资源被永久冻结，要靠回滚标记让后到的 Try 拒绝执行）。正因为复杂度这么高，我们只在最核心的链路才考虑。
> 2PC 我们不用，因为它是同步阻塞的，准备阶段锁资源，性能太差，而且协调者是单点，挂了参与者会一直挂着。这是典型的用可用性换一致性，代价太大。

**Q2：什么是最终一致性？怎么保证数据最终一致？**

参考回答：
> 最终一致是指系统允许存在短暂的中间不一致状态，但经过一段时间后所有副本/服务的数据会收敛到一致。这是 BASE 理论里的 E。
> 保证手段分三层：
> **第一层是可靠的消息投递**——本地消息表保证「业务成功则消息一定发出」，消费端手动 ACK 保证「消息一定被处理」；
> **第二层是消费幂等**——at-least-once 必然重复，靠唯一索引/状态机 CAS 保证重复消费不产生脏数据；
> **第三层是对账兜底**——这是最容易被忽略但最重要的。消息可能因为超过重试上限、进了死信队列、或者业务逻辑 bug 而永久失败，所以必须有一个**定时对账任务**，比对两边的数据差异并修复。我们的经验是：不管你前面做得多好，最后一定要有对账，因为总有意料之外的失败方式。
> 另外要**明确一致性的时间窗口**，比如「3 秒内一致」和「1 小时内一致」是完全不同的设计。工单状态同步可以容忍几秒，财务报表必须 T+1 对账，这些都影响方案选择。

**Q3：雪花算法了解吗？时钟回拨怎么处理？**

参考回答：
> 雪花算法是 64 位整型 ID，结构是：1 位符号位恒为 0 保证正数，41 位毫秒时间戳（相对自定义纪元的差值，可用约 69 年），10 位机器 ID（最多 1024 个节点），12 位序列号（同毫秒最多 4096 个）。单机理论峰值是 409.6 万 ID/秒，而且因为高位是时间戳，生成的 ID 是**趋势递增**的，对 MySQL 的 B+ 树索引非常友好——这是它比 UUID 最大的优势，UUID 无序会导致频繁的页分裂和随机 IO。
> **时钟回拨是它唯一的硬伤**：如果机器时钟被 NTP 往回校准，可能出现「同一时间戳被生成两次」，产生重复 ID。我的处理是分级的：**小回拨（几毫秒）就自旋等待追平**；**大回拨直接抛错**，宁可服务不可用也不能生成重复 ID，因为重复 ID 造成的脏数据比短暂的不可用严重得多。更进一步的做法是预留几个备用 workerId，检测到回拨就切换一个没被用过的 workerId；还有持久化上次最大时间戳，重启后对比，防止重启时时钟倒退。
> 另一个工程问题是 **workerId 的分配**：K8s 环境下 Pod 的 IP 是动态的，不能写死。我们可以在启动时从 ETCD 或 Redis 申请一个租约化的 workerId，实例宕机后租约到期自动归还，这样动态扩缩容也不会冲突。
> 如果不想自己维护这些，业界有现成的：美团的 Leaf（号段模式 + 雪花模式双支持）、百度 UidGenerator。号段模式虽然性能略低，但不依赖时钟，运维更简单。

### 6.4.3 结合项目的话术提示

> **【可结合 AI 漏洞研判系统作答】**
>
> 「AI 漏洞研判那个项目里有典型的最终一致性场景：多 Agent 工作流跑完之后，要把结果同步到 Jira 和飞书。这两个外部系统的调用不能放在主流程里同步等待——一个是慢，另一个是可能失败。我们的做法就是**工作流产出结果后落库 + 记录一条待同步的消息，然后异步同步**，同步失败进重试队列，超过次数就告警并落到人工处理列表。这就是本地消息表思路的一个变体。
> 而且那个项目里有个更微妙的点：**人工审批环节是有状态的长流程**。审批卡片发到飞书后，用户可能在几小时后才点，中间服务重启过、工作流状态可能已经变了。所以我们做了**审批记录落库 + 状态机 CAS**：只有状态还是「待审批」时才能被审批，重复点击或过期点击都会被拒绝，这保证了长流程下的幂等和一致性。」

> **【可结合 POS 数据贯通作答】**
>
> 「POS 数据贯通里的最终一致场景是**多产品线数据汇聚**：各产品线的数据陆续到达，需要一个统一的上传状态。我们用的是「每条数据一个状态字段 + 定时对账任务」的模式：数据处理完标记状态，上传成功后更新为已完成；如果发现某些记录长时间处于中间状态，对账任务会捞出来重新处理或告警。对账这一步很关键——因为总有你没预想到的失败路径，比如服务在写状态前被 kill，这类问题只能靠对账发现。」

> **【可引申到客服系统】**
>
> 「客服系统里需要分布式事务的地方主要有两个：一，**工单创建 + 通知发送 + SLA 计时启动**，这三个动作必须都成功，我用本地消息表保证；二，**工单与订单/CRM 的数据同步**，跨系统只能最终一致，靠消息加对账。工单 ID 我会用雪花算法生成，因为工单表是高频写入的大表，趋势递增的 ID 能显著减少索引页分裂——如果用 UUID，插入会变成随机 IO，数据量上千万后性能差距非常明显。」

## 6.5 系统设计题（重点）

### 6.5.0 通用答题框架（务必背熟）

系统设计题**没有标准答案，考的是思维过程**。推荐的答题结构：

```
第 1 步：需求澄清（2-3 分钟，最重要，千万别跳过）
   ├─ 功能需求：做什么？核心功能是什么？哪些是必须的？
   ├─ 非功能需求：用户量/QPS/数据量/延迟要求/可用性要求？
   ├─ 边界：要不要支持多租户？要不要支持附件？要不要对接外部？
   └─ 明确「今天重点讨论哪一块」——主动收敛范围，展示掌控力

第 2 步：容量估算（1-2 分钟）
   ├─ 用户量 → 日活 → QPS（峰值 = 均值 × 3~5）
   ├─ 存储：单条数据大小 × 日增量 × 保留期（估算到 GB/TB 级别）
   └─ 带宽、连接数（IM 场景：长连接数 × 单连接内存）

第 3 步：概要设计（5 分钟，画架构图）
   ├─ 分层：接入层 → 应用层 → 领域服务 → 存储层 → 中间件
   └─ 说清每个模块的职责和交互方式（同步 RPC / 异步 MQ）

第 4 步：数据模型（5 分钟，核心表 DDL）
   ├─ 核心实体与关系
   ├─ 表结构 + 索引设计（说清为什么这么建索引）
   └─ 分库分表策略（如果要分）

第 5 步：关键流程（5 分钟，挑 1-2 个讲透）
   └─ 时序：从请求进入到返回，每一步做什么

第 6 步：扩展与高可用（3 分钟）
   ├─ 瓶颈在哪？怎么扩容？
   ├─ 单点故障怎么办？
   └─ 一致性、幂等、监控怎么做
```

**答题技巧**：
- **主动反问**比闷头设计得分高得多（「这个系统的用户量级大概是？我按 10 万坐席设计可以吗？」）；

- **留一个亮点**（某个别人想不到的细节，如 SLA 超时升级、坐席技能路由、工单合并）。

- `idx_assignee_status` 的字段顺序是「过滤性从高到低 + 排序列最后」，覆盖「我的待处理工单按更新时间倒序」这个最高频查询；

**状态机实现（Go）**：
```go
// 状态转移表：把「合法转移」做成数据而不是 if-else
var ticketTransitions = map[string][]string{
    "pending":    {"processing", "closed"},        // 待处理 → 处理中/直接关闭
    "processing": {"resolved", "pending"},         // 处理中 → 已解决/退回待处理
    "resolved":   {"closed", "processing"},        // 待确认 → 关闭/重新处理
    "closed":     {"processing"},                  // 已关闭 → 重开
}

func CanTransfer(from, to string) bool {
    for _, s := range ticketTransitions[from] {
        if s == to { return true }
    }
    return false
}

// 带 CAS 的状态变更：并发安全和幂等一次解决
func (l *TicketLogic) Transfer(ctx context.Context, ticketID int64, from, to string, opID int64) error {
    if !CanTransfer(from, to) {
        return errors.New("非法的状态流转")
    }
    // 关键：WHERE 里带上原状态，受影响行数为 0 说明状态已被别人改了
    res := l.svcCtx.DB.Exec(
        "UPDATE ticket SET status = ?, update_time = NOW(), version = version + 1 "+
        "WHERE id = ? AND status = ?", to, ticketID, from)
    if res.RowsAffected == 0 {
        return errors.New("工单状态已变更，请刷新后重试")
    }
    // 记录流转日志（异步或同事务）
    l.appendFlowLog(ctx, ticketID, from, to, opID)
    // 发事件，驱动通知/SLA/统计
    l.publishEvent(ctx, TicketStatusChangedEvent{TicketID: ticketID, From: from, To: to})
    return nil
}
```

**关键点**：把状态转移表做成**数据**而不是一串 `if-else`，好处是新增状态/流转规则只改配置；用 `WHERE status = from` 的 CAS 保证并发下不会出现两个坐席同时改状态导致的状态错乱。

#### 关键流程一：工单创建

```
1. 校验：参数、客户是否存在、是否重复提交（Token 幂等）
2. 生成工单号：雪花 ID + 业务前缀（TK + 日期 + 序列）
3. 落库：ticket 表插入，status = pending

6. 事务提交后发 MQ 事件 ticket.created

   ├─ 通知服务：站内信/短信/企微 通知坐席
   ├─ SLA 服务：写入延迟队列，到期未响应触发升级
   └─ 统计服务：累加实时看板指标
8. 返回工单号给用户
```

#### 关键流程二：工单分配（坐席分配策略）

**四种策略**（能说出四种并能讲清适用场景是加分项）：
1. **轮询（Round Robin）**：Redis `INCR` 取模坐席数 / 或用环形队列。最简单、绝对均匀，但不考虑坐席当前负载——一个手上压着 20 个工单的坐席和新来的坐席会被分到一样多。
2. **最少活跃会话数（Least Active）**：分配时选「当前处理中工单数最少」的坐席。需要维护坐席的实时负载计数（Redis Hash 或 ZSet，`ZADD` 分数为当前负载，取分数最小的）。**生产环境最常用**。
3. **技能组路由（Skill-based）**：工单先按类型路由到技能组，组内再按最少活跃分配。这是客服系统的标配——退款问题只有退款组能处理。
4. **加权分配**：给坐席配权重（新手 0.5、老手 1.5），按权重比例分配。用于新人培养期。

```go
// 坐席选择：技能组 + 最少活跃（Redis ZSet 实现）
func (s *AssignService) pickAgent(ctx context.Context, groupID int64, exclude []int64) (int64, error) {
    key := fmt.Sprintf("agent:load:%d", groupID)

    // 1. 先取负载最小的前 5 个候选（多取几个，防止选到已下线的）
    candidates, err := s.redis.ZRangeByScore(ctx, key, &redis.ZRangeBy{
        Min: "-inf", Max: "+inf", Offset: 0, Count: 5,
    }).Result()
    if err != nil || len(candidates) == 0 {
        return 0, errors.New("技能组无可用坐席")
    }

    // 2. 过滤掉离线 / 已满 / 在 exclude 列表里的
    for _, c := range candidates {
        agentID, _ := strconv.ParseInt(c, 10, 64)
        if contains(exclude, agentID) { continue }
        if !s.isOnline(ctx, agentID) { continue }              // 在线检查
        if s.currentLoad(ctx, agentID) >= s.maxLoad(agentID) { continue } // 超载检查
        return agentID, nil
    }
    return 0, errors.New("无可分配坐席，进入排队")
}

// 分配成功后，原子增加负载计数
func (s *AssignService) onAssigned(ctx context.Context, groupID, agentID int64) {
    s.redis.ZIncrBy(ctx, fmt.Sprintf("agent:load:%d", groupID), 1, strconv.FormatInt(agentID, 10))
}
```

**分配失败怎么办**：进**排队池**（Redis List 或 ZSet 按优先级 + 时间排序），有坐席释放时（工单关闭）触发一次分配。同时要有**超时兜底**：排队超过 N 分钟仍无人接单，升级给班组长或转人工主管。

#### 关键流程三：SLA 超时升级

```go
// 用延迟队列实现，不要用定时扫全表
// 方案：RabbitMQ TTL + DLX 分档延迟队列
//   sla.5min / sla.30min / sla.2h 三个队列，工单创建时按 SLA 时长投递到对应档位

// 消费者：处理超时事件
func (c *SlaConsumer) HandleTimeout(ctx context.Context, msg amqp.Delivery) error {
    var evt SlaTimeoutEvent
    json.Unmarshal(msg.Body, &evt)

    // 幂等：工单可能已经被处理了
    ticket, err := c.repo.Get(ctx, evt.TicketID)
    if err != nil { return err }
    if ticket.Status == "resolved" || ticket.Status == "closed" {
        return nil // 已处理完，直接 ACK，忽略这次超时
    }
    if ticket.FirstReplyAt != nil {
        return nil // 已响应过，不再升级
    }

    // 分级升级：L1 通知坐席，L2 通知班组长，L3 通知客服总监
    switch evt.Level {
    case 1:
        c.notify(ctx, ticket.AssigneeID, "您有工单即将超时")
        c.scheduleNext(ctx, evt, 30*time.Minute, 2) // 安排下一级
    case 2:
        c.notify(ctx, c.getLeader(ticket.AssigneeID), "工单已超时")
        c.scheduleNext(ctx, evt, time.Hour, 3)
    case 3:
        c.notify(ctx, c.getDirector(), "工单严重超时")
        c.markEscalated(ctx, ticket.ID) // 标记并计入考核
    }
    return nil
}
```

#### 扩展与高可用

| 挑战 | 方案 |
| --- | --- |
| 工单表数据量大（TB 级） | 按 `tenant_id` 分库、按 `create_time` 按月分表；历史数据归档到冷存储 |
| 列表查询慢 | 高频查询走 Redis 缓存「我的工单」第一页；列表页限制最大翻页深度（如 100 页），深翻页用游标 |
| 全文搜索 | 工单标题/内容/客户名搜索走 Elasticsearch，MySQL 只存主数据 |
| 附件存储 | 对象存储（COS/S3），数据库只存 URL；大文件走分片上传 + CDN 加速 |
| 热点工单（如爆款商品问题） | 工单**合并**：相同 `order_no` 或相同 `type + 客户` 的工单自动关联，避免坐席重复处理 |
| 消息可靠性 | 本地消息表 + 手动 ACK + 幂等消费；通知失败进死信队列人工重投 |
| 服务高可用 | 无状态服务水平扩容，ETCD 注册发现，配置中心动态下发；MySQL 主从 + MHA/Orchestrator 切换 |
| 缓存一致性 | 先更新 DB 再删缓存（Cache-Aside），删除失败用 MQ 补偿；本地缓存用短 TTL 兜底 |

**亮点加分项**（主动说出来）：
- **工单合并与关联**：同一客户短时间内提交同类问题，自动合并为一个工单，避免坐席重复劳动；
- **智能预填**：创建工单时用 RAG 检索历史相似工单，自动推荐解决方案，让用户自助解决（**这可以直接结合求职者的 RAG 经验**）；
- **质检与回流**：工单关闭后抽样质检，结果回流到坐席考核和知识库优化；
- **CSAT 回访**：关闭后自动发满意度调查，低分自动触发重开或升级。

#### 关键技术点

**① 长连接接入与路由**
```
连接建立：客户端带 token 连接 → 网关校验 JWT → 注册到本地 ConnManager
         → 把「uid → 网关节点」写入 Redis（route:uid:{uid} = node_ip）
         → 订阅该 uid 的消息 channel（本地订阅 or Redis Pub/Sub）

消息投递：
  1. 消息到消息服务
  2. 查 Redis 路由表拿到接收方所在的网关节点
  3. 如果在本节点 → 直接写连接
     如果不在 → 通过 gRPC 转发到目标节点
  4. 接收方不在线 → 存离线消息（Redis List + MySQL 兜底），上线后拉取

心跳：客户端 30s 发一次 ping，服务端 90s 未收到就断开并清理路由
```

**② 消息可靠性（对标求职者的腾讯 IM 对接经验）**
- **客户端 ACK**：消息投递后客户端回 ACK，服务端收到 ACK 才标记为已送达；未 ACK 的消息在重连后重推；
- **服务端 ACK**：客户端发的消息，服务端落库成功后才回 ACK，客户端超时未收到 ACK 则重发（**所以服务端必须按 `client_msg_id` 做幂等**）；
- **序号（seq）机制**：每个会话维护一个递增 seq，客户端按 seq 排序和去重，发现 seq 不连续就主动拉取缺失消息（**这正是求职者在 LoveSpouse 项目里做过的腾讯 IM 幂等场景**）；
- **消息不丢的三段**：客户端本地存储 + 服务端落库 + 对端 ACK。

**③ 离线消息与多端同步**
```
离线消息：接收方不在线 → 写入 Redis List（保留最近 1000 条）
          → 超过 1000 条或超时 → 标记「消息过多」，上线后走「拉取接口」批量拉
上线拉取：客户端带「本地最大 seq」→ 服务端返回 seq 之后的消息 → 分页拉取
多端同步：一个 uid 多端在线时，给每个端都投递；已读状态用「最大已读 seq」同步
```

**④ 排队与转人工**
```
客户进线 → 机器人接待（RAG 检索知识库）
   ├─ 命中且客户满意 → 会话结束，记录为「机器人解决」
   └─ 未命中 / 客户点「转人工」/ 情绪识别为负面
          ▼
      进入排队池（Redis ZSet，score = 优先级 × 10^10 + 等待时间戳）
          ▼
      分配服务按技能组 + 最少活跃会话数选坐席
          ├─ 分配成功 → 推送给坐席，通知客户「XXX 为您服务」
          └─ 无可用坐席 → 排队等待，定时重试；超过 3 分钟提示客户
```

**排队优先级**：VIP 客户 > 已等待久的 > 普通客户。用 ZSet 的 score 组合「优先级权重」和「等待时长」实现，`ZPOPMIN` 原子取出最高优先级。

**⑤ 会话与工单关联**
- 一次会话解决不了的问题 → 坐席一键「转工单」，把会话记录（含聊天上下文）作为工单内容；
- 工单处理过程中可再次发起会话，会话与工单双向关联（`session.ticket_id` / `ticket.session_id`）；
- 好处：客户不用重复描述问题，坐席能看到完整上下文，质检也有据可查。

**⑥ AI 客服（结合求职者 RAG 经验）**

> **面试话术**：「我在 AI 漏洞研判项目里搭过基于 pgvector 的 RAG 检索链路，那套经验可以直接迁移到智能客服：把历史工单的解决方案、产品文档、FAQ 建成向量库，用户提问先做向量检索 + 关键词检索的混合召回，再把 Top-K 作为上下文交给 LLM 生成回答。关键设计有三点：一，**灰度和兜底**——低置信度的回答不直接给用户，转人工；二，**效果闭环**——坐席对 AI 回答的采纳/修改要回流，作为评估和优化语料的来源；三，**引用可溯源**——回答里带上知识来源，让用户和坐席能核实，这在客服场景对降低幻觉风险特别重要。」

### 6.5.4 设计题答题的通用加分点

无论哪道设计题，最后主动补充这几点都能拉开差距：
1. **权限**：数据权限（谁能看哪些工单/哪些部门的审批单）—— 这正是本岗位的考察点；
2. **审计**：所有关键操作 append-only 记录，谁在什么时候改了什么（合规要求）；
3. **可观测**：核心接口 P99、错误率、MQ 积压、DB 慢查询，全链路 TraceID；
4. **灰度与开关**：新功能配置中心控制，出问题一键回滚；
5. **数据归档**：冷数据定期归档到低成本存储，主库只保留热数据；
6. **成本**：估算存储和机器成本，提一句「按这个量级大概是 X 台机器 / X TB 存储」。

## 6.6 精选 10+ 道架构高频面试题与参考回答

**Q1：你们的服务是怎么做服务治理的？**

> 分四块讲。
> **服务发现**用 ETCD，租约 10 秒自动续约，消费方 watch 前缀拿实例列表缓存在本地，调用时本地负载均衡，避免每次都查注册中心。
> **负载均衡**用 P2C，随机挑两个实例选负载低的那个，比轮询更能自动避开慢节点——轮询会把请求平均打到已经出问题的实例上。
> **超时和熔断**：所有 RPC 都设超时，并且逐跳递减；熔断用 go-zero 内置的自适应熔断，它是基于 Google SRE 的算法按成功率动态算丢弃概率，不用手工配阈值，比固定阈值更适应流量波动。
> **优雅上下线**：启动时先通过健康检查再注册；下线时先从 ETCD 注销、等 3 秒让消费方刷新缓存、再处理完在途请求、最后关闭。少了这个等待窗口，会有一批请求打到已经关闭的实例上产生 connection refused。
> **可观测**：TraceID 全链路透传（包括通过 MQ 传递），统一结构化日志，核心接口 P99 和错误率告警。

**Q2：服务雪崩是怎么产生的？怎么防止？**

> 雪崩的传导链是这样的：服务 D 变慢（比如数据库慢查询）→ 调用 D 的 C 的请求全部卡在等 D 上 → C 的 goroutine 和连接池被占满 → C 也开始拒绝服务 → 调用 C 的 B 也卡住 → 一路往上，最后整个系统不可用。**本质是「同步等待 + 资源有限」导致的连锁耗尽**。
> 防止手段是四层：
> **第一层超时**，让等待有上限，这是最基本也是最重要的；
> **第二层熔断**，下游错误率超阈值就快速失败，不再发请求过去，直接切断传导链；
> **第三层隔离**，给不同的下游配独立的连接池/goroutine 池，一个下游慢不会耗尽所有资源（这就是 Hystrix 线程池隔离的价值）；
> **第四层降级**，真的扛不住时返回兜底数据保住核心功能。
> 另外**限流**也很关键，它是从入口处挡住超出系统能力的流量。还有就是**压测和演练**——不演练的熔断降级配置，真出事的时候大概率是失效的。

**Q3：为什么用消息队列？MQ 带来了哪些问题？**

> 用 MQ 主要解决三个问题：**异步**（非核心链路异步化，缩短响应时间）、**解耦**（生产者不用知道消费者是谁，新增消费方不用改生产端）、**削峰**（把突发流量缓冲起来，下游按自己的节奏消费）。
> 但它引入了新的复杂度，主要是四个：
> 一，**一致性**——本地事务和消息发送不能原子，需要本地消息表或事务消息，还要处理重复消费；
> 二，**顺序性**——多消费者和重试都会打乱顺序，要按业务 key 分区；
> 三，**可靠性**——消息可能丢在生产端、Broker 或消费端，三段都要堵，还有死信和积压的运维成本；
> 四，**可观测性变差**——链路跨了 MQ，TraceID 如果没透传，排查问题会非常痛苦。
> 所以我的态度是：**MQ 不是免费的，能用同步 RPC 简单解决的场景不要上 MQ**。只有确实需要异步、解耦或削峰时才用，而且要提前把可靠性、幂等、监控都设计好。

**Q4：缓存和数据库怎么保证一致性？**

> 首先明确：**强一致做不到，只能做到最终一致**，因为更新缓存和更新数据库不是原子的。
> 主流方案是 **Cache-Aside + 先更新数据库再删除缓存**。为什么是删缓存而不是更新缓存？一是更新缓存可能写入了并发场景下的旧值，二是如果缓存值需要复杂计算，更新它的成本可能很高而它未必会被读到（懒加载更划算）。
> 为什么是先更新数据库再删缓存，不是反过来？考虑「删缓存 → 更新数据库」这个顺序：删除后、更新前，另一个请求读数据库拿到旧值并写回了缓存，之后就一直是脏数据。反过来「更新数据库 → 删缓存」虽然理论上也有一个极小窗口（读请求在更新前查到旧值、在删除后才写入缓存），但这个窗口要求读操作比写操作还慢，概率极低。所以推荐后者。
> 但删除缓存也可能失败，我们有三重兜底：**一，删除失败重试**，把失败的 key 发到 MQ 上异步重试；**二，给缓存设过期时间**，这是最后的保底，即使前面都失败了，过期后也会恢复一致；**三，订阅数据库 binlog**（Canal）异步刷新缓存，把删缓存这个动作与业务代码解耦，更可靠。
> 还有一个容易被忽略的点：**读写分离下的主从延迟**会导致「写后读不到」，我们的做法是关键路径上的「写后一段时间内的读强制走主库」。

**Q5：接口响应慢怎么排查？**

> 我会按「从外到内、从粗到细」的顺序排查：
> **第一步，确定范围**：是全部接口慢还是个别接口？是所有用户还是部分用户？是突然变慢还是逐渐变慢？这决定了是全局问题（如网络、DB、机器资源）还是局部问题（某段代码、某个数据）。
> **第二步，看监控大盘**：CPU、内存、磁盘 IO、网络、GC（Go 看 GC pause 和 goroutine 数）、DB 连接池、依赖服务的 P99。先确认是不是资源瓶颈。
> **第三步，链路追踪**：看 Trace 找出耗时最长的那一段，是自身逻辑、DB、缓存还是下游 RPC。这一步能快速定位到「慢在哪个环节」。
> **第四步，针对性深入**：
>   - 自身逻辑慢 → pprof 的 CPU profile 看火焰图，找热点函数；
>   - DB 慢 → 看慢查询日志，explain 分析执行计划，是不是缺索引、是不是回表太多、是不是锁等待；
>   - 下游 RPC 慢 → 看下游自己的监控，或者是不是网络问题；
>   - 缓存慢 → 看是不是大 key、热 key、或者缓存击穿导致都打到 DB 了。
> **第五步，验证与回归**：改完后要用同样的压测条件验证效果，并观察一段时间防止反弹。
> 我实际排查过一类问题是「goroutine 泄漏」——某个下游超时后没设超时，goroutine 一直堆积，最后内存和调度都受影响。这类问题的特征就是 goroutine 数持续上涨，pprof 的 goroutine profile 一看就能定位。

**Q6：怎么设计一个分布式锁？**

> 基于 Redis 的话，核心是三个：
> **一，加锁要原子**：`SET lock_key unique_value NX PX 30000`，一条命令同时完成「不存在则设置」和「设置过期时间」。绝对不能 `SETNX` 之后再 `EXPIRE`，因为两步之间进程挂了就死锁了。
> **二，value 要是唯一值**（如 UUID），解锁时先比对 value 再删，且比对和删除要用 Lua 保证原子，否则会「解掉别人的锁」——比如 A 的锁超时释放了，B 拿到了锁，A 执行完直接 DEL 就把 B 的锁删了。
> **三，要处理锁续期**：业务执行时间可能超过锁的过期时间，需要看门狗机制（Redisson 的做法）定期续期。
> **Redlock 的争议**：Redis 作者提出的多节点 Redlock 在极端时钟漂移和 GC 停顿下仍可能失效，Martin Kleppmann 有专门的文章质疑。我的实践观点是：**如果对正确性要求极高，用 ETCD 或 ZooKeeper 的锁**（基于 Raft/ZAB，有 fencing token 概念更安全）；如果用 Redis，要做好「锁失效后的兜底」——也就是业务本身要幂等，不能假设锁是绝对安全的。
> 实际上我们项目里用得更多的是**用数据库唯一索引或 CAS 代替分布式锁**——比如扣金币用 `UPDATE ... WHERE coins >= ?`，工单状态流转用 `WHERE status = ?`，这类方案比分布式锁更简单也更可靠，因为不依赖外部组件的可用性。

**Q7：分库分表怎么分？分了之后有什么问题？**

> **先说时机**：不要过早分。单表在千万级以内、加了合适的索引后性能通常没问题。真正需要分表的信号是：单表超过 2000 万行且查询明显变慢、单库磁盘容量或写入 QPS 到瓶颈、DDL 变得不可执行（加个字段锁表几小时）。
> **怎么分**：垂直拆分（按业务拆库、按字段冷热拆表）+ 水平拆分（按分片键）。分片键的选择是最关键的——要选**查询中一定会带上的、且分布均匀的字段**。工单系统选 `tenant_id`（多租户天然隔离，不会有跨租户查询），消息表选 `session_id`（会话内消息一定在同一分片，能保证顺序），日志类按时间分片（便于归档和删除）。
> **分片算法**：范围分片（易于扩容和归档，但可能热点）、哈希取模（分布均匀，但扩容要重新分布）、一致性哈希（扩容影响小）、雪花 ID 里嵌入分片位。
> **分了之后的问题**：跨分片查询和分页（要么做冗余表，要么用 ES，要么限制只能按分片键查）、跨分片聚合（走汇总表或离线计算）、分布式事务（本地消息表 + 最终一致）、全局唯一 ID（雪花算法）、扩容（一致性哈希或双写迁移）。
> **我的建议**：**能用分区表、读写分离、加索引、归档解决的，就不要分库分表**，因为它的运维成本和业务改造成本非常高。分之前先把「不分」的手段用尽。

**Q8：什么是无状态服务？为什么要无状态？**

> 无状态是指**服务实例本身不保存请求相关的会话状态**，所有状态都外置到共享存储（Redis、DB、对象存储）。这样任何实例都能处理任何请求，可以随意地增加、减少、重启实例。
> 为什么要无状态？因为**水平扩容的前提是无状态**。如果登录态存在本地内存，用户第一次请求打到实例 A，第二次打到实例 B 就掉登录了，那就得靠会话粘滞（sticky session），而粘滞会导致负载不均、扩缩容时用户掉线、实例故障时用户全部重新登录。
> 落地做法：会话/登录态放 Redis（JWT 更彻底，状态在 token 里）；文件上传直接传到对象存储；本地缓存要么去掉，要么接受不一致并设短 TTL；定时任务要加分布式锁避免多实例重复执行（或者用选主机制）。
> 我做的多个服务都是无状态设计，Docker 部署后可以随意扩缩容。有个细节：**优雅停机是无状态服务的必备配套**——收到 SIGTERM 后要停止接新请求、处理完在途请求、注销服务注册，否则滚动发布时会有一批请求失败。

**Q9：如何做容量规划？**

> 核心公式是 Little's Law：**并发数 = QPS × 平均响应时间**。比如目标 QPS 1000、RT 100ms，就需要 100 的并发处理能力。
> 规划步骤：
> **一，估算流量**：从业务指标推导。比如 100 万日活，每人每天访问 20 次，日请求 2000 万，平均 QPS 约 230，按峰值系数 5 算需要支撑 1150 QPS。
> **二，估算单机能力**：压测得到单实例的 QPS 上限（不是拍脑袋），一般按「压测值的 50%~70%」作为安全水位。
> **三，算实例数**：`实例数 = 峰值QPS / 单机安全QPS`，再考虑冗余（至少 N+1，重要服务 N+2 或跨可用区）。
> **四，估算存储**：单条数据大小 × 日增量 × 保留天数，再乘索引膨胀系数（1.5~2 倍），最后加上备份空间。
> **五，留缓冲**：实际资源使用率控制在 60% 以下，给突发流量和故障转移留空间。
> 关键是**压测要真实**：用生产数据量级的测试数据集、模拟真实调用比例、压到拐点找到真正的瓶颈，并且要区分「压力机瓶颈」和「服务瓶颈」。还有一个经验是**全链路压测**，单服务压测没问题不代表整条链路没问题，瓶颈往往在你不关注的那个依赖上。

**Q10：单体、微服务、服务网格怎么选？**

> 我的判断标准是**团队规模和系统复杂度**，而不是技术先进性。
> **单体**适合团队 10 人以内、业务边界还不清晰、需要快速迭代的阶段。它的开发调试体验最好（一个进程、一次启动、断点随便打）、事务简单、部署简单。**大多数创业项目应该从单体开始，而且是模块化单体**——代码层面分模块、模块间只通过明确的接口调用，为将来拆分留好接缝。
> **微服务**适合团队规模到了一定程度（比如超过 30 人）、业务边界已经稳定、不同模块的性能和扩缩容诉求差异很大时。它的收益是独立部署、独立扩缩容、技术异构、故障隔离；代价是分布式事务、调用链复杂度、运维成本、排查难度。
> **服务网格（Istio 等）**把服务治理能力（流量管理、mTLS、可观测）下沉到 Sidecar，业务代码不用管。它解决的是「多语言技术栈下的统一治理」问题，代价是运维复杂度显著上升（控制面、数据面、Sidecar 资源开销、延迟增加一两毫秒）。**除非是多语言大集群且团队有专门的平台工程能力，否则不建议上**。
> 我的实践观点是：**先模块化单体，等边界稳定和团队变大后再拆微服务，服务网格等到确实有跨语言治理需求时再说**。我们 POS 项目用微服务是因为确实存在多产品线适配 + 数据量差异大的问题，而不是因为微服务「更先进」。

**Q11：线上 CPU 100% 怎么排查？**

> **第一步，定位进程**：`top` 找到 CPU 最高的进程 PID，`top -Hp <pid>` 找到具体哪个线程（Go 里是哪个 OS 线程）。
> **第二步，看是什么类型的 CPU 消耗**：
>   - 是 `us`（用户态）高 → 业务代码在算，多半是死循环、热点计算、序列化、正则回溯；
>   - 是 `sy`（内核态）高 → 系统调用频繁，可能是网络 IO 密集、上下文切换过多；
>   - 是 `wa`（IO 等待）高 → 其实是磁盘或网络瓶颈，不是 CPU 真的忙。
> **第三步，Go 程序直接用 pprof**：`go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30`，看火焰图找热点函数。同时看 `/debug/pprof/goroutine?debug=2` 确认是不是 goroutine 数量暴涨（比如某个循环里起 goroutine 没有退出条件）。
> **第四步，常见根因**：
>   - 死循环或正则回溯（Go 的 regexp 是 RE2 不会回溯，但如果用了其他库就难说）；
>   - 频繁 GC（内存分配过多）→ 看 GC 指标，用 `sync.Pool` 或减少小对象分配；
>   - 锁竞争激烈 → `mutex profile` 看；
>   - 大量 goroutine 调度 → 看 goroutine 数；
>   - 序列化开销（大量 JSON 编解码）→ 换 Protobuf 或优化结构体。
> **第五步，应急先把问题止血**（重启、限流、扩容、切流量），再慢慢定位根因——线上问题的第一原则是**先恢复再排查**。

**Q12：你参与过架构设计吗？讲讲你做过的一次架构决策。**

> **【这道题一定要用 STAR 讲一个真实案例，推荐用 POS 数据贯通】**
>
> 「讲一个我在 POS 数据贯通项目里做的架构决策。**背景**是公司有五六条 POS 产品线，每条产品线的销售流水、发票、商品档案的字段定义都不一样——有的流水号叫 `sale_no` 有的叫 `order_id`，金额有的用分有的用元，日期格式也有三种。原来的做法是每接一条新产品线就复制一套代码改一改，导致同样的逻辑有五六份，改一个 bug 要改五遍还经常漏。
> **我的方案**是做一层**统一接入层 + 适配器模式**。首先定义一套内部统一的 Protobuf 模型来归一化所有产品线的数据；然后抽象一个 `DataAdapter` 接口，每个产品线一个实现，负责把自家格式翻译成统一模型；核心的数据处理、校验、上传逻辑只写一份，对所有产品线共用。消息路由上，我们用 RabbitMQ 的 topic 交换机，routing key 设计成 `pos.{产品线}.{数据类型}`，队列按数据类型绑通配符。
> **效果**是接入一条新的存量产品线，现在只需要实现一个适配器类，核心链路零改动，工作量从原来的两周降到两三天，也不会再出现「某个产品线的 bug 修复漏了另一条产品线」这类问题。同时因为我们用的是 go-zero 微服务 + gRPC，新增产品线的适配器可以独立部署和扩容，不影响其他产品线。
> **这个决策背后的原则是依赖倒置和开闭原则**——把变化的部分（产品线差异）和不变的部分（数据处理流程）隔离开。事后复盘我觉得可以改进的是，适配器的配置化程度还可以更高，有些简单的字段映射其实可以用配置而不是写代码。」

| --- | --- |
| 服务拆分 | 按业务能力 + 变更频率拆，用「变更耦合半径」判断粒度 |
| ETCD | Lease 租约 + KeepAlive 续约 + Watch 推送；下线先注销再停机 |

| 熔断 | Closed → Open → Half-Open 三态机；保护调用方，快速失败 |
| 降级 | 开关放配置中心、必须有告警、方案要产品确认、要演练 |
| MQ 可靠性 | 生产 Confirm + Return、Broker 持久化、消费手动 ACK，三段都要堵 |
| MQ 幂等 | 业务唯一键 + 数据库唯一索引兜底；不能「先查后插」 |
| MQ 顺序 | 先问「全局顺序还是分区顺序」；按业务 key 哈希到不同队列 |
| 死信/延迟 | 失败隔离防毒消息；延迟优先用定时扫表，TTL+DLX 要分档建队列 |
| 分布式事务 | 首选本地消息表（最终一致）；TCC 用于资金库存但要处理空回滚/悬挂 |
| 分布式 ID | 雪花算法趋势递增；时钟回拨小等待大报错；workerId 用 ETCD 租约分配 |
| 系统设计 | 需求澄清 → 容量估算 → 架构图 → 数据模型 → 关键流程 → 扩展高可用 |
