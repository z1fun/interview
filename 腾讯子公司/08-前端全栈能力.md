## 一、Vue 3 核心原理

### 1.1 响应式系统：从 `Object.defineProperty` 到 `Proxy`

**要解决的问题**：数据变了，视图怎么知道要更新？

Vue 的核心思路是「数据劫持 + 依赖收集 + 派发更新」三步：

1. **数据劫持**：把数据对象的读写拦截下来。
2. **依赖收集**：谁读了这个数据（哪个渲染函数、哪个 computed），就把谁记下来。
3. **派发更新**：数据被写的时候，通知所有记下来的依赖重新执行。

Vue 2 和 Vue 3 的差别，**全部集中在第一步的手段上**。

#### Vue 2：`Object.defineProperty`

```js
// Vue 2 简化版响应式
function defineReactive(obj, key, val) {
  const dep = []                       // 该属性的依赖集合（Watcher 列表）
  Object.defineProperty(obj, key, {
    get() {
      if (Dep.target) dep.push(Dep.target)   // 依赖收集：谁在读我
      return val
    },
    set(newVal) {
      if (newVal === val) return
      val = newVal
      dep.forEach(w => w.update())           // 派发更新
    }
  })
}
```

**Vue 2 的四个硬伤**（这就是 Vue 3 换 Proxy 的原因，面试必答）：

| 问题 | 说明 |
|---|---|
| **无法监听新增/删除属性** | `defineProperty` 只能劫持**已存在**的属性，所以 `obj.newKey = 1` 不会触发更新，必须用 `Vue.set` / `Vue.delete` |
| **无法监听数组下标赋值和 length 修改** | `arr[0] = 1`、`arr.length = 0` 不触发；Vue 2 只能重写数组的 7 个变更方法（push/pop/shift/unshift/splice/sort/reverse）来打补丁 |
| **必须递归遍历整个对象** | 初始化时要深度遍历所有属性逐个 `defineProperty`，对象大时初始化慢、内存占用高（每个属性一个 Dep 实例） |
| **不支持 Map / Set / WeakMap** | 这些数据结构无法被劫持，需要额外实现 |

#### Vue 3：`Proxy` + `Reflect`

```js
function reactive(target) {
  return new Proxy(target, {
    get(t, key, receiver) {
      track(t, key)                     // 依赖收集
      const res = Reflect.get(t, key, receiver)
      // 惰性代理：只有真正访问到嵌套对象时，才递归代理（对比 Vue2 的初始化全量递归）
      return isObject(res) ? reactive(res) : res
    },
    set(t, key, val, receiver) {
      const old = t[key]
      const ok = Reflect.set(t, key, val, receiver)
      if (old !== val) trigger(t, key)  // 派发更新
      return ok
    },
    deleteProperty(t, key) {
      const ok = Reflect.deleteProperty(t, key)
      trigger(t, key)                   // 删除也能监听
      return ok
    }
  })
}
```

**Proxy 带来的关键改进**：

| 维度 | Vue 2 (defineProperty) | Vue 3 (Proxy) |
|---|---|---|
| 拦截范围 | 只能是对象的属性（get/set） | 整个对象，13 种拦截行为（get/set/has/deleteProperty/ownKeys/getPrototypeOf…） |
| 新增/删除属性 | 不支持，需 `$set` | 天然支持 |
| 数组下标 / length | 不支持 | 天然支持 |
| 嵌套对象 | 初始化时递归全量劫持 | **惰性**：访问到才代理（`get` 里递归），初始化快 |
| Map / Set | 不支持 | 支持（`collectionHandlers` 专门处理） |
| 兼容性 | IE9+ | 不支持 IE（无法 polyfill，因为 Proxy 是语言级能力） |
| 性能 | 初始化慢、运行快 | 初始化快、按需代理 |

**面试官最爱的追问**：「Proxy 有没有缺点？」
参考回答：有两点。**一是不支持 IE**，而且 Proxy 没法被 polyfill，所以 Vue 3 直接放弃了 IE11；这也是很多老项目留在 Vue 2 的真实原因。**二是 `Proxy` 返回的是代理对象，不是原对象**，所以 `reactive(obj) !== obj`，把原对象和代理对象混用会出现「改了没反应」的问题；Vue 3 内部用 `WeakMap` 做了缓存（`reactiveMap`），保证同一个原对象永远返回同一个代理，同时在 `toRaw` 里保留反查表。

#### `reactive` 与 `ref` 的区别（源码级差异）

- `reactive`：基于 `Proxy`，**只能代理对象/数组/Map/Set**，对基本类型无效。
- `ref`：本质是 `RefImpl` 类，内部用 `get value / set value` 的**访问器属性**做劫持（因为基本类型没法 Proxy）。
  - 如果传入的是对象，`ref` 内部会调 `reactive` 包一层（`toReactive`）。
  - 模板中 `ref` 自动解包（因为模板编译后访问的是 `_ctx.xxx`，走了 proxyRefs）；但在 `<script setup>` 的 JS 里必须 `.value`。
- 为什么语言层面需要 `ref`？**因为 Proxy 无法劫持一个数字**。`let a = 1` 是值语义，没有任何钩子可以挂，所以只能用对象包一层。

```ts
import { ref, reactive, toRefs } from 'vue'

// ref：基本类型 + 对象都能用，脚本里必须 .value
const count = ref(0)
count.value++                          // 模板里可以写 {{ count }}

// reactive：只能对象，不需要 .value，但解构会丢失响应式
const state = reactive({ name: 'a', age: 1 })
const { name } = state                 // ❌ 丢失响应式：解构出来的是普通字符串
const { name: nameRef } = toRefs(state) // ✅ toRefs 转成 ref，保持响应式

// 为什么解构会丢？因为响应式挂在 Proxy 的 get 上，
// 解构时执行了 get 拿到值就断开了引用，之后改 state.name 与 name 这个局部变量无关。
```

> **话术提示**：可结合商云前台（Vue 3 + TS）作答——
> 「商云前台里我用的就是 `<script setup>` + ref/reactive 这套。印象比较深的是收银主界面有个订单明细列表，
> 我一开始用 `reactive` 存整个订单对象，做打印小票时需要对明细解构传参，结果打印出来的是旧数据——
> 后来定位到是解构丢了响应式，改成 `toRefs` / 直接用 `storeToRefs` 从 Pinia 取，问题解决。
> 这类问题看文档好像很浅，但真踩过一次就理解为什么 Vue 3 要同时提供 ref 和 reactive 两套 API。」

### 1.2 依赖收集与触发更新：track / trigger / effect

面试如果只答「Proxy 拦截」，深度是不够的。**完整的链路是：effect → track → trigger**。

```js
// 全局：当前正在执行的副作用函数
let activeEffect = null

// 副作用栈 + 嵌套处理
const effectStack = []

function effect(fn) {
  const _effect = function () {
    if (!effectStack.includes(_effect)) {
      try {
        effectStack.push(_effect)
        activeEffect = _effect
        return fn()                  // 执行期间所有被读到的属性都归我
      } finally {
        effectStack.pop()
        activeEffect = effectStack[effectStack.length - 1]
      }
    }
  }
  _effect()
  return _effect
}

// 依赖表：WeakMap<target, Map<key, Set<effect>>>
const targetMap = new WeakMap()

function track(target, key) {
  if (!activeEffect) return            // 不在任何 effect 里读取，不需要收集
  let depsMap = targetMap.get(target)
  if (!depsMap) targetMap.set(target, (depsMap = new Map()))
  let dep = depsMap.get(key)
  if (!dep) depsMap.set(key, (dep = new Set()))
  dep.add(activeEffect)                // Set 天然去重
}

function trigger(target, key) {
  const depsMap = targetMap.get(target)
  if (!depsMap) return
  const dep = depsMap.get(key)
  dep && dep.forEach(e => e())         // 通知所有依赖重新执行
}
```

**为什么依赖表是 `WeakMap<target, Map<key, Set<effect>>>` 三层结构？**

- 第一层 `WeakMap` 的 key 是**原对象**：用 WeakMap 是为了**不阻止垃圾回收**——如果组件销毁后对象没人引用了，依赖表不应该把它强引用住（内存泄漏）。WeakMap 的 key 是弱引用。
- 第二层 `Map` 的 key 是**属性名**：精确到属性级别，`obj.a` 变化不应该触发只用了 `obj.b` 的组件。
- 第三层 `Set` 的 key 是**副作用函数**：一个属性可能被多个组件/计算属性依赖，用 Set 自动去重，避免同一 effect 重复执行。

**Vue 3 的调度（scheduler）——为什么改数据不会立刻重渲染？**

```js
// 渲染 effect 带 scheduler：不是立即执行，而是推入队列
const queue = new Set()
let isFlushPending = false

function queueJob(job) {
  queue.add(job)                        // Set 去重：同一组件一次更新只渲染一次
  if (!isFlushPending) {
    isFlushPending = true
    Promise.resolve().then(flushJobs)   // 微任务批量执行 —— 这就是 nextTick 的基础
  }
}

function flushJobs() {
  try {
    queue.forEach(job => job())
  } finally {
    queue.clear()
    isFlushPending = false
  }
}
```

三个工程结论（这些才是面试加分点）：

1. **异步批量更新**：同一轮同步代码里改 100 次数据，只渲染 1 次（Set 去重 + 微任务批处理）。
2. **`nextTick` 的本质**：`nextTick(cb)` 就是把 cb 放到 `flushJobs` 之后的微任务里，保证拿到的是**更新后的 DOM**。
3. **渲染顺序**：`flushJobs` 前会按组件 id 排序（父组件 id 更小先渲染），保证父先于子更新。

### 1.3 组合式 API 与 `<script setup>`

**为什么要有组合式 API？** 选项式 API（Options API）的问题是**逻辑按选项类型分片**：一个「搜索功能」的状态在 `data`、方法在 `methods`、监听在 `watch`、生命周期在 `mounted`，一个功能被拆到四个地方。功能一多，读代码要来回跳。

组合式 API 的核心是**按功能组织代码 + 逻辑复用（组合函数）**。

```vue
<script setup lang="ts">
import { ref, computed, watch, onMounted, onUnmounted } from 'vue'

// 1. 定义：<script setup> 中顶层变量自动暴露给模板，不需要 return
const keyword = ref('')
const list = ref<Order[]>([])

// 2. 派生状态：computed 有缓存，依赖不变不重新计算
const filtered = computed(() => list.value.filter(i => i.no.includes(keyword.value)))

// 3. 副作用：watch 需要显式指定源，可拿到新旧值；watchEffect 自动收集依赖
watch(keyword, (nv, ov) => { console.log('从', ov, '变成', nv) }, { immediate: true })
watch(() => list.value.length, n => console.log('数量变化', n))

// 4. 生命周期：直接在 setup 里调用（不用写 beforeCreate/created，它们被 setup 取代）
onMounted(() => { /* 拉数据 */ })
onUnmounted(() => { /* 清理定时器、取消事件监听，防内存泄漏 */ })
</script>
```

**`watch` 与 `watchEffect` 的区别（高频）**：

| | `watch` | `watchEffect` |
|---|---|---|
| 依赖收集 | 显式指定（ref / getter / 数组） | 自动收集回调里用到的响应式数据 |
| 是否立即执行 | 默认否，`immediate: true` 才立即 | 立即执行一次 |
| 能否拿旧值 | 能（回调第三个参数是 `onCleanup`，第二个是 oldValue） | 不能 |
| 适用 | 依赖明确、需要新旧值对比、需要惰性 | 依赖多而变化逻辑简单 |

**组合函数（Composable）——这是组合式 API 最大的价值，面试要主动讲**：

```ts
// usePermission.ts：把「权限判断」抽成可复用逻辑
import { computed } from 'vue'
import { useUserStore } from '@/stores/user'

export function usePermission(pageCode: string) {
  const userStore = useUserStore()
  // 商云前台是 POS 桌面应用，权限来自后台下发的角色-功能点映射
  const canRead  = computed(() => userStore.perms.includes(`${pageCode}:read`))
  const canWrite = computed(() => userStore.perms.includes(`${pageCode}:write`))
  const canPrint = computed(() => userStore.perms.includes(`${pageCode}:print`))
  return { canRead, canWrite, canPrint }
}

// 组件里：一行复用，且每个组件实例的状态互相独立
const { canWrite } = usePermission('selfService')
```

> **话术提示**：可结合商云前台作答——
> 「商云前台支持**自助模式**和**收银员模式**两种形态，同一个页面在不同模式下能看到的按钮不一样。
> 我把权限判断抽成了 `usePermission` 组合函数，返回 `canRead/canWrite/canPrint` 三个 computed，
> 页面里用 `v-if="canPrint"` 控制。好处有两层：一是逻辑只写一遍，十几个页面复用；
> 二是组合函数内部用的是 `ref/computed`，每个组件实例调用都是独立状态，不像 mixin 那样会互相污染、也说不清变量从哪来——
> 这正是组合式 API 相对 Vue 2 mixin 最实在的收益。」

### 1.4 虚拟 DOM 与 diff 算法

#### 为什么需要虚拟 DOM

真实 DOM 操作昂贵，不是因为「改一个 DOM 慢」，而是因为**不确定要改哪些**，只能粗暴地整体替换（`innerHTML`）导致大量重排重绘。虚拟 DOM 的价值是：

1. **把 DOM 操作变成 JS 对象的比较**（JS 计算远比 DOM 操作便宜）。
2. **跨平台能力**：同一份 vnode 树可以渲染成 DOM（浏览器）、原生控件（Weex/小程序）、甚至 Canvas。商云前台的 Wails 应用就是「同一份 Vue 代码跑在 WebView 里」。
3. **提供声明式编程的抽象层**：开发者只描述「UI 应该长什么样」，diff 负责算最小更新。

#### 虚拟节点的结构

```ts
// 简化后的 VNode 类型
interface VNode {
  type: string | Component        // 'div' 或组件对象
  props: Record<string, any> | null
  children: string | VNode[] | null
  key: string | number | null     // diff 的身份标识
  el: Node | null                 // 对应的真实 DOM
  shapeFlag: number               // 类型标记位：元素/文本/组件/数组子节点…（位运算）
  patchFlag: number               // 编译期注入的动态特性标记（Vue 3 独有）
  dynamicProps: string[] | null   // 需要动态更新的 props 名
}
```

#### Vue 2 的 diff：双端对比

Vue 2 的核心是**同层比较**（不跨层级移动，因为跨层移动成本高于重建） + **双端对比**。

```
旧：a  b  c  d
新：a  c  d  e

四指针：oldStart(a) / oldEnd(d) / newStart(a) / newEnd(e)

① oldStart == newStart (a==a) → 复用，双头指针都后移
② 现在 oldStart=b, oldEnd=d, newStart=c, newEnd=e
   比较 oldEnd==newEnd? (d==e) ✗
   比较 oldStart==newEnd? (b==e) ✗
   比较 oldEnd==newStart? (d==c) ✗
   → 都不匹配，用 key 去旧节点 map 里找 newStart(c)，找到就移动复用，找不到就新建
③ 循环直到一方遍历完，剩下的一批批量新增或批量删除
```

双端对比的意义：**把「首尾常见变动」（数组头部插入、尾部追加）变成 O(1) 的指针移动**，避免整表移位。缺点是**中间插入一个节点时仍然会做较多移动**（没有求最小移动序列）。

#### Vue 3 的 diff：编译期 PatchFlag + 最长递增子序列

Vue 3 的思路是「**能编译期确定的，就不要留到运行时算**」。

**第一步：PatchFlag 缩小比较范围。** 编译器把动态节点标记出来：

```vue
<template>
  <div class="static">
    <span>纯静态，永远不会变</span>
    <span :id="dynamicId">{{ msg }}</span>  <!-- PatchFlag = TEXT | PROPS -->
  </div>
</template>
```

旧节点和新节点 patch 时，看到 `PatchFlag & TEXT` 才去比 children 的文本，看到 `PROPS` 才去比 props，**静态部分直接跳过**。对比 Vue 2 运行时全量递归比对，Vue 3 的 diff 复杂度从「与模板大小相关」变成「与动态节点数量相关」。

**第二步：求最长递增子序列（LIS）确定最小移动。** 当没有 key 匹配的快速路径时，Vue 3 会：

1. 建立 `newIndexToOldIndexMap`（新节点 key → 旧节点下标）。
2. 对新节点的下标序列求**最长递增子序列**——LIS 中的节点**相对顺序没变，不需要移动**。
3. 只移动不在 LIS 中的节点（从后往前遍历，逐个 patch + insertBefore）。

```ts
// 求最长递增子序列（返回下标数组）——Vue 3 源码思路：贪心 + 二分 + 回溯
function getSequence(arr: number[]): number[] {
  const p = arr.slice()          // 记录前驱，用于最后回溯出完整序列
  const result = [0]             // result 存的是「下标」，对应值单调递增
  let i, j, u, v, c
  const len = arr.length
  for (i = 0; i < len; i++) {
    const arrI = arr[i]
    if (arrI !== 0) {            // 0 表示新增节点，不参与
      j = result[result.length - 1]
      if (arr[j] < arrI) {       // 比当前最长序列的末尾还大 → 直接追加
        p[i] = j
        result.push(i)
        continue
      }
      // 二分找到第一个 >= arrI 的位置替换（贪心：让序列增长潜力最大）
      u = 0; v = result.length - 1
      while (u < v) {
        c = (u + v) >> 1
        if (arr[result[c]] < arrI) u = c + 1
        else v = c
      }
      if (arrI < arr[result[u]]) {
        if (u > 0) p[i] = result[u - 1]
        result[u] = i
      }
    }
  }
  // 回溯出正确下标序列
  u = result.length; v = result[u - 1]
  while (u-- > 0) { result[u] = v; v = p[v] }
  return result
}
```

时间复杂度 **O(n log n)**，对比「暴力找最小移动次数」的 O(n²) 或 LCS 的 O(n²)。

**面试必须能说清的一句话结论**：
> Vue 2 是**运行时**的双端对比，靠首尾指针减少移动；Vue 3 是**编译时 + 运行时**协同——编译期用 PatchFlag 和 Block Tree 把「要比较的节点」圈出来，运行时只在这些动态节点上做 diff，并用最长递增子序列求出最小移动集。所以 Vue 3 的 diff「快」不是某一处算法变快了，而是**需要比较的规模变小了**。

#### key 的作用（超高频，答错就扣分）

- **有 key**：diff 用 key 建立新旧节点的对应关系，能正确复用和移动节点，保证**组件状态（输入框内容、组件内部 state）跟随节点而不是跟随位置**。
- **无 key（或 key 用 index）**：退化成「就地复用」——按下标逐个 patch，位置对不上的时候会**错误复用**组件状态。
- **经典 bug**：列表 `[A, B, C]` 用 index 当 key，删除 A 后变成 `[B, C]`，Vue 认为是「第 0 项从 A 变成 B」，于是复用了 A 的组件实例并只更新 props，**输入框里已输入的内容会串行**。
- **index 作为 key 什么时候可以接受**：列表**只读不增删不排序**（纯展示）。否则一律用业务唯一 id。

### 1.5 编译优化：静态提升 / Block Tree / PatchFlag

Vue 3 的编译器（`@vue/compiler-dom`）在编译 `<template>` 时做三件事：

```vue
<template>
  <div>
    <p class="a">静态文本</p>                 <!-- ① 静态提升 -->
    <p :title="t">动态</p>                    <!-- ② PatchFlag=PROPS -->
    <p>{{ msg }}</p>                          <!-- ② PatchFlag=TEXT -->
  </div>
</template>
```

**① 静态提升（hoistStatic）**：纯静态节点被提升到 `render` 函数**外面**，只创建一次 vnode，后续渲染直接引用同一个对象，跳过创建和 diff。

```js
// 编译产物（简化）
const _hoisted_1 = createElementVNode('p', { class: 'a' }, '静态文本')  // 只创建一次

function render(_ctx) {
  return createElementBlock('div', null, [
    _hoisted_1,                                        // 直接引用，不重新创建
    createElementVNode('p', { title: _ctx.t }, null, 8 /* PROPS */, ['title']),
    createElementVNode('p', _ctx.msg, null, 8 /* TEXT */)
  ])
}
```

**② PatchFlag**：每个动态节点携带一个数字标记（`TEXT=1`、`CLASS=2`、`PROPS=8`、`STYLE=4`…），运行时 patch 只看标记位对应的部分。`8 /* PROPS */, ['title']` 还带了 `dynamicProps`，**精确到具体是哪个 prop 变了**。

**③ Block Tree**：`createElementBlock` 创建的是 Block（块），Block 内部会把自己所有的**动态后代节点**收集到 `dynamicChildren` 数组里（一层扁平数组，不含静态节点和组件子树中的静态部分）。patch 时直接遍历 `dynamicChildren`，**不再递归整棵树**。

- 这就把「树形递归对比」变成了「一维数组遍历」。
- 遇 到 `v-if` / `v-for` 会打断收集，所以要作为新的 Block 结构处理，保证动态节点不漏收集。

**④ 事件缓存（cacheHandlers）**：`@click="fn"` 编译为 `_cache[0] || (_cache[0] = $event => _ctx.fn($event))`，避免每次渲染都创建新函数导致子组件 props 变化而重渲染。

### 1.6 Vue 3 高频问答（一）

**Q1：说一下 Vue 3 的响应式原理。**
> 参考回答（30 秒版，按「拦截 → 收集 → 触发 → 调度」四步讲）：
> 「Vue 3 用 `Proxy` 拦截对象的读写，`Reflect` 完成默认行为。当渲染函数或其他 `effect` 执行时，会有一个全局的 `activeEffect`，读取到的属性会通过 `track` 被记录到 `WeakMap → Map → Set` 三层依赖表里，粒度精确到「对象的某个属性 → 依赖它的所有副作用」。属性被修改时 `trigger` 找到对应的 `Set` 逐个通知。渲染 effect 带 scheduler，不会同步重渲染，而是 `queueJob` 推入队列去重，在微任务里 `flushJobs` 批量执行，这就是异步批量更新和 `nextTick` 的由来。相对 Vue 2 的 `defineProperty`，Proxy 能监听新增/删除属性和数组下标，且嵌套对象是惰性代理，初始化更快。」
> 追问预判：三层依赖表为什么用 WeakMap？→ 防止依赖表强引用对象导致内存泄漏。
> **话术提示**：收尾加一句「商云前台是 Vue 3，我们收银界面高频刷新订单列表，因为批量更新机制同一轮只渲染一次，所以性能上没有压力。」

**Q2：`nextTick` 是干什么的？什么时候需要用？**
> 参考回答：「Vue 的 DOM 更新是异步的，数据改完后 DOM 不会立刻变。`nextTick(cb)` 把回调放进 `flushJobs` 之后的微任务队列，保证回调执行时 DOM 已经是最新的。典型场景有两个：一是在 `v-if` 切换后立刻操作刚出现的 DOM 元素（比如让输入框自动聚焦）；二是修改数据后立刻读取 DOM 尺寸（比如弹窗内容高度自适应）。实现上 Vue 3 用 `Promise.resolve().then()`（微任务优先，降级到 `MutationObserver` / `setImmediate` / `setTimeout`）。」
> **话术提示**：可结合商云前台「电子小票预览弹窗」讲——「自助模式结账后会弹出电子小票预览，需要等弹窗渲染完再计算内容高度做滚动，我当时就是放在 `await nextTick()` 之后取的 DOM。」

**Q3：diff 为什么快？key 有什么用？**
> 参考回答：先给结论——「Vue 3 的 diff 快，主要不是算法常数变小，而是**参与比较的节点变少了**。」然后分三层：
> ① 编译期：静态提升让静态节点只创建一次并跳过 diff；PatchFlag 让运行时只 patch 动态部分；Block Tree 把树形递归变成动态节点数组的一维遍历。
> ② 运行时：同层比较（不跨层）避免 O(n³)；带 key 时用最长递增子序列求出「不需要移动的节点集合」，最小化 DOM 移动（O(n log n)）。
> ③ key 的作用是给节点一个稳定身份，让 diff 能正确复用与移动，避免就地复用导致的组件状态错乱（举 index 作为 key 删除后输入框串数据那个例子）。
> 追问预判：为什么不跨层级比较？→ 跨层移动的真实 DOM 代价高于「删除 + 重建」，且算法会退化，所以框架层面直接放弃跨层复用。

## 二、Vue 3 生态

### 2.1 Vue Router

```ts
const router = createRouter({
  history: createWebHistory(),          // 或 createWebHashHistory()（不需要服务端配置）
  routes: [
    { path: '/login', component: () => import('@/views/Login.vue'), meta: { public: true } },
    {
      path: '/',
      component: Layout,
      children: [
        { path: 'self-service', component: () => import('@/views/SelfService.vue'),
          meta: { title: '自助模式', code: 'selfService' } },
      ]
    },
    { path: '/:pathMatch(.*)*', redirect: '/' }   // 兜底
  ]
})

// 全局前置守卫：登录 + 权限（商云前台真实场景）
router.beforeEach((to, from, next) => {
  const userStore = useUserStore()
  if (to.meta.public) return next()
  if (!userStore.token) return next({ path: '/login', query: { redirect: to.fullPath } })
  // 动态权限：菜单/按钮权限由后台下发，前端只做拦截和展示控制
  if (to.meta.code && !userStore.perms.includes(to.meta.code)) return next('/403')
  next()
})
```

**要点**：

- **两种 history 模式**：`createWebHistory` 用 HTML5 History API，URL 干净但**需要服务端把 404 都回退到 index.html**（Nginx `try_files $uri $uri/ /index.html`）；`createWebHashHistory` 用 `#`，刷新不会 404，但 URL 难看、SEO 差。Wails 桌面应用里用的是 hash 或 memory 模式（没有真实的 HTTP 服务端）。
- **懒加载**：`() => import(...)` 让路由组件单独打包成 chunk，首屏只加载当前页面需要的代码。
- **守卫三种**：全局（`beforeEach`/`beforeResolve`/`afterEach`）、路由独享（`beforeEnter`）、组件内（`onBeforeRouteLeave`）。
- **动态路由**：登录后拉取权限菜单，用 `router.addRoute()` 动态注册，配合 `router.removeRoute` 处理退出登录。**注意刷新页面后动态路由会丢失**，需要在守卫里判断「已登录但路由未注册」时重新拉取再 `next({ ...to, replace: true })`。

### 2.2 Pinia 状态管理

**为什么 Vue 3 推荐 Pinia 而不是 Vuex**：

| | Vuex 4 | Pinia |
|---|---|---|
| 写法 | `mutations` + `actions` 分离，改状态必须走 mutation | 只有 `state / getters / actions`，action 里直接改 state |
| TypeScript | 类型推断差，需要手写大量类型体操 | 原生 TS 友好，`defineStore` 自动推导 |
| 模块 | 需要 `modules` + `namespaced`，嵌套层级深 | **每个 store 天然独立**，互相直接 import 使用 |
| 体积 | 较大 | 约 1KB |
| 组合式 API | 弱 | 支持 setup 写法（和组件写法一致） |

```ts
// stores/order.ts —— setup 写法（推荐，与组件风格统一）
export const useOrderStore = defineStore('order', () => {
  const list = ref<Order[]>([])
  const total = computed(() => list.value.reduce((s, o) => s + o.amount, 0))

  async function fetchList() {
    list.value = await api.getOrders()
  }
  function add(o: Order) { list.value.push(o) }

  return { list, total, fetchList, add }   // 只暴露需要给外部的
})

// 组件里使用：解构必须用 storeToRefs 才保持响应式
const orderStore = useOrderStore()
const { list, total } = storeToRefs(orderStore)   // state / getters 用 storeToRefs
const { fetchList } = orderStore                  // action 直接解构没问题（本身就是函数）
```

**Pinia 原理（一句话版）**：`defineStore` 返回一个 `useStore` 函数，内部用 `reactive`（options 写法）或 `ref`（setup 写法）包住 state；它只是为了**让状态脱离组件树共享**，本质上还是 Vue 3 的响应式系统，没有魔法。所以 Pinia 的 store 在 `app.use(pinia)` 之后是**单例**（同一个 pinia 实例下）。

**什么时候该用 Pinia / 什么时候不该用（面试官喜欢问判断力）**：
- 该用：跨页面/跨组件共享（登录用户信息、权限、购物车/订单缓存、主题配置）。
- 不该用：只在一个页面内几个子组件之间传的值（用 props/emit 或 provide/inject 更简单）、纯服务端数据（用请求库缓存更合适）。

### 2.3 组件通信的 8 种方式

| 方式 | 方向 | 适用场景 | 注意 |
|---|---|---|---|
| `props` | 父 → 子 | 最常见的数据传递 | 单向数据流，子组件不能直接改 |
| `emit` | 子 → 父 | 子组件通知父组件 | 配合 `defineEmits` 声明，TS 有类型提示 |
| `v-model` | 双向 | 表单类组件封装 | 本质是 `:modelValue` + `@update:modelValue`；Vue 3 支持多个 `v-model:xxx` |
| `defineExpose` + `ref` | 父 → 子（主动调用） | 父组件调用子的方法（如 `formRef.validate()`） | `<script setup>` 默认封闭，必须 `defineExpose` |
| `provide / inject` | 祖先 → 后代（跨层） | 主题、i18n、深层嵌套配置 | 注入的普通值不响应式，需要 provide 一个 ref 或 readonly 包 |
| `attrs` / `v-bind="$attrs"` | 父 → 子（透传） | 二次封装第三方组件 | `inheritAttrs: false` 时才手动透传 |
| 事件总线（`mitt`） | 任意 | 简单场景、非父子 | Vue 3 移除了 `$on/$emit`，需用三方库；滥用会导致数据流难追踪 |
| Pinia / 全局状态 | 任意 | 跨页面共享 | 见上节 |

```vue
<!-- 父子双向：v-model 的本质 -->
<!-- 父 -->
<AmountInput v-model:value="price" v-model:qty="count" />

<!-- 子：defineModel（Vue 3.4+ 语法糖） -->
<script setup lang="ts">
const value = defineModel<number>('value', { required: true })
const qty   = defineModel<number>('qty', { default: 1 })
// 等价于：props.modelValue + emit('update:modelValue', v)
</script>
```

> **话术提示**：可结合商云前台的「收银主界面 → 付款弹窗 → 金额键盘」三层结构作答：
> 「我们是主界面传订单给付款弹窗（props），付款成功后 emit 回来触发打印和清台；
> 跨多层的配置类数据（比如打印机型号、语音提示开关、语言）用 provide/inject；
> 登录信息、权限、当前班次这些跨页面的用 Pinia。
> 我的原则是**能用 props/emit 就不用状态管理**，因为数据流越短越好排查。」

### 2.4 权限控制实战（商云前台真实细节，面试的差异化素材）

商云前台的权限控制分成**三层**，这套分层思路可以迁移到 OA 系统（岗位强相关）：

1. **路由级（能不能进这个页面）**：登录后从后台拉取功能点列表，前端用 `meta.code` 与权限集比对，守卫拦截。
2. **按钮级（能不能点这个操作）**：`v-if="canWrite"` 控制显示，`usePermission` 组合函数复用；**关键原则是「前端控制展示、后端控制安全」**——前端隐藏按钮只是体验优化，真正的鉴权必须在后端接口层再做一次。
3. **数据级（能看到哪些数据）**：门店/收银员维度的数据隔离，由后端在 SQL 层加门店条件，前端只做展示。

**前端加密部分（商云前台的技术亮点，可以主动讲）**：
- 登录/支付等敏感信息用 **RSA**（公钥在前端，私钥在后端）做非对称加密，或 **AES** 对称加密传输内容，密钥再经 RSA 交换——即「混合加密」。
- 桌面端还涉及**串口通信**（电子秤、钱箱、打印机）和本地 **SQLite** 缓存，这部分是 Web 前端做不到、必须靠 Go 侧完成的能力。

## 三、前端工程化

### 3.1 Vite 原理

**为什么 Vite 冷启动快？**（面试标准答法，要对比 Webpack）

| | Webpack | Vite |
|---|---|---|
| 启动方式 | **先打包再启动**：把整个依赖图编译成 bundle，再启动 dev server | **不打包**：直接启动 server，浏览器请求哪个模块才编译哪个 |
| 模块格式 | 内部用 CommonJS 启动（再转 ESM） | 原生 **ESM**，由浏览器发起 `import` 请求，Vite 按需转换返回 |
| 依赖处理 | 每次冷启动都要重新处理 node_modules | **依赖预构建**（esbuild）只做一次，缓存在 `node_modules/.vite` |
| 单文件编译 | loader/plugin 链，串行处理，慢 | esbuild（Go 写的）做转换，比 babel 快 10~100 倍 |
| 生产构建 | Webpack（慢） | Rolldown/Rollup（成熟的 tree-shaking + 代码分割） |
| HMR | 需要重新构建受影响模块链路 | 基于 ESM 的**模块级热更新**，只让受影响的模块失效并重新请求 |

**依赖预构建（Optimize Deps）解决三个问题**：

1. **CommonJS → ESM**：很多 npm 包只提供 CJS，浏览器不能直接 `import`，需要预构建转成 ESM。
2. **请求瀑布问题**：像 `lodash-es` 有几百个内部模块，若一个个请求会触发上百次 HTTP 请求，预构建合并成一个文件后只需一次请求。
3. **性能**：esbuild 用 Go 编写，多线程并行，速度远快于 JS 实现的打包器。

```js
// vite.config.ts 关键配置
export default defineConfig({
  plugins: [vue()],
  resolve: { alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) } },
  server: {
    port: 5173,
    proxy: {
      // 开发环境代理，解决跨域（生产由 Nginx 反代）
      '/api': { target: 'http://127.0.0.1:8080', changeOrigin: true, rewrite: p => p.replace(/^\/api/, '') }
    }
  },
  build: {
    rollupOptions: {
      output: {
        manualChunks: {   // 拆包：把不常变的第三方库单独打包，利用浏览器长缓存
          vendor: ['vue', 'vue-router', 'pinia'],
          ui: ['element-plus']
        }
      }
    }
  }
})
```

**HMR 原理（面试会追问）**：
1. Vite dev server 通过 WebSocket 与浏览器建立连接。
2. 文件变更 → 找到受影响的模块边界（Vue 文件会被 `@vitejs/plugin-vue` 处理成组件边界）。
3. 服务端下发 `update` 消息，浏览器通过 `import('./Foo.vue?t=时间戳')` 重新请求模块。
4. `import.meta.hot.accept()` 回调里替换旧模块，**只重新渲染受影响的组件**，不刷新页面、不丢状态。

### 3.2 TypeScript 在 Vue 中的使用

```vue
<script setup lang="ts">
// 1. defineProps：编译宏，运行时是 props 选项，编译期自动生成类型
interface Props {
  order: Order
  mode?: 'self' | 'cashier'      // 字面量联合类型，比 string 更安全
  amount?: number
}
const props = withDefaults(defineProps<Props>(), { mode: 'cashier', amount: 0 })

// 2. defineEmits：事件名和参数都能类型校验
const emit = defineEmits<{
  (e: 'paid', orderId: string): void
  (e: 'cancel'): void
}>()

// 3. 泛型组件（Vue 3.3+）：表格列定义这类通用组件
// <script setup lang="ts" generic="T extends { id: number }">
// defineProps<{ list: T[]; columns: { key: keyof T; title: string }[] }>()

// 4. 类型收窄配合后端返回的联合类型
type Result =
  | { code: 0; data: Order }
  | { code: 1; msg: string }
function handle(r: Result) {
  if (r.code === 0) console.log(r.data.no)   // 收窄到成功分支
  else console.log(r.msg)
}
</script>
```

**面试常问：「为什么用 TS？」**（回答要落到工程收益，不要只说「类型安全」）
> 「三个具体收益：一是**接口对接成本**——商云前台要和 Go 后端、RabbitMQ、云端同步一堆接口，我把后端返回结构定义成 `interface` 放在 `types/` 下，字段改名或类型变化时编译器会直接把所有用错的地方报出来，不用等联调才发现。二是**重构信心**，改一个公共组件的 props，IDE 立刻列出所有调用点。三是**代码即文档**，新人看类型就知道数据长什么样。代价是写类型有成本，所以我们的原则是**公共模块和接口层严格写类型，纯展示组件允许宽松**。」

## 四、React 核心概念与对比（岗位要求「至少一种」，但对比题是深度探针）

### 4.1 JSX 与渲染流程

```jsx
// JSX 是 React.createElement 的语法糖（React 17+ 走 jsx-runtime，不用手动 import React）
const el = <div className="box">hello {name}</div>
// 等价于：
const el = React.createElement('div', { className: 'box' }, 'hello ', name)
```

JSX 与 Vue 模板的**哲学差异**：

- **JSX 是 JS 表达式**：可以在 `if/for/三元` 里自由用 JS 的能力控制结构，灵活度高，但没有编译期优化信息（React 近年来靠 React Compiler 补这块）。
- **Vue 模板是受限的 DSL**：写起来受约束，但**编译器可以理解模板语义**，从而做静态提升、PatchFlag 这些优化。Vue 也支持 `render` 函数/JSX，但会失去部分编译优化。

### 4.2 Hooks 原理浅析

**`useState` 为什么不能写在条件语句里？**

React 的 Hooks 存储在组件对应的 **Fiber 节点上的链表**里（`fiber.memoizedState` 指向第一个 hook，每个 hook 的 `next` 指向下一个）：

```
fiber.memoizedState → hook1(count) → hook2(name) → hook3(effect) → null
```

每次渲染时，React 按**调用顺序**依次取链表上的 hook；`setState` 更新的是对应 hook 的 `memoizedState`，然后调度重渲染。

- 如果 hook 写在 `if` 里，两次渲染的 hook 数量/顺序不一致，第 N 个 hook 就会读到别的 hook 的数据——这就是「**Hooks 规则**」的根源，所以必须写在顶层。
- 对比 Vue：Vue 的组合式 API **没有调用顺序约束**（`setup` 只在初始化时执行一次，响应式靠 `activeEffect` 全局变量 + 依赖表定位，不靠顺序），所以 Vue 里可以条件调用组合函数。**这个对比说出来会很加分**。

**`useEffect` 的依赖与清理**：

```jsx
useEffect(() => {
  const timer = setInterval(tick, 1000)
  return () => clearInterval(timer)   // 清理函数：卸载时 + 依赖变化重新执行前
}, [orderId])                         // 依赖数组决定是否跳过本次 effect
```

- 依赖为 `[]`：只在挂载后执行一次（相当于 `onMounted`）。
- 不传依赖数组：每次渲染后都执行（**容易写出循环渲染**）。
- 返回函数：清理副作用（相当于 Vue 的 `onUnmounted` + `watch` 的 `onCleanup`）。

**闭包陷阱（React 高频坑，Vue 里不常见）**：

```jsx
function Counter() {
  const [count, setCount] = useState(0)
  useEffect(() => {
    const id = setInterval(() => {
      console.log(count)          // ❌ 永远打印 0：捕获的是本次渲染的 count
    }, 1000)
    return () => clearInterval(id)
  }, [])                          // 依赖为空 → effect 只跑一次 → count 永远是初始值
}
```

三种修法：把 `count` 加进依赖数组；用 `setCount(c => c + 1)` 的函数式更新；用 `useRef` 保存最新值。

**为什么 React 需要 `useMemo`/`useCallback` 而 Vue 不需要？**
> React 的函数组件**每次渲染都会整体重新执行**，函数里定义的变量和函数都是新的，所以需要 `useMemo`/`useCallback` 缓存计算和引用（否则 `React.memo` 包裹的子组件会因为 props 引用变化而无效重渲染）。Vue 的 `setup` 只执行一次，`computed` 自带缓存、模板里的依赖是响应式的，**只有依赖变化才会触发更新**，所以不需要手动 memo。原因在于 React 是「重新执行整个函数」，Vue 是「响应式精确追踪」。

### 4.3 不可变数据与状态更新

```jsx
// React：状态必须整体替换，不能原地改
const [list, setList] = useState([{ id: 1, done: false }])

// ❌ 原地修改：引用没变，React 用 Object.is 比较后认为没变化，不重渲染
list[0].done = true

// ✅ 创建新对象/新数组
setList(list.map(i => i.id === 1 ? { ...i, done: true } : i))
setList(prev => [...prev, newItem])          // 函数式更新，避免闭包陷阱
```

- 为什么不可变？**因为 React 靠引用比较（`Object.is`）判断状态是否变化**，而 Vue 靠 Proxy 的 setter 直接知道哪变了。
- 更新对象嵌套深时手写展开很痛苦，实践里用 `immer` 的 `produce` 或 `useReducer`。

### 4.4 Vue 与 React 对比表（建议背下来，面试官很爱用）

| 维度 | Vue 3 | React 18 |
|---|---|---|
| 编程范式 | 模板 DSL + 组合式 API（也可 JSX） | JSX 函数式，一切都是 JS |
| 响应式 | `Proxy` 自动依赖追踪，**精确到属性** | `setState` 手动触发，**组件级重渲染**（靠 memo 优化） |
| 更新粒度 | 属性/节点级 | 组件级（React Compiler / memo 做缓解） |
| 状态更新 | 直接改（`state.x = 1`） | 必须 `setState`，且**不可变更新** |
| 视图更新 | 异步批量，微任务队列 `flushJobs` | 自动批处理（React 18 `createRoot` 后所有更新都批处理） |
| 逻辑复用 | 组合函数（可条件调用） | 自定义 Hook（**不可条件调用**，依赖调用顺序） |
| 副作用 | `watch` / `watchEffect` + `onUnmounted` | `useEffect` 依赖数组 + 清理函数 |
| 性能优化手段 | 响应式自动 + `v-memo` | `memo`/`useMemo`/`useCallback` 手动 |
| 学习曲线 | 上手快，约定多 | 上限高，心智模型（闭包、Hooks 规则）陡 |
| 生态 | 官方全家桶（Router/Pinia/Vite），整合度高 | 社区选择多（Next.js、Zustand、Redux Toolkit），灵活但需选型 |
| 适合场景 | 中后台、快速交付、团队水平参差 | 大型复杂交互、跨端（RN）、需要 JS 完全表达力 |

**被问「你 Vue 熟还是 React 熟，为什么选 Vue」怎么答**：
> 「我主力是 Vue 3 + TypeScript，商云前台整套前端是我负责的。React 我能读懂也能写，Hooks 的机制、不可变更新这些概念我清楚。选 Vue 是项目场景决定的——我们做的是 POS 桌面端，页面多、表单和列表密集、迭代快，Vue 的模板和官方全家桶能让我们更快交付、团队协作成本更低。但我的判断是：**框架只是工具，我更在意的是把后端接口、状态管理、鉴权、部署这条链路打通**，这也是我这个岗位最看重的能力。」

## 五、全栈实践：Wails 桌面应用架构（结合商云前台）

### 5.1 架构总览

Wails 是 Go 生态里的「Electron 替代品」——用系统原生 WebView 渲染前端，用 Go 作为后端，**不打包 Chromium**，所以安装包体积和内存占用远小于 Electron。

```
┌────────────────────────────────────────────────────────────┐
│                    Wails 应用（单进程）                      │
│                                                            │
│  ┌───────────────────────┐     ┌────────────────────────┐  │
│  │   前端（WebView）      │     │   Go 运行时（同一进程）  │  │
│  │   Vue 3 + TS + Vite   │◄───►│   main.go + app.go     │  │
│  │   Pinia / Vue Router  │ IPC │   业务逻辑 / 外设 / DB   │  │
│  └───────────────────────┘     └────────────────────────┘  │
│         ▲           │                    │                 │
│         │           │                    ├── SQLite（本地） │
│    EventsEmit       │ Bindings           ├── 串口（电子秤） │
│   （Go → 前端推送）  │（前端 → Go 调用）    ├── 打印机 / 钱箱  │
│         │           ▼                    └── RabbitMQ / HTTP│
│  ┌──────────────────────────────────────────────────────┐  │
│  │              WebView2 / WebKit / WKWebView            │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

**关键点（面试要能说清「为什么」）**：

- **为什么不用 Electron**：Electron 每个应用内置一个 Chromium（安装包 100MB+，内存 200MB 起）；POS 收银机是低配工控机，Wails 用系统 WebView 后安装包只有十几 MB，内存占用低得多。
- **为什么不用纯 Web（浏览器）**：收银场景必须访问**本地硬件**——串口电子秤、票据打印机、钱箱、扫码枪；浏览器沙箱做不到，Wails 里 Go 侧可以直接调系统 API 和串口。
- **离线能力**：门店断网也要能收银，所以本地 SQLite 做主力存储，联网后同步到云端（这也是「商云」名字的由来）。

### 5.2 Go 与前端通信机制（高频重点）

**方向一：前端 → Go（Bindings / 方法调用）**

```go
// app.go —— 把方法挂在 App 结构体上，Wails 会自动生成 TS 类型和方法绑定
type App struct {
    ctx context.Context
    db  *sqlite.DB
}

// 自助模式：结算并打印小票（我负责的模块）
func (a *App) SelfCheckout(payload CheckoutReq) (*CheckoutResp, error) {
    if payload.OrderNo == "" {
        return nil, fmt.Errorf("订单号不能为空")
    }
    // 1. 本地落库（事务）
    if err := a.db.SaveOrder(payload); err != nil {
        return nil, fmt.Errorf("保存订单失败: %w", err)
    }
    // 2. 打印小票 + 弹钱箱
    if err := a.printer.PrintReceipt(payload); err != nil {
        log.Printf("打印失败 orderNo=%s err=%v", payload.OrderNo, err)  // 打印失败不阻断交易
    }
    // 3. 生成微信电子小票（我负责的模块）
    url, err := a.wechat.CreateEBill(payload)
    return &CheckoutResp{Success: true, EBillURL: url}, err
}
```

```ts
// 前端调用：wailsjs/go/main/App 由 wails generate 自动生成
import { SelfCheckout } from '../../wailsjs/go/main/App'

async function onPaySuccess(order: Order) {
  const res = await SelfCheckout({ orderNo: order.no, amount: order.amount })
  if (res.success) ElMessage.success('结算成功')
}
```

**方向二：Go → 前端（Events）**

```go
// Go 侧主动推送：打印机状态、语音提示、异步任务进度
func (a *App) watchPrinter() {
    for status := range a.printer.StatusChan() {
        runtime.EventsEmit(a.ctx, "printer:status", map[string]any{
            "online": status.Online, "paperLow": status.PaperLow,
        })
    }
}
```

```ts
// 前端订阅
import { EventsOn } from '../../wailsjs/runtime/runtime'

onMounted(() => {
  EventsOn('printer:status', (s: PrinterStatus) => {
    printerStore.online = s.online
    if (s.paperLow) speak('打印纸不足，请更换')     // 语音提示模块
  })
})
onUnmounted(() => EventsOff('printer:status'))     // 必须解绑，否则重复订阅
```

**面试常被追问的细节**：

| 追问 | 参考回答 |
|---|---|
| 前端调 Go 是同步还是异步？ | 前端 JS 侧返回 Promise（异步），Go 侧方法**同步执行**（在 Wails 的 goroutine 里跑），长耗时任务要自己在 Go 里开 goroutine + 事件推送进度，否则会阻塞前端调用 |
| 传参怎么序列化？ | 走 JSON（结构体 ↔ JS 对象），所以 Go 侧字段要有 `json` tag，且**前端类型定义要与 Go 结构体保持一致**（我们用 `wails generate` 自动生成 `.d.ts`） |
| 错误怎么传？ | Go 方法返回 `(result, error)`，error 非 nil 时前端 Promise 会 reject；前端统一 try/catch 提示 |
| 同一进程会不会互相阻塞？ | 不会，WebView 渲染和 Go 运行时是不同线程/进程模型；但**Go 侧不要在绑定的方法里做长时间同步 I/O**，否则该次调用会长时间挂起 |
| 和 HTTP 比有什么好处？ | 不用起本地端口、没有 CORS、不受浏览器同源限制、可以直接访问文件与硬件，启动更快 |

### 5.3 前后端联调与鉴权（结合商云前台）

**联调链路分层**：

```
Vue 页面 → （Wails binding）→ Go 本地服务层 → （HTTP/gRPC + JWT）→ 云端后台
                                      ↓
                                 本地 SQLite（离线缓存，联网后同步）
```

**鉴权设计（面试可深挖）**：

1. **登录**：账号密码 → 密码前端用 RSA 公钥加密传输（防明文被抓包）→ 后端校验后返回 `token`（JWT）+ 权限点列表 + 门店信息。
2. **token 存放**：桌面端存在本地（加密后写 SQLite 或系统 keychain），**不是 localStorage**（桌面端 localStorage 在 WebView 数据目录明文可读）。
3. **请求携带**：Go 侧统一在 HTTP client 的 RoundTripper/中间件里注入 `Authorization`，前端不直接接触 token——这也是桌面端相对纯 Web 的安全优势（token 不进浏览器环境）。
4. **续期**：access token 短期（如 2h）+ refresh token 长期，401 时自动刷新并重放请求（在 Go 侧统一处理，前端无感）。
5. **离线与降级**：token 过期但门店断网时，允许本地继续收银（业务上容忍），联网后补传并重新鉴权。

### 5.4 「商云前台」项目讲述稿（面试直接可用，1 分钟版）

> 「商云前台是我们给零售商户做的**桌面收银应用**，技术栈是 **Wails + Go + Vue 3 + TypeScript**，
> 前端跑在系统 WebView 里，Go 侧负责本地业务、外设和云端同步，数据用本地 SQLite + 云端双写。
> 我负责的主要有四块：
> **一是自助模式后台模块**——自助收银机的整个流程，从扫码、计价、支付回调到清台；
> **二是微信电子小票**——结账后生成电子小票链接，用户扫码取票，涉及与微信侧接口对接和本地小票模板渲染；
> **三是打印与钱箱**——票据打印指令、钱箱弹开控制，这部分踩过不少打印机的坑，不同型号指令集不一样，我们做了一层适配；
> **四是权限控制和语音提示**——权限做了路由级、按钮级两层，语音提示是给收银员播报「收款成功」「打印纸不足」这类实时状态。
> 另外我还参与了登录、电子秤（串口称重）和外卖模块，以及一部分前端界面。
> 这个项目让我对**全栈链路**理解比较深：前端怎么调 Go、Go 怎么调硬件、断网了数据怎么不丢、打印失败了交易不能失败——
> 这些不是课堂知识，是踩坑踩出来的。」

**面试官可能追问的深水区（提前准备）**：
- 打印失败了怎么办？→ 打印与交易解耦：交易先落库成功，打印失败记录到重打队列，界面提示并提供「补打小票」入口，避免因外设故障导致交易数据丢失。
- 断网怎么处理？→ 本地 SQLite 为主库，写入带 `sync_status` 标记，后台 goroutine 定期扫描未同步记录上传，成功后置为已同步；上传接口做**幂等**（用订单号做唯一键）。
- 数据一致性怎么保证？→ 本地用事务 + 唯一索引防止重复插入；云端用订单号做幂等键，重复上传直接返回成功。
- 为什么权限要前后端都做？→ 前端控制展示（体验），后端控制安全（真正拦截），只做前端等于没有权限。

## 六、精选高频前端面试题（12 题，含参考回答）

**Q1：Vue 3 的响应式原理？和 Vue 2 有什么区别？**
> 见 1.6 Q1。核心四步：Proxy 拦截 → track 收集（WeakMap/Map/Set 三层）→ trigger 触发 → scheduler 微任务批量更新。与 Vue 2 的差异：拦截范围（新增/删除属性、数组下标）、惰性代理、Map/Set 支持、不支持 IE。
> 话术：可结合商云前台高频更新的订单列表讲批量更新的实际收益。

**Q2：`nextTick` 的原理和使用场景？**
> 见 1.6 Q2。要点：DOM 更新异步（微任务批处理）→ `nextTick` 在 flush 后执行 → 场景（操作刚渲染的 DOM、读取更新后的尺寸）。
> 话术：结合「电子小票预览弹窗渲染后计算高度」。

**Q3：diff 算法为什么快？key 的作用是什么？用 index 做 key 有什么问题？**
> 见 1.6 Q3。三层回答：编译期（静态提升/PatchFlag/Block Tree）、运行时（同层比较 + LIS 最小移动）、key 的语义。
> 话术：商云前台商品列表用「商品编码 + 行号」做 key，避免称重商品重复编码导致复用错乱。

**Q4：Vue 3 有哪些性能优化手段？**（面试官想听你**做过什么**）
> 分四层回答：
> ① **编译层**：静态提升、PatchFlag、Block Tree 是框架自动做的，不用管。
> ② **渲染层**：`v-if` vs `v-show` 选对（频繁切换用 `v-show`）；`v-for` 加 key；大数据列表用虚拟滚动（`vue-virtual-scroller`）；`v-memo` 缓存子树。
> ③ **数据层**：大对象不要塞进 `reactive`（Proxy 递归代理有成本）；不用的数据用 `shallowRef`；`computed` 替代模板里的复杂表达式；避免在模板里写函数调用（每次渲染都执行）。
> ④ **加载层**：路由懒加载、`manualChunks` 拆包、组件按需引入（Element Plus 按需加载）、图片懒加载与压缩。
> ⑤ **工程层**：`vite build` 的产物体积分析（`rollup-plugin-visualizer`）、gzip/brotli 压缩、CDN。
> 话术：「商云前台是低配工控机，我做的最有效的一件事其实是**把权限判断从模板里的方法调用改成 computed**——原来模板里 `checkPerm('print')` 每次重渲染都执行一遍，上千行订单时能明显感觉到卡顿，改成 computed 缓存后就好了。」
> （注：这个「模板里调方法」的坑是真实高频优化点，讲出来很可信。）

**Q5：Vue 组件通信有哪些方式？分别在什么场景用？**
> 见 2.3 表格。答题顺序建议：props/emit（最常用）→ v-model → defineExpose + ref（父调子）→ provide/inject（跨层）→ attrs 透传 → mitt（非父子）→ Pinia（跨页面）。收尾强调原则：**数据流越短越好，能用 props 就不用全局状态**。
> 话术：商云前台「主界面 → 付款弹窗 → 金额键盘」的三层结构。

**Q6：Pinia 和 Vuex 的区别？为什么 Vue 3 推荐 Pinia？**
> 四点：① 去掉了 mutations，action 里直接改 state，代码量减半；② 原生 TS 推导，不用写类型体操；③ 模块扁平，天然命名空间，store 之间可直接引用；④ 体积小、支持组合式写法。
> 追问「Pinia 原理」：本质是 `reactive`/`ref` 包一层 + 单例，没有魔法，所以 `storeToRefs` 才能保持响应式。
> 话术：商云前台用 Pinia 管「登录用户 + 权限 + 当前班次 + 购物车」，其中权限数据是路由守卫和按钮渲染都要读的，放 store 最合适。

**Q7：`v-if` 和 `v-show` 的区别？分别什么时候用？**
> `v-if` 是**真实的销毁/创建**（有创建销毁开销、可配合 `v-else`、懒渲染）；`v-show` 是 `display: none` 切换（初始渲染开销大、切换开销小）。
> 选择原则：**频繁切换用 `v-show`，条件很少变用 `v-if`**；需要懒加载（首屏不渲染）用 `v-if`。
> 注意点：`v-if` 和 `v-for` 不要同用（Vue 3 中 `v-if` 优先级更高，会拿不到 `v-for` 的变量，写在同一元素上会报错/行为不符预期），应该在外层套 `<template v-for>` + 内层 `v-if`。

**Q8：Vite 为什么比 Webpack 快？**
> 见 3.1。核心两点：**开发环境不打包**（原生 ESM 按需编译）+ **依赖预构建用 esbuild**（Go 实现、多线程，比 JS 打包器快一个数量级）。生产环境仍然打包（Rollup/Rolldown）以获得最优产物体积。
> 追问「Vite 有什么缺点」：① 生态插件不如 Webpack 丰富；② 开发时首屏请求多，深层依赖会出现请求瀑布（预构建缓解）；③ 生产构建与开发行为有差异，偶发「开发正常打包报错」。

**Q9：React 的 Hooks 为什么不能写在条件语句里？**
> 见 4.2。因为 Hooks 按调用顺序存在 Fiber 的链表上，两次渲染顺序不一致会导致 hook 状态错位。
> **加分对比**：「Vue 的组合式 API 没有这个约束，因为 `setup` 只在初始化时执行一次，响应式靠全局的 `activeEffect` 和依赖表定位，不依赖调用顺序——所以 Vue 里可以条件调用组合函数。」

**Q10：Vue 和 React 的核心差异？你更倾向哪个？**
> 见 4.4 表格。答题时不要背表格，抓住三条主线：**响应式模型（自动追踪 vs 手动 setState）**、**更新粒度（属性级 vs 组件级）**、**心智负担（约定多 vs 心智模型陡）**。
> 结尾态度要中性且有判断力：「工具选型看场景，中后台和交付速度我选 Vue，需要极致灵活和跨端我选 React。我更看重的是把前后端链路打通的工程能力。」

**Q11：前端怎么做鉴权？token 存哪里？**
> 三点：① 登录换 token（JWT），② 存储位置（Web 端：`httpOnly` Cookie 最安全，防 XSS 读取；`localStorage` 方便但可被 XSS 读取；桌面端存加密后的本地文件），③ 请求携带与刷新（请求拦截器注入 header，401 时用 refresh token 静默续期并重放请求），④ 路由守卫 + 按钮级权限，**但真正鉴权必须在后端**。
> 话术：商云前台在 Go 侧统一注入 token，前端完全不接触，天然规避 XSS 窃取。

**Q12：首屏加载慢怎么优化？**
> 先**量化**再优化（面试官爱听这句）：
> ① 定位：`Lighthouse` / Chrome Performance 面板 / `vite-bundle-visualizer` 看产物构成。
> ② 体积：路由懒加载、`manualChunks` 拆分 vendor、UI 库按需引入、`lodash` 换成按需函数或原生实现、大依赖换成轻量替代。
> ③ 网络：开启 gzip/brotli、CDN、HTTP 缓存（hash 文件名 + 长缓存）、图片用 WebP + 懒加载。
> ④ 渲染：首屏关键路径优先、骨架屏、避免同步阻塞的大计算（放 Web Worker）。
> ⑤ 指标：FCP / LCP / TTI / CLS 是衡量标准。
