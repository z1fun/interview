## 二、★ 中间件选型方法论（架构师视角）

### 2.1 选型到底在选什么

> **一句话**：选型不是选「最强的」，是选「在当前团队、当前阶段、当前业务量下**总成本最低且能活到下一阶段**的那个」。

七个评估维度，**按优先级排序讲**（小公司场景下，运维成本和团队熟悉度天然该排前面）：

| 维度 | 要问自己的问题 | 举例 |
| --- | --- | --- |
| **① 功能匹配度** | 业务的数据模型、一致性要求、查询模式，它天生适配吗？ | 事务 + 多表关联 → MySQL；全文检索 + 聚合 → ES |
| **② 性能与容量** | 目标是 QPS / 数据量 / 延迟多少？它单机、单集群能到多少？ | 10 万 QPS 计数 → Redis；10 亿条日志检索 → ES |
| **③ 运维成本** | 谁来运维？故障了谁会修？备份恢复流程有吗？ | 0-20 人公司，能少一个组件就少一个 |
| **④ 团队熟悉度** | 团队里有人踩过坑吗？出问题能定位吗？ | **你最熟的 PostgreSQL 可能比理论最优的 MongoDB 更合适** |
| **⑤ 生态与社区** | 文档全不全、客户端 SDK 成熟吗、遇到问题能搜到答案吗？ | Go 生态里 go-redis / mongo-go-driver 都很成熟 |
| **⑥ 成本** | 硬件、License、云服务费用、人力 | 自建 ES 集群 vs 云上 ES 按量付费 |
| **⑦ 扩展性** | 数据涨 10 倍、QPS 涨 10 倍时，是加机器就行，还是要重构？ | Redis Cluster 水平扩容；MySQL 分库分表是重构级动作 |

### 2.2 ★★ 「为什么选 X 不选 Y」的通用答题框架

这是选型题的**唯一正确结构**。面试官问「为什么用 MongoDB 不用 MySQL」，不是要你背书，是要看你**有没有决策过程**。

> **四步框架：场景 → 约束 → 候选对比 → 决策 + 代价**

| 步骤 | 说什么 | 时长 | 关键动作 |
| --- | --- | --- | --- |
| **① 先问场景** | "先看业务：这个数据是**写多还是读多**？**结构固定吗**？**要不要事务**？**量级多少**？" | 15 秒 | ⚠️ **别急着答选哪个**。先问需求是架构师的基本动作，也是把题从"背书题"变成"讨论题"的关键 |
| **② 说约束** | 团队规模、技术栈、运维能力、成本、上线时间 | 15 秒 | 小公司面试这里特别加分——**你把他们真实处境说出来了** |
| **③ 列候选做对比** | 2-3 个方案，各说**一条决定性差异**（不要念参数表） | 40 秒 | 用「维度对比」而不是「我更喜欢谁」 |
| **④ 给决策 + 说代价** | "所以选 X，代价是 Y，我用 Z 来补" | 20 秒 | ★ **主动说代价是可信度的来源**。只有骗子才给的方案没缺点 |

**示范（背下来，套任何选型题）**：

> "我先看这个场景的约束——数据是网关策略配置，**读多写少**（读 QPS 几万、写一天几十次）、**结构不固定**（不同插件类型的策略字段完全不一样）、**要求秒级生效**、团队就 3 个人。候选三个：**MySQL** 结构固定、事务强，但每次加策略类型要改表结构、多版本快照要额外设计；**MongoDB** 文档模型天然适配多变的策略结构、支持多版本快照、读性能好，但运维要多维护一个组件；**Redis** 快但持久化不可靠，只能当缓存不能当唯一的配置源。**最后我会选 MySQL + Redis 缓存**——不是 Mongo 不好，是因为在 3 个人的团队里，**策略配置这一点灵活性和 MySQL 带来的运维成本比起来不划算**；如果策略类型真的爆炸式增长，再迁 Mongo 也不迟。"

> ⚠️ **陷阱提醒**：面试官问「为什么选 X 不选 Y」时，**说「Y 不行」是下策，说「Y 在我们这个约束下不是最优」才是上策**。任何一个能活下来的中间件都有它的适用场景，贬低它是新手表现。

### 2.3 用过的技术 vs 没用过的技术，分别怎么讲

| 类型 | 讲法 | 模板 |
| --- | --- | --- |
| **用过（MySQL / Redis / RabbitMQ）** | **讲踩过的坑 + 决策细节 + 数字**，不讲"我会用" | "POS 流水表我建的是 `(shop_id, biz_date, id)` 联合索引，因为查询固定是门店 + 时间段，等值列必须在最左——这里踩过一次坑，一开始我把 biz_date 放前面，结果 90% 查询用不上索引。" |
| **没用过（MongoDB / ES / Kafka / K8s）** | **三步走**：① 承认边界（一句，不啰嗦）② 讲清原理与选型逻辑 ③ 给"如果我来做"的方案 | "**MongoDB 我还没在生产用过**，我的存储经验集中在 MySQL 和 Redis 上。不过它的选型逻辑我理解：文档模型解决的是 schema 多变和多版本快照的问题，代价是丢了 JOIN 和跨文档事务。**如果这个网关的策略配置要我选**，我会先看策略结构的变更频率……" |

> ★ **关键心法**：**承认边界不是减分项，"承认得干脆"反而是加分项**——它证明你其他部分说的是真的。真正减分的是支支吾吾、含糊其辞，面试官一眼就能看出来。
>
> ⚠️ 绝对不要说的三句话：「MongoDB 我了解一些」（含糊，一定被追问到底）、「我在项目里用过 MongoDB」（编造，两层追问就崩）、「MongoDB 我用得不多，但我学得很快」（空话，零信息量）。

### 2.4 ★ 结合本岗位：给 AI 安全网关做中间件选型

**这是本岗位最可能出现的选型题**，因为 JD 第 4 条白纸黑字写了「能够根据业务场景完成中间件架构选型」。三大系统各要一套存储，**先记住这张判断总表**：

| 数据类别 | 特征 | 我的选型 | 理由（一句话） | 备选 |
| --- | --- | --- | --- | --- |
| **策略配置** | 读多写少、结构多变、要求热更新 | **MySQL（权威源）+ Redis（缓存/发布订阅）** | 配置要事务与审计、又要秒级下发 | MongoDB、ETCD |
| **租户与配额** | 强一致、要扣减、金额相关 | **MySQL（账单/配额）+ Redis（实时计数）** | 钱的事必须落库、实时性靠 Redis | — |
| **访问审计日志** | 海量、写多读少、要全文检索与聚合 | **ES（检索）+ 对象存储/Mongo（冷归档）** | ES 是为检索和聚合生的 | ClickHouse、Loki |
| **流量统计（TPS/延迟/拦截数）** | 时序、高频写、按时间窗聚合 | **Redis（实时计数）+ MySQL/ClickHouse（分钟级预聚合落库）** | 实时看板要毫秒级，长周期分析要列存 | Prometheus、Mongo 时间桶 |
| **网关节点状态** | 秒级心跳、要 watch、要强一致 | **ETCD** | Raft 强一致 + watch 天然适合做控制平面 | Consul、ZooKeeper |
| **限流计数/防重放** | 高频、原子、可容忍少量丢失 | **Redis** | 内存原子操作是它的主场 | 本地滑动窗口 |
| **请求内容样本（用于 AI 分析/取证）** | 半结构化、字段不固定、量中等 | **MongoDB**（如果上了这套） | 请求体结构随模型和插件变 | 对象存储 + ES |

**面试话术（把这张表讲成一个方案）**：

> "如果我来给 AI 安全网关做存储选型，我会**按数据的性质分四类**，而不是'一个库装所有东西'：
> **第一类是配置类**——策略、路由、租户。这是权威数据，要求事务和审计，我用 **MySQL**，同时用 **Redis 做缓存 + Pub/Sub 或 ETCD watch 做多节点秒级下发**。
> **第二类是计数类**——限流令牌、配额余额、实时 QPS。要求高并发原子操作，必须放 **Redis**，用 Lua 保证原子性；**但不能只放 Redis**，因为重启会丢，所以做「Redis 实时扣 + 异步落 MySQL 账本 + 定时对账」。
> **第三类是日志类**——访问日志、审计日志、拦截记录。**ES 是首选**，因为量级大（一天几亿条）、要按关键词检索、要按时间聚合。冷数据定期转对象存储。
> **第四类是时序统计类**——TPS、延迟分位、拦截率。实时用 Redis 计数，分钟级聚合成宽表落 MySQL 或直接在 ES 聚合。
> 至于 **MongoDB**，在网关这个场景里它最合适的位置是**策略配置的文档化存储和请求样本归档**——因为它 schema 灵活，正好匹配「不同策略类型字段不同」这件事。但如果策略结构的变更频率不高，我会优先用 MySQL，**少一个组件就少一份运维负担**。"

## 三、★★ MongoDB 专项（岗位标签有，简历里没有）

> **本节目标**：不求会运维，求**被问到能站住**。三个必答层次：① 为什么会有 MongoDB（✔ 到这里及格）② MongoDB vs MySQL 怎么选（✔ 到这里良好）③ 副本集 / 分片 / 选型判断题（✔ 到这里优秀）。

### 3.1 为什么会有 MongoDB

> **一句话**：MongoDB 解决的是「**数据模型不固定 + 我要水平扩展 + 我想少写 ORM 映射代码**」这三件事，代价是丢掉了 JOIN 和跨文档强事务。

四份推动力：

| 驱动力 | 具体含义 | 对比 SQL |
| --- | --- | --- |
| **文档模型** | 数据以 BSON 文档（≈ JSON）存储，一个聚合根（如订单 + 明细 + 地址）塞进一个文档，读一次全拿到 | SQL 要 JOIN 三张表 |
| **灵活 Schema** | 同一个集合里不同文档字段可以不同，"无 Schema"（其实是"Schema 由应用管"） | 加字段要 DDL，大表改结构是运维事件 |
| **开发效率** | 文档结构与语言里的对象基本同构，**不需要 ORM 映射层** | ORM 的映射与阻抗失配 |
| **水平扩展** | 内建分片（Sharding）能力，加机器就能扩容量和吞吐 | MySQL 分库分表要自己搞中间件 |

⚠️ **一定要说出口的代价**：**没有 JOIN**（用 `$lookup` 但性能差）、**多文档事务性能代价大**（4.0 才有）、**默认读性能换一致性的空间更大（要自己选 readConcern）**、**占用内存多**（WiredTiger 缓存 + 索引）、**运维复杂度高**（副本集 + 分片集群）。

**MongoDB 的典型适用场景**（记住这 5 个就够）：

1. **内容管理 / 商品档案**：字段随品类变化，SKU 属性差异极大。
2. **用户画像 / 行为事件**：埋点数据、事件流，字段天天变。
3. **物联网 / 设备上报**：海量写入 + 时间序列（配合**时间桶模式**）。
4. **日志与审计（中等规模）**：TTL 索引自动过期是天然优势。
5. **配置与规则引擎**：策略结构多变、需要多版本快照。

### 3.2 MongoDB vs MySQL 完整对比表（★ 必背）

| 对比维度 | MongoDB | MySQL (InnoDB) |
| --- | --- | --- |
| **数据模型** | 文档（BSON，嵌套结构），一个文档 = 一个聚合根 | 行 + 列，二维表，第三范式拆表 |
| **Schema** | 灵活（可选校验 validator），字段可不同 | 严格，DDL 变更要 Online DDL |
| **查询语言** | MQL（`db.coll.find({...})`）+ 聚合管道 | SQL |
| **关联查询** | ❌ 无 JOIN，`$lookup` 是左连接且性能差、有索引限制 | ✅ 多表 JOIN，优化器完善 |
| **事务** | 单文档原子；**4.0** 副本集多文档事务；**4.2** 分片事务；**性能代价大、默认 60 秒超时** | ✅ 天然多表事务，成熟 |
| **索引** | B 树（WiredTiger），支持**多键索引**（数组字段）、**文本索引**、**TTL 索引**、地理空间索引、通配符索引 | B+ 树，支持前缀索引、全文索引（弱）、无 TTL |
| **扩展方式** | ★ **原生水平扩展**：分片（Sharding），内置路由（mongos）与均衡器 | **垂直扩展为主**，水平要分库分表中间件 |
| **一致性** | ★ 可调：`writeConcern`（w:0/1/majority）+ `readConcern`（local/majority/snapshot/linearizable） | 强一致（单机），主从复制可配半同步 |
| **存储引擎** | WiredTiger，**文档级并发控制**（3.0+），支持压缩 | InnoDB，行锁 + MVCC |
| **内存模型** | WiredTiger cache 默认 = (物理内存 - 1GB) × 50% | Buffer Pool 默认 128MB（要手调） |
| **适用场景** | 结构多变、嵌套聚合、海量写入、要水平扩、日志/画像/内容 | 事务、关联、强一致、报表、金额 |
| **不适用场景** | 强事务、复杂关联、多表统计报表、金额账务 | 超大字段灵活结构、超大规模水平扩展 |

> **面试话术（30 秒版）**：
> "MySQL 和 MongoDB 的区别，我总结成**三个问题**：**结构固定吗**（固定选 MySQL）、**要跨表事务吗**（要选 MySQL）、**数据量会大到单机扛不住吗**（会就得考虑 Mongo 或分库分表）。MongoDB 的杀手锏是**文档模型 + 原生分片**，MySQL 的护城河是**事务 + JOIN + 成熟生态**。所以在我做过的业务里——**POS 的流水与账务必须 MySQL**，因为要事务和报表；**如果是网关的策略配置和请求样本**，MongoDB 的灵活性就值钱了。"

### 3.3 核心概念

> **一句话**：Database → Collection → Document 是层级关系；Document 是 BSON 格式；`_id` 默认是 ObjectId，**12 字节 = 4 字节时间戳 + 5 字节随机值 + 3 字节自增计数器**。

| 概念 | 对应 SQL | 说明 |
| --- | --- | --- |
| Database | Database | 一个实例多个库 |
| Collection | Table | **无固定 Schema** |
| Document | Row | BSON 文档，最大 **16MB**（单文档硬上限） |
| Field | Column | 可嵌套子文档、数组 |
| `_id` | 主键 | 不指定则自动生成 ObjectId，**自动建唯一索引** |

**ObjectId 的 12 字节构成（★ 常考细节，答出来很加分）**：

```
| 4 字节 | 5 字节 | 3 字节 |
 时间戳    随机值    自增计数器
（秒级）  （进程级）  （进程内递增）
```

- **4 字节时间戳**：秒级精度 → **ObjectId 大致有序**，可以近似当创建时间用（`ObjectId("...").getTimestamp()`）。
- **5 字节随机值**：每个**进程**启动时生成一次 → 多进程/多机不冲突。
- **3 字节计数器**：进程内单调递增 → 同一秒内不冲突。

⚠️ **陷阱**：**ObjectId 单调递增 = 分片时的热点隐患**。如果按 `_id` 做范围分片键，所有新写入都落在**最后一个 chunk**（"单调递增键热点"），写入压力全压在一个分片上。**正确做法是用哈希分片键**（`{_id: "hashed"}`）或换一个随机性好的分片键。

**BSON vs JSON**：
- BSON = Binary JSON，**二进制编码 + 类型信息 + 长度前缀**。长度前缀让解析器可以**跳读**（skip）不需要的字段，这是它比 JSON 快的核心原因。
- 支持 JSON 没有的类型：`Date`、`ObjectId`、`Decimal128`、`Binary`、`Timestamp`。
- ⚠️ 代价：**字段名在每个文档里都重复存储**，短字段名（`uid` 而非 `userId`）能省空间——这是 Mongo 的经典优化技巧。

### 3.4 索引

> **一句话**：MongoDB 索引也是 B 树（WiredTiger），逻辑与 MySQL 相通，**差异在于它多了「多键索引」「TTL 索引」这两类为文档模型定制的索引**。

| 索引类型 | 用法 | 典型场景 |
| --- | --- | --- |
| **单字段索引** | `db.c.createIndex({name: 1})` | 基础 |
| **复合索引** | `db.c.createIndex({tenantId: 1, status: 1, createdAt: -1})` | 多条件查询 |
| **多键索引 Multikey** | 字段是数组时**自动**变多键索引 | `{tags: ["a","b"]}`，一个文档占多个索引项 |
| **文本索引 Text** | `db.c.createIndex({title: "text"})` | 全文检索，**一个集合只能有一个文本索引** |
| **TTL 索引** | `createIndex({expireAt: 1}, {expireAfterSeconds: 3600})` | **到期自动删文档**（日志、会话、验证码） |
| **地理空间** | `2dsphere` / `2d` | 附近的人、区域围栏 |
| **唯一索引** | `{unique: true}` | 幂等键、业务主键 |
| **部分索引 Partial** | `{partialFilterExpression: {...}}` | 只索引符合条件的文档，省空间 |
| **稀疏索引 Sparse** | 只索引存在该字段的文档 | 可选字段 |
| **通配符索引 Wildcard** | `{"$**": 1}` | 字段完全不可预知时（慎用，占空间） |

**★ 复合索引的 ESR 原则**（对应 MySQL 的"最左前缀"，Mongo 的版本叫 **ESR**）：

> **Equality（等值）→ Sort（排序）→ Range（范围）**

理由：索引 B 树先按等值字段收敛到一个点，再按排序字段决定顺序（**让排序能直接用索引，避免内存排序**），最后范围字段做扫描范围。**范围字段放在中间会让后面的字段完全用不上**（和 MySQL 一样）。

**索引原理要点**：
- WiredTiger 里**每个索引是一棵独立的 B 树**。
- ⚠️ **一个易错点**：MongoDB 的集合**不是按 `_id` 聚簇存储的**（5.3 之前）。普通集合的数据按内部 RecordId 存储，`_id` 是**独立的唯一索引**，所以「按 `_id` 查」需要**两次 B 树查找**（先 `_id` 索引拿到 RecordId，再取文档）——**这本质上就是 MySQL 的「回表」**。
- **覆盖查询（Covered Query）**：查询字段全在索引里、且不返回 `_id`（`{_id: 0}`）时，直接从索引返回，不回表。对应 MySQL 的覆盖索引。
- **WiredTiger 压缩**：默认 snappy（可配 zlib/zstd），索引也有前缀压缩，这是 Mongo 存储成本低的原因之一。

**explain 分析（★ 会说这个就赢一半）**：

```javascript
db.orders.find({tenantId: "t1", status: "paid"}).explain("executionStats")
```

重点看三个数字 + 一个字段：

| 字段 | 含义 | 健康的信号 |
| --- | --- | --- |
| `winningPlan.stage` | 执行方式 | **`IXSCAN`**（走索引）好；**`COLLSCAN`**（全表扫）❌ 必须优化 |
| `keysExamined` | 扫描的索引键数 | 越接近 `nReturned` 越好 |
| `docsExamined` | 扫描的文档数 | ⚠️ **如果远大于 `nReturned`，说明索引没起到过滤作用** |
| `nReturned` | 实际返回数 | 基准值 |
| `executionTimeMillis` | 耗时 | 参考 |

> **"3 个数字"心法**：`keysExamined : docsExamined : nReturned` 理想是 **1 : 1 : 1**。如果 `keysExamined` 很大说明索引选择性差；`docsExamined` 大说明要回来过滤很多文档（缺覆盖索引或条件没进索引）。

### 3.5 副本集（Replica Set）★

> **一句话**：副本集 = 一组存同样数据的 mongod 实例，**1 个 Primary 收写 + N 个 Secondary 复制**，**多数派选举**产生新 Primary，实现自动故障切换。

| 角色 | 说明 |
| --- | --- |
| **Primary** | 唯一接受写入的节点，**所有写都先到它** |
| **Secondary** | 从 Oplog 异步复制，可配置为读（readPreference） |
| **Arbiter** | **只投票、不存数据**，用于凑够奇数票（省钱但有风险，见下方 ⚠️） |
| **Hidden** | 副本但客户端不可见，用于备份/报表 |
| **Delayed** | 延迟 N 秒应用 Oplog，**用于误操作兜底**（类似"回收站"） |

**关键机制**：

- **Oplog**：local 库里的**固定大小集合（capped collection）**，记录主节点的**幂等写操作**（把 `$inc` 直接记成结果，保证重放安全）。Secondary 拉取 Oplog 并重放。⚠️ **Oplog 是滚动覆盖的**，如果 Secondary 落后太多、位点已被覆盖，就**无法增量追赶，必须全量重同步（initial sync）**。
- **选举**：Primary 挂了 → 存活的 Secondary 发起选举 → **需要获得多数派（N/2+1）投票**才能当选。所以 **3 节点是标准配置**（1 主 2 从，容忍挂 1 台）。
- **优先级 priority**：数值高的更可能当选；设为 0 表示永不成为 Primary（用于异地/报表节点）。
- **故障切换时间**：通常 **10-30 秒**（心跳 10 秒 + 选举），期间**写入不可用**——这是必须说出口的代价。

**★★ 读写关注（readConcern / writeConcern）—— 这是 MongoDB 一致性调优的核心**

**writeConcern**（写要多少个节点确认）：

| 值 | 含义 | 场景 |
| --- | --- | --- |
| `w: 0` | 不等待确认（fire and forget） | 日志类、可丢 |
| `w: 1` | Primary 确认（**默认**） | 一般业务；**Primary 崩溃可能丢这段写** |
| `w: "majority"` | 多数派确认 | **金额、账务、不可丢的数据** |
| `j: true` | 写入 journal（落盘）后才返回 | 与 w 组合使用 |

**readConcern**（读到什么程度的数据）：

| 值 | 含义 | 场景 |
| --- | --- | --- |
| `local` | 读本节点最新数据（**默认**），**可能被回滚** | 一般查询 |
| `available` | 分片下读本分片最新（最弱） | 不关心一致的统计 |
| `majority` | 只读**已被多数派确认**的数据，**不会被回滚** | 金额、关键业务读 |
| `linearizable` | 线性一致（读一定看到之前完成的写） | 极少数强一致场景，性能差 |
| `snapshot` | 事务内的一致性快照 | **多文档事务必须用** |

> ★ **面试话术**：
> "MongoDB 的一致性可以**按操作调**，这是它比 MySQL 灵活的地方，也是容易出事的地方。我的口径是：**默认的 `w:1` + `readConcern: local` 在 Primary 宕机时有丢数据和脏读的风险**，所以**涉及金额和状态流转的操作必须显式升到 `w: majority` + `readConcern: majority`**；而日志、埋点这类可以容忍丢失的，就用默认值换性能。**读从库时也要注意**：`readPreference: secondary` 可能读到旧数据，**刚写完就读的场景必须走 primary。**"

⚠️ **PSA 架构陷阱**（高级加分点）：如果副本集是 **Primary + Secondary + Arbiter**，当 Secondary 挂掉时，**能投票的只剩 Primary 和 Arbiter（2/3 = 多数派）**，此时如果写用 `w: majority` 且 `wtimeout` 到了，**Primary 会主动降级为 Secondary，导致整个集群不可写**。所以**生产不推荐 Arbiter，推荐 PSS（1 主 2 从）**。

### 3.6 分片（Sharding）★

> **一句话**：分片 = 把数据按**分片键**切到多个分片上，`mongos` 做路由，`config server` 存元数据，**均衡器在后台搬 chunk**。

**架构三件套**：

| 组件 | 角色 |
| --- | --- |
| **mongos** | 无状态路由进程，客户端连它；解析查询 → 路由到目标分片 → 聚合结果 |
| **config server** | 必须有（3.4+ 必须是副本集 CSRS），存**分片元数据、chunk 分布** |
| **shard** | 每个分片**本身是一个副本集**（高可用 + 分片叠加） |

**分片键的选择（★★ 关键，选错直接毁掉集群）**

三个必须同时满足的性质：

| 性质 | 含义 | 反例 |
| --- | --- | --- |
| **高基数（Cardinality）** | 取值要足够多 | `{gender: 1}` 只有两个值 → 最多 2 个 chunk，无法均衡 |
| **低频率（Frequency）** | 单个值不能占太大比例 | `{tenantId: 1}` 如果有一个大客户占 80% 数据 → 它所在的 chunk 永远最大且**不可再分** |
| **非单调（Non-monotonic）** | 新写入不要集中在同一区间 | `{_id: 1}`、`{createdAt: 1}` → **所有写都打到最后一个 chunk** |

**分片方式**：

| 方式 | 说明 | 适用 |
| --- | --- | --- |
| **范围分片（ranged）** | 按分片键区间切 | 查询**经常按范围**（如时间），但**单调键会热点** |
| **哈希分片（hashed）** | 对分片键求哈希后分片 | **写入均匀**，但范围查询要**广播到所有分片**（scatter-gather） |
| **复合分片键** | `{tenantId: 1, _id: 1}` | ★ **最常见的正确解**：既有租户隔离（查询能定向），又用 `_id` 打散（写入不热点） |

**chunk 与均衡器**：
- chunk = 一段连续的分片键区间，**默认 64MB**（可调）。
- 写入增长超过阈值 → **分裂（split）**；各分片 chunk 数不均 → **均衡器（balancer）后台搬迁 chunk**。
- ⚠️ chunk 搬迁**消耗 IO 和网络**，业务高峰期可以设置**均衡窗口（balancer window）**避开。

**分片键的坑（说得出这些，面试官会认为你真研究过）**：
- ⚠️ **分片键一旦选定，改起来很痛**：4.2 起支持更新分片键字段值，4.4 起可用 `refineCollectionShardKey` **追加后缀字段**，**5.0 起才支持 `reshardCollection` 完整换分片键**（且是大操作）。
- ⚠️ **查询不带分片键 = 广播查询**（scatter-gather）：mongos 要问所有分片再合并，**最慢**。所以「**最常用的查询条件要能带上分片键**」是选键的第一原则。
- ⚠️ **唯一索引必须包含分片键**（否则无法在分片层面保证唯一）——这条对"用唯一索引做幂等"的设计有直接影响。

### 3.7 事务

> **一句话**：**单文档操作天然原子**（这是 Mongo 的设计哲学）；多文档事务 4.0 支持副本集、4.2 支持分片，**但性能代价大，能用文档模型规避就不要用事务**。

| 版本 | 能力 |
| --- | --- |
| 4.0 | 副本集内**多文档事务**（复制集成员，跨集合、跨库） |
| 4.2 | **分片集群事务**（跨分片） |
| 4.4+ | 支持在事务中创建集合/索引（有限制） |

**使用要点与代价**：
- 默认**事务存活 60 秒**（`transactionLifetimeLimitSeconds`），超时自动中止。
- **事务内单文档仍有 16MB 限制**，且**事务的 Oplog 条目总大小也有限制**（16MB）→ **事务不能太大**。
- ⚠️ **性能代价**：事务会持有更多锁、快照隔离（snapshot readConcern），**冲突高时大量 abort 重试**。
- ★ **重要理念**：MongoDB 的设计哲学是「**用文档模型把需要一起改的数据放进同一个文档**」，这样单文档原子就够了、根本不需要事务。**如果发现需要频繁跨文档事务，往往是数据模型没设计好**——这句话面试时说出来很显功力。

**在事务里怎么写（Go 示例，能讲就行）**：

```go
// mongo-go-driver：会话 + 事务
sess, err := client.StartSession()
defer sess.EndSession(ctx)

_, err = sess.WithTransaction(ctx, func(sc mongo.SessionContext) (interface{}, error) {
    if _, err := accounts.UpdateOne(sc,
        bson.M{"_id": from, "balance": bson.M{"$gte": amount}},
        bson.M{"$inc": bson.M{"balance": -amount}}); err != nil {
        return nil, err          // 返回 error 会自动 abort 并重试（可重试写）
    }
    if _, err := accounts.UpdateOne(sc,
        bson.M{"_id": to}, bson.M{"$inc": bson.M{"balance": amount}}); err != nil {
        return nil, err
    }
    return nil, nil
}, options.Transaction().SetWriteConcern(writeconcern.Majority()))
```

⚠️ **面试官追问「转账这种场景你会用 MongoDB 吗」** → 标准答法：
> "**我会优先用 MySQL**。MongoDB 事务虽然能用，但它是「**为了补齐文档模型的短板而加的功能**」，而不是它最强的地方；跨文档事务在高冲突下 abort 重试成本高。**如果非要用 Mongo，我会改数据模型**——把转账的两个账户放在同一个文档（如按 '账户对' 分片），或者用『**流水先行 + 异步冲正**』的方式做最终一致，而不是硬上事务。"

### 3.8 聚合管道（Aggregation Pipeline）

> **一句话**：聚合管道把数据处理拆成**一串阶段（stage）**，每个阶段的输出是下一个阶段的输入，**`$match` 和 `$sort` 放最前面能用上索引，这是优化的第一原则**。

| 阶段 | 作用 | 类比 SQL |
| --- | --- | --- |
| `$match` | 过滤 | `WHERE`（**放最前，且尽量用索引**） |
| `$project` | 选择/改名字段 | `SELECT` |
| `$group` | 分组聚合 | `GROUP BY` |
| `$sort` | 排序 | `ORDER BY`（放 `$group` 前后意味完全不同） |
| `$limit` / `$skip` | 分页 | `LIMIT` / `OFFSET` |
| `$unwind` | **展开数组**（每个元素出一行） | 类似 UNNEST，SQL 没有直接对应 |
| `$lookup` | 左外连接另一个集合 | `LEFT JOIN`（性能差，慎用） |
| `$facet` | **一次查询出多组结果** | 多个 GROUP BY 合并 |
| `$bucket` / `$dateTrunc` | 分桶/按时间粒度聚合 | 时间维度统计 |

**实战例子（网关：按小时统计各租户的拦截数）**：

```javascript
db.access_logs.aggregate([
  { $match: { type: "block", createdAt: { $gte: ISODate("2026-09-01") } } }, // ① 先过滤，走索引
  { $group: {
      _id: { tenantId: "$tenantId",
             hour: { $dateTrunc: { date: "$createdAt", unit: "hour" } } },
      count: { $sum: 1 },
      avgLatency: { $avg: "$latencyMs" }
  }},
  { $sort: { "_id.hour": 1 } },        // ② 排序
  { $limit: 100 }
])
```

**优化要点**：
- ★ **`$match` 尽量放管道第一步**，让它命中索引；放在 `$project`/`$group` 之后就变成内存过滤了。
- `$lookup` 是**每个文档一次查询**（类似 N+1），大集合上会炸——**能靠文档嵌套解决的，绝对不要 `$lookup`**。
- `$group` / `$sort` 超过 100MB 内存需要 `{allowDiskUse: true}`（会落盘，慢）。
- **`$facet` 是给"一次查询出多个统计口径"用的**，比如运营后台一个看板同时要总量、分类型、分租户三个统计。

### 3.10 ★★ 结合本岗位场景判断（这题很可能被问！）

**题目**：网关的**策略配置**、**访问审计日志**、**流量统计数据**——各适合用 MongoDB 吗？

**通用答题框架**：对每一类数据，问三个问题 → **① 结构固定吗？② 量级与读写比？③ 查询模式是什么？**

#### 场景 1：网关的**策略配置**（路由规则、限流规则、拦截规则、多租户配置）

| 判断维度 | 分析 |
| --- | --- |
| 结构固定吗？ | **不固定**：限流策略有 QPS/突发窗口，拦截策略有正则/关键词库，路由策略有上游地址——**同一条"策略"的字段差异极大**，且**类型会不断增加** |
| 读写比 | **读极多写极少**（读 QPS 上万、写一天几十次），且要求**秒级热更新** |
| 查询模式 | 按租户 + 路由 + 优先级查，**极少复杂关联** |
| 一致性要求 | **配置变更要有审计与回滚**（多版本快照） |

**结论：有条件地适合** ★

> **判断**：**如果策略类型会持续爆炸式增长，MongoDB 是比 MySQL 更顺的选择**——文档模型天然容纳"不同策略字段不同"，**多版本快照**可以用「配置文档 + 版本子文档数组」实现，省掉 MySQL 的 varchar JSON 列 + 版本表的设计。但有两个前提：① **必须用 MySQL 或 ETCD 做权威源做双写/校验**（配置是控制平面，不能因为 Mongo 挂了就全网关失配）② **策略下发不要依赖 Mongo 的 change stream 做唯一通道**，用 Redis Pub/Sub 或 ETCD watch 更可靠。

> **但更保守也更可能的答案**：**MySQL + Redis 就够了**。因为在 3 个人的团队里，"加一个 MongoDB 副本集"的运维成本，比不上"策略字段灵活性"带来的收益——**策略的字段变化完全可以用 JSON 列 + 应用层校验扛住**。

> ★ **面试话术**：
> "策略配置我会分两种情况看：**如果策略类型是稳定的一二十种，我选 MySQL**，用 JSON 列存差异化字段，理由是**配置是控制平面，权威性比灵活性重要**，多一个存储组件就多一个单点。**如果策略是插件化的、类型持续增长、还要存多版本历史**，那 MongoDB 的文档模型就值这个运维成本了。**我的原则是「权威配置必须有强一致存储兜底」**，MongoDB 只能作为加速层或者确实适配时的主存储，**不能是唯一的那份配置**。"

#### 场景 2：网关的**访问审计日志**（每天 10 亿条请求记录、拦截记录）

| 判断维度 | 分析 |
| --- | --- |
| 结构固定吗？ | 半固定：基础字段固定，但**请求头/请求体/Prompt 内容**差异大、长度不定 |
| 量级与读写比 | **写入极多、读极少**（写多读少 10000:1）；需要**定期过期** |
| 查询模式 | **全文检索**（查某个 Prompt 关键词）、**聚合统计**（错误率、拦截率、TOP 攻击 IP）、**按时间范围查** |

**结论：ES 首选，MongoDB 只能做"冷归档/明细兜底"**

> **判断**：**不适合作为主存储**。理由：① MongoDB 的**文本索引功能弱**（一个集合只能有一个文本索引、分词能力差、不支持中文分词扩展），做不到"日志检索"的核心需求 ② 按时间范围 + 聚合统计，**ES 的倒排索引 + doc_values 列存是专门为这个场景设计的** ③ 10 亿条/天量级下，MongoDB 的写入和存储成本都比 ES 高（Mongo 索引开销大、压缩率不如 ES 的列存）。
> **但 MongoDB 有一个 ES 没有的优势——TTL 索引**：如果只是"**存 30 天明细，过期自动删，偶尔按 ID 查一下**"，MongoDB 反而是**极简方案**（不用维护 ES 集群、不用管分片、TTL 自动清理）。

> ★ **面试话术**：
> "**审计日志我首选 ES**，因为检索和聚合是它的主场，10 亿条/天的量级它扛得住，而且冷热分层（热数据 SSD + 冷数据对象存储）生态成熟。**MongoDB 在这里的位置是"轻量替代"**：如果这个网关的日志量在每天几百万到千万条、又只要求'按 ID 查 + 定期过期 + 偶尔按关键词搜'，那我去上一个 ES 集群就不划算了——**MongoDB 的 TTL 索引 + 文档模型能以十分之一的运维成本满足需求**。所以判断标准就一句话：**要的是「全文检索 + 复杂聚合」就用 ES，要的是「明细存储 + 自动过期」就用 MongoDB。**"

#### 场景 3：**流量统计数据**（TPS、延迟分位、拦截次数、租户配额消耗）

| 判断维度 | 分析 |
| --- | --- |
| 结构固定吗？ | **极其固定**：就是 (租户, 指标, 时间窗口, 值) 四元组 |
| 量级与读写比 | 写入高频（每秒都在累加）、**读取要毫秒级**（看板实时刷新） |
| 查询模式 | 按时间窗口求和/求分位、按租户分组、**不需要全文检索** |

**结论：不适合 MongoDB，选 Redis + ClickHouse/MySQL 汇总表**

> **判断**：**MongoDB 不是这个场景的最优解**。理由：① 实时累加**必须靠 `$inc` 原子操作**，虽然 Mongo 支持，但**Redis 的 `INCR`/`HINCRBY` 在内存里做这件事快一个数量级**，而且网关每秒几十万次计数，用 Redis 是压倒性的成本优势 ② 长周期分析（按月、按租户维度下钻）**列式存储（ClickHouse）碾压行存** ③ 统计数据的 schema 是固定的，**MongoDB 的"灵活"在这里完全用不上，纯付出代价**。
> **MongoDB 唯一能出场的变体是——时间桶模式（Bucket Pattern）**：把一分钟/一小时的指标预聚合成一个文档（`{bucket: "2026-09-22T10:00", total: 12345, byTenant: {...}}`），用 `$inc` 累加、一次读整个桶。**这在中小规模下非常优雅**，是官方推荐的时序数据方案，**但量级上来还是要换时序库/列存。**

> ★ **面试话术**：
> "流量统计我会做**两层**：**实时层用 Redis**——`HINCRBY gateway:stat:{ts} tps 1`，网关每个实例本地先聚合（比如 1 秒汇总一次再写 Redis），避免把每个请求都变成一次 Redis 调用；**分钟级以上用预聚合落库**——定时任务把 Redis 的分钟值刷进 MySQL 汇总表，或者量大了直接进 ClickHouse / ES 做明细聚合。
> **MongoDB 在这里不适合**——统计数据的结构是固定的，用它等于白白承担了灵活性带来的索引和运维成本，而**它擅长的 `$inc` 累加，Redis 做得更好**。如果非要在文档库里做，我会用**时间桶模式**，把一小时的数据压成一个文档，这样读的时候一次就拿到整桶。"

#### 场景判断题的三句话总结（★ 背这个就够）

> **① 结构固定 + 要事务 + 要关联 → MySQL。**
> **② 结构多变 + 要嵌套聚合 + 要横向扩 + 可接受最终一致 → MongoDB。**
> **③ 海量 + 要全文检索 + 要复杂聚合 → ES；要毫秒级计数 → Redis；要列式分析 → ClickHouse。**
> **选型的本质是：数据形态决定模型，模型决定引擎。**

## 四、MySQL

> **你在这一节的定位**：**这是你的主场**。POS 数据贯通用过 go-zero + GORM + MySQL 做过真实的中台表设计、批量写入、消费落库；LoveSpouse 做过高并发写与冷热分离。**八股只是外壳，落点一定要在你的项目上。**

### 4.1 索引

#### 4.1.1 为什么是 B+ 树

> **一句话**：B+ 树是「**矮胖 + 有序 + 叶子成链**」——非叶子节点只存键不存数据，一页 16KB 能装上千个键，**3 层就能存 2000 万行，查任意一行最多 3 次磁盘 IO**。

| 对比 | 为什么不用 |
| --- | --- |
| **vs B 树** | B 树的非叶子节点也存数据行 → 一页装的键少 → 扇出小 → 树更高 → IO 更多。B+ 树数据全在叶子，非叶子是纯索引 |
| **vs 哈希表** | 等值 O(1) 最快，但**不支持范围查询、排序、最左前缀**；用在 Memory 引擎和 InnoDB 自适应哈希索引（AHI） |
| **vs 跳表** | 跳表是 Redis ZSet 的选择（内存友好、范围查询好），但它是**链表、随机 IO 太差**；B+ 树一个节点就是一页，天然对齐磁盘 |
| **vs 二叉树/红黑树** | 树太高，几次 IO 就退化成几十次 |

**扇出计算（会算这个很加分）**：bigint 主键 8B + 页指针 6B ≈ 14B，一页 16KB ≈ **1170 个键**；3 层 ≈ 1170 × 1170 × 16 ≈ **2000 万行**。

⚠️ **别用 UUID 做聚簇索引主键**：随机插入会导致**页分裂**、页利用率低（约 50%），插入性能断崖下跌。要做全局唯一 ID 就用**雪花 ID 另存一列**，主键仍是自增 bigint。
> 项目话术：「POS 流水表我坚持自增 bigint 主键 + 另外一列全局单号 `order_no`（唯一索引），因为 UUID 随机插入会让 B+ 树频繁页分裂；对外暴露的幂等键用 `order_no`，内部关联和排序用自增 `id`。」

#### 4.1.2 聚簇索引 / 二级索引 / 回表 / 覆盖索引

> **一句话**：InnoDB **主键索引就是聚簇索引**，叶子直接存整行；**二级索引叶子只存「索引列 + 主键」**，所以查非索引列要**回表**再走一次聚簇索引——**覆盖索引就是让这次回表不发生**。

- 一张表**只有一个聚簇索引**：有主键用主键 → 没主键用第一个非空唯一索引 → 都没有则隐式生成 6 字节 `row_id`。
- **回表 = 两次 B+ 树查找**：二级索引定位到主键值 → 拿主键去聚簇索引取整行（这里是**随机 IO**，回表次数多了就是性能杀手）。
- **覆盖索引**：查询的列全在索引里，`EXPLAIN` 的 `Extra` 显示 `Using index`。因为二级索引自带主键，`select id, name from user where name=?` 在 `idx_name(name)` 上就已经是覆盖索引。
- **主键要短**：二级索引的叶子要存主键，主键越长，**所有二级索引都越大**（UUID 36B vs bigint 8B）。
- ★ **索引下推 ICP（5.6+）**：把 WHERE 中**能用索引列判断的条件**下推到引擎层过滤，减少回表次数，`Extra` 显示 `Using index condition`。
  - 例子：索引 `(name, age)`，`where name like '张%' and age = 20`。没有 ICP 时，引擎只按 `name` 过滤出所有姓张的，**全部回表**再由 Server 层筛 age；有 ICP 时，引擎层就直接用 age 过滤掉不匹配的，**回表次数大幅减少**。

> 项目话术：「POS 的商品档案列表接口我做成了覆盖索引 `idx_tenant_status(tenant_id, status, id)`，列表只查 id 和状态，`Extra` 从 `Using filesort` 变成 `Using index`，省掉了每次回表的随机 IO。」

#### 4.1.3 最左前缀与索引失效

> **一句话**：联合索引 `(a,b,c)` 在 B+ 树里按 a→b→c 排序，查询必须**从最左列开始连续匹配**；**索引失效的本质是「条件让 B+ 树没法利用有序性去定位」**。

**⚠️ 索引失效清单（背这张表就够）**：

| 场景 | 例子 | 说明 |
| --- | --- | --- |
| 跳过最左列 | `where b=1`（索引 `(a,b)`） | 完全用不上 |
| 范围列之后的列 | `where a=1 and b>2 and c=3` | 只能用 a、b；c 失效 |
| 对索引列做函数/运算 | `where date(created_at)='2026-01-01'`、`id+1=5` | 改成 `>= '2026-01-01' and < '2026-01-02'` |
| 隐式类型转换 | `where phone=13800000000`（phone 是 varchar） | 等价于 `CAST(phone AS int)`，**等于对列加了函数** |
| 前导模糊 | `like '%abc'` | 后模糊 `like 'abc%'` 可以走索引 |
| `or` 连接非索引列 | `where a=1 or d=2` | 退化为全表扫 |
| `!=` / `not in` / `is not null` | — | **不一定失效**，看优化器成本判断（别答死） |
| 区分度太低 | 性别、状态只有几个值 | 优化器主动放弃索引（回表成本 > 全表扫） |

**联合索引设计口诀（★ 直接说）**：

> **等值在前，范围在后，排序列跟上，区分度高的优先。**

- `order by` 也走最左前缀：`(a,b)` 下 `order by a,b` 免排序；`order by b` 会 `Using filesort`。
- **8.0 的索引跳跃扫描（Skip Scan）**：a 区分度很低时，不写 a 也能用上索引——**加分项，但别当主要方案**。

> 项目话术：「POS 流水的核心查询是『某门店 + 某时间段』，我建的是 `(shop_id, biz_date, id)`：**等值的 shop_id 在最左**，**范围的 biz_date 其次**，**最后带 id 让排序分页也能走索引**，避免 filesort。这里踩过一次坑——我一开始把 `biz_date` 放最左，结果 90% 的查询用不上索引，`EXPLAIN` 一看 `type=ALL`。」

### 4.2 事务

#### 4.2.1 ACID 与隔离级别

> **一句话**：**ACID 里最难做到的是 I（隔离性）**——它是靠「锁 + MVCC」两套机制实现的；**隔离级别越高一致性越好、并发越差**，而 **MySQL 默认是 RR（可重复读），Oracle/PG 默认是 RC**。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 |
| --- | --- | --- | --- | --- |
| 读未提交 RU | ✅ 会 | ✅ 会 | ✅ 会 | 直接读最新 |
| **读已提交 RC** | ❌ | ✅ 会 | ✅ 会 | **每次 SELECT 新建 ReadView** |
| **可重复读 RR**（默认） | ❌ | ❌ | ❌（InnoDB 基本避免） | **第一次 SELECT 建 ReadView 并复用** + 间隙锁 |
| 串行化 | ❌ | ❌ | ❌ | 加锁串行，性能最差 |

#### 4.2.2 ★★ MVCC 详解

> **一句话**：MVCC = 「**每行数据有多个历史版本（undo log 版本链）+ 每个事务有一份可见性规则（ReadView）**」，读的时候顺着版本链找到自己可见的那个版本，**读不加锁，所以读写不阻塞**。

**三件套**：

| 组件 | 说明 |
| --- | --- |
| **隐藏字段** | 每行有 `DB_TRX_ID`（6B，最后修改它的事务 ID）、`DB_ROLL_PTR`（7B，指向 undo log 的版本链）、`DB_ROW_ID`（无主键时的隐式主键） |
| **undo log 版本链** | 每次修改都把**旧版本**写进 undo log，`DB_ROLL_PTR` 串成链表，**越老的版本在链尾** |
| **ReadView** | 事务快照，4 个字段：`m_ids`（活跃事务 ID 列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id` |

**可见性判断规则（★ 能背出这四步说明你真懂）**：拿版本的 `DB_TRX_ID` 去比对 ReadView：

1. `trx_id < min_trx_id` → **可见**（事务早就提交了）
2. `trx_id >= max_trx_id` → **不可见**（在我快照之后才开启的事务）
3. `min_trx_id <= trx_id < max_trx_id`：
   - 在 `m_ids` 里 → **不可见**（当时还是活跃事务）
   - 不在 `m_ids` 里 → **可见**（当时已提交）
4. 不可见就顺着 `DB_ROLL_PTR` 找下一个版本，直到找到可见的或链尾。

**★ RC 与 RR 的唯一区别**：

| | ReadView 生成时机 | 效果 |
| --- | --- | --- |
| **RC** | **每次 SELECT 都重新生成** | 能读到别人已提交的新数据 → **不可重复读** |
| **RR** | **第一次 SELECT 时生成，整个事务复用** | 从头到尾看同一份快照 → **可重复读** |

> ★ 面试话术（讲透版）：
> "MVCC 的本质是**用「保留历史版本 + 可见性判断」换掉了读锁**。InnoDB 每行记录上有两个隐藏列——事务 ID 和回滚指针，回滚指针把 undo log 里的旧版本串成链。事务开始时（RR 下是第一次读时）生成一个 ReadView，里面记着**当时还活跃的事务 ID 列表**。读一行时，拿行上的事务 ID 和 ReadView 比：比最小活跃 ID 小说明早就提交了，可见；比最大 ID 还大说明是后来才开的事务，不可见；在中间就看它在不在活跃列表里。不可见就顺着回滚指针往前翻版本，直到翻到可见的。
> **RC 和 RR 的差别只有一行代码**——RC 每次 SELECT 都重新生成 ReadView，RR 只在第一次生成然后复用。**这行差别带来两个后果**：RR 能重复读同一份快照，但代价是**快照老了之后版本链会很长、purge 不能及时清理**，长事务会拖累整个实例的内存。"

#### 4.2.3 幻读与间隙锁

> **一句话**：**RR 下的快照读天然不会幻读**（读的是同一个 ReadView）；**幻读发生在「当前读」**（`select ... for update`、`update`、`delete`）——InnoDB 用**间隙锁**堵住区间来防止它。

⚠️ **这题有陷阱，别答「RR 靠 MVCC 解决了幻读」**：

| 读类型 | 语句 | 幻读 |
| --- | --- | --- |
| **快照读** | 普通 `SELECT` | ✅ 不会（ReadView 冻结了可见集合） |
| **当前读** | `SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE` / `UPDATE` / `DELETE` | ⚠️ **可能幻读**，靠**间隙锁**防 |

**为什么间隙锁能防幻读**：幻读 = "我锁了 id=5 这一行，别人却**插入**了 id=6 让我的 `where id>4` 多出一条"。间隙锁锁的是**记录之间的空隙**（不含记录本身），**别人不能在这个空隙里插入**，新记录就长不出来。

### 4.3 锁

> **一句话**：InnoDB 的锁按粒度分「全局锁 → 表锁 → 行锁」，行锁又有「记录锁 / 间隙锁 / 临键锁」三种形态；**锁的规则只有一个目的：在保证一致性的前提下尽量并发**。

| 锁 | 说明 | 何时出现 |
| --- | --- | --- |
| **全局锁** | `FLUSH TABLES WITH READ LOCK`，整个库只读 | 全库备份（现在用 `--single-transaction` 免锁备份） |
| **表锁** | `LOCK TABLES ... READ/WRITE`，或 **MDL（元数据锁）** | DDL 时自动加 MDL，**长事务会阻塞 DDL** |
| **意向锁（IS/IX）** | 表级标志，表示"表里有行被锁了" | 加行锁前自动加，**目的是快速判断表锁能否加** |
| **记录锁 Record Lock** | 锁**单条**索引记录 | `where id=5 for update`（唯一索引等值命中） |
| **间隙锁 Gap Lock** | 锁**开区间** `(4, 6)`，**不含记录** | RR 下范围查询/未命中；**只阻止插入，不互斥其他间隙锁** |
| **临键锁 Next-Key Lock** | **记录锁 + 间隙锁**，锁**左开右闭** `(4, 6]` | ★ **RR 下加锁的默认形态** |
| **插入意向锁** | 特殊的间隙锁，表示"我要在这里插"，**插入之间不互斥** | INSERT 前 |

**记忆口诀（★ 面试时说出来立刻显得清楚）**：
> "**RR 下默认是临键锁，等值命中唯一索引会退化成记录锁，等值未命中或范围查询就用间隙锁。**"

**⚠️ 关键陷阱：`for update` 不走索引 = 锁全表**
> `UPDATE t SET ... WHERE name = 'x'`（name 无索引）→ **扫描所有行并全部加锁**（RR 下还有全部间隙），**几乎等于锁表**，极易死锁。所以**更新语句一定要走索引**。

**死锁**：
- **产生条件**：两个事务以相反顺序持有并请求锁（如事务 A 锁了 id=1 要 id=2，事务 B 锁了 id=2 要 id=1）。
- **InnoDB 会自动检测**（wait-for graph），**回滚"权重小"的那个事务**（通常是修改行数少的），报 `Deadlock found when trying to get lock`。
- **排查手段**：
  - `SHOW ENGINE INNODB STATUS` → `LATEST DETECTED DEADLOCK` 段落（能看到两条 SQL 和锁等待）。
  - `innodb_print_all_deadlocks = ON` → 把**所有**死锁打到 error log。
  - `performance_schema.data_locks` / `data_lock_waits`（8.0）实时看锁等待。
- **预防**：
  1. **固定加锁顺序**（如永远按 id 升序更新）★ 最有效
  2. **缩短事务、避免大事务**
  3. **更新/删除走索引**，避免锁范围扩大
  4. **把并发更新改成串行**（`select ... for update` 一次锁定，或者用 Redis 分布式锁前置）
  5. 业务上**用乐观锁（版本号）替代悲观锁**

> 项目话术：「POS 的批量上传流水里我会**固定按 `order_no` 排序后入库**，就是为了避免两个批次交叉加锁。另外批量上传天然是热点，我在 GORM 层用 `clause.OnConflict` 做 upsert 而不是先查后写，**减少了持锁时间也顺手解决了重复消费的幂等。**」

### 4.4 日志：redo / undo / binlog

> **一句话**：**redo log 保证崩溃不丢（crash-safe），undo log 保证可回滚 + 支撑 MVCC，binlog 保证主从复制和数据恢复**——三种日志各司其职，**redo 是物理逻辑日志、binlog 是逻辑日志**。

| | redo log | undo log | binlog |
| --- | --- | --- | --- |
| **归属** | InnoDB 引擎层 | InnoDB 引擎层 | **MySQL Server 层**（所有引擎共用） |
| **内容** | **物理逻辑**（"在哪个页做了什么修改"） | **逻辑**（反向 SQL，如 INSERT 对应 DELETE） | **逻辑**（SQL 语句或行变更） |
| **作用** | **崩溃恢复**（crash-safe）、WAL | **回滚**、**MVCC 版本链** | **主从复制**、**数据恢复/归档** |
| **写入方式** | **循环写**（固定大小，write pos / checkpoint 两个指针） | 随事务写，purge 线程清理 | **追加写**（不覆盖，可无限增长） |

**redo log 的关键参数**：

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `innodb_flush_log_at_trx_commit` | **1（默认）** | 每次提交都 fsync → **不丢数据**，性能最低 |
| | 2 | 每次提交写 OS cache（不 fsync），**MySQL 崩溃不丢，断电丢 1 秒** |
| | 0 | 每秒刷一次，**崩溃丢 1 秒**，性能最高 |
| `innodb_log_file_size` | — | 太小 → 频繁 checkpoint，**写性能抖动** |

**★ 两阶段提交（2PC）—— 面试高频难点**

> **一句话**：为了保证 **redo log 和 binlog 的一致性**（否则主从/备份会不一致），InnoDB 提交时分成 **prepare 和 commit 两个阶段**，binlog 写在中间。

**流程**：

```
① 写 redo log（prepare 状态）
② 写 binlog
③ 写 redo log（commit 状态）   ← 提交完成
```

**崩溃恢复规则（★ 一定要能推出来）**：

| 崩溃时刻 | redo 状态 | binlog | 恢复动作 |
| --- | --- | --- | --- |
| ① 之前 | 无 | 无 | **回滚** |
| ① 之后 ② 之前 | prepare | ❌ 不完整 | **回滚**（主库没有 binlog，从库也不该有） |
| ② 之后 ③ 之前 | prepare | ✅ 完整 | **提交**（binlog 完整 = 全流程成功） |

> **判断逻辑**：**"redo log 是 prepare 且 binlog 完整 → 提交；否则回滚"**。反过来说——**在写 binlog 之前崩溃，不算提交**。

**binlog 的三种格式（★ 必答）**：

| 格式 | 记录内容 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **STATEMENT (SBR)** | 原始 SQL 语句 | 日志小、可读 | ⚠️ **`now()`、`uuid()`、`limit` 等不确定函数会导致主从不一致** |
| **ROW (RBR)**（8.0 默认） | 每行的前后值 | ✅ **绝对一致**，能配合闪回 | 日志大（批量更新放大成 N 行），**大事务会撑爆** |
| **MIXED** | 自动选 | 折中 | 两种都有 |

- ★ **加分回答**：「**8.0 默认 ROW，我们做数据同步/CDC 时也要求 ROW**，因为 Canal / Debezium 这类工具是靠解析 ROW 格式的 binlog 工作的；STATEMENT 格式它们解析不出来。」
- `sync_binlog = 1`：每次提交都把 binlog fsync 到磁盘（**配合 `innodb_flush_log_at_trx_commit=1` 是"双 1 配置"，最安全**）。
- **组提交（group commit）**：多个事务的 fsync 合并成一次，缓解"双 1"的性能损失。

### 4.5 SQL 优化

> **一句话**：`EXPLAIN` 我只看四个字段——**`type` 看访问方式、`key` 看实际用了哪个索引、`rows` 看预估扫多少行、`Extra` 看有没有 filesort / temporary / 回表**。

**`type` 从好到坏**：`system` / `const`（主键或唯一索引等值，最多一行）> `eq_ref`（JOIN 被驱动表走主键）> `ref`（普通二级索引等值）> `range`（between / in / 范围）> `index`（扫整棵索引树）> **`ALL`（全表扫，必须优化）**。

**`Extra` 关键字速查**：

| 关键字 | 含义 | 好坏 |
| --- | --- | --- |
| `Using index` | 覆盖索引，没回表 | ✅ 好 |
| `Using index condition` | ICP 生效 | ✅ 好 |
| `Using where` | Server 层过滤 | 中性 |
| `Using filesort` | 额外排序（内存或磁盘） | ⚠️ 要优化 |
| `Using temporary` | 用了临时表（group by / distinct / union） | ⚠️ 要优化 |
| `Using join buffer` | 被驱动表连接列没索引 | ⚠️ 要优化 |

**★ 慢 SQL 治理五步（按顺序说，别跳步）**：

1. **捞**：慢日志（`slow_query_log=ON`、`long_query_time=0.5~1`）→ `pt-query-digest` 按「**总耗时 = 次数 × 单次**」排序。⚠️ **高频小慢 SQL 比偶发大慢 SQL 更值得治**。
2. **看**：`EXPLAIN` 定位是 `type=ALL`、还是 `filesort`、还是回表太多。
3. **改**：**优先加/改索引或改写 SQL**（成本最低、可回滚）。
4. **减**：减少数据量——归档、汇总表、**游标分页替代深分页**。
5. **拆**：最后才动架构——读写分离 → 分区表 → 分表 → 分库。

**★ 深分页优化（高频）**：

```sql
-- ❌ 慢：扫 100 万行再丢掉，回表 100 万次
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

-- ✅ 方案 A：延迟关联（先走覆盖索引拿 id，再回表 10 次）
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) x ON o.id = x.id;

-- ✅ 方案 B（最好）：游标分页，记住上一页最后的 id
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;
```

**SQL 改写技巧**：
- `count(*)` —— InnoDB **不存行数**（MVCC 导致每行可见性不同），只能扫最小的二级索引树。（8.0 有并行扫描优化；MyISAM 存了行数但没用）。**要快就维护汇总表**，别每次 `count(*)`。
- `or` 改 `union all`（各自走索引）。
- 批量操作改 `INSERT ... VALUES (...),(...)` 或 `CASE WHEN` 批量更新。
- `join` 时**小表驱动大表**，被驱动表的连接列必须有索引。

### 4.6 ★★ 结合 POS 数据贯通（真实经验，重点讲）

#### 4.6.1 数据中台的表设计

**销售流水表（核心表）设计**：

```sql
CREATE TABLE `sale_flow` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '自增主键（聚簇）',
  `tenant_id`   BIGINT UNSIGNED NOT NULL COMMENT '租户/产品线',
  `shop_id`     BIGINT UNSIGNED NOT NULL COMMENT '门店',
  `biz_date`    DATE            NOT NULL COMMENT '业务日期（分区/范围键）',
  `order_no`    VARCHAR(64)     NOT NULL COMMENT '全局单号（幂等键）',
  `amount`      DECIMAL(12,2)   NOT NULL COMMENT '金额（绝不用 float）',
  `pay_type`    TINYINT         NOT NULL,
  `status`      TINYINT         NOT NULL,
  `created_at`  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),                        -- ★ 幂等靠它
  KEY `idx_shop_date_id` (`shop_id`, `biz_date`, `id`),          -- ★ 核心查询
  KEY `idx_tenant_date` (`tenant_id`, `biz_date`, `id`)          -- ★ 跨产品线统计
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
PARTITION BY RANGE (TO_DAYS(biz_date)) (                          -- ★ 冷热分离
  PARTITION p202601 VALUES LESS THAN (TO_DAYS('2026-02-01')),
  PARTITION p202602 VALUES LESS THAN (TO_DAYS('2026-03-01')),
  ...
);
```

**设计要点（★ 每条都要能讲出"为什么"）**：

| 设计 | 理由 |
| --- | --- |
| **自增 bigint 主键** | 聚簇索引顺序插入不页分裂；二级索引存主键只要 8 字节 |
| **`uk_order_no` 唯一索引** | ★ **消息重复消费的幂等兜底**，是数据中台的生命线 |
| **`idx_shop_date_id`** | 等值（shop）+ 范围（date）+ 排序（id）符合最左前缀 + 免 filesort |
| **`DECIMAL` 而非 FLOAT** | ⚠️ float 有精度问题，**金额绝不能用浮点** |
| **按 `biz_date` RANGE 分区** | ① 冷热分离（历史分区可归档到冷存储）② **删除历史数据用 `DROP PARTITION` 秒级完成**，比 `DELETE` 快几个数量级且不产生大量 undo |
| **`DATETIME(3)` 带毫秒** | 同一秒内多笔流水要能排序 |

> ⚠️ **分区表的坑（说出来显专业）**：
> - **分区键必须出现在主键/唯一键里**，否则建不了（所以我把 `biz_date` 显式带上，或使用 `(id, biz_date)` 复合主键）。
> - **分区数不要太多**（几百个以上时优化器选分区本身有开销）。
> - **跨分区查询会扫所有分区**，所以查询条件**必须带上分区键**。

#### 4.6.2 ★ 批量写入优化（你的真实经验）

> **一句话**：批量写入的三个杠杆是 —— **① 合并 SQL 减少网络往返和事务开销 ② 控制批次大小避免大事务 ③ 用 upsert 顺手解决幂等**。

| 优化点 | 做法 | 收益 |
| --- | --- | --- |
| **批量 INSERT** | `INSERT INTO t (a,b) VALUES (1,2),(3,4),...` 一条 SQL 插多行 | ① 一次网络往返 ② 一个事务一次提交（**少 N 次 redo fsync**） |
| **批次大小** | **每批 500 ~ 1000 行**（GORM `CreateInBatches(&list, 500)`） | 太小浪费往返；太大则**单事务过大 → 主从延迟、undo 膨胀、锁持有久** |
| **事务包裹** | 手动 `BEGIN` / `COMMIT` 包住多批（而不是 mysql 驱动 autocommit 逐条） | 减少提交次数（但要权衡） |
| **关闭 binlog 的无关开销** | 数据同步表可考虑 `binlog_format=ROW` + `binlog_row_image=minimal` | binlog 体积小很多 |
| **幂等 upsert** | `INSERT ... ON DUPLICATE KEY UPDATE` | ⚠️ **别用 `REPLACE INTO`**（它是 delete + insert，会丢其他列、触发级联删除、自增 ID 跳号） |

> **项目话术（POS RabbitMQ 消费落库，必背）**：
> "POS 中台消费 RabbitMQ 的流水数据时，我做的是**批量化 + 幂等**两条线：
> **批量化**上，消费端不是来一条写一条，而是**攒够 500 条或满 1 秒就批量写一次**，用 GORM 的 `CreateInBatches` 一次落库；队列消费和数据库写入解耦后，单次插入的 SQL 开销被摊薄到 1/500，**吞吐提升了大概一个数量级**。批次大小选 500 是因为实测再往上收益递减，而**单事务太大反而会拉长主从延迟**——我曾经用过 5000 一批，主从延迟直接跳到十几秒。
> **幂等**上，每张表都有业务唯一键 `order_no` 的唯一索引，写入统一走 `INSERT ... ON DUPLICATE KEY UPDATE`，**即使消息重复投递，最坏结果也只是把同样的值再写一遍**。另外我在消费端前面用 Redis 做了一层 `SETNX` 快速去重，命中就跳过，**避免把重复流量打到数据库**——Redis 是"快筛"，数据库唯一索引是"兜底"，**两层缺一不可**：Redis 可能因为过期或者重启失效，数据库那层是最后防线。"

> ⚠️ **面试官可能追问「批量写入失败了怎么办」**：
> "**整批失败就整批重投，不能部分提交**——所以一批就是一个事务。另外 `ON DUPLICATE KEY UPDATE` 和**唯一索引**保证了重投是安全的（幂等）。这批里有坏数据（比如字段超长）的话，我会**把这批拆开逐条重试**，把坏数据单独扔进一张 `dead_letter` 表人工处理，剩下的照常入库——**绝不能让一条脏数据卡住整条队列**。"

#### 4.6.3 冷热数据分离

> **一句话**：**热数据留 MySQL，温数据进汇总表/ES，冷数据归档到对象存储或 Mongo/历史库**——通过分区表让"归档"变成一次 `DROP PARTITION`。

- **触发时机**：单表超过 2000 万行、或查询 P99 开始抖动、或历史数据查询占比极低（< 5%）。
- 三种做法：
  1. **RANGE 分区 + DROP PARTITION**（如上）。
  2. **按时间分表**（`sale_flow_202601`），查询走路由层。
  3. **归档到冷库**（历史表 / Mongo / 对象存储），MySQL 只留最近 N 个月。

### 4.7 ★ 结合 LoveSpouse（高并发写与冷热分离）

**问题**：数字人对话系统每天产生大量对话记录（每条消息都落库），并且**长期记忆需要跨会话读取**。

| 数据 | 特征 | 存储策略 |
| --- | --- | --- |
| **近期对话消息** | 写多、读多、只在会话活跃期内被读 | **Redis List/ZSet 做热存**（最近 N 条）+ 异步落 MySQL |
| **会话摘要** | 写少、读多、按会话查 | MySQL，按 `session_id` 索引；**生成后不常变** |
| **长期摘要 / 稳定事实** | 写少、读多、按 role_id 查 | MySQL + **Redis 缓存**（角色维度缓存，命中率高） |
| **金币流水** | **高频写、不能丢、要能对账** | Redis 实时扣减 + MySQL 账本（下一节详述） |

> 项目话术：
> "对话记录我做了**读写分离**：**写入**走「Redis List 缓存最近 N 条 + 异步批量落 MySQL」，因为对话列表查询 90% 都是最近几十条，**根本不需要每次查库**；**落库用批量写 + 按 session 分片**，避免单个会话的大事务。**读取**分两路：**短期上下文从 Redis 直接拿**（一次 `LRANGE` 就够），**长期记忆（摘要、稳定事实）走 MySQL + 角色维度缓存**。这样做的好处是**写入路径完全异步、不进事务**，对话接口的延迟不受落库影响。
> 另外我做了**冷热分离**：超过 N 天的对话记录从主表归档到历史表，主表只保留活跃会话，**主表体积小则索引小，查询就快**。"

## 五、Redis

> **你在这一节的定位**：**LoveSpouse 的金币计费是你的第二张王牌**，必须讲到"设计者"的深度；POS 数据贯通里 Redis 的用法是补充。**Redis 是面试里最容易问穿的部分**（因为大家都写过 `SET`/`GET`），所以你要准备的是**底层 + 一致性 + 分布式锁**这三块硬骨头。

### 5.1 数据结构与选型

> **一句话**：Redis 有 9 种常用结构，**选型的判断依据是「我要的是单个值、字段集合、有序列表、去重集合、带分数的排序集合，还是计数/近似/位置/消息流」**。

| 结构 | 底层实现 | 典型场景 | 命令示例 |
| --- | --- | --- | --- |
| **String** | SDS（int / embstr / raw 三种编码） | **计数、缓存对象、分布式锁、限流** | `INCR`、`DECR`、`SETNX`、`SETEX` |
| **Hash** | listpack（小）/ hashtable（大） | **对象存储**（用户信息、商品档案）、**部分字段更新** | `HSET`、`HINCRBY`、`HGETALL` |
| **List** | quicklist（= 双向链表 + listpack 节点） | **消息队列、最新 N 条、时间线** | `LPUSH`+`BRPOP`、`LRANGE` |
| **Set** | intset（整数）/ listpack / hashtable | **去重、共同好友（交集）、抽奖** | `SADD`、`SINTER`、`SISMEMBER` |
| **ZSet** | listpack / **跳表 + 字典** | ★ **排行榜、延时队列（score=时间戳）、滑动窗口限流** | `ZADD`、`ZRANGEBYSCORE`、`ZREMRANGEBYSCORE` |
| **Bitmap** | String 的位操作 | **签到、活跃用户、布隆过滤器** | `SETBIT`、`BITCOUNT`、`BITOP` |
| **HyperLogLog** | 概率算法（12KB 固定） | **UV 统计**（误差 0.81%） | `PFADD`、`PFCOUNT` |
| **GEO** | ZSet（geohash 编码为 score） | **附近的人、位置检索** | `GEOADD`、`GEOSEARCH` |
| **Stream** | Radix Tree | **带消费组的消息队列**（可回溯） | `XADD`、`XREADGROUP`、`XACK` |

**★ 选型口诀（面试时好用）**：

> "**单值或计数用 String，对象用 Hash，列表用 List，去重用 Set，要排序用 ZSet，只问'有多少个不重复'用 HyperLogLog，问'某个用户在不在'用 Bitmap。**"

⚠️ **踩坑提醒（说出来很专业）**：
- **Hash 不要塞太多字段**（`HGETALL` 在大 Hash 上会阻塞）；**单 Hash 建议 < 1000 字段**，超了就分桶（`user:1:profile`、`user:1:stat`）。
- **List 做队列不适合多消费者**（没有 ACK，弹出即丢）；要 ACK 用 **Stream** 或用专业 MQ。
- **HyperLogLog 不能取具体元素**，只能估数量；**Bitmap 需要连续 ID**，稀疏 ID 会浪费空间。

### 5.2 底层原理

#### 5.2.1 SDS

> **一句话**：SDS（简单动态字符串）= `len + alloc + buf` 的结构体，**O(1) 取长度、二进制安全、预分配减少内存重分配**。

- **vs C 字符串**：C 字符串靠 `\0` 判断结尾 → ① 取长度 O(n) ② **不能存二进制**（图片、protobuf 里可能有 `\0`）③ 拼接必扩容。
- **空间预分配**：扩容时**多分配一倍**（< 1MB 时翻倍，≥ 1MB 时多给 1MB），减少后续 append 的重新分配。
- **惰性释放**：缩短时不立即回收内存，留着下次用。

#### 5.2.2 跳表（ZSet 底层）

> **一句话**：跳表 = **多层链表 + 随机层高**，查询平均 O(logN)，**实现比红黑树简单得多，且范围查询天然友好**。

- **为什么 ZSet 用跳表而不用 B+ 树**：跳表是**内存结构**，不存在磁盘 IO 的问题；插入删除只改指针，**不需要旋转/分裂**；范围查询顺着底层链表走即可。
- **ZSet 是"跳表 + 字典"双结构**：字典（`member → score`）让 `ZSCORE` 是 O(1)；跳表让**范围/排行查询**高效。（**用空间换两个操作都很强**）
- **层高怎么定**：**每层晋升概率 1/4**，期望层高 ~1.33，最大 32 层。
- **什么时候从 listpack 转跳表**：`zset-max-listpack-entries`（默认 **128**）或 `zset-max-listpack-value`（默认 **64** 字节）任一超出即转换。

#### 5.2.3 渐进式 rehash

> **一句话**：字典扩容时**不一次性搬完**，而是维护两张哈希表、用一个 `rehashidx` 指针**每次操作顺带搬一个桶**，把 O(N) 的阻塞摊到多次操作里。

- **期间的行为**：**查找两张表都查**（先查 ht[0] 再查 ht[1]）；**新增只写 ht[1]**（保证 ht[0] 只减不增，最终能搬空）。
- **触发条件**：`负载因子 = used / size`；**≥ 1 且没有 bgsave/bgrewriteaof 时扩容**，≥ 5 时强制扩容；< 0.1 时缩容（有持久化子进程时不缩）。
- **为什么要这样**：Redis 是单线程，一次搬百万 key 会**阻塞几秒**——这是"如何避免阻塞"的经典解法，**面试常考**。

#### 5.2.4 ★ 单线程模型

> **一句话**：**Redis 的单线程指的是"命令执行是单线程"**——它快的原因是「**纯内存操作 + epoll IO 多路复用 + 无锁无竞争 + 高效数据结构**」，不是"因为单线程所以快"。

| 快的原因 | 说明 |
| --- | --- |
| **纯内存** | 内存随机访问 ~100ns，比磁盘快 10 万倍 |
| **IO 多路复用** | epoll + 事件循环，单线程管理上万连接 |
| **避免锁与上下文切换** | 没有多线程竞争，不需要加锁，也没有线程切换开销 |
| **高效数据结构** | SDS、跳表、listpack、渐进式 rehash 都是精心设计 |
| **协议简单** | RESP 协议解析成本低 |

**⚠️ 单线程的代价（必须说）**：**一个慢命令会阻塞所有客户端**。

| 危险命令 | 替代方案 |
| --- | --- |
| `KEYS *` | **`SCAN`**（游标分批） |
| `HGETALL`（大 Hash） | `HSCAN` / 拆分成多个小 Hash |
| `DEL`（大 Key） | **`UNLINK`**（异步删除） |
| `FLUSHALL` | `FLUSHALL ASYNC` |
| Lua 脚本写长循环 | 拆小、控制脚本耗时（`lua-time-limit`） |

**★ Redis 6.0 的多线程 IO**：
- **只是把"网络读写 + 协议解析"放到多线程**（`io-threads`，默认 4），**命令执行仍然是单线程**。
- 目的：解决高并发下**网络 IO 成为瓶颈**的问题（尤其大 value 时）。
- ⚠️ **别答成"Redis 6.0 变成多线程了"**——这是经典陷阱题。正确说法：**"6.0 引入多线程 IO 处理网络读写，但命令执行依然单线程，所以数据结构的原子性和无锁设计没有变。"**

### 5.3 持久化

> **一句话**：**RDB 是快照（恢复快、丢数据多），AOF 是日志（丢数据少、文件大、恢复慢）**，**4.0 之后的混合持久化（RDB 全量 + AOF 增量）是生产推荐**。

| | RDB | AOF |
| --- | --- | --- |
| **原理** | **fork 子进程**，用 COW（写时复制）遍历内存写二进制快照 | 追加记录**写命令**，重启时重放 |
| **触发** | `save` 规则（如 900 秒 1 次变更）、`BGSAVE` | `appendonly yes`，`appendfsync` 控制 |
| **文件** | 小、紧凑 | 大（可 `BGREWRITEAOF` 重写压缩） |
| **恢复速度** | ✅ 快（直接加载） | ❌ 慢（重放所有命令） |
| **丢数据** | ⚠️ 丢**最后一次快照后**的所有数据 | 取决于 fsync 策略 |
| **fork 代价** | ⚠️ 内存大时 fork 会阻塞（页表复制），COW 期间内存可能翻倍 | 重写时同样有 fork 代价 |

**AOF 的 fsync 策略（★ 高频）**：

| `appendfsync` | 行为 | 丢数据 |
| --- | --- | --- |
| `always` | 每条命令都 fsync | **几乎不丢**，性能最差 |
| **`everysec`（默认）** | 每秒 fsync 一次 | **最多丢 1 秒**（推荐折中） |
| `no` | 交给 OS 决定 | 丢得多 |

**AOF 重写**：`BGREWRITEAOF` → fork 子进程**根据当前内存状态生成新 AOF**（比如 100 次 `INCR` 压成 1 条 `SET`）；重写期间的新命令**写入 AOF 重写缓冲区**，重写完成后追加到新文件。
- ⚠️ **对比 MySQL 的 binlog**：**AOF 是写后日志（命令执行后才记录，不检查语法），redo log 是写前日志（WAL）**——Redis 不担心语法错误（命令已经执行成功了），MySQL 需要 redo 保证崩溃恢复。

**混合持久化（4.0+，`aof-use-rdb-preamble yes`）**：AOF 文件**前半部分是 RDB 格式的全量快照，后半部分是 AOF 格式的增量命令**——**兼得"恢复快"和"丢数据少"**。

> ★ 面试话术：
> "生产上我会开**混合持久化**：AOF 保证最多丢 1 秒（everysec），RDB 头保证重启恢复快。**但我要提醒一点：Redis 的持久化不能当数据库用**——它是异步的，主从切换、实例宕机都可能丢数据。**所以凡是"不能丢"的数据（比如金币余额），我一定在 MySQL 里有账本，Redis 只是加速层**，这是我在 LoveSpouse 计费系统里的核心设计。"

### 5.4 高可用

#### 5.4.1 主从复制

> **一句话**：**一主多从，主写从读**；从库首次连接触发**全量同步（RDB + 缓冲区）**，之后走**增量同步（repl_backlog）**。

- **流程**：从库 `REPLICAOF` → `PSYNC` → 主库 `BGSAVE` 生成 RDB 发给从库 + 期间的新写命令进 **replication buffer** → 从库加载完 RDB 后开始接收增量命令。
- **`repl_backlog`（复制积压缓冲区）**：环形缓冲，从库短暂断连后可**增量续传**；⚠️ **如果从库落后超过 backlog 容量或 `replid` 变了，就要全量重同步**（和 MongoDB 的 oplog 是同一类机制）。
- **⚠️ 主从延迟**：从库读到的可能是旧数据；**「写后立即读」的场景必须走主库**（或者用 `WAIT` 命令等 N 个副本确认）。

#### 5.4.2 哨兵（Sentinel）

> **一句话**：哨兵是**独立进程的集群**，负责监控、通知、**自动故障转移**和**配置提供**——它解决了"主库挂了要人工切"的问题。

- **主观下线（sdown）** 与 **客观下线（odown）**：单个哨兵 ping 超时 = 主观下线；**达到 `quorum` 数量的哨兵都认为下线 = 客观下线**。
- **选举 Leader 哨兵**：哨兵之间用类 Raft 的投票选出**一个**执行故障转移。
- **选新主库的顺序**（★ 背下来）：① `replica-priority` 小的优先 ② 复制偏移量（offset）**大**的优先（数据最新） ③ `runid` 小的优先。
- **客户端如何感知**：哨兵通过 **Pub/Sub** 发布新主库地址，**客户端订阅 `+switch-master` 频道**（或用支持哨兵的客户端库）。
- ⚠️ **哨兵的坑**：**脑裂**——主库假死但还在跑，哨兵选了新主，**旧主库恢复后成了从库，它期间收到的写入会丢失**（可用 `min-replicas-to-write` 限制主库至少要有 N 个从库才允许写，预防脑裂）。

#### 5.4.3 ★ Cluster（集群）

> **一句话**：Redis Cluster = **数据分片（16384 个槽）+ 去中心化（Gossip 协议）+ 主从复制**，**槽是数据分布的单元，key 决定它在哪个节点**。

| 概念 | 说明 |
| --- | --- |
| **槽位（slot）** | **16384 个**，`CRC16(key) % 16384` 决定归属；每个主节点负责一部分槽 |
| **为什么是 16384** | ★ 加分点：① 心跳包要带**槽位 bitmap**，16384 位 = **2KB**，65536 位 = 8KB，**心跳包太大很浪费带宽** ② 集群规模一般不超过 1000 个节点，16384 够用了 |
| **Gossip 协议** | 节点之间互相 ping/pong 交换状态，**去中心化**，没有 proxy |
| **转发** | 客户端可以连任意节点；槽不对会返回重定向 |

**★ MOVED vs ASK（必答，最容易混）**：

| | MOVED | ASK |
| --- | --- | --- |
| **含义** | "这个槽**永久**不归我管了" | "这个槽**正在迁移**，这个 key 现在在对面" |
| **触发** | 槽的归属已经变更完成 | **槽迁移过程中**，key 已经搬到目标节点 |
| **客户端动作** | **更新本地槽位缓存**，以后直接连新节点 | **不更新缓存**，先给目标节点发 `ASKING` 再发命令 |

> **记忆方法**：**MOVED = 搬家搬完了（永久改地址）；ASK = 搬家搬到一半（这次去对面拿一下，下次还来问我）。**

**其他要点**：
- **跨槽操作不支持**：`MGET`、`MSET`、涉及多 key 的事务、Lua 脚本——**所有 key 必须在同一个槽**。解决方案：**用 Hash Tag**（`{user:1}:name` 和 `{user:1}:age` 中的 `{}` 内容相同 → 强制同槽）。
- **集群的批量操作**：用 `redis-cli --cluster` 或客户端 SDK 按节点分组并行执行。
- **扩缩容**：加节点 → 分配槽（`reshard`）→ 迁移过程中用 ASK 保证可用。

### 5.5 ★ 缓存三兄弟（必背）

| 问题 | 现象 | 根因 | 解决方案 |
| --- | --- | --- | --- |
| **缓存穿透** | 查一个**不存在**的数据，缓存没有 → 每次都打到 DB | 恶意攻击、参数错误 | ① **缓存空值**（短 TTL，如 60 秒）② **布隆过滤器**（前置拦截）③ 参数校验 + 限流 |
| **缓存击穿** | **某个热点 key 过期**的瞬间，大量请求同时打到 DB | 热点 key + 同时失效 | ① **互斥锁/分布式锁**（只让一个线程去查 DB）② **逻辑过期**（key 不过期，值里带逻辑过期时间，异步更新）③ 热点 key 永不过期 + 后台刷新 |
| **缓存雪崩** | **大量 key 同时失效**，或 Redis 整体宕机，DB 被打垮 | TTL 集中、Redis 故障 | ① **TTL 加随机值**打散 ② **多级缓存**（本地 Caffeine + Redis）③ **熔断降级**（DB 保护）④ Redis 集群 + 持久化 |

**★ 各自的代码/伪代码要说得出**：

```go
// 缓存穿透：空值缓存
val, err := rdb.Get(ctx, key).Result()
if err == redis.Nil {
    v, e := db.Query(key)
    if e == sql.ErrNoRows {
        rdb.Set(ctx, key, "NULL", 60*time.Second)  // ★ 缓存空值，短 TTL
        return nil, ErrNotFound
    }
    ...
}

// 缓存击穿：单飞（singleflight）+ 分布式锁
v, err, _ := singleflightGroup.Do(key, func() (interface{}, error) {
    lockKey := "lock:" + key
    ok, _ := rdb.SetNX(ctx, lockKey, "1", 3*time.Second).Result()
    if !ok { time.Sleep(50*time.Millisecond); return rdb.Get(ctx, key) } // 自旋等
    defer rdb.Del(ctx, lockKey)
    // 查 DB → 写缓存（★ 注意：写缓存也要带随机 TTL）
    ttl := 300*time.Second + time.Duration(rand.Intn(60))*time.Second
    v := loadFromDB(key)
    rdb.Set(ctx, key, v, ttl)
    return v, nil
})
```

> **★ 项目话术**：
> "缓存三兄弟我在 POS 中台里都做了防护：**热点商品档案的 key 用 `singleflight` 合并并发请求**（同一进程内只发一次 DB 查询，比分布式锁轻），**所有缓存 TTL 都加了 0~60 秒的随机抖动**避免同时失效，**不存在的商品用空值缓存 60 秒**防止刷接口。**另外我加了一层本地缓存**放最热的租户配置，Redis 挂了也不会瞬间全打 DB。"

### 5.6 ★ 缓存一致性（必考）

> **一句话**：**没有"强一致"的缓存方案，只有"最终一致"和"不一致窗口多小"**。工程上主流是 **Cache Aside（先更新 DB，再删缓存）**，代价是**删除失败/并发交叉时会有短暂的脏数据**。

**三种方案对比（★ 直接甩这张表）**：

| 方案 | 顺序 | 问题 | 结论 |
| --- | --- | --- | --- |
| **先删缓存，再更新 DB** | DEL → UPDATE | ⚠️ **最差**：删完缓存、DB 还没更新，此时并发读会**把旧值重新加载进缓存**，脏数据长期存在 | ❌ 不推荐 |
| **先更新 DB，再删缓存**（Cache Aside） | UPDATE → DEL | ⚠️ 极小概率不一致：读线程在 DEL 之前把旧值写回缓存；或 DEL 失败 | ✅ **推荐（业界标准）** |
| **延迟双删** | DEL → UPDATE → 延迟 N 毫秒 → DEL | 缓解上面的窗口，但**延迟时间难确定**、第二次 DEL 也可能失败 | 🔶 补充手段 |

**为什么"先更新 DB，再删缓存"的不一致窗口极小**：
> 要出问题需要「**读请求查 DB 拿到旧值** → **写请求更新 DB 并删缓存** → **读请求才把旧值写进缓存**」这个顺序。而"查 DB + 写缓存"的耗时通常**远小于**"更新 DB + 删缓存"，所以并发交叉的概率极低。

**★ 更稳的方案（说出来是加分项）**：

1. **删缓存失败怎么办** → **重试**（消息队列 / 本地重试表）+ **订阅 MySQL binlog（Canal/Debezium）异步删缓存**，把"删缓存"从业务代码里解耦出去。
2. **给缓存加过期时间**——**最终一致的最后保险**，即使删失败，TTL 到了自然恢复。
3. **读写都加版本号**：缓存里存 `{data, version}`，DB 更新时 version+1，读到旧 version 就丢弃。
4. **强一致场景直接不用缓存**，或缓存只做"降级读"。

> ★ 面试话术（讲完整版）：
> "缓存一致性我会先给结论：**在允许缓存存在的架构里，强一致是做不到的**——因为更新 DB 和删缓存是两个操作，没有分布式事务保证。**能做的是把不一致窗口做到尽可能小**。
> 我的方案是**先更新数据库，再删缓存**，这是业界主流，因为它的不一致窗口只在"读操作比写操作慢很多"的极端并发下才出现。**但光靠这两步不够**，我会加两道保险：**第一道是给缓存设 TTL**，就算删失败，过期时间到了也会自然纠正；**第二道是订阅 binlog**——用 Canal 把删缓存的动作做成异步消费，即使业务代码里那次删除失败，binlog 这条链路也会重试，**而且它把缓存失效逻辑从业务代码里解耦了，业务只需要保证 DB 写成功**。
> 至于**延迟双删**，我个人不太推荐作为主力方案，因为**延迟多久很难定**——定短了没用，定长了就是把不一致时间人为拉长。**如果我确实需要读到自己刚写的数据，我会让这次读直接走主库**，而不是在缓存上做文章。"

### 5.7 ★ 分布式锁（必考）

> **一句话**：Redis 分布式锁 = **`SET key value NX PX ttl`**（一条命令同时完成"不存在才设置"和"设置过期"），**释放必须用 Lua 校验 value 再删**，**续期用看门狗**。

**★ 三段式演进（面试这样讲最清楚）**：

```go
// ① 最朴素（❌ 有 bug）
ok, _ := rdb.SetNX(ctx, key, "1", 10*time.Second).Result()
// bug1: 业务超时 → 锁提前过期 → 别人拿到锁 → 你释放时删了别人的锁
// bug2: SetNX + Expire 不是原子的 → 中间宕机就死锁（SetNX 已经解决）

// ② 唯一 value + Lua 释放（✅）
val := uuid.New().String()                                  // ★ 唯一标识
ok, _ := rdb.SetNX(ctx, key, val, 10*time.Second).Result()
// 释放：Lua 保证"判断是自己持有"和"删除"是原子的
var releaseScript = redis.NewScript(`
  if redis.call("GET", KEYS[1]) == ARGV[1] then
      return redis.call("DEL", KEYS[1])
  else
      return 0
  end`)
releaseScript.Run(ctx, rdb, []string{key}, val)

// ③ 看门狗自动续期（✅✅ 生产方案 = Redisson 的看门狗）
// 锁默认 30 秒，后台每 10 秒检查：业务还在跑就把锁续到 30 秒
// 业务结束 → 停止续期 → 释放锁
```

**⚠️ 必须知道的坑**：

| 坑 | 说明 | 应对 |
| --- | --- | --- |
| **误删别人的锁** | 业务超时锁过期 | **唯一 value + Lua 校验** |
| **业务没跑完锁过期** | 锁 TTL 小于业务耗时 | **看门狗续期**（或合理设置 TTL） |
| **主从切换丢锁** | 主库加了锁还没同步到从库就宕机，从库升主 → 别人能拿到同一把锁 | **Redlock**（多节点）或 **改用 ETCD** |
| **锁不可重入** | 同一线程二次加锁失败 | Redisson 用 Hash 实现可重入（`field=线程ID, value=重入次数`） |

**Redlock 及其争议（★ 高级考点）**：
- **Redlock 算法**：向 **N 个（通常 5 个）独立 Redis 主节点**依次加锁，**超过半数成功且总耗时小于锁有效期**才算加锁成功。
- **Martin Kleppmann 的批评**（背这个名字非常加分）：① 依赖**各节点时钟基本同步**，而**时钟漂移/GC 停顿/NTP 跳变**会让锁提前失效 ② 即便 Redlock 正确，**也解决不了"业务侧"的问题**——锁过期时业务还在跑（需要 **fencing token**：把递增的 token 传给被保护的资源，资源侧拒绝旧 token 的请求）。
- **结论口径**：**"如果是效率型场景（重复做一次也无害），Redis 锁够用；如果是正确性型场景（做两次会出错，比如扣款），我不会只靠 Redis 锁，我会在数据层再加唯一约束或乐观锁兜底，或者直接换成 ETCD。"**

**★ Redis 锁 vs ETCD 锁（本岗位很可能会问，因为你有 ETCD 经验）**：

| | Redis 锁 | ETCD 锁 |
| --- | --- | --- |
| **一致性** | 主从异步复制，**可能丢锁** | **Raft 多数派写入**，强一致 |
| **实现** | `SET NX PX` + Lua | **Lease（租约）+ Revision + Watch** |
| **续期** | 看门狗（业务侧实现） | **租约自动续期（KeepAlive）** |
| **阻塞等待** | 要自己轮询 | **Watch 天然支持排队等待** |
| **性能** | ✅ 更高（内存 + 单线程） | 略低（要多数派落盘） |
| **适用** | 效率型、高并发、可容忍极小概率失效 | **正确性要求高**、配置/选主/调度类 |

> **项目话术**："我做过 go-zero + ETCD 的服务（POS 数据贯通里用的就是 ETCD 做服务注册发现和配置），**ETCD 的 lease + watch 本身就是一把很可靠的分布式锁**，语义比 Redis 干净——租约过期锁自动释放，客户端用 watch 排队。所以在**控制平面、选主、需要强一致的场景我会优先 ETCD**；**高并发的业务计数、防重复提交这种场景用 Redis**，因为性能差一个量级，而且失败了影响可控。"

### 5.8 大 Key / 热 Key

> **一句话**：**大 Key 害的是"阻塞"（删除、读写、持久化都变慢），热 Key 害的是"单点"（某个节点 CPU 打满）**——两者都要靠拆。

| | 大 Key | 热 Key |
| --- | --- | --- |
| **定义** | 经验值：String > 10KB / 集合元素 > 5000 | 单 key QPS 占比极高（如 10 万 QPS 里 5 万打在一个 key 上） |
| **危害** | ① 单次操作耗时高，**阻塞单线程** ② 网络拥塞 ③ `DEL` 大 key 直接卡死 ④ 持久化 fork/写盘慢 ⑤ 集群下**数据倾斜** | ① **该节点 CPU 打满**，影响同节点其他 key ② 缓存击穿时打垮 DB |
| **发现** | `redis-cli --bigkeys`（遍历，Sample 模式）、`MEMORY USAGE key`、分析 RDB 文件（`rdb-tools`）、离线巡检 | `redis-cli --hotkeys`（需 LFU 策略）、`MONITOR`（生产慎用）、**客户端埋点统计**、代理层（如 Redis Proxy）统计 |
| **解决** | ① **拆分**：大 Hash → 按字段分桶（`user:{id}:0..N`）；大 List → 分片 ② **渐进删除**：`UNLINK` 异步删，或 `HSCAN` + `HDEL` 分批 ③ 压缩 value（protobuf/gzip） ④ 用 `SCAN` 替代 `KEYS` | ① **本地缓存**（进程内 Caffeine，抗量最大、最有效）② **多副本 key**：`hotkey:1`~`hotkey:N` 随机取，把压力散到多个节点 ③ **读写分离**：热 key 走从库 ④ 集群下把热 key 所在 slot 独立扩容 |

> 项目话术："我在 POS 里遇到过**商品档案的 Hash 过大**——一个租户的全部商品塞在一个 Hash 里，`HGETALL` 直接卡了 300 毫秒。后来我**按商品 ID 取模拆成 64 个 Hash**（`goods:{tenant}:{id%64}`），单次操作从毫秒级降到微秒级。**大 key 的危害不是"慢"，而是"它把整个 Redis 拖慢"**——因为命令执行是单线程，一个慢命令会让所有客户端排队。"

### 5.9 Pipeline / Lua / 事务

> **一句话**：**Pipeline 省网络往返（不保证原子）；Lua 保证原子且能写逻辑（但会阻塞）；MULTI/EXEC 事务没有回滚、不能条件判断，所以实战中基本被 Lua 替代。**

| | Pipeline | Lua 脚本 | MULTI/EXEC 事务 |
| --- | --- | --- | --- |
| **原子性** | ❌ 不是原子（命令之间可能插别的请求） | ✅ **整个脚本原子执行** | ✅ 提交后顺序执行不被打断 |
| **能否读返回值做判断** | ❌ | ✅ **可以**（这是关键优势） | ❌ 不能（命令先入队后执行） |
| **回滚** | 不涉及 | ❌ 出错不回滚（已执行的部分保留） | ❌ **不支持回滚**（运行时错误其他命令继续执行） |
| **阻塞风险** | 低 | ⚠️ **脚本越长阻塞越久** | 低（命令短） |
| **用途** | 批量读写（如一次取 100 个 key） | ★ **原子扣减、分布式锁释放、限流** | 很少用 |

**⚠️ 三句必须说清的话**：
1. **Pipeline 不是原子**——它只是"打包发送"，服务端还是逐条执行，期间可能插别人的命令。
2. **Lua 的原子性来自 Redis 单线程执行**——脚本执行期间不会执行其他命令；但**代价是脚本必须极短**（毫秒级），否则整个实例卡住。
3. **Redis 事务不支持回滚**——这是 MySQL 思维的直接冲突点，**面试官爱问**。原因：Redis 认为语法错误在执行前就能发现（入队时直接报错），而运行时错误（如对 String 执行 `LPUSH`）是**编程错误**，回滚也没意义，不如继续执行。

### 5.10 ★★ 结合 LoveSpouse 金币计费（你的王牌，必须讲透）

> **背景**：数字人接 Gemini Live 实时语音，按用量**扣金币**；真人用户会**并发发起多路通话**（多设备、重试、网络抖动重连），这是**典型的高并发扣减不能超扣的场景**。

#### 5.10.1 方案对比（★ 这是这道题的核心）

| 方案 | 做法 | 能防超扣吗 | 问题 |
| --- | --- | --- | --- |
| **① 先查后扣** | `GET balance` → 判断够 → `DECRBY` | ❌ **不能** | 典型的 check-then-act，**两个请求都查到 100，都扣 100，余额 -100** |
| **② DECRBY 后判断** | `DECRBY` → 如果 < 0 再 `INCRBY` 补回 | ✅ 能 | ⚠️ 会短暂出现**负数余额**（其他读请求会看到），且**回补失败会真超扣**；语义脏 |
| **③ Lua 脚本原子扣减** ★ | 在 Lua 里"判断 + 扣减"一气呵成 | ✅ **能，且无中间态** | 脚本要短；并发高时是单线程串行（但每条都是微秒级） |
| **④ 分布式锁** | 加锁 → 查 → 扣 → 解锁 | ✅ 能 | ❌ **太重**：锁竞争、锁失效、性能差，**只在跨资源多步操作时才用** |
| **⑤ MySQL 悲观锁** | `SELECT ... FOR UPDATE` | ✅ 能 | ❌ 数据库成瓶颈，QPS 上不去 |

**★ 最终方案：Lua 原子扣减 + 预扣/结算两阶段 + 幂等键**

```lua
-- 扣减脚本：KEYS[1]=余额 key  KEYS[2]=幂等key  ARGV[1]=扣减数量  ARGV[2]=幂等key的TTL
-- 返回：>=0 扣减后的余额；-1 余额不足；-2 重复请求
local balance = tonumber(redis.call('GET', KEYS[1]) or '-1')
if balance < 0 then return -1 end                       -- 账户不存在，视为异常
local amount = tonumber(ARGV[1])
if balance < amount then return -1 end                   -- ★ 余额不足，直接拒绝，不产生中间态
if redis.call('EXISTS', KEYS[2]) == 1 then return -2 end -- ★ 幂等：同一 requestId 只扣一次
redis.call('SET', KEYS[2], '1', 'EX', tonumber(ARGV[2]))
redis.call('DECRBY', KEYS[1], amount)
return balance - amount
```

```go
// Go 调用（go-redis）
var deductScript = redis.NewScript(luaDeduct)

func (s *BillingSvc) Deduct(ctx context.Context, userID int64, amount int64, requestID string) (int64, error) {
    keys := []string{
        fmt.Sprintf("coin:balance:%d", userID),
        fmt.Sprintf("coin:idem:%s", requestID),   // ★ 幂等键
    }
    res, err := deductScript.Run(ctx, s.rdb, keys, amount, 86400).Int64()
    if err != nil { return 0, err }
    switch res {
    case -1: return 0, ErrInsufficientBalance
    case -2: return 0, ErrDuplicateRequest     // 幂等命中，直接返回成功
    }
    return res, nil
}
```

#### 5.10.2 为什么用 Redis 而不是 MySQL

> **一句话**：**余额扣减是"高频写 + 极致原子 + 要抗并发"，这是 Redis 的主场；MySQL 是账本（要持久、要对账），不是计数器。**

- 实时语音按秒/按 token 计费 → **扣减频次极高**（一次通话几十上百次），MySQL 行锁扛不住。
- Redis 的 `DECRBY` 是**内存原子操作**，单机 10 万 QPS 级别，**Lua 保证"判断 + 扣减"不可分割**。

#### 5.10.3 ★ 预扣 + 结算（防止"通话跑完发现钱不够"）

**问题**：实时语音是**先消费后付费**的模式——如果通话结束时才扣，用户余额不够就产生了坏账。

**方案：两阶段（借鉴 TCC 思路）**：

```
① 开始通话 → 按"预估时长 × 单价"预扣（freeze）
        ↓ 余额不足直接拒绝发起通话
② 通话中   → 心跳续期：每 N 秒按已用时长结算一次（增量扣减）
        ↓ 余额耗尽 → 网关侧主动中断通话，通知客户端
③ 通话结束 → 按实际用量结算：多退少补
```

| 阶段 | 目的 |
| --- | --- |
| 预扣 | **把"余额不足"拦在通话开始之前**，避免产生坏账 |
| 心跳续期 | 长通话不会因为预扣额度用完被误中断；也能**及时发现余额耗尽并中断** |
| 结束结算 | 按实际用量**退还**多扣的部分（多退少补），体验更好 |

> **话术**："我开始做的是**先扣后通话**的预扣模型——发起通话时按预估时长先冻结一笔，余额不够直接拒绝，**这样根本不会产生坏账**。通话过程中按心跳做增量结算，余额耗尽就主动断线。**结束时按实际用量多退少补**，避免按整分钟扣导致用户投诉。这套跟 TCC 的思路是一样的：**Try（预扣）/ Confirm（增量结算）/ Cancel（退还）**——只是我没上分布式事务框架，用 Lua 脚本 + 幂等键在 Redis 里实现了。"

#### 5.10.4 ★ 扣减与落库的一致性 + 对账

**问题**：Redis 扣了，MySQL 流水没写 → 数据不一致；Redis 挂了 → 余额丢失。

**方案：Redis 是"实时账"，MySQL 是"流水账本"，双写 + 对账**

```
① Lua 原子扣减（Redis 是权威实时余额）
② 扣减成功后：把"扣减事件"发到 MQ（或直接批量写）→ 异步落 MySQL 流水表
③ 定时对账任务：
     MySQL:  SELECT SUM(amount) FROM coin_flow WHERE user_id=?   ← 账本累计
     Redis:  GET coin:balance:{user_id}                           ← 实时余额
     对比：  初始余额 - 流水累计 == Redis 余额 ？
     不一致 → 告警 + 以 MySQL 为准修正 Redis
```

| 关注点 | 做法 |
| --- | --- |
| **幂等** | 每笔扣减带 `requestID`（通话 ID + 序号），MySQL 流水表 `request_id` 建**唯一索引** → 重复落库被拒绝 |
| **不丢** | 扣减成功后写流水失败 → **MQ 重投**（用本地消息表/事务消息保证不丢）|
| **对账** | 定时任务按用户比对 Redis 余额与 MySQL 累计流水，**差异超阈值告警** |
| **降级** | Redis 不可用 → 拒绝新的计费请求（**宁可暂时不可用，也不能乱扣钱**）；已发起的通话按本地状态继续，恢复后补账 |

> ★ **完整项目话术（这道题一定要能连续讲 2 分钟）**：
> "LoveSpouse 的金币计费我做了三层设计。
> **第一层是扣减的原子性**。最初的写法是先 `GET` 判断余额再 `DECRBY`，我在压测时发现**并发下会超扣**——两个请求同时读到 100，各自扣 100，余额变成 -100。改成 `DECRBY` 后判断负数再补回，又不干净：会短暂出现负余额，而且补回失败就真超扣了。最后我用的是 **Lua 脚本**——把"判断余额、校验幂等键、扣减"三步写在一个脚本里，**Redis 单线程执行脚本，天然原子**，既不会超扣，也不会出现负余额的中间态。
> **第二层是幂等**。客户端超时重试、网络抖动、用户手快连点，都会带来重复的扣减请求。我在 Lua 里用 `requestID` 做了一层幂等——**同一个 requestID 只扣一次，重复请求直接返回成功**，`requestID` 我设了 1 天过期，既能覆盖重试窗口又不会无限膨胀；**MySQL 流水表的 `request_id` 唯一索引是第二道防线**，即使 Redis 那层因为过期失效了，落库也会被唯一索引挡住。
> **第三层是一致性与对账**。Redis 是实时账，MySQL 是账本——**扣减成功后异步把流水落库，用 MQ 保证不丢**；再跑一个**定时对账任务**比对"Redis 余额"和"MySQL 流水累计"，有差异就告警并以 MySQL 为准修正 Redis。**这块我的原则是：Redis 可以丢，但账不能丢。**
> 另外业务上我用了**预扣 + 增量结算**：发起通话先按预估时长冻结一笔，余额不够直接拒绝，**从源头避免坏账**；通话中按心跳增量扣，余额耗尽主动断线；结束时按实际用量多退少补。"

#### 5.10.5 ★ 跨实例通话控制（你的另一个真实亮点）

**问题**：用户可能在 A 实例发起通话，重连后落到 B 实例——**怎么保证同一用户不会同时在两个实例上跑两路通话（重复计费 + 状态错乱）**？

**方案：用 Redis 做"全局会话注册表" + 分布式锁**

| 需求 | Redis 实现 |
| --- | --- |
| **同一用户只能有一路通话** | `SET call:user:{uid} {instanceID} NX PX 30000` —— 加锁成功才能发起；**用 TTL + 心跳续期**（实例挂了锁会自动释放） |
| **跨实例中断通话** | 把"中断指令"写到 `call:cmd:{uid}`，目标实例的**心跳线程轮询到就把通话停掉**（或者用 **Pub/Sub** 广播） |
| **状态同步** | 通话状态写 Redis（`call:state:{uid}` = active/ending），**任何实例都能读到**，不依赖本地内存 |
| **续期/保活** | 通话中心跳 `EXPIRE`，**实例崩溃 → 锁自动过期 → 允许用户重连** |

> 项目话术："实时语音的**跨实例控制**我用 Redis 做了一个全局通话注册表。核心是 `SET call:user:{uid} {实例ID} NX PX 30000` ——**同一用户在同一时刻只能有一个实例持有通话锁**；实例每 10 秒续期一次，如果实例崩了，锁 30 秒自动过期，用户就能在别的实例重连上。**中断通话**是通过 Pub/Sub 给目标实例发指令，目标实例收到后停止 Gemini Live 会话并做最后一次结算。**这套设计的关键点是：所有状态都在 Redis 里，实例本身无状态**——这样网关扩容、重启都不影响进行中的通话。"

### 5.11 ★ 结合 POS 数据贯通：Redis 在数据中台里的用法

| 用途 | 实现 | 要点 |
| --- | --- | --- |
| **商品档案缓存** | Hash 存商品，`goods:{tenant}:{id%64}` 分桶 | 大 key 拆分（见 5.8） |
| **RabbitMQ 消费去重** | `SETNX msg:dedup:{msgID} 1 EX 86400` | ★ **快速拦截重复消息**，DB 唯一索引兜底 |
| **接口限流** | `INCR ratelimit:{api}:{ts}` + `EXPIRE`（固定窗口）；或 ZSet 滑动窗口 | 保护下游 DB |
| **分布式锁** | `SET lock:sync:{tenant} NX PX 60000` | 防止多实例**重复跑同一个租户的同步任务** |
| **统计计数** | `HINCRBY stat:20260922 tenant:1 1` | 分钟级刷进 MySQL 汇总表 |
| **UV 去重统计** | `PFADD uv:20260922 {deviceID}` | 12KB 存千万级 UV |

> 项目话术："POS 中台里 Redis 我主要用在四个地方：**消费去重**（`SETNX` 消息 ID，命中就跳过，避免重复流量打 DB）、**商品档案缓存**（Hash 分桶，避免大 key）、**接口限流**（`INCR` + `EXPIRE` 固定窗口，防止异常客户端把 DB 打死）、**分布式锁**（保证同一租户的同步任务只有一台实例在执行）。**这四个用法有个共同点：都是"用 Redis 挡在前面保护 MySQL"**——Redis 挂了最坏是性能下降，业务逻辑不依赖它的持久性。"

## 六、消息队列

> **你在这一节的定位**：**RabbitMQ 是你的主场**（POS 数据贯通 + 商云前台都用了），**消息幂等是你的王牌**（腾讯 IM 消息幂等）。**Kafka / RocketMQ 没用过**，按"了解选型"处理。

### 6.1 为什么用 MQ

> **一句话**：MQ 解决三件事——**解耦（生产者不关心谁消费）、异步（不阻塞主流程）、削峰填谷（把突发流量缓存在队列里）**；代价是**系统复杂度上升 + 一致性变弱（从强一致变最终一致）**。

| 价值 | 说明 | 你的项目 |
| --- | --- | --- |
| **解耦** | 上游只管发消息，下游有多少消费者、怎么处理都与它无关 | POS：各产品线的流水都发到交换机，中台统一消费 |
| **异步** | 主流程不等下游完成，直接返回 | 商云前台：打印钱箱、语音提示、电子小票走 MQ 异步 |
| **削峰填谷** | 突发流量堆在队列里，消费者按自己的能力慢慢消费 | POS：门店集中上传流水（早/晚高峰） |
| ⚠️ **代价** | ① 系统变复杂（要处理重复、丢失、顺序）② **一致性从强一致变最终一致** ③ 链路的可观测性变难（消息去哪儿了） | — |

### 6.2 ★ 四种 MQ 对比（★ 必背）

| 维度 | **RabbitMQ** | **Kafka** | **RocketMQ** | **Pulsar** |
| --- | --- | --- | --- | --- |
| **模型** | Broker + Exchange/Queue（**AMQP**） | **分区日志（Partition Log）** | 队列 + 主题（阿里系，类 Kafka） | 计算存储分离（Broker + BookKeeper） |
| **语言** | Erlang | Scala/Java | Java | Java |
| **单机吞吐** | 万级（~几万） | **十万级 ~ 百万级** | **十万级** | 十万级 |
| **延迟** | **微秒~毫秒（最低）** | 毫秒（批量时更高） | 毫秒 | 毫秒 |
| **消息顺序** | 队列内有序（多消费者会乱） | ✅ **分区内严格有序** | 队列内有序 | 分区内有序 |
| **事务消息** | ❌ 无（只有 publisher confirm） | ✅ 事务 + 幂等生产者 | ✅ **事务消息（半消息 + 回查）** | ✅ |
| **延迟消息** | ✅ TTL+DLX / 延迟插件 | ❌ 不支持（要自己做） | ✅ **内置延迟级别** | ✅ |
| **消息回溯** | ❌ 消费即删（除非配置） | ✅ **保留期长，可按 offset 重放** | ✅ 支持 | ✅ 支持 |
| **重复消费** | 可能（at-least-once） | 可能 | 可能 | 可能 |
| **运维复杂度** | 低（单机就能跑） | 中高（依赖 ZK/KRaft，要管分区） | 中 | 高（组件多） |
| **典型场景** | **业务解耦、任务队列、RPC 异步化**、中小规模 | **日志采集、埋点、流式计算、大数据管道** | **电商交易、金融、订单** | 多租户、大集群 |

**★ 选型话术（重点：说明"你没用过 Kafka 但知道什么时候该用"）**：

> "**RabbitMQ 和 Kafka 的分水岭是「业务消息」还是「数据流」**。
> **RabbitMQ 是消息中间件**——消息被消费后就删，重点是**灵活的路由（Exchange）和低延迟**，适合业务解耦、任务分发。我在 POS 中台和商云前台用的都是 RabbitMQ，就是因为这两处的诉求是**可靠地把每条业务数据送到、且要灵活路由到不同产品线的队列**。
> **Kafka 是分布式日志**——消息是**可回溯的追加日志**，分区内有序，重点是**吞吐量和数据重放**，适合日志采集、埋点、流计算这种"数据量大、要能重放、可以接受批量延迟"的场景。
> **⚠️ 所以如果这个网关要做「全量访问日志的采集管道」，我会选 Kafka**——因为日志是典型的"数据流"，量级大、允许批量延迟、可能要重放做分析；**而如果是「配置变更通知」「告警事件分发」这类业务消息，RabbitMQ 或直接用 Redis Pub/Sub 更合适**，运维成本低得多。
> **RocketMQ 我了解它的事务消息和延迟消息做得好**，适合交易场景，但我没在生产用过。**我的实际经验集中在 RabbitMQ，Kafka 是理解原理和选型逻辑这个层次。**"

### 6.3 ★ RabbitMQ 详解（你的主场，要讲细）

#### 6.3.1 核心概念与消息流转

> **一句话**：生产者 → **Exchange（交换机）** → 按 **RoutingKey + Binding** 路由 → **Queue** → 消费者；**Exchange 不存消息，Queue 才存**。

```
Producer → [Exchange] --binding--> [Queue] → Consumer
                |
                └── 路由规则决定消息投到哪些 Queue
```

| 概念 | 说明 |
| --- | --- |
| **Connection** | TCP 连接（重量级，**一个应用一个**） |
| **Channel** | ★ 连接内的**虚拟信道**（轻量级，**消息收发的实际通道**）；多线程共用一个 Connection 会相互影响，所以**每个线程一个 Channel** |
| **Exchange** | 只做路由，不存消息 |
| **Queue** | 消息的**实际存储处**，有 FIFO 特性 |
| **Binding** | Exchange 与 Queue 之间的绑定规则 |
| **RoutingKey** | 生产者发消息时带的"地址" |
| **vhost** | 虚拟主机（隔离环境/租户） |

#### 6.3.2 ★ Exchange 四种类型（必答）

| 类型 | 路由规则 | 场景 |
| --- | --- | --- |
| **direct** | RoutingKey **完全匹配** | 精确路由：按 `order.created` 精确投递 |
| **topic** | RoutingKey **通配符匹配**（`*` 一词，`#` 零或多词） | ★ **最常用**：`order.*.created`、`log.#` |
| **fanout** | **忽略 RoutingKey，广播到所有绑定的队列** | 广播通知：配置变更、缓存刷新 |
| **headers** | 按**消息头（headers）**匹配（性能差，很少用） | 复杂条件路由 |

**★ 项目话术（POS 数据贯通，一定用得上）**：
> "POS 中台我用 **topic 交换机**做产品线隔离——RoutingKey 设计成 `{产品线}.{业务类型}.{动作}`，比如 `posA.sale.flow`、`posB.invoice.create`。这样**接入新产品线只需要加一条 binding**，不用改代码；而且可以让某个队列用 `posA.#` 一次订阅整个产品线，**这就是'统一接口 + 适配多产品线'的实现方式**。"

#### 6.3.3 ★ 消息可靠性（三个环节，必背）

> **一句话**：消息丢失只可能发生在三个地方——**生产者到 Broker（发送时）、Broker 内部（存储时）、Broker 到消费者（消费时）**，所以可靠性设计就是**在这三段各加一道保险**。

| 环节 | 风险 | 措施 |
| --- | --- | --- |
| **① 生产者 → Broker** | 网络抖动、Broker 没收到 | **publisher confirm（发布确认）** + 失败重试 + **本地消息表/定时补发** |
| **② Broker 存储** | Broker 宕机、消息没落盘 | **① `durable=true`（队列持久化）+ `DeliveryMode=2`（消息持久化）+ 落盘** ② **镜像队列（3.8 前）/ 仲裁队列 Quorum Queue（3.8+，基于 Raft）** ③ 集群至少 2 个节点 |
| **③ Broker → 消费者** | 消费者处理失败、进程崩溃 | ★ **手动 ACK**（处理完再 ack，绝不用 autoAck）+ 失败 nack/requeue + **死信队列兜底** |

**★ publisher confirm vs 事务（RabbitMQ 特有）**：

| | 事务（`txSelect`/`txCommit`） | **Confirm 机制** |
| --- | --- | --- |
| 原理 | 类似 DB 事务 | Broker 收到消息后回一个 **ack/nack** |
| 性能 | ⚠️ **差（同步阻塞，吞吐降几十倍）** | ✅ 好（异步回调，可批量确认） |
| 结论 | ❌ 生产不用 | ✅ **生产标准做法** |

```go
// Go（amqp091-go）：开启 confirm 模式，异步监听确认
ch.Confirm(false)
confirms := ch.NotifyPublish(make(chan amqp.Confirmation, 1))

go func() {
    for c := range confirms {
        if !c.Ack {
            // ★ 未确认 → 记录到本地重试表 / 落库补偿，稍后重发
            saveToRetryTable(deliveryTag)
        }
    }
}()

err := ch.PublishWithContext(ctx, "pos.topic", "posA.sale.flow", false, false, amqp.Publishing{
    DeliveryMode: amqp.Persistent,   // ★ 消息持久化
    ContentType:  "application/json",
    Body:         body,
})
```

> ⚠️ **必说的一句**："**只开 confirm 只能保证 Broker 收到了，不能保证业务处理成功了**——因为 Broker 收到消息后自己也可能在落盘前宕机。所以我会**再加一个本地消息表**：业务事务里把消息写到 `local_message` 表（状态=待发送），发成功后更新为已发送，定时任务扫"待发送"的记录补发。**这样做到的是"至少一次投递"，配合消费端幂等就是"恰好一次的效果"。**"

#### 6.3.4 ★ ACK 机制、prefetch 与公平分发

> **一句话**：**消费者必须手动 ACK**（`autoAck=false`），处理成功才 ack；**prefetch（`basic.qos`）限制每个消费者未确认的消息数**，这是"能者多劳"的关键。

| 参数 | 建议 | 理由 |
| --- | --- | --- |
| `autoAck` | **false（手动 ACK）** | autoAck=true 时消息一发出就标记删除，消费者崩溃 = **消息丢失** |
| `prefetchCount` | **1~50**（按处理耗时定） | ⚠️ **默认 0 = 不限制 = 平均分发**（慢的消费者越堆越多）；设为 1 是**最公平但吞吐最低**；实践中按吞吐与公平取折中 |
| `basicAck` | 处理成功后调用 | — |
| `basicNack` + `requeue=true` | 临时故障（如 DB 抖动） | ⚠️ **要防止无限重入队**（死循环），配合**重试次数上限 → 进死信队列** |
| `basicReject` + `requeue=false` | 明确失败（如数据格式错） | 直接进死信 |

**★ 公平分发（fair dispatch）**：
> 默认情况下 RabbitMQ 是**轮询分发（round-robin）**——不管消费者忙不忙，一人一条。结果是一个消费者积压、其他闲着。设 `prefetchCount=1` 后变成**"谁处理完谁再拿"**，也就是能者多劳。

#### 6.3.5 ★ 死信队列（DLX）与延迟队列

**死信（Dead Letter）的三种来源**：

1. 消息被**拒绝**（`basicNack`/`basicReject` 且 `requeue=false`）
2. **消息 TTL 过期**
3. **队列达到最大长度**（`x-max-length`）被丢弃的

> **DLX 的本质**：给队列设 `x-dead-letter-exchange` 参数——**当消息变成死信，RabbitMQ 会自动把它重新投到指定的交换机**。所以死信队列 = 一个普通队列 + 一个专门收死信的绑定关系。

| 用途 | 为什么用它 |
| --- | --- |
| **兜底** | 处理失败的消息不丢，**人工介入或定时重试** |
| **延迟队列** | ★ **TTL + DLX 的组合能实现延迟** |
| **监控告警** | 死信队列有堆积 → 说明业务有系统性问题 |

**★ 延迟队列的两种实现**：

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| **TTL + DLX** | 消息设 TTL，过期后进死信交换机，**死信队列的消费者才真正处理** | ✅ 不用装插件；⚠️ **队列 TTL 是"队头阻塞"的**——先入队的消息 TTL 长会让后面的短 TTL 消息一起等待；**要按延迟档位分多个队列** |
| **延迟插件（rabbitmq_delayed_message_exchange）** | 安装插件，直接用 `x-delayed-type` 交换机 | ✅ 灵活、支持任意延迟；⚠️ 要装插件（有些云服务不给装） |

> 项目话术："POS 的**上传失败重试**我就是用 TTL + DLX 做的：第一次失败进延迟队列，5 分钟后重试；再失败延迟 30 分钟；三次都失败就进最终的**死信队列**并告警，人工介入。**这样做的好处是重试不占着主队列，而且不会因为一条坏消息把整个队列堵住。**"

#### 6.3.6 ★★ 消息幂等（你的王牌）

**为什么消息一定会重复（★ 先讲原因，再讲方案）**：

| 原因 | 说明 |
| --- | --- |
| **网络重试** | 生产者没收到 confirm → 重发；消费者 ack 丢了 → Broker 重投 |
| **ACK 丢失** | ★ **最常见的**：消费者处理完了，ack 在网络上丢了，Broker 认为没消费 → 重投 |
| **消费者异常** | 处理到一半进程崩溃，`requeue=true` 后重新投递 |
| **重平衡/超时** | Kafka 消费者重平衡；RabbitMQ 消费者超时未 ack |
| **上游重复触发** | 定时任务重跑、webhook 被第三方重推 |

> ★ **核心结论（面试直接说这句）**：
> **"MQ 只能做到「至少一次」投递，做不到「恰好一次」。所以「不重复」这件事只能由消费端自己保证——投递语义的下限是 at-least-once，消费端幂等把它补成 exactly-once 的效果。"**

**四种幂等方案（★ 按场景选）**：

| 方案 | 做法 | 优点 | 缺点/适用 |
| --- | --- | --- | --- |
| **① 唯一 ID + 去重表** | 建 `msg_dedup(msg_id unique, created_at)`，消费前先 `INSERT`，**主键冲突说明重复**；在**同一个事务**里写业务数据 | ✅ **最可靠**，和业务数据同事务 | 每次都要写库；表会膨胀（要定期清理） |
| **② Redis SETNX** | `SETNX msg:{id} 1 EX 86400`，返回 0 直接跳过 | ✅ **最快**（内存操作） | ⚠️ **不可靠**：Redis 重启/过期就失效 → **只能当快筛，不能当唯一防线** |
| **③ 数据库唯一索引** | 业务表上建业务唯一键（如 `order_no`），`INSERT ... ON DUPLICATE KEY UPDATE` | ✅ **零额外成本**，最优雅 | 要求业务本身有天然唯一键；**跨表操作覆盖不到** |
| **④ 状态机 + 版本号** | 状态只能单向流转（`待支付 → 已支付`），更新带条件：`UPDATE ... WHERE status='待支付'` | ✅ 天然幂等，**防的是"重复的状态变更"** | 只适用于有状态流转的场景；**影响行数为 0 说明是重复** |

**★★ 结合 LoveSpouse：腾讯 IM 消息幂等的真实实现**

**背景**：数字人系统对接腾讯 IM，用户的消息通过 **IM 的回调（webhook）** 推给我们的后端。腾讯 IM 的**回调是"至少一次"语义**——**超时未响应或响应失败会重推**，所以同一条消息可能到达多次。

⚠️ **如果不去重会怎样**：
- 同一条用户消息触发**两次 AI 回复**（用户看到机器人说了两遍）；
- 触发**两次金币扣费**（用户投诉）；
- 分层记忆里存了**两条一样的对话**（污染上下文和摘要）。

**我的实现思路（★ 三层防护，讲这个结构最清楚）**：

```
腾讯 IM 回调 → 【第一层】Redis SETNX 快速去重（ms 级，挡掉 95%+ 的重复）
                    ↓ 未命中
              【第二层】MySQL 唯一索引（msg_id）兜底（可靠，挡住 Redis 失效的情况）
                    ↓ 插入成功
              【第三层】状态机（消息状态：processing → done）
                    ↓ 只有 processing → done 这次的流转成功
                   业务处理（AI 回复 + 扣费，扣费再用 requestID 幂等）
```

| 层 | 实现 | 作用 |
| --- | --- | --- |
| **① Redis 快筛** | `SETNX im:msg:{msgID} 1 EX 600`（**注意 TTL：覆盖腾讯的重试窗口即可，不必太长**） | 挡掉绝大多数重复，**不打 DB** |
| **② DB 唯一索引** | `im_message(msg_id varchar(64), UNIQUE KEY uk_msg_id)`，用 `INSERT IGNORE` 或捕获 `Duplicate entry` 错误 | ★ **可靠性防线**：Redis 挂了、key 过期了，这里还能挡住 |
| **③ 状态机** | 消息状态 `received → processing → done`；用**带条件的 UPDATE**推进状态，**影响行数=0 说明已被别的线程处理** | **防并发**：同一消息的两个请求同时到达时，只有一个能推进状态 |

**★ 幂等键怎么选（这个细节很加分）**：
> "幂等键不能随便选。腾讯 IM 的消息有 `MsgKey` 和 `MsgSeq`，但**单用其中任何一个都不够**——`MsgSeq` 是**会话内递增**的，不同会话会重复，所以要组合成 **`{会话ID}:{MsgSeq}`** 或者直接用腾讯给的**全局唯一的 `MsgKey`**。另外要注意：**如果同一条消息在腾讯侧被编辑/撤回后重推，幂等键相同但内容不同**——这种场景我会在幂等表里**额外存一个内容摘要**，内容不一致时不跳过而是走"更新"逻辑，避免把真实变更误判为重复。"

**⚠️ 面试官可能的追问：「幂等键的 TTL 设多久？」**
> "**分两层看**：Redis 那层的 TTL 只需要**覆盖上游的重试窗口**——腾讯 IM 的重试一般在几分钟到几小时内，我设了 10 分钟到 1 小时，**太长会浪费内存，太短就白做了**。**数据库那层我一般设成"永久保留 + 定期归档"**，因为它是最终防线，删早了就出现幂等漏洞。**如果存储压力大，就按业务能承受的最大重试窗口来定，比如 7 天，配一个定时归档任务搬到历史表。**"

**★ 结合 POS：RabbitMQ 消费的重复消费防护**

> 项目话术：
> "POS 中台消费流水数据的幂等，我用的是**唯一索引 + upsert** 的组合——**每张业务表都有天然唯一键**（流水表的 `order_no`、发票表的 `invoice_no`），落库统一走 `INSERT ... ON DUPLICATE KEY UPDATE`，**重复消费最坏就是重新写一遍同样的值**，不影响结果。
> 另外我在**消费入口**加了一层 Redis `SETNX` 快速去重——**不是为了替代数据库那层，而是为了不让重复流量打到数据库**。这两层的关系是：**Redis 挡住 99%，数据库唯一索引兜住那 1%，缺一不可**。
> ⚠️ **这里有个细节要注意**：**`SETNX` 和业务处理不是原子的**——如果 `SETNX` 成功但业务处理失败，这条消息就永远被"误杀"了。所以我的做法是**只有业务处理成功后，才把这条消息标记为已处理**；如果处理失败抛异常，**要把 Redis 的那个 key 删掉再抛出异常让消息重投**，否则重试也会被自己的幂等键挡住。"

### 6.4 消息顺序性

> **一句话**：**乱序来自"并发"**——多消费者并行消费同一个队列、或消息被重投后跳到队尾；**保证顺序的唯一办法是"把需要有序的消息路由到同一个队列、同一个消费者，并且串行处理"**。

| 乱序原因 | 说明 |
| --- | --- |
| **多消费者并行** | 同一队列多个消费者，后发的消息可能先被处理 |
| **失败重投** | 处理失败 `requeue=true` 后消息**回到队头或队尾**，顺序被打乱 |
| **多队列/多分区** | 一个业务的消息散了多个队列 |
| **生产端并发** | 多线程发消息本身就没有顺序 |

**怎么保证顺序（★ 三个层次）**：

1. **按业务 key 路由**：同一订单/同一用户的消息 → **同一个队列**（RabbitMQ：用 `hash(key) % N` 选队列 / 一致性哈希；Kafka：**按 key 指定 partition**）。
2. **单队列 + 单消费者 + 串行处理**（最简单可靠，代价是吞吐降）。
3. **应用层排序**：消息带**版本号/序号**，消费端按序号排序后再处理（能容忍一定乱序时用）。
4. ⚠️ **重试会破坏顺序**：需要有序的消息，**失败后不要 requeue**（会跑到队尾），而是进死信/延迟队列，**让它原地重试或人工处理**。

> 项目话术："POS 中台有个业务是**商品的变更顺序不能乱**——先改价格再改库存，如果倒过来结果是错的。我的做法是**按 `product_id` 哈希路由到固定队列**，保证同一个商品的消息在**同一个队列、被同一个消费者串行处理**。**代价是牺牲了一点并行度**——因为不同商品之间本来是可以并行的，所以我把哈希取模的值设成跟消费者数量匹配，这样总体吞吐还是够的。**这里的原则是：只对'真正需要有序'的维度做顺序保证，不要把整个系统都搞成串行。**"

### 6.5 消息堆积

> **一句话**：**堆积本身是"消费者追不上生产者"**，先判断是**持续性**（要扩容/优化）还是**突发性**（等一等就好）；处理的优先级是「**先扩容 → 再优化消费逻辑 → 最后才是降级丢弃**」。

| 步骤 | 动作 |
| --- | --- |
| **① 发现** | RabbitMQ：`rabbitmqctl list_queues name messages messages_ready messages_unacknowledged`、管理后台的 queue 深度、Prometheus 指标；Kafka：**consumer lag** |
| **② 定位** | 是**突发流量**（等一会儿自然消下去）还是**消费者变慢**（下游 DB 慢、外部接口超时、消费逻辑阻塞）|
| **③ 处理（按顺序）** | 1. **加消费者实例**（最快见效；注意**队列的并行度**——单队列多消费者可以，但要保证幂等）<br>2. **提高并发**：增大 `prefetch`、批量拉取、消费者内部用 goroutine 池并发处理（**注意顺序要求**）<br>3. **优化消费逻辑**：批量写库、去掉同步的外部调用、加缓存<br>4. **临时降级**：非关键消息直接丢弃/降采样（如埋点日志），或者**先落磁盘/对象存储稍后离线补**<br>5. **极端情况**：**新建队列 + 新消费者组**并行消化（Kafka 可以重置 offset 从头消费）|
| **④ 预防** | 监控告警（队列深度 > 阈值）、**压测出消费者的最大吞吐**、限流保护（生产端在系统压力高时主动降级）|

> ⚠️ **面试官爱问的陷阱**：「堆积了你怎么快速清空？」
> "**首先我不会盲目清空**——消息里可能有业务数据，清了就丢单了。我会先判断**这些消息是不是可以丢**：如果是埋点/日志类的非关键消息，可以批量丢弃或落盘；**如果是订单/流水这类业务数据，绝对不能丢**，只能扩容消费、优化消费逻辑，或者**先把消息导出到文件/对象存储、清空队列把线上压力解掉，再离线慢慢补**。**这是"先止血、再治疗"的思路**——线上最要紧的是别让积压把下游拖垮。"

> 项目话术："POS 里我在**门店早高峰**遇到过流水队列堆积——因为门店集中上传，而中台消费时要写 MySQL 而且批量小。我的处理是**两步**：先把 `prefetch` 调大、批次从 1 条改成 500 条一批（**吞吐立刻上一个数量级**），然后把消费者的 goroutine 数量按 DB 连接池的容量调到刚好打满（**再高就打爆连接池了**）。另外我加了**队列深度的监控告警**，超过 10 万条就提前预警，**不等用户投诉才发现**。"

### 6.6 消息丢失

> **一句话**：**三个环节各查一遍**——生产者有没有拿到确认、Broker 有没有持久化、消费者是不是处理完才 ACK。

| 环节 | 检查清单 |
| --- | --- |
| **生产者** | ✅ 开了 **publisher confirm** 吗？✅ 失败重试了吗？✅ 有**本地消息表/定时补发**兜底吗？（**只异步发送不检查结果 = 一定丢**） |
| **Broker** | ✅ 队列 `durable=true`？✅ 消息 `DeliveryMode=Persistent`？✅ 用了**镜像队列/Quorum 队列**（至少 2 副本）？✅ 磁盘满了会有 `x-max-length` 丢弃？ |
| **消费者** | ✅ `autoAck=false`？✅ **处理成功才 ack**？✅ 异常时有 nack/死信兜底而不是静默吞掉？✅ 有没有 `try/catch` 里把异常吃了、还是照样 ack？⚠️ **这是最常见的丢消息原因** |

> 项目话术："POS 的消费端我特意强调过**不要在 `defer` 里无条件 ack**。曾经有个同事的代码是 `defer msg.Ack()`，结果**业务 panic 之后 ack 照样执行了，消息就永久丢了**。我改成的是**显式 ack**：只有业务逻辑返回 nil 才 ack，返回错误就 nack 进重试队列。**这是一个很容易被忽略但后果很严重的坑。**"

### 6.7 ★★ 结合 POS 数据贯通：完整的可靠性设计（★ 一次讲完）

**场景**：多条零售 POS 产品线的门店，把销售流水/电子发票/商品档案上传到中台。

```
[门店 POS]  --HTTP-->  [接入服务]  --publish-->  [RabbitMQ topic exchange]  -->  [中台消费服务]  -->  [MySQL 批量落库]
                            │                             │                              │
                       ① 幂等键                       ② 持久化 + 仲裁队列            ③ 手动ACK + 批量 + 幂等
                       本地消息表                      死信 + 延迟重试                 Redis 快筛 + 唯一索引
```

| 环节 | 我做的设计 | 为什么 |
| --- | --- | --- |
| **接入** | 接口带 `order_no`，**先落"接入表"再发 MQ**（本地消息表模式） | 保证"请求收到了"和"消息发出去了"这两件事不丢 |
| **投递** | **topic exchange + 按产品线 RoutingKey**，`posA.sale.#` 这样的绑定 | 多产品线共用一套中台，**新增产品线只加 binding 不改代码** |
| **Broker** | **队列持久化 + 消息持久化 + publisher confirm + Quorum 队列（3 节点）** | 单节点宕机不丢消息 |
| **消费** | **手动 ACK** + **prefetch=20** + **攒批 500 条或 1 秒落库** + **失败进延迟队列重试（3 次）→ 死信** | 吞吐与可靠性的平衡；坏消息不阻塞队列 |
| **幂等** | **Redis `SETNX` 快筛 + MySQL `order_no` 唯一索引兜底 + `ON DUPLICATE KEY UPDATE`** | 重复消费永远安全 |
| **顺序** | **按 `shop_id` 哈希路由到固定队列**，同门店串行 | 同门店的流水顺序不能乱 |
| **监控** | 队列深度、消费速率、死信数量、消费延迟告警 | 提前发现问题 |

> ★ **面试话术（把上面压缩成 90 秒讲出来）**：
> "POS 中台的 MQ 我做的是**端到端的可靠性设计**，按"三个环节"来配：
> **生产端**，接入接口收到数据后**先写一张本地消息表**，状态是待发送，然后才发 MQ；发成功了更新状态，发失败的由定时任务扫出来补发。**这样即使发消息那一刻服务挂了，数据也不会丢。**
> **Broker 端**，队列和消息都持久化，开了 publisher confirm，集群用 3 节点的 Quorum 队列（基于 Raft，比老的镜像队列可靠），**任何一个节点宕机不影响消息**。
> **消费端**，**手动 ACK、处理成功才确认**；`prefetch` 设成 20 让消费能力强的实例多拿一些；消费逻辑是**攒够 500 条或满 1 秒批量落库**，一趟 SQL 写 500 行，吞吐比逐条高一个数量级；失败的消息进**延迟队列重试（5 分钟、30 分钟、2 小时）**，三次都失败进死信队列告警人工介入。
> **幂等**是两层：消费入口用 **Redis `SETNX` 按消息 ID 去重**，挡住绝大部分重复；数据库层用**业务唯一键 `order_no` 的唯一索引 + `ON DUPLICATE KEY UPDATE`**兜底。**Redis 是快筛、数据库是兜底，缺一不可。**
> **顺序**上，我把同一个门店的消息**按 `shop_id` 哈希路由到固定的队列**，保证同门店串行处理。
> 最后是**监控**：队列深度、消费速率、死信数量都接了告警，**不等出问题才发现**。"

> ⚠️ **核心策略**：**不要在 ES 上装作有经验**，而要**把 ES 讲成"我理解它在什么场景下不可替代"**——这个层次对架构岗够用了。

### 7.1 为什么需要 ES

> **一句话**：ES 解决的是「**海量数据的全文检索 + 近实时聚合**」——**这两件事 MySQL 都做不好**（`LIKE '%x%'` 全表扫、`GROUP BY` 大表跑不动）。

| 需求 | MySQL 的做法 | 问题 | ES 的做法 |
| --- | --- | --- | --- |
| **全文检索** | `LIKE '%关键词%'` | ⚠️ **索引失效、全表扫描**；不能分词、不能相关度排序 | **倒排索引**，毫秒级 |
| **海量聚合** | `GROUP BY` + `COUNT` | 百万级以上就很慢，几亿级跑不动 | **doc_values 列存 + 分布式并行聚合** |
| **多条件组合** | 多列索引 + `OR` | 组合维度多了索引建不过来 | **倒排（找文档集合）+ 列存（排序聚合）双引擎** |
| **日志场景** | 单表过亿要分表、归档 | 运维成本高，检索体验差 | **按时间滚动的索引 + 自动过期（ILM）** |

**ES 的定位（★ 一句话讲清）**：
> **"ES 不是数据库，它是一个分布式的搜索与分析引擎。它不保证事务、不擅长更新、不做强一致——所以它的角色永远是"搜索层/分析层"，权威数据一定在 MySQL。"**

### 7.2 ★ 倒排索引原理

> **一句话**：正排是「文档 → 词」，**倒排是「词 → 文档列表（Posting List）」**；查"包含某个词的文档"变成一次**查词典 + 取列表**，这就是全文检索快的根本原因。

**结构三件套**：

| 组件 | 说明 |
| --- | --- |
| **Term Dictionary（词典）** | 所有词的**有序集合**，用 **FST（有限状态转换器）** 组织 |
| **Term Index（词典索引）** | ★ **FST 驻留内存**，用前缀共享压缩存储，**让"查词典"不用读磁盘** |
| **Posting List（倒排表）** | 每个词对应的文档 ID 列表，**有序 + 增量编码 + Roaring Bitmap 压缩**；还存词频、位置（用于短语查询）、偏移（用于高亮） |

**为什么用 FST**：
- 用**前缀共享**大幅压缩（"mo","mot","moth","mother" 共享路径）。
- **常驻内存**，只有 FST 指向的词典块才需要磁盘 IO。
- ⚠️ **代价：FST 构建后不可变**——这正是 ES **segment 不可变**的原因之一（见 7.5）。

**★ 分词器（Analyzer）三件套**：

```
字符过滤器（char filter）→ 分词器（tokenizer）→ 词元过滤器（token filter）
  去掉 HTML 标签           按规则切成词           小写化、去停用词、同义词、词干提取
```

| 场景 | 分词器 |
| --- | --- |
| 英文 | `standard`（默认）、`english`（含词干提取） |
| **中文** | ★ **`ik_max_word`（细粒度，建索引用）/ `ik_smart`（粗粒度，查询用）** —— **必须装 IK 插件**，ES 自带的分词器对中文是"单字切分"，效果很差 |
| 日志 | 通常 `keyword`（不分词）或 `standard` |

**★ `text` vs `keyword`（最常考映射问题）**：

| 类型 | 是否分词 | 用途 |
| --- | --- | --- |
| **`text`** | ✅ 分词，建倒排索引 | **全文检索**（文章内容、日志正文） |
| **`keyword`** | ❌ 不分词，整体作为一个 term | **精确匹配、排序、聚合**（状态码、设备 ID、IP） |
| **`text` + `fields.keyword`** | 两个都建（多字段） | ★ **要搜索又要聚合时的标准做法** |

> ⚠️ **经典陷阱**：「为什么我用 `term` 查 `text` 字段查不到？」
> 因为 **`term` 不分词、直接拿原值去匹配倒排索引里的 term**，而 `text` 字段入库时已经被**分词**了。"Hello World" 在索引里是 `hello` 和 `world` 两个 term，你用 `term: "Hello World"` 当然匹配不到。**要精确匹配就用 `keyword` 字段。**

### 7.3 ES vs MySQL 全文检索

| | MySQL | ES |
| --- | --- | --- |
| 全文检索 | `LIKE '%x%'` **全表扫**；`FULLTEXT` 索引（仅 InnoDB，**只支持英文分词，中文要插件且效果差**） | ✅ 倒排索引，**毫秒级**，中文分词成熟（IK） |
| 相关度排序 | ❌ 无 | ✅ **TF-IDF / BM25 打分** |
| 高亮 | ❌ | ✅ 内建 highlight |
| 多条件组合 | 索引组合爆炸 | ✅ bool 查询任意组合 |
| 聚合分析 | 大表跑不动 | ✅ 分布式并行聚合 |
| 事务/强一致 | ✅ | ❌ **近实时（默认 1 秒延迟）、无事务** |
| 存储成本 | 低 | ⚠️ **高（倒排 + 列存 + 副本，通常是原始数据的 2-5 倍）** |

> ★ 面试话术：
> "**MySQL 的全文检索不能用在生产**——`LIKE '%x%'` 是全表扫，`FULLTEXT` 索引对中文基本不可用。所以在"要在海量日志里搜一个关键词"这个需求上，**ES 不是"更好"，而是"唯一可行的选择"**。反过来，**ES 不能当数据库用**——它没有事务、写入是近实时、更新实际上是"标记删除 + 新文档"，**要用 ES 存权威数据一定会出事**。"

### 7.4 集群概念

| 概念 | 说明 |
| --- | --- |
| **Index（索引）** | 逻辑上的"表"，如 `access-log-2026.09.22` |
| **Shard（分片）** | ★ **索引的水平切分，每个分片是一个完整的 Lucene 实例**（一个 shard = 一个 Lucene index） |
| **Primary Shard** | 主分片，**数量在索引创建时确定，之后不能改**（要改必须 reindex / `_split` / `_shrink`） |
| **Replica Shard** | 副本分片，**① 提高读吞吐（副本也能查）② 故障转移（主分片挂了副本顶上）** |
| **节点角色** | `master`（管集群状态）、`data`（存数据）、`coordinating`（转发请求、合并结果）、`ingest`（预处理管道）；**生产建议用独立 master 节点** |
| **作用域** | 默认 `1 primary + 1 replica`（7.x 起），所以**单节点集群是 yellow 状态**（副本未分配） |

**⚠️ 分片数量的选择（常见的架构判断）**：
- **分片不是越多越好**：每个分片都有固定开销（Lucene 的 segment、文件句柄、堆内存），**分片过多会导致"集群很忙但没干正事"**（oversharding）。
- 经验值：**单分片 10-50GB**；按这个反推分片数。
- **日志场景用"按时间滚动"的索引**（如按天），**配 ILM（索引生命周期管理）**：热 → 温 → 冷 → 删除，自动滚动和清理。

### 7.5 写入流程与"近实时"

> **一句话**：ES 写入**不是实时的**——**默认每 1 秒 refresh 一次**，把内存缓冲区的数据生成新的 segment 才能被搜到，这就是"**近实时（NRT）**"的含义。

```
写入 → ① 写入内存 Buffer（同时写 translog 保证不丢）
     → ② refresh（默认每 1s）：Buffer 生成新 Segment，写入 OS 文件缓存 → ★ 此时可被搜索
     → ③ flush（translog 满或 30 分钟）：fsync 落盘 + 清空 translog
     → ④ 后台 merge：合并小 segment 成大 segment，真正删除已标记删除的文档
```

| 概念 | 作用 |
| --- | --- |
| **refresh** | 让数据**可被搜索**（默认 1 秒）；`refresh=true` 可以强制立即刷新（⚠️ **生产慎用，会生成很多小 segment，严重拖慢性能**）|
| **translog** | 类似 MySQL 的 redo log，**保证 refresh 之间崩溃不丢数据** |
| **flush** | 落盘 + 清空 translog（真正的持久化点） |
| **segment 不可变** | ★ 核心设计：**更新 = 标记旧文档删除 + 写新文档**；删除也是"软删除"，**merge 时才真正物理删除** |

⚠️ **面试官追问「ES 的更新为什么慢？」（答这个很加分）**：
> "因为 **Lucene 的 segment 是不可变的**——更新一条文档实际上是「**把旧文档标记为删除 + 写入一条新文档**」，然后后台 merge 的时候才真正物理清理。所以**频繁更新的场景 ES 会迅速膨胀**（大量被标记删除的文档占用空间，直到 merge）。这也是为什么**ES 不适合当主数据库**——它擅长的是"写一次、查很多次"的场景。"

### 7.6 查询

**★ `match` vs `term`（最常考）**：

| | `match` | `term` |
| --- | --- | --- |
| **分词** | ✅ **会分词** | ❌ 不分词，**精确匹配 term** |
| **用于** | `text` 字段（全文检索） | `keyword` / 数值 / 日期 |
| **行为** | 分词后**任意一个词命中就算命中**（默认 or） | 值必须**完全相等** |

**bool 查询四子句**：

| 子句 | 语义 | 打分 |
| --- | --- | --- |
| `must` | 必须匹配（AND） | ✅ 参与打分 |
| `should` | 应该匹配（OR，`minimum_should_match` 控制） | ✅ 参与打分 |
| `must_not` | 必须不匹配（NOT） | ❌ 不参与 |
| **`filter`** | **必须匹配，但不打分** | ❌ **★ 不参与打分 → 可被缓存 → 比 must 快** |

> ★ **性能要点**：**不需要算分的条件一律用 `filter`**——ES 会缓存 filter 的结果（bitset），重复查询直接命中缓存。**这是最实用的 ES 优化技巧之一。**

**聚合（Aggregation）**：

```json
// 按状态码分组统计 + 算平均延迟
{
  "size": 0,                                    // ★ 只要聚合结果，不要文档，省开销
  "query": { "range": { "@timestamp": { "gte": "now-1h" } } },
  "aggs": {
    "by_status": {
      "terms": { "field": "status.keyword", "size": 10 },
      "aggs": { "avg_latency": { "avg": { "field": "latency_ms" } } }
    },
    "p99_latency": { "percentiles": { "field": "latency_ms", "percents": [95, 99] } }
  }
}
```

| 聚合类型 | 用途 |
| --- | --- |
| `terms` | 分组计数（类似 `GROUP BY`）—— **TOP N 统计** |
| `date_histogram` | 按时间分桶（**画趋势图**） |
| `cardinality` | 去重计数（类似 `COUNT(DISTINCT)`，**近似**，基于 HyperLogLog++） |
| `percentiles` | 分位数（**P95/P99 延迟**，网关监控的核心指标） |
| `avg` / `sum` / `max` | 数值聚合 |

**⚠️ 深分页问题（ES 的经典限制）**：
- `from + size` **默认最多到 10000 条**（`index.max_result_window`）——因为每个分片都要返回 `from+size` 条给协调节点排序，**越翻页内存和 CPU 消耗越大**。
- 解决方案：
  - **`search_after` + 排序字段**（推荐，**无状态、支持无限翻页**）
  - **`scroll`**（快照式遍历，**适合导出，不适合用户翻页**，会占用资源）
  - **PIT（Point In Time，7.10+）** + `search_after`（一致的快照视图）

### 7.7 ★ 结合本岗位：为什么网关的日志分析适合 ES

**问题**：AI 安全网关每天产生海量访问日志 + 审计日志，怎么做存储和检索？

**完整理由（★ 这题很可能被问，四条理由要能顺着说出来）**：

| 理由 | 展开 |
| --- | --- |
| **① 海量写入** | 每天几亿到几十亿条，**必须能水平扩展**——ES 天然分片 + 按时间滚动索引（`access-log-2026.09.22`），**写入能力随节点线性增长** |
| **② 需要全文检索** | 安全场景的核心查询是"**查某个 Prompt 关键词、某个攻击特征串、某个 IP**"——**这是倒排索引的主场，MySQL 的 `LIKE` 在这里完全不可用** |
| **③ 需要聚合统计** | 运营平台要看「**拦截率、TOP 攻击来源、错误码分布、P95 延迟**」——ES 的 `terms` / `date_histogram` / `percentiles` 聚合就是为这个生的，**一次查询出多维统计** |
| **④ 按时间范围 + 自动过期** | 日志查询**天然带时间范围**（"最近 1 小时"），ES 可以**用时间分区索引把这个范围裁剪到极少的几个分片上**；同时 **ILM 能自动把冷数据转存储、到期自动删除**，**不需要写归档脚本** |

**★ 完整答题话术**：

> "网关日志我会用 **ES 作为检索与分析层**，理由有四条：
> **第一，量级**。网关一天几亿条日志，MySQL 单表几千万就要分表了，ES 靠分片 + 按天滚动索引能线性扩展，**这是最根本的原因**。
> **第二，查询模式**。安全运营的核心操作是"**在日志里搜一个关键词**"——搜某个 Prompt、某个攻击 Payload、某个 IP。**倒排索引让这个操作是毫秒级**，而 MySQL 的 `LIKE '%x%'` 是几十秒级的全表扫。**这不是快慢的问题，是能不能用的问题。**
> **第三，聚合统计**。运营看板要的"拦截率趋势、TOP 攻击 IP、延迟 P99"，在 ES 里是一次聚合查询就能出，**而且是分布式的、能并行**。
> **第四，运维成本**。日志有天然的时间属性——**ES 的索引生命周期管理（ILM）能自动做"热 → 温 → 冷 → 删"**，不用自己写归档脚本。
> **但我会明确一点：ES 只存"日志"，不存"权威数据"**。策略配置、租户信息这些还在 MySQL。而且我会做**采样和分级**——**不是所有请求都写全量日志**，正常请求只记摘要（甚至按比例采样），只有**异常和拦截的请求才记完整的请求体和 Prompt**，**这样存储成本能降一个数量级。**"
>
> ⚠️ **补充一句暴露你真懂的话**："另外**网关写 ES 绝对不能是同步阻塞的**——一定是**异步批量写**（本地先攒批，再用 Bulk API 批量提交），而且 **ES 写失败不能影响网关的主流程**，只能降级丢日志 + 告警。**日志是可以丢的，请求不能失败。**"

### 7.8 ⚠️ 诚实边界话术

**如果被问「你用过 ES 吗」**：

> "**ES 我没有在生产环境搭过集群**，我的检索经验是**用 PostgreSQL 做 RAG 里的向量检索**（AI 漏洞研判系统里用的 pgvector），思维上是相通的——都是"**索引结构决定查询模式**"，但 ES 的分布式特性和运维我没实操过。
> **不过 ES 的选型逻辑我清楚**：它是为「**海量 + 全文检索 + 聚合分析**」准备的，代价是**不能当数据库用、近实时、更新代价高**。**如果这个网关的日志检索要我选**，我会先看两个数——**每天多少条、要保留多久**；如果只有几百万条、保留 30 天，我可能先用 **MongoDB 的 TTL 索引**扛住（少维护一个集群）；量再上一个数量级，**ES 就是唯一的选择了**。"

| 2 | 聚簇索引与回表？ | **主键索引即聚簇索引，叶子存整行**；二级索引叶子只存索引列 + 主键，查其他列要**回表** | **覆盖索引**怎么避免回表 |【必答】|
| 3 | MVCC 是什么？ | **隐藏列（事务 ID + 回滚指针）+ undo 版本链 + ReadView 可见性判断**，实现读不加锁 | ★ **RC 和 RR 的区别**（ReadView 生成时机）|【必答】|
| 4 | RR 怎么解决幻读？ | **快照读**靠 MVCC 的 ReadView；**当前读**靠**间隙锁 / 临键锁**堵住区间插入 | ⚠️ 别答成"MVCC 解决了所有幻读" |【陷阱】|
| 5 | 两阶段提交是什么？ | 写 redo（prepare）→ 写 binlog → 写 redo（commit）；**崩溃恢复看 redo 是否 prepare 且 binlog 是否完整** | **为什么需要 2PC**（保证 redo 和 binlog 一致，否则主从不一致）|【必答】|
| 6 | binlog 三种格式？ | **STATEMENT（小但不一致）/ ROW（大但绝对一致，8.0 默认）/ MIXED** | ★ **CDC 必须用 ROW**（Canal/Debezium 靠解析行变更）|【必答】|
| 7 | 死锁怎么排查？ | `SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`；`innodb_print_all_deadlocks=ON` 记录所有 | 预防：**固定加锁顺序、缩短事务、走索引、乐观锁** |【加分】|
| 8 | 单表数据量大了怎么办？ | **五步走**：归档/冷热分离 → 汇总表 → 读写分离 → 分区表 → 分库分表（**成本递增**） | ★ **分库分表的痛点**：跨库 JOIN、分布式 ID、分页、扩容 |【必答】|

#### Redis（8 题）

| # | 问题 | 一句话答案 | 追问方向 | 标记 |

| 9 | Redis 为什么快？ | **纯内存 + epoll 多路复用 + 单线程无锁无切换 + 高效数据结构** | ⚠️ 别答成"因为单线程"；6.0 的**多线程只是网络 IO** |【陷阱】|
| 10 | 缓存穿透/击穿/雪崩？ | **穿透 = 查不存在的数据**（空值缓存 + 布隆过滤）；**击穿 = 热点 key 过期**（互斥锁 + 逻辑过期）；**雪崩 = 大量 key 同时失效**（TTL 打散 + 多级缓存） | ★ **每一类都要能接上自己的项目** |【必答】|

| 14 | 持久化怎么选？ | **RDB 快恢复但丢数据多；AOF 丢数据少但恢复慢；生产用混合持久化** | AOF 的 `everysec` 最多丢 1 秒；**Redis 不能当数据库用** |【必答】|
| 15 | Cluster 的 16384 个槽是什么？ | `CRC16(key) % 16384`；**16384 是因为心跳包的槽位 bitmap 只有 2KB** | ★ **MOVED vs ASK**（永久迁移 vs 临时重定向）|【加分】|
| 16 | 大 Key / 热 Key 怎么处理？ | **大 Key → 拆分 + UNLINK 异步删**；**热 Key → 本地缓存 + 多副本分发 + 读写分离** | 发现手段：`--bigkeys`、`--hotkeys`、客户端埋点 |【必答】|

### Q1：设计一个支持 10 万 QPS 的 AI 安全网关（存储层怎么选型？）

**【面试官意图】**
看你会不会**从需求拆解到选型**，而不是上来就报组件名。这道题 80% 的分在**存储选型**和**分层思路**上。

**【答题框架】**
1. **先问需求**：10 万 QPS 是峰值还是均值？请求大小？是否流式？策略变更频率？日志保留多久？
2. **分层设计**：接入层 → 网关层（无状态水平扩）→ 缓存层 → 存储层 → 异步链路
3. **按数据分类做存储选型**（★ 核心）
4. **风险与兜底**

**【具体答法】**

> "先确认几个约束：如果是**峰值 10 万 QPS、请求体平均 10KB、包含流式响应**，那第一件事是**单机不可能扛**——我会用**无状态网关 + 水平扩展**，按单机 1 万 QPS 算（Go 的 HTTP 服务单机能到几万，但要做安全检测会降到万级），**至少 10-15 个实例，再加 N+1 冗余**。
> **存储我会按数据性质分四类，而不是找"一个能装所有的库"**：

| 数据 | 选型 | 关键理由 |
| --- | --- | --- |
| **策略配置** | **MySQL（权威）+ Redis（缓存）+ ETCD/Redis Pub/Sub（下发）** | 配置是控制平面，**权威性 > 灵活性**；读多写少，缓存命中率极高 |
| **限流计数/配额** | **Redis（Lua 原子操作）** | 10 万 QPS 的原子计数只有内存能扛；**且用本地+Redis 两级**（本地令牌桶先拦，超出的才查 Redis） |
| **审计/访问日志** | **Kafka（缓冲）→ ES（检索）+ 对象存储（冷归档）** | 10 万 QPS × 86400 ≈ **86 亿条/天**，**必须异步 + 采样**，同步写日志会直接拖垮网关 |
| **实时统计** | **Redis 计数 + 分钟级聚合落库** | 看板要毫秒级，历史分析要列存 |

> **三个关键决策我要强调**：
> **第一，网关实例必须完全无状态**——配置从缓存读、计数在 Redis、日志异步发 Kafka，**这样扩缩容、重启都不丢东西**。
> **第二，写日志绝对不能同步**——网关的每次请求都在关键路径上，**日志写入必须走"本地攒批 + 异步发送"**，而且**发送失败只能降级丢弃 + 告警，绝不能阻塞请求**。**请求可以少记一条日志，但不能因此变慢。**
> **第三，全量日志是不可能全存的**——86 亿条/天，按 1KB/条算就是 **8.6TB/天**。所以必须**分级采样**：正常请求只记摘要（甚至可以按 1% 采样），**只有拦截、异常、超时的请求才记完整内容**。这一刀砍下去，存储成本能降两个数量级。
> **兜底方面**：Redis 挂了 → 限流降级为**本地令牌桶**（宁可放多一点也不能全拦）；配置中心挂了 → 各实例**用本地缓存继续跑**（配置是只读的，短时间不更新没关系）；ES 挂了 → 日志降级到本地文件，恢复后补传。**核心原则是：安全策略和转发不能依赖任何"可能挂掉的组件"。**"

**★ 结合候选人项目**：
> "这套思路我在 POS 中台里用过**缩小版**——中台的接入层也是无状态的，靠 ETCD 拿服务列表，Redis 做限流和去重，RabbitMQ 做异步链路，**日志同样不阻塞主流程**。10 万 QPS 的差别主要是**量级和采样策略**，但**"分层 + 无状态 + 异步 + 降级"这四个原则是一样的**。"

### Q2：大模型请求怎么做限流和计费？（★ 结合 LoveSpouse 金币计费）

**【面试官意图】**
这是**本岗位的核心业务题**。考察：① 限流算法的选择 ② 计费的准确性与幂等 ③ 你有没有真实踩过坑。

**【答题框架】**
限流（多维度）→ 计费（预扣 + 结算）→ 幂等 → 对账与兜底。

**【具体答法】**

> "**限流和计费是两件事，但都要防同一个东西——超用**。我分开讲。

**一、限流要分维度，不能只有一个总限流**：

| 维度 | 目的 | 实现 |
| --- | --- | --- |
| **租户/API Key** | 套餐隔离（免费版 vs 付费版） | **Redis + Lua 令牌桶**（分布式，精确） |
| **用户** | 防单个用户刷 | 同上，key 换成用户维度 |
| **节点本地** | 减少 Redis 压力、防 Redis 挂 | **本地令牌桶/滑动窗口**（单机先拦，超出的才查 Redis） |
| **Token 消耗** | ★ **大模型特有**——按请求数限流不够，因为一个请求可能烧几万 Token | **按 Token 配额限流**（预估 + 实际修正） |
| **成本** | 防成本攻击 | 按"预估 Token × 单价"折算额度 |

> **两级限流的做法**：**本地先做粗限流**（比如按 `总额度 / 实例数 × 1.5` 分配），**每个实例在本地用令牌桶拦住大部分**，只有本地放行的才去 Redis 做**精确校验和扣减**。**这样 Redis 的压力能降一到两个数量级**，而且 Redis 挂了本地限流还在，不会全放行。

**二、计费我用的是"预扣 + 增量结算 + 幂等"**（这部分 **LoveSpouse 是我真实做过的**）：

> "我在 LoveSpouse 做 Gemini Live 实时语音的金币计费，**最开始写的是先 `GET` 查余额再 `DECRBY` 扣**——压测时发现**并发下会超扣**：两个请求同时读到 100，各扣 100，余额变成 -100。改成先 `DECRBY` 再判断负数补回，也不干净——**会有负余额的中间态，而且补回失败就真超扣了**。
> 最后我用 **Lua 脚本**把三件事做成一个原子操作：**校验余额 → 校验幂等键 → 扣减**。既不会超扣，也没有中间态。**这是我印象最深的一次"教科书上的并发问题在真实业务里发生"的经历。**
> 业务流程上是**预扣 + 结算**：发起通话先按预估时长**冻结**一笔，余额不够直接拒绝（**从源头避免坏账**）；通话中按心跳做**增量扣减**，余额耗尽主动断线；结束时按**实际用量多退少补**。这套跟 TCC 的 Try/Confirm/Cancel 是一个思路，只是我没上分布式事务框架，用 Lua + 幂等键在 Redis 里实现了。
> **幂等**上，每次扣减带一个 `requestID`，Lua 里判断——**同一个 ID 只扣一次，重复请求直接返回成功**；MySQL 流水表上 `request_id` 建唯一索引作为**第二道防线**（Redis 的 key 会过期，数据库不会）。
> **一致性和对账**：Redis 是实时账，MySQL 是账本。扣减成功后异步把流水落库（用 MQ 保证不丢），再跑一个**定时对账任务**比对"初始余额 - 流水累计"和"Redis 余额"，有差异就告警并以 MySQL 为准修正。**我的原则是：Redis 可以丢，但账不能丢。**"

**★ 迁移到 AI 网关**：
> "**如果放到 AI 安全网关里，我会做两处调整**：**第一，从"按时长"改成"按 Token"** —— 计费单元变成输入/输出 Token 数，所以要在流式响应里**累计 Token 用量**，结束时结算；**第二，增加"预估预扣"这一层** —— 因为大模型请求的 Token 数无法提前精确知道，我会按"Prompt 长度估算 + 最大输出 Token 上限"来预扣，结束时按实际用量退还。**这样既能防止用户超额，又不会让预扣太保守导致体验差。**"

### Q3：怎么设计一个支持多租户的策略配置系统？（存储用 MySQL 还是 MongoDB？）

**【面试官意图】**
① 多租户设计能力 ② **选型判断题**（岗位标签有 MongoDB）③ 配置的下发与热更新。

**【答题框架】**
数据模型 → 存储选型（★ 重点）→ 下发机制 → 版本与回滚 → 灰度。

**【具体答法】**

> "先拆分'策略配置'这个需求：**谁写（运营/租户管理员，低频）、谁读（网关实例，高频）、怎么生效（秒级）、要不要审计（要）**。这四个问题的答案决定了方案。

**一、存储选型（★ 这道题的核心）**

> **我的判断是：MySQL 做权威存储 + Redis 做缓存，MongoDB 只在特定条件下才值得引入。**

| 方案 | 优势 | 代价 | 什么时候选 |
| --- | --- | --- | --- |
| **MySQL + JSON 列 + Redis 缓存** | 事务、审计、运维熟悉、**少一个组件** | 策略字段差异要靠 JSON 列 + 应用层校验 | ★ **策略类型稳定（十几种）、团队小** → **默认选它** |
| **MongoDB** | **文档模型天然容纳不同策略的差异字段**；多版本快照方便；读性能好 | 多一套副本集运维；无 JOIN；团队不熟 | **策略是插件化的、类型持续增长、还要存大量历史版本** |
| **ETCD** | watch 天然热更新、强一致 | 不适合存大配置和复杂结构 | **只存"配置的版本号指针"**，不存内容 |

> **我的决策口径**：**"我会先问策略类型会不会持续爆炸式增长。**如果会——比如这个网关要支持几十种插件、每种插件的策略字段完全不同——那 MongoDB 的文档模型就值这个运维成本，**因为用 MySQL 你就要不停加列或者把所有差异塞进一个 JSON 列，那还不如直接用文档库**。**如果策略是稳定的一二十种，我选 MySQL**，因为**配置是控制平面，权威性比灵活性重要**，而且少维护一个组件对 0-20 人的团队是实打实的收益。**"

**二、数据模型（多租户的关键）**

```
tenant（租户）
  └── policy_group（策略组，按业务场景分）
        └── policy（策略条目：类型 + 优先级 + 生效范围 + 规则内容 JSON）
              └── policy_version（历史版本，用于回滚）
```

- ★ **所有表必须带 `tenant_id`**，并且**所有查询都必须带租户条件**（防止越权）。
- **策略用"优先级 + 匹配条件"模型**：`priority`（数字越大越优先）+ `match`（路由、模型、用户组），**求值从高到低取第一个命中的**——这就是网关策略路由的标准做法。
- **多版本**：每次修改生成一个新 version 记录，**发布是"把指针指向某个 version"**，回滚 = 指针指回旧版本。**这样回滚是秒级的。**

**三、下发机制（★ 秒级生效怎么保证）**

| 方案 | 说明 |
| --- | --- |
| **推送（推荐）** | 配置变更 → 写 MySQL → **发布到 Redis Pub/Sub 或 ETCD** → 各网关实例收到通知 → **主动拉取全量配置**（不是推全量） |
| **拉取兜底** | 网关**每 30 秒轮询一次版本号**（`GET config:version`），版本变了才拉——**防止推送丢失导致的配置不一致** |
| **本地缓存** | 每个实例内存里存一份**当前生效的配置**，配置中心挂了也能继续跑 |

> ★ **"推 + 拉"双保险是这道题的加分点**：
> "**只推的话，一个实例网络抖一下没收到通知，就会一直用旧配置**；**只拉的话，实时性受轮询周期限制**。所以我的做法是**推送负责实时性、轮询负责兜底正确性**。而且推送的内容只是**一个版本号**，实例收到后自己去拉全量——**避免大配置在广播时把消息通道打爆。**"

**四、灰度与安全**
- **灰度发布**：配置带"生效范围"（按实例标签/百分比），**先发 1% 的实例**，观察指标再全量。
- **写操作要审计**：谁改了什么、什么时间、改前改后是什么（`policy_audit` 表）。
- **校验前置**：配置发布前**必须做语法/语义校验**（一条写错的策略可能让整个网关不可用）。

**★ 结合候选人项目**：
> "**POS 中台里我做过类似的"多租户配置分发"** —— 多条产品线接入，每条产品线的字段映射规则不一样，我当时的做法是**配置存 MySQL、用 ETCD 做变更通知**（go-zero 的配置中心就是基于 ETCD 的 watch），**网关/消费端监听 key 变化后重新加载**。所以**"推 + 拉 + 本地缓存"这套模式我实操过**，只是当时的数据量小，一个 JSON 列就够了，没有用 MongoDB 的必要。"

### Q4：网关每天产生 10 亿条访问日志，怎么存储和检索？

**【面试官意图】**
① 海量数据的架构能力 ② ES 的定位（JD 要求）③ 成本意识。

**【答题框架】**
采集 → 缓冲 → 存储分层 → 检索 → 生命周期 → 成本控制。

**【具体答法】**

> "10 亿条/天，按平均 1KB 算就是 **1TB/天、一年 365TB**——**这道题真正的考点不是"用什么存"，而是"怎么能不存这么多"**。

**一、先砍量（★ 这是最容易被忽略但最有价值的一步）**

| 手段 | 效果 |
| --- | --- |
| **分级记录** | 正常请求只记摘要字段（时间、租户、模型、状态、耗时），**只有拦截/异常/超时的才记完整请求体** |
| **采样** | 正常流量**按 1%~10% 采样**（可配）；错误流量 100% 记录 |
| **字段裁剪** | 请求头只留必要的几个，**不存原始 body**（大 body 存对象存储，日志里只存引用 ID） |
| **聚合** | 秒级明细保留 3 天，之后只有分钟级聚合（TPS/延迟/错误率） |

> **这一刀下去，10 亿条 → 可能只剩 1 亿条**，成本直接降一个数量级。

**二、采集链路（★ 必须异步）**

```
网关（本地攒批，200 条或 1 秒）→ Kafka（削峰 + 缓冲）→ 消费写入 ES
                                        └→ 同步写对象存储（原始全量，冷归档）
```

> **为什么中间要加 Kafka**：① **削峰**（ES 写入有抖动时不会拖垮网关）② **解耦**（ES 挂了消息还在 Kafka 里，可以重放）③ **一进多出**（同一份数据既写 ES 又写对象存储、还能给实时计算用）。**直接写 ES 的架构在流量高峰一定会出问题。**

**三、存储与检索（ES 是主力）**

| 层 | 存储 | 保留 | 用途 |
| --- | --- | --- | --- |
| **热** | ES（SSD，多副本） | 7 天 | 实时检索、聚合、告警 |
| **温** | ES（大容量盘，副本降为 1） | 30 天 | 事后排查 |
| **冷** | 对象存储（Parquet 格式） | 1 年+ | 合规归档，用 Trino/Spark 离线查 |

- **索引按天滚动**（`access-log-2026.09.22`），**用 ILM 自动做"热→温→冷→删"**。
- ⚠️ **分片规划**：按"单分片 10-50GB"反推——1TB/天的话，**每天索引大概 20-40 个主分片**；分片太多会有 oversharding 问题，所以**也可以按小时滚动或调大单分片容量**。
- **字段映射**：`tenant_id`、`status`、`model` 用 **`keyword`**（要聚合）；`prompt`、`path` 用 **`text` + IK 分词**（要检索）；时间字段用 `date`。
- **检索优化**：**不过算分的过滤条件一律用 `filter`**（走缓存）；**深分页用 `search_after`** 不用 `from+size`。

**四、成本与兜底**
- ⚠️ **ES 的存储成本大约是原始数据的 2-5 倍**（倒排 + 列存 + 副本）——**这是必须主动说出来的**。
- **ES 挂了**：日志降级写本地磁盘 + 告警，恢复后补传。**绝不能让写日志失败影响网关转发。**
- **降级开关**：流量异常时**动态调低采样率**（配置化，秒级生效）。

**★ 结合候选人项目**：
> "这套**分层 + 异步 + 采样**的思路我用过缩小版——**POS 中台的数据上传链路**，门店高峰期流量集中，我的做法是**接入层先落本地消息表 → 发 MQ → 消费端批量落库**，而且**非关键的埋点数据我做了采样**。**差别只在量级（我们是百万级、这里是十亿级）和检索引擎上**；**"先砍量、再缓冲、后分层"的顺序是一样的。**"

### Q5：线上突然大量 502，怎么排查？

**【面试官意图】**
**排障方法论**——这是运维能力和冷静度的体现。★ 注意：**不要一上来就说"重启"**。

**【答题框架】**
定性（范围）→ 分层排查 → 定位根因 → 止损 → 复盘。

**【具体答法】**

> "**第一步不是查，是界定范围**——四个问题：**① 全部请求还是部分？② 所有实例还是个别实例？③ 什么时候开始的？④ 之前有没有变更（发布/配置/扩容）？**
> 这四个问题能砍掉 80% 的排查空间。**而且如果有变更，第一动作是回滚，不是排查**——线上优先恢复服务。

**502 的本质**：**网关/代理从上游拿不到有效响应**（Bad Gateway）。所以链路是：**客户端 → 网关/Nginx → 上游服务**，逐段查。

| 层 | 检查项 | 命令/方法 |
| --- | --- | --- |
| **① 上游服务还活着吗？** | 进程在不在、端口在不在听 | `ps`、`ss -lntp`、`curl 本机健康检查` |
| **② 是不是全挂了还是部分？** | 如果**部分实例挂**，是死循环/OOM/连接泄露 | 看各实例错误率分布 |
| **③ 资源到顶了吗？** | CPU、内存、**文件描述符**、连接数 | `top`、`free`、`ulimit -n`、`ss -s` |
| **④ 是不是连接被拒绝？** | ★ **`connect() failed (111: Connection refused)`** = 后端没在听（进程挂了/端口错）；**`upstream timed out`** = 后端在但没响应（**线程/协程池满了**） | Nginx error log、网关日志 |
| **⑤ DNS / 服务发现正常吗？** | 上游地址解析对不对 | `dig`、看注册中心 |
| **⑥ 是不是被限流/熔断了？** | ★ **网关主动返回 502/503 是熔断生效**（保护下游） | 看熔断器状态 |
| **⑦ 上游依赖挂了吗？** | DB / Redis / 下游 API 超时导致业务整体不可用 | 看依赖的健康状态 |

**常见根因排序（按我遇到过的频率）**：
1. ★ **上游服务 OOM 或崩溃重启**（内存泄露、大对象、goroutine 泄露）
2. ★ **连接池/协程池打满**（下游慢导致积压）
3. **文件描述符耗尽**（`too many open files`）——连接没关闭
4. **配置发布错误**（上游地址改了、权重错了）
5. **网络问题**（DNS、安全组、跨机房抖动）
6. **突发流量超过容量**（没限流）

**止损动作（按优先级）**：
1. **回滚最近的变更**（最快见效）
2. **扩容**（加实例）
3. **限流/降级**（保住核心接口）
4. **重启挂掉的实例**（⚠️ **治标**，要同时留现场：`kill -QUIT` 拿 goroutine dump、`pprof` 拿 heap）

**★ 结合候选人项目**：
> "我在 POS 中台遇到过类似的问题——**大量接口 502，最后定位是消费服务被 MQ 的消息压垮了**：消费端 goroutine 数量没限制，DB 连接池被打满，导致 HTTP 接口也拿不到连接。**根因不是 502 本身，是资源池共享**。
> 我的修复是**把资源池隔离**：消费任务和 HTTP 接口用**不同的数据库连接池**，消费端加了**并发上限和背压**（队列满就暂停消费）。**这件事让我记住了"隔离"这条原则——一个模块把共享资源耗光，会把整个服务拖死。**"

### Q6：数据库 QPS 扛不住了，你的优化路径是什么？

**【面试官意图】**
**优化方法论**——按成本递增的顺序说，体现你**不会上来就分库分表**。

**【答题框架】**
**先看是不是 SQL 的问题 → 再缓存 → 再读写分离 → 最后才拆**。

**【具体答法：五步走，成本从低到高】**

| 步骤 | 手段 | 成本 | 收益 |
| --- | --- | --- | --- |
| **① 先看慢 SQL** | 慢日志 + `EXPLAIN`；**80% 的情况是几个慢 SQL 拖垮了整个实例** | ★ **极低** | 常常直接解决问题 |
| **② 加/改索引 + 改写 SQL** | 覆盖索引免回表、去掉 filesort、深分页改游标 | 低（在线 DDL 有风险） | 高 |
| **③ 加缓存** | Redis 缓存热点读；**写少读多的场景收益最大** | 中（要处理一致性） | 高 |
| **④ 读写分离** | 一主多从，读走从库 | 中（⚠️ **主从延迟**） | 中高 |
| **⑤ 垂直拆分 / 分库分表** | 按业务拆库 → 按分片键水平拆 | ★ **高（改代码、跨库 JOIN、分布式 ID、扩容）** | 高但代价大 |

> **我的顺序理由（★ 说这句显得务实）**：
> "**这五步是"成本递增"的**——前面几步可能一两天就能做完，最后一步要做几个月而且**会永久提高系统复杂度**。所以**我会先把①②③做到底，再评估要不要走到⑤**。
> **补充一点：如果是"读"扛不住**，缓存 + 读写分离基本能解决；**如果是"写"扛不住**，那才是分库分表的场景——**写的问题没有捷径。**"

**★ 结合候选人项目（POS 数据贯通）**：
> "POS 中台我走过完整的这个路径：
> **第一阶段**，慢日志里发现流水查询的 `EXPLAIN` 是 `type=ALL`、扫几百万行——**根因是我最初把 `biz_date` 放在了联合索引最左**，查询实际是"门店 + 时间段"，等值列必须在最左。**改成 `(shop_id, biz_date, id)` 之后，扫的行数从百万级降到几百行，P99 从秒级降到百毫秒内。**
> **第二阶段**，接入产品线变多之后写入压力上来了，我做了**批量写入**（攒批 500 条）+ **冷热分离**（按 `biz_date` 分区，历史分区直接 `DROP`）。
> **第三阶段**，统计类查询我用 **Redis 缓存 + 分钟级汇总表**，**把原来直接打 MySQL 的看板查询全部挡住**。
> **我们最终没有走到分库分表**——因为上面三步做完，单实例还能撑很久。**我的判断是：分库分表是"最后一招"，因为它是不可逆的架构复杂度。**"

### Q7：一个接口偶发超时，怎么定位？

**【面试官意图】**
**"偶发"是最难的排查类型**——考察你有没有系统性的方法，而不是靠猜。

**【答题框架】**
先说清"偶发"的难点 → 三段定位（入口/中间/依赖）→ 手段 → 常见根因。

**【具体答法】**

> "**"偶发"的难点在于无法复现**，所以思路是：**先把"偶发"变成"可观测"，再用数据定位。**

**一、先明确超时的位置（★ 最关键的一步）**
> "**我要先看这个超时发生在哪一段**：是网关到服务的超时、服务内部的超时、还是服务到下游的超时？**这决定了后面往哪个方向查。**"

**二、必备的观测手段**

| 手段 | 作用 |
| --- | --- |
| **全链路 Trace（TraceID）** | ★ **最重要**——把一次请求的所有跨度串起来，**直接看到哪个 span 慢** |
| **分位数指标（P50/P95/P99/Max）** | ⚠️ **平均值会掩盖偶发问题**；看 **P99 和 Max** |
| **日志（带耗时打点）** | 记录每个阶段的耗时，定位到具体调用 |
| **pprof / 火焰图** | 如果是 CPU/GC 问题，直接看火焰图 |
| **网络抓包（tcpdump）** | 看是不是有重传、握手慢 |

**三、常见根因（按"偶发"的典型性排序）**

| 根因 | 特征 | 定位方法 |
| --- | --- | --- |
| ★ **GC 停顿** | 周期性出现，与 GC 日志时间吻合 | 开 GC 日志、看 `GODEBUG=gctrace=1`、pprof |
| ★ **连接池打满** | 高峰期集中出现，伴随"等连接"日志 | 连接池指标、`wait_time` |
| ★ **锁竞争** | 特定接口并发时出现 | pprof 的 mutex/block profile |
| **下游偶发慢** | 调用下游的耗时抖动 | Trace 里能看到 span 变长 |
| **网络抖动/重传** | 随机的、跨实例的 | 抓包、看 TCP 重传率 |
| **慢 SQL（偶发）** | 特定参数触发的索引失效、锁等待 | 慢日志按"偶发"筛选 |
| **定时任务抢资源** | ★ **周期性的**——每天几点、每小时的整点 | 对比时间分布 |
| **限流/熔断触发** | 特定流量下触发 | 中间件指标 |

**四、我的定位流程**
1. **确认超时分布**：是随机的、还是周期性的？是集中在某些实例/某些时间段？→ **周期性 = 定时任务；集中在某实例 = 该实例有问题；随机 = 依赖抖动。**
2. **用 TraceID 捞几条慢请求的完整链路**，看卡在哪个环节。
3. **看那一段的资源指标**（连接池、线程/协程、GC、DB 慢日志）。
4. **加埋点复现**（打点每个阶段耗时，把"偶发"变成"能统计"）。

**★ 结合候选人项目**：
> "LoveSpouse 里我遇到过**偶发的通话建立超时**——不是每次，但高峰期偶发。**用 TraceID 串起来后发现卡在"获取分布式锁"这一步**：我一开始的锁等待是**固定 sleep 后重试**，在锁竞争激烈时会累积等待时间。后来改成**带超时的自旋 + 快速失败**（拿不到锁就返回"当前有其他通话"，让客户端重试），**把偶发超时变成了明确的可重试错误**。
> **这件事让我学到的经验是：偶发超时最好的解法常常不是"优化到不超时"，而是"把它变成一个明确的、可重试的失败"**——把不确定变成确定。"

### Q8：Redis 挂了怎么办？怎么保证业务不雪崩？

**【面试官意图】**
**容灾与降级**——考察你有没有"假设依赖会挂"的思维。

**【答题框架】**
高可用（不让它挂）→ 降级（挂了怎么办）→ 具体到自己的业务。

**【具体答法】**

**一、先分层：Redis 挂有不同的程度**

| 程度 | 影响 | 应对 |
| --- | --- | --- |
| **单节点挂** | 主从切换（哨兵/集群自动） | **秒级自愈**，业务几乎无感 |
| **主从切换期间** | **短暂不可写**（几秒到几十秒） | 客户端**重试 + 短暂降级** |
| **整个集群挂** | ★ **严重**：缓存全部失效 | **降级 + 熔断 + 多级缓存** |

**二、预防（不让它挂）**
- **高可用部署**：哨兵或 Cluster（3 主 3 从），**禁用一键 `FLUSHALL`**、`rename-command` 屏蔽危险命令。
- **容量监控**：内存使用率、**大 key 巡检**、慢查询、连接数告警。
- **⚠️ 最大的风险不是"Redis 挂"，而是"Redis 慢"** —— 慢查询阻塞单线程会让所有请求超时，**效果和挂了一样**。所以要监控"**命令耗时 P99**"。
- **客户端超时必须设**（⚠️ 不设超时 = Redis 卡住会拖垮整个应用），**连接池要有上限**。

**三、降级（挂了怎么办）—— ★ 这部分是重点**

| 数据用途 | 挂了怎么办 |
| --- | --- |
| **缓存（可重建）** | ★ **回源到 DB**，但要**加并发控制**（`singleflight`），**否则缓存失效瞬间 DB 被击穿**——这就是"雪崩" |
| **计数/限流** | 降级为**本地限流**（每个实例按 `总额度/实例数` 分配），**宁可限得不准也不能不限** |
| **分布式锁** | ⚠️ **绝不能降级为"直接放行"**（会破坏互斥）；应该**快速失败**，让业务重试 |
| **计费余额** | ★ **拒绝新请求，而不是放行**——"临时不可用"比"乱扣钱"好 |
| **Session/登录态** | 降级为**本地缓存 + 短 TTL**（可容忍） |

> ★ **这里有一个关键的设计原则要说清楚**：
> "**降级策略取决于"这个数据是"可以重建的"还是"不能错的"**：**缓存类数据可以回源**（顶多是慢），**锁和余额这类状态数据必须快速失败**（宁可不可用，不能出错）。**这两种情况的降级方向是相反的，不能一刀切说"Redis 挂了就放行"。**"

**四、多级缓存（真正的抗雪崩）**
```
本地缓存（进程内，抗量最大）→ Redis（分布式共享）→ DB（最后防线）
```
> **最热的 20% 数据放本地缓存**（如租户配置、热门商品），**TTL 很短（几秒）**——**Redis 全挂时，本地缓存还能扛住大部分读流量**。这是"**雪崩**"问题最有效的解法。

**★ 结合候选人项目**：
> "**LoveSpouse 的计费场景，我的降级策略就是"快速失败"** —— Redis 不可用时**拒绝新的通话请求**，而不是让用户免费打。**因为乱扣钱和免费送都是业务事故，但"暂时不可用"不是。**
> **POS 中台里 Redis 主要是缓存和去重**，所以降级策略相反——Redis 挂了就**回源到 MySQL**，同时**用 `singleflight` 把并发的回源请求合并**，避免缓存失效瞬间把 DB 打穿。**限流那一层降级成本地限流**，保证保护作用还在。
> **所以我的结论是：降级策略要按"数据性质"分别设计，而不是系统级的一刀切。**"

### Q9：消息队列积压了 100 万条消息，怎么处理？

**【面试官意图】**
**应急处理能力** + **对 MQ 机制的理解**。⚠️ 千万别答"直接清空队列"。

**【答题框架】**
定性 → 止血（扩容）→ 根因（为什么慢）→ 消化 → 预防。

**【具体答法】**

> "**先定性，别急着动手**——三个问题：**① 是突发流量（等一会儿自己会消）还是消费者变慢（不会自己好）？② 消息能不能丢？③ 现在还在持续进消息吗？**"

**一、止血（按见效速度排序）**

| 措施 | 说明 |
| --- | --- |
| **① 加消费者实例** | 最快见效；⚠️ 注意**消费者总数不要超过队列的分区/并发能力**（RabbitMQ 单队列多消费者是可以的，但要保证幂等和顺序要求） |
| **② 提高 prefetch / 批量拉取** | 减少往返。从 `prefetch=1` 调到 20-50 |
| **③ 消费者内部并发处理** | 用 goroutine 池并行处理（⚠️ **只有在不需要顺序时才能这么做**）|
| **④ 批量落库** | 我做过的最有效的一招：**每次攒 500 条一次写库**，吞吐直接上一个数量级 |
| **⑤ 优化消费逻辑** | 去掉同步的外部调用（改成批量/异步）、加缓存、避免每条都查一次 DB |

**二、如果还是追不上（★ 分情况）**

| 情况 | 做法 |
| --- | --- |
| **消息可丢（埋点/日志）** | 按比例**降级丢弃**，或者**先把消息落盘到对象存储**再清队列，离线补 |
| **消息不能丢（业务数据）** | ★ **绝不能清空**。做法：**导出到文件/中转存储 → 清空队列让线上止血 → 起离线任务慢慢补**；或者**开新的消费者组/新队列专门并行消化**（Kafka 可以重置 offset 从头消费） |
| **生产者持续在发** | ★ **必须同时给生产者限流或降级**——不然一边消一边涨，永远追不上 |

**三、根因（为什么积压）**
- 下游变慢（DB 慢查询、外部 API 超时）→ **消费线程全卡在等下游**
- 消费者数量不足 / 单消费者串行
- **大消息**（单条处理耗时高）
- **消费逻辑里有个耗时的同步调用**
- **一条坏消息不停重试**（★ **死循环重投**，看起来像积压但其实是"一条消息卡住整个队列"）

⚠️ **最后一类要说出来，因为它最容易误判**：
> "**有一个特别容易误判的情况：队列里其实只有几条消息，但消费者一直在重试同一批坏消息，看起来是"消费不动"**。这时候要看的是**消息的重投次数**而不是队列深度——**我的做法是给消息带一个重试计数，超过 3 次直接进死信队列 + 告警，不让它继续占着消费者。**"

**四、预防**
- **队列深度 + 消费延迟告警**（提前发现，不等用户投诉）
- **压测出消费者的最大吞吐**，按这个配容量和扩容阈值
- **消费端加背压**（队列超过阈值就暂停拉取）
- **监控消费速率 vs 生产速率**（★ **看趋势比看绝对值有用**）

**★ 结合候选人项目**：
> "**POS 中台我处理过一次真实的积压**——门店早高峰集中上传，队列堆了几十万条。我的处理顺序是：**先把 `prefetch` 调大、批次改到 500 条一批**（吞吐立刻上一个数量级），**再把消费者 goroutine 数量按 DB 连接池的容量调到刚好打满**——注意这里**不能再往上调了，否则会打爆连接池**，反而更慢。**然后把非关键的埋点消息临时降级丢弃**，优先保证流水数据。
> **事后我做的是预防**：加了队列深度告警（超过 10 万条预警）、给消息加了重试计数上限进死信。**这个经验的总结是：扩容只能解决"消费者不够"，如果是"下游慢"导致的，扩容反而会加剧下游的压力。**"

### Q10：怎么设计一个幂等的支付/计费接口？

**【面试官意图】**
**这是最经典的分布式设计题**。考察幂等键的设计、存储选型、并发控制、对账。

**【答题框架】**
幂等键设计 → 幂等的实现（多层）→ 并发控制 → 一致性 → 对账 → 失败补偿。

**【具体答法】**

**一、幂等键的设计（★ 第一步，也是最容易被忽略的）**

> "**幂等的前提是有一个能唯一标识"这一次业务操作"的键**。它的来源有三种：
> **① 客户端生成**（推荐）：客户端生成 `requestID`（UUID）随请求带上，**重试时用同一个 ID** —— 这是最可靠的，因为**客户端的重试意图它自己最清楚**。
> **② 业务键组合**：如 `订单号 + 操作类型`，或者 `用户ID + 时间戳 + 金额` 的哈希。**要求业务上天然唯一。**
> **③ 服务端生成**：不推荐——服务端生成的话，重试时无法判断是不是同一次请求。"

⚠️ **要提醒的坑**：
> "**幂等键不能只用"消息 ID"**——比如腾讯 IM 的消息，`MsgSeq` 是**会话内递增**的，跨会话会重复，必须组合成 `{会话ID}:{MsgSeq}` 或使用全局唯一的 `MsgKey`。**幂等键选错了，幂等就是假的。**"

**二、实现方案（★ 四层，按可靠性排序）**

| 方案 | 实现 | 特点 |
| --- | --- | --- |
| **① 数据库唯一索引** ★ | 建 `(idempotent_key)` 唯一索引，插入冲突即重复 | **最可靠**；缺点是要写库 |
| **② 状态机 + 条件更新** ★ | `UPDATE ... SET status='paid' WHERE id=? AND status='pending'`，**影响行数=0 说明已处理** | 天然幂等，**同时防并发** |
| **③ Redis SETNX** | `SETNX idem:{key} 1 EX 3600` | 最快，但**不可靠**（重启/过期会失效）→ 只能当快速拦截 |
| **④ 去重表** | `dedup(key unique, biz_id, created_at)`，**和业务在同一个事务里** | 通用（业务没有天然唯一键时用） |

> **我的组合口径**：**"Redis 快筛 + 数据库唯一索引兜底 + 状态机防并发"**——三层各管一件事：**Redis 挡流量、唯一索引保正确、状态机防并发重复执行。**"

**三、并发控制（同一请求的两次调用同时到达）**
- **数据库层面**：唯一索引会有一个成功一个失败（**唯一索引冲突**），失败的捕获异常返回"处理中/已完成"。
- **Redis 层面**：`SETNX` 只能有一个成功。
- ⚠️ **陷阱**：如果两次请求的幂等键不同但业务相同（如用户点了两次"支付"按钮生成了两个 requestID），**那就不是幂等问题，是业务防重问题** —— 需要**业务维度的唯一键**（如"该订单只能有一笔成功的支付"用订单号做唯一索引）。

**四、一致性（★ 支付/计费的关键）**
- **资金变动必须落库**（MySQL 事务），**缓存的余额只能是加速层**。
- **Redis 扣减 + 异步落库**的模式（LoveSpouse 用的）：要配**对账任务**兜底。
- **"先扣 Redis 还是先写 MySQL"**：
  - 高频计费用 **先扣 Redis（原子）+ 异步落库 + 对账**；
  - **低频但金额敏感**的直接 **MySQL 事务 + 行锁**（性能要求不高时优先正确性）。

**五、失败补偿与对账**
- **补偿**：扣减成功但落库失败 → **MQ 重投**（本地消息表 / 事务消息）。
- **对账**：定时任务比对**流水累计**与**余额**，差异告警 + 以账本为准修正。
- **人工兜底**：异常的挂账记录进"待处理表"，运营后台可查可修。

**★ 结合候选人项目（★ 完整版，讲 2 分钟）**：
> "**LoveSpouse 的金币计费就是这道题的原型，我完整做过一遍**：
> **幂等键**我用的是**通话 ID + 计费序号**——因为一次通话要扣很多次（按心跳增量扣），所以单纯的"通话 ID"不够，要加上序号才能区分每一笔。**同一个 (通话ID, 序号) 只会扣一次。**
> **实现是三层**：**Redis 的 Lua 脚本**做原子扣减 + 幂等校验（同一 requestID 直接返回成功），**MySQL 流水表的 `request_id` 唯一索引**兜底（Redis 过期或重启后还能挡住），**通话状态机**防止同一通话被并发结算两次。
> **一致性**上，Redis 是实时余额，MySQL 是账本；扣减成功后**异步把流水落库**，再跑**定时对账**比对"初始余额 - 流水累计"和"Redis 余额"。有差异就告警并以 MySQL 为准修正 Redis。
> **失败补偿**上，通话中途断了要**退还预扣的部分**——这个退还本身也要幂等（用同一个 `requestID` 加后缀标识"退款"操作），**否则重试可能退两次**。
> **最关键的取舍是**：**Redis 挂了我会拒绝新的计费请求，而不是放行** —— 因为**"暂时不能用"是可接受的，"乱扣钱"是不可接受的。**"

### Q11：怎么保证缓存与数据库的一致性？

**【面试官意图】**
考察你对"**一致性只能做到最终一致**"的清醒认识，以及**具体的工程手段**。

**【具体答法】**（详细内容见 5.6，这里给面试口径）

> "**先给结论**：**在允许缓存存在的架构里，强一致做不到**——更新 DB 和删缓存是两个操作，没有分布式事务保证。**能做的是把不一致窗口做到尽可能小，并且保证最终一定一致。**
>
> **我的方案是「先更新数据库，再删缓存」，加三道保险**：
> **第一道是 TTL 兜底**——即使删缓存失败，过期时间到了也会自然纠正。**这是最终一致的最后防线。**
> **第二道是订阅 binlog**——用 Canal 订阅 MySQL 的 binlog，异步触发缓存删除。**它的价值是把"删缓存"从业务代码里解耦出去**：业务只需要保证 DB 写成功，即使那一次删除调用失败了，binlog 这条链路也会重试。**而且它天然覆盖了"所有改库的路径"**（包括运维手工改数据、其他服务的写入）。
> **第三道是并发兜底**——在极端并发下（读请求把旧值写回缓存），我用**给缓存值带版本号**的方式：DB 里的版本号变了，读到旧版本的缓存直接丢弃并重新加载。
>
> **⚠️ 至于「先删缓存再更新 DB」，我不推荐**——因为它有更长的脏数据窗口：删完缓存、DB 还没更新时，并发读会把**旧值重新加载进缓存**，脏数据会一直存在直到过期。**而「先更新 DB 再删缓存」的最坏情况只在"读操作比写操作慢很多"的极端并发下才出现，概率低得多。**
>
> **延迟双删我也不作为主力方案**——因为**延迟多久很难定**：定短了没用，定长了就是把不一致时间人为拉长，而且第二次删除同样可能失败。**如果我确实需要读到自己刚写的数据，我会让这一次读直接走主库**，而不是在缓存上做文章。
>
> **最后一句**：**如果业务要求强一致（比如余额），那就不该用缓存**——或者缓存只能用来做降级读，**权威判断必须每次都查库**。"

**★ 结合候选人项目**：
> "POS 中台的商品档案就是"写少读多"的典型，我用的是 Cache Aside + TTL + **更新后主动删缓存**。因为商品变更频率很低（一天几十次），**不一致窗口对业务几乎无影响**。而 LoveSpouse 的余额我**根本不做缓存**——每次判断余额都直接打 Redis（它本身就是内存数据库，不需要再缓存一层），**避免引入"缓存和 Redis 又不一致"的第二层问题**。"

### Q12：如果要给系统做容量规划，你怎么做？

**【面试官意图】**
**架构师的必备能力**——判断你是不是只会"写代码"，还是能"对系统负责"。

**【答题框架】**
定义目标 → 压测 → 计算 → 冗余 → 验证 → 持续校准。

**【具体答法】**

**一、先要三个数（★ 不问清楚就没法做规划）**
1. **业务目标**：多少用户、多少 QPS（峰值/均值）、数据量增长曲线。
2. **SLA 要求**：可用性（99.9% 还是 99.99%）、延迟目标（P99 < ?）。
3. **成本约束**：预算多少、能不能接受弹性扩容的成本。

**二、压测（★ 不压测的容量规划都是猜）**

| 要点 | 说明 |
| --- | --- |
| **压测环境要接近生产** | ⚠️ 配置差一倍的机器，容量差很多 |
| **压到拐点** | 一直加压到**延迟陡增/错误率上升**，记录拐点 QPS |
| **分层压测** | 分别压**网关、业务服务、DB、Redis**，找**最短的那块板** |
| **稳定性压测** | 不是压 10 分钟，是**压 8-24 小时**（暴露内存泄露、连接泄露、GC 问题）|
| **工具** | `wrk` / `vegeta` / `k6` / `JMeter`；Go 服务配合 pprof 看瓶颈 |

**三、计算（★ 给出公式，显得专业）**

```
所需实例数 = 峰值 QPS / 单实例容量 / 冗余系数(0.6~0.7)
                       ↑压测得出              ↑留 30-40% 余量

存储容量 = 日增数据量 × 保留天数 × (1 + 索引/副本开销)
                          日志类索引开销 1.5~5 倍

带宽 = 峰值 QPS × 平均请求/响应大小 × 2(出入)
```

**四、冗余与高可用（★ 这是"规划"和"算数"的区别）**
- **N+1 冗余**：任何时刻能挂一台（或一个可用区）不影响服务。
- **分级冗余**：核心链路多留余量，非核心可以少留。
- **⚠️ 扩容速度也是容量的一部分**：如果扩容要 10 分钟，那你的冗余必须撑住 10 分钟的峰值增长。
- **依赖也要算**：DB 连接数、Redis 内存、第三方接口配额——**最慢的那个环节决定整体容量**。

**五、验证与持续校准**
- **容量水位监控 + 告警**（如 CPU > 70%、连接池使用率 > 80% 告警）——**别等到 100% 才发现**。
- **定期复压**（业务变更后容量会变）。
- **记录容量基线**：每次扩容/优化后更新基线数据。

**★ 结合候选人项目**：
> "**POS 中台我做过一次容量评估**：门店早高峰集中上传，峰值大约【**必填**：真实数字】条/秒。我先**压测消费端**，找出瓶颈是 MySQL 批量写入——**单批 500 条时单实例大约能消费 X 条/秒**；然后按"峰值 + 40% 余量"算出需要 **N 个消费实例**；再核对**数据库连接池的总容量**能不能支撑（**这一步很关键——实例数 × 每实例连接数不能超过 DB 的 `max_connections`**）；最后留一台冗余。
> **Redis 的容量我是按"商品档案数据量 × 1.5 + 30% 冗余"算的**（要留出 RDB fork 时的 COW 内存翻倍空间）——**这一步以前我漏过，后来发现 Redis 内存接近上限时 fork 会失败，RDB 生成不了。**"

### 10.1 ★★★ LRU 缓存（最高频，几乎必考）

> **思路一句话**：**map 存 key → 链表节点（O(1) 定位）+ 双向链表维护访问顺序（O(1) 移动）；队首是最近使用的，淘汰时删队尾。**

```go
package lru

import "container/list"

type entry struct {
	key, value int
}

type LRUCache struct {
	mu    sync.Mutex
	cap   int
	ll    *list.List               // 队首 = 最近使用，队尾 = 最久未使用
	cache map[int]*list.Element
}

func NewLRUCache(capacity int) *LRUCache {
	return &LRUCache{
		cap:   capacity,
		ll:    list.New(),
		cache: make(map[int]*list.Element, capacity),
	}
}

// Get：命中则把节点移到队首（标记为最近使用）
func (c *LRUCache) Get(key int) int {
	c.mu.Lock()
	defer c.mu.Unlock()

	if e, ok := c.cache[key]; ok {
		c.ll.MoveToFront(e)
		return e.Value.(*entry).value
	}
	return -1
}

// Put：已存在则更新值并移到队首；不存在则插入队首，超容量则删队尾
func (c *LRUCache) Put(key, value int) {
	if c.cap <= 0 {
		return // ★ 边界：容量为 0
	}
	c.mu.Lock()
	defer c.mu.Unlock()

	if e, ok := c.cache[key]; ok {
		c.ll.MoveToFront(e)
		e.Value.(*entry).value = value
		return
	}

	e := c.ll.PushFront(&entry{key: key, value: value})
	c.cache[key] = e

	if c.ll.Len() > c.cap {
		last := c.ll.Back()          // 最久未使用
		if last != nil {
			c.ll.Remove(last)
			delete(c.cache, last.Value.(*entry).key) // ★ 别忘了删 map
		}
	}
}
```

**讲解要点（★ 面试时主动说这几句）**：
1. **为什么两者都要**：map 让查找 O(1) 但**不记录顺序**；双向链表记录顺序但查找 O(n)。**组合起来 get/put 都是 O(1)**。
2. **为什么是双向链表**：删除一个中间节点需要拿到它的前驱（`list.Remove` 内部就是靠前驱指针）——**单链表要 O(n) 找前驱**。
3. **为什么用 `container/list`**：标准库实现的就是双向链表，`PushFront` / `MoveToFront` / `Remove` 全是 O(1)。**如果面试官要求手写，就自己定义 `Node{key, val int; prev, next *Node}` + 两个哨兵节点（head/tail），哨兵能省掉大量 nil 判断。**
4. **并发安全**：加 `sync.Mutex`（**更优的做法是分片锁**，见 10.3）。
5. **复杂度**：时间 O(1)，空间 O(capacity)。

⚠️ **常见追问**：
| 追问 | 答法 |
| --- | --- |
| "手写双向链表版" | 定义 Node + head/tail 哨兵；`remove(n)` / `addToHead(n)` / `moveToHead(n)` / `removeTail()` 四个私有方法，逻辑就清楚了 |
| "怎么实现 LFU？" | **每个频率一个双向链表**（`freq → list`）+ `minFreq` 指针；访问时把节点从当前频率链表移到 `freq+1`；淘汰时从 `minFreq` 链表尾部删 |
| "Redis 的 LRU 怎么实现的？" | ★ **近似 LRU**——Redis 不维护真正的 LRU 链表（太占内存），而是**随机采样 N 个 key（默认 5），淘汰其中最久未使用的**；4.0 起还支持 LFU |
| "为什么不直接用 map + 时间戳排序？" | 排序是 O(n log n)，**不符合 O(1) 的要求** |

### 10.2 ★★ 限流器

#### 令牌桶（懒计算版，★ 推荐）

> **思路**：**不用定时器去补充令牌**（会有大量 goroutine），而是**每次请求时按"距上次请求经过的时间"计算应该补充多少令牌**。

```go
type TokenBucket struct {
	mu       sync.Mutex
	capacity float64   // 桶容量（允许的突发量）
	tokens   float64   // 当前令牌数
	rate     float64   // 每秒补充的令牌数（= 限流速率）
	last     time.Time
}

func NewTokenBucket(capacity, rate float64) *TokenBucket {
	return &TokenBucket{
		capacity: capacity,
		tokens:   capacity,          // 初始满桶
		rate:     rate,
		last:     time.Now(),
	}
}

func (b *TokenBucket) Allow(n float64) bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	now := time.Now()
	// ★ 懒补充：按流逝的时间线性补充，上限是桶容量
	elapsed := now.Sub(b.last).Seconds()
	b.tokens = math.Min(b.capacity, b.tokens+elapsed*b.rate)
	b.last = now

	if b.tokens >= n {
		b.tokens -= n
		return true
	}
	return false
}
```

**讲解要点**：
- ★ **"懒计算"是这道题的灵魂**——不需要后台定时器，**每次请求时按时间差补令牌**，是 Redis 令牌桶和 Go 限流库（`golang.org/x/time/rate`）的标准做法。
- **令牌桶 vs 漏桶**：**令牌桶允许突发**（桶里有存货就能一次性拿走，只要 ≤ capacity）；**漏桶是恒定速率流出**（不允许突发）。**面试时要说清这个区别。**
- ⚠️ **`x/time/rate` 的 `Allow()` 和 `Wait()`**：`Wait` 会阻塞等待，`Allow` 立即返回——**面试时提一句"生产上我会直接用 `golang.org/x/time/rate`，但原理就是上面这个"，既显诚实又显懂。**

#### 滑动窗口（Redis + Lua，★ 分布式限流的标准答案）

```lua
-- KEYS[1] = 限流 key（如 ratelimit:tenant:1）
-- ARGV[1] = 窗口大小（毫秒）  ARGV[2] = 阈值
-- ARGV[3] = 当前时间戳（毫秒） ARGV[4] = 本次请求的唯一 ID
-- 返回 1 = 放行，0 = 限流

-- ① 把窗口之外的记录删掉
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[3] - ARGV[1])
-- ② 统计窗口内的请求数
local count = redis.call('ZCARD', KEYS[1])
if count >= tonumber(ARGV[2]) then
    return 0
end
-- ③ 记录本次请求（score = 时间戳）
redis.call('ZADD', KEYS[1], ARGV[3], ARGV[4])
redis.call('PEXPIRE', KEYS[1], ARGV[1])   -- 自动清理
return 1
```

**讲解要点**：
- ★ **为什么用 ZSet**：**score 存时间戳，成员存请求唯一 ID** —— 既能按时间范围删除（`ZREMRANGEBYSCORE`），又能去重（同一 ID 不会重复计数）。
- **为什么必须用 Lua**：**"删过期 + 计数 + 添加"三步必须原子**，否则并发下会超限。
- ⚠️ **代价**：每个请求存一个成员，**高 QPS 下内存开销大**。优化方案：**固定窗口 + 令牌桶混合**（用 `INCR` + `EXPIRE` 做粗限流，只在边界做精确判断），或者**用令牌桶的"懒计算 + INCRBYFLOAT"** 避免存每个请求。
- **四种限流算法的对比（面试要说）**：**固定窗口**有临界问题（两个窗口各放 N 个，边界处瞬时 2N）；**滑动窗口**平滑但占内存；**漏桶**恒定速率不允突发；**令牌桶**允许突发。

### 10.3 ★ 并发安全的 Map（分片锁）

> **思路**：`sync.Map` 只适合读多写少；**通用场景用"分片锁"** —— 把一个大 map 拆成 N 个加锁的小 map，**减少锁竞争**。

```go
const shardCount = 32

type concurrentMap struct {
	mu sync.RWMutex
	m  map[string]interface{}
}

type ShardedMap struct {
	shards [shardCount]*concurrentMap
}

func NewShardedMap() *ShardedMap {
	sm := &ShardedMap{}
	for i := 0; i < shardCount; i++ {
		sm.shards[i] = &concurrentMap{m: make(map[string]interface{})}
	}
	return sm
}

// ★ FNV 哈希决定落在哪个分片
func (s *ShardedMap) shard(key string) *concurrentMap {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return s.shards[h.Sum32()%shardCount]
}

func (s *ShardedMap) Set(key string, val interface{}) {
	sh := s.shard(key)
	sh.mu.Lock()
	sh.m[key] = val
	sh.mu.Unlock()
}

func (s *ShardedMap) Get(key string) (interface{}, bool) {
	sh := s.shard(key)
	sh.mu.RLock()
	v, ok := sh.m[key]
	sh.mu.RUnlock()
	return v, ok
}

// ★ 注意：Range / Len 这类跨分片操作需要遍历所有分片，无法保证原子快照
func (s *ShardedMap) Len() int {
	n := 0
	for i := 0; i < shardCount; i++ {
		s.shards[i].mu.RLock()
		n += len(s.shards[i].m)
		s.shards[i].mu.RUnlock()
	}
	return n
}
```

**讲解要点**：
- ★ **为什么分片能提升并发**：锁竞争只发生在"落到同一个分片"的 key 之间，**32 个分片理论上是 32 倍的并发度**。
- **分片数怎么选**：**2 的幂**（位运算代替取模，更快）；一般取 **CPU 核数的 4-8 倍**（32 或 64）。
- ⚠️ **哈希不均的风险**："热点 key 落在同一个分片"就退化了——**所以哈希函数要均匀（FNV / xxhash）**。
- **`sync.Map` 的适用场景**：**读多写少、key 集合稳定**（如缓存、注册表）；**写多或者要遍历时，分片锁更好**。

### 10.4 ★ 生产者-消费者

```go
// 版本一：channel + WaitGroup（★ 最简洁，推荐）
func producerConsumer() {
	jobs := make(chan int, 100) // ★ 带缓冲：削峰
	var wg sync.WaitGroup

	// 3 个消费者
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for job := range jobs { // ★ channel 关闭后自动退出循环
				fmt.Printf("worker %d 处理任务 %d\n", id, job)
			}
		}(i)
	}

	// 生产者
	for i := 0; i < 1000; i++ {
		jobs <- i
	}
	close(jobs) // ★ 由发送方关闭，消费者靠它退出
	wg.Wait()
}
```

```go
// 版本二：条件变量（sync.Cond）—— 面试官要求"不用 channel"时用
type Queue struct {
	mu    sync.Mutex
	cond  *sync.Cond
	items []int
	cap   int
}

func NewQueue(capacity int) *Queue {
	q := &Queue{cap: capacity}
	q.cond = sync.NewCond(&q.mu)
	return q
}

func (q *Queue) Push(v int) {
	q.mu.Lock()
	defer q.mu.Unlock()
	for len(q.items) >= q.cap { // ★ 用 for 而不是 if（防虚假唤醒）
		q.cond.Wait()
	}
	q.items = append(q.items, v)
	q.cond.Broadcast()
}

func (q *Queue) Pop() int {
	q.mu.Lock()
	defer q.mu.Unlock()
	for len(q.items) == 0 {
		q.cond.Wait()
	}
	v := q.items[0]
	q.items = q.items[1:]
	q.cond.Broadcast()
	return v
}
```

**讲解要点**：
1. ★ **channel 版本的关键三句**：**"带缓冲削峰"、"channel 关闭后 `range` 会自动退出"、"由发送方 close"**。
2. ⚠️ **`sync.Cond` 必须用 `for` 而不是 `if` 包住 `Wait()`** —— 因为**存在虚假唤醒（spurious wakeup）**，被唤醒时条件可能仍不满足。**这是经典陷阱题。**
3. **优雅退出**：实际项目里要用 `select { case <-ctx.Done(): return }` 让消费者能响应取消。

### 10.6 排序

```go
// 快速排序：分治 + 原地
func QuickSort(a []int) {
	if len(a) <= 1 {   // ★ 递归出口
		return
	}
	pivot := a[len(a)/2]
	left, right := 0, len(a)-1
	for left <= right {
		for a[left] < pivot { left++ }
		for a[right] > pivot { right-- }
		if left <= right {
			a[left], a[right] = a[right], a[left]
			left++
			right--
		}
	}
	QuickSort(a[:right+1])
	QuickSort(a[left:])
}
```

```go
// 归并排序：分治 + 额外空间（★ 稳定排序）
func MergeSort(a []int) []int {
	if len(a) <= 1 {
		return a
	}
	mid := len(a) / 2
	left := MergeSort(a[:mid])
	right := MergeSort(a[mid:])

	res := make([]int, 0, len(a))
	i, j := 0, 0
	for i < len(left) && j < len(right) {
		if left[i] <= right[j] {   // ★ <= 保证稳定性
			res = append(res, left[i]); i++
		} else {
			res = append(res, right[j]); j++
		}
	}
	res = append(res, left[i:]...)
	res = append(res, right[j:]...)
	return res
}
```

**讲解要点**：
| | 快排 | 归并 |
| --- | --- | --- |
| 平均 / 最坏 | O(n log n) / **⚠️ O(n²)** | **O(n log n) / O(n log n)** |
| 空间 | O(log n)（递归栈） | **O(n)**（额外数组） |
| 稳定性 | ❌ 不稳定 | ✅ **稳定** |
| 适用 | 内存排序、缓存友好 | **外排（大文件）、链表排序、要稳定** |

- ★ **快排为什么最坏 O(n²)**：**每次选的 pivot 都是最大或最小值**（已排序数组 + 取首元素做 pivot）。**优化：随机选 pivot / 三数取中 / 小区间用插入排序。**
- **Go 的 `sort.Slice` 用的是什么**：**pdqsort（pattern-defeating quicksort）**，是快排的工程优化版（结合了插入排序和堆排序的兜底）。**这个细节说出来很加分。**

### 10.7 链表

```go
type ListNode struct {
	Val  int
	Next *ListNode
}

// 反转链表（迭代版，★ 三指针）
func ReverseList(head *ListNode) *ListNode {
	var prev *ListNode
	cur := head
	for cur != nil {
		next := cur.Next // ★ 先存下一个，否则断链后找不回来
		cur.Next = prev  // 反向指
		prev = cur       // 前移
		cur = next
	}
	return prev // ★ 返回 prev（cur 此时是 nil）
}
```

```go
// 判断链表有环（Floyd 快慢指针）
func HasCycle(head *ListNode) bool {
	slow, fast := head, head
	for fast != nil && fast.Next != nil {   // ★ 两个条件都要判
		slow = slow.Next
		fast = fast.Next.Next
		if slow == fast {
			return true
		}
	}
	return false
}

// 找环的入口（★ 加分：数学推导）
// 设头到入口距离 = a，入口到相遇点 = b，相遇点到入口 = c
// 快指针走了 a+b+c+b = a+2b+c，慢指针走了 a+b，快是慢的两倍 → a = c
// 所以：相遇后，一个指针从头开始、另一个从相遇点开始，同速前进，相遇处就是入口
func DetectCycle(head *ListNode) *ListNode {
	slow, fast := head, head
	for fast != nil && fast.Next != nil {
		slow = slow.Next
		fast = fast.Next.Next
		if slow == fast {
			p := head
			for p != slow {
				p = p.Next
				slow = slow.Next
			}
			return p   // ★ 环入口
		}
	}
	return nil
}
```

**讲解要点**：
- 反转链表：**迭代三指针**（O(1) 空间）；递归版（O(n) 栈空间）也可以写，但**面试时优先迭代**——不会有栈溢出风险。
- 环检测：★ **能推导出"a = c"这一步是加分项**，说明你不是背的。

### 10.8 字符串处理

```go
// 字符串反转（★ 注意 Unicode！）
func ReverseString(s string) string {
	r := []rune(s)          // ✅ 用 []rune，不是 []byte
	for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {
		r[i], r[j] = r[j], r[i]
	}
	return string(r)
}
```

```go
// 最长回文子串（中心扩展法，O(n²) 时间 / O(1) 空间）
func LongestPalindrome(s string) string {
	if len(s) < 2 {
		return s
	}
	r := []rune(s)
	start, maxLen := 0, 1

	expand := func(l, rr int) int {
		for l >= 0 && rr < len(r) && r[l] == r[rr] {
			l--
			rr++
		}
		return rr - l - 1 // 回文长度
	}

	for i := 0; i < len(r); i++ {
		len1 := expand(i, i)     // ★ 奇数长度（以 i 为中心）
		len2 := expand(i, i+1)   // ★ 偶数长度（以 i 和 i+1 之间为中心）
		if l := max(len1, len2); l > maxLen {
			maxLen = l
			start = i - (l-1)/2  // 反推起点
		}
	}
	return string(r[start : start+maxLen])
}
```

```go
// 最长无重复字符子串（滑动窗口，★ 高频）
func LengthOfLongestSubstring(s string) int {
	last := make(map[rune]int) // 字符 → 最后出现的位置
	maxLen, left := 0, 0
	for right, c := range s {
		if idx, ok := last[c]; ok && idx >= left {
			left = idx + 1   // ★ 窗口左边界跳到重复字符的下一位
		}
		last[c] = right
		if right-left+1 > maxLen {
			maxLen = right - left + 1
		}
	}
	return maxLen
}
```

**讲解要点**：
- ★ **`[]rune` vs `[]byte`**：Go 的 `string` 是 UTF-8 字节序列，**中文占 3 个字节**——用 `[]byte` 反转会把中文字符切碎成乱码。**这是 Go 特有的坑，答出来很加分。**
- **中心扩展 vs 动态规划**：中心扩展 O(1) 空间（DP 是 O(n²) 空间），**面试优先中心扩展**；还有 O(n) 的 Manacher 算法（**说一句"还有一个 Manacher 算法能到 O(n)，但实现复杂，实际很少用"就够**）。

### 10.9 ★ 两个 Goroutine 交替打印

```go
// 版本一：两个 channel 互相轮流（★ 最经典）
func PrintAlternate() {
	ch1 := make(chan struct{})  // 通知 goroutine 2
	ch2 := make(chan struct{})  // 通知 goroutine 1
	done := make(chan struct{})

	go func() {                  // 打印数字
		for i := 1; i <= 10; i++ {
			<-ch1
			fmt.Println("A:", i)
			ch2 <- struct{}{}
		}
	}()

	go func() {                  // 打印字母
		for i := 'a'; i <= 'j'; i++ {
			<-ch2
			fmt.Println("B:", string(i))
			ch1 <- struct{}{}
		}
		close(done)
	}()

	ch1 <- struct{}{}            // ★ 由主 goroutine 踢第一脚
	<-done
}
```

```go
// 版本二：单个 channel 交替（更简洁，★ 推荐）
func PrintAlternate2(n int) {
	ch := make(chan int)
	done := make(chan struct{})

	go func() { // 偶数
		for i := 0; i < n; i += 2 {
			<-ch
			fmt.Println("偶数:", i)
			ch <- 1
		}
		close(done)
	}()

	go func() { // 奇数
		for i := 1; i < n; i += 2 {
			<-ch
			fmt.Println("奇数:", i)
			ch <- 1
		}
	}()

	ch <- 1     // ★ 踢第一脚
	<-done
}
```

**讲解要点**：
- ★ **交替的本质是"用 channel 做接力棒"** —— 谁拿到令牌谁执行，执行完把令牌传出去。
- ⚠️ **最后一步要处理"多传了一次令牌"**：奇数 goroutine 最后一次 `ch <- 1` 之后没有接收者时，**要么用带缓冲的 channel（`make(chan int, 1)`），要么让最后一个发送者不管**——**这是最容易出错的地方，写完要主动说。**
- **更直观的写法**：**用带缓冲 channel 做令牌（`sem := make(chan struct{}, 1)`）**，两个 goroutine 都去抢令牌。

### 10.10 用 channel 实现超时控制

```go
// 版本一：time.After（★ 最简洁）
func WithTimeout(fn func() (string, error), timeout time.Duration) (string, error) {
	ch := make(chan string, 1)   // ★ 缓冲为 1：避免超时后 goroutine 永久阻塞（goroutine 泄露）

	go func() {
		res, err := fn()
		if err != nil {
			ch <- ""             // 简化处理
			return
		}
		ch <- res
	}()

	select {
	case res := <-ch:
		return res, nil
	case <-time.After(timeout):
		return "", fmt.Errorf("timeout after %v", timeout)
	}
}
```

```go
// 版本二：context（★ 生产推荐：能取消、能级联、能传值）
func WithContextTimeout(ctx context.Context, fn func(context.Context) (string, error), d time.Duration) (string, error) {
	ctx, cancel := context.WithTimeout(ctx, d)
	defer cancel()               // ★ 必须调用，否则 context 泄露

	type result struct {
		val string
		err error
	}
	ch := make(chan result, 1)

	go func() {
		v, err := fn(ctx)        // ★ 把 ctx 传下去，让内部能感知取消
		ch <- result{v, err}
	}()

	select {
	case r := <-ch:
		return r.val, r.err
	case <-ctx.Done():
		return "", ctx.Err()     // ★ 返回 DeadlineExceeded 或 Canceled
	}
}
```

**讲解要点**：
- ★ **channel 必须带缓冲（`make(chan string, 1)`）** —— 否则超时返回后，那个 goroutine 会**永远阻塞在 `ch <- res` 上，造成 goroutine 泄露**。**这是这道题的核心考点，一定要主动说。**
- **`context` 比 `time.After` 好在哪**：① **可以级联取消**（上游取消能传到下游）② **可以主动 cancel**（不用等超时）③ **能携带值**。**生产代码一律用 context。**
- ⚠️ **`defer cancel()` 必须调用** —— 否则 context 会一直挂在父节点上，**造成内存泄露**（`golangci-lint` 的 `lostcancel` 检查就是这个）。
- **`time.After` 的一个坑**：**它创建的 timer 在触发前不会被 GC**（1.23 前）——**循环里用 `time.After` 会累积大量定时器**。改用 `time.NewTimer` + `Stop()`。

### MongoDB 三句话

> ① **结构固定 + 要事务 + 要 JOIN → MySQL；结构多变 + 嵌套聚合 + 要水平扩 → MongoDB。**
> ② **副本集 = 1 主 N 从 + 多数派选举**，`writeConcern: majority` + `readConcern: majority` 给金额类数据；**默认 w:1 有丢数据风险**。
> ③ ★ **分片键三原则：高基数、低频率、非单调**；**`_id` / 时间戳是单调键，会热点，要用哈希分片。**
> 场景判断：**策略配置**（MySQL 优先，Mongo 有条件）、**审计日志**（ES 优先，Mongo 做轻量替代）、**流量统计**（Redis + 列存，**Mongo 不合适**）。

### ES 三句话

> ① **倒排索引 = 词 → 文档列表**；`text` 分词（搜索用）、`keyword` 不分词（聚合排序用）。
> ② **近实时 = refresh 默认 1 秒**；**segment 不可变 → 更新是"标记删除 + 新文档"。**
> ③ **日志适合 ES 的四条理由：海量写入、全文检索、聚合统计、按时间范围 + ILM 自动过期**；★ **但 ES 不能当数据库。**

### MySQL 三个必答

> ① **B+ 树**：矮胖 + 有序 + 叶子成链；3 层 2000 万行。**别用 UUID 做主键**（页分裂）。
> ② **MVCC**：隐藏列 + undo 版本链 + ReadView；★ **RC 和 RR 只差"ReadView 生成时机"。**
> ③ **两阶段提交**：redo prepare → binlog → redo commit；★ **"redo 是 prepare 且 binlog 完整 → 提交，否则回滚"。**

### Redis 三个必答

> ① **快的原因**：内存 + epoll + 单线程无锁 + 高效结构。★ **6.0 的多线程只是网络 IO，命令执行仍单线程。**
> ② **缓存一致性**：**先更新 DB 再删缓存 + TTL 兜底 + binlog 异步删**；★ **没有强一致，只有最终一致。**
> ③ **分布式锁**：`SET NX PX` + **唯一 value** + Lua 释放 + **看门狗续期**；★ **Redis 锁是效率型，ETCD 锁是正确性型。**

### ★★ 两张王牌（一定要讲出来）

> **① 金币计费**：**先查后扣会超扣** → **Lua 原子扣减（校验 + 幂等 + 扣减一体）** → **预扣 + 增量结算 + 多退少补** → **Redis 实时账 + MySQL 账本 + 定时对账** → **Redis 挂了拒绝新请求，不放行**。
> **② 消息幂等**：**MQ 只能"至少一次"，靠消费端幂等补成"恰好一次的效果"** → **Redis SETNX 快筛 + MySQL 唯一索引兜底 + 状态机防并发** → 幂等键选不对（如单用 `MsgSeq`）幂等就是假的。
