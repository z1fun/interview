## 二、★ GMP 调度模型（必考）

### 2.1 一句话答案

> Go 的调度器是 **GMP 三层模型**：**G** 是 goroutine（要执行的任务），**M** 是内核线程（真正干活的），**P** 是逻辑处理器（持有本地运行队列和内存缓存）。**M 必须绑定一个 P 才能执行 G**，P 的数量由 `GOMAXPROCS` 决定（默认等于 CPU 核数）。调度器的核心目标是用**少量内核线程**跑**海量 goroutine**，并且**大部分调度决策在用户态完成，不进内核**。

### 2.2 G / M / P 三者职责

| 角色 | 是什么 | 关键字段 | 数量 |
| --- | --- | --- | --- |
| **G** | goroutine，用户态协程 | `stack`（栈上下界）、`sched`（保存的 SP/PC 等寄存器）、`atomicstatus`（状态）、`goid`、`m`（正在哪个 M 上跑） | **十万~百万级** |
| **M** | machine，OS 线程 | `g0`（调度用的系统栈）、`curg`（当前跑的 G）、`p`（绑定的 P）、`spinning`（是否在自旋找活干） | **几十~几百** |
| **P** | processor，逻辑处理器 | `runq[256]`（本地队列）、`runnext`（下一个优先跑的 G）、`mcache`（无锁内存分配缓存）、`status` | **默认 = CPU 核数** |

**三者关系一句话**：**P 是"执行 G 所需的资源许可证"**。M 想跑 G，必须先拿到一个 P；G 想被跑，必须挂在某个 P 的队列里。

**G 的状态（能说出 4 个就够）**：`_Gidle`（刚分配）→ `_Grunnable`（在队列里等）→ `_Grunning`（正在 M 上跑）→ `_Gwaiting`（阻塞中，如等 channel/网络）→ `_Gdead`（可复用）。**注意 `_Gwaiting` 的 G 不占 M，也不占 P**——这是 Go 高并发的根本原因。

### 2.3 ★ 为什么需要 P（高频追问，必答三点）

很多人只背得出"P 是处理器"，被追一句"那 M 直接跑 G 不就行了，要 P 干嘛"就卡住。**这是本节最高频的追问。**

| 原因 | 一句话解释 | 没有 P 会怎样 |
| --- | --- | --- |
| **① 解耦 G 与 M** | G 不再直接绑线程，几十万个 G 分时复用少量 M | 一个 G 一个线程，直接退回 thread-per-request，1 万连接就崩 |
| **② 减少锁竞争** | 本地队列 `runq` 和内存缓存 `mcache` 都是 **P 私有**的，G 的创建/入队/小对象分配**基本无锁** | 所有 G 都去抢全局队列的一把大锁，核越多越慢 |
| **③ 并行度独立可控** | `GOMAXPROCS` 决定同时有几个 G 在跑，与机器线程数解耦 | 无法在不改代码的情况下限制 CPU 占用 |

**记忆口诀**：**P 是"私有的跑道 + 私有的内存池"，M 是"运动员"，G 是"要跑的任务"。**

### 2.4 完整调度流程

**创建**：`go f()` → `newproc` → 分配/复用 G（**从 P 的自由 G 链表 `gFree` 拿，拿不到才新建**）→ 设置栈和入口 → `runqput` 入队。

**入队优先级（重要）**：

```
runnext（下一个优先执行）  →  LRQ 本地队列（最多 256）  →  GRQ 全局队列（有锁）
```

- 新创建的 G **优先放到当前 P 的 `runnext`**；如果 `runnext` 已被占，**把原来那个挤到 LRQ 队尾**。
- `runnext` 的意义：**提升时间局部性**（刚创建的子 goroutine 大概率和父 goroutine 操作同一批数据，cache 热、不需要切换）。

**执行（`schedule()` 调度循环）**，按顺序找活干：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `runnext` | 最快，无线程切换 |
| 2 | **LRQ 本地队列** | 无锁，最多 256 个 |
| 3 | **GRQ 全局队列** | **每 61 次调度强制查一次**（`schedtick%61==0`），防止全局队列被饿死 |
| 4 | **netpoll（非阻塞）** | 看有没有网络 IO 就绪的 G，**这一步让网络密集型服务几乎零延迟唤醒** |
| 5 | **work stealing（偷）** | 从其他 P 偷 |
| 6 | 都没活 → M 休眠 | 阻塞在 `epoll_wait`/futex 上等唤醒 |

**⚠️ 第 4 步是重点**：`findRunnable` 里**先做一次非阻塞的 netpoll**，这就是"网络事件能被快速响应"的机制。很多八股文漏掉这一点。

### 2.5 ★ work stealing（偷取）与 handoff（移交）

**work stealing**：

- 当前 P 的队列空了 → 随机选一个**起始 P**，**顺序遍历所有 P**，从受害者那里**偷走一半**的 G（`runqsteal` → `runqgrab` 取一半）。
- **最多尝试 4 轮**，**最后一轮才允许连受害者的 `runnext` 和定时器一起偷**（因为偷 runnext 会破坏局部性，代价高，放最后）。
- 意义：**动态负载均衡**，避免"一个 P 忙死，另一个 P 闲着"。这是 Go 不需要手写线程池就能打满多核的原因。

**handoff（移交）**：

- 当 G 发起**阻塞式系统调用**（文件 IO、`cgo`、部分同步 syscall）时，**M 会被内核挂起**，此时 runtime 会做 `entersyscall` → **把 M 上的 P 摘下来（releasep）**，交给其他空闲 M 继续跑别的 G。
- syscall 返回后，M 尝试**抢回一个 P**；抢不到就把自己跑的 G 扔进 **GRQ**，然后 M 去休眠。
- **⚠️ 为什么网络 IO 不需要 handoff**：Go 的网络 fd 是**非阻塞**的，读不到数据会立刻返回 `EAGAIN`，然后 G 主动 `gopark` 挂起 ——**G 让出 M，但不让出 P**。只有真正的"阻塞式 syscall"才需要 handoff。**这个区别是理解 Go netpoller 的关键（见 9.3）**。

**sysmon（监控线程）**：

- 一个**不需要 P** 的特殊 M，由 runtime 启动，**常驻后台**，是调度器"最后的保险"。
- 主要工作（记 4 条）：
  1. **retake**：发现某个 P 在 syscall 里卡住**超过约 20μs**，强制把 P 抢回来；
  2. **抢占**：发现某个 G **连续运行超过 10ms**（`forcePreemptNS`），发起抢占（见 2.6）；
  3. **netpoll**：如果所有 P 都忙，主动调一次 netpoll 把就绪的 G 捞出来，**保证网络事件不被饿死**；
  4. **强制 GC**：**每 2 分钟**（`forcegcperiod`）触发一次 GC，兜底防止"不分配内存的程序永远不 GC"；另外还会做**内存回收（scavenge，把内存还给 OS）**。
- sysmon 的睡眠是**自适应**的：从 **20μs** 开始，每次没事干就翻倍，上限 **10ms**。**这个数字说明 Go 在"响应及时"和"不空转烧 CPU"之间做了权衡。**

### 2.6 ★ 协作式抢占 vs 抢占式调度（Go 1.14 的分水岭）

**旧方案（Go 1.14 之前）：协作式抢占**

- 抢占检查点放在**函数序言**（每次调用函数时检查 `stackguard0` 是否有抢占标记）。
- **致命缺陷**：`for {}` 这种**没有函数调用的死循环永远不会命中检查点**，无法被抢占。
- 后果：这个 G 会**一直霸占 M**，同 P 上其他 G 全部饿死；更严重的是 **GC 的 STW 会被它卡住**——GC 要停下来等所有 G 到达安全点，等不到就是整个程序卡死。

**新方案（Go 1.14+）：基于信号的异步抢占**

| 步骤 | 动作 |
| --- | --- |
| 1 | `sysmon` 发现某 G 运行超 **10ms** |
| 2 | 调用 `preemptM`，向目标 M 发送 **SIGURG 信号**（选 SIGURG 是因为它默认不用于其他用途，不会干扰用户程序） |
| 3 | M 的信号处理函数介入，**检查当前 G 是否处于"异步安全点"**（能不能安全地保存现场） |
| 4 | **是安全点** → 插入 `asyncPreempt`，把寄存器保存到 G 的 `sched`，G 变回 runnable，重新走调度 |
| 5 | **不是安全点**（在 runtime 临界区、汇编函数里） → 退化成协作式：给 `stackguard0` 打上抢占标记，**等下一个函数序言**再抢占 |

**为什么这个改进很关键（这段说出来很加分）**：

> Go 1.14 之前，一个死循环 goroutine 能把整个进程拖垮；1.14 之后，**任何 goroutine 都能在 10ms 量级被强制让出 CPU**。这是 Go 敢在**延迟敏感场景**（比如网关、广告竞价）用的前提——**没有任何一个用户代码能独占 CPU 影响全局**。

**常见追问**：*那是不是所有 goroutine 都能被准时抢占？* → 不是。**在非安全点仍然要退化成协作式**，所以理论上存在"最多等到下一个函数调用/栈检查"的窗口，但实践上 10ms 量级的响应已经足够。另外 **`runtime.LockOSThread` 之后、以及 `cgo` 调用中是抢不动的**，这类代码要自己控制执行时间。

### 2.7 goroutine vs 线程（经典对比表）

| 维度 | goroutine | OS 线程 |
| --- | --- | --- |
| **初始栈** | **2KB**（`stackMin = 2048`） | 1~8MB（创建时固定） |
| **栈增长** | **按需翻倍扩容**，64 位上限默认 **1GB** | 固定，创建时确定，超了直接栈溢出 |
| **创建开销** | **百纳秒级**（只分配 G 结构 + 2KB 栈，且常从 `gFree` 复用） | 微秒~毫秒级（要建内核对象 + 映射大栈） |
| **切换开销** | **用户态，约百纳秒**（只把寄存器存回 G 的 `sched`） | **陷入内核，约 1~2μs**（改页表、刷 TLB） |
| **调度者** | Go runtime（GMP，用户态） | OS 调度器（内核态，抢占式，时间片） |
| **通信方式** | **channel**（CSP：通过通信共享内存） | 共享内存 + 锁 |
| **数量级** | **十万~百万** | 几千个就开始吃内存 |

**栈扩容细节（会被追问）**：

1. 函数序言检查 `stackguard0`：栈快不够用了；
2. 触发 `morestack` → `newstack`：**申请 2 倍大小的新栈**；
3. 把旧栈内容**整个拷贝**到新栈，**修正所有指向栈上的指针**；
4. 旧栈**留给 GC 回收**（不是立刻 free）。

**所以"返回局部变量的指针"在 Go 里是安全的** —— 要么变量被逃逸分析移到堆上，要么栈扩容时指针被修正。**这解释了为什么 Go 没有"野指针"这种问题。**

**缩容**：GC 期间会做 `shrinkstack`：如果**栈使用量不到 1/4**，就把栈缩到一半（最小仍是 2KB）。**所以 goroutine 闲置久了会自己变小**，这对长连接场景是有利的。

### 2.8 ★ GOMAXPROCS 怎么设（含容器陷阱）

**一句话答案**：**默认值就是对的选择**（`runtime.NumCPU()`）。它的含义是"**同时能有多少个 goroutine 在真正并行执行**"，不是"能创建多少 goroutine"。

| 场景 | 建议 |
| --- | --- |
| CPU 密集型 | **= 核数**，不要超配（超了只会增加切换开销） |
| IO 密集型（网关、WebSocket） | **还是 = 核数**。不要因为"IO 多"就调大 —— **阻塞在网络 IO 上的 G 不占 M，P 会自动让出去干活**，调大纯属浪费 |
| cgo / 阻塞式 syscall 多 | 可以考虑调大（这类调用真占 M），但更好的做法是**改用 netpoller** |

**⚠️ 容器里的陷阱（必答，非常加分）**：

> 容器的 CPU 限额是通过 **cgroup 的 cfs_quota / cfs_period** 实现的，**不是通过限制 CPU 核数**。而 Go 早期版本的 `NumCPU()` 读的是 `/proc/cpuinfo`（看到的是**宿主机的核数**）。结果：**K8s 里给容器限 2 核，但 GOMAXPROCS 拿到 64** → 开 64 个 P 抢 2 核的配额 → **频繁被 cgroup 限流（throttling）、上下文切换暴涨、延迟抖动**。

| 版本 | 解决方案 |
| --- | --- |
| **Go ≤ 1.24** | 引入 `uber-go/automaxprocs`，启动时读 cgroup 配额自动设置 GOMAXPROCS（**几乎零成本，建议无脑加**） |
| **Go 1.25+** | **runtime 原生感知容器 CPU 限额**，自动设置 GOMAXPROCS（可用 `GODEBUG=containermaxprocs=0` 关闭） |

**回答模板**：

> 我一般保持默认，因为是 IO 密集的网络服务，阻塞在网络上的 goroutine 不占线程，调大没有收益。**但容器里我会特别处理 GOMAXPROCS** —— 因为 `NumCPU` 在早期版本读到的是宿主机核数，会出现"2 核限额跑 64 个 P"的情况，导致 cgroup 限流和延迟抖动。所以我用 `automaxprocs` 让 Go 按 cgroup 配额来设；Go 1.25 之后 runtime 原生支持了，就不用额外引库了。**验证方式也很直接：看 `/sys/fs/cgroup/cpu.stat` 里的 `nr_throttled` 和 `throttled_usec`。**

**⚠️ 注意**：如果你不确定公司的 Go 版本，就只说 automaxprocs 那一半，把 1.25 那句说成"听说新版本原生支持了"，**不要赌版本号**。

### 2.9 ★ 结合 LoveSpouse：几万个 WebSocket 连接对应几万个 goroutine 可行吗？

**一句话答案**：**完全可行，这正是 Go 的强项。** 几万连接在 Go 里是"很舒服"的量级，不是极限。

**为什么可行（四层理由，按重要性排序）**：

| 理由 | 说明 |
| --- | --- |
| **① 等待 IO 的 G 不占线程** | WebSocket 连接 99% 的时间在等数据。G 挂起在 netpoller 上（`_Gwaiting`），**既不占 M 也不占 P**。几万个连接实际只有几十个 M 在干活 |
| **② 栈是动态的** | idle 连接的 goroutine 栈几乎不增长，**稳定在 2KB 左右**；GC 还会把用过的栈缩容回去 |
| **③ 创建/切换成本低** | 百纳秒级，相对于一次网络往返（毫秒级）**完全可忽略** |
| **④ GMP 天然负载均衡** | work stealing 把活跃连接的打散到各个 P，不会出现"某个核忙死" |

**要做连接数估算（面试官爱问这个）**：

| 项目 | 单连接占用 | 5 万连接 |
| --- | --- | --- |
| goroutine 栈（读+写 2 个 G） | 2KB × 2 = 4KB | 200 MB |
| G 结构体 + sudog 等 | ~1KB | 50 MB |
| 读缓冲（建议 4KB） | 4KB | 200 MB |
| 写缓冲 / 发送队列 | 4~16KB | 200~800 MB |
| 业务状态（会话、用户、订阅） | 1~2KB | 50~100 MB |
| **合计** | **约 15~30KB** | **约 0.7~1.4 GB** |

**结论话术**：

> 我们的模型是**每个连接一个读 goroutine + 一个写 goroutine**，加上心跳用 `time.AfterFunc`（不额外占 goroutine，底层是时间堆 + 一个 timer goroutine）。按这个模型，**5 万连接大约 10 万个 goroutine、1GB 出头内存**，在单机 8G/16G 上是安全的。**真正的瓶颈不是 goroutine 数量，而是：① 文件描述符上限（`ulimit -n`，5 万连接至少要 10 万）② 广播时的扇出写放大 ③ 慢客户端导致的写队列积压。** 这三点我们在设计时是重点处理的。

**⚠️ 边界提醒**：**请不要编造具体的连接数**。真实量级填在【】，没有数据就用上面这段"按模型估算"的说法——**能自己算出容量，比报一个假数字强得多**。

**常见追问**：

- *那 goroutine 有没有上限？* → **没有硬上限，瓶颈是内存和 GC**。每个 G 至少 2KB 栈 + 结构体，100 万 G 就是 GB 级；另外 **GC 扫描栈的时间随 goroutine 数增长**（虽然 StackScan 是并发的），G 越多越吃 CPU。
- *一个连接两个 goroutine 会不会太多？* → 这是**最清晰、最不容易出 bug** 的模型（读和写解耦，避免多 goroutine 并发写同一个 conn）。如果真的到百万连接级别，再考虑 **epoll 多路复用 + 单 goroutine 管多连接**（类似 `gnet` 的模式），**但那是拿可维护性换性能，几万连接完全不需要**。
- *为什么不用线程池？* → **Go 里不需要**。GMP 本身就是个自适应线程池，且 work stealing 比手工线程池的静态分配更灵活。**手工线程池解决的是"线程创建贵"的问题，而 goroutine 创建不贵。**

## 三、★ channel 底层

### 3.1 一句话答案

> channel 的底层是 **`hchan` 结构体**：**一把互斥锁 + 一个环形缓冲区 `buf` + 两个等待队列 `recvq`/`sendq`**。**无缓冲 channel 是"同步交接"**（发送方直接把数据拷给接收方，握手后各自继续）；**有缓冲 channel 是"异步入队"**（缓冲区满/空才阻塞）。

### 3.2 hchan 结构（能说出这 6 个字段就够）

| 字段 | 作用 |
| --- | --- |
| `qcount` | 当前缓冲区里的元素个数（**`len(ch)` 返回的就是它**） |
| `dataqsiz` | 缓冲区容量（**`cap(ch)` 返回的就是它**，无缓冲为 0） |
| `buf` | **环形缓冲数组**的指针（无缓冲时为 nil，不分配内存） |
| `sendx` / `recvx` | 环形缓冲的**写指针 / 读指针**（取模环绕） |
| `recvq` / `sendq` | **等待队列**，元素是 `sudog`（对 G 的包装，记录"哪个 G 在等、等哪个 channel、数据放哪"） |
| `closed` + `lock` | 关闭标志 + **一把保护整个 hchan 的互斥锁** |

**⚠️ 关键认知**：**channel 内部就是一把锁 + 队列**。所以"channel 比 mutex 快"是错的（见 3.6）。

### 3.3 发送流程（`chansend`）

```
加锁
 ├─ channel 已关闭？ → panic: send on closed channel
 ├─ recvq 里有等待的接收者？
 │    └─ 有 → ★ 直接把数据从【发送方的栈】拷贝到【接收方的栈】，
 │             然后把接收方 G 置为可运行（goready），解锁返回。
 │             ⚠️ 数据完全不经过缓冲区
 ├─ 缓冲区没满（qcount < dataqsiz）？
 │    └─ 是 → 拷到 buf[sendx]，sendx++，qcount++
 └─ 都不行 → 把当前 G 包成 sudog 挂到 sendq 队尾，gopark 阻塞
              （等接收者来唤醒 / 被 close 唤醒后 panic）
```

**接收流程（`chanrecv`）完全对称**：先看 `sendq`（有就直接从发送方栈拷过来，**并顺手把发送方 buffer 里的数据补进缓冲区**）→ 再看缓冲区有没有数据 → 都没有就挂到 `recvq`。

### 3.4 ★ `succ` 直接内存拷贝的优化（写在这里显得你读过 runtime）

**面试官追问：为什么说 channel 传递大数据效率还可以？**

> 因为 runtime 里有个叫 `send()` / `recv()` 的优化路径：**当发送方和接收方直接碰上了（一方在等，另一方来了），数据是直接从发送方的栈帧拷贝到接收方的栈帧的**（`typedmemmove(dst, src)`），**完全绕过环形缓冲区**。也就是说 unbuffered channel 的一次交接，本质上是**一次内存拷贝 + 两次 goroutine 状态切换**。缓冲区只在"两边没碰上"的时候才用。

**⚠️ 但要注意**：拷贝的是**值**。所以：
- 传**大结构体**会触发大 memcpy → **传指针**（但要小心共享可变数据，容易出数据竞争）；
- 传 `[]byte` 传的是**切片头**（3 个字），底层数组是共享的 → **如果发送方之后还会改这个 buffer，就会出问题**（这是 Go 里最经典的隐藏 bug 之一）。**正确做法是传递 buffer 的所有权，或者拷贝一份。**

### 3.5 无缓冲 vs 有缓冲

| 维度 | 无缓冲（`make(chan T)`） | 有缓冲（`make(chan T, n)`） |
| --- | --- | --- |
| **语义** | **同步交接**：发送方必须等到有人接 | **异步解耦**：只要缓冲没满就立刻返回 |
| **`len()`/`cap()`** | 都是 0 | `len` 是当前堆积数，`cap` 是 n |
| **阻塞条件** | 永远阻塞到对方就绪 | 满（发送）/ 空（接收）才阻塞 |
| **典型用途** | **信号通知、交接即同步**（`done chan struct{}`、`chan error`） | **生产消费解耦**、削峰、控制并发数 |
| **能当信号量用** | 不能（没有容量概念） | **能**：容量 n 的有缓冲 channel = 最多 n 个并发 |

**⚠️ 常见坑**：

1. **`make(chan T, 0)` 和 `make(chan T)` 完全一样**，不是"无限缓冲"；**想当信号量必须给容量**。
2. **用超大缓冲来掩盖消费慢**：`make(chan T, 100000)` 看起来不阻塞了，实际上只是**把背压问题转化成了内存占用和延迟**——消息越堆越多，用户看到的响应越来越旧。**正确做法：有界队列 + 满了就降级/拒绝，而不是无限堆**。
3. **有缓冲 channel 只有在需要"解耦速率"时才用**；如果是为了"避免阻塞"，先想清楚是不是设计有问题。

### 3.6 ★ channel vs Mutex（高频对比题）

| 维度 | channel | Mutex |
| --- | --- | --- |
| **解决什么** | **数据在 goroutine 之间传递（所有权转移）** | **保护共享状态的临界区** |
| **底层** | `hchan`（锁 + 环形队列 + 等待队列） | 原子状态 + 信号量 |
| **额外开销** | 要分配 `sudog`、要挂起/唤醒 G、要内存拷贝 | 原子操作 + 可能的 park |
| **性能量级** | 无竞争约 **50~100ns** | 无竞争约 **20ns** |
| **高竞争表现** | **所有 G 抢同一把 hchan 锁**，可能更差 | 有自旋 + 饥饿模式兜底，更稳 |
| **可读性** | 意图清晰（"我在传数据"） | 需要自己保证加锁范围 |

**选择标准（背这段）**：

> 我的判断标准是：**如果是在"传递数据的所有权/信号"，用 channel；如果是"保护一小段共享状态的读写"，用 Mutex；如果只是个计数器/标志位，用 atomic。** 举两个我做过的例子：LoveSpouse 里每个连接有一个**发送队列 channel**，把要推的消息从业务 goroutine 交给写 goroutine —— 这是典型的所有权传递，用 channel 最自然；而**本地的连接表/订阅表**是多个 goroutine 都要读写的共享状态，用 `sync.RWMutex` 保护比用 channel 更好，因为用 channel 得为每次查询发一个请求再等回复，**多一层调度开销**。

**⚠️ Go 官方那句话**（说出来很地道）："**不要通过共享内存来通信，而要通过通信来共享内存**"—— 但官方也明确说过，**这句话不是"禁止用锁"**。channel 是给"所有权转移"用的，不是替代所有锁。

### 3.7 select 多路复用原理

**一句话答案**：`select` 是把所有 case 的 channel **先随机打散（pollorder），再按 channel 地址排序（lockorder）加锁**，然后统一扫描哪一路就绪。

| 机制 | 说明 |
| --- | --- |
| **pollorder（随机轮询顺序）** | 用 `cheaprand()` 洗牌。**为什么随机**：如果固定顺序，前面的 case 永远优先，**后面的 case 会被饿死（starvation）**。随机保证长期公平 |
| **lockorder（加锁顺序）** | **按 hchan 的内存地址排序**后依次加锁。**为什么排序**：保证多个 goroutine 用不同的 case 顺序做 select 时**加锁顺序一致，不会死锁**（防死锁的经典手段） |
| **有 `default`** | 所有 case 都不就绪 → 立即执行 `default`，**不阻塞**（"尝试发送/接收"模式） |
| **没有 `default`** | 所有 case 都不就绪 → 当前 G 挂到**所有** case 的等待队列上，**任一就绪就唤醒** |

**⚠️ 经典陷阱**：`select` 挂起时 G 会被挂到多个 channel 的 `recvq`/`sendq` 上，所以 `sudog` 里有 `isSelect`、`success`、`parent` 这些字段专门处理"被多个队列同时挂着"的场景。**面试官如果问这个，说明他在考 runtime 细节，你可以说"它的等待是按 select 整体处理的，不是拆成多个独立等待"，点到为止即可。**

### 3.8 关闭 channel 的行为（必背表格）

| 操作 | 结果 |
| --- | --- |
| 向**已关闭**的 channel **发送** | **`panic: send on closed channel`** |
| **重复关闭** | **`panic: close of closed channel`** |
| **关闭 nil channel** | **`panic: close of nil channel`** |
| 从**已关闭**的 channel **接收** | **永不阻塞**，立即返回**零值 + `ok=false`**（注意：缓冲区里剩余数据会先被读完，然后才开始返回零值） |
| **nil channel 上发送/接收** | **永久阻塞**（因为 nil channel 不在任何队列里，永远不会被唤醒） |

**⚠️ 三个必须记住的推论**：

1. **`close` 是广播机制**：关闭一个 `chan struct{}` 会**同时唤醒所有阻塞的接收者**（每个都拿到零值 + `ok=false`）。这是 Go 里做"一对多通知"最经典的手法。
2. **不要由接收方关闭 channel**：**谁发送谁关闭**（发送方才是数据的所有者）。多个发送方时，**谁都不该直接 close** —— 要么用 `sync.Once` 保证只关一次，要么**更好的做法是用 `context.Done()` 替代 close**，取消信号天然能通知所有接收方，谁都不用关。
3. **向已关闭 channel 发送会 panic**，哪怕是"刚关闭、还有人正在阻塞发送" —— 此时被阻塞的发送者会直接收到 panic。**所以"关闭正在使用的 channel"是高危操作。**

**为什么向已关闭 channel 发送要 panic 而不是返回错误？** → **因为这是程序逻辑错误，不是运行时状况**。发送方在关闭后还发，说明所有权管理错了，Go 选择**快速失败**而不是静默丢数据（静默丢数据的 bug 更难查）。

### 3.9 ★ channel 会导致内存泄漏吗？（会被追问）

**答案**：**channel 本身不会泄漏，但"没人收的 channel + 阻塞在上面的 goroutine"会泄漏，而且是 Go 最常见的内存泄漏形态。**

| 泄漏场景 | 现象 | 修复 |
| --- | --- | --- |
| **无缓冲 chan 发了没人收** | 发送方 goroutine 永久 `_Gwaiting`，**连同它引用的所有对象一起无法回收**（GC 认为它还活着） | 发送时 `select` + `ctx.Done()` 兜底 |
| **有缓冲 chan 满了没人消费** | 消费者挂了/退出了，生产者慢慢堆满后全部卡死 | **有界队列 + 满则丢弃或拒绝**，并加监控 |
| **`for range ch` 但没人 close** | 接收方永久阻塞等下一个元素 | 明确"谁负责 close" |
| **context 没 cancel** | 子 goroutine 永远等 `ctx.Done()` | `defer cancel()`（见第五章） |

**怎么检测（面试官爱问"你怎么发现"）**：

| 手段 | 用法 |
| --- | --- |
| **`len(ch)` / `cap(ch)`** | 把"队列堆积深度"打成监控指标。**堆积持续上涨 = 消费跟不上或消费者死了**，这是最廉价的早期预警 |
| **`runtime.NumGoroutine()`** | 暴露成指标，**持续上涨且不回落 = 有泄漏** |
| **goroutine profile** | `curl http://ip:port/debug/pprof/goroutine?debug=2` 看**同一段栈的 goroutine 数量**，数量最多的那组就是泄漏源 |
| **监控 `chansend`/`chanrecv` 的阻塞时长** | block profile（`runtime.SetBlockProfileRate(1)`），能看到大量时间耗在哪个 channel 上 |

**回答模板**：

> 会，而且这是 Go 里最典型的内存泄漏——**不是 channel 泄漏，是阻塞在 channel 上的 goroutine 泄漏，而且它引用的所有对象都跟着一起泄漏**。我的防御手段是三条：① **goroutine 必须有明确的退出条件**，发送/接收一律 `select` 带上 `ctx.Done()`；② **队列必须有界**，满了就降级而不是无限堆；③ **把 `len(ch)` 和 `NumGoroutine` 打成监控指标**，堆积上涨就能提前发现。（如果 LoveSpouse 实际做过，可以补一句：我们在长连接服务上就是这么做的，【具体指标名/告警阈值】。）

## 四、sync 包与并发原语

### 4.1 一句话答案

> **Mutex** 有**正常/饥饿**两种模式（等超 1ms 转饥饿）；**RWMutex** 读写分离，写优先；**WaitGroup** 是一个原子计数 + 信号量；**sync.Pool** 是降低 GC 压力的对象缓存（**高并发场景最值钱的一个**）；**sync.Map** 是"读多写少、key 稳定"场景的空间换时间容器。

### 4.2 Mutex：正常模式 vs 饥饿模式

**底层结构**：`state int32`（低 3 位是 `locked`/`woken`/`starving` 标志，高位存**等待者数量**）+ `sema uint32`（信号量）。

| 模式 | 触发 | 行为 | 代价 |
| --- | --- | --- | --- |
| **正常模式**（默认） | — | 唤醒的等待者要**和新来的 goroutine 一起竞争**（新来的正在 CPU 上跑、cache 热，**通常新来的赢**）；竞争失败就重新排队 | **吞吐高，但有长尾**——老等待者可能等很久 |
| **饥饿模式** | 某等待者**等待超过 1ms**（`starvationThresholdNs`） | **锁直接交给队首**等待者；**新来的 goroutine 不自旋、不参与竞争，直接排到队尾** | **公平**，1ms 量级能拿到锁；吞吐略降 |

**模式切换**：拿到锁的等待者如果**等待时间 < 1ms**，或者**自己已经是最后一个等待者**，就切换回正常模式。

**自旋条件**（4 个都要满足才自旋）：多核 + `GOMAXPROCS > 1` + 自旋次数未超限 + **当前 P 的本地队列为空**（避免自旋妨碍同 P 上其他 G 的运行）。

**回答模板**：

> Mutex 的设计是在**吞吐**和**公平**之间切换：正常模式让刚到的 goroutine 直接抢锁（它 cache 热，抢到最划算），吞吐高；但如果有人等超过 1ms 就进入饥饿模式，**锁直接交给队首、新人只排队不抢**，保证不会有人被饿死。**这个 1ms 的阈值说明 Go 的目标是"平均快 + 长尾可控"。**

**⚠️ 追问：那 Mutex 会不会导致延迟抖动？** → 会，**长尾就来自锁竞争**。高并发下减少竞争的手段是**分片（sharding）**：把一个 map 拆成 N 个，每个一把锁（见 9.1 与场景题）。

### 4.3 RWMutex：读多写少，但有代价

**一句话答案**：RWMutex 允许多个读者并行，写者独占。**写者等待时会阻塞新的读者**（防止写饥饿），代价是**写操作会拉高所有读的延迟**。

**底层**：`readerCount`（读锁计数，写者会把它减去 `rwmutexMaxReaders = 1<<30` 来标记"有写者在等"）、`readerWait`、`writerSem` / `readerSem`。

**⚠️ 三个真实问题（说出来比背定义强）**：

| 问题 | 说明 | 应对 |
| --- | --- | --- |
| **写锁会拖累读延迟** | 一旦有写者在等，**新读者全部被挡住** → 写少但慢的场景下，读延迟会出现尖刺 | 读极多写极少时，考虑 **`atomic.Pointer[T]` + 整体替换**（COW，写时复制），读路径完全无锁 |
| **读锁不免费** | 每次 `RLock` 都要对 `readerCount` 做**原子操作**，所有核打**同一个缓存行** → **cacheline 抖动（cacheline bouncing）**，核多时可能比普通 Mutex 还慢 | 数据分片，降低单点竞争；或用 atomic 替代 |
| **递归读锁会死锁** | 持有读锁时再 `RLock`，如果中间有写者在等，**新读者被阻塞** → 自己等自己，死锁 | **不要嵌套读锁**；需要嵌套就改用普通 Mutex |

**⚠️ `-race` 检测不到死锁**（race detector 只查数据竞争），死锁只能靠 `pprof` 或 `GODEBUG` 排查。

### 4.4 WaitGroup / Once / atomic

| 原语 | 一句话 | 坑 |
| --- | --- | --- |
| **WaitGroup** | 一个原子的 `state`（高 32 位计数 + 低 32 位等待者数）+ 信号量；`Wait` 阻塞直到计数归零 | **① `Add` 必须在 `Wait` 之前调用**（否则可能 Wait 已经返回了才 Add，行为未定义）；**② 计数不能变负**（会 panic）；**③ `Wait` 返回后可复用**（Go 1.25 还加了 `WaitGroup.Go`，省掉手动 Add/Done —— 不确定团队版本就别说这个） |
| **Once** | 原子标志 + 慢路径 Mutex，保证**只执行一次**（注意：**如果 `Do` 里的函数 panic，Once 会认为"已执行过"**，后续调用不再执行） | Go 1.21 起可用 `sync.OnceFunc` / `OnceValue` / `OnceValues`，更简洁 |
| **atomic** | **CAS（Compare-And-Swap）**、Add、Load、Store、Swap | **① Go 1.19 起把 `sync/atomic` 正式纳入内存模型，语义是"顺序一致"**；② 优先用 typed atomics（`atomic.Int64`、`atomic.Pointer[T]`），**避免手动算对齐**；③ **CAS 在低竞争下快，高竞争下会疯狂自旋烧 CPU**（锁至少在竞争时会把 G park 掉） |

**CAS vs Mutex（高频对比）**：

> **低竞争用 CAS（atomic），高竞争用 Mutex。** CAS 是无锁的，失败就重试，**在竞争激烈时会变成"大家一起空转烧 CPU"**；Mutex 在竞争激烈时会把等待者 park 起来，虽然慢但**不会浪费 CPU 且能保证公平**。另一个判断标准：**临界区只有一两条指令（计数、标志位、指针替换）用 atomic；有多步需要保持一致的读改写，用 Mutex。**

**★ 一个非常加分的细节：false sharing**

> 高并发计数器如果用**一个数组**存多个计数（比如每个连接一个计数器），相邻的计数器会落在**同一个 64 字节缓存行**上。不同核分别更新它们时，**缓存行在核之间来回弹（false sharing）**，性能比单线程还差。解法是**按缓存行填充（padding 到 64 字节）**或者**分片计数后汇总**。我在做连接数统计的时候会注意这个点。

### 4.5 ★ sync.Pool（高并发降 GC 的关键）

**一句话答案**：`sync.Pool` 是**临时对象的复用池**，用来减少高频对象的分配 → **直接降低分配速率和 GC 压力**。在网关这类"每请求都要 buffer"的场景，它是**收益最大的单个优化**。

**适用场景（判断标准）**：

| 适合 | 不适合 |
| --- | --- |
| **生命周期短、创建频繁、大小固定**的对象 | **长生命周期**的对象（那叫连接池，用 `database/sql` 或自己管理） |
| **读写 buffer**（`[]byte`）、`bytes.Buffer`、编解码临时结构 | **有状态**的对象（用之前必须 Reset，容易忘） |
| 大对象（省下的分配成本更高） | 需要**强保证不被回收**的对象 |

**⚠️ 四个必知的坑**：

1. **会被 GC 清空**。Pool 里的对象**任何时候都可能被 GC 回收**（Go 1.13 加了 **victim cache**：对象能**多活一轮 GC**，缓解了"每次 GC 全清空"的问题，但**依然不保证活到下次**）。**所以 Pool 只适合"缓存"语义，不能当"存储"用。**
2. **取出来必须重置**。`buf.Reset()` 或 `buf[:0]`，否则会带着上次的脏数据 → **这是 Pool 最经典的 bug**。
3. **不能放有 finalizer 的对象**，也不能依赖 Pool 做资源释放（比如归还数据库连接、关闭文件）——**GC 清 Pool 时不会通知你**。
4. **Pool 不解决内存占用上限**。它降低的是"分配速率"，不是"峰值内存"。**如果要限制内存，还得配合 GOGC / GOMEMLIMIT。**

**★ 代码（背这一段就行，讲的时候照着说）**：

```go
var bufPool = sync.Pool{
    New: func() any { return make([]byte, 0, 4096) }, // 固定 4KB，避免频繁扩容
}

func handle(w io.Writer, r io.Reader) error {
    buf := bufPool.Get().([]byte)
    defer func() {
        bufPool.Put(buf[:0]) // ★ 必须重置长度再放回，否则脏数据 + 内存不释放
    }()

    n, err := r.Read(buf[:cap(buf)])
    if err != nil {
        return err
    }
    _, err = w.Write(buf[:n])
    return err
}
```

**讲这段时的加分点**：

> 这里有三个细节：① **`New` 里给固定容量**，避免用的时候还要扩容；② **`Put` 之前切回 `buf[:0]`**，一是清数据，二是**不要把 append 长大的大 buffer 塞回池里**（否则池里的对象越来越大，内存只涨不降）；③ 这个池的价值在**网关**场景特别明显 —— 每转发一个请求要一个读写缓冲，**没有池的话每次请求都产生一次堆分配，GC 频率直接翻几倍**。

### 4.6 sync.Map（适用场景 + 什么时候不要用）

**一句话答案**：`sync.Map` 是**为"读多写少、key 相对稳定"优化的 map**（内部是 `read` 只读快照 + `dirty` 脏 map + 一个 Mutex + miss 计数），**通用的读写场景不如 `RWMutex + map`**。

| 维度 | sync.Map | RWMutex + map |
| --- | --- | --- |
| **读（命中 read）** | **无锁**，一次原子 load，很快 | 需要 RLock（原子操作） |
| **写 / 新增 key** | 要**升级 dirty map**、要加锁，**比 RWMutex 慢** | 直接加锁写入 |
| **内存** | **空间换时间**（read/dirty 两份引用，删除是标记 `expunged` 而不是真删） | 一份 |
| **类型安全** | `any`，要类型断言 | 泛型 map 可以强类型 |

**✅ 适合**：注册表、元数据缓存、配置快照、**读远多于写且 key 集合基本固定**的场景。

**❌ 不适合**：

- **写多**的场景（每次新 key 都要升级 dirty map）；
- **需要 `len()` 和遍历**的场景（`Range` 不保证一致性，`len` 需要遍历）；
- **需要原子"读-改-写"**（`Load` 后 `Store` **不是原子的**，中间会被插队，这种情况还是要 Mutex）。

**⚠️ 高并发下更好的方案：分片 map**

> 如果要一个高并发、读写都频繁的 map，**最实用的方案是"分片"**：按 key 的 hash 取模拆成 32/64/256 个桶，**每个桶一个 `sync.RWMutex` + 普通 map**。这样锁竞争从"全局一把"降到"1/N"，核越多收益越大，而且 `len`、遍历、原子读改写都能实现。**（如果面试官追问"你在项目里用过吗"，诚实说：我的连接表和会话表用的是分片思路 / 或者坦白说"我知道这个方案，项目里量级没到需要分片"。）**

### 4.7 ★ 结合商云前台：本地 SQLite 并发写 + 串口通信的并发控制

> 这两块是我在 POS 桌面应用里真实处理过的并发问题，**是很典型的"资源独占"场景**，跟 Go 的并发原语直接相关。

**问题一：SQLite 本地并发写**

| 事实 | 说明 |
| --- | --- |
| SQLite **写是库级排他锁** | 同一时刻**只能有一个写事务**，其他写会拿到 `SQLITE_BUSY` |
| WAL 模式下**读写可以并发** | 但**写与写仍然互斥** |
| 多 goroutine 直接写 | 会频繁 `SQLITE_BUSY`，重试逻辑写不好就丢数据 |

**我的处理（三层）**：

1. **写操作串行化**：**用一个专门的写 goroutine 消费一个 channel**，所有模块的写请求都投递到 channel，由它单线程执行。**这样"写互斥"从我自己的代码层面保证了，不依赖 SQLite 的锁。**（`select` + `ctx.Done()` 保证不泄漏。）
2. **WAL + busy_timeout**：打开 WAL 模式让读不被写阻塞；设 `busy_timeout` 兜底，避免偶发冲突直接报错。
3. **读走连接池并发**：读写分离，**读可以多个 goroutine 并行**，只有写被串行化。**代价是写有一点延迟（进队列），但收银场景写的是本地流水，延迟完全可接受。**

**问题二：串口的并发控制**

> 串口（电子秤、打印机、钱箱）是**独占设备**，同一时刻只能有一个会话，否则命令和应答会串。这和 channel 的用法是连在一起的：

| 场景 | 问题 | 做法 |
| --- | --- | --- |
| **命令-应答型**（电子秤读重量） | 两个 goroutine 同时发命令，**应答会串到错误的调用方** | **串行化 + 请求 ID 配对 + 超时**：命令走一个 channel，一个专门的读写 goroutine 顺序执行；每个请求带序号，应答按序号匹配回给对应的等待者；**超时就返回错误而不是永久等** |
| **单向下发型**（打印钱箱） | 发完不等回复，并发发会不会乱？ | 只要**写是原子的**（一次 `Write` 完整写完一帧）就没问题；但为了避免字节交错，**仍然统一走同一个写 goroutine** |
| **设备热插拔/异常** | 串口断了，等待中的请求永远挂着 | 用 `context` 做统一超时；**设备错误时 cancel 掉所有在途请求** |

**回答模板**：

> 这两块的共同点是**资源独占**：SQLite 的写锁、串口设备，本质都是"同一时刻只能有一个持有者"。我的统一做法是**把独占资源封装成一个后台 goroutine + 一个请求 channel**，调用方投递请求、等结果、带超时。**好处是并发控制只在一个地方实现，业务代码完全不用关心锁；而且天然支持"设备异常时统一失败"** —— 把 channel 关掉或 cancel context，所有在途请求立刻返回错误，不会永久挂住。**这跟 Go 里"用 channel 传递所有权，而不是到处加锁"是同一个思路。**

## 五、context

### 5.1 一句话答案

> `context` 是 Go 的**取消信号传播机制 + 请求作用域数据载体**。它的核心能力只有两件事：**① 一个 goroutine 能通知它派生出的所有 goroutine"取消"；② 携带请求级的元数据（trace id、认证信息）**。它是**树形结构**，取消会**向下传播**。

### 5.2 层级结构与四个构造函数

| 构造函数 | 返回 | 用途 |
| --- | --- | --- |
| `context.Background()` | 空 context | **根节点**，main/初始化/测试用 |
| `context.TODO()` | 空 context | 占位，语义上"还没想好该用哪个" |
| `WithCancel(parent)` | ctx + **CancelFunc** | 手动取消（**最常用**） |
| `WithTimeout(parent, d)` | ctx + CancelFunc | 超时自动取消（**= WithDeadline(now+d)**） |
| `WithDeadline(parent, t)` | ctx + CancelFunc | 到绝对时间取消 |
| `WithValue(parent, k, v)` | ctx | 携带请求级数据 |

**内部结构（能说出这三个就够）**：

| 类型 | 关键字段 |
| --- | --- |
| `cancelCtx` | `done chan struct{}`（**只关一次**）、`children map[canceler]struct{}`、`err`、`mu` |
| `timerCtx` | 内嵌 `cancelCtx` + `timer`（**这才是需要 cancel 的真正原因**） |
| `valueCtx` | 内嵌父 `Context` + `key`/`val`（**链表结构，查 value 是 O(深度) 的线性查找**） |

### 5.3 取消信号的传播机制

```
调用 cancel()
 ├─ 关掉自己的 done channel（★ close 是广播，所有监听者立刻被唤醒）
 ├─ 遍历 children，递归调用每个 child 的 cancel()   ← 向下传播
 ├─ 把自己从父节点的 children map 中移除（removeChild）
 └─ 如果有 timer，停掉它（避免定时器泄漏）
```

**★ 这里有个高并发下的性能陷阱（说出来很加分）**：

> **取消是深度优先、递归向下传播的**。如果一个 context 下面挂了成千上万个子 context（比如一个"全局配置刷新"context 下挂了几万个连接的 context），**一次 cancel 会遍历整棵树，是有代价的**。所以实践中不要建特别宽的 context 树 —— **连接级的 context 从请求/连接自己开始建，不要全都挂在同一个父节点上**。

### 5.4 ★ 为什么必须调用 cancel（否则泄漏）

**记住两个泄漏点**：

| 泄漏点 | 机制 |
| --- | --- |
| **children map 引用** | 子 context 会把自己登记到**父的 `children` map** 里。**只要不 cancel，父 context 就持有子的引用，子以及子引用的所有对象都不能被 GC 回收**（直到父被取消）。 |
| **定时器泄漏** | `WithTimeout`/`WithDeadline` 会起一个 `time.Timer`。**不调用 cancel 的话，定时器到期前一直挂在全局时间堆上**，占用内存和 timer 处理开销。（在**长生命周期**的父 context 上尤其严重 —— 比如一个服务级 context 下每秒派生几百个带超时的子 context，很快就积累几十万个定时器。） |

**⚠️ 两个必答细节**：

1. **`defer cancel()` 要写在创建后立刻**，不要写在函数末尾，也不要包在条件里 —— 否则一旦中间 `return` 或 `panic` 就漏了。
2. **即使你的逻辑不需要取消，也必须调用 cancel** —— 因为你要的是**释放它注册在父节点上的资源和定时器**。这就是 `go vet` 会报 `lostcancel` 的原因。

**标准写法（背这段）**：

```go
func handle(ctx context.Context, req *Req) error {
    ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
    defer cancel() // ★ 紧跟着写，不解释

    return doWork(ctx, req)
}
```

### 5.5 ★ 为什么 Value 不该传业务参数

| 原因 | 说明 |
| --- | --- |
| **没有类型安全** | key 是 `any`，取出来必须断言；**key 冲突没有编译期检查**（必须用**非导出的自定义类型**做 key，而不是 string，否则不同包会撞） |
| **是隐藏参数** | 函数签名上看不出依赖，**破坏了函数的显式契约**；调用方不知道要给什么，容易漏 → 运行时才 panic |
| **性能** | `Value()` 是**沿父链的线性查找**，深度越大越慢（还有锁）。**放在热路径上会被放大** |
| **职责混乱** | 一旦开始传业务参数，context 就会变成一个"什么都能塞的袋子"，最后谁都不敢改 |

**✅ 正确用法**：只放**请求作用域的横切元数据**：trace id / request id、认证主体、日志字段、超时预算。

**✅ 业务参数走显式参数或结构体**：

```go
// ❌ 不要
func GetUser(ctx context.Context, id int64) (*User, error) {
    tenant := ctx.Value("tenant_id").(string) // 隐藏依赖 + 可能 panic
    ...
}

// ✅ 要
func GetUser(ctx context.Context, tenantID string, id int64) (*User, error) { ... }
```

**回答模板**：

> context 的 Value 我只会放**请求级的元信息**：trace id、用户身份、日志上下文。**业务参数一定走显式参数**。原因有三：① 没有类型安全，key 冲突和类型断言失败都是运行时才炸；② 函数签名上看不出依赖，是"隐藏参数"，新人容易漏；③ **`Value` 是沿着父链线性查找的，放热路径上会拖性能**。如果团队里有人往里塞业务字段，我会在 CR 的时候拦下来。

### 5.6 ★ 结合 LoveSpouse

**场景一：WebSocket 连接的超时控制**

> 每条 WebSocket 连接我会建一个**连接级的 context**（`WithCancel`，从服务根 context 派生）。**连接关闭时 cancel 它，所有下游调用立刻取消**：
>
> - 模型 API 调用（带 `WithTimeout`，比如首包 3s、整体 30s）—— **用户关掉 App 之后，后端不该还在跑模型请求烧钱**；
> - IM 消息发送、Redis 写入、DB 落库；
> - **实时语音流**（Gemini Live）—— 这个最关键，**语音是长连接流式的，context 一 cancel 就要能把流关掉，否则会一直占着上游配额**。
>
> **收益非常直接**：**连接断了 → 资源立刻释放**，不会出现"用户已经走了，后端还在算"的情况。这在**付费按量计费**的场景下尤其重要 —— 每多跑一次模型调用都是真金白银。

**场景二：跨实例通话控制的取消传播**

> 通话控制（开始通话、挂断、切换角色）的业务逻辑是**跨实例**的：用户可能连在实例 A，但也可能重连到实例 B。我的做法是：
>
> 1. **状态外置到 Redis**：会话状态 + "会话 → 实例"的映射，**服务本身无状态**，这样实例能随意扩容重启；
> 2. **控制指令通过 Redis Pub/Sub（或 MQ）广播**，各实例收到后**只处理自己持有的会话**，其余直接忽略；
> 3. **每条控制指令带自己的 context 超时**（比如 2s）；如果本实例上找不到会话或处理超时，**取消掉这条指令在途的一切操作**，由上层做**幂等重试**；
> 4. **通话建立/结束用幂等保护**：一次通话只允许一个实例持有，用 Redis 原子操作（SET NX / Lua）保证。
>
> **核心思路**：**context 负责"这个操作超时了要停"，Redis 负责"跨实例的协调"，两者分工明确**。不要把跨实例协调塞进 context —— **context 只管一个请求的生命周期，管不了分布式事务。**

**⚠️ 追问：跨实例场景 context 能传过去吗？** → **不能**。context 是**进程内的对象**，跨网络传递时你只能传"deadline 和取消原因"这类**信息**（比如把 deadline 放在请求头里传给下游服务），不能传 context 本身。**这是一个很好的加分回答 —— 说明你真正理解 context 的边界。**

## 六、内存模型与逃逸分析

### 6.1 一句话答案

> Go 的变量**能放栈上就放栈上**（分配快、不用 GC、函数返回即释放），**放不下就"逃逸"到堆上**（要 GC）。判断依据是**逃逸分析**：编译器静态分析"这个变量的引用会不会活过当前函数栈帧"。**优化 Go 程序的一大半收益，来自于减少堆分配。**

### 6.2 栈 vs 堆

| 维度 | 栈 | 堆 |
| --- | --- | --- |
| **分配成本** | **极低**（就是移动一下栈指针） | 较高（走 size class、mcache/mcentral/mheap，可能要加锁） |
| **回收** | **函数返回自动释放，零成本，不用 GC** | **靠 GC**（三色标记 + 清扫） |
| **访问速度** | 快（栈内存局部性好，cache 命中率高） | 相对慢（分散在堆里，cache 不友好） |
| **谁决定** | **逃逸分析（编译期决定）** | 逃逸分析判定"逃逸"的才上堆 |
| **数量** | 每个 goroutine 一个栈（2KB 起，可增长） | 全局共享 |

**⚠️ 一个常见误解**：**"Go 的变量在栈上还是堆上，不是你决定的，是编译器决定的"**（不像 C/C++ 有 `malloc` vs 局部变量）。`new(T)` 出来的对象**也可能在栈上**（如果没逃逸）！

### 6.3 ★ 常见逃逸场景（背这 6 类）

| 场景 | 例子 | 为什么逃逸 |
| --- | --- | --- |
| **① 返回局部变量的指针** | `func f() *T { t := T{}; return &t }` | 引用活过了函数栈帧，**必须搬到堆上**（这也是为什么"返回局部变量指针"在 Go 里是安全的） |
| **② 赋值给 `interface{}`** | `fmt.Println(v)`、`var a any = t`、放进 `[]any` | **`interface` 底层是 (type, pointer) 两个指针**，编译器无法证明这个指针的寿命 |
| **③ 闭包捕获变量** | `func() { return func() { _ = x } }()` 里被捕获的 x | 闭包可能比捕获它的函数活得更久 |
| **④ 大小不确定的分配** | `make([]byte, n)`（n 是变量）、`append` 超出栈容量 | **编译期不知道大小，栈上放不下**（变长） |
| **⑤ 对象过大** | 超过编译器阈值的局部大数组/大结构体 | 栈太小（2KB 起），大对象直接放堆上 |
| **⑥ 被更长寿的对象引用** | 存进全局 map / 全局 slice / 传给别的 goroutine | 引用被"更长的生命周期"持有 |

**★ 一个高频陷阱（切片扩容导致逃逸）**：

```go
func bad() []int {
    s := make([]int, 0, 4) // 常量容量，可能还在栈上
    return append(s, 1, 2, 3, 4, 5) // ★ 超出容量触发扩容 → 必须申请新数组 → 逃逸
}
```

**⚠️ 还有一个更隐蔽的"假逃逸"来源**：如果一个函数被**内联**，它的局部变量可能就不逃逸了；反之，**禁用内联（`-gcflags="-l"`）会凭空多出一堆逃逸**。所以看逃逸报告时要注意内联状态。

### 6.4 ★ 怎么减少逃逸（工程化建议）

| 手法 | 说明 |
| --- | --- |
| **返回值优先返回结构体/值，不要无脑返回指针** | 小对象返回值比返回指针更可能留在栈上（**注意：大结构体返回值会有拷贝成本，要权衡**） |
| **避免无谓的 `interface{}` 装箱** | 热路径上不要用 `fmt.Sprintf`（参数全是 interface），改用 `strconv`；用**泛型/concrete type** 替代 `any` |
| **避免在热路径用闭包捕获** | 或者把捕获的变量按值传进去 |
| **预分配容量** | `make([]T, 0, n)` 一次到位，避免 `append` 反复扩容（**每次扩容都新分配 + 拷贝 + 老数组变垃圾**） |
| **用 `sync.Pool` 复用大对象** | 见 4.5 |
| **不要在热路径用 `map[string]any` 和反射** | JSON 序列化用 `sonic`/`jsoniter` 之类的库，比标准库 `encoding/json` 分配的少很多 |
| **传 `[]byte` 而不是 `string`** | `string(b)` 和 `[]byte(s)` 会有**完整的内存拷贝**（除非编译器优化掉）；用 `unsafe` 或直接全程 `[]byte` |

**⚠️ 但要避免过度优化**：

> **不要为了减少逃逸把代码写得不忍直视。** 我的原则是：**先用 pprof 找出真正的分配热点，再针对它优化**。大部分代码怎么写都无所谓，**只有每秒执行几十万次的那几行决定了性能**。

### 6.5 ★ 怎么看逃逸分析

```bash
# 基础：报告每个变量的逃逸决策
go build -gcflags="-m" ./...

# 更详细（-m 两次）：能看到具体的推理过程
go build -gcflags="-m -m" ./...

# 禁用内联（因为内联会改变逃逸结论，想看"最坏情况"时用）
go build -gcflags="-m -l" ./...
```

**输出怎么读**：

| 输出 | 含义 |
| --- | --- |
| `escapes to heap` | ⚠️ **逃逸了，上堆**（要关注） |
| `does not escape` | ✅ **没逃逸，在栈上**（好） |
| `moved to heap: x` | 变量 x 被搬到堆上 |
| `leaking param: x` | 参数 x 逃逸了 |
| **`inline`** | 这个函数被内联了（会影响逃逸结论） |

**回答模板**：

> 我一般用 `go build -gcflags="-m"` 看逃逸报告，重点关注**热路径上函数**的 `escapes to heap`。但**逃逸分析本身不是目的** —— 最终还是要用 **`pprof` 的 `alloc_space`** 找到**真正的分配热点**，因为逃逸报告里全是噪音，只有少数几行值得优化。**顺序是：压测找瓶颈 → pprof 定位分配热点 → 看逃逸报告找原因 → 改代码 → 再压测验证。**

### 6.6 make vs new / slice vs array / 切片扩容

**make vs new（经典题）**：

| | `new(T)` | `make(T, ...)` |
| --- | --- | --- |
| **返回** | **`*T`**，指向**零值**内存 | **`T` 本身**（不是指针） |
| **适用类型** | **任意类型** | **只能 slice / map / chan** |
| **是否初始化** | 只清零 | **会初始化内部结构**（slice 的底层数组、map 的哈希表、chan 的 hchan） |
| **实际使用** | **很少用**（"返回指针"的场景更推荐直接 `&T{}`） | 创建 slice/map/chan 的唯一方式 |

**⚠️ 一句话记住**：**`new` 只是分配 + 清零；`make` 是"创建并初始化"一个特殊类型。`new([]int)` 返回的是"指向 nil slice 的指针"，几乎没有任何用处。**

**slice vs array（经典题）**：

| 维度 | array `[5]int` | slice `[]int` |
| --- | --- | --- |
| **类型** | **长度是类型的一部分**（`[3]int` 和 `[4]int` 是不同类型） | 长度不属于类型 |
| **本质** | **值类型**（一整块连续内存） | **3 个字的头结构**：`{ptr, len, cap}` |
| **传参** | **整个数组拷贝**（大数组拷贝很贵！） | **只拷贝 24 字节的头部**，**底层数组共享** |
| **能否扩容** | 不能 | 能，`append` |
| **比较** | 能用 `==` | **不能用 `==`**（只能和 nil 比，或用 `slices.Equal`） |

**⚠️ slice 共享底层数组是 Go 最容易出的 bug 之一**：

```go
a := []int{1, 2, 3, 4}
b := a[1:3]      // b = [2 3]，共享 a 的底层数组
b[0] = 99        // ★ a 变成 [1 99 3 4] —— 改了 a！
b = append(b, 5) // ★ 如果 cap 够，会写到 a[3] 的位置
```

**⚠️ 反向的内存泄漏**（面试加分）：

```go
// 一个只关心前 10 字节的函数，却让整个 1MB 的 buffer 无法回收
func parse(data []byte) []byte {
    return data[:10] // ★ 返回的 slice 依然引用着 1MB 的底层数组
}

// ✅ 正确：拷贝出来，切断对大数组的引用
func parse(data []byte) []byte {
    out := make([]byte, 10)
    copy(out, data[:10])
    return out
}
```

**★ 切片扩容策略（Go 1.18+ 的 256 阈值，能说出版本差异很加分）**：

| 版本 | 策略 |
| --- | --- |
| **Go 1.18 之前** | `cap < 1024` → **翻倍**；`cap >= 1024` → **每次 ×1.25** |
| **Go 1.18 及以后** | 需要的大小 `> 2*cap` → **直接用需要的大小**；否则 `oldCap < 256` → **翻倍**；否则 → **`(oldCap + 3*256) / 4`**，也就是**从 2 倍平滑过渡到 1.25 倍** |

**为什么改成 256？** → **原来的 1024 阈值在小切片阶段（1024 以下）每次都翻倍，最后一次翻倍会造成最多 2 倍的内存浪费**。改成 256 之后**更早地切换到 1.25 倍增长**，内存浪费更小。

**⚠️ 两个必答细节**：

1. **扩容后的容量还要经过 `roundupsize` 向上对齐到内存 size class**（Go 的内存分配是按 size class 分档的），**所以你实测的 `cap` 往往比公式算的大**——这是正常的，不是记错了公式。
2. **扩容后是新数组**，原本共享这个底层数组的其他 slice **不受影响**（各自指向老数组）。**这是"为什么 append 之后原 slice 没变"的原因，也是很多 bug 的来源。**

## 七、★ GC 原理（必考）

### 7.1 一句话答案

> Go 的 GC 是**并发的、三色标记清除（concurrent mark-sweep）、不分代、不整理（non-moving）**。核心是**三色标记法**保证正确性，**混合写屏障**保证并发标记期间不漏标（Go 1.8+），**只有两个极短的 STW 阶段**（开启标记、标记终止），**所以停顿能做到亚毫秒**。

**⚠️ 三个"不"要记住**：**不分代、不整理（不移动对象）、不压缩**。这是 Go GC 和 Java GC 最大的区别。

### 7.2 ★ 三色标记法

| 颜色 | 含义 | 状态 |
| --- | --- | --- |
| **白色** | **还没被访问到** | GC 开始时**全是白色**；结束时**还是白色的就被回收** |
| **灰色** | **被访问到了，但它引用的对象还没扫完** | **待处理队列**（标记队列） |
| **黑色** | **自己扫完了，它引用的对象也都扫完了** | **活对象** |

**标记流程**：

```
① 起点：所有对象都是白色
② 根对象（root）标灰：全局变量、各 goroutine 的栈、寄存器
③ 循环：从灰色队列取一个对象 → 把它标黑 → 把它引用的所有白色对象标灰
④ 队列空了 → 标记结束，剩下的白色对象就是垃圾
⑤ 清扫（sweep）：并发地回收白色对象的内存
```

**★ 核心不变式（Invariant）**：

> **任何时刻，黑色对象都不能直接指向白色对象。** 否则那个白色对象会在本轮被误回收（但它是活的）。

**为什么会被破坏？** → 因为**标记和用户程序（mutator）是并发执行的**。用户程序可能在标记过程中**修改指针**，制造出"黑色 → 白色"的新引用：

```
标记器：把 A 标黑（此时 A 引用的 B 已经是黑的，或 B 就是黑的）
用户程序：把 C（黑）的字段指向 D（白），同时把指向 D 的唯一路径 B→D 删掉
结果：D 是活的，但它是白的 → 被误回收 → 程序崩溃
```

**解决方案就是写屏障。**

### 7.3 ★ 写屏障（混合写屏障，Go 1.8+）

**一句话答案**：写屏障是**在指针赋值时插入的一小段代码**（由编译器在写指针的地方自动插入），用来在并发标记期间**维护"黑色不指向白色"的不变式**。

| 屏障类型 | 做什么 | 缺陷 |
| --- | --- | --- |
| **Dijkstra 插入屏障** | 写入新指针时，**把新指针指向的对象标灰** | 无法覆盖"删除引用"的情况；且**栈上的写操作无法加屏障**，所以必须在标记结束时**重新扫描所有栈（STW 较长）** |
| **Yuasa 删除屏障** | 覆盖旧指针时，**把旧指针指向的对象标灰** | 保守：本轮不回收一些实际已死的对象（浮动垃圾），但**不会漏标** |
| **★ Go 1.8+ 混合写屏障** | **两者都做：既把新值标灰，也把旧值标灰** | 见下 |

**混合写屏障的关键收益（这段说出来很加分）**：

> **Go 1.8 的混合写屏障最大的贡献，是让标记终止阶段不再需要重新扫描所有 goroutine 的栈。** 之前必须 STW 重扫栈，**栈越多、goroutine 越多，这个停顿就越长**（几百微秒到毫秒级，且随程序规模增长）。用了混合写屏障后，**栈在标记开始时被一次性标黑，之后就不再需要重扫** —— 这是 Go 能把 GC 停顿压到亚毫秒的**决定性一步**。

**⚠️ 一个必答细节**：**写屏障只对堆上的指针写生效，栈上的指针写不加屏障**（因为栈是自己独占的、会被单独处理）。这是为什么混合写屏障要同时用删除屏障 —— 用来覆盖"栈上的指针写"这个漏洞。

**⚠️ 另一个加分细节**：写屏障**在 STW 期间是关闭的**，只有在并发标记阶段才是打开的。所以它不是永远的运行时税，只在标记期间有开销（大约让程序慢 5%~30%，取决于指针写的频率）。

### 7.4 ★ STW 发生在哪些阶段

**Go 一次 GC 周期的完整阶段**：

| 阶段 | 是否 STW | 做什么 | 典型耗时 |
| --- | --- | --- | --- |
| **① Sweep Termination（清扫终止）** | ★ **STW** | 确认上一轮清扫完成，准备开始新周期 | **极短**（微秒级） |
| **② Mark Setup（标记准备）** | ★ **STW** | **开启写屏障**、准备根扫描任务 | **极短**（微秒~几十微秒） |
| **③ Concurrent Mark（并发标记）** | 并发 | 标记器与用户程序同时跑；**用户程序分配过快时会"辅助标记"（mark assist）** | **毫秒~几十毫秒（但不 STW！）** |
| **④ Mark Termination（标记终止）** | ★ **STW** | **关闭写屏障**、计算下一轮 GC 目标、收尾 | **极短**（微秒~百微秒） |
| **⑤ Concurrent Sweep（并发清扫）** | 并发 | **惰性清扫**：分配内存时才顺便清扫对应的 span | 不 STW |

**★ 为什么能做到亚毫秒（核心答案）**：

> **因为最耗时的"标记"和"清扫"都是并发的，STW 阶段只做"簿记"** —— 开/关写屏障、算下一轮的目标。**没有任何"跟随指针遍历对象图"的工作发生在 STW 里。** 加上 Go 1.8 的混合写屏障去掉了"重扫栈"这个大头，Go 1.19 又重写了 GC pacer 让标记开始得更及时，**所以 STW 稳定在几十~几百微秒，且不随堆大小线性增长**。

**⚠️ 但真正的延迟杀手不是 STW（关键认知，面试官会欣赏）**：

| 隐藏开销 | 说明 |
| --- | --- |
| **★ Mark Assist（辅助标记）** | **堆增长太快时，分配内存的 goroutine 会被"罚款"——必须先帮忙标记一段**。**这是唯一会直接拖慢业务请求的 GC 开销**，表现为"某个请求突然变慢"。网关这种高分配速率场景**必须重点防这个** |
| **标记占用 CPU** | 后台标记 worker 默认占 **25% 的 P**（`gcBackgroundUtilization = 0.25`），**等于 GC 期间你的有效算力少了 1/4** |
| **写屏障开销** | 标记期间所有指针写都变慢 |

**⚠️ 所以正确的说法是**：**"Go 的 GC 停顿不是问题，GC 的 CPU 开销和 mark assist 才是问题。"** 这句话说出来，面试官会知道你真的调过。

### 7.5 GC 触发时机

| 触发条件 | 说明 |
| --- | --- |
| **★ 堆增长达到目标** | 由 `GOGC` 控制（**默认 100**，意思是"**堆比上次 GC 后的存活量大 100% 就触发**"，即**堆翻倍就 GC**）。比如上次 GC 后存活 100MB，那么堆到 200MB 就触发 |
| **★ 每 2 分钟强制一次** | `forcegcperiod = 2min`，由 sysmon 兜底。**防止"不分配内存的程序永不 GC"** |
| **手动 `runtime.GC()`** | 显式触发，会 STW 完整跑一轮。**只在测试/内存敏感的操作后用，生产别乱调** |
| **★ `GOMEMLIMIT` 逼近时** | Go 1.19+ 的**软内存限制**，见 7.6 |

**`GOGC` 怎么用**：

| 值 | 含义 |
| --- | --- |
| `GOGC=100`（默认） | 堆翻倍就 GC。**内存换 CPU 的中间点** |
| `GOGC=200` ~ `400` | **GC 次数更少、CPU 占用更低，但内存占用更高**。**网关/高 QPS 服务常用**（用内存换延迟和吞吐） |
| `GOGC=off` | 关闭自动 GC（**只有配合 GOMEMLIMIT 才能用，否则 OOM**） |
| `GOGC=50` | GC 更频繁、CPU 更忙、内存更省（**内存紧张时用**） |

### 7.6 ★ GOMEMLIMIT（Go 1.19+ 软内存限制）

**一句话答案**：`GOMEMLIMIT` 给 Go 运行时的**堆总量设一个软上限**（不是硬限制，**可能被超过，但会尽最大努力不超**）。**它和 GOGC 是互补的**：GOGC 控制"增长比例"，GOMEMLIMIT 控制"绝对上限"。

**为什么它重要（必答）**：

> **GOGC 有个根本缺陷：它是按"比例"控制的，而容器是按"绝对值"限制内存的。** 比如一个服务存活对象 500MB，GOGC=100 意味着堆会涨到 1GB 才 GC —— **如果容器限额是 800MB，直接 OOMKilled。** GOMEMLIMIT 就是解决这个的：**它保证在接近绝对上限时会提前 GC。**

**★ 面试推荐配置（记住这个组合）**：

| 参数 | 建议值 | 理由 |
| --- | --- | --- |
| `GOMEMLIMIT` | **容器内存限额的 90%~95%** | 留出运行时/栈/碎片的空间（**不要设成 100%，会被 OOMKilled**） |
| `GOGC` | **off（配合 GOMEMLIMIT）** 或 **200~400** | 让 GC **只在真的需要省内存时才跑**，把 CPU 省下来给业务 |

**⚠️ 三个坑**：

1. **它是软限制，不是硬限制** —— 如果存活对象本身就超过限额，**照样 OOM**。它不能救内存泄漏。
2. **设太小会引发"GC 死亡螺旋"** —— 内存一直贴着上限 → GC 不停跑 → CPU 全去标记了 → 业务处理变慢 → 请求堆积 → 内存更多 → **雪崩**。**所以别设太紧，且一定要监控 GC CPU 占比。**
3. **它只管 Go 的堆**，不管 **cgo 内存、栈内存、二进制自身、mmap**。**所以在 cgo 多的程序里要留更多余量。**

**回答模板**：

> 我在容器里会同时设两个：**`GOMEMLIMIT` 设为容器限额的 90%**，**`GOGC` 适当放大（200~400）或者直接配合 off**。这样 GC **平时不动，快到内存上限才启动**，等于把"按比例 GC"换成了"按实际内存压力 GC"，**GC 的 CPU 开销和不必要的停顿都显著降低**。但有个前提：**它不能救内存泄漏**，而且设太紧会导致 GC 死亡螺旋，所以我一定会同时盯 **GC CPU 占比（`GODEBUG=gctrace=1`）** 和 **GC assist 时间**。

### 7.7 Go 1.19 / 1.20+ 的 GC 演进（知道方向即可）

| 版本 | 变化 |
| --- | --- |
| **Go 1.8** | **混合写屏障**，消除了标记终止阶段重扫栈的停顿（**最关键的一次**） |
| **Go 1.14** | 基于信号的**异步抢占**，解决了"死循环卡住 GC 的 STW"的问题（见 2.6） |
| **Go 1.19** | **`GOMEMLIMIT` 软内存限制**；**GC pacer 重新设计**（用更简单的公式，更不容易"GC 跑得太晚导致堆暴涨"） |
| **Go 1.20** | GC 内部数据结构优化；**arena 实验特性**（`GOEXPERIMENT=arenas`，手动管理一块内存来减少 GC 扫描） |
| **Go 1.25 及以后** | 有 **"Green Tea" GC** 的实验（改善对象遍历的内存局部性，让标记更快），**还是实验性的，别在生产赌它** |

**⚠️ 关于 arena（会被追问吗）**：

> arena 的设想是"**手动申请一块大内存，里面放的对象不被 GC 扫描**"，适合网关里"一批同生命周期的临时对象"。**但它一直是实验特性，后来也没进主线**，我的判断是**不值得依赖** —— 同样的目标用 `sync.Pool` + 减少分配就能达到大部分收益，而 arena 会带来**内存管理复杂度和"忘记释放就是泄漏"**的风险。

### 7.8 ★ Go GC vs Java GC（高频对比）

| 维度 | Go GC | Java GC（G1 / ZGC / CMS 等） |
| --- | --- | --- |
| **算法** | **并发标记清除（mark-sweep）** | 分代 + 复制/标记整理（G1 是 region + 复制） |
| **分代** | **不分代** | **分代**（年轻代/老年代，或有 region 概念） |
| **整理/移动** | **不移动对象**（non-moving） | **会移动/压缩**（ZGC 并发整理） |
| **停顿** | **亚毫秒**（两个极短 STW） | 从几十 ms（CMS/G1）到亚毫秒（ZGC/Shenandoah） |
| **可调参数** | **极少**（GOGC、GOMEMLIMIT，就两个） | **极多**（堆大小、各代比例、区域大小、GC 线程数……） |
| **写屏障** | 混合写屏障（插入 + 删除） | 各种（卡表 / 染色指针 / 读屏障） |
| **吞吐 vs 延迟** | **偏延迟**（并发做得多，CPU 换延迟） | 可调（G1 偏吞吐可控，ZGC 瞄延迟） |

**★ 为什么 Go 不做分代？（高频追问，必答）**

**分代假说**：**大部分对象"朝生夕死"**。所以把新对象放年轻代，用廉价的复制算法频繁回收，就很划算。

**Go 不做的理由（4 条，按说服力排序）**：

1. **★ 逃逸分析 + 栈分配已经"吃掉"了很多朝生夕死的对象**。Java 也有逃逸分析但不总是可靠，而 Go 的小对象**大量根本不上堆**（在栈上），**年轻代里剩下的"短命对象"没那么多，分代的收益被大幅削弱。**
2. **分代的成本对 Go 不划算**：分代需要**记忆集（remembered set）** 来记录"老年代指向年轻代的引用"、需要**对象头存年龄**、需要**移动对象**（复制算法必然移动）→ **而移动对象意味着所有指针都要能更新，Go 选择了"不移动"来换取实现的简单和稳定**。**多出来的内存和复杂度，对上一代 Go GC 的收益不明显。**
3. **Go 的并发标记已经能做到亚毫秒停顿** —— **分代主要是为了减少"每次都要扫全堆"的工作量**，但 Go 通过并发标记 + 写屏障已经把这个问题解决到"停顿不再是痛点"的程度。**既然停顿不是问题，为什么要引入分代的复杂度？**
4. **★ Go 的价值观：可预测性和简单**。"GOGC 调一下就行"和"调 20 个参数才能调好"是两种产品哲学。**Go 选择让用户不需要成为 GC 专家。**

**⚠️ 加一句边界，避免显得武断**：

> 当然这不是"分代是错的"——**ZGC 就是既分代又并发**，效果很好。"Go 不做分代"是**在它的目标（低延迟、简单、可预测）和成本之间做的取舍**，不是技术上的绝对优劣。

### 7.9 ★ 怎么排查 GC 问题（gctrace 怎么看）

**开启**：

```bash
GODEBUG=gctrace=1 ./your-service
```

**输出格式（每一行是一次 GC）**：

```
gc 14 @12.345s 1%: 0.021+1.2+0.015 ms clock, 0.17+0.9/1.1/0.02+0.12 ms cpu, 120->125->60 MB, 121 MB goal, 8 P
```

**逐段解读（★ 这个表格是本节最值钱的东西）**：

| 字段 | 含义 | 怎么判断有问题 |
| --- | --- | --- |
| `gc 14` | **第 14 次 GC** | **这个数字涨得快 = GC 太频繁** |
| `@12.345s` | 程序启动后经过的时间 | — |
| `1%` | **到目前为止，GC 占用的 CPU 时间百分比** | **★ 超过 5% 就说明 GC 压力大；超过 25% 是严重问题** |
| `0.021+1.2+0.015 ms clock` | **三个阶段的墙钟时间**：清扫终止（STW）+ **并发标记** + 标记终止（STW） | **看首尾两个数的和，就是 STW 总停顿**。这里的 STW 约 0.036ms = 36μs，**非常好** |
| `0.17+0.9/1.1/0.02+0.12 ms cpu` | 三个阶段的 **CPU 时间**（中间那段有辅助标记/后台标记的拆分） | **CPU 时间远大于墙钟时间 = 并发做得好**（多个核在并行标记） |
| `120->125->60 MB` | **堆大小：GC 开始时 → 标记结束时 → 标记结束后的存活量** | **★ 第三个数字（60MB）持续上涨 = 内存泄漏**（存活对象越来越多） |
| `121 MB goal` | **下一轮 GC 的堆目标**（到 121MB 就再 GC 一次） | **goal 很小但堆涨得快 = GC 会非常频繁** |
| `8 P` | 使用的 P 数量（= GOMAXPROCS） | — |

**★ 三种典型异常 + 对应处置**：

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| **GC 次数暴涨**（`gc` 序号涨得飞快），**`1%` 高** | **分配速率太高**（每个请求都在大量分配） | 用 **pprof `alloc_space`** 找分配热点 → 对象池 / 减少逃逸 / 复用 buffer |
| **存活量（第三个数字）持续上涨** | **内存泄漏**（map 只增不减、goroutine 泄漏、缓存无上限） | 用 **heap profile 做 diff**（见 8.4、场景题 Q2） |
| **STW（首尾两个 clock 数）变长** | **goroutine 数量过多**（栈扫描成本）、或者有**不可抢占的 goroutine**（老版本 / cgo 中） | 控制 goroutine 数量；检查 `LockOSThread` / cgo 代码 |

**其他 GC 相关调试手段**：

| 手段 | 用途 |
| --- | --- |
| `GODEBUG=gctrace=1` | 上面这些 |
| `GODEBUG=schedtrace=1000` | **每秒打印调度器状态**（G/M/P 数量、runqueue 长度、GC 次数）——**排查"goroutine 爆炸"和调度延迟很有用** |
| `runtime.ReadMemStats` / `expvar` / Prometheus `go_*` 指标 | **生产必备**：`go_gc_duration_seconds`（GC 停顿分位）、`go_memstats_heap_inuse_bytes`、`go_goroutines`、`go_gc_cycles_total`、`go_memstats_gc_cpu_fraction`（**≈ gctrace 的 `1%`**） |
| `debug.SetGCPercent` / `debug.SetMemoryLimit` | **运行时动态调整**（不用重启改 GOGC） |
| **`GODEBUG=gccheckmark=1`** | 开启 GC 正确性校验（慢，仅调试用） |

**⚠️ 生产环境的现实做法**：

> gctrace 是"**看现象**"的，生产上更实用的是**把 GC 指标接进 Prometheus 看趋势**：**`go_memstats_gc_cpu_fraction` 和 `go_gc_duration_seconds` 的 P99**。前者反映"GC 吃了多少 CPU"（>10% 就要优化分配），后者反映"GC 停顿有多长"（正常在几百微秒内）。**这两个指标如果平稳，就说明 GC 不是瓶颈，别在这儿浪费时间；如果它们和 P99 延迟曲线同步抖动，那就是 GC 的锅。**

### 7.10 ★ 结合网关场景：高并发下怎么让 GC 不影响延迟

**⚠️ 前提说明**：这一段是**"如果我来设计"的推演**，不是"我们网关当时这么做"。讲的时候用"**我会这么设计**"的口吻。

**先分清主次（这个框架本身就很加分）**：

| 影响延迟的机制 | 是不是主要矛盾 | 为什么 |
| --- | --- | --- |
| **STW 停顿** | ❌ **不是**（只有几十~几百微秒，且不随堆增长） | 已被 runtime 解决 |
| **★ Mark Assist（辅助标记）** | ✅ **是**（直接拖慢业务 goroutine） | 分配越快，罚款越重，**是"请求突然变慢"的主因** |
| **★ 标记占用 25% 的 P** | ✅ **是**（有效算力直接少 1/4） | 高 QPS 下直接体现为吞吐下降 |
| **GC 频率** | ✅ **是**（越频繁，总开销越大） | 分配速率决定 |

**★ 所以优化方向只有一句话：减少分配 + 控制堆大小 + 让 GC 跑得更少。**

| 手段 | 具体做法 | 收益 |
| --- | --- | --- |
| **★ 对象池复用 buffer** | `sync.Pool` 复用读写缓冲（4KB/32KB 分档）。**代理转发是"每请求都要 buffer"的典型场景，这是第一优先级的优化** | **直接砍掉最大的一块分配** |
| **★ 预分配 + 复用** | `bytes.Buffer` / `[]byte` 从池里取；`make([]T, 0, n)` 一次到位；**避免 `append` 反复扩容** | 减少"扩容产生的新数组"这种垃圾 |
| **★ 减少序列化分配** | 用 `sonic`/`jsoniter` 替代标准库 `json`（标准库 `encoding/json` **反射 + 大量小对象**，是网关里最常见的分配黑洞之一） | 序列化分配降 3~10 倍 |
| **★ 避免 `fmt` / 反射 / `map[string]any`** | 日志用结构化 logger（`zap`/`zerolog`），热路径用 `strconv`；**能写具体类型就不写 `any`** | 每处都能省下堆分配 + 逃逸 |
| **★ 流式转发，不整包缓冲** | 大 body（比如文件上传、SSE 流）**用 `io.Copy` 直接管道转发**，不要 `io.ReadAll` 读进内存 | **避免大对象**（大对象对 GC 更不友好：分配成本高、扫描时间长） |
| **★ 调 `GOGC` + `GOMEMLIMIT`** | **`GOGC=200~400`** 或配合 `GOMEMLIMIT` 用 off；**`GOMEMLIMIT` = 容器限额的 90%** | **GC 次数直接减半以上**，CPU 省下来给业务 |
| **降低指针密度** | 用 `[]byte`、`[]struct`（**值数组**）代替 `[]*struct`（指针数组）。**GC 是跟着指针走的，指针越少、标记越快** | 标记阶段更短、更省 CPU |
| **合批 / 削峰** | 上报类数据**攒批（batch）再写**，而不是每条一次分配 + 一次 IO | 降低分配速率（**mark assist 的触发条件就是分配速率**） |
| **控制常驻内存** | 减少"永久存活的大对象"（大缓存、大索引），**存活集越大，每轮 GC 的标记量越大** | 降低每轮 GC 的固定成本 |
| **★ 监控兜底** | 盯 **`go_memstats_gc_cpu_fraction`**（目标 < 5%）和 **GC assist 时间** | **优化前先量化，优化后能验证** |

**★ 一段可以直接背的回答**：

> 网关场景我会分两步走。**第一步是"让 GC 不是问题"**：把每请求必产生的分配砍掉 —— **读写缓冲走 `sync.Pool`、序列化换低分配的库、避免 `fmt`/反射、大 body 流式转发不整包读进内存、指针数组换值数组**。**第二步是"让 GC 跑得更少"**：**`GOGC` 调到 200~400，`GOMEMLIMIT` 设成容器限额的 90%**，把"按比例触发"变成"按内存压力触发"。
>
> 但我要强调一个容易被忽略的点：**Go 的 GC 停顿（几十微秒）不是网关延迟的主要矛盾，真正的杀手是 mark assist 和标记占用的 CPU。** mark assist 是"分配太快的 goroutine 被罚去帮忙标记"，它会**直接拖慢业务请求**，表现就是 P99 抖动。所以**优化的核心指标不是"GC 停顿多长"，而是"分配速率有多高"和"GC CPU 占比（`gc_cpu_fraction`）是多少"**。我会把 `gc_cpu_fraction` 和 `go_gc_duration_seconds` 接进监控，**目标是把 gc_cpu_fraction 压在 5% 以内**。

**⚠️ 万一被追问"你们实际调过吗"**：

> 老实说，**专门的 GC 调优我没有在生产上系统做过**，因为我们服务的量级还没到需要精调 GC 的程度。**但减少分配这件事我是有实操的** —— LoveSpouse 里对接模型和 IM 的时候，我会用对象池复用请求缓冲、避免在热路径上打结构化日志之外的 `fmt`。**GC 参数的调整我理解原理，但没在生产上线验证过效果。**

**这个回答的价值在于：承认边界 + 展示你知道"该怎么做" + 拿真实做过的部分兜底。**

## 八、pprof 与性能调优

### 8.1 一句话答案

> `pprof` 是 Go 自带的**采样式性能分析工具**，能看 **CPU、内存分配、goroutine、锁竞争、阻塞**五类问题。**定位性能问题的标准流程是：压测复现 → pprof 看火焰图找热点 → 改代码 → 再压测验证。**

### 8.2 各类 profile 速查表（★ 记住这张表）

| Profile | 采集什么 | 怎么开 | 看什么 |
| --- | --- | --- | --- |
| **CPU** | **CPU 时间花在哪些函数上**（默认采样 30s，100Hz） | `go tool pprof http://ip:port/debug/pprof/profile?seconds=30` | **火焰图最宽的叶子 = 热点** |
| **Heap** | **堆内存分配**（采样，默认每 512KB 采一个） | `go tool pprof http://ip:port/debug/pprof/heap` | **`inuse_space`：当前占用的（找泄漏）；`alloc_space`：累计分配的（找分配热点）** |
| **Goroutine** | **所有 goroutine 的调用栈** | `curl 'http://.../debug/pprof/goroutine?debug=2'` | **同一段栈重复出现很多次 = 泄漏或阻塞** |
| **Block** | **阻塞在同步原语上的时间**（channel、锁、select） | 需代码里 `runtime.SetBlockProfileRate(1)`（**有性能开销，别常开**） | 哪里在等/被等 |
| **Mutex** | **锁竞争**（谁持锁久、谁等锁久） | 需 `runtime.SetMutexProfileFraction(1)` | **竞争最激烈的锁在哪**，用于决定要不要分片 |
| **Trace** | **时间线**：调度、GC、syscall、goroutine 生命周期 | `go tool trace` | **调度延迟、GC 事件、goroutine 何时被阻塞** |

**⚠️ Block / Mutex profile 默认是关的**（有开销），**这是高频考点**：面试官问"怎么查锁竞争"，你答"上 mutex profile"但不知道要手动开，就露馅了。

**踩坑提醒**：

- **heap profile 是采样的**，不是精确值 —— **小对象的统计有偏差，但足够定位热点**。
- **`inuse_space` 和 `alloc_space` 的区别是必考题**：前者是"**此刻还活着的**"（找泄漏），后者是"**历史上分配过的总量**"（找热点）。**找内存泄漏用 inuse，找 GC 压力用 alloc。**

### 8.3 怎么在服务里接上 pprof

```go
import (
    "net/http"
    _ "net/http/pprof" // ★ 匿名导入即注册 /debug/pprof/* 路由
)

func main() {
    // ⚠️ 单独起一个端口，不要和业务端口混在一起，也不要暴露到公网
    go func() {
        _ = http.ListenAndServe("127.0.0.1:6060", nil)
    }()
    // ... 业务代码
}
```

**⚠️ 安全提醒（说出来很加分）**：

> **pprof 端点会泄露大量内部信息（调用栈、内存内容、甚至源码片段），绝对不能暴露在公网。** 我的做法是**绑定 127.0.0.1 或者独立的内网端口**，通过跳板机/端口转发访问，或者加一层鉴权中间件。**这个点在做"安全网关"的公司面试里提出来，非常对味。**

**命令行方式（不引入 net/http）**：

```go
import "runtime/pprof"

f, _ := os.Create("cpu.prof")
pprof.StartCPUProfile(f)
defer pprof.StopCPUProfile()
```

### 8.4 ★ 火焰图怎么看 + 常见瓶颈模式

**怎么生成**：

```bash
go tool pprof -http=:8080 http://ip:port/debug/pprof/profile?seconds=30
# 浏览器打开后选 Flame Graph
```

**★ 看火焰图的三条规则（很多人的误区）**：

| 规则 | 说明 |
| --- | --- |
| **① 横轴是"采样占比"，不是时间** | 横向越宽 = 这个函数占用的 CPU 越多。**从左到右的顺序没有时间含义**（这点和"时间线"完全不同） |
| **② 纵轴是调用栈深度** | 下面是被调用者，上面是调用者（父在下、子在上的画法各家不同，看颜色和宽度） |
| **③ 找"宽而平坦的叶子"** | **最上面那些又宽、又没有子节点的框，就是真正烧 CPU 的地方**。如果宽框下面还有很多子框，说明时间花在更深的地方 |

**★ 常见瓶颈模式对照表（背这张表，面试直接说）**：

| 火焰图特征 | 说明 | 处置 |
| --- | --- | --- |
| **`runtime.mallocgc` / `runtime.gcWriteBarrier` 很宽** | **分配太多，GC 压力大** | 对象池、减少逃逸（见 7.10） |
| **`runtime.gopark` / `runtime.park_m` / `sync.(*Mutex).Lock` 宽** | **锁竞争或 channel 阻塞严重** | 分片、减少临界区、Mutex profile 定位具体锁 |
| **`syscall.Syscall` / `net.(*netFD).Read` 宽** | **系统调用太多**（小包多次读写） | 加大缓冲、合并写、批量、`bufio` |
| **`encoding/json` / `reflect.*` 宽** | **序列化太重** | 换 sonic/jsoniter，或减少序列化次数 |
| **`fmt.*` / `Sprintf` 宽** | **格式化的隐式分配 + 反射** | 换 `strconv`、结构化日志 |
| **`runtime.memmove` / `copy` 宽** | **数据拷贝太多** | 减少拷贝、零拷贝、`io.CopyBuffer` |
| **`runtime.futex` / `os/signal` 宽** | 调度/上下文切换开销 | 检查 goroutine 数量是否失控 |
| **`runtime.scanobject` / `runtime.gcDrain` 宽** | **GC 标记本身占用 CPU** | 减少存活对象、降低指针密度 |

**★ 一句话总结这个表**：**火焰图上看不到你的业务逻辑，只看到 runtime / 系统调用 / 序列化，就说明瓶颈不在业务算法，而在"基础设施开销"上。**

### 8.5 benchmark 写法

```go
var sink []byte // ★ 包级变量，防止编译器把没被使用的计算结果优化掉

func BenchmarkForward(b *testing.B) {
    // 准备阶段（不计入计时）
    req := makeRequest()
    buf := make([]byte, 0, 4096)

    b.ReportAllocs()      // ★ 报告每次操作的分配次数和字节数
    b.ResetTimer()        // ★ 重置计时器，把准备时间排除

    b.RunParallel(func(pb *testing.PB) { // ★ 并发压测（模拟多核）
        for pb.Next() {
            sink = forward(req, buf)
        }
    })
}
```

**运行与解读**：

```bash
go test -bench=. -benchmem -count=10 -cpuprofile=cpu.prof -memprofile=mem.prof ./...

# 输出：
# BenchmarkForward-8   1000000   1234 ns/op   512 B/op   8 allocs/op
#                     ↑次数      ↑单次耗时    ↑单次字节  ★↑单次分配次数
```

| 参数 | 含义 |
| --- | --- |
| `-benchmem` | **显示 B/op 和 allocs/op** —— **这两个数比 ns/op 更值得优化** |
| `-count=10` | 跑 10 次，**取统计值而不是单次结果**（单次结果抖动很大，不可信） |
| `-benchtime=3s` | 延长单次运行时间（默认 1s，太短误差大） |
| `-cpuprofile` / `-memprofile` | **直接采 profile**，用来定位为什么慢 |
| `-benchstat`（外部工具） | **对比前后两次 benchmark 的差异是否显著** —— `benchstat old.txt new.txt` |

**⚠️ 三个必知的坑**：

1. **编译器可能把整个 benchmark 优化掉** → **把结果赋给包级变量（`sink`）**。
2. **准备代码要 `b.ResetTimer()`**，否则热身开销算进去了。
3. **单次 benchmark 结果不可信** → **`-count=10` + `benchstat` 看统计显著性**。**优化前后的差异小于 5% 时，很可能只是噪音。**

**回答模板**：

> 我写 benchmark 有个习惯：**第一版永远先看 `allocs/op`，不看 `ns/op`**。因为在 Go 里**分配次数基本决定了性能上限** —— 分配少的地方，就算算法写得笨一点也不会慢；分配多的地方，算法再漂亮也会被 GC 拖垮。所以我优化的时候是**先降 allocs/op，再看 ns/op**，最后用 `benchstat` 对比确认优化是真实的（不是抖动）。

### 8.6 逃逸分析 + pprof 配合（定位问题的组合拳）

**标准流程**：

```
① 压测发现 QPS 上不去 / P99 抖动 / CPU 高
② go tool pprof -http=:8080 http://ip:port/debug/pprof/profile?seconds=30
③ 看火焰图：runtime.mallocgc 是不是很宽？
     ├─ 是 → 分配问题 → 继续 ④
     └─ 否 → 是锁/系统调用/序列化问题 → 查 Mutex profile / 具体函数
④ go tool pprof -sample_index=alloc_space http://ip:port/debug/pprof/heap
   ★ 找到"哪个函数分配最多"（按字节 or 按对象数都看一遍，两个维度经常不一样）
⑤ 对那个函数跑 go build -gcflags="-m" 看逃逸报告，找到为什么它上了堆
⑥ 改代码（对象池 / 避免 interface / 预分配 / 换成值类型）
⑦ 重新压测 + benchstat 对比，确认收益
```

**⚠️ 一个高频追问**：*怎么区分"分配热点"和"内存泄漏"？*

> **`alloc_space` 高但 `inuse_space` 平稳** → **分配热点**（东西分得多但都及时释放了，问题在 GC 压力，优化方向是减少分配）。
> **`inuse_space` 持续上涨** → **内存泄漏**（东西分出去就没还回来，优化方向是找谁在持有引用）。
> **这两个问题的解法完全不同，所以第一步一定是先看 `inuse` 还是 `alloc` 有问题。** 我一般会**隔几分钟采两次 heap，用 `-base` 做差**：`go tool pprof -base base.prof cur.prof`，**差值里最大的那几行就是增长源** —— 这个方法找内存泄漏非常有效。

## 九、★ 高并发设计方法论（本文档第二大重点）

### 9.1 通用手法（九板斧）

**⚠️ 这一段要按"我看到问题 → 我会选哪个手段 → 为什么"来讲，不要罗列名词。** 面试官最反感的就是背名词。

| 手法 | 解决什么 | 典型落地 | 代价 / 坑 |
| --- | --- | --- | --- |
| **① 缓存** | **减少重复计算 / 重复查库** | 本地缓存（`bigcache`/自建 LRU）→ Redis → DB；**多级缓存** | **一致性**（更新策略、过期策略）；**缓存穿透/击穿/雪崩**；**本地缓存必须设上限**（否则就是内存泄漏） |
| **② 异步** | **削峰、解耦、缩短响应时间** | 写操作先落 MQ 再异步处理；**响应只做必要的事** | **最终一致性**、**消息幂等**、**MQ 堆积监控** |
| **③ 池化** | **减少创建/销毁开销** | `sync.Pool`（内存）、连接池（DB/Redis/HTTP）、**goroutine worker pool** | **池大小要匹配下游承受能力**（池开太大等于把压力全推给下游） |
| **④ 批处理** | **摊薄单次开销** | Redis pipeline / `MGET`、DB 批量 `INSERT`、日志攒批、**合并读请求** | **延迟增加**（要等攒够），要设最大等待时间 |
| **⑤ 减少锁竞争** | **提升多核扩展性** | **分片（sharding）**、原子操作、**COW（写时复制）**、无锁队列 | 分片后**跨片操作变复杂**；COW 的写放大会放大内存 |
| **⑥ 限流** | **保护自己不被压垮** | **令牌桶**（允许突发）/ **漏桶**（恒定速率）/ 滑动窗口；**Sentinel** | **要按维度限**（用户/IP/接口/租户）；**限流阈值必须压测过才知道** |
| **⑦ 降级** | **有损服务，保核心** | 关非核心功能、返回兜底数据、**只读模式** | **要能一键开关**（配置中心）、**要演练过** |
| **⑧ 预热** | **避免冷启动抖动** | 缓存预热、连接池预热、**JIT/GC 预热**（Go 里是让编译器和栈先跑起来） | 预热数据要选得对 |
| **⑨ 背压（Backpressure）** | **别把请求堆在内存里** | **有界队列 + 满了就拒绝**；`semaphore` 限并发 | **拒绝策略要明确**（返回 429 还是排队）；**排队时间不能算进超时预算** |

**★ 一段能显示"架构思维"的总纲**：

> 我做高并发设计的时候，思路是**从后往前推**：**先看最底层（DB/下游）能扛多少 → 再决定中间要加几层缓冲和削峰 → 最后才看接入层怎么扛。** 因为**高并发系统的瓶颈永远在最慢的那一环**，接入层再怎么优化，DB 撑不住照样雪崩。所以我的优先级是：**① 保护后端（限流、池化、批处理）→ ② 减少后端压力（缓存、异步）→ ③ 提升前端吞吐（减少锁竞争、减少分配、扩容）。**

### 9.2 ★ 连接数管理：C100K 问题

**一句话答案**：C100K（十万并发连接）的瓶颈**从来不是"连接数"本身**，而是**文件描述符、内存、内核参数**这三样。**Go 用 netpoller 解决了"线程模型"这一层，但另外三样必须自己调。**

**★ 完整检查清单（这张表能直接答"怎么支撑 10 万连接"）**：

| 层次 | 限制项 | 怎么调 |
| --- | --- | --- |
| **① 文件描述符** | **每个连接一个 fd，默认 `ulimit -n` 只有 1024** | `ulimit -n 1000000` + `/etc/security/limits.conf` 的 `nofile`；**容器里还有 docker/systemd 的 `LimitNOFILE`**（这一层最容易漏） |
| **② 内核参数** | `net.core.somaxconn`（accept 队列）、`net.ipv4.tcp_max_syn_backlog`（半连接队列）、`ip_local_port_range`（**作为客户端连下游时的源端口数**） | 调到 **65535 / 65535 / "1024 65535"**；`tcp_tw_reuse=1`（注意：**不是 tcp_tw_recycle，那个在新内核已被移除**） |
| **③ 内核内存** | **每个 socket 都有读写缓冲区（`tcp_rmem`/`tcp_wmem`）**，这是连接数最硬的约束 | 单连接内核侧约 **4~16KB**（可以调小到 4KB）；**10 万连接 ≈ 1~2GB 内核内存**（**这部分不计入容器内存限额，容易被忽视**） |
| **④ 应用内存** | **每个连接在 Go 侧的占用** | 见 2.9 的估算表：**约 15~30KB/连接** → **10 万连接 ≈ 1.5~3GB** |
| **⑤ 线程 / GMP** | **不需要担心**（netpoller，见 9.3） | — |
| **⑥ 单机上限** | 经验值：**Go 服务单机 1~5 万连接比较舒服** | **超过就水平扩展，别硬堆单机**（单机故障域太大，也无法无损发布） |

**⚠️ 一个"加分项"提醒**：

> **容器内存限额往往漏算内核 socket 缓冲。** 比如给容器限 4GB、应用自己算下来 2GB 内存，看起来有富余 —— 但**10 万连接的内核 socket 缓冲可能有 1.5GB，而且在 host 内核里统计**，可能导致**宿主机内存紧张甚至节点驱逐**。所以我会额外关注**宿主机级别的内存水位**，而不是只看容器的 cgroup 数字。

### 9.3 ★ Go netpoller 原理（为什么 Go 能做到高并发连接）

**★ 这是本章最重要的原理，必须能画着讲。**

**传统 thread-per-connection 的困境**：

```
每个连接一个线程 → 1 万个连接 = 1 万个线程
问题：① 每个线程栈 1~8MB，内存直接爆
      ② 线程切换要陷入内核，1 万个线程的上下文切换把 CPU 吃光
      ③ 大部分线程都在阻塞等数据 —— 纯粹的浪费
```

**Go 的方案：netpoller（网络轮询器）**

| 步骤 | 发生了什么 |
| --- | --- |
| **① 非阻塞 fd** | Go 创建网络连接时，**把 fd 设成非阻塞**（`O_NONBLOCK`） |
| **② 读到没数据** | goroutine 调用 `Read`，内核立刻返回 **`EAGAIN`**（"没数据，别等了"），**而不是把 G 挂起** |
| **③ G 主动挂起** | runtime 拦截到这个错误 → **把当前 G 挂到该 fd 对应的 `pollDesc` 上**（`pollDesc` 里只有两个槽位：`rg`（读等待者）和 `wg`（写等待者））→ **`gopark` 挂起 G** |
| **④ M 继续干活** | **M 完全没有阻塞**，立刻转去跑其他 G。**注意：G 让出了 M，但没有让出 P**（这就是 2.5 里说的"网络 IO 不需要 handoff"） |
| **⑤ 事件就绪** | 任何有空闲的 M 在 `findRunnable` 里**调一次非阻塞的 `netpoll(0)`**（`epoll_wait` 超时 0），拿到就绪的 fd 列表 → **从 `pollDesc` 里取出等待的 G，置为 runnable，扔进 P 的本地队列** |
| **⑥ G 被唤醒继续** | G 重新被调度，**重试刚才的 Read（这次能读到数据了）** |
| **⑦ 兜底** | 如果所有 M 都在忙，**sysmon 会主动调 netpoll**，保证网络事件不被饿死；如果完全没活，**最后一个 M 会阻塞在 `epoll_wait` 上**（带超时，`pollUntil` 用来兼顾定时器） |

**★ 结论（这段是答"为什么 Go 高并发"的标准答案）**：

> **因为"等网络"这件事在 Go 里不消耗任何 OS 资源。** 十万个连接里，99999 个在等数据，**它们只是挂在 epoll 上的 `pollDesc` 里的一个指针**，**不占线程、几乎不占 CPU**。真正消耗资源的是"正在处理数据的那几十个连接"。所以 **Go 的服务能同时持有十万连接，却只用几十个 OS 线程。**
>
> **这也是为什么 Go 的 HTTP 服务不用写任何异步代码就天然支持高并发** —— 你用"同步阻塞"的写法（`data, err := conn.Read(buf)`），runtime 在底下自动帮你变成了"异步 + 回调"的模型。**编程模型是同步的，执行模型是异步的** —— 这是 Go netpoller 最大的设计价值。

**⚠️ 三个容易被追问的点**：

| 追问 | 回答 |
| --- | --- |
| *epoll 用什么模式？* | **Go runtime 自己维护 `pollDesc` 状态机来避免重复唤醒，具体用 ET 还是 LT 是实现细节，业务代码不需要关心。** （**别赌细节，这句答法既诚实又专业**） |
| *那文件 IO 呢？* | **⚠️ 坑在这里：普通文件的读写 Go 没有用 netpoller，是真正阻塞的 syscall**（因为普通文件 IO 在 Linux 上本来就是"立刻返回"的，epoll 也不支持普通文件）。所以**大量文件 IO 会阻塞 M**，此时会触发 handoff。**如果 M 全被文件 IO 占满，会创建新 M，可能导致线程数暴涨** —— 这是 Go 服务里"线程数莫名很多"的常见原因。**解决：文件 IO 用带缓冲的读写 + 控制并发数。** |
| *`database/sql` 也走 netpoller 吗？* | **走**（底层是网络连接），**所以慢 SQL 不会阻塞线程，但会占着连接**。**连接池大小决定了能并发多少慢查询** —— 池子太小，请求全在等连接（**这就是为什么"慢 SQL 会拖垮整个服务"，不是因为占线程，是因为占池子**）。 |

### 9.4 ★ 结合 LoveSpouse 长连接网关

**⚠️ 前提**：这一段是**"我设计/我负责的部分"**，可以说"我负责对话链路和实时语音，连接管理是团队一起做的"，**具体量级务必填【】**。

**① 连接管理模型**

**★ 每个连接两个 goroutine（这是最清晰的模型）**：

```go
func serveConn(conn *websocket.Conn) {
    // 每条连接一个独立 context，连接关闭时 cancel 掉所有下游调用
    ctx, cancel := context.WithCancel(rootCtx)
    defer cancel()

    sendCh := make(chan []byte, 64) // ★ 有界！满了就说明消费跟不上

    // 写 goroutine：唯一允许写 conn 的人
    go func() {
        ticker := time.NewTicker(30 * time.Second) // 应用层心跳
        defer ticker.Stop()
        for {
            select {
            case msg := <-sendCh:
                if err := conn.WriteMessage(websocket.TextMessage, msg); err != nil {
                    cancel() // ★ 写失败 → 立刻取消整条连接
                    return
                }
            case <-ticker.C:
                _ = conn.WriteControl(websocket.PingMessage, nil, time.Now().Add(5*time.Second))
            case <-ctx.Done():
                return
            }
        }
    }()

    // 读 goroutine（当前 goroutine）
    for {
        _, msg, err := conn.ReadMessage()
        if err != nil {
            cancel() // ★ 读失败（客户端断开）→ 取消，写 goroutine 也跟着退出
            return
        }
        handleMessage(ctx, msg)
    }
}
```

**★ 讲这段时的三个加分点**：

| 设计 | 为什么 |
| --- | --- |
| **只有一个 goroutine 写 conn** | **多 goroutine 并发写同一个 WebSocket 会字节交错，消息直接损坏。** 用 channel 把"写"的所有权交给一个 goroutine，从设计上消除这个 bug |
| **`sendCh` 有界（64）** | **慢客户端会让队列积压**。有界 + 满了就断开，**把"内存无限增长"变成"断开慢客户端"** —— 这是**背压**的正确做法 |
| **每条连接一个 context** | **连接断开 → cancel → 所有在途的模型调用、IM 调用、DB 操作立刻中止**（见 5.6）。**这是省资源的关键，尤其在付费按量调用模型的场景** |

**② 心跳保活**

| 层次 | 做法 | 说明 |
| --- | --- | --- |
| **TCP 层** | `SetKeepAlive(true)` + `SetKeepAlivePeriod` | **系统默认 2 小时，太长了，基本没用** —— 移动网络下 NAT 超时往往只有几分钟 |
| **★ 应用层（主力）** | **服务端主动 ping（30~60s）+ 客户端 pong 超时判定** | **为什么服务端主动**：能同时做两件事 —— **探测死连接** + **刷新 NAT/中间设备的映射表** |
| **超时踢除** | **连续 2 次 pong 没收到（约 60~120s）→ 关闭连接** | **没有这一步，连接泄漏就发生了**：客户端掉线（拔网线/切网络）**不会发 FIN**，服务端会一直以为连接活着，**goroutine 和内存永远不释放**（这就是场景题 Q2 的头号元凶） |
| **连接数统计** | 原子计数器（**注意分片避免 false sharing**，见 4.4） | 上监控告警：连接数突降 = 大量断线；连接数持续上涨 = 泄漏 |

**③ 广播优化：写扩散 vs 读扩散**

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **写扩散（Push / fan-out on write）** | 消息来了，**主动写到每个订阅者的发送队列** | **实时性最好**（消息一到就走） | **N 个订阅者 = N 次写**；**大房间/热点广播时 CPU 和内存暴涨** | **在线用户少、要求实时**（IM 单聊、小群） |
| **读扩散（Pull / fan-out on read）** | 消息**只写一份到共享存储**，客户端**自己拉或轮询** | 写成本 O(1)，**不怕大房间** | **实时性差**（要等下次拉）；**需要消息 ID/游标管理** | **大房间、直播弹幕、公告广播** |

**★ 实践中的结论（说出来像做过）**：

> 真实系统一般是**混合**的：**单聊/小群用写扩散（要实时），大群/公告用读扩散（扛得住量）。** 但**我在长连接服务上更关心的是"广播的扇出写"这个动作本身**：
>
> 1. **广播不能在一个 goroutine 里串行 for 循环写所有连接** —— 一个慢客户端会把整个广播卡住。**正确做法是把消息投递到每个连接的 `sendCh`（非阻塞投递，`select` + `default`），投不进去就说明这个客户端慢了 → 丢消息或断开它。**
> 2. **投递循环本身要做分片**：几万个连接的投递，可以按连接 ID 分片并行投递（多个 goroutine 各投一片），**避免单个 goroutine 成为瓶颈**。
> 3. **消息体只序列化一次**，所有连接共享同一个 `[]byte`（**注意：不能修改它，只读共享是安全的**）。**如果每个连接都序列化一遍，CPU 直接打满。**

**④ 跨实例路由**

> 长连接是**有状态**的（用户连在哪个实例上决定了消息发给谁）。处理方式：
>
> - **连接状态外置 Redis**：`连接ID → 实例ID` 的映射 + 会话状态都放 Redis，**服务本身无状态，可以随意扩容重启**；
> - **投递时先查路由表**：目标用户不在本实例 → **通过 Redis Pub/Sub 或 MQ 转发给持有该连接的实例**；
> - **实例下线时**：**先把路由表里自己的记录清掉（或标记为不可用）**，再优雅关闭；
> - **⚠️ 一致性**：路由表可能有短暂不一致（实例刚挂、映射还没清）→ **消息投递要设计成"投不到就落离线消息"，投递本身做成幂等的**。**不要指望路由表强一致。**

**⑤ 优雅关闭（无损发布，这个点很加分）**

```go
// 捕获信号 → 摘流量 → 排空连接 → 退出
sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, syscall.SIGTERM, syscall.SIGINT)
<-sigCh

// ★ ① 先摘流量：从注册中心/路由表下线，停止接收新连接
deregister()

// ★ ② 给已建立的连接发"服务重启"通知，让客户端主动重连
broadcastGoingAway()

// ★ ③ 等待连接排空（带超时），而不是直接退出
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
srv.Shutdown(ctx) // 停止接受新连接，等在途请求完成

// ★ ④ 超时了还没排空 → 强退（但要确保状态已持久化）
```

**⚠️ 回答时的诚实边界**：**上面这些"① 摘流量 ② 通知 ③ 排空"是标准做法，但不要声称自己在 LoveSpouse 全做过。** 说法：**"优雅关闭这块我们做了基础的（监听 SIGTERM、等连接处理完），但'从注册中心摘流量、通知客户端重连'这种完整的无损发布流程，是我理解的正确做法，我们当时的量级还没做到这一步。"**

### 9.5 ★ 压测：wrk / ab / ghz 与结果解读

**工具选择**：

| 工具 | 协议 | 特点 | 用法 |
| --- | --- | --- | --- |
| **wrk** | HTTP | **★ 首选**：多线程 + epoll，**单机就能压出很高的 QPS**；支持 Lua 脚本定制请求 | `wrk -t12 -c400 -d30s --latency -s post.lua http://host/api` |
| **ab** | HTTP | 简单直观，**⚠️ 默认不用 keep-alive（要加 `-k`）**，**单线程性能差**，不适合压高并发 | `ab -n 100000 -c 1000 -k http://host/api` |
| **ghz** | **gRPC** | **gRPC 专用（我们的 POS 项目就适合用这个）** | `ghz --insecure --proto ./api.proto --call pkg.Svc/Method -d '{"id":1}' -c 50 -n 20000 127.0.0.1:50051` |
| **k6 / vegeta** | HTTP | 脚本化更强，适合复杂场景编排 | — |

**★ 怎么读压测结果（这段比工具用法重要）**：

| 指标 | 含义 | 怎么看 |
| --- | --- | --- |
| **QPS / RPS** | 吞吐量 | **一定要和"错误率"一起看** —— **QPS 高但错误率 10% 是没有意义的** |
| **Latency 分布** | 延迟 | **看 P50 / P90 / **P99** / **P999**，不看平均值**（见下） |
| **★ 错误率** | 失败请求占比 | **超过 0.1% 就要查**；压测中出现的超时/连接拒绝都算 |
| **CPU / 内存 / GC** | 资源曲线 | **★ 压测时必须同时看服务端的指标**，否则你不知道 QPS 是被什么限制住的（CPU 100%？GC？锁？DB？） |

**★ 为什么看 P99 / P999 而不是平均值（必答）**：

> **平均值会掩盖长尾。** 假设 100 个请求里 99 个是 10ms，1 个是 500ms，**平均值只有 14.9ms，看起来一切正常**，但那个 500ms 的请求就是用户体验最差、最容易导致超时重试、最容易引发雪崩的那个。
>
> **更重要的是：在高并发下，P99 和平均值之间的差距会自我放大** —— 慢请求会占着连接/线程/资源不放（**Little's Law：并发 = QPS × 延迟**），延迟升高 → 占用资源时间变长 → 需要的并发数变多 → 排队更严重 → 延迟进一步升高。**这就是"雪崩"的数学形态。** 所以**P99 和 P999 才是决定系统稳定性的指标**，很多公司直接拿 P999 做 SLO。

**⚠️ 压测的三个常见错误（说出来显得懂行）**：

| 错误 | 后果 |
| --- | --- |
| **压测机和被测服务在同一台机器** | 压测机自己把 CPU 吃掉了，**测出来的 QPS 是假的** |
| **没有压到瓶颈就停了** | 只验证了"能用"，**没找到拐点**（QPS 上不去的那一点、延迟开始飙升的那一点） |
| **不监控服务端指标** | **不知道瓶颈在哪** —— 可能是 DB、可能是连接池、可能是 GC，光看客户端指标没意义 |

**★ 正确的压测方法（阶梯式）**：

> 我的做法是**阶梯加压**：从低并发开始，**每一档跑够足够的时间（至少 1~2 分钟，让 GC 和连接池达到稳态）**，记录 QPS / P99 / 错误率 / 服务端 CPU 和 GC 指标，**一直加到"错误率上升或 P99 突然抬起来"为止**。**那个拐点就是系统的实际容量**，而我能接受的线上水位一般是**拐点的 50%~70%**（留出突刺和故障切换的余量）。

### 9.6 容量评估方法论

**★ 核心公式（Little's Law）**：

> **并发数 L = 到达率 λ（QPS）× 平均处理时间 W（秒）**
>
> 例：QPS = 1000，平均耗时 50ms → **L = 1000 × 0.05 = 50 个并发请求**。
> **反过来用**：如果你有 200 个 worker，每个请求 50ms，**最大吞吐 = 200 / 0.05 = 4000 QPS**。

**为什么这个公式重要**：**它把"并发"和"吞吐"和"延迟"三个量绑在一起了**。任何两个值变了，第三个必然跟着变。**这也解释了"为什么延迟升高会导致系统雪崩"**（W 变大 → 同样 worker 数下吞吐 L/W 变小 → 请求堆积 → W 更大）。

**★ 五维容量评估表**：

| 维度 | 估算方法 | 例（假设：10 万连接、峰值 5 万 QPS、平均请求 2KB、响应 8KB） |
| --- | --- | --- |
| **① 连接数** | 业务模型 × 在线率 | 10 万连接 |
| **② 带宽** | `QPS × (请求大小 + 响应大小)` | 50000 × 10KB = **500 MB/s ≈ 4 Gbps** → **必须万兆网卡 + 多机分摊** |
| **③ 内存** | `连接数 × 单连接占用` + `QPS × 单请求临时对象` + 缓存 | 10 万 × 25KB = **2.5 GB**（连接）+ 缓存 + 池 |
| **④ CPU** | **压测测得"单核 QPS"→ 反推核数**（**唯一可信的方法**） | 若单核能转发 5000 QPS → 5万/5000 = **10 核 → 留 1.5~2 倍余量 → 16~20 核** |
| **⑤ fd / 端口** | `连接数 × 2`（服务端 + 到下游的连接） | 10 万 × 2 = **20 万** → `ulimit -n` 至少 30 万 |

**⚠️ 三条必须记住的原则**：

1. **CPU 只能靠压测，不能靠算。** "一个请求大概多少 CPU 周期"这种算法永远不准（**编译器优化、cache 命中率、GC 开销、锁竞争都会大幅改变结果**）。**先压测拿到"单核 QPS"这个基准数，再线性外推 —— 而且外推要打折扣，因为并行度上去后锁竞争和 GC 会变得更糟。**
2. **内存要算"最坏情况"**：`连接数 × 单连接最大占用`（**不是平均**），因为**内存是尖峰杀手**。
3. **留余量**：线上水位控制在压测容量的 **50%~70%**。**余量是给这三件事的：流量突刺、实例故障（少一台要能扛住）、以及扩容期间的时间窗口。**

**★ 一段可以直接背的"架构师式回答"**：

> 我评估容量会**先定指标再算数**：**连接数、QPS、延迟目标（P99 多少毫秒）、可用性目标**。然后**从压测拿基准值**（单核 QPS、单实例连接数上限），**再反推需要多少实例**。
>
> 一个例子：如果要支撑 **10 万连接 + 5 万 QPS + P99 50ms**，我会这样推：带宽 4Gbps → 单机万兆网卡不够，**至少 2~3 台**；内存按每连接 25KB 算要 2.5GB，加缓存和池，**单机 8G 内存够但只能放 2~3 万连接**；CPU 按压测基准反推，**留 2 倍余量**。
>
> **结论是：单机支撑 1~3 万连接比较舒服，10 万连接要 4~6 台组成集群。** 而这个集群又带来新问题：**负载均衡（L4 还是 L7）、连接的状态怎么共享（外置 Redis）、怎么无损发布（先摘流量再排空连接）**。**架构设计就是这样一层推一层的 —— 解决了容量问题，就冒出了分布式状态问题，再解决就是一致性问题。**

### 9.7 附：Go 工程化规范速答

JD 提了"熟悉 Go 工程化开发规范"。这块**不用长篇大论，记住下面这张表就能应付**（详细的话术见 `02_岗位解读与架构话术.md`）。

| 主题 | 做法 |
| --- | --- |
| **项目分层** | `cmd/`（入口）· `internal/`（业务，**外部不可导入**）· `pkg/`（可复用库）· `api/`（proto/接口定义）· `configs/`· `deploy/` |
| **错误处理** | **`errors.Is` / `errors.As` / `%w` 包装**（保留错误链）；**不用 `panic` 做业务错误**（只在初始化/不可恢复时 panic）；**错误要带上下文**（`fmt.Errorf("get user %d: %w", id, err)`） |
| **依赖注入** | **构造函数注入**（`NewService(store, cache, logger)`），**不用全局变量**；接口定义在**使用方**（Go 的惯例：**接口属于调用者，不属于实现者**） |
| **并发安全** | **谁创建谁关闭**（channel/goroutine 的生命周期责任明确）；**所有 goroutine 必须有退出条件**；`ctx` 一路透传 |
| **日志** | **结构化日志（zap/zerolog）**；**热路径避免 `fmt.Sprintf`**；**关键链路带 trace id** |
| **单元测试** | **表驱动测试**；**`-race` 必开**；并发代码用 `goleak` 断言无 goroutine 泄漏；**mock 用接口而非框架** |
| **CI 检查** | `go vet`、`golangci-lint`、`go test -race`、**`staticcheck`** |
| **配置** | **配置与代码分离**，**支持环境变量覆盖**（12-factor）；配置热更新用 `atomic.Pointer[Config]` 整体替换（**读路径无锁**） |
| **接口设计** | **小而专注**（1~3 个方法，如 `io.Reader`）；**用 `context.Context` 作为第一个参数**；返回 `error` 永远是最后一个 |
| **版本管理** | 语义化版本；`go.mod` 里 **`replace` 只能临时用**；**锁死依赖版本 + 定期升级** |

**★ 配置热更新那段代码（很短，可以讲）**：

```go
var cfg atomic.Pointer[Config] // ★ Go 1.19+；旧版本用 atomic.Value

func Get() *Config { return cfg.Load() } // 读路径完全无锁

// 配置中心（etcd/Nacos）watch 到变更时整体替换
func onConfigChange(newCfg *Config) { cfg.Store(newCfg) }
```

> **要点**：**用"整体替换"而不是"逐个字段改"** —— 这样读方永远看到一个**完整一致的快照**，不需要加锁，也不会读到"改了一半"的配置。**这个模式在网关里特别重要，因为策略配置会被每个请求读取。**

### Q1：网关要支撑 10 万并发连接，Go 这边怎么设计？

**面试官意图**：这是**本岗位最核心的开放题**。他其实在一次性验证三件事：① 你懂不懂 Go 高并发的底层（netpoller / GMP / 内存）② 你有没有**体系化的容量思维**（会不会算数）③ 你知道不知道**网关特有的问题**（长连接、协议解析、无损发布）。**这题答好，这个岗位就有五成把握。**

**答题框架（六层，按顺序讲）**：

```
① 先算账（容量评估）→ ② 单机怎么扛住（netpoller + 内存 + 内核参数）
→ ③ 集群怎么分（负载均衡 + 连接路由）→ ④ 网关特有难点（协议/缓冲/流式）
→ ⑤ 怎么保证不出事（限流/背压/监控）→ ⑥ 怎么发布和容错
```

| 层次 | 要点 |
| --- | --- |
| **① 容量评估** | 用 Little's Law 和 9.6 的五维表，**先算带宽、内存、fd、CPU**。**算出"单机 1~3 万连接比较舒服"→ 结论是 4~6 台集群，而不是硬堆单机** |
| **② 单机优化** | **Go 侧**：netpoller（见 9.3）、`GOMAXPROCS`（容器注意 automaxprocs）、`GOGC` 调优、`sync.Pool` 复用 buffer、**每连接 2 个 goroutine**；**系统侧**：`ulimit -n`、`somaxconn`、`tcp_rmem/wmem`、**关闭不必要的 TIME_WAIT 堆积** |
| **③ 集群与负载均衡** | **L4（LVS/DPVS）打散连接 + L7 网关集群**（**长连接场景 L4 比 L7 好**，因为 L7 负载均衡会**终止并重建连接**，破坏长连接）；**连接状态外置 Redis**，实现跨实例路由与无状态扩容 |
| **④ 网关特有难点** | **协议解析**（HTTP/1.1 keep-alive 的连接复用、H2 的多路复用、**WebSocket 的升级与长驻**、**SSE 的流式转发**）；**缓冲策略**（`sync.Pool` 复用、**大 body 流式转发不整包读**）；**超时链**（连接空闲超时、请求超时、下游超时、**必须保证内层超时 < 外层超时**） |
| **⑤ 保护机制** | **限流**（按连接/租户/接口维度，令牌桶）、**背压**（每连接有界发送队列，满了断慢客户端）、**熔断**（下游故障快速失败）、**连接数上限硬保护**（到达上限直接拒绝新连接，**而不是让内存涨到 OOM**） |
| **⑥ 发布与容错** | **优雅关闭**（先摘流量 → 通知客户端重连 → 排空连接 → 退出）；**多可用区部署**；**健康检查**（不只是端口活着，要检查"还能不能正常处理请求"） |

**★ 结合候选人的具体答法**：

> 我先说一个前提：**我没有做过网关产品，所以这一题我按"如果我来设计"的思路讲，中间我会对照我做过的长连接服务。**
>
> **第一步我会算账**。10 万连接、假设峰值 5 万 QPS、平均请求 2KB、响应 8KB，那带宽就是 `50000 × 10KB = 4Gbps`，**单机万兆网卡打满都没有余量，所以必须多机**；内存按每连接 25KB 估（goroutine 栈 + 读写缓冲 + 连接结构 + 业务状态）要 2.5GB；**CPU 只能靠压测定基准，比如单核转发 5000 QPS，5 万 QPS 就需要 10 核，留 2 倍余量就是 20 核**。**所以结论是：单机 1~3 万连接、4~6 台集群，而不是硬刚单机 10 万。**
>
> **第二步是单机怎么扛住 2 万连接。** 这块 Go 本身帮了大忙 —— **netpoller 让"等数据"不占线程**，2 万个连接里 99% 在等 IO，实际只有几十个 M 在干活。我要做的是：**每连接一个读 goroutine + 一个写 goroutine**、**读写缓冲走 `sync.Pool`**、**`GOGC` 调到 200~400 配合 `GOMEMLIMIT`**、**容器里用 automaxprocs 修 GOMAXPROCS**。系统侧要调 `ulimit -n`（10 万连接至少 20 万 fd）、`somaxconn`、**并且注意内核 socket 缓冲的内存不在容器限额里统计**。
>
> **第三步是集群。** **长连接场景我倾向用 L4 负载均衡而不是 L7** —— 因为 L7 会终止连接再重建，**把长连接打散了，心跳和状态全乱**。连接状态外置 Redis，记录"连接 ID → 实例 ID"，实例无状态，可以随便扩容重启。
>
> **第四步是网关特有的坑**，这也是我觉得和普通长连接服务最不一样的地方：**① 协议解析**（要区分 HTTP/1.1 的 keep-alive、HTTP/2 的多路复用、WebSocket 的 upgrade、SSE 的流式，**每种协议的超时和缓冲策略都不一样**）；**② 超时链**（连接超时、请求超时、下游超时，**必须保证内层比外层短，否则永远是你的超时先触发，日志上看不到下游真正的错误**）；**③ 保护**（限流 + 每连接有界队列做背压 + **连接数硬上限，到顶了直接拒绝而不是 OOM**）。
>
> **第五步是发布。** 长连接服务的发布是最麻烦的 —— **不能直接重启，那 2 万个连接全断了**。要**先摘流量（停止接受新连接）→ 给客户端发通知让它重连 → 等连接自然排空（带超时）→ 再退出**。
>
> **⚠️ 最后我补一句边界**：**上面"从注册中心摘流量 + 通知客户端重连"这套完整流程，是我理解的做法，我没有在生产完整落地过。** 我做过的部分主要是**连接的生命周期管理（心跳、超时踢除、取消传播）和资源估算**，在 LoveSpouse 上【填：具体做了什么，比如"每连接两个 goroutine + context 取消传播 + 连接数监控"】。

**⚠️ 这题的加分点**：**主动说"先算账"**。99% 的候选人一上来就讲"用 epoll、用协程"，**而架构师的第一反应是"先算清楚约束在哪"**。**这个开场就能把你和普通后端区分开。**

### Q2：你的 WebSocket 长连接服务内存持续上涨，怎么排查？

**面试官意图**：考**排查方法论**（不是"猜"）+ 考你**知不知道 Go 特有的内存现象**（RSS vs heap）。**这题最容易看出一个人是"真排查过"还是"背过八股"。**

**答题框架（五步，★ 第一步是分水岭）**：

```
① 先分清：是真泄漏，还是"Go 没还给 OS"
② 定位增长的是哪个指标（heap inuse / RSS / goroutine 数）
③ 用 heap profile 做 diff 找增长源
④ 对照常见泄漏清单逐个排除
⑤ 修复 + 加监控防御
```

**★ 第一步：不要急着说"内存泄漏"（这个开场就赢了）**：

> **第一步不是"找泄漏"，而是先分清两种情况。** Go 有个很常见的现象：**`inuse_space` 平稳，但 RSS（进程常驻内存）一直很高**。原因是 **Go 的 scavenger 把内存还给 OS 是渐进的**，而且 Linux 上**用 `MADV_FREE` 标记的内存虽然可以被回收，但 RSS 数字不会立刻下降**。**所以如果容器监控只看 RSS，很容易误报成内存泄漏。**
>
> **判断方法**：看 `go_memstats_heap_inuse_bytes`（Go 自己认为在用多少）**和 RSS 对比**。如果 inuse 平稳而 RSS 高 → **不是泄漏**，可以调 `GOGC` / 用 `GOMEMLIMIT` 逼它更积极回收，或者接受它（操作系统内存压力大时会自己回收）。

**第二步：三个指标一起看**：

| 指标 | 如果它在涨，说明 |
| --- | --- |
| **`heap_inuse_bytes`** | **堆里的对象真的变多了** → 真泄漏 |
| **`go_goroutines`** | **goroutine 泄漏** → 大概率是连接泄漏（连接没被正确关闭） |
| **`process_resident_memory_bytes`（RSS）** | 可能是上面的假象，也可能是 cgo / 栈 / 未归还的内存 |

**★ 第三步：heap profile diff（最有效的手段，一定要讲）**：

```bash
# 隔 10 分钟采两次
curl -o base.prof 'http://ip:port/debug/pprof/heap?seconds=60'
sleep 600
curl -o cur.prof  'http://ip:port/debug/pprof/heap?seconds=60'

# 做差，看"多出来"的是什么
go tool pprof -base base.prof cur.prof
(pprof) top
(pprof) list <可疑函数>
```

> **关键技巧**：**一定要用 `-base` 做差**，不要只看单次快照。**单次快照里最大的往往是正常的大对象（比如启动时就分配好的缓存），做差之后"增长的部分"才会浮出来。** 另外**`inuse_space`（字节）和 `inuse_objects`（对象数）两个维度都要看** —— 有时候是"少量大对象"在涨，有时候是"大量小对象"在涨，**原因完全不同**。

**★ 第四步：长连接服务的泄漏清单（按发生概率排序）**：

| 排名 | 原因 | 怎么确认 | 怎么修 |
| --- | --- | --- | --- |
| **🥇 ①** | **连接泄漏：客户端掉线没被检测到**（**拔网线/切网络不发 FIN**），conn 和它的 goroutine、缓冲、业务状态永远不释放 | **`go_goroutines` 同步上涨**；goroutine profile 里**同一段栈出现几万次** | **★ 心跳 + pong 超时踢除**（见 9.4）；读/写都设 `SetReadDeadline`；**连接断开必须走 `defer close` 和 `cancel()`** |
| **🥈 ②** | **发送队列积压（慢客户端）** | `len(sendCh)` 持续增长；heap 里 channel 的 buffer 对象变大 | **队列有界 + 满了断开慢客户端**（背压） |
| **🥉 ③** | **本地缓存/map 只增不减**（会话表、路由表、去重表、订阅关系） | heap diff 指向那个 map；**`len(map)` 持续上涨** | **加 TTL / LRU 上限 / 定期清理**；或者**换成 Redis 并设过期** |
| **④** | **slice 共享大底层数组** | heap profile 里几个对象占了巨量内存 | 用 `copy`/`slices.Clone` 切断引用（见 6.6） |
| **⑤** | **`time.Ticker` / `time.AfterFunc` 没 Stop** | 定时器数量上涨（`go_memstats_...` 或 trace） | `defer ticker.Stop()` |
| **⑥** | **context 没 cancel**（泄漏 children map 和 timer） | heap 里 `context` 相关对象增长 | `defer cancel()`（见 5.4） |
| **⑦** | **真的业务缓存/历史数据越攒越多** | 数据量随时间线性增长 | 归档、分页、冷热分离 |

**第五步：修复 + 防御**：

| 防御措施 | 说明 |
| --- | --- |
| **所有连接必须有"最大空闲时间"** | **没有心跳超时的长连接服务，一定会有连接泄漏** |
| **`go_goroutines` 上告警** | 比内存指标**更早发现连接泄漏**（goroutine 涨在内存涨之前） |
| **`len(ch)` 上监控** | 提前发现队列积压 |
| **每个 map 都有淘汰策略** | **本地缓存一律设上限**，不允许出现"理论上不会太大"的 map |
| **压测 + 长稳测试** | **跑 24 小时看内存曲线**，比跑 1 小时有用得多 |

**★ 结合候选人的具体答法**：

> 长连接服务的内存排查我有个固定的套路。**第一步我一定会先说清楚：不能一看到 RSS 涨就喊内存泄漏** —— Go 的 `MADV_FREE` 和渐进式的 scavenger 会让 RSS 迟迟不降，**得先对比 `heap_inuse` 和 RSS**。
>
> **第二步是看三个指标一起涨不涨**：`heap_inuse`、`go_goroutines`、RSS。**如果 `go_goroutines` 跟着一起涨，那基本可以锁定是连接泄漏** —— 客户端断网不发 FIN，服务端不知道连接已经死了，**goroutine、conn、缓冲、业务状态全挂着**。
>
> **第三步用 heap profile 做差**：采两次快照，`go tool pprof -base`，**增长的部分就是答案**，然后 `list` 到具体函数。
>
> **落到长连接服务上，最常见的三个元凶我按概率排是**：**① 连接泄漏（心跳检测不到位）② 发送队列积压（慢客户端）③ 本地 map 没有淘汰**。
>
> **⚠️ 我实际处理过的部分是**：**连接生命周期和 context 取消传播**（我在 LoveSpouse 里给每条连接建了独立 context，断开就 cancel，避免下游模型调用还在跑）；**监控这块我们做得比较基础**【填：有没有做过 goroutine 数监控 / 有没有真出过内存问题】。**完整的 heap diff 排查我在生产上没主导做过，但方法论我清楚**。

### Q3：一个接口 P99 突然从 50ms 涨到 2s，怎么排查？

**面试官意图**：**考排查的系统性和优先级**。这题的关键不是"你知道多少工具"，而是**"你会不会瞎试"** —— 面试官想看你的排查路径是不是**从上到下、由外向内、先止血后根治**。

**★ 答题框架（六步，先讲"两个分叉"再讲路径）**：

```
第 0 步：先止血（能回滚就回滚、能扩容就扩容）—— 别在故障中做研究
第 1 步：先看范围 —— 是所有接口还是这一个？是所有实例还是某一台？是持续还是抖动？
第 2 步：看"两个曲线的形状" —— P50 涨不涨？错误率涨不涨？（★ 关键分叉）
第 3 步：按链路逐层排除（客户端 → 网络 → LB → 网关 → 应用 → 下游/DB）
第 4 步：应用层用 pprof + trace 定位到具体代码
第 5 步：找到根因 → 修 → 加监控告警防复发
```

**★ 第 2 步的"两个分叉"（这是本題最值钱的判断）**：

| 现象 | 说明 | 优先排查方向 |
| --- | --- | --- |
| **P50 正常，只有 P99 涨** | **典型的"长尾问题"** —— 大部分请求很快，少数请求极慢 | **① 锁竞争 / 排队**（少数请求抢不到锁）② **GC 的 mark assist**（分配快的请求被罚款）③ **少量慢 SQL / 慢下游**（比如没命中缓存的请求）④ **goroutine 调度延迟**（runqueue 太长）⑤ **偶发的连接建立**（连接池不够，偶发新建连接） |
| **P50 和 P99 一起涨** | **整体变慢** —— 资源饱和或依赖整体退化 | **① CPU/内存饱和** ② **下游/DB 整体变慢** ③ **连接池耗尽**（所有请求都在等连接）④ **流量突增** ⑤ **实例数减少**（有实例挂了/被限流） |
| **错误率也涨了** | **不只是慢，是开始失败了** | **过载/超时/熔断** —— 到了雪崩边缘，**优先止血（限流、降级、扩容）** |

**★ 第 3 步：链路逐层排除表（照着念都行）**：

| 层 | 查什么 | 工具 / 命令 |
| --- | --- | --- |
| **变更** | **★ 永远先问：最近有没有发布/配置变更/依赖升级？** | 发布记录、配置中心 diff |
| **流量** | QPS 是不是涨了？是不是有异常来源（攻击/爬虫/某个租户）？ | 网关监控、按来源拆分 |
| **客户端/网络** | 是不是某一地区/某运营商慢？DNS 解析慢？TLS 握手慢？ | 分地域监控、`dig`、`curl -w`（看各阶段耗时） |
| **LB / 网关** | 连接数是不是打满？后端健康检查有没有摘除实例？ | LB 监控、`ss -s`（连接状态统计） |
| **应用（资源）** | **★ CPU throttling！** 容器被 cgroup 限流是最隐蔽的原因之一 | **`cat /sys/fs/cgroup/cpu.stat` 看 `nr_throttled` 和 `throttled_usec`** |
| **应用（运行时）** | GC 频率？goroutine 数？协程队列积压？ | `GODEBUG=gctrace=1`、`go_gc_duration_seconds`、`go_goroutines`、`schedtrace` |
| **应用（代码）** | CPU 热点 / 锁竞争 / 内存分配 | **pprof**（CPU / mutex / block） |
| **应用（依赖）** | 连接池是否耗尽？等待时长大不大？ | `db.Stats()`、Redis/HTTP 客户端指标 |
| **DB / 中间件** | **慢查询**？**锁等待**？**热点 key**？**主从延迟**？ | 慢查询日志、`SHOW PROCESSLIST`、Redis `SLOWLOG` / `latency` |
| **★ 容器/宿主** | 宿主机是不是超卖了？邻居在抢 IO？ | 节点级监控、`iostat`、`top` |

**★ 第 4 步：应用层的三板斧**：

| 手段 | 看什么 |
| --- | --- |
| **CPU profile** | 如果是 CPU 打满 → 看火焰图，**是不是某个函数突然变热了**（比如某个新加的校验逻辑） |
| **goroutine profile** | **goroutine 数暴增 → 通常是某个下游变慢导致请求堆积**（每个请求一个 goroutine 等在那里）**★ 这是"下游变慢"最灵敏的信号** |
| **block / mutex profile** | 如果是长尾 → **看是不是锁竞争**（比如某个全局锁的持有时长变长了） |
| **trace** | 能看到**单个请求的时间线**：**它在哪一段被卡住了**（等锁？等网络？等 GC？等调度？） |

**★ 结合候选人的具体答法**：

> 我会按"**先止血，再分层，最后定位到代码**"来走。
>
> **第一步是止血**：如果能回滚最近的发布就立刻回滚，如果是流量问题就先限流或扩容 —— **在故障里做根因研究是最贵的**。
>
> **第二步我会先看两个曲线的形状**，这一步决定后面往哪查：**如果 P50 正常只有 P99 涨，那是长尾问题**，我优先怀疑**锁竞争、GC assist、少量慢 SQL、连接池偶发新建连接**；**如果 P50 跟着一起涨，那是整体饱和**，我优先怀疑**CPU/内存饱和、下游整体变慢、连接池耗尽、实例数变少**。
>
> **第三步按链路逐层排除**：**先看有没有变更**（这是最容易被忽略也最常见的原因），**再看流量有没有异常来源**，然后从客户端 → 网络 → LB → 应用 → 下游 → DB，一层层看指标。
>
> 有两个**特别隐蔽**的点我一定会查：**① 容器的 CPU throttling** —— `cpu.stat` 里的 `nr_throttled`，**如果容器 CPU 限额设小了，或者 GOMAXPROCS 没按 cgroup 设（第一节讲的那个坑），会周期性被限流，表现就是 P99 规律性地抖动**；**② goroutine 数** —— **goroutine 数突然暴涨通常意味着某个下游变慢了，请求全堆在那儿**，这比看下游自己报的 RT 更灵敏。
>
> **第四步到应用层就用 pprof**：CPU 高就看 CPU profile 找热点，长尾就看 mutex/block profile 找锁竞争，再用 trace 看单个请求的时间线到底卡在哪一段。
>
> **⚠️ 我的实际经验**：【填：有没有真实排查过线上性能问题。如果没有，就说"这块我在生产上没主导做过完整的排查，主要是自己压测和本地调优的经验"，然后补一句"但排查思路我理得清"。】**不编"我在线上定位过 P99 突刺"，这题一问细节就露馅。**

### Q4：高并发下怎么减少 GC 停顿对延迟的影响？

**面试官意图**：**这题是第七、九章的合体**。核心考两个认知：① **你知不知道 Go 的 GC 停顿其实不是主要矛盾**（能说出这句就赢一半）② **你有没有具体的落地手段**（不是空谈"减少分配"）。

**★ 这题的最高分答案就是那个"反转"**：

> **Go 的 GC 停顿（几十到几百微秒）几乎不是延迟的主要来源。** 真正影响 P99 的是**辅助标记（mark assist）**和**标记阶段占用的 25% CPU** —— 前者会**直接让正在分配内存的业务 goroutine 停下来帮忙标记**，后者会让**你的有效算力凭空少四分之一**。
>
> **所以问题的本质不是"怎么减少停顿"，而是"怎么让 GC 跑得更少、更轻"。** 而这两件事都指向同一个答案：**降低分配速率**。

**答题框架（三层）**：

```
① 降分配（治本，收益最大）→ ② 调 GC 参数（治标，立竿见影）→ ③ 加监控（验证 + 兜底）
```

**① 降分配（按收益排序）**：

| 手段 | 具体做法 | 收益 |
| --- | --- | --- |
| **★ 对象池复用 buffer** | `sync.Pool` 缓存读写缓冲（**记得 `Put` 前 `buf[:0]`**） | **代理场景最大的一块** |
| **★ 换低分配的序列化** | `sonic`/`jsoniter` 替代 `encoding/json`（标准库走反射 + 大量小对象） | 3~10 倍 |
| **★ 消灭 `fmt` / 反射 / `any` 装箱** | 日志用 zap/zerolog，热路径用 `strconv`；能写具体类型就不写 `any` | 每处都省 |
| **★ 预分配** | `make([]T, 0, n)` 一次到位，避免 `append` 反复扩容 | 减少"扩容产生的垃圾" |
| **★ 流式转发** | 大 body 用 `io.CopyBuffer` 直接转发，**别 `io.ReadAll`** | **避免大对象**（大对象分配贵、扫描久） |
| **降低指针密度** | `[]byte` / `[]struct` 代替 `[]*struct` —— **GC 是跟着指针走的** | 标记更快更省 CPU |

**② 调 GC 参数**：

| 参数 | 建议 | 效果 |
| --- | --- | --- |
| **`GOGC`** | **200~400**（默认 100） | **GC 次数直接减半以上**，CPU 省下来给业务；代价是内存占用变高 |
| **`GOMEMLIMIT`** | **容器限额的 90%** | **把"按比例触发"变成"按内存压力触发"**；配合 GOGC=off 可让 GC 只在必要时跑 |
| **⚠️ 但要看 GC CPU 占比** | `go_memstats_gc_cpu_fraction` < 5% | **如果这个数已经很低了，调参数没用，回去降分配** |

**③ 监控**：

| 指标 | 目标 |
| --- | --- |
| **`go_memstats_gc_cpu_fraction`** | **< 5%**（这是核心指标） |
| **`go_gc_duration_seconds`（P99）** | 几百微秒内 |
| **alloc 速率**（`rate(go_memstats_alloc_bytes_total[1m])`） | **越低越好**，优化前后对比这个数 |
| **★ mark assist 时间** | 从 gctrace 的 CPU 时间拆分里看，**这部分是直接拖慢业务的** |

**★ 结合候选人的具体答法**：

> 我先说一个可能和直觉相反的结论：**Go 的 GC 停顿本身（几十到几百微秒）不是高并发延迟的主要矛盾**，而且它**不随堆大小线性增长**（混合写屏障之后，标记终止不用重扫栈了）。**真正拖累 P99 的是 ① mark assist —— 分配太快时业务 goroutine 被罚款去帮忙标记，这是唯一直接停在业务请求上的 GC 开销；② 后台标记占掉 25% 的 P，等于有效算力少四分之一。**
>
> **所以我的优化方向不是"减少停顿"，而是"让 GC 跑得更少"**，而这等价于**降低分配速率**。
>
> **具体手段上，网关/代理这类服务我会这样做**：**① 读写缓冲走 `sync.Pool` 复用（这是最大的一块）**；**② 序列化换低分配的库**；**③ 热路径禁掉 `fmt` 和反射**；**④ 大 body 流式转发，不整包读进内存**；**⑤ 容器里 `GOGC` 调到 200~400 配 `GOMEMLIMIT=限额的 90%`**。
>
> **然后一定要用指标验证**：我会盯 **`gc_cpu_fraction`（目标 5% 以内）** 和**分配速率**。**如果 `gc_cpu_fraction` 本来就低，那说明 GC 根本不是瓶颈，调参数是白费功夫 —— 这个判断很重要，能避免瞎优化。**
>
> **⚠️ 边界**：**上面这套"参数调优"我没有在生产上系统做过**（我们服务的量级没到），**但"减少分配"我是有实操的**：LoveSpouse 里【填：具体做过什么，比如用对象池复用请求缓冲 / 避免在热路径打 fmt 日志】。

### Q5：你怎么定位一个 goroutine 泄漏？

**面试官意图**：考**你知不知道 Go 程序最常见的"慢性病"**，以及**你有没有主动防御的意识**。**这题答得好不好，直接反映你写并发代码是否规范。**

**★ 答题框架（四步）**：

```
① 发现 → ② 定位到栈 → ③ 对照成因清单 → ④ 修复 + 防御（★ 这步最能加分）
```

**① 怎么发现**

| 手段 | 说明 |
| --- | --- |
| **`runtime.NumGoroutine()` 打指标** | **最直接的早期预警**：持续上涨不回落 = 泄漏 |
| **`go_goroutines`（Prometheus）** | 生产必备，**上告警** |
| **`GODEBUG=schedtrace=1000`** | 每秒打印调度器状态，看 G 的数量变化 |

**② 怎么定位到具体代码（★ 核心操作）**

```bash
# 方式一：直接看所有 goroutine 的完整栈（最直观）
curl 'http://ip:port/debug/pprof/goroutine?debug=2'

# 方式二：用 pprof 聚合
go tool pprof http://ip:port/debug/pprof/goroutine
(pprof) top        # ★ 按"相同栈"聚合排序，数量最多的栈就是泄漏源
(pprof) traces     # 看每一组栈的完整调用链
(pprof) list <函数名>  # 定位到具体行
```

**★ 技巧（说出来显得真做过）**：

> **关键是看"同一段栈"的重复次数** —— pprof 会把相同调用栈的 goroutine 聚合起来，**排名第一的那组基本就是泄漏源**。**再对比两次采样**（间隔几分钟），**哪个栈的数量在增长，就是它在泄漏** —— 数字在涨的那一组才是问题，一直是 100 个的那组可能是正常的后台 worker。

**③ 成因清单（四大类，覆盖 95% 的情况）**：

| 类型 | 具体场景 | 识别特征 |
| --- | --- | --- |
| **★ channel 阻塞** | ① 向无缓冲/满的 channel 发送，**没有接收者**（对端提前退出了）② `for range ch` 等一个**永远不会 close** 的 channel ③ 往一个没人消费的 channel 发数据 | 栈停在 **`chan send` / `chan receive`** |
| **★ context 未取消** | 子 goroutine `<-ctx.Done()` 永久等待，因为**父的 cancel 从没被调用** | 栈停在 `select` / `ctx.Done()` |
| **★ 网络 IO 无超时** | ① `http.Client` **没设 `Timeout`**，或**读 body 后没 `Close`** ② 连接池里的连接泄漏 ③ **长连接掉线没被检测到**（**这是长连接服务的头号原因**） | 栈停在 `net.(*netFD).Read` / `readLoop` / `dial` |
| **同步原语误用** | ① `WaitGroup.Add` 和 `Done` **不配对** ② `Mutex` 死锁 ③ `errgroup` 里某个任务永久阻塞 | 栈停在 `sync.WaitGroup.Wait` / `Mutex.Lock` |

**④ 修复 + 防御（★ 这步是加分项）**：

| 防御 | 说明 |
| --- | --- |
| **★ 每个 goroutine 必须有明确的退出条件** | **写 `go func()` 之前先问自己："它什么时候退出？"** 答不出来就是泄漏。**这是唯一的根本原则。** |
| **★ 所有阻塞操作都 `select` 带 `ctx.Done()`** | 发送、接收、等待都要能被打断 |
| **`defer cancel()` 紧跟创建** | 见 5.4 |
| **所有网络调用设超时** | `http.Client{Timeout: ...}`；**读到的 body 必须 `Close` 且读干净**（否则连接无法复用） |
| **长连接必须有心跳超时** | 见 9.4 |
| **★ 单元测试里用 `goleak` 断言** | `goleak.VerifyTestMain(m)` —— **CI 里跑，泄漏直接测试失败**。这是**性价比最高的防御手段** |
| **优雅关闭时等 goroutine 退出** | `wg.Wait()` + 超时兜底 |

**★ 结合候选人的具体答法**：

> **发现**靠指标：`NumGoroutine` 或者 Prometheus 的 `go_goroutines`，**持续上涨不回落就是泄漏**。
>
> **定位**上我最常用的是直接拉 goroutine profile，**`go tool pprof .../goroutine` 然后 `top`** —— 它会把相同栈聚合，**数量最多的那一组就是答案**。更严谨的话**隔几分钟采两次做对比，看哪一组在增长**。
>
> **成因上，Go 里 goroutine 泄漏基本就是四类**：**① channel 阻塞（没人收/没人关）② context 没取消 ③ 网络 IO 没超时或长连接掉线没检测到 ④ WaitGroup/锁用错**。
>
> **在长连接服务里，第 ③ 类的"连接掉线没被检测到"是最常见的** —— **客户端拔网线不会发 FIN，服务端一直以为连接活着**，于是读 goroutine 永远卡在 `Read` 上，**连带 conn、缓冲、业务状态一起泄漏**。**这就是为什么长连接服务必须做应用层心跳 + 超时踢除**。
>
> **防御上我给自己定的规矩是：写 `go func()` 之前必须能说出它的退出条件。** 说不出来就是有问题的代码。另外**所有阻塞点都要 `select` 带上 `ctx.Done()`**，**所有网络调用都要有超时**。
>
> **⚠️ 我实际做过的**：**在 LoveSpouse 里我给每条连接建了独立 context，连接断开就 cancel，所以下游调用不会挂住**；【填：有没有用过 goleak / 有没有真排查出过 goroutine 泄漏】。**goleak 我知道这个工具，但没用在实际项目里** —— **这个我会想在新项目里加上，因为它是把"goroutine 泄漏"从"线上才发现"提前到"CI 就发现"的最有效手段。**

### Q6：一个秒杀式的高并发场景（如限时付费活动），你怎么设计？

**面试官意图**：这题是**综合题**，考**"库存/额度"类问题的完整设计能力**。**⚠️ 注意：你要把它答成"我做过的金币计费"的放大版** —— 这是你唯一能讲出真实细节的高并发场景（**LoveSpouse 的金币计费就是"不能超扣、可对账"**）。

**★ 答题框架（七层，从外到内）**：

```
① 接入层限流（挡住无效流量）→ ② 资格校验前置（缓存 + 快速失败）
→ ③ 原子扣减（★ 核心：不能超卖）→ ④ 异步落库（削峰）
→ ⑤ 幂等（★ 不能重复扣）→ ⑥ 降级与兜底 → ⑦ 对账与补偿
```

| 层次 | 做法 | 关键点 |
| --- | --- | --- |
| **① 接入层限流** | **按用户维度 + 全局维度**双限流（令牌桶）；**同一用户短时间重复请求直接拒绝**（防脚本） | **秒杀场景 90% 的流量都是无效的**，要**尽早挡掉** |
| **② 资格校验前置** | 活动开始时间、库存、用户资格**全放 Redis**，**在应用内存里做第一层判断**（本地缓存活动状态，避免每个请求都打 Redis） | **失败要"快速失败"**，不要走到扣减 |
| **③ ★ 原子扣减** | **用 Redis 的原子操作**：`DECR` / **Lua 脚本**（判断 + 扣减一步完成）；**`SET NX` 抢资格** | **绝对不能用"先 GET 再 SET"** —— 那是并发 bug。**Lua 脚本保证多步操作的原子性** |
| **④ 异步落库** | **扣减成功 → 写 MQ → 异步落 MySQL** | **削峰 + 缩短响应时间**；**MQ 要保证消息不丢（持久化 + 确认机制）** |
| **⑤ ★ 幂等** | **每个请求带业务唯一 ID**（订单号/请求 ID），Redis 里 `SET NX` 去重 | **客户端重试、MQ 重复投递都会导致重复扣**，**必须在扣减前就去重** |
| **⑥ 降级与兜底** | Redis 挂了怎么办？→ **本地令牌/直接拒绝**（**宁可拒绝也不能超卖**）；非核心功能关掉 | **要有明确的降级开关** |
| **⑦ 对账与补偿** | **Redis 的数据是"流水"，MySQL 是"账本"**；**定时对账**（比如每分钟比对总量）；**不一致就以 MySQL 为准修正 Redis**；**流水表留痕，可追溯** | **最终一致性 + 可审计** |

**★ 结合候选人的具体答法（这是本題的重点）**：

> 我做过的**最接近的场景是 LoveSpouse 的金币计费** —— **用户付费解锁媒体、实时语音按时长扣金币**。它和秒杀的本质完全一样：**并发环境下"额度"不能超扣、不能重复扣、出了错要能对账**。所以我按套下来的经验讲。
>
> **① 不能超扣 —— 用 Redis 的原子性保证。** 金币扣减走 **Redis 的原子操作（`DECR` 或者 Lua 脚本）**，**绝对不用"先查余额再扣"** —— 那是典型的并发 bug，两个请求都查到余额够，结果扣成负数。**Lua 脚本能把"判断余额够不够 + 扣减"合并成一次原子操作。**
>
> **② 不能重复扣 —— 幂等。** 每条扣费请求带一个**业务唯一 ID**，在 Redis 里 `SET NX` 去重，**重复的请求直接返回上次的结果**。**这一步是必须的**：腾讯 IM 的消息是**至少一次投递**，会重复推；客户端网络抖动也会重试；**没有幂等，用户就会被重复扣费** —— **这在付费产品里是事故级的 bug。**
>
> **③ 按时长扣费 —— 分段扣。** 实时语音是**流式长连接**，**不能等通话结束才扣**（可能通几个小时）。我的做法是**按固定时间片（比如每分钟）分段扣费**，**每次扣费都是一次独立的、幂等的原子操作**。好处是：**中途挂断不会多扣，也不会漏扣**；**并且每一段的扣费记录都有流水，可以对账。**
>
> **④ 落库与对账。** **Redis 负责"并发正确性"，MySQL 负责"账本持久化"。** 扣减成功后**异步落 MySQL 流水表**；另外有**对账逻辑比对 Redis 的余额和 MySQL 的流水汇总**，**不一致就以 MySQL 为准修正 Redis**。**为什么要对账？因为 Redis 可能丢数据（重启/主从切换），但账不能丢。**
>
> **⑤ 防超扣的底线：唯一索引兜底。** 除了 Redis 原子扣减，**MySQL 流水表上还有业务唯一 ID 的唯一索引**。**即使 Redis 出问题导致重复，写库时也会被唯一索引挡住** —— **这叫"最后一层防线"，做资金相关的功能我会习惯性加。**
>
> **⑥ 如果是"限时活动秒杀"这种更极端的场景**，我会在这个基础上再加三样：**① 活动开始前把库存预热到 Redis（避免缓存击穿打 DB）；② 接入层按用户限流 + 挡住重复请求（秒杀 90% 流量是无效的）；③ 扣减成功后走 MQ 异步落库削峰**，**响应时间能压到 Redis 的一次原子操作**。
>
> **⑦ 降级思路**：**如果能接受"少量用户请求失败"，我会选择"Redis 不可用就直接拒绝扣费"，而不是"降级到直接查 MySQL 扣减"** —— **因为宁可少卖，也不能超卖。涉及钱和额度的场景，保守永远优于激进。** 反过来如果是**非关键的计数类场景**（比如点赞数），我就会选择降级到底层存储，可用性优先。**这个取舍要看业务对"准确性"和"可用性"哪个更敏感。**

**⚠️ 这题的两个加分点**：

1. **主动做取舍（第 ⑦ 点）** —— "**宁可少卖不能超卖**"，这句话体现的是**业务判断力**，不是技术。**架构师和技术骨干的区别就在这儿。**
2. **提到"唯一索引兜底"** —— 说明你**不迷信单点方案**，知道**多层防御**。**这是做过线上系统的人才会有的习惯。**

## 十二、最后 30 秒速记

> **面试前最后看这一页。只看加粗的部分。**

### ★ 五个必背的"一句话答案"

| 题目 | 30 秒答案 |
| --- | --- |
| **GMP** | **G 是任务，M 是线程，P 是许可证（持有本地队列和内存缓存）。M 必须绑 P 才能跑 G。要 P 是因为：解耦 G 与 M、本地队列减少锁竞争、并行度独立可控。** |
| **为什么 goroutine 轻量** | **初始栈只有 2KB 且按需翻倍，创建百纳秒级，切换在用户态不陷内核。核心是等待 IO 的 G 不占 M —— 网络 IO 走 netpoller，G 只是挂在 fd 上等唤醒。** |
| **channel 底层** | **hchan = 一把锁 + 环形缓冲 + 两个等待队列。无缓冲是同步交接（直接从发送方栈拷到接收方栈），有缓冲是异步入队。** |
| **三色标记** | **白=没访问，灰=待扫描，黑=扫完了。不变式是"黑不能指向白"。并发标记期间靠混合写屏障（插入 + 删除都标灰）维持，Go 1.8 之后不需要重扫栈 —— 这是亚毫秒停顿的关键。** |
| **GC 停顿怎么看** | **STW 只有两处（标记准备、标记终止），都只做簿记，几十到几百微秒。★ 真正的延迟杀手是 mark assist（分配快的 goroutine 被罚款帮忙标记）和标记占用的 25% CPU —— 所以要优化的是分配速率，不是停顿。** |

### ★ 结合项目的三句话

| 场景 | 话术 |
| --- | --- |
| **几万 WebSocket 连接可行吗** | **完全可行**：**每连接两 goroutine、栈 2KB、等待不占线程，5 万连接约 10 万 G、1GB 出头内存。真正的瓶颈是 fd 上限、广播写放大、慢客户端的队列积压。** |
| **商云前台的并发控制** | **SQLite 写锁和串口都是"资源独占"。统一做法：封装成后台 goroutine + 请求 channel，调用方投递、等结果、带超时 —— 并发控制只在一个地方实现，业务代码不用管锁。** |
| **金币计费（Q6 的弹药）** | **Redis 原子扣减防超扣、业务唯一 ID 幂等防重复扣、按时长分段扣、MySQL 流水对账、唯一索引兜底。原则是"宁可少卖，不能超卖"。** |

### ★ 场景题的一句话框架

| 题目 | 一句话 |
| --- | --- |
| **10 万连接网关** | **先算账（带宽/内存/fd/CPU）→ 单机 1~3 万 + 集群 4~6 台 → netpoller + 对象池 + GOGC 调优 → L4 负载均衡 + 状态外置 Redis → 有界队列背压 → 优雅关闭。** |
| **内存持续上涨** | **先分清"真泄漏 vs RSS 没归还" → 看 heap_inuse / goroutines / RSS 三个指标 → heap profile 做 diff → 长连接常见元凶：连接泄漏（心跳不到位）、队列积压、map 无淘汰。** |
| **P99 从 50ms 涨到 2s** | **先止血 → 先看"P50 涨不涨"分叉（只有 P99 涨=长尾查锁/GC/慢SQL；都涨=整体饱和查资源/下游）→ 逐层排除（先问变更！查 CPU throttling！）→ pprof + trace 定位。** |
| **减少 GC 影响** | **方向不是减少停顿，而是让 GC 跑得更少 → 降分配（对象池/低分配序列化/避免 fmt/流式转发）+ 调参数（GOGC 200~400 + GOMEMLIMIT 90%）+ 盯 gc_cpu_fraction < 5%。** |
| **goroutine 泄漏** | **NumGoroutine 指标发现 → pprof goroutine 聚合看"同一段栈"数量最多的 → 四大成因（channel 阻塞 / context 没取消 / 网络无超时或长连接掉线 / 同步原语误用）→ 防御关键：写 go func() 前必须能说出它的退出条件。** |
| **秒杀/限时活动** | **限流挡无效流量 → 资格校验前置 → ★ Redis 原子扣减（Lua）防超卖 → ★ 业务唯一 ID 幂等防重复 → MQ 异步落库削峰 → MySQL 唯一索引兜底 → 对账补偿。** |
