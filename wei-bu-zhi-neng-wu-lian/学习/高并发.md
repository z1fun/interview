## 一、Go 并发原语速览

### 1.1 为什么 Go 是高并发的天然选择

| 特性 | Go | Python | Java |
|------|-----|--------|------|
| 并发模型 | Goroutine（用户态轻量线程） | asyncio（协程）/ threading | Thread（内核线程） |
| 内存开销 | ~2KB/goroutine（初始栈） | ~1MB/thread | ~1MB/thread |
| 通信方式 | Channel（CSP 模型） | Queue / asyncio.Queue | BlockingQueue |
| 并发原语 | goroutine + channel + select + sync | asyncio + await | synchronized + Lock |
| 百万连接 | 单机可达 | 困难 | 困难 |

> **Go 的并发哲学**：不要通过共享内存来通信，而要通过通信来共享内存（CSP 模型）

### 1.2 核心原语

```go
// 1. Goroutine —— 轻量线程
go func() {
    // 并发执行
}()

// 2. Channel —— 协程间通信
ch := make(chan int, 100)     // 带缓冲
ch := make(chan int)           // 无缓冲（同步）
ch <- value                    // 发送
value := <-ch                  // 接收

// 3. Select —— 多路复用
select {
case msg := <-ch1:
    // 处理 ch1
case ch2 <- data:
    // 发送到 ch2
case <-time.After(5 * time.Second):
    // 超时
default:
    // 非阻塞
}

// 4. sync 包 —— 同步原语
var mu sync.Mutex             // 互斥锁
var wg sync.WaitGroup         // 等待组
var once sync.Once            // 单次执行
```

### 1.3 常见并发模式

**Worker Pool（协程池）**：
```go
func workerPool(numWorkers int, jobs <-chan Job, results chan<- Result) {
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range jobs {
                results <- process(job)
            }
        }()
    }
    wg.Wait()
    close(results)
}
```

**Fan-out / Fan-in**：
```go
// Fan-out: 一个输入 → 多个 worker
func fanOut(input <-chan int, workers int) []<-chan int {
    channels := make([]<-chan int, workers)
    for i := 0; i < workers; i++ {
        channels[i] = worker(input)
    }
    return channels
}

// Fan-in: 多个 worker → 一个输出
func fanIn(channels ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, ch := range channels {
        wg.Add(1)
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c { out <- v }
        }(ch)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}
```

## 二、go-zero 三大核心能力（你的实战武器）

### 2.1 自适应降载（Adaptive Load Shedding）

> 这是 go-zero 最亮眼的特性，面试中**必须能讲出原理**。

**核心思想**：不设固定的 QPS 阈值，而是**基于 CPU 负载动态决策**。

```
采集 CPU 使用率（每 250ms）→ CPU > 阈值（90%）→ 进入降载
  → 计算：当前请求等待时间 / 历史平均等待时间
  → 比值 < 1（等待短于历史）→ 放行
  → 比值 > 1（等待长于历史）→ 以概率拒绝
```

**为什么比固定 QPS 好？**
- 固定 QPS：业务低谷浪费，业务高峰误杀
- 自适应：实时响应 CPU 负载，过载时优先保护已处理的请求

**数字人场景的应用**：
```go
// 在 LLM API 调用前加自适应降载保护
// 当系统 CPU 飙升时，新对话请求概率拒绝，
// 保证已在对话中的用户不受影响
```

### 2.2 Breaker（熔断器）三态

```
关闭态（Closed）  ——正常调用，记录失败率
     ↓ 失败率 > 阈值
开启态（Open）    ——快速失败，不调用下游
     ↓ 冷却时间到
半开态（Half-Open）——试探性放行少量请求
     ↓ 成功 → 关闭态 / 失败 → 开启态
```

**数字人场景**：当 LLM API 或记忆服务出现故障时，熔断器直接返回降级响应（"我正在思考，请稍等..."），避免大量请求堆积导致雪崩。

### 2.3 MapReduce（并发聚合）

```go
// 同时查多个数据源，聚合结果
// 数字人场景：同时查记忆 + RAG + 用户画像 → 合并注入上下文
results, err := mr.MapReduce(
    func(source chan<- interface{}) {
        source <- "memory_query"
        source <- "rag_query"
        source <- "profile_query"
    },
    func(item interface{}, writer mr.Writer, cancel func(error)) {
        result := queryDataSource(item.(string))
        writer.Write(result)
    },
    func(pipe <-chan interface{}, writer mr.Writer, cancel func(error)) {
        var all []Result
        for r := range pipe {
            all = append(all, r.(Result))
        }
        writer.Write(all)
    },
)
```

### 3.2 WebSocket 长连接层

**为什么选 WebSocket 而不是 SSE？**

| 维度 | WebSocket | SSE |
|------|-----------|-----|
| 方向 | 双向 | 单向（服务器→客户端） |
| 协议 | 独立协议（ws://） | HTTP |
| 主动推送 | ✅ | ❌（不支持客户端→服务器推送） |
| 用户打断 | ✅ 支持 | ❌ |
| 部署复杂度 | 较高 | 较低 |
| **数字人适用度** | ⭐⭐⭐（主动交互+打断） | ⭐⭐（纯推送） |

**连接管理**：

```go
// 连接分片
```

**单机内存估算（百万连接）**：
- Goroutine 栈：1,000,000 × 8KB = 8GB
- 读写缓冲：1,000,000 × 4KB × 2 = 8GB
- 总计约 16GB → 在生产可达范围内
- 千万级：10 台 WebSocket 节点，每台 100 万连接

### 3.3 LLM 代理层（最关键的一层）

```go
type LLMProxy struct {
    // 信号量并发控制
    semaphore    chan struct{}
    
    // 优先级队列（付费用户优先）
    priorityQueue *PriorityQueue
    
    // Token 桶限流
    rateLimiter  *rate.Limiter
    
    // 多模型路由
    routers      map[string]LLMClient
}

// 请求处理
func (p *LLMProxy) Chat(req ChatRequest) (<-chan string, error) {
    // 1. Token 桶限流
    if !p.rateLimiter.Allow() {
        return nil, ErrRateLimited
    }
    
    // 2. 获取信号量（保护 LLM API 不被冲垮）
    p.semaphore <- struct{}{}
    defer func() { <-p.semaphore }()
    
    // 3. 多模型路由
    client := p.route(req)
    
    // 4. 调用 LLM
    return client.StreamChat(req)
}
```

**多模型路由策略**：
| 对话类型 | 路由目标 | 原因 |
|---------|---------|------|
| 简单问候/日常闲聊 | 小模型（如 Haiku） | 延迟低、成本低 |
| 复杂推理/情感对话 | 大模型（如 Sonnet/Opus） | 质量高 |
| 特定领域（心理咨询） | 精调模型 | 领域优化 |

**成本控制**：
- **Prompt Caching**：人设 System Prompt 是固定的 → 缓存命中后延迟降 50-80%，成本大幅降低
- **上下文压缩**：长对话超过 N 轮后自动摘要，缩短 prompt
- **模型分层定价**：80% 对话走小模型，20% 走大模型

### 3.4 多级缓存

```
L1: 本地内存（人设 System Prompt）
  ├─ 容量：KB 级
  ├─ TTL：永久（启动时加载）
  └─ 命中延迟：< 1μs

L2: Redis（用户画像 + 短期记忆）
  ├─ 容量：GB 级
  ├─ TTL：1小时
  └─ 命中延迟：< 1ms

L3: Redis（RAG 检索结果）
  ├─ 容量：MB 级
  ├─ TTL：5分钟（相似问题复用）
  └─ 命中延迟：< 1ms
```

### 3.5 流式对话专项

**TTFT（首字延迟）优化，目标 < 500ms**：

```go
// 预加载：WebSocket 连接建立时并发加载
func (s *Server) preload(userID string) (*Session, error) {
    var (
        profile  *UserProfile
        memories []Memory
        err      error
    )
    
    // 并发加载
    g, ctx := errgroup.WithContext(context.Background())
    g.Go(func() error {
        profile, err = s.loadProfile(ctx, userID)
        return err
    })
    g.Go(func() error {
        memories, err = s.loadMemories(ctx, userID)
        return err
    })
    
    if err := g.Wait(); err != nil {
        return nil, err
    }
    return &Session{Profile: profile, Memories: memories}, nil
}
```

**背压控制**：
```go
// 流式返回时，如果客户端消费慢，需要背压
func (s *Server) streamWithBackpressure(ch <-chan string, conn *WSConn) {
    for token := range ch {
        select {
        case conn.send <- token:
            // 客户端能消费
        case <-time.After(100 * time.Millisecond):
            // 客户端太慢，累积 buffer 发送
            // 或跳过非关键 token
        case <-conn.ctx.Done():
            return // 连接断开，停止发送
        }
    }
}
```

### 3.6 任务体系的高并发

**记忆写入异步化**：
```
对话完成 → 发消息到 MQ（不阻塞主链路）

            ├─ 摘要生成
            ├─ 情感标注
            ├─ 关键信息提取
            └─ 向量化 → 写入 pgvector
```

**主动交互调度器**：
```go
type ProactiveScheduler struct {
    ticker    *time.Ticker
    taskQueue chan ProactiveTask
    shardCnt  int  // 用户分片数
}

func (s *ProactiveScheduler) Run() {
    for range s.ticker.C {
        // 按用户分片扫描
        for shard := 0; shard < s.shardCnt; shard++ {
            users := s.scanShard(shard)  // 只扫一个分片
            for _, u := range users {
                if s.shouldTrigger(u) {
                    s.taskQueue <- ProactiveTask{UserID: u.ID, Type: s.detectType(u)}
                }
            }
        }
    }
}
```

## 今晚记忆要点

1. Go 并发三大件：goroutine（轻量）+ channel（通信）+ select（多路复用）
2. go-zero 自适应降载：CPU 负载 + 请求等待时间比值 → 动态决策（不是固定 QPS）
3. Breaker 三态：关闭 → 开启 → 半开，保护下游不雪崩
4. 千万级架构四层：WebSocket 长连接 + LLM 代理层 + 多级缓存 + MQ 异步
5. WebSocket 推荐理由：双向通信 + 主动推送 + 用户打断（vs SSE 单向）
6. TTFT 优化：Prompt Caching + 预加载 + 流式返回 + 模型分层
7. 灰度闭环：10% → 评估 → 50% → 评估 → 100%，任何阶段不通过自动回滚
