## 二、基础层（✅ 大概率真实，重点是把语言换对）

### 2.1 Docker 与容器化

#### Dockerfile 怎么写（Go 项目）—— 必问

一个标准的 Go 服务 Dockerfile（**多阶段构建**，这是必须能讲出来的关键词）：

```dockerfile
# 构建阶段
FROM golang:1.22-alpine AS builder
WORKDIR /app
# 先拷依赖文件，利用 Docker 层缓存
COPY go.mod go.sum ./
RUN go mod download
# 再拷源码
COPY . .
# 关键：CGO_ENABLED=0 生成静态二进制，才能跑在 scratch/alpine 里
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o server .

# 运行阶段
FROM alpine:3.19
RUN apk add --no-cache ca-certificates tzdata
WORKDIR /app
COPY --from=builder /app/server .
EXPOSE 8080
CMD ["./server"]
```

**必须能说清的几个点**：

| 知识点 | 面试话术 |
| --- | --- |
| **为什么用多阶段构建** | > 编译需要 Go 的完整工具链，镜像好几个 G；运行只需要一个二进制。多阶段构建让最终镜像只有十几 M，构建环境不会进到生产镜像里。 |
| **为什么 `CGO_ENABLED=0`** | > 关掉 CGO 才能编译出完全静态的二进制，不依赖 glibc，才能跑在 alpine 或者 scratch 这种极简镜像里。我们的服务没用需要 CGO 的库，所以可以直接关。 |
| **`-ldflags="-s -w"` 干什么** | > 去掉符号表和调试信息，二进制能小 30% 左右。代价是不能用 gdb 调试，但我们生产环境靠日志和 pprof，不需要。 |
| **为什么先 COPY go.mod** | > Docker 是分层缓存的，只要 go.mod 没变，`go mod download` 这层就会命中缓存，不用每次重新拉依赖。改代码不会让依赖层失效。 |
| **基础镜像怎么选** | > 最稳的是 alpine，有 shell 能进去排查问题；最小的做法是 scratch 或者 distroless，但进去排查就麻烦了。我们用的是 alpine，留了排查的余地。 |
| **时区问题** | > alpine 默认没有时区数据，不装 tzdata 的话时间会是 UTC，日志时间对不上。这是个很常见的坑。 |

**⚠️ 如果你没用过多阶段构建**（只写过简单的 `FROM golang` 然后跑），就说：

> 我们当时的 Dockerfile 写得比较简单，直接把代码拷进去编译运行。多阶段构建我是了解的，主要是为了减小镜像体积、隔离构建环境，原理我清楚，只是当时没做这块优化。

#### 镜像与运行

| 知识点 | 话术 |
| --- | --- |
| 镜像分层 | > 每条 Dockerfile 指令是一层，层是只读的、可复用的。容器运行时会在最上面加一个可写层，容器删了可写层就没了，所以数据要挂 volume。 |
| volume 与 bind mount | > 数据库数据、日志这类要持久化的东西必须挂出来，不然容器一删数据就没了。配置我们是用环境变量注入的，不打包进镜像，这样同一个镜像能跑不同环境。 |
| 环境变量与配置管理 | > 我们把数据库地址、Redis 地址、密钥这些通过环境变量注入，镜像本身跟环境无关。敏感信息不写进代码和镜像里。 |
| 容器日志 | > 我们让程序把日志打到 stdout，用 `docker logs` 看，或者用 docker-compose logs 一次看多个服务。这样不用进容器也能排查。 |
| 资源限制 | > 可以限制容器的 CPU 和内存，防止一个服务把宿主机吃满。Go 服务要注意 GOMAXPROCS 和容器 CPU 限额的配合，不然程序会以为能用满宿主机所有核。 |

#### docker-compose

**这个大概率你用过**，能讲出来就很实在：

> 我们本地和测试环境是用 docker-compose 编排的，一个 yaml 里定义服务、MySQL、Redis，一条 `docker-compose up -d` 全起来。服务之间通过 compose 创建的网络用服务名互相访问，不用记 IP。依赖关系用 `depends_on` 控制启动顺序。

**⚠️ 要注意的追问**：`depends_on` **只保证容器启动顺序，不保证里面的服务真的就绪了**。这是个加分回答：

> `depends_on` 只管容器起来，不管里面的 MySQL 是不是已经能接受连接了。所以我们的服务启动时会做重试，连不上数据库就退避重试几次，而不是直接挂掉。更好的做法是用 healthcheck 配合 `depends_on` 的 condition 判断。

## 三、部署层（✅ 挖细节，你大概率真做过）

### 3.1 Linux 服务器部署

**基础但必会的命令**（被问到不要卡壳）：

```bash
# 看资源
top / htop              # CPU、内存、负载
free -h                 # 内存
df -h                   # 磁盘
iostat                  # 磁盘 IO
# 看网络与端口
netstat -tunlp / ss -tunlp   # 谁占了哪个端口
curl -v                  # 测接口连通性
# 看进程
ps aux | grep server
lsof -p <pid>           # 进程打开的文件
# 看日志
tail -f app.log
grep "traceid" app.log
journalctl -u myservice -f   # systemd 管理的服务
```

**话术**：

> 服务部署在 Linux 服务器上，我们用的是【Ubuntu / CentOS】。部署就是把镜像拉下来跑起来，用 systemd 或者 docker 的 restart policy 保证进程挂了能自动起来。排查问题基本就是看日志、看服务器资源、看端口通不通这三板斧。

### 3.2 Nginx 反向代理（**大概率配过，重点准备**）

**为什么需要 Nginx**：

> 一般不会让 Go 服务直接对外，前面挂一层 Nginx。作用有几个：一是反向代理，把请求转发到后面的服务；二是做 HTTPS 卸载，证书配在 Nginx 上；三是可以配 gzip 压缩、限流、静态文件；四是后面有多个实例时可以做负载均衡。Go 服务只监听内网端口。

**一个典型的配置**（能看懂、能讲清每一行）：

```nginx
upstream backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;   # 多实例负载均衡
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # ★ 流式接口（SSE / WebSocket）必须单独配
    location /api/stream {
        proxy_pass http://backend;
        proxy_buffering off;          # 关键！否则流式响应会被缓冲
        proxy_cache off;
        proxy_read_timeout 300s;      # 长连接要放大超时
        proxy_http_version 1.1;
        proxy_set_header Connection '';
    }

    location /ws {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;     # WebSocket 要更长
    }
}
```

> **★ 这段是你能拿分的地方**：`proxy_buffering off` 和 WebSocket 的 `Upgrade` 头，是**做 AI 流式输出必踩的坑**。把它和你的 LoveSpouse 项目串起来讲：

> 我们做流式输出的时候踩过一个坑——本地测试没问题，部署到服务器上之后流式就变成一次性返回了。排查下来是 Nginx 默认开了 `proxy_buffering`，它会把上游的响应缓冲起来，攒够了才发给客户端，流式的效果就没了。解决办法是对流式接口单独配置 `proxy_buffering off`。WebSocket 也有类似的坑，要显式设置 `Upgrade` 和 `Connection` 头，还要把 `proxy_read_timeout` 放大，不然长连接会被 Nginx 掐断。

**这段的价值**：它把"运维配置"和"AI 流式响应"这两个岗位要求**串成了一个真实的故事**，而且是你确实做过的。这比空谈运维知识强得多。

### 3.3 HTTPS 与域名

| 知识点 | 话术 |
| --- | --- |
| 证书怎么来的 | > 用 Let's Encrypt 的 certbot 签的免费证书，能自动续期。商业证书也可以，但从功能上没区别，主要是保险和背书。 |
| HTTPS 干了什么 | > 握手阶段用非对称加密协商出一个对称密钥，之后的数据传输用对称加密，兼顾安全和性能。 |
| 为什么必须上 HTTPS | > 现在 App 端基本都强制 HTTPS，明文传输会被系统拦。另外我们用到的很多第三方能力（比如微信相关、大模型 API）都要求 HTTPS 回调。 |
| 证书续期 | > Let's Encrypt 的证书 90 天过期，用 certbot 的定时任务自动续，续完 reload Nginx。踩过的坑是忘了配自动续期，某天证书过期整个服务不可用。 |

### 3.4 发布与回滚（**面试官很爱问**）

**要能讲出一个完整流程**：

> 我们的发布流程大概是：
> 1. 代码合并到主干，CI 跑测试和构建，打镜像推到镜像仓库，镜像 tag 用 git commit 号或者版本号，**不用 latest**；
> 2. 到服务器上拉新镜像，重启容器；
> 3. 重启后有个健康检查接口，确认服务真的起来了；
> 4. 出问题就回滚到上一个版本的 tag，重新拉起来。
>
> 因为镜像是按版本 tag 存的，回滚很快，就是把旧镜像重新跑起来。

**关键概念（能说出来是加分）**：

| 概念 | 话术 |
| --- | --- |
| **为什么不用 latest** | > latest 是个移动标签，你不知道服务器上跑的到底是哪个版本，回滚也没法回。必须用明确的版本号。 |
| **健康检查** | > 服务提供一个 /health 接口，检查数据库、Redis 这些依赖是不是通的。发布后探一下这个接口，通了才算发布成功，不然自动回滚。 |
| **优雅停机** | > Go 服务要处理 SIGTERM 信号，收到后先停止接收新请求，等正在处理的请求做完再退出。不然发布时正在处理的请求会直接断掉。这个用 `http.Server` 的 `Shutdown` 方法做。 |
| **滚动发布** | > 有多个实例时，一个一个换，保证始终有实例在服务。 |
| **蓝绿 / 灰度** | > 蓝绿是准备一套新环境，切流量过去，出问题切回来；灰度是先放一小部分流量到新版本，观察没问题再全量。 |
| **数据库变更** | > 发布里最麻烦的是数据库变更，因为回滚代码容易，回滚数据难。所以一般要求变更向后兼容，比如加字段先加可空的，不要直接删字段或改名。 |

**⚠️ 如果你们的发布很原始**（手工传文件、手工重启），就说：

> 我们当时的发布比较原始，是拉代码编译然后重启进程，没有完整的 CI/CD。规范的发布流程我是了解的，包括镜像版本管理、健康检查、优雅停机、灰度这些，只是当时团队规模小，没做到这一步。

### 3.5 数据库备份

## 四、可观测层（⚠️ 没做过就用"了解"的说法）

> **重要**：这一节**不要编造经历**。用"我了解这块该怎么做"来答，展示的是**技术判断力**，不是经历。面试官对非本职模块通常只要求这个深度。

### 4.1 日志（这块你肯定做过，可以讲实的）

**话术**：

> 日志这块我们做得比较基础但实用。服务把日志打到 stdout，按级别分。关键是**每条日志带上 traceid**——一个请求从入口生成一个唯一 ID，一路透传到所有相关的日志里。排查问题时用这个 ID 一 grep，整个请求链路的日志就都出来了。这在没有链路追踪系统的情况下，是最实用的排查手段。

**加分点：结构化日志**

> 更好的做法是打 JSON 格式的结构化日志，而不是纯文本。这样日志采集系统可以直接按字段检索和聚合，不用写正则去解析。Go 里常用 zap 或者 zerolog。

**日志级别怎么说**：

| 级别 | 用途 |
| --- | --- |
| DEBUG | 开发调试，生产一般关掉 |
| INFO | 关键业务节点，比如请求进来、调用外部服务、返回 |
| WARN | 可恢复的异常，比如重试成功、降级触发 |
| ERROR | 需要人介入的错误，比如调用失败、数据不一致 |
| FATAL | 服务无法继续，通常伴随退出 |

**⚠️ 坑点（说出来显得有经验）**：

> 日志最容易犯的错是打太多。把整个请求体、整个响应体都打出来，一是磁盘扛不住，二是里面可能有敏感信息。另外**日志里绝对不能打密码、Token、身份证、手机号这些**，这是合规红线。

### 4.2 链路追踪（⚠️ 你没做过，用"了解"讲）

被问到时，**先诚实、再展示理解**：

> 完整的链路追踪我们没上，当时是靠日志里的 traceid 串联排查的，这算是链路追踪的手工版。
>
> 完整的方案我了解，核心是 OpenTelemetry 这套标准：在服务里埋点，每次调用生成一个 Span，同一个请求链路的所有 Span 共享一个 TraceID、各自有 SpanID、通过 ParentSpanID 串成树。跨服务调用的时候，TraceID 通过 HTTP header 或者 gRPC 的 metadata 透传下去。数据上报到 Jaeger 或者 Zipkin 这类后端，就能看到一个请求在哪些服务上花了多少时间，很直观地定位瓶颈在哪个环节。
>
> 这块对微服务架构是刚需，因为服务一多，光看日志很难还原一个请求的完整路径。我们当时服务不多，日志 traceid 还能应付。

**为什么这个答法好**：承认没做过（安全）+ 说清原理（有料）+ 解释为什么当时不需要（有判断力）。

### 4.3 监控与告警（⚠️ 用"了解"讲）

**分四个层次讲，显得有体系**：

| 层次 | 监控什么 | 工具 |
| --- | --- | --- |
| **基础设施** | CPU、内存、磁盘、网络 | node_exporter + Prometheus |
| **应用** | QPS、响应时间（P50/P95/P99）、错误率、goroutine 数、GC 情况 | Go 服务暴露 `/metrics` 接口，Prometheus 拉取 |
| **中间件** | MySQL 连接数/慢查询、Redis 内存/命中率、MQ 堆积量 | 各自的 exporter |
| **业务** | 订单量、付费转化、消息量、AI 调用量与成本 | 自己埋点上报 |

**话术**：

> 监控的体系我了解，标准做法是服务暴露一个 /metrics 接口，用 Prometheus 定时拉取指标，Grafana 做可视化面板，配 Alertmanager 做告警。
>
> 指标主要看四类：**QPS、延迟、错误率、饱和度**。延迟不能只看平均值，要看 P99，因为平均值会掩盖长尾——一百个请求里 99 个很快、1 个慢 10 秒，平均值看起来很正常，但用户就是会投诉。
>
> 告警规则要克制，**告警太多等于没有告警**，大家会麻木。一般只对"影响用户的核心指标"和"容量水位"配告警，而且要配好阈值和持续时间，避免抖动误报。

**如果被追问"你自己搭过吗"**：

> 没有完整搭过，我们当时主要是看服务器的基础指标和日志。Prometheus 这套我了解原理，也想过要做，但当时的团队规模和服务数量，优先级没排到前面。

**⚠️ 不要做的**：不要为了显得懂而背诵 Prometheus 的配置细节，一问就穿。

### 4.4 Go 服务的可观测性特有项（你能讲的）

> Go 服务有几个特有的排查点。一个是 **goroutine 泄漏**——goroutine 起来没退出，会一直占内存，pprof 的 goroutine 视图能直接看到哪些 goroutine 卡在哪一行。另一个是 **GC 压力**，GC 频繁说明内存分配太猛，可以用 GODEBUG=gctrace=1 看。还有连接池，数据库连接和 Redis 连接都要限制上限，不限制的话高并发下会把下游打垮。

## 五、线上排查方法论（★ 加分项，这块是你真本事）

**面试官问"线上出过什么问题，你怎么排查的"，用这套框架答，比背知识点强十倍。**

### 5.1 排查四步法

```
1. 确认现象 → 影响范围多大？全部用户还是部分？什么时候开始的？
2. 定位环节 → 从入口往下游查：网关 → 服务 → 缓存 → 数据库 → 外部依赖
3. 缩小范围 → 看日志 traceid、看监控指标、看最近的变更
4. 处理与复盘 → 先止损（回滚/降级/扩容），再定位根因，最后写复盘
```

### 5.2 关键原则（说出来很专业）

> **先止损，再定位。** 线上出问题，第一优先级是恢复服务，不是找到根因。能回滚就回滚，能降级就降级，把问题定位放到服务恢复之后。
>
> **先怀疑最近的变更。** 出问题前如果刚发过版本、改过配置、调过参数，那大概率就是它。这是排查的第一直觉。
>
> **看变更、看指标、看日志，三者交叉验证。**

### 5.3 可讲的真实场景（挑一个你确实遇到的）

**模板 A —— 服务内存持续上涨（OOM）**

> 遇到过一次服务内存一直涨，最后 OOM 被杀。排查过程是：先看监控确认是内存问题不是 CPU；然后用 pprof 抓了堆内存快照，发现是某个缓存没有设上限，一直往里塞；再抓 goroutine 快照，看到一个 goroutine 数量也在涨。定位到是有一处 goroutine 起了没退出。修复是给缓存加了容量上限和过期时间，goroutine 那边加了 context 取消。

**模板 B —— 接口变慢**

> 有一次接口响应时间从几十毫秒涨到几秒。先看数据库，慢查询日志里发现一条 SQL 突然变慢了，用 EXPLAIN 看执行计划，发现没走索引——原因是数据量涨上来之后，优化器认为走索引不如全表扫。解决办法是改写 SQL 强制走索引，或者调整索引结构。这个也提醒我们数据量增长会改变执行计划，要定期 review 慢查询。

**模板 C —— 数据库连接被打满**

> 服务报"too many connections"。查下来是有一处代码在循环里查数据库，属于 N+1 问题，并发一上来连接数就爆了。短期是把连接池上限调大先扛住，长期是把循环查询改成批量查询。

**⚠️ 这三个模板是常见的典型场景，如果你确实遇到过类似的，用自己的细节替换。如果没遇到过，不要硬讲，说"我们线上比较平稳，印象比较深的是某次 XX"也可以。**

## 六、高频追问 TOP 10 速答

| 追问 | 速答 |
| --- | --- |
| 你搭过 CI/CD 吗？ | > 简单的是有的，提交代码后自动构建镜像、跑测试。【没做过就说】完整的流水线我没搭过，了解是用 GitLab CI 或者 GitHub Actions 触发构建、推镜像、通知部署，原理清楚。 |
| 容器和虚拟机什么区别？ | > 虚拟机虚拟的是硬件，每个 VM 有自己的内核，重；容器共享宿主机内核，只隔离进程和文件系统，启动快、开销小。 |
| K8s 用过吗？ | > 没有在生产用过。【如实说】了解核心概念，Pod 是最小调度单位，Service 做服务发现和负载均衡，Deployment 管副本数和滚动更新。我们服务数量少，用 docker-compose 就够了。 |
| 服务怎么保证高可用？ | > 多实例部署，前面挂负载均衡，任何一个实例挂了流量能切到其他实例。关键是服务要无状态，会话状态放 Redis 不放本地内存。数据库做主从，主挂了能切从。 |
| 服务器磁盘满了怎么排查？ | > 先 df -h 看是哪个分区满，再用 du -sh 逐层找大文件。最常见的是日志文件没清理，或者是容器镜像和日志堆积。处理是清理旧日志、配日志轮转、清没用的镜像。 |
| 负载均衡怎么做的？ | > 最外层可能是云厂商的 LB，或者直接用 Nginx 做。Nginx 的 upstream 配多个后端，默认是轮询，也支持权重、IP hash、最少连接。 |
| 灰度发布怎么做？ | > 按流量比例或者按用户维度分流。按用户分就是让一部分用户走新版本，用网关或者 Nginx 按规则转发。关键是新老版本要能共存，数据库结构要兼容。 |
| 数据库怎么做高可用？ | > 主从复制，从库实时同步主库的 binlog。主库挂了切到从库，这时候要注意主从延迟，可能丢一点数据。要求更高的用 MHA 或者云上的高可用方案。 |
| 你怎么做容量评估？ | > 先压测拿到单机的 QPS 上限，然后按预估的峰值流量除以单机能力，再留一倍以上的冗余。要考虑的不只是 QPS，还有连接数、内存、数据库的压力。 |
| 你觉得自己运维能力怎么样？ | > 基础的部署、容器化、Nginx、日志排查我是能独立做的，我们服务一直是开发自己维护的。但完整的监控告警体系、K8s 这类偏平台的东西，我是了解原理没深入做过。我觉得对咱们这个规模的团队，前面这些够用，后面的可以边做边补。 |

## 八、面试前 10 分钟速记

背这五条，其余临场发挥：

1. **主话术**：「我们没有专职运维，服务是开发自己部署维护的，Dockerfile、compose、Nginx、日志排查这些我实际做过。完整的监控体系没搭过，原理我了解。」
2. **Docker 三个关键词**：多阶段构建、CGO_ENABLED=0 静态编译、层缓存（先 COPY go.mod）。
3. **Nginx 杀手锏**：`proxy_buffering off` 解决流式输出被缓冲——**串到 LoveSpouse 的流式响应上讲**。
4. **发布流程四步**：打镜像用版本 tag（不用 latest）→ 拉新镜像重启 → 健康检查 → 出问题回滚旧 tag。
5. **排查方法论**：先止损再定位、先怀疑最近变更、看变更看指标看日志三交叉。
