# 06｜BLE 与硬件通信（了解级）

> **本文件用法与边界**：这是一份「了解级」文档——目标不是让你成为 BLE 工程师，而是让你在被问到蓝牙时**能听懂问题、能讲清链路、能说出方案思路、不被判定为完全不懂**。读法：第 1 章话术和第 8 章速答表必须背熟，第 2~6 章按「能用自己的话复述一张表」为标准，**不要背协议细节**。全文不包含任何虚构的 BLE 项目经历。

## 一、开场话术：如何诚实处理「没有 BLE 经验」（最重要，放最前面）

### 1. 处理原则

面试官大概率会直接问：「你做过蓝牙吗？」——**答案是没做过，这一点不能编，也没必要编**。天使轮公司招人，最怕的是「嘴上全懂、上手全废」。所以策略是四步：

| 步骤 | 做什么 | 目的 |
| --- | --- | --- |
| ① 坦诚 | 一句话承认没做过 BLE | 建立信任，避免被追问细节时崩盘 |
| ② 迁移 | 立刻接上串口外设通信经验（有协议帧、指令下发、状态读取） | 让面试官知道你不是「没碰过设备」，而是「换了一种物理层」 |
| ③ 准确 | 用 30 秒讲清 BLE 的链路分层，证明理解是对的 | 证明「不懂」是缺经验，不是缺认知 |
| ④ 落地 | 说清上手路径：拿 SDK 跑通读写 → 抓包看帧 → 参与协议定义 | 给出可信的、可验证的成长曲线 |

### 2. 30 秒过渡话术（可直接背）

> 「我先直说：**我没有做过 BLE 的开发**，简历里也没有这一块，不想含糊过去。
>
> 但我做过一年多的**外设串口通信**——商云前台是 Go + Wails 的桌面收银应用，我对接过电子秤、小票打印机、钱箱、扫码枪。做的是同一类事情：**定义私有协议帧、下发指令、读设备状态、处理校验和异常重连**。电子秤是持续往上推重量，我按帧解析；打印机是我发 ESC/POS 指令、再查状态位确认。这些和 BLE 的 Characteristic 读写、Notify 上报，在通信设计上是同一个模型，差别主要在物理层和链路层。
>
> BLE 这块我了解它的分层：底层 PHY/Link Layer 负责广播和连接，上面是 L2CAP，再往上是 ATT，**GATT 是在 ATT 之上定义 Service 和 Characteristic 的组织方式**，App 侧就是读写 Characteristic、订阅 Notify。协议栈本身是手机系统和 SDK 实现好的，业务侧真正要设计的是**指令帧格式、确认重传、状态同步和 OTA 流程**——这块是我擅长的部分。
>
> 上手路径我也想清楚了：先拿现成的 BLE 调试 App 把读写、Notify、MTU 协商跑一遍，用抓包看真实报文，再参与协议文档的评审。有串口协议的经验，这一层不会太慢。」

### 3. 为什么这样说安全

- **不装懂**：把「没做过」摆在最前面，后面讲的全是理解层面的内容，面试官不会用细节来验证你。
- **给了替代证据**：串口外设是真的做过的，协议帧、AES/RSA 加密、设备状态读取都是真的，可追问。
- **主动划出边界**：明确「底层协议栈是 SDK 做的，业务设计是我的强项」——这正是服务端在这个岗位上的真实定位。
- **反问留钩子**：话术最后可以加一句「想请教下咱们设备端是自研固件还是方案商提供的？」，把话题从「你会不会」转到「怎么协作」。

### 4. 三个不能踩的雷

1. **不要说「BLE 我熟」**——面试官只要问一句连接参数或 CCCD，就全是坑。
2. **不要编 BLE 项目**——一旦编了，追问「用的什么芯片、MTU 协商到多少、iOS 有没有后台断连」就结束了。
3. **不要贬低蓝牙**（比如「蓝牙很简单」）——这是对方产品的核心链路，态度上要尊重。

## 二、BLE 基础（了解级）

### 2.1 BLE 与经典蓝牙的区别

| 维度 | 经典蓝牙（BR/EDR） | BLE（Bluetooth Low Energy，4.0 引入） |
| --- | --- | --- |
| 定位 | 持续数据流，如音频、文件传输 | **低功耗、小数据量、间歇通信** |
| 功耗 | 高，需持续保持链路 | 极低，可纽扣电池跑数月 |
| 数据模型 | 面向流的 Socket（RFCOMM/SPP） | **面向属性的读写与通知**（GATT） |
| 典型场景 | 耳机、音箱、车载 | 手环、智能玩具、传感器、配网 |
| 速率 | 实际 1~2 Mbps | 实际应用层几 KB/s ~ 几十 KB/s |

一句话记法：**经典蓝牙是「打电话」，BLE 是「发短信」**。智能玩具、手环这类产品选 BLE，就是为了那颗电池。

### 2.2 协议栈分层（每层一句话）

| 层 | 全称 | 一句话职责 |
| --- | --- | --- |
| PHY | Physical Layer | 物理层，2.4GHz 上切出 40 个信道（3 个广播信道 + 37 个数据信道），GFSK 调制 |
| LL | Link Layer | 链路层，负责广播/扫描/建连、跳频、CRC 校验和链路级重传 |
| L2CAP | Logical Link Control and Adaptation | 逻辑信道复用、分段与重组，向上提供通道 |
| SM | Security Manager | 配对与密钥协商，负责链路加密（配对、绑定） |
| ATT | Attribute Protocol | 属性协议，定义「句柄 + UUID + 值」的读写与通知，是 GATT 的地基 |
| GATT | Generic Attribute Profile | 在 ATT 之上把属性组织成 Service / Characteristic，业务真正面对的一层 |
| GAP | Generic Access Profile | 定义角色（广播者/观察者/从机/主机）和广播、扫描、建连的流程 |

记忆顺序：**PHY → LL → L2CAP → ATT → GATT**，GAP 是横向的「流程规范」，不在这条数据通路上。

### 2.3 广播、扫描、连接

1. **广播（Advertising）**：设备（Peripheral，如玩具）周期性往外喊，包里带设备名、厂商 ID、Service UUID 等。传统广播包有效载荷 31 字节，BLE 5.0 扩展广播可到 255 字节。
2. **扫描（Scanning）**：手机（Central）监听广播。被动扫描只听；主动扫描会额外发 Scan Request，设备回 Scan Response（可以多塞 31 字节，常用于放自定义信息）。
3. **连接建立**：App 选中设备后发起连接请求，之后双方按**连接事件（Connection Event）**周期性通信——每个事件里主机发包、从机回包，一轮结束就休眠，这正是省电的来源。

一句话：**广播是「喊话找对象」，连接是「约好每隔几毫秒见一次面」**。

### 2.4 连接参数：功耗与实时性的天平

| 参数 | 范围 | 作用 | 调大 / 调小的代价 |
| --- | --- | --- | --- |
| Connection Interval 连接间隔 | 7.5ms ~ 4s | 两次通信的间隔 | 调小：实时性好、功耗高；调大：省电、延迟高 |
| Slave Latency 从机延迟 | 0 ~ 499 | 从机可跳过多少个连接事件不应答 | 调大：省电，但主机下发指令的响应变慢 |
| Supervision Timeout 监督超时 | 100ms ~ 32s | 多久没收到包判定断连 | 调小：断连判定快但易误判；调大：异常发现慢 |

约束关系：`Timeout > (1 + Latency) × Interval × 2`，且参数由**手机侧（Central）决定**，设备只能通过请求建议。iOS / Android 对参数都有各自限制，实际值往往是系统定的。

**面试只需要说一句**：连接间隔是「实时性 vs 功耗」的旋钮，硬件产品会在这里做取舍；服务端设计协议时要接受「一次交互可能是几十毫秒级」这个前提，不能按 HTTP 的思维设计同步调用。

### 2.5 为什么服务端也要懂这些

- **定协议要受链路约束**：MTU 决定一次能塞多少字节，连接间隔决定交互节奏，不知道这些设计出来的帧格式没法落地。
- **联调排障**：App 说「设备没反应」，你要能判断是蓝牙没连上、Notify 没订阅、还是指令发出去了没 ACK——这三层的责任方完全不同。
- **性能与成本估算**：传一个固件要多久、一条 AI 回复要拆几包、用户等着急不急，都依赖对速率的量级感。

## 三、GATT 协议（面试必问，要讲准）

### 3.1 层次结构

| 层次 | 含义 | 例子 |
| --- | --- | --- |
| Profile | 不是实际存在的对象，是「一套约定」的文档集合 | 电池服务 + 设备信息服务合起来构成一个产品 Profile |
| Service | 一组相关功能的集合，有 UUID | `0x180F` 电池服务、自定义 `0xFFE0` 私有服务 |
| Characteristic | 真正被读写/通知的数据点，含 Properties、Value、Descriptor | 电池电量、玩具的「表情指令」通道 |
| Descriptor | 描述 Characteristic 的元数据 | `0x2902` CCCD（通知开关）、`0x2901` 用户描述 |

设备侧每个属性都有一个 **Handle（16 位句柄）**，是寻址用的「门牌号」；UUID 说明「这是什么」，Handle 说明「在哪儿」。

### 3.2 UUID 与自定义 Service

- **16 位 UUID**：SIG 标准化服务/特征，如 `0x180F` 电池、`0x180A` 设备信息、`0x180D` 心率。
- **128 位 UUID**：厂商自定义，通常基于基础 UUID `0000xxxx-0000-1000-8000-00805F9B34FB` 派生。
- **岗位相关约定**：
  - 标准 Service 能用的就用标准的（电池、设备信息），App 和第三方工具都能直接读。
  - **私有功能一律放自定义 Service**，并在协议文档里固化：Service UUID、每个 Characteristic 的 UUID、Properties、字节序、字段含义、是否加密。
  - 私有 Service 最好做**能力声明**：例如用一个「命令通道」Characteristic 走所有指令，而不是每加一个功能就新增一个 Characteristic——否则固件升级、App 兼容会很痛苦。

### 3.3 Characteristic 的 Properties 与选用

| Property | 方向 | 有无应答 | 适用场景 |
| --- | --- | --- | --- |
| Read | 设备 → App | 有（ATT Read Response） | 读静态或低频状态：电量、固件版本、SN |
| Write | App → 设备 | **有**（ATT Write Response） | 关键指令，必须确认落地的 |
| Write Without Response | App → 设备 | 无 | 高频、可丢、追求吞吐：固件分片、实时音频流 |
| Notify | 设备 → App | 无（应用层无确认） | 高频状态上报，如实时电量、播放进度 |
| Indicate | 设备 → App | **有**（需 ATT Confirmation） | 关键事件：OTA 结果、升级完成、告警 |

选用口诀：**要可靠就用带确认的（Write / Indicate），要快就用无确认的（Write Without Response / Notify）**，两者常常配合——主通道走可靠，数据流走快速。

### 3.4 Notify vs Indicate 与订阅流程

| 对比项 | Notify | Indicate |
| --- | --- | --- |
| 是否需要接收方确认 | 不需要 | 需要，收方要回 Confirmation |
| 速率 | 快，可连续发 | 慢，同一时刻只能有一个未确认的 Indicate |
| 可靠性 | 可能丢（缓冲满、链路抖动） | 更可靠，但代价是慢 |
| 适用 | 周期上报、状态流 | 关键事件、一次性结果 |

订阅（开启通知）的标准流程：

1. App 发现服务（Service Discovery），拿到 Characteristic 的 Handle。
2. App 向该 Characteristic 的 **CCCD（`0x2902`）写入 `0x0001`（Notify）或 `0x0002`（Indicate）**。
3. 等系统回调 `onDescriptorWrite` 成功——**这一步很重要，很多「Notify 收不到」就是没等回调就发数据**。
4. 关闭时写 `0x0000`。断开连接后订阅失效，重连必须重新订阅。

### 3.5 MTU 协商与分包

- **默认 ATT MTU = 23 字节**，其中 3 字节是 ATT 头（1 字节 opcode + 2 字节 handle），**有效载荷只有 20 字节**。
- 双方可以发起 **MTU Exchange**，最大到 517。实际常见协商结果：iOS 自动协商约 185，Android 需 App 主动请求，常见 247 / 512。
- **单包有效载荷 = MTU − 3**。
- 超过一包的数据要**应用层拆包重组**：每包带 `序列号 + 总包数 / 偏移量`，接收方按序拼装，缺包请求重传。

```
一条 1KB 的指令，MTU 协商到 247：
  有效载荷 244 字节/包 → 需要 5 包
  每包：seq(2) + total(2) 或 offset(2) + data(≤240)
```

量级感（面试可以直接说）：**MTU 23 时约 20 字节/包，按 20ms 连接间隔算，理论上限也就 1KB/s 上下；协商到 247 并连发，实测能到十几 KB/s 量级**。所以 BLE 不适合传大文件——这个数字后面讲 OTA 会用到。

### 3.6 常见坑（面试爱问「你遇到过什么问题」，可以拿这些当「我知道的坑」）

- **连接不稳定**：连接参数被系统改写、2.4GHz 干扰（WiFi 拥挤）、距离与遮挡、设备天线设计差。
- **Notify 丢失**：① CCCD 写完没等回调就发数据；② 链路抖动或设备发送缓冲满；③ 多条 Notify 短时间连发被系统合并/丢弃。
- **Android / iOS 差异**：MTU 协商一个自动一个要手动请求；后台行为不同（iOS 后台需声明 bluetooth-central 且扫描受限，Android 8.0 后后台扫描受限）；权限模型不同（Android 12 起用 `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT`，此前扫描还要位置权限）。
- **后台限制**：App 退到后台后连接可能被挂起或降频，长时间传输（比如 OTA）必须在前台做，并引导用户不要切走。

## 四、指令下发与状态同步（岗位职责原文，重点）

### 4.1 私有指令帧设计（给一个具体可讲的例子）

物理层只负责搬字节，**「这句话什么意思」全靠应用层协议帧**。串口时代我是这么设计的，BLE 上是同一套思路：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| Magic 包头 | 2 字节 | 固定值如 `0xA5 0x5A`，用于帧同步 |
| Version | 1 字节 | 协议版本，便于灰度兼容新旧固件 |
| CmdType | 1 字节 | 命令字：0x01 设置表情 / 0x02 查询状态 / 0x03 OTA 开始 / 0x81 ACK … |
| Seq | 2 字节 | 序列号，请求与 ACK 对应，也用于去重 |
| PayloadLen | 2 字节 | 载荷长度，接收方据此判帧 |
| Payload | N 字节 | 业务数据，常用 TLV（Type-Length-Value）便于扩展 |
| CRC16 | 2 字节 | 校验，串口时代用 Checksum，BLE 建议 CRC16 |

```
A5 5A | 01 | 01 | 00 07 | 00 05 | 01 03 01 02 03 | 3F 2A
包头   版本  命令   序列号    长度      载荷(TLV)      校验
```

**面试可以强调的三点设计意识**：

1. **留版本号**：固件升级不同步是常态，协议必须能共存。
2. **用 TLV 而不是定长结构**：加字段不用改协议版本。
3. **长度 + 校验前置校验**：长度不对或校验失败直接丢帧，不要往下传。

### 4.2 指令可靠性四件套

| 机制 | 做法 | 解决的问题 |
| --- | --- | --- |
| ACK 确认 | 设备收到指令后回 `CmdType=0x81, Seq=原序列号` | 知道到底送到没有 |
| 超时重传 | 未收到 ACK 则重发，指数退避，设最大次数 | 链路抖动导致的偶发丢失 |
| 序列号去重 | 设备/SDK 记录最近处理过的 Seq | 重传导致的重复执行 |
| 幂等设计 | 指令本身可重复执行无副作用（如「设置为 XX 状态」而非「+1」） | 无法去重时的兜底 |

补充一句加分：**重传有上限，超限后不是死循环，而是上报失败给 App/云端，由业务决定降级**（提示用户重试、或标记设备异常）。

### 4.3 大指令的分包与重组

- 发送方按 `MTU − 3 − 帧头开销` 切片，每片带 `offset` 或 `seq/total`。
- 接收方维护重组缓冲：按偏移写入，收齐后校验整体 CRC。
- **乱序处理**：BLE 单连接内基本保序，但跨连接事件、重传后会乱。做法是**用偏移寻址而非顺序追加**，缺片就等或请求重传指定偏移。
- 与串口对照：串口是纯字节流，必须自己做「找包头 → 算长度 → 收完 → 校验」的状态机；BLE 有天然的包边界（GATT 写），反而更省事。

### 4.4 状态同步的三种模式

| 模式 | 链路 | 适用场景 | 缺点 |
| --- | --- | --- | --- |
| 设备主动上报（Notify） | 设备 → App | 状态变化频繁、要求实时（电量、正在播放、按键） | 断连就断更，App 不在线就丢 |
| App 轮询（Read / 发查询指令） | App → 设备 | 低频、打开页面时刷新，如进入设置页读一次状态 | 实时性差、耗电、连接开销大 |
| 云端下发查询 | 云 → App → 设备 | 需要云侧权威状态：定时对账、客服排障、运营统计 | 链路长，设备离线就失败 |

工程上的常见组合：**Notify 做实时增量 + 定期全量对账（App 打开或每 N 分钟拉一次）+ 云端保存权威副本**。

### 4.5 设备影子（Device Shadow）—— 解决设备离线

核心思想：**云端为每台设备保存一份「影子」文档，包含 `desired`（期望状态，云端想让它怎样）和 `reported`（设备上报的实际状态），带版本号**。

- 用户在线改设置 → 写入 `desired` → 设备在线则立即下发，离线就挂着。
- 设备上线 → 拉取 `desired` → 应用后回 `reported` → 版本对齐。
- App 展示状态时**先信影子**，连上设备后再用 `reported` 校正。

一句话话术：「**设备的真实状态不该只存在于设备里**——离线时用户还能看到、还能改，靠的就是云端影子。」

### 4.6 状态冲突怎么解决

| 手段 | 说明 |
| --- | --- |
| 按字段定权威方 | 用户意图类的以云端 desired 为准；传感器实测类的以设备 reported 为准 |
| 版本号 | 每次变更递增，低版本写入被拒绝，避免旧指令覆盖新状态 |
| 时间戳 + 防重放 | 帧里带时间戳/nonce，过期指令直接丢弃（如「立即播放」晚到 10 分钟就没意义了） |
| 最后写入胜出（LWW） | 简单场景可用，但必须配版本号，否则重传会造成状态回退 |

## 五、OTA 升级（岗位职责原文，重点）

### 5.1 整体流程

```
① App/云查询当前版本 → ② 云端比对版本库，决定是否升级
→ ③ 下发「准备升级」指令（设备检查电量、进 OTA 模式）
→ ④ 传输固件（分片）
→ ⑤ 设备端整体校验（CRC / Hash / 签名）
→ ⑥ 写入备份分区，设置启动标志
→ ⑦ 重启切到新分区
→ ⑧ 新固件上报版本号 → 云端记录升级结果
```

### 5.2 固件从哪来：三种传输方案

| 方案 | 路径 | 速度 | 适用 |
| --- | --- | --- | --- |
| BLE 直传 | 云 → App → BLE 逐片写设备 | 最慢，几 KB/s，500KB 要十几分钟 | 无联网能力的小设备、小补丁 |
| **App 下载后经 BLE 转发** | 云 → App（HTTPS 全速）→ BLE 转发 | 中，瓶颈在 BLE 段 | **最常见**，产品形态是「App + 玩具」时几乎都这么做 |
| 设备自带联网直下 | 设备 Wi-Fi / 4G 直接 HTTPS 下载 | 最快，几分钟内 | 联网设备（音箱、摄像头） |

结合岗位：这家公司是「App + 蓝牙硬件」，**大概率是第二种**——固件放云端（对象存储 + CDN），App 负责下载和转发，服务端负责版本管理和策略。这一句判断很值得在面试里说出来。

### 5.3 关键机制

- **分片传输**：每片带偏移，设备按偏移写 Flash。片大小受 MTU 限制（常见 128~244 字节）。
- **断点续传**：App 重连后先问设备「你收到多少字节了」，从该偏移继续——用户中途走开、锁屏断连是常态。
- **双分区 A/B（A/B Partition）**：固件分两个区，运行时用 A，新固件写 B，**校验通过才切启动标志**；新固件启动失败由 Bootloader 自动回滚到 A。这是防变砖的核心。
- **签名校验**：厂商私钥签名固件，设备内置公钥验签，防止刷入伪造固件（智能玩具尤其要考虑，防止被刷成别的东西）。
- **升级前检查**：电量阈值（如低于 30% 拒绝升级）、必须连接稳定、提示用户不要切后台。

### 5.4 升级失败与兜底

| 失败点 | 兜底 |
| --- | --- |
| 传输中断/断电 | 双分区，旧固件完好可回滚；支持断点续传 |
| 校验失败 | 丢弃该分区，重试下载；连续失败 N 次上报云端标记异常 |
| 新固件启动失败 | Bootloader 检测启动标志与心跳，超时自动回滚 |
| 升级后功能异常 | 云端支持「指定设备回退到某版本」——前提是保留了旧版本包 |

### 5.5 服务端在 OTA 里到底负责什么（回答这题要落到自己的强项）

1. **固件版本管理**：设备型号 × 硬件版本 × 固件版本，含大小、MD5/SHA256、签名、Release Notes。
2. **升级策略**：强制升级 / 可选升级 / 静默升级；按版本区间匹配（如「1.2.0 以下升到 1.2.5」）。
3. **灰度发布**：白名单 → 5% → 全量；按设备 SN、用户、地域分批，出问题立即停发。
4. **下发通道**：App 拉取升级任务（HTTP 接口 + 推送），或通过长连接下发。
5. **结果统计**：升级成功率、失败原因分布（断连/校验/电量）、卡在哪个分片、各版本占比——**这是纯服务端的工作，也是最能体现「我能直接上手」的部分**。
6. **回滚与止损**：一键停止某版本下发、指定设备回退。

## 六、端-云-硬件链路架构（设计题常考）

### 6.1 三种拓扑

| 拓扑 | 链路 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| A. App 直连 BLE | App ↔ 设备，云不参与 | 简单、无服务器成本、离线可用 | 无远程控制、无法统计、内容不能热更新 | 工具类小硬件（体重秤、手环） |
| B. **App 中转** | 设备 ↔ BLE ↔ App ↔ HTTPS ↔ 云 | 设备无需联网、成本低、云侧可管内容与策略 | 依赖 App 在前台、链路长、断点多 | **AI 交互玩具、情感陪伴类** |
| C. 设备自带联网 | 设备 ↔ Wi-Fi/4G ↔ MQTT/HTTPS ↔ 云 | 可远程、OTA 方便、不依赖手机 | 成本/功耗高、配网复杂、需处理弱网 | 智能音箱、摄像头、带屏设备 |

### 6.2 结合 LoveSpouse 场景推演（这是加分题）

「AI 情感陪伴 App + 智能玩具」这类产品，我会这么设计：

- **主链路走 B 拓扑**：玩具只做「执行器」——收指令做动作/发声/震动，上报按键、电量、姿态。**所有 AI 对话、记忆、计费都在云端**，因为大模型能力和内容更新必须能热更，不能烧进固件。
- **语音场景两种走法**：玩具采集音频 → BLE 回传 App → App 上行云端 ASR（BLE 带宽紧张，音频要么压缩要么降采样）；或玩具自带 Wi-Fi 直连云端。**如果实时性要求高（像 Gemini Live 那种双工语音），BLE 直传音频会很吃力，通常需要设备侧联网或本机唤醒词 + 短指令模式**。
- **App 做协议网关**：BLE 指令 ↔ 云端 API 的双向转换，App 侧维护连接状态与重连。
- **云端做**：设备影子、指令编排与状态机、对话与计费（LoveSpouse 里我做的金币计费、跨实例通话控制就是这一层）、OTA 版本管理。
- **混合方案**：BLE 配网 + Wi-Fi 长连，是这类产品成熟后的常见演进路径。

> 话术：「这个形态我在 LoveSpouse 里做过镜像版本——那套是 App + 智能玩具 + 腾讯 IM + 实时语音。我没做 BLE 那段，但**云端这半边的设备管理、状态同步、计费与消息可靠性是我做过的**，BLE 那段补上的是协议和联调。」

### 6.3 设备配网与绑定流程

1. 设备进入配网/广播模式，广播包里带产品标识与 SN。
2. App 扫描 → 连接 → 读设备信息（SN、MAC、固件版本、证书/密钥）。
3. App 调云端接口**绑定**：SN + 用户 ID，云端记录设备归属（一设备一用户，或支持解绑/转移）。
4. 若设备需联网：通过 BLE 加密通道下发 Wi-Fi SSID/密码，设备连上后回报云端。
5. 云端确认设备在线 → App 展示「绑定成功」。

### 6.4 设备认证与安全（可以拿商云前台的 AES/RSA 经验迁移）

| 要点 | 做法 |
| --- | --- |
| 一机一密 | 每台设备出厂烧入唯一密钥/证书，不用全局同一个 |
| 双向认证 | 设备验云端、云端验设备；BLE 侧依赖配对绑定（SM 层） |
| 应用层加密 | 敏感载荷（如配网密码、支付相关）在协议帧内再做 AES 加密 |
| 防重放 | 帧带时间戳 + 随机数 nonce + 递增序列号，云端/设备各存一份校验窗口 |
| 绑定校验 | 设备只接受已绑定用户的指令，防止他人连上玩具乱发指令 |
| 固件签名 | OTA 包必须验签，防止刷入恶意固件 |

> 迁移话术：「商云前台里我做过加密信息处理，用的是 AES + RSA 组合——对称密钥加密数据、非对称加密传密钥，同时帧里带时间戳和序列号防重放。设备通信的安全模型是相通的，换成 BLE 只是通道变了。」

### 6.5 离线场景

| 场景 | 方案 |
| --- | --- |
| 用户下发指令时设备不在线 | 云端指令队列 + 设备影子，设备上线后补发 |
| 有时效性的指令 | 带 TTL，过期直接丢弃（「现在开始哄睡」晚到 20 分钟无意义） |
| App 与设备断连 | App 侧缓存待发指令队列，重连后按序补发，靠 Seq 去重 |
| 状态不一致 | 上线后先拉一次全量状态（reported）与影子对齐，再恢复正常增量的 Notify |
| 补发风暴 | 队列限长 + 合并同字段指令（只保留最后一次），避免上线瞬间灌爆设备 |

## 七、串口经验迁移话术

### 7.1 概念对译表（自己的经验 → 面试官的语言）

| 商云前台（串口时代） | BLE 里的对应物 |
| --- | --- |
| 打开串口、配置波特率/校验位 | 扫描、连接、协商 MTU 与连接参数 |
| 私有协议帧：包头 + 长度 + 命令 + 数据 + 校验 | 私有 GATT Service 上的指令帧（Magic + Cmd + Seq + Len + Payload + CRC16） |
| 写串口下发指令 | Write / Write Without Response 写 Characteristic |
| 电子秤持续上报重量，按帧解析 | **Notify 主动上报，App 订阅后接收** |
| 打印机状态查询指令（发指令 → 读状态位） | Read 读状态 Characteristic，或发查询指令等 Notify 回包 |
| 指令后等设备回 ACK，超时重发 | 应用层 ACK + 超时重传（BLE 的 ATT Write Response 只保证到协议栈，不保证业务执行） |
| 串口读到的字节流自己分帧 | GATT 天然有包边界，但要自己按 MTU 分包重组 |
| AES/RSA 加密通信、时间戳防重放 | BLE 配对加密 + 应用层加密 + nonce/Seq 防重放 |
| 设备拔了重插、端口重连 | 断连自动重连、重连后重新订阅 Notify |

### 7.2 可直接用的一段话

> 「我以前做收银外设，电子秤是**一直往串口推数据**，我按协议帧解析出重量——这跟 BLE 的 Notify 是同一个模型，设备主动推、App 订阅接收。
>
> 打印机相反，是我**主动发指令、再读状态位**确认纸够不够、有没有卡纸——这跟 BLE 的 Write 加读状态 Characteristic 是一个逻辑：发出去、等回应、超时就重发、帧里带序列号和校验防止重复和出错。
>
> 唯一不同的是物理层和链路层：串口是点对点独占的字节流，我得自己找包头分帧；BLE 是广播 + 连接 + 属性模型，有 MTU 协商、连接参数、配对加密这些额外的复杂度，而且 iOS 和 Android 行为还不一样。但这层是系统和 SDK 提供的，业务侧要设计的还是**帧格式、可靠性、状态同步**这几件事——这块我有实际经验。」

### 7.3 必须主动说清的差异（自曝短板反而更可信）

- 串口是**独占、点对点、无连接状态**；BLE 有连接生命周期、连接参数、配对绑定，工程复杂度更高。
- 串口没有 MTU 概念（或很大），BLE 一次就 20 字节起，**分包拆包是必须做的功课**。
- BLE 有**平台差异**（iOS/Android 后台限制、MTU 协商方式），这是我没踩过的坑，需要实际项目里积累。

## 八、高频追问 TOP 10 速答表

| # | 问题 | 一句话答法 |
| --- | --- | --- |
| 1 | BLE 传输速率多少？ | 理论 1~2 Mbps，**实际应用层也就几 KB/s 到几十 KB/s**，MTU 23 时一个包才 20 字节有效数据；所以大文件不会走 BLE。 |
| 2 | Notify 会不会丢？ | **会**——未订阅、链路抖动、缓冲满、CCCD 写完没等回调都可能导致。所以关键状态用 Indicate 或加应用层 ACK + 定期全量同步兜底。 |
| 3 | 怎么保证指令一定送达？ | 应用层 ACK + 超时重传 + 序列号去重 + 指令幂等，最后**以设备上报的实际状态对账**，不靠「我发了」当成功。 |
| 4 | 设备离线了怎么办？ | 云端指令队列 + **设备影子（desired/reported）**，上线后补发；时效性指令带 TTL，过期直接丢。 |
| 5 | OTA 失败变砖怎么办？ | **双分区 A/B + Bootloader 自动回滚**，校验不通过不切启动标志；再加签名校验、电量阈值、失败上报重试。 |
| 6 | 为什么固件不直接走 BLE 传？ | 带宽太低，几百 KB 要十几分钟。主流做法是 **App 用 HTTPS 全速下载，再经 BLE 转发给设备**；设备能联网就让它自己下。 |
| 7 | MTU 23 是什么意思？ | ATT 默认 MTU 23 字节，减 3 字节协议头，**有效载荷 20 字节**；可以协商，常见到 185 / 247 / 512。 |
| 8 | 服务端又不直连蓝牙，你负责什么？ | 协议帧与状态机设计、设备影子与状态同步、指令下发通道、OTA 版本管理与灰度、设备数据与排障日志——**云端这半边就是我的主战场**。 |
| 9 | 用户说「设备没反应」，你怎么查？ | 分层定位：① App 蓝牙权限/连接状态 → ② Notify 是否订阅成功 → ③ 指令是否发出、有没有 ACK → ④ 设备是否上报状态 → ⑤ 云端指令记录。**关键是端到端带同一个 trace ID**。 |
| 10 | iOS 和 Android 有什么差异？ | Android 要手动请求 MTU、后台扫描受限、权限模型更严；iOS 自动协商 MTU、后台需声明模式、连接参数由系统定。**联调时两套都要测**。 |

**附加两问**（问到就答，答不上来不硬撑）：

| 问题 | 答法 |
| --- | --- |
| 连接参数谁决定？ | 手机（Central）决定，设备只能给建议值；所以「实时性 vs 功耗」的取舍实际由 App 侧和系统策略共同决定。 |
| 配对和绑定是什么？ | 配对是协商密钥建加密链路；绑定是保存密钥，下次免配对直接加密连接。BLE 的加密在链路层（SM 层）。 |

## 九、面试官问到 BLE 时的三条应对原则

1. **不装懂，第一时间承认没做过，但不让话题冷场**——承认之后立刻用串口外设经验接上，把「我没有某项经验」变成「我做过同类问题的另一种形态」。
2. **只讲能讲准的，主动划边界**——协议栈分层、GATT 层次、Properties、Notify/Indicate、MTU 分包、OTA 流程，这几块讲清楚就够了；芯片型号、SDK API、具体连接参数数值一律不猜，直接说「这块我没实操过，我的理解是……」。
3. **把话题拉回自己的主场**——设备通信的难点从来不只是蓝牙：**指令帧设计、确认重传与幂等、状态同步与设备影子、OTA 版本管理与灰度、离线补偿**，这些是服务端真正要交付的东西，也正是我有实战经验的部分。**面试官要的是「这个人能不能接住这条链路」，不是「他会不会写蓝牙 SDK」。**
