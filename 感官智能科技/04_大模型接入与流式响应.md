## 0｜先立主线：三根钩子，把话题拽到你的主场

**面试官最想确认的一件事**：你是不是真的**上线过**一个大模型功能，而不是跑通过一个 demo。所以每个回答都要回到两个项目。

| --- | --- | --- |

| B：分层记忆 | "陪伴类产品最大的成本在上下文，我们没做全量历史，做的是分层记忆 + Prompt 预算分配" | 上下文管理、Token 成本、缓存命中 |
| C：Agent 工具调用 | "另一个项目是漏洞研判，定级定价必须靠 Function Calling 拿事实，不能让模型编 CVSS 分数" | Tool Use、幻觉治理、人工兜底 |

## 1｜大模型 API 接入基础形态

### 面试官为什么问

- 岗位职责第 4 条原文就是「大模型 API 调用、对话上下文管理、流式响应」，**点名考察项**。
- 分辨你是「接过 SDK 的」还是「调过 API 的」：说清各家差异，才做得了多模型路由与降级（第 6 节）。
- 天使轮预算敏感，他们要能选型、能省钱、能随时换模型的人。

### 答题要点

**统一抽象的五个差异点**（一句话立住工程能力）：端点与鉴权、system 的位置、角色命名、流式结束标记、工具调用结构。把这五处收敛在一个 adapter 里，业务代码只依赖统一消息模型。

| 维度 | OpenAI | Gemini | Claude | 国内（通义 / 豆包 / DeepSeek） |
| --- | --- | --- | --- | --- |
| 端点 | `/v1/chat/completions`；新一代面向 Agent 的 Responses API `/v1/responses` | `/v1beta/models/{m}:generateContent`，流式 `:streamGenerateContent?alt=sse` | `/v1/messages` | 绝大多数兼容 OpenAI 的 `/chat/completions` |
| system | messages 里 `role=system` | 顶层 `systemInstruction` 字段 | **顶层 `system` 参数，不在 messages 里** | 同 OpenAI |
| 角色名 | user / assistant / tool | user / **model** | user / assistant | user / assistant |
| 流结束 | `data: [DONE]` | 最后一块带 `finishReason=STOP` | **`message_stop` 事件，没有 `[DONE]`** | 多为 `[DONE]` |
| 工具调用 | `tool_calls[].function.arguments`（JSON 字符串，要手动 unmarshal） | `functionCall` part | `stop_reason=tool_use` + `tool_use` block（`input` 已是对象） | 兼容 OpenAI，细节有出入 |
| 其它约束 | `max_tokens` 可选 | `safetySettings` 分级 | **`max_tokens` 必填** | 需实名/备案、内置内容审核 |

**参数调优（要讲出"为什么"，不要背书）**：

| 参数 | 作用 | LoveSpouse（陪伴对话） | 漏洞研判（研判定级） |
| --- | --- | --- | --- |
| `temperature` | 采样随机性 | **0.8~0.9**，太高人设会飘、太低像客服 | **0~0.2**，定级不能有随机性 |
| `top_p` | 核采样 | 不动它，只调 temperature | 同 |
| `max_tokens` | 输出上限 | 200~300，角色回复太长反而出戏 | 800~1500，要放得下结构化 JSON |
| `frequency_penalty` | 抑制重复用词 | 0.1~0.3，再高语言会变怪、人设崩 | 0 |
| `response_format` / `responseSchema` | 强制结构化输出 | 剧情节点、指令路由返回 JSON | 定级结果强制 json_schema |
| `stream_options.include_usage` | **流式下才拿得到 usage** | true —— 这是流式计费的前提，很多人不知道 | true |

### 参考话术

> 我接过的模型比较杂，Gemini Live、腾讯系的、还有国内兼容 OpenAI 协议的那几家都接过。我的做法是先定一层统一的消息模型 —— `Message{Role, Content, ToolCalls}` —— 然后每个厂商一个 adapter 去消化差异。
>
> 差异主要就五处：system 放哪、角色叫什么名、流式什么时候算结束、工具调用的结构、计费口径。举个例子，Claude 的 system 是顶层参数不在 messages 里，而且 `max_tokens` 必填；Gemini 的角色名是 `user/model` 不是 `user/assistant`；流式结束也不一样，OpenAI 是 `[DONE]`，Claude 是 `message_stop` 事件。这些在 adapter 里抹平之后，上层业务换模型只改一行配置。
>
> 参数上我的经验是：**陪伴类对话温度要偏高**，0.8 到 0.9，因为用户要的是"她有自己的情绪"，温度低了回复非常像客服话术；但**结构化输出的场景必须压到 0.2 以下** —— 像漏洞研判里的定级定价节点，输出要直接进审批流，随机性等于风险。另外有个坑很多人踩：OpenAI 的流式响应默认**不返回 usage**，必须在 `stream_options` 里显式打开 `include_usage`，否则根本没法做流式的 token 计费。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| Responses API 和 Chat Completions 区别？ | Responses 是面向 Agent 的：内置 web search / file search / code interpreter，`previous_response_id` 让服务端管状态，`instructions` 取代 system，事件粒度更细。但 Chat Completions 是事实标准 —— 国内模型全对齐它，所以抽象层是按它做的。 |
| 你说换模型只改配置，真有这么简单？ | 协议层确实简单，**难的是体验一致性**：不同模型的"语气"和指令遵循度不一样，人设卡要跨模型调优过。切模型是运维手段，体验一致靠 Prompt 不靠模型。 |
| 国内模型和海外模型怎么取舍？ | 四个维度：合规（数据出境、备案）、价格（国内普遍便宜一个量级）、能力（Gemini 的多模态和实时语音领先）、稳定性。所以我们是**文本走国内、实时语音走 Gemini Live** 的混合结构；参数走配置中心，按「场景」而不是按「模型」配置。 |

## 2｜流式响应（本节是重中之重，必须讲到细节）

### 面试官为什么问

- 职责原文点名「流式响应」。
- **能答出 Nginx 缓冲、客户端断线、goroutine 泄漏的人，才是真上线过的人**。大多数候选人只会说"调 `stream=true`，前端逐字显示"。
- 这一节追问密度最高，答住了就能把节奏握在自己手里。

### 答题要点

**SSE 协议细节（背到能画出来）**：

| 要素 | 内容 |
| --- | --- |
| 响应头 | `Content-Type: text/event-stream; charset=utf-8`、`Cache-Control: no-cache, no-transform`、`Connection: keep-alive`、`X-Accel-Buffering: no` |
| 帧格式 | `event:` / `id:` / `data:` / `retry:` 四个字段 + 一个空行结束一帧；`:` 开头是注释行（用来发心跳，如 `: ping`） |
| 结束标记 | OpenAI 系 `data: [DONE]`；Claude 是 `message_stop` 事件；Gemini 是最后一块带 `finishReason` |
| 编码坑 | SSE 是 UTF-8 字节流，**一个中文字符可能被 TCP 分包切成两半**；按行读（`ReadString('\n')` / `bufio.Scanner`）就不会有问题，自己按字节切 JSON 一定会炸 |
| 心跳 | 每 15s 发一次 `: ping` 注释行，防网关和手机网络把空闲连接掐掉 |
| 断线续传标准机制 | 服务端给每帧带 `id:`，客户端重连带 `Last-Event-ID` 头，服务端从该 id 之后补发（浏览器 `EventSource` 内置这套逻辑） |

**选型对比（结论先行：单向 token 流用 SSE，双向才上 WebSocket）**：

| 维度 | SSE | WebSocket | HTTP 长轮询 |
| --- | --- | --- | --- |
| 方向 | 单向，服务端→客户端 | 全双工 | 客户端拉，半双工 |
| 协议 | 就是 HTTP，无 Upgrade | 独立 `ws://`，需 Upgrade | HTTP |
| 自动重连 | 浏览器内置（带 `Last-Event-ID`） | **要自己写心跳 + 重连 + 补发** | 天然 |
| 二进制 | 只支持文本 | 二进制/文本都行 | 只文本 |
| 网关兼容 | 好 | 差，要 Upgrade 透传 + 粘性路由 | 最好 |
| 适合 | LLM token 流、通知推送 | 语音双工、强交互、需上行 | 兼容性兜底 |

**Go 侧转发（三个关键点）**：

```go
// 1. 响应头
w.Header().Set("Content-Type", "text/event-stream; charset=utf-8")
w.Header().Set("Cache-Control", "no-cache, no-transform")
w.Header().Set("X-Accel-Buffering", "no") // 比改 Nginx 配置更灵活
c.Writer.Flush()                          // Gin: c.Stream 每步自动 Flush、c.SSEvent 组装帧
                                          // Go 1.20+ 更推荐 http.NewResponseController(w).Flush()

// 2. 上游读取：流式场景 Client.Timeout 必须为 0（它覆盖整个 body 读取，会在生成中途切断）
client := &http.Client{Timeout: 0, Transport: &http.Transport{
    MaxIdleConnsPerHost: 100, IdleConnTimeout: 90 * time.Second,
    ResponseHeaderTimeout: 10 * time.Second,
}}
sc := bufio.NewScanner(resp.Body)
sc.Buffer(make([]byte, 0, 64*1024), 1<<20) // Scanner 默认单行上限 64KB，必须抬高

// 3. 客户端断开：用 c.Request.Context() 派生上游 ctx，用户关 App 时上游自动 cancel
//    否则 goroutine 泄漏 + 模型还在烧 token
```

**FastAPI 侧（漏洞研判用的）**：`StreamingResponse(gen(), media_type="text/event-stream")`，生成器 `yield` 即推。**坑**：Starlette 的 `GZipMiddleware` 会先攒够 `minimum_size` 字节才开始输出，等于人为加了首字延迟，SSE 路由上不要挂它。LangGraph 的 `astream_events` / `stream_mode="messages"` 能把 Agent 内部 token 级事件流出来，但**我们的研判场景对外没做流式** —— 审批场景用户要的是"结论 + 依据"，逐字蹦反而干扰阅读，我们用飞书卡片分段更新进度。**不是所有场景都该上流式。**

**Nginx / 网关的缓冲坑（答出前四个就已经赢了）**：

| 配置 | 为什么 |
| --- | --- |
| `proxy_buffering off;` 或响应头 `X-Accel-Buffering: no` | 默认开启时 Nginx 会攒够缓冲才转发，流式变成"憋一大坨" |
| `proxy_cache off;` | 别让流式响应进缓存 |
| `proxy_read_timeout 300s;` | **默认 60s**，LLM 首字慢或长回复会被网关掐断 |
| `gzip off;`（至少 `gzip_types` 不含 `text/event-stream`） | 压缩器要攒数据才输出，等于加缓冲 |
| `proxy_http_version 1.1;` + `proxy_set_header Connection "";` | 保持到上游的 keep-alive |
| 云 LB（SLB/ALB） | 同样有 buffering 和空闲超时，要单独调，别只盯着 Nginx |

**断线续传（答好直接拉开档次）**：

- 教科书答案：`id:` + `Last-Event-ID` 补发。
- 现实：**模型的输出没法"重放"**，除非你缓存了。
- 我们的做法（LoveSpouse，关键设计）：**流式只是"体验层"，不是"事实层"**。消息的权威副本走腾讯 IM（可靠、有序、支持离线推送）；服务端先生成一条 `generating` 状态的消息记录，流式结束后写入最终文本并置 `completed`。客户端断线重连后**不续流**，直接按 `messageId` 拉最终消息 —— "续传"被降级成了"最终一致性"问题。同时每个 delta 按 `seq` 增量写 Redis（TTL 5 分钟），真要续也续得上。
- **幂等**：重连不能重复计费，`messageId` 做幂等键（Redis `SETNX` + DB 唯一索引）。

### 参考话术

> 我们的做法是**分层的：SSE 负责体验，IM 负责可靠**。用户发一条消息，服务端先落一条 `generating` 状态的消息记录，然后流式推给 App；这条消息的最终版本会通过腾讯 IM 再走一遍可靠通道。好处是 —— 流式断了、App 切后台被系统杀了、网络抖了一下，用户重新进来看到的仍然是完整消息，因为权威副本在 IM 那边，流式只是"让字早点出现"。
>
> 这套设计顺带解决了一个很麻烦的问题：**模型的输出是不可重放的**。教科书上 SSE 续传靠 `Last-Event-ID`，但 LLM 生成完的内容你怎么补发？除非你缓存。我们每个 delta 会按 seq 增量写 Redis，要续也能续，但主路径上不做续传 —— 断线重连拉一次最终消息，比补发一堆 delta 更简单可靠。
>
> 踩过最典型的坑是 **Nginx 缓冲**：默认 `proxy_buffering` 是开的，你本地跑得好好的，一上线就变成"等好几秒一次性刷出来"。解决办法是在响应头里加 `X-Accel-Buffering: no` —— 这个比改 Nginx 配置好，因为它是**按响应生效**的，不用为一个流式接口把整个站点的缓冲关掉。另外 `proxy_read_timeout` 默认只有 60 秒，长回复会被网关直接切断，也要调。
>
> 还有个 Go 侧的坑：流式场景 **`http.Client.Timeout` 必须设成 0**。因为它覆盖整个请求生命周期包括读 body，你设 30 秒，模型生成到第 31 秒就会中途断掉，报一个很迷惑的 `context deadline exceeded`。我们用 context 做超时控制，加"首包超时"和"chunk 间空闲超时"，比一个全局超时精确得多。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 文本聊天为什么不用 WebSocket？ | 上行需求小；SSE 走标准 HTTP，鉴权、网关、日志、灰度这些现成设施都能复用，浏览器 `EventSource`、移动端 OkHttp 都有现成重连。WebSocket 要自己维护心跳、重连、粘性路由，成本高得多。**真正需要双向（语音、打断信号）才上 WS。** |
| 客户端断线你怎么知道的？ | `c.Request.Context().Done()`；同时写数据时的 error 也要判（对端可能已 RST 但 ctx 还没触发）。关键是**要把上游请求 cancel 掉**，不然模型那侧还在生成、还在计费。 |
| 上游卡住不返回怎么办？ | 两级超时：`ResponseHeaderTimeout` 管建连后到响应头；再起 timer 监控第一个 chunk。首包超时才能切备用模型 —— **流一旦开始就不能降级了**（见第 6 节）。 |
| 流式怎么统计 token？ | 必须开 `stream_options.include_usage`，最后一块 chunk 会带 usage。有些平台流式下不给 usage，只能本地用 tokenizer 估算，成本归因时要标注是估算值。 |

## 3｜首字延迟（TTFT）优化

### 面试官为什么问

情感陪伴产品的体验核心是「她回得快不快」。TTFT 是从「能跑」到「好用」的分水岭，也是应届生和 5 年经验的分界线。

### 答题要点（五个层面）

| 层面 | 手段 | 收益量级 |
| --- | --- | --- |
| 模型选择 | 用 Flash / mini 一级的模型做首包；**避开 reasoning 模型**（先思考很久才开始吐字）；MoE 架构普遍比 dense 快 | TTFT 降 40%~60% |
| Prompt | prefill 成本随输入长度增长；**静态内容（人设、规则）放最前**并用 prompt caching；RAG 先粗排再精排，别一股脑塞 10 段 | 命中缓存省 50%~90% 输入成本，TTFT 降 20%~40% |
| 连接 | HTTP 连接池复用、TLS 会话复用、**预热**（定时发 `max_tokens=1` 的最小请求保活）、就近 region | 省掉首次 TLS + 握手 100~200ms |
| 工程编排 | 意图识别 / 记忆检索 / 安全审核**并行**（`errgroup`），不要串行三段 await；记忆预取（收到消息立刻开始检索） | 省掉被串行化掉的检索耗时 |
| 感知优化 | 先推 `event: start` 或角色化的口头占位（"嗯…让我想想"）**把感知延迟压到接近 0**；Gemini Live 端到端音频比 ASR→LLM→TTS 少两段 | 感知 TTFT ≈ 0 |

**度量**：TTFT p50/p95、TPOT（每 token 耗时）、端到端首帧音频延迟，全部埋点。**分段埋点**是排查前提：入队 → 上下文组装 → 上游建连 → 首 chunk → 首字节出网。

### 参考话术

> TTFT 我们是从**真实延迟**和**感知延迟**两头优化的。
>
> 真实延迟上，最大的杠杆是**别让串行的编排挡住模型调用**。我们一轮回复要做事挺多：意图识别、检索记忆、拉剧情上下文、内容安全预审。一开始是串行写的，光这些就两三百毫秒；后来全部改成并行发起，模型调用只等一个 `errgroup` 的汇总。
>
> 第二个杠杆是 **Prompt 结构**。陪伴类产品的 system prompt 很长 —— 人设卡、语言风格、安全边界、记忆摘要 —— 这部分每次都一样，所以我把**稳定内容全部放最前面、动态内容放最后**，让模型厂商的前缀缓存能命中（OpenAI 自动，1024 token 起；Claude 要显式打 `cache_control`）。这里有个反直觉的点：**时间戳、随机 session id 这类东西绝对不能放进前缀**，哪怕一个字节变了整个缓存就废了。我们踩过 —— 一个用于日志的 request id 混进 system，缓存命中率直接掉到 0。
>
> 第三是感知层，这对陪伴产品特别重要：**首字之前先推一个角色化的占位**，不是冷冰冰的"正在输入"，而是带人设的一句话，用户感知到的等待会短很多。反正在情感交互里，**秒回但敷衍，不如稍慢但认真**。
>
> 度量上我坚持分段埋点 —— 入队、上下文组装、上游建连、首 chunk 各一段。不然你只知道"慢"，不知道是模型慢还是自己慢。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| Prompt 缓存怎么才算命中？ | 前缀**字节级完全一致**才行。稳定内容在前、动态内容在后，中间不能夹随机值；各家还有最小长度门槛（OpenAI 1024 token 起）。 |
| 并发高了 TTFT 会变差吗？ | 会，上游排队。我们做**本地并发闸门**（信号量限制 in-flight 数），保证不触发上游限流 —— 宁可本地排队，也不要被上游 429 后全体退化。 |
| 语音场景的 TTFT 怎么算？ | 不看 token，看**首帧音频到达时间**。端到端 Live API 比三段式快，因为省掉 ASR 出文本、TTS 合成两段往返；代价是可控性差（不能中途插自己的审核逻辑）。 |

## 4｜对话上下文管理

### 面试官为什么问

职责原文点名「对话上下文管理」；它同时是记忆系统（文档 05）的地基和成本的第一来源。答好了，面试官会顺势问记忆系统 —— 那是你的主场。

### 答题要点

**上下文窗口（量级）**：Gemini 1M、Claude 200K、GPT-4o 128K、DeepSeek 64K~128K。

> 关键认知：**窗口大 ≠ 要填满**。填满有三个代价：成本线性上涨、TTFT 变慢、**lost-in-the-middle**（中间信息容易被忽略）。我们要的是"精准的短上下文"，不是"全量的长上下文"。

**Token 计数**：OpenAI 用 `tiktoken`，Gemini 有 `countTokens`，Claude 有 `count_tokens` 端点。工程近似：**中文约 1 token ≈ 1~1.5 个汉字，英文约 1 token ≈ 4 字符**（不同 tokenizer 差异不小，预算要用真实 tokenizer 实测，别猜）。**必须预留输出侧的 `max_tokens`**。

**四级截断策略（从土到精）**：

| 级别 | 做法 | 代价 |
| --- | --- | --- |
| 1. 滑动窗口 | 只保留最近 N 轮原文 | 简单，但早期事实全丢 |
| 2. 摘要 + 近况 | 老对话压成摘要，近 N 轮留原文 | 主流做法，摘要会丢细节 |
| 3. **分层记忆**（我们的做法） | 稳定事实常驻 + 长期摘要 + 会话摘要 + 近期原文 | 实现复杂，但成本与效果最优 |
| 4. 检索式记忆 | 不常驻，按当前话题检索相关历史片段（依赖检索质量，适合超长关系） | 再往前一步的形态 |

**Token 预算分配（LoveSpouse 的实际口径，可照此讲）**：

| 区块 | 预算（tokens） | 稳定性 | 说明 |
| --- | --- | --- | --- |
| 人设 / 角色卡 | 400~800 | 稳定 | **放最前，进缓存前缀** |
| 安全与边界规则 | ~150 | 稳定 | 放最前 |
| 长期记忆摘要 | 300~600 | 半稳定 | 变更频率低 |
| 稳定事实（称呼、偏好、关系进度） | 100~200 | 半稳定 | **键值化，不要写成自然语言段落** |
| 剧情 / RAG 检索片段 | 400~800 | 动态 | 精排后取 top-k，截断长度 |
| 近期对话原文 | 剩余（约 1500~2500） | 动态 | 放最后 |
| 输出预留 | 200~300 | - | 对应 `max_tokens`，必须留 |

**压缩触发**：按 **token 水位线**触发（窗口的 60%~70%），不是按轮次 —— 一轮的长度差异极大（用户可能发一段 500 字的倾诉）。

**摘要怎么做**：增量摘要（旧摘要 + 被淘汰的对话 → 新摘要），Prompt 要约束保留什么：**关系进展、未完话题、情感状态、用户明确表达过的偏好**。摘要任务用便宜模型、走异步，**失败不影响主链路**。

**冲突处理**：用户改口（"别叫我宝贝了"）→ 事实表 **upsert + 时间戳**，冲突取最新；**只注入"当前有效"的设定，旧设定不注入**（不要指望模型自己判断哪个更新）。

### 参考话术

> 陪伴类产品最容易犯的错是**把历史对话一股脑塞进去**。对话越长成本越高、首字越慢，而且模型在长上下文里对中间部分其实不敏感 —— 你塞了 50 轮，它真正用上的还是最近几轮和开头的人设。
>
> 我们做的是**分层记忆**：不是一条线性的消息列表，而是几个不同"新鲜度"的层。稳定事实层存键值化的硬信息 —— 用户怎么称呼、喜欢什么、关系进度到哪；长期摘要层是压缩过的历史叙事；会话摘要层是当前会话的进行时；再往下才是最近几轮的原文。组装 Prompt 时按层拼装，每层有固定的 token 预算。
>
> 有两个细节挺关键。**第一，稳定事实是键值化的，不是摘要生成的。** 摘要会丢细节、还会漂移，但"用户的猫叫咪咪"这种事实必须准 —— 所以我们用抽取式做法，让模型输出结构化的 facts 数组，走 upsert 更新、带时间戳、冲突取最新。**第二，事实表更新后旧设定就不再注入了。** 用户说"别叫我宝贝了"，如果你把新旧两个称呼都塞进 Prompt，指望模型自己判断哪个有效，它大概率混着用。
>
> 成本上，分层之后我们单轮上下文 token 基本是**恒定**的，不随关系变长而线性上涨 —— 这对陪伴类产品的商业模型是决定性的，见第 7 节。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 摘要不丢信息吗？ | 会丢，所以**分层的目的就是把"不能丢的"和"可以模糊的"分开**：硬信息走事实表（结构化、不丢），叙事连续性走摘要（可以模糊）。 |
| 摘要用哪个模型？ | 便宜的小模型，异步做。摘要质量不够会污染后续所有轮次，所以摘要 Prompt 是**结构化输出**（返回 facts + 摘要两段），facts 进事实表、不靠自由生成。 |
| 多语言怎么办？ | 产品是多语言的，不同语种 token 效率差挺多 —— 同一句话中英文 token 数不一样，所以预算表按语言分层，不能一套走天下。token 计数用 tiktoken 做近似、关键路径用厂商 count API 校准。 |

## 5｜Function Calling / Tool Use

### 面试官为什么问

判断你是「只会聊天」还是「会做 Agent」。职责里的「AI 模型能力接入与应用开发」，Tool Use 是最有技术含量的部分。

### 答题要点

**本质**：把函数签名用 JSON Schema 描述给模型，模型**只输出调用意图**，执行权在你手里（模型不执行任何东西）。这个边界感要讲出来。

**完整流程**：

```
注册工具(JSON Schema) → 模型决策(可能一次返回多个 tool_call)
  → 服务端并发执行 → 结果回填(tool 角色 / tool_result / functionResponse)
  → 再请求模型 → 直到 stop_reason 不再是 tool_use（或达到 max_iterations）
```

**三个容易答错的细节**：

1. **并行工具调用**：OpenAI `parallel_tool_calls`（默认 true）一次可能返回多个 `tool_call`，必须**全部执行、全部回填**，用 `tool_call_id` 一一对应；**漏一个直接报 400**。Claude 是同一 assistant 消息里多个 `tool_use` block，Gemini 是多个 `functionCall` part。
2. **失败怎么处理**：工具执行失败**不要把异常抛给用户**，把错误信息作为 tool result 回填（`{"error": "资产不在 SRC 范围内"}`），让模型自己决策 —— 换参数、换工具、或直接回答"这个不在范围内"。同时设 `max_iterations`（8~10）防死循环。
3. **参数解析容错**：模型可能返回带 markdown 围栏的 JSON、参数名漂移。三层防护：`json_schema` 强约束 → 解析失败带错误重试一次 → 业务校验失败把错误回填让模型改。

**工具设计五原则**（说出来很显水平）：

- 描述里写清「**什么时候用**」，不只是"是什么"；
- 参数越少越好，能推断的不要暴露；
- **返回值要裁剪/摘要**再回填 —— 一个 50KB 的 JSON 塞回去，token 全烧在这儿；
- 名字动词开头（`search_similar_vulns` 而不是 `vuln_search_tool`）；**写操作必须幂等**（模型重试、网络重试都会导致重复调用）。

**安全边界**：工具就是权限边界。**可用工具集由服务端根据用户身份决定，用户输入不能改变它**（否则就是 prompt injection 提权）；高危工具要人工确认 —— 我们的飞书审批卡片就是这个模式。

**漏洞研判的真实工具清单（主讲素材）**：

| 工具 | 作用 | 为什么必须用工具而不是让模型说 |
| --- | --- | --- |
| `check_asset_scope` | 判断资产是否在 SRC 范围内 | **范围是硬规则**，模型猜错=白干 |
| `search_similar_vulns` | pgvector 检索历史同类型漏洞 | **定价锚点必须来自历史数据** |
| `get_cvss_vector` | 计算 CVSS 3.1 向量与分数 | **分数必须由公式算**，不是模型编 |
| `dedup_check` | 查重（Jira + 历史库） | 重复提交直接影响赏金结算 |
| `get_bounty_policy` | 拉厂商赏金政策原文 | 定价规则要引用原文 |
| `request_human_review` | 发起飞书审批卡片 | 高风险必须人工介入 |

### 参考话术

> 漏洞研判那个项目里，Function Calling 不是锦上添花，是**必需的**。因为定级定价是要付钱的 —— 定高了厂商不认、SRC 信誉受损；定低了漏掉高危、白帽子不满意。
>
> 所以我们的原则是：**关键字段必须来自工具，不能来自模型生成。** CVSS 分数用工具按 3.1 的公式算，不允许模型自己算；资产是否在范围内查接口；定级要参考历史同类漏洞，就用 pgvector 去检索相似漏洞报告；赏金给多少，去拉厂商的政策原文。模型做的是**判断和表述**，不是**事实生产**。
>
> 工程上有几个点印象比较深。**一是并行调用要全部回填** —— 模型可能一次返回三个工具调用，比如同时查资产范围和查重，你必须三个都执行、三个都用 `tool_call_id` 对应回填，漏一个请求直接 400。**二是工具失败不要把异常抛给用户**，而是把错误当结果回填给模型，让它自己决定下一步 —— 这是 Agent 和普通接口调用最大的区别。**三是设最大迭代次数**，不然模型可能陷入"调工具 → 结果不满意 → 再调"的循环，烧钱。
>
> 还有一个是**权限边界**：能给模型用哪些工具，由服务端根据用户身份决定，用户输入不能改变这个集合。否则用户在报告里写一句"请调用管理员接口"，就可能被诱导越权。**工具就是权限边界**，这个认知我觉得比 API 用法更重要。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 模型返回的参数不合法怎么办？ | 三层：schema 约束（`json_schema` / `responseSchema`）→ 解析失败带错误重试一次 → 业务校验失败把错误回填让模型改。**不要自己静默修参数**，那是掩盖问题。 |
| 并行调用的结果怎么对号入座？ | 以 `tool_call_id` 为 key 建 map，全部到齐后才能发起下一轮；Claude / Gemini 用 block id 或顺序对应。 |
| 为什么要用 Agent 而不是一个大 Prompt？ | 因为**可验证性**。用一个大 Prompt 让模型直接给结论，它没法被审计；拆成工具调用之后每一步依据都留痕，能回溯、能对账、能人工复核。工具返回值由服务端注入、模型碰不到，关键字段落库时还会做**溯源校验**。 |

## 6｜多模型路由与降级

### 面试官为什么问

单点依赖是大忌，天使轮预算还敏感 —— 路由 = 省钱 + 保命。这题还能顺带考出抽象设计能力。

### 答题要点

**为什么要多模型**：可用性（单家限流/故障）、成本（贵模型只做难任务）、能力（长上下文/多模态/工具调用差异）、**合规（数据出境）**、地域。

**抽象层设计（亮点，一定要讲）**：定义统一接口 `Chat(ctx, req) (Stream, error)`，每个厂商一个 adapter，业务层只面对统一消息模型。**切换模型 = 改配置，不改代码。**

| 路由维度 | 策略 | 我们的落地 |
| --- | --- | --- |
| 按任务分级 | 简单任务用小模型 | 意图识别 / 摘要 / 审核 → 轻量模型；人设对话 → 主力模型；复杂研判 → 旗舰模型 |
| 按成本 / 配额 | 先看余额和配额 | 主 key 配额告急时自动切备用 key |
| 按用户价值 | 付费/高价值会话走强模型 | 结合金币体系（见第 7 节） |
| 按合规 | 敏感数据不出境 | 文本走国内模型、实时语音走 Gemini Live |

**降级链**：主 → 备（异厂商同能力）→ 再备（同厂商另一 region）→ **兜底（预置话术，绝不返回 500）**。

**错误分类决定动作（背下来）**：

| 错误类型 | 动作 |
| --- | --- |
| 429 限流 / 余额不足 | 退避重试（尊重 `Retry-After`）→ 换备用 provider 或备用 key，同时告警 |
| 5xx / 连接失败 | 立即切备用 |
| 首包超时 | 切备用 —— **前提是流还没开始** |
| 内容审核拦截（如 DashScope `DataInspectionFailed`） | **不重试**，走审核/兜底话术 |
| 400 参数错误 / 401、403 | **不重试**，直接告警（这是代码或配置 bug） |

> **最重要的一条原则：流一旦开始就不能降级。** 已经推给客户端的 token 收不回来。降级决策必须发生在**首包之前** —— 这就是第 3 节讲"首包超时"的另一个理由。

**限流与配额**：单实例并发闸门（信号量）+ 分布式令牌桶（Redis + Lua）+ **按 provider 分桶**（共用配额会互相挤）；配额可预扣，失败回滚。**熔断**：连续失败率超阈值 → 打开 → 半开探测恢复。**没有熔断的重试就是雪上加霜** —— 上游挂了，重试会把连接池和 goroutine 全占满。

### 参考话术

> 多模型不是为了炫技，是三个很实际的压力逼出来的：**限流、成本、合规**。
>
> 限流是常态，高峰期单一 provider 一定会 429。所以我们做了完整的路由和降级链：主模型、异厂商备用、同厂商另一个 region，最后还有一层兜底话术。**底线是绝不因为我们上游的问题给用户返回 500。** 但我这里有一条很硬的原则：**降级只能在首包之前做**。流一旦开始往外推就没有回头路 —— 你已经推了 200 个字给客户端，这时候切模型，用户会看到前后两段语气完全不同、甚至互相矛盾的回复。所以降级判断挂在"首包超时"这个点上：超过阈值没收到第一个 chunk，才切备用。
>
> 另一个值得说的是**错误要分类**。不是所有错误都该重试：429 要退避重试，5xx 直接切备用，但**内容审核拦截不能重试** —— 那是模型的审核判定，重试十次结果一样，只会浪费配额；400 参数错误更不该重试，那是我们自己的 bug，应该直接告警。很多系统的重试逻辑写得粗暴，一律重试三次，结果把限流放大成了雪崩。
>
> 架构上我把它收敛成一层统一接口，业务代码只依赖我们自己的消息模型，每个厂商一个 adapter。所以**换模型是改配置，不是改代码**。这套东西做出来之后，我们试新模型、做 A/B 的成本非常低。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 切换模型后角色说话风格变了怎么办？ | 好问题。**人设卡是唯一事实源、跨模型共用**，我们把语气要求和一个固定的 few-shot 示例都写在角色卡里，上线前做同一批用例的跨模型对比。切模型是运维手段，体验一致靠 Prompt 不靠模型。 |
| 降级会不会把会话历史搞乱？ | 降级是**单请求粒度**的，不改会话历史；消息记录里存实际使用的模型，方便排查"为什么这轮回复怪"。灰度按 userId / sessionId hash 分流，对比 TTFT、审核拦截率、单会话成本和业务侧的留存转化。 |
| 备用模型能力不一样，Prompt 通用吗？ | 不完全通用。人设卡通用，但**结构化输出的 schema 要按模型能力调**（有的模型对 `json_schema` 支持不完整，要退回 `json_object` + Prompt 约束）。这类差异都封在 adapter 里。 |

## 7｜Token 成本与计费

### 面试官为什么问

**陪伴类产品的成本结构就是生死线**。能聊到这一层的候选人极少，答好了面试官会觉得你在用老板的视角想问题。

### 答题要点

**计费原理**：

- 按 token 计，**input / output 分开定价，output 通常是 input 的 2~5 倍**；
- **缓存命中**的 input 大幅打折（各家 10%~50%）；
- **reasoning 模型的思维链 token 按 output 计费**（很容易超预算）；
- 离线批处理接口（Batch API）通常半价。

| 档位 | 代表 | 典型用途 | 相对成本 |
| --- | --- | --- | --- |
| 旗舰 | GPT-4o / Claude Sonnet / 通义-Max | 复杂研判、长链推理 | $$$$ |
| 主力 | Gemini Flash / GPT-4o-mini / 豆包 | 人设对话 | $$ |
| 轻量 | DeepSeek-chat / Qwen-Turbo | 意图识别、摘要、审核 | $ |

> 具体价格以官网当期为准；国内模型普遍比海外便宜一个数量级，**缓存命中还能再降一半以上**。

**成本控制六招**：① 分层记忆替代全量历史（第 4 节）；② 模型分级路由（第 6 节）；③ 缓存（精确 hash + 语义缓存，人设介绍、常见问题这类高重复请求命中率很高）；④ **收紧 `max_tokens`** —— 陪伴聊天 200~300 token 足够，长回复反而出戏；⑤ 单会话预算上限，超了降级或提示；⑥ 非实时任务全部异步 / 批处理。

**成本归因**：每次调用落一条 usage 流水（模型、input/output tokens、耗时、归属用户/会话/功能），既用于对账，也用于定价迭代。**没有成本归因，就不知道哪个功能在亏钱。**

### 结合 LoveSpouse 金币计费（本节的杀手锏）

**商业模式**：用户充值 → 金币 → 消费。消费点：实时语音通话按分钟、付费媒体 / 剧情章节一次性解锁、部分高级互动。

**核心认知**：**不同交互的单次成本差 10 倍以上** —— 一条文字消息和一分钟实时语音完全不是一个量级（音频按秒折算 token，消耗远大于文本）。**定价如果按"感觉"定，一定会出现某个功能越用越亏。**

| # | 机制 | 为什么 |
| --- | --- | --- |
| 1 | **预扣 + 结算** | 通话前用 Redis Lua 原子预扣 N 分钟金币，结束按实际时长结算退补 —— 防"打完电话欠费跑路" |
| 2 | **幂等** | 通话 ID / 消息 ID 做幂等键（Redis `SETNX` + DB 唯一索引），重连、回调重投都不重复扣 |
| 3 | **跨实例通话控制** | 通话状态（双方、剩余时长、心跳）放 Redis，心跳续期 TTL；**TTL 过期自动挂断并停扣**（客户端崩溃不会一直扣钱）；用 Redis 原子脚本保证同一用户不会并发开两通电话 |
| 4 | **成本流水** | 每次模型调用记 usage（模型、tokens、耗时、归属）。**金币账本和 token 账本必须能对上**，这是定价迭代的依据 |

**一句话总结**：**金币是用户感知的价格，token 是我们真实的成本，两个账本必须能对上。**

### 参考话术

> 这个我特别有感触，因为 LoveSpouse 是**要收钱的**，成本控制不是技术优化，是商业模型的一部分。
>
> 先说成本侧。陪伴类产品的成本有个特点：**不同交互方式的成本差一个量级。** 一条文字消息，上下文恒定，可能就几百个 token；但一次实时语音通话，音频是按秒折算 token 的，一分钟的消耗比文字高得多。所以如果按"感觉"定价，很容易出现某个功能被用户薅爆、越用越亏。我们的做法是**每次模型调用都记一条 usage 流水** —— 模型、输入输出 token、耗时、归属到用户和功能 —— 然后按功能维度做成本归因。哪个功能的单次成本是多少，是有数的，定价才敢定。
>
> 再说计费侧，这块的工程坑比模型调用还多。**第一是预扣加结算**：通话开始前先原子预扣 N 分钟金币，结束按实际时长结算、多退少补 —— 不然用户打完电话余额是负的，你追不回来。**第二是幂等**：通话 ID 做幂等键，用户网络抖动重连、我们的回调重投，都不能重复扣费 —— 扣钱这件事，重复一次就是事故。
>
> **第三我觉得最值得说的是通话状态的跨实例控制。** 通话是有状态的：用户在哪个实例上、剩余多少时长、是不是还在线，我们都放 Redis。心跳续期 TTL，**TTL 过期就自动挂断并停止扣费** —— 因为客户端崩溃、断网、被系统杀进程时，它是不会给你发"挂断"的，只依赖客户端上报就会出现一直扣钱。另外我们用 Redis 原子脚本保证同一用户不会同时开两通电话，否则并发场景下余额会被扣两次。
>
> 一句话总结我的理解：**金币是用户感知的价格，token 是我们真实的成本，这两个账本必须能对上**，对不上就说明定价或者埋点有问题。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 长通话怎么实时扣？ | 分钟级循环扣（Redis Lua 原子操作）；余额不足提前 10 秒提示并**优雅结束**（不能硬切，陪伴产品体验优先）；剩余时长存 Redis，心跳续期。 |
| 用户掉线了还扣吗？ | 心跳 TTL 兜底，30~60 秒无心跳自动结束通话。已消费时长不退，**未开始的预扣部分退回**。 |
| 怎么防刷？ | 幂等键 + 频控 + **余额变更全部走原子脚本**（避免并发下扣成负数）+ 全量流水可审计。 |
| 成本这么高怎么赚钱？ | 模型分级 + 缓存 + 输出长度控制 + 单会话预算上限，把单次交互成本压到定价的安全倍数以内；高成本交互（语音）的定价倍率要高于文字。 |

## 8｜幻觉与内容安全

### 面试官为什么问

陪伴类产品的红线，也是国内做 AIGC 的合规要求。答得好说明你有"上线意识"。

### 答题要点

**幻觉成因（一句话五点）**：训练目标是"像人话"而不是"说真话"；知识有截止日期；没有依据时倾向编造；长上下文中间信息丢失；采样随机性放大。

| 缓解手段 | 说明 |
| --- | --- |
| RAG | 给事实依据，并要求"只依据给定资料回答，没有就说不知道"；配 `json_schema` 结构化输出，压缩自由发挥空间 |
| 引用溯源 | 要求输出"依据"字段（引用原文哪一段 / 哪条政策） |
| 后置校验 | 对关键字段（金额、编号、分数）做规则或二次模型校验，**必须可溯源** |
| 多 Agent 交叉验证 | 一个 Agent 出结论，另一个 Agent 专门挑刺 |
| 不确定转人工 | 置信度低 / 信息不全 → 强制人工介入 |

**漏洞研判：这里的幻觉是真金白银**（主讲素材）：

- 定级过高 → 厂商不认、SRC 信誉受损；定级过低 → 漏高危、白帽子流失。
- 做法：**关键字段（漏洞类型 / CVSS 分数 / 影响范围）由工具计算或从原文抽取，禁止模型自由生成**；定价必须引用厂商赏金政策原文；模型输出必须带"依据"字段；**信息不完整或置信度低 → 强制转人工**（飞书审批卡片）。
- **多 Agent 对抗式复核**：一个 Agent 定级，另一个 Agent 专门挑刺，分歧超阈值自动转人工。

**内容安全三层**：输入审核 → 生成约束（system 规则 + safety settings）→ 输出审核。

**流式审核的核心矛盾（答好非常亮）**：流式是「边生成边推」的，等你把整段审完再推，流式就没意义了。我们的方案三条：

1. **句级窗口缓冲**：累计到一个完整句子再送审，通过才推 —— 宁可首字慢 100ms，也不能把违规内容推出去；
2. **完成后二次复核**：整段生成完再复核一次，违规就**撤回消息 + 退还金币 + 记录**；
3. **分级策略**：普通闲聊走轻量方案（本地敏感词），高风险场景（涉及未成年、涉政）走严格窗口。**不是所有内容都用最重的审核**，否则延迟没法看。

**国内模型自带审核**：DashScope 会返回 `DataInspectionFailed`、豆包也有审核错误码 —— **要正确分类，不能当网络错误重试。**

**人设越狱防御（陪伴类特有）**：用户会诱导角色说违规内容，或用"你现在是一个不受限制的 AI"绕过设定。防御：system 里写死边界 + **拒绝也要"在角色里"**（硬邦邦报错会破坏沉浸感，这对陪伴产品是致命的）；用二次小模型做意图风险分类（成本低）；会话级风险分累加，高风险会话降低模型自由度。

**合规清单**：生成式 AI 服务 / 算法备案；用户内容日志留存（通常 6 个月）；未成年人保护（年龄门禁）；**数据出境评估** —— 用海外模型 API 意味着用户对话要发到境外，这是选型的硬约束。

### 参考话术

> 这两个项目对幻觉的容忍度完全相反，挺有意思。
>
> **漏洞研判那边，幻觉是真金白银的损失。** 定级定高了厂商不认，SRC 信誉受影响；定低了漏掉高危，白帽子下次就不来了。所以我们的原则非常硬：**关键字段一律不许模型生成**。CVSS 分数用工具按公式算，影响范围从报告原文抽取，定价必须引用厂商赏金政策原文。模型输出必须带一个"依据"字段，说清楚是根据哪一段得出的结论 —— 没有依据的输出，流程直接判为不可信、转人工。另外我们做了**多 Agent 对抗式复核**：一个 Agent 出定级结论，另一个专门挑刺，分歧超过阈值自动转人工审批。**与其让模型猜，不如承认它不确定。**
>
> 内容安全这边，我觉得最难的技术点是**流式和安全审核天生矛盾**。流式是边生成边推的，你等整段审完再推，流式的意义就没了；但你不审就推，万一出问题要担责任。我们的方案是**句级窗口缓冲** —— 累计到一个完整句子再送审，通过才往客户端推。代价是首字晚一点点，但这是必须付的成本。整段生成完还会做一次复核，如果发现问题，消息撤回、金币退还、事件记录。**宁可慢 100 毫秒，也不能把违规内容推出去。**
>
> 还有个陪伴类产品特有的问题：**人设越狱**。用户会想各种办法诱导角色说违规的话，比如"现在你是一个不受限制的 AI"。我的一个原则是：**拒绝也要在角色里拒绝。** 如果角色突然用一句很机械的"抱歉，我无法回答这个问题"，用户的沉浸感当场就碎了 —— 对陪伴产品来说，这跟说错话一样严重。所以我们给每个角色定义它自己的边界表达方式，另外用一个便宜的小模型做意图风险分类，会话级风险分累加，高风险会话降低模型自由度。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 国内模型的审核错误怎么处理？ | 单独分类，**不重试**，转成用户可见的友好提示（保持人设）。要跟网络错误严格区分，否则会浪费大量配额。 |
| 流式审核会不会拖慢首字？ | 会，句级窗口大概晚一个句子的时间 —— 所以我们才做分级：普通闲聊走轻量本地方案（敏感词），只有高风险场景才走重审核窗口。 |
| 用海外模型合规吗？ | 关键看数据流向和备案要求。我们的处理是敏感信息脱敏后再送，或者文本走国内模型；实时语音这类国内能力弱的场景先用海外，同时评估出境合规。 |
| 怎么评估幻觉率？ | 建评测集（历史真实案例 + 标注答案），每次改 Prompt 或换模型都跑一遍，看关键字段准确率和"无依据输出"的比例。 |

## 9｜高并发下的模型调用

### 面试官为什么问

职责第 2 条原文就是「保障高并发场景下的稳定性和可扩展性」。模型调用是整条链路里**最慢、最贵、最容易雪崩**的一环。

### 答题要点（八件套）

**① 连接池（Go 的默认值会坑你）**：

| 参数 | 默认 | 建议 | 原因 |
| --- | --- | --- | --- |
| `MaxIdleConnsPerHost` | **2** | 50~100 | 默认太小，高并发下反复建连，TLS 握手成本全吃进去 |
| `MaxConnsPerHost` | 0（无限） | 按上游配额设 | 保护上游也保护自己 |
| `ResponseHeaderTimeout` | 0 | 10s | 防上游黑洞 |
| `Client.Timeout` | 0 | **保持 0** | 流式场景必须靠 ctx 控（前面讲过） |

**② 并发闸门**：单实例用信号量限制 in-flight 请求数。**没有闸门，上游一限流你就雪崩** —— 所有请求一起超时、一起重试、把连接池占满。

**③ 分层超时**：

| 层 | 阈值 | 动作 |
| --- | --- | --- |
| 建连 | 3~5s | 重试下一个地址 / 切备用 |
| 首包（TTFT） | 10~15s | 切备用 provider（流未开始才可切） |
| 空闲（两个 chunk 之间） | 20~30s | 判定卡死，断开并降级 |
| 整体 | 60~120s | 强制结束，写失败状态 |
| 单次工具执行 | 5~10s | 超时把错误回填给模型（见第 5 节） |

**④ 重试 + ⑤ 熔断**：只重试**未产生副作用**的失败；指数退避 + **jitter**（防惊群）；尊重 `Retry-After`；最多 2~3 次；**流已开始不重试**。熔断按错误率 + 最小请求数触发、半开探测 —— **重试和熔断要配套**，只有重试没有熔断等于放大故障。

**⑥ 异步化削峰**：

- **实时路径**（用户在等）：只做「组装上下文 → 调模型 → 推流」。
- **异步路径**（丢 RabbitMQ）：记忆抽取、会话摘要、内容复核、成本统计、埋点。
- 好处：主链路耗时可控，下游慢不拖累对话；但**队列消费要限并发**（消费者数按上游配额算），否则堆积的队列会在恢复瞬间集中打爆模型。

**⑦ 会话串行（真实踩过的坑）**：同一个 session 的消息**必须串行处理**。用户快速连发两条、或多端同时发，两轮并发生成会互相看不见对方，上下文错乱。做法：`sessionId` 粒度的 Redis 分布式锁，或按 `sessionId` hash 路由到固定实例的队列。

**⑧ 背压与降级预案**：

- 客户端消费慢于模型产出 → 写缓冲增长。设 write deadline 和缓冲上限，超限**丢弃中间 delta**（最终消息以落库为准）。
- **兜底预案**：上游全挂或大范围限流时，产品要有"非 AI 模式"（预置语料、离线话术、只读历史），**不能让整个 App 不可用** —— 天使轮公司特别爱听这个。

### 参考话术

> 模型调用是整条链路里最慢、最贵、也最容易雪崩的一环，所以我在这一层做的事比别的地方都多。
>
> 先说一个 Go 的默认值坑：**`http.Transport` 的 `MaxIdleConnsPerHost` 默认是 2**。低并发看不出来，一上量就是每个请求都在重新建连、重新 TLS 握手，白白多几十上百毫秒，这个必须调。
>
> 第二是**并发闸门**。我们每个实例会限制同时在飞的模型请求数。这主要不是为了保护自己，而是**保护上游不被我们打爆** —— 你打到上游限流，会发现所有请求一起超时、一起重试，连接池瞬间占满，整个服务连锁挂掉。**宁可本地排队，也不要触发上游限流。**
>
> 第三是**超时一定要分层**。只有一个总超时是不够的：建连慢、首包慢、生成到一半卡住，这三种情况要区别对待。我们分了建连超时、首包超时、chunk 之间的空闲超时和整体超时，每层超时对应不同动作 —— 只有首包超时可以切备用模型。
>
> 还有一个我踩过的真实的坑：**同一个会话的消息必须串行处理**。用户手快连发两条，或者手机和平板同时在线，如果两轮生成并发跑，第二轮是看不到第一轮结果的，上下文直接错乱。后来我们用 session 粒度的分布式锁把它串起来 —— **并发控制不能只看机器，还要看业务语义。**
>
> 最后是**异步化**。用户等的路径上我只留三件事：组装上下文、调模型、推流。记忆抽取、会话摘要、内容复核、成本统计全部丢消息队列异步做。这样主链路耗时可预期，下游再慢也不拖累对话。但队列消费的并发也要卡住 —— 不然服务恢复那一瞬间，堆积的几千条消息会集中打爆模型。

### 追问预判

| 追问 | 你怎么答 |
| --- | --- |
| 上游限流了怎么办？ | 三层：本地并发闸门（不超配额）、退避重试、切备用；用户侧要么排队要么降级到小模型，并给一个符合产品的等待反馈（陪伴类产品不能用干巴巴的"系统繁忙"）。 |
| 你怎么知道系统快不行了？ | 看这几个指标：in-flight 请求数、上游错误率、TTFT p95、队列积压长度、账户余额、余额消耗速率。**余额告警特别重要，很多人不做。** |
| 队列积压了怎么处理？ | 先看是不是上游限流导致消费变慢。做优先队列：实时性要求高的记忆抽取优先，统计类任务降级或丢弃 —— **不是所有消息都同等重要**。 |
| 模型调用和数据库事务怎么配合？ | 绝不能把模型调用放进数据库事务，它可能几秒到几十秒，会长时间占着连接和锁。做法是先落"生成中"状态提交事务，拿到结果再开一个事务更新。 |

| 2 | 流式上线后变成"一次性刷出来"？ | Nginx `proxy_buffering` 默认开着，响应头加 `X-Accel-Buffering: no` 或关 buffering；`proxy_read_timeout` 默认 60s 要调大；gzip 也会造成缓冲。 |
| 3 | 客户端断线怎么办？会泄漏吗？ | 用 `Request.Context()` 派生上游 ctx，断开时**必须 cancel 上游请求**，否则 goroutine 泄漏且模型继续烧 token。 |
| 4 | TTFT 怎么优化？ | 两头：真实延迟（小模型、静态前缀进缓存、连接预热、编排并行化）+ 感知延迟（角色化的首包占位）。分段埋点定位瓶颈。 |
| 5 | 上下文超长怎么截？ | 分层：稳定事实键值化常驻 + 长期/会话摘要 + 近期原文；按 token 水位线（60%~70%）触发压缩，预留输出 token。 |
| 6 | Function Calling 完整流程？ | 注册 schema → 模型出多个 tool_call → 并发执行 → **用 tool_call_id 全部回填** → 再请求模型，直到不再有 tool_call；失败把错误回填让模型决策，设最大迭代数。 |
| 7 | 怎么防幻觉？ | 关键字段不许模型生成（工具算、原文抽）；输出强制带"依据"；后置溯源校验；不确定就转人工；漏洞研判里还有多 Agent 对抗复核。 |
| 8 | 怎么降成本？ | 分层记忆、模型分级路由、前缀缓存（**别把随机值塞进前缀**）、收紧 max_tokens、异步化批处理；每次调用记 usage 做成本归因，并和金币账本对账。 |
| 9 | 上游挂了/限流了怎么办？ | 本地并发闸门 → 退避重试（带 jitter）→ 切备用 provider → 熔断 → 兜底话术；**降级只能在首包之前**，流开始后没有回头路。 |
| 10 | 流式内容怎么审核？ | 句级窗口缓冲（审过再推）+ 完成后二次复核（违规撤回、退金币）+ 分级策略（闲聊走轻量、高风险走重审）。宁可慢 100ms 也不能推违规内容。 |
