## 二、LoveSpouse 一页纸（★ 主战场）

**一句话定位**：> 成人智能玩具的配套 App，硬件是实体玩具，App 提供虚拟角色陪伴，有长期记忆、剧情、实时语音和付费内容。

**我负责三块**：
1. **对话链路** — 意图识别 → 场景路由 → Prompt 组装 → 结构化回复（返回带情绪/动作/付费点字段）
2. **分层记忆系统** — 近期对话 / 会话摘要 / 长期摘要 / 稳定事实
3. **实时语音** — Gemini Live + 腾讯 IM + 金币计费 + 跨实例通话控制

**三个必答追问**：

| 追问 | 一句话答 |
| --- | --- |
| **腾讯 IM 为什么要幂等？** | > IM 是至少一次投递，会重复推。用消息 ID 在 Redis 去重，**关键是要原子**。重复处理会导致重复扣金币。 |
| **跨实例通话怎么控制？** | > **服务无状态，状态外置 Redis**。会话状态 + 会话到实例的映射，其他实例据此转发控制指令。这样实例才能随便扩容重启。 |
| **金币怎么保证不超扣？** | > Redis 做原子扣减保证并发安全，MySQL 落账。每次扣费带业务唯一 ID 保证幂等。语音按时长**分段扣**，中途挂断不会多扣。 |

**记忆系统四层口诀**：
> **近期对话保原文、会话摘要压本次、长期摘要跨会话、稳定事实抽结构。**

**开场认知（讲这个显得懂产品）**：
> 普通问答答完就完了，陪伴产品的价值在**关系**。但窗口有限、关系无限，所以要在有限 Token 里塞最有用的记忆。

## 四、三处边界的说法（★ 别踩坑）

| 领域 | 说法 |
| --- | --- |
| **微服务** | 先确定自己层次：**只用过 go-zero 的 API 层** → 「我们服务是分模块的，没拆成独立部署的集群。go-zero 的微服务能力我了解，配套 zrpc、服务发现、内置限流熔断，但没在需要拆分的规模上实践过。」<br>**绝不说**："我主导过服务拆分" |
| **链路追踪** | > 完整的没上，当时靠**日志 traceid 串联**排查，算是链路追踪的手工版。完整方案我了解，是 **OpenTelemetry** 那套——TraceID 全链路共享，SpanID + ParentSpanID 组成调用树，跨服务通过 header 或 gRPC metadata 透传，上报到 Jaeger 展示。 |

## 五、运维话术（★ 重点准备）

**主话术**：
> 我们**没有专职运维，服务是开发自己部署维护的**，这块我有实际做。写过 Dockerfile、用多阶段构建打小镜像、docker-compose 编排、服务器部署、Nginx 反代、HTTPS、日志排查都是我自己弄的。但像 Prometheus、Grafana 这种完整的监控告警体系没搭起来，当时主要靠日志和基础指标排查。**这块原理我了解，但没在生产完整落地过。**

**五个关键词**：
1. **多阶段构建** — 编译用 Go 镜像，运行只拷二进制，镜像从几个 G 降到十几 M
2. **CGO_ENABLED=0** — 静态编译，不依赖 glibc，才能跑在 alpine/scratch
3. **层缓存** — 先 COPY go.mod 再 `go mod download`，改代码不会让依赖层失效
4. **`proxy_buffering off`** — ★ 杀手锏：**Nginx 默认缓冲上游响应，会让流式输出变成一次性返回**。这是做 AI 流式必踩的坑，**串到 LoveSpouse 的流式响应上讲**
5. **版本 tag 不用 latest** — 回滚才能回得去；发布后探健康检查接口，不通过就回滚

**排查方法论**：
> **先止损再定位**（能回滚就回滚）；**先怀疑最近的变更**；看变更、看指标、看日志三交叉。

## 六、蓝牙话术（★ 被问到再用，别主动提）

**30 秒过渡话术**：
> 蓝牙这块我要坦诚说，**BLE 我没有直接做过**。但我做过**串口的外设通信**——收银系统里对接电子秤、打印机、钱箱，走的是自定义协议帧，本质是一样的：定义帧格式、下发指令、等应答、校验、状态同步。所以 BLE 的 GATT 这套模型我理解起来不陌生。
>
> GATT 的层次是 Service 包 Characteristic，Characteristic 有 Read/Write/Notify 几种属性，下发指令就是往可写的 Characteristic 写数据，状态同步用 Notify 订阅。**跟串口的差别主要是传输层——BLE 有 MTU 限制要分包，连接参数会影响功耗和实时性。**
>
> 这块我上手应该不慢，而且咱们说的**指令下发、状态同步、OTA 升级**，本质上都是设备通信协议的设计问题，跟我做过的外设通信是同一类问题。

**三个必须说对的点**：
1. **GATT 层次**：Profile → Service → Characteristic → Descriptor
2. **Notify vs Indicate**：Notify 不确认、Indicate 要确认（更可靠但更慢）
3. **MTU 与分包**：默认 23 字节，可协商到更大，超了要拆包重组

**OTA 要点**：版本查询 → 下发升级指令 → 分片传输固件 → 校验 → 切分区 → 重启 → 上报结果。**关键是 A/B 双分区 + 校验失败回滚，防止变砖**。服务端负责固件版本管理、灰度发布、结果统计。

## 七、技术关键词速查（扫一眼，被问到别卡壳）

**Go 并发**：GMP 调度 / channel 无缓冲 vs 有缓冲 / sync.Mutex 正常模式与饥饿模式 / context 四种衍生 / **goroutine 泄漏（pprof goroutine 视图定位）**

**高并发**：限流（令牌桶/漏桶/滑动窗口）、熔断降级、**先止损再定位**、服务无状态才能水平扩展、**WebSocket 多实例路由（Redis Pub/Sub 广播）**

**MySQL**：B+ 树索引 / 最左前缀 / 覆盖索引免回表 / EXPLAIN 看 type 和 Extra / MVCC（undo log + read view）/ 间隙锁 / 慢查询治理

**Redis**：**缓存三兄弟**——穿透（布隆过滤器/空值缓存）、击穿（互斥锁）、雪崩（过期时间打散）/ **分布式锁**（SETNX + 唯一 value + Lua 删 + 看门狗续期）/ 热 Key 大 Key 治理

**大模型接入**：SSE 流式（`data:` 前缀 + `[DONE]`）/ **首字延迟 TTFT** / Function Calling / 多模型路由降级 / Token 成本控制 / 多模型兜底
