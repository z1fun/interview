## 一、核心策略

这场面试的胜负手只有一句话：**让面试官觉得"这个人做过和我们一模一样的产品"**。

你的 LoveSpouse 和这家公司的产品几乎是同款——AI 情感交互 + 虚拟角色 + 配套智能硬件 + App。这不是"相关经验"，这是**同赛道同形态的直接经验**。所以：

- 自我介绍**不要把六个项目平铺**，要重锤 LoveSpouse，其他一句话带过。
- 主动往 AI 接入、对话链路、记忆系统上引——这是你的主场。
- **蓝牙不要主动提**。等面试官问，用 06 篇的话术接。

**禁忌**：
- ❌ 不要背简历流水账（"我 2021 年入职…2023 年入职…"）——面试官手上有简历
- ❌ 不要说"我什么都能做"——天使轮公司要的是能扎进 AI 方向的人

## 四、3 分钟版（CTO / 创始人面 / 让你详细讲）

在 2 分钟版基础上，展开以下两段（插在 LoveSpouse 介绍之后）：

> 我想重点讲一下记忆系统这块，因为它是这类产品最核心的技术点之一。
>
> 情感陪伴产品跟普通问答机器人的区别在于，用户要感觉"这个角色记得我"。但大模型的上下文窗口是有限的，你不可能把几个月的聊天记录全塞进去。
>
> 我们的做法是分层：最近的对话保留原文，保证短期连贯；再往外的历史，用模型压缩成会话摘要；更长周期的，压缩成长期摘要；另外还有一类叫稳定事实，就是用户明确告诉过你的、需要长期记住的关键信息，比如称呼、喜好、重要的日期，这类不进摘要，直接结构化存起来。
>
> 每次组装上下文的时候，按 Token 预算把这些层次拼起来，保证既不失忆，又不超窗口。这块的难点在于摘要的时机和粒度——摘早了丢细节，摘晚了浪费 Token。

> 实时语音这块也有几个坑。我们接的是 Gemini Live，它是端到端的实时语音接口，跟传统的 ASR → LLM → TTS 三段式不一样，延迟低很多。但它带来几个工程问题：一是音频流要走 WebSocket 双向传输，二是要处理用户打断 AI 说话的场景，三是通话是长时任务，用户在哪个实例上、计费怎么算，都需要额外设计。
>
> 我当时做的是把通话会话状态管起来，配合金币计费做实时扣减，跨实例的通话控制用 Redis 做协调。

## 五、LoveSpouse 主项目讲述脚本（重点，背熟）

### 5.1 一句话定位（被问"介绍一个你最有代表性的项目"时）

> 我讲一下 LoveSpouse 这个项目吧，它是我做过的跟咱们业务最接近的一个。

### 5.2 完整 STAR 脚本

**S — 背景**

> 这是一个成人智能玩具的配套 App，硬件是实体玩具，App 里提供虚拟角色陪伴。用户可以选不同的角色，每个角色有自己的人设和声音，可以文字聊天也可以语音通话。产品想解决的是"陪伴感"——所以角色要有长期记忆、有剧情推进、有多语言支持，另外有一部分内容是付费解锁的，用金币体系。

**T — 我的职责**

> 我在后端主要负责三块：
> 一是**数字人的对话链路**，从消息进来怎么识别意图、路由到哪个场景、怎么组装 Prompt、怎么把模型返回变成结构化数据给 App；
> 二是**分层记忆系统**，这是我投入最多的地方；
> 三是**实时语音通道**，接的 Gemini Live，以及配套的金币计费和跨实例通话控制。

**A — 具体做法**

> **对话链路**这块，我没有让所有消息都直接丢给大模型。前面加了一层意图识别和场景路由——先把用户的话分类，比如是闲聊、是剧情推进、还是要触发付费互动，不同类别走不同的 Prompt 模板和不同的处理流程。这样做的好处是可控性高，也省钱，因为不是每一句都需要全量的上下文和最强的模型。
>
> 最终返回给 App 的是结构化的数据，不是纯文本。除了回复内容，还会带上情绪标记、表情动作、有没有付费点这些字段，App 拿到就能直接渲染，不需要再做解析。
>
> **记忆系统**是分四层的：近期对话保留原文，会话摘要按轮次触发压缩，长期摘要按更长的周期压缩，稳定事实单独结构化存储。组装上下文的时候按 Token 预算分配每一层的额度。
>
> **实时语音**接的是 Gemini Live。它跟传统三段式不一样，是端到端的，延迟明显低。工程上要处理音频流的双向传输、用户打断、还有通话状态管理。
>
> **消息通道**用的是腾讯 IM，这里有个坑——IM 的消息投递是 at-least-once 的，可能重复推给你，所以必须做幂等。我们是用消息 ID 做去重，保证同一条消息只处理一次，否则用户会收到重复回复，而且金币会被重复扣。

**R — 结果**

> 【**这里必须填你真实的结果**，不要编。可以讲的方向：】
> - 角色数量 / 支持语言数 / 日活消息量 / 语音通话时长
> - 首字响应延迟从多少优化到多少
> - 记忆系统上线后多轮对话的连贯性改善（比如用户反馈、会话时长提升）
> - 付费转化或金币消耗的变化
>
> **如果确实没有可量化的数字，用这个说法**：
> > 这块我们当时没有做很细的埋点统计，我能说的是，记忆系统上线前，用户聊到第三四轮之后角色就会开始"失忆"，上线之后跨会话的连贯性明显好了，用户反馈里提到这点的也少了。

### 5.3 追问预判与答法（必看）

| 面试官可能问 | 答题要点 | 参考话术 |
| --- | --- | --- |
| 意图识别怎么做的？规则还是模型？ | 诚实说清楚；如果是模型分类要给类别设计 | > 我们用的是模型做分类，不是纯规则。类别不是很多，主要是区分闲聊、剧情推进、付费互动引导这几类。规则那套我们试过，但用户表达太发散，维护成本高。 |
| 分层记忆具体怎么分层？每层存什么？ | 四层要能一口气说清 | 见 05 篇，那里有完整答法 |
| 摘要什么时候触发？用什么模型？ | 触发时机是关键考点，要说出取舍 | 见 05 篇 |
| 怎么保证角色人设不崩？ | System Prompt + 校验 + 兜底 | 见 05 篇 |
| 腾讯 IM 为什么要幂等？怎么做的？ | at-least-once 语义 + 去重表/Redis | > IM 的消息投递是至少一次，网络抖动或者客户端重连都可能重复推。我们是用消息 ID 在 Redis 里做去重，处理前先查、处理时原子写入，保证同一条只处理一次。这不只是体验问题，因为我们的回复会扣金币，重复处理就是重复扣费。 |
| Gemini Live 接入难点是什么？延迟多少？ | 双向流 + 打断 + 长连接管理 | 见 08 篇（实时语音部分） |
| **跨实例通话控制怎么做的？**（★高概率，考分布式） | 这是你能讲的最接近"分布式"的真实场景，一定要答好 | > 通话是长时任务，用户在通话期间可能因为负载均衡落到不同实例，或者服务重启要迁移。我们的做法是把通话会话的状态放在 Redis 里，不放在单个实例的内存里，实例本身做到无状态。然后通过一个会话到实例的映射表，让其他实例知道该把控制指令发给谁。通话结束后的计费和状态落地再统一写回。 |
| 金币计费怎么保证不超扣 / 不漏扣？ | 并发扣减 + 幂等 + 对账 | > 扣费是典型的并发场景。我们用 Redis 做实时扣减，保证原子性，MySQL 做最终落账。每次扣费都带业务唯一 ID，保证幂等。语音通话这种按时长计费的是分段扣，不是一次性扣完，这样用户中途挂断也不会多扣。 |
| 为什么选 Gemini Live 而不是自己拼 ASR+LLM+TTS？ | 延迟对比 + 成本对比 + 可控性取舍 | > 主要图延迟。三段式每一段都有网络往返和排队，串起来通常要一到两秒以上，对话会有明显的"等"的感觉。端到端方案把这一段压得很低，体验差别很大。代价是可控性差一些，中间过程拿不到细粒度的中间结果。 |
| 这个项目做了多久？你一个人做后端吗？ | 如实回答，团队小是加分不是减分 | > 项目大概做了四个月。后端不是我一个人，我们是【填真实人数】。 |

## 七、项目讲述的通用框架与禁忌

### 7.1 讲述框架（任何项目都套这个）

```
一句话定位 → 背景与目标 → 我的职责（强调"我"不是"我们"）→
技术难点（挑 1-2 个讲透）→ 我的解法 → 结果/收获
```

**关键：不要平均用力。** 挑一个技术难点讲透，比把六个功能都念一遍强十倍。

### 7.2 禁忌

- ❌ **不要用"我们"代替"我"**——面试官想知道**你**做了什么。说"我们团队做了 X，我负责其中的 Y"。
- ❌ **不要只讲功能不讲难点**——"我做了聊天功能"是废话，"我解决了上下文窗口不够的问题"才是信息。
- ❌ **不要编造数字**——被追问口径答不上来，比没有数字糟糕得多。
- ❌ **不要贬低前公司**——"那个项目技术很烂"会被理解为你不好合作。
- ❌ **不要一口气讲超过 3 分钟**——讲完主动停一下，看面试官反应。

### 7.3 万能过渡句（讲不下去或想引导话题时用）

> 这块展开讲会比较长，不知道您更想听哪部分？是记忆系统的设计，还是实时语音的工程问题？

> 这个问题我们在项目里也踩过坑，不过可能跟咱们的具体场景不太一样，您想了解我的思路还是具体实现？

**作用**：把"输出"变成"对话"，同时探出面试官真正关心的方向。

## 九、练习方法（限时 40 分钟）

1. **前 10 分钟**：把 60 秒版和 2 分钟版各读 3 遍，标记出你读不顺的地方，改成你自己的话。
2. **接下来 15 分钟**：**录音**。用手机录一遍 2 分钟版，回放听——你会发现自己有口头禅、语速过快或逻辑断层，改掉。
3. **接下来 15 分钟**：把 LoveSpouse 的 STAR 脚本讲一遍，重点练 5.3 追问表里标★的那几题（腾讯 IM 幂等、跨实例通话控制、金币计费）。

**验收标准**：能在不看稿的情况下，2 分钟内讲完自我介绍，3 分钟内讲完 LoveSpouse 且被随机打断后能接回来。
