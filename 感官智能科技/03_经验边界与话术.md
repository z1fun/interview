# 03 · 经验边界与话术

> **本文件用法**：处理简历中三处需要小心的地方——**微服务、链路追踪、分布式**。核心原则是：**不编造项目故事，但把真做过的事用正确的语言讲出来，把没做过的补到"讲得清原理"**。
>
> 面试前 30 分钟通读一遍，重点记住第六节的四条救场模板。

---

## 一、处理原则

### 1.1 为什么不能硬编

**编造的经历在面试里活不过三个问题。** 比如你说"我主导过服务拆分"，接下来必然是：

> 拆了几个服务？→ 按什么维度拆的？→ 服务间怎么通信的？→ 注册中心用的什么？→ 跨服务的事务怎么处理的？→ 拆分后遇到过什么问题？

到第三个问题就崩了。而崩掉的不只是这一个问题——**面试官会开始怀疑你简历上的所有内容**，包括你真实做过的 AI 项目，那才是真正的损失。

### 1.2 正确的做法

| 层次 | 做法 |
| --- | --- |
| **真做过的** | 用准确的行业术语讲出来，讲细节、讲取舍、讲踩过的坑 |
| **半懂的** | 说清原理 + 明确边界（"我了解，但没在生产落地过"） |
| **完全不会的** | 坦诚 + 展示学习路径和判断力，不要硬扯 |

### 1.3 一个关键认知

**你其实做过不少"分布式"的事，只是没用那个词包装。** 对照一下：

| 你做过的事 | 它其实是 |
| --- | --- |
| 腾讯 IM 消息幂等处理 | **分布式系统的幂等设计**——这是分布式面试的核心考点 |
| 跨实例通话控制 | **分布式会话管理 / 分布式协调**——需要分布式锁或状态外置 |
| RabbitMQ 消费业务数据 | **消息队列的可靠性、顺序性、重复消费**——分布式异步通信的核心 |
| 金币计费的并发扣减 | **分布式环境下的并发控制与最终一致性** |
| 服务无状态 + Redis 外置状态 | **水平扩展的前提条件** |

**这些全是分布式的核心议题。** 你不需要吹"我设计过分布式架构"，只需要把上面这些讲清楚——面试官自然会认为你**懂分布式**，而且比背概念的人可信得多。

**这就是"包装"的正确姿势：不是加形容词，是把真事实的术语说对。**

## 二、微服务：真实边界与说法

### 2.1 先搞清楚你的真实情况

go-zero **本身就是一个微服务框架**。你用它写了服务，这件事本身就是"微服务相关经验"。区别只在于深度：

| 层次 | 内容 | 自检 |
| --- | --- | --- |
| **A. 只用 API 框架** | 用 go-zero 的 rest 部分写 HTTP 服务，没用 RPC | ☐ |
| **B. 用过 RPC** | 用 goctl 生成过 proto 和 RPC 代码，服务间通过 zrpc 调用 | ☐ |
| **C. 接触过服务治理** | 配过 ETCD 做服务发现、用过内置的限流熔断 | ☐ |
| **D. 主导过拆分** | 参与设计过服务怎么拆、边界在哪 | ☐ |

**回忆一下 POS 数据贯通项目**（go-zero + gRPC + ETCD + Protobuf）：如果那里你写过 proto、调过 RPC，那你至少是 B；如果 ETCD 是你配的，你就是 C。

### 2.2 按层次对应的话术

**如果你是 A**：

> 我们用 go-zero 做服务框架，但主要是用它的 API 层，服务是按业务模块划分的，不过没有拆成独立部署的微服务集群，还是一个服务里分模块。
>
> go-zero 的微服务能力我了解，它配套有 zrpc、服务发现、内置的限流熔断，用 goctl 生成代码。原理我清楚，但没有在需要拆分的规模上实践过。

**如果你是 B**：

> 我们用 go-zero 做服务框架，服务之间是通过 gRPC 通信的，proto 文件用 goctl 生成。相比 HTTP，gRPC 用 Protobuf 序列化，体积小、性能好，而且接口定义是强类型的，改接口的时候编译期就能发现不兼容。
>
> 服务发现用的是 ETCD，服务启动时把自己的地址注册上去，调用方从 ETCD 拿到可用实例列表。这样服务扩容或者重启，调用方不用改配置。

**如果你是 C**：

> 我们用 go-zero，服务间走 gRPC，服务发现用 ETCD。go-zero 本身内置了自适应限流和熔断，我们在配置文件里配了阈值。这块的体感是，框架把治理能力封装好了，业务代码里不用自己写，但要知道它什么时候会触发、触发之后是什么表现。

**⚠️ 如果你是 A 或 B，绝对不要说**："我主导过服务拆分""我设计过微服务架构""我做过服务治理"。

### 2.3 被问"微服务怎么拆分"——怎么答

**这是一个设计题，不是经历题。** 你完全可以用"我的理解"来答，这不涉及撒谎：

> 微服务拆分我没有主导做过，但我的理解是，拆分的前提是**业务边界清晰**，而不是技术上有多少服务。常见的拆法有按业务领域拆，比如用户、订单、支付各自独立；也有按读写分离拆的。
>
> 我觉得比"怎么拆"更重要的是"要不要拆"。服务拆开之后会引入很多新问题：跨服务的事务、数据一致性、链路追踪、部署复杂度、联调成本。如果团队规模不大、业务还在快速变化，过早拆分反而拖慢迭代。我倾向于先模块化，等某个模块确实有独立的扩容需求或者团队要独立负责了，再拆出去。

**这段回答的杀伤力在哪**：

1. 诚实说没主导过，**安全**；
2. 给出了拆分的维度，**有料**；
3. 最后一段展示了**技术判断力**——知道什么时候不该拆，这比知道怎么拆更值钱。很多面试官会在这里对你改观。

### 2.4 微服务配套知识（被追问时的弹药）

| 追问 | 答题要点 |
| --- | --- |
| 服务间怎么通信？ | > 同步用 gRPC 或 HTTP，异步用消息队列。同步调用简单直观但会耦合、有雪崩风险；异步解耦但增加复杂度、要处理消息可靠性。 |
| 服务发现怎么做？ | > 服务启动时注册到注册中心（ETCD/Consul/Nacos），调用方从注册中心拿实例列表并做负载均衡。ETCD 用的是 Raft 协议保证一致性。 |
| 跨服务事务怎么办？ | > 强一致的分布式事务（2PC、TCC）代价大，业务上一般用最终一致性：本地消息表、事务消息、或者 Saga 补偿。核心是每一步都要幂等，并且有补偿机制。 |
| 服务雪崩怎么防？ | > 熔断、限流、降级三件套。调用下游要设超时，超时了要快速失败，不能无限等待把线程/goroutine 拖死。 |
| 链路追踪怎么做？ | 见下一节。 |

## 三、链路追踪：诚实版 + 原理

### 3.1 你没做过，但有替代方案

**你实际上用过 traceid 做手工链路串联**（这是很多小团队的做法）。所以话术是：

> 完整的链路追踪系统我们没上，当时是用日志里的 traceid 做手工串联的——请求进来生成一个唯一 ID，往下游调用的时候透传下去，所有相关日志都带上这个 ID，排查时 grep 一下就能还原整条链路。
>
> 完整的方案我了解。核心是 OpenTelemetry 这套标准：在代码里埋点，每次操作生成一个 Span，同一条请求链路上的所有 Span 共享一个 TraceID，各自有 SpanID，通过 ParentSpanID 组成调用树。跨服务的时候 TraceID 通过 HTTP header 或者 gRPC 的 metadata 透传。数据上报到 Jaeger、Zipkin 这类后端，就能看到一个请求在各个服务上分别花了多少时间，瓶颈在哪一目了然。
>
> 我们当时服务数量不多，日志 traceid 够用了。如果服务拆得多，这套是刚需。

### 3.2 关键词（能说出来就够了）

| 词 | 一句话解释 |
| --- | --- |
| **Trace** | 一次完整的请求链路 |
| **Span** | 链路中的一个操作单元，比如一次 RPC 调用、一次数据库查询 |
| **TraceID** | 整条链路的唯一标识，全链路共享 |
| **SpanID / ParentSpanID** | 标识自己和父节点，用来还原调用树 |
| **Context 透传** | 跨进程传递 TraceID 的机制（HTTP header / gRPC metadata） |
| **OpenTelemetry** | 厂商中立的埋点与上报标准，是目前的行业共识 |
| **Jaeger / Zipkin** | 链路数据的存储与展示后端 |

### 3.3 ⚠️ 不要做的事

- ❌ 不要说"我们用 SkyWalking / 我们搭过 Jaeger"——被问"怎么部署的""采样率怎么配的"立刻穿帮
- ❌ 不要把 traceid 手工串联说成"链路追踪系统"——这是偷换概念，被追问会很难看
- ✅ **正确姿势**：说"日志 traceid 串联，是链路追踪的手工版"——**主动点破它是简化版**，反而显得你清楚完整方案长什么样

## 四、分布式：你能讲的真话

**这部分你有真货，要敢讲。** 参考第一节的对照表，这些都是你真做过的分布式问题：

### 4.1 幂等设计（★ 必讲，你的强项）

> 幂等在分布式里是个基础但关键的问题。我们做腾讯 IM 对接的时候必须处理这个——IM 的消息投递是至少一次的语义，同一个消息可能推给你两次，网络抖动、客户端重连都会造成重复。
>
> 我们的做法是给每条消息一个业务唯一 ID，处理之前先查这个 ID 有没有处理过。关键是**查询和写入要有原子性**，不然两个重复消息同时进来还是会重复处理。简单做法是用 Redis 的 SETNX，或者数据库的唯一索引兜底——让数据库的唯一约束来保证，插入冲突就说明处理过了。
>
> 这个不只是体验问题。我们的回复会扣金币，重复处理就是重复扣费，用户会投诉的。

**这段为什么强**：把"去重"这个小功能，讲成了分布式幂等设计的完整方案（唯一 ID + 原子性 + 兜底），而且有业务后果做支撑。

### 4.2 分布式会话与状态外置（★ 必讲）

> 我们的语音通话是长时任务，用户在通话期间可能因为负载均衡落到不同实例上，服务重启也可能要迁移。如果把通话状态放在实例的内存里，就会出问题——用户在 A 实例建立的通话，下一个请求打到 B 实例，B 完全不知道这回事。
>
> 所以我们的原则是**服务本身无状态，状态外置到 Redis**。通话会话的状态存在 Redis 里，另外维护一个会话和实例的映射关系，这样其他实例知道该把控制指令转给谁。通话结束的时候再统一把计费和状态落回数据库。
>
> 这也是服务能水平扩展的前提——实例无状态，才能随便加机器、随便重启。

**这段为什么强**：这是**真正的分布式会话管理**，而且是很多候选人答不上来的场景题。你是真做过的。

### 4.3 消息队列的可靠性（你有真经验）

> RabbitMQ 这块主要关注三件事：
> 一是**消息不能丢**——生产者要开 confirm 确认，队列和消息要持久化，消费者要手动 ack 而不是自动 ack，处理成功才确认；
> 二是**不能重复消费**——所以消费端必须幂等，道理跟前面说的一样；
> 三是**消费积压**——要有监控看队列堆积量，积压了要么加消费者，要么优化消费逻辑。实在处理不了的进死信队列，别把整个队列堵死。

### 4.4 缓存一致性

> 缓存和数据库的一致性是经典问题。常规做法是 Cache Aside：读的时候先查缓存，没有再查库并回写；写的时候先更新数据库，再删除缓存。
>
> 为什么是删缓存不是更新缓存？因为并发更新的时候，两个写请求的缓存更新顺序可能和数据库的更新顺序不一致，会留下脏数据，删除则相对安全。
>
> 严格一致很难做到，一般追求最终一致，配合过期时间兜底。要求更高的可以订阅数据库的 binlog 来失效缓存。

### 4.5 ⚠️ 边界声明（主动说，别等被问）

如果面试官追问"你们服务是怎么部署的、有几个服务"，**主动交代**：

> 我要说明一下，我们的服务数量不多，没有到需要完整的微服务治理体系的规模。所以像服务网格、完整的链路追踪这些，我是了解原理但没有实际落地。我的分布式经验更多是在具体的点上——幂等、状态外置、消息可靠性这些。

**主动划边界的好处**：面试官会觉得你**可信**，而且清楚自己的位置。这比被问穿之后狼狈解释强一百倍。

## 六、救场模板（★ 最重要，背熟）

### 6.1 完全不会的题

> 这块我没有实际做过，不太好瞎说。不过我可以讲讲我的理解——【说出你知道的部分】。如果实际要做，我会先去搞清楚【XX】，因为这块的风险主要在【XX】。

**要点**：承认边界 → 给出理解 → 展示你会怎么入手。**"不太好瞎说"这句话是加分项**，它传递的是"这个人不吹牛"。

### 6.2 半懂的题

> 我了解原理，但没有在生产环境完整落地过。原理是【XX】，实际做的时候要重点考虑【XX】。

**要点**：明确划出"知道"和"做过"的分界。面试官据此判断你的真实水平，**不会觉得你在骗人**。

### 6.3 需要思考时间

> 我理一下思路，稍等。

或者（更主动）：

> 这个问题我从几个角度想一下：先看【XX】，再看【XX】。

**要点**：**不要沉默超过 5 秒**，也不要不懂装懂地乱说。说出来你在想什么，比沉默好。

### 6.4 答错了被纠正

> 您说得对，我这里理解偏了。我想一下——【复述正确的思路】。谢谢指正，这块我回去补一下。

**要点**：**立刻承认，不要辩解，不要嘴硬**。面试官看的是你面对错误的态度，不是你会不会这道题。**嘴硬才是真的减分**。

### 6.5 被质疑经历真实性

如果面试官追问细节发现你答不上来，**坦诚止损**：

> 这个细节我记不太清了，项目过去有一段时间了，我不想说一个不确定的答案误导您。我能确定的是【你确实记得的部分】。

**要点**：**宁可说记不清，也不要现编**。说"记不清"是正常的，说错了被抓住是致命的。

### 6.6 万能兜底

> 这块我确实没做过，是我这次的短板。不过我觉得以我的经验，上手应该不慢——我做过的【XX】跟它是相通的，都是【XX】。如果入职后需要，我可以快速补上。

**★ 蓝牙问题就用这个模板**，具体话术见 06 篇。

## 七、面试前 5 分钟速记

1. **微服务**：确定自己是 A/B/C 哪一层，用对应话术。**绝不说"主导过拆分"**。
2. **链路追踪**：说"日志 traceid 串联，是链路追踪的手工版"，然后讲 OpenTelemetry 原理。
3. **分布式**：**这四个你都能讲**——幂等设计（IM）、状态外置（跨实例通话）、消息可靠性（RabbitMQ）、缓存一致性。这是你的真货。
4. **主动划边界**：「我们的服务数量没到需要完整微服务治理的规模，所以服务网格、链路追踪这些我了解原理但没落地。我的分布式经验更多在具体点上——幂等、状态外置、消息可靠性。」
5. **救场四句**：
   - 不会 → 「这块我没有实际做过，不太好瞎说」
   - 半懂 → 「我了解原理，但没在生产完整落地过」
   - 想一下 → 「我理一下思路」
   - 答错 → 「您说得对，我这里理解偏了」
