## 第一部分：Go 并发核心（八股速答）

### 1.1 GMP 调度模型

**一句话答案**：G 是 goroutine，M 是内核线程，P 是逻辑处理器（持有本地队列和 mcache）；M 必须绑定 P 才能执行 G，P 的数量由 `GOMAXPROCS` 决定（默认 = CPU 核数）。

| 角色 | 是什么 | 关键点 |
| --- | --- | --- |
| **G** | goroutine 的运行实体 | 栈（初始 2KB）+ 指令指针 + 状态（`_Grunnable/_Grunning/_Gwaiting/...`） |
| **M** | OS 线程 | 由内核调度；进入 syscall 被阻塞时会把 P 交出去（handoff） |
| **P** | 逻辑处理器 | 数量 = GOMAXPROCS；持有**本地运行队列 LRQ（最多 256 个 G）**、mcache（无锁内存分配） |

**调度流程**：`go f()` → `newproc` 创建 G → 优先放当前 P 的 `runnext`（下一个优先执行），否则进 LRQ → 调度循环 `schedule()` 从 `runnext → LRQ → GRQ（全局队列，有锁）→ 其他 P 偷` 取 G → `execute()` 在 M 上跑。

**为什么需要 P**（高频追问，必答三点）：
1. **解耦 G 与 M**：G 不再直接绑线程，几十万个 G 分时复用少量 M。
2. **减少锁竞争**：LRQ + mcache 都是 P 私有的，G 的创建、入队、内存分配大多无锁；没有 P 就只能全部抢 GRQ 的全局锁。
3. **并行度可独立控制**：`GOMAXPROCS` 决定同时跑多少个 G，与机器线程数解耦。

**work stealing（偷）**：P 的 LRQ 空了 → 先看 GRQ → 再随机挑一个受害者 P，**偷走它一半的 G**（`runqsteal`）。这是负载均衡的关键，保证没有 P 闲着而别的 P 排队。

**handoff（移交）**：G 发起阻塞式 syscall（如文件 IO）时，M 会被内核挂起，此时 runtime 把**这个 M 上的 P 摘下来**（`entersyscall → releasep`），交给其他空闲 M 继续跑别的 G；syscall 返回后 M 尝试抢回一个 P，抢不到就把 G 放到 GRQ 并休眠。**sysmon**（runtime 的监控线程，不需要 P）会兜底：P 在 syscall 中阻塞超过约 **20μs** 就强制 retake。

**抢占式调度（版本演进，能说出 1.14 就赢了）**：
- **Go 1.14 之前是协作式**：只在函数序言检查 `stackguard0` 的抢占标记（本质是栈增长检查点）。所以 `for {}` 这种无函数调用的死循环**永远无法被抢占**，会把 GC 的 STW 卡住（表现为整个程序停顿）。
- **Go 1.14 起基于信号的异步抢占**：sysmon 发现某个 G 连续运行超过约 **10ms**（`forcePreemptNS`），就给对应的 M 发 **SIGURG** 信号，M 的信号 handler 直接把当前 G 置为可抢占状态、重新走调度。协作式检查点仍然保留（成本更低，优先走那条路）。

**常见追问**：
- *GOMAXPROCS 设成多少合适？* → 默认（= 核数）通常最好。CPU 密集型不要超配；大量 syscall/IO 阻塞的场景没必要调大（阻塞时 P 会自动 handoff，不会浪费）。容器里注意 `automaxprocs`，否则可能拿到宿主机的核数。
- *一个 G 能占满一个 M 吗？* → 能，抢占点会救场，但**密集纯计算的 goroutine 仍会拖慢同 P 上其他 G 的响应**，这类任务要主动 `runtime.Gosched()` 或分片。
- *P 的数量能超过 CPU 核数吗？* → 可以设，但同一时刻真正并行执行的仍是核数个，多出来的 P 只会增加切换开销。

### 1.2 goroutine

**一句话答案**：goroutine 是 runtime 调度的用户态协程，初始栈 2KB 且**按需扩容**，创建成本是百纳秒级；线程是内核调度、栈 MB 级、创建和切换都要陷入内核。

| 维度 | goroutine | OS 线程 |
| --- | --- | --- |
| 栈 | **初始 2KB**，按需翻倍扩容/缩容，64 位上限默认 1GB | 固定 1~8MB，创建时确定 |
| 创建开销 | 百纳秒级（只分配 G + 2KB 栈） | 微秒~毫秒级（内核对象 + MB 栈） |
| 切换成本 | 用户态，约百纳秒（只存活的寄存器进 G 的 sched） | 陷入内核，约 1~2μs |
| 调度 | GMP，用户态 | OS 调度器，抢占式 |
| 通信 | channel（CSP：通过通信共享内存） | 共享内存 + 锁 |
| 数量级 | **十万~百万** | 几千个就开始吃内存 |

**栈扩容机制**：栈溢出检查点在函数序言（`stackguard0`）→ 触发 `morestack` → 申请**两倍**大小的新栈 → 把旧栈内容拷过去 → 老栈后续被 GC 回收（不是 free）。所以「栈上取地址」是安全的，Go 会帮你把指针搬到新栈。

**数量上限与实践中如何控制**（面试爱问，你的答案是「我们在项目里怎么控」）：
- 理论上没有硬上限，**内存和 GC 压力**才是瓶颈（一个 G 至少 2KB 栈 + 结构体，10 万 G 大约 2~3GB 级别，具体看栈用量）。
- **不要 fire-and-forget**：`go func()` 前先说清楚它的生命周期和退出条件，否则就是泄漏。
- 控制手段（按场景选）：
  1. **worker pool + 有缓冲 channel 当信号量**（最常用，项目里就是这么写的）；
  2. `errgroup.SetLimit(n)`（Go 1.20+）或 `golang.org/x/sync/semaphore`；
  3. 用**有界队列**接任务，队列满就拒绝/降级，而不是无限开 G；
  4. 外部依赖调用统一加 `context.WithTimeout`。

**常见追问**：
- *goroutine 比线程快在哪？* → 栈小且动态、切换在用户态不陷内核、调度器批量处理（`runnext` 让新 G 优先执行，提高时间局部性）。

### 1.3 channel

**一句话答案**：channel 的底层是 `hchan`（带一把 mutex 的环形缓冲 + 两个等待队列 `recvq/sendq`）；无缓冲是**同步交接**（发送方直接拷给接收方），有缓冲是**异步入队**（缓冲满/空才阻塞）。

**hchan 关键字段**：`qcount`（当前元素数）、`dataqsiz`（缓冲大小）、`buf`（环形数组）、`sendx/recvx`（环形读写下标）、`recvq/sendq`（`sudog` 等待链表）、`closed`、`lock`。

**发送流程（`chansend`）**：加锁 → 若 `recvq` 有等待的接收者，**直接把数据拷贝给它**并唤醒（不走缓冲）→ 否则若缓冲有空位，写入 `buf` 并返回 → 否则把当前 G 包成 `sudog` 挂到 `sendq`，`gopark` 阻塞等唤醒。接收流程对称（`chanrecv`）。

**关闭规则与 panic 场景（必背）**：

| 操作 | 结果 |
| --- | --- |
| 向已关闭的 channel **发送** | `panic: send on closed channel` |
| **重复关闭** | `panic: close of closed channel` |
| 关闭 **nil** channel | `panic: close of nil channel` |
| 从已关闭的 channel **接收** | 永不阻塞，立即返回**零值** + `ok=false`（缓冲里剩余数据会先被读完） |

**优雅关闭的四种做法**：
1. **只有一个发送方** → 由发送方 `close`（发送方才是数据的所有者，接收方永远不该关）。
2. **多个发送方** → 不要直接关；用一个额外的「关闭信号 channel」，或 `sync.Once` 保证只关一次，发送方在 send 前 `select` 检查是否已关闭。
3. **业务场景（推荐）** → 用 `context.Done()` 代替 close：谁都不用关，取消信号天然通知所有接收方。
4. **需要广播** → 关闭一个 `chan struct{}` 就是最经典的广播（所有接收者同时被唤醒）。

**select / default / nil channel**：
- `select` 有多个 case 就绪时**随机选一个**（runtime 里做了随机洗牌，保证公平，不会饿死某个 case）。
- 带 `default` → 不阻塞，立刻执行 default（用于「尝试发送，满就丢」的非阻塞写）。
- `select {}` 永久阻塞（可以用来挂住 main goroutine）。
- **nil channel**：发送和接收都**永久阻塞**；`close(nil)` panic。**技巧**：在 select 里把某个 case 的 channel 置为 nil 就等于「动态关闭这个分支」——这是控制 goroutine 生命周期最干净的写法。

**常见追问**：
- *channel 一定比 Mutex 慢吗？* → 分场景。channel 要分配 `sudog`、要挂起/唤醒 G，**高竞争下所有 G 抢同一把 hchan 锁**，反而可能不如分片 Mutex；简单计数器用 atomic 最快，共享状态的临界区用 Mutex，**跨 goroutine 传递数据所有权**才用 channel。
- *缓冲多大合适？* → 无缓冲用于「交接即同步」；有缓冲用于解耦生产/消费速率（如 per-connection 写队列），**不要用超大缓冲来掩盖消费慢的问题**，那只是把背压变成了内存占用。
- *关闭一个已被阻塞发送者的 channel 会怎样？* → 该发送者收到 panic（它是发送操作）。

### 1.4 sync 包

**一句话答案**：Mutex 有**正常/饥饿**两种模式（等待超 1ms 转饥饿，锁直给队首）；RWMutex 读写分离但写优先；WaitGroup 靠一个原子 state 计数 + 信号量；sync.Map 是空间换时间的读优化容器。

**Mutex**
- 底层：`state int32`（低 3 位标记 locked / woken / starving，高位存等待者数量）+ `sema` 信号量。
- **正常模式（非公平）**：唤醒的等待者要和新来的、正在自旋的 goroutine 一起竞争，**新来的通常赢**（它正在 CPU 上跑，cache 热），老等待者可能等很久 → 长尾。
- **饥饿模式**：等待超过 **1ms**（`starvationThresholdNs`）进入。规则：锁**直接交给队首**等待者，新来的 goroutine **不自旋、不入队竞争，直接排到队尾**。拿到锁的等待者如果等待时间 < 1ms 或已是最后一个等待者，就切回正常模式。
- 自旋条件：多核 + `GOMAXPROCS > 1` + 自旋次数有限 + **当前 P 的 LRQ 为空**（避免自旋妨碍其他 G）。
- 结论话术：*「Mutex 的设计是在吞吐（正常模式）和公平（饥饿模式）之间切换，正常模式吞吐高但有长尾，饥饿模式保底 1ms 级别能拿到锁。」*

**RWMutex**
- 读锁共享、写锁独占；**有写者等待时，新的读者会阻塞**（写优先，防写饥饿）。
- 适用：**读多写极少**（如配置、路由表）。读多写多时 RWMutex 的原子操作开销反而比 Mutex 高。
- 坑：**读锁不可重入**——goroutine 持有读锁时再去拿读锁，若中间有写者在等，直接死锁。

**WaitGroup**
- 原理：一个 `uint64` state——高 32 位计数器、低 32 位 waiter 数，配合 `sema`。
- **必须遵守**：`Add` 要在 `Wait` **之前**完成（通常是启动 goroutine 之前）。在 goroutine 内部 `Add` 可能与 `Wait` 竞争 → 提前返回或 `panic: sync: WaitGroup is reused before previous Wait has returned`。
- `Add` 传负数导致计数为负 → `panic: sync: negative WaitGroup counter`。
- **不能值传递**（复制会切断 state，`go vet` 会报）。
- 可复用，但必须等上一轮 `Wait` 全部返回后再 `Add`。（Go 1.25 起了 `WaitGroup.Go`，能直接用更省事。）

**Once**：`done uint32` + Mutex，`Do` 快路径是 `atomic.Load` 双检查，慢路径加锁再查一次。**坑：`f` 里 panic，`Once` 依然算「已执行」，之后再 `Do` 不会重试**——初始化失败要么 panic 到底，要么自己加错误状态变量。

**sync.Map**：`read`（只读快照，atomic 加载，命中完全无锁）+ `dirty`（有锁）+ `misses` 计数；miss 累计到 `dirty` 长度就把 `dirty` 提升为 `read`。
- **适用**：读多写少、key 相对稳定（只增不减），典型就是**本机连接注册表、本地缓存**。
- **不适用**：写频繁（dirty 提升开销大）、需要 `len()`、需要强一致遍历（`Range` 是弱一致快照）。
- 写多的场景用**分片锁**（按 key hash 到 N 个 `map + Mutex`），比 `sync.Map` 更可控。

**sync.Pool**：临时对象复用，降低 GC 压力。每个 P 一个本地池（无锁）+ 共享池；**Pool 里的对象随时可能被 GC 清掉**（Go 1.13 加了 victim cache 缓解抖动），所以 `Get` 可能返回 nil，**不能当缓存用**。
- 适用：`[]byte` 缓冲、临时大对象等**生命周期短、创建成本高**的。
- 不适用：连接、有状态对象（Pool 不保证有效性，也没有清理语义）。

**atomic**：`Add / Load / Store / Swap / CompareAndSwap`，Go 1.19 起了 `atomic.Int64` 等类型（避免忘记 64 位对齐）。
- 只能保证**单个变量**的原子性；多个变量组合要互斥（Mutex）或用「整体替换指针 / `atomic.Value`」的思路。
- `atomic.Value` 存取必须是**同一个具体类型**，存不同类型会 panic。

### 1.5 context

**一句话答案**：context 是**请求作用域**的取消/超时/元数据传递机制，四个衍生函数 `WithCancel / WithTimeout / WithDeadline / WithValue`，取消**只能由父传子**，方向单向不可逆。

| 衍生 | 用途 | 要点 |
| --- | --- | --- |
| `WithCancel` | 手动取消 | 返回 `cancel` **必须调用**（`defer cancel()`） |
| `WithTimeout` | 相对超时 | 内部就是 `WithDeadline` |
| `WithDeadline` | 绝对时间点 | 与上游 deadline 取**更早**的那个 |
| `WithValue` | 传请求域元数据 | key 用自定义类型，别用 string |

**传播机制**：`cancelCtx` 内部维护 `children` 集合，取消时遍历子节点递归取消（`err` 置为 `Canceled` / `DeadlineExceeded`），同时关闭 `Done()` channel 唤醒所有等待者；**子取消不影响父**。`Done()` 是唯一该被 select 的入口。

**为什么不能存业务数据**（这题答好显水平）：
1. **无类型安全**：`interface{}` 取值要断言，编译期查不出错误；
2. **依赖被隐藏**：函数签名 `f(ctx)` 完全看不出它依赖哪些值，调用方无法正确构造；
3. **不可静态检查 / 难测试**：写错 key 只有运行时才发现；
4. **语义污染**：context 应只承载「取消信号 + 超时 + 请求级元数据（traceID、用户身份、语言）」，业务参数请走函数入参或结构体。

**HTTP / RPC 链路中的传递**：
- HTTP：middleware 从 header（`X-Request-ID`、token）解析后 `r.WithContext(...)` 塞进去，后续全链路用 `r.Context()`；请求结束/客户端断开时 `r.Context()` 自动 Done，**HTTP handler 里所有阻塞操作都应该带这个 ctx**。
- gRPC：`metadata.NewOutgoingContext` / `metadata.FromIncomingContext` 传递 metadata；**gRPC 自动把 ctx 的 deadline 编码成 `grpc-timeout` header**，服务端解出来就是同一个 deadline，所以「上游超时能传到下游」是免费获得的。
- go-zero：`rpc` 调用都要求显式传 ctx，用 `context.WithTimeout` 包一层，天然适配它的链路超时。

**常见坑**：忘记 `cancel()` 导致 timerCtx 挂在父节点上直到 deadline（**context 泄漏**）；把 context 存进结构体字段（应该按参数传）；在请求链路里用 `context.Background()`（丢掉了取消能力）；`WithValue` 存了可变对象。

### 1.6 内存模型与并发安全

**一句话答案**：Go 内存模型定义的是 **happens-before**：goroutine 创建 → 其内部执行；channel **发送 happens-before 对应接收完成**；`Unlock` happens-before 之后的 `Lock`；`Once.Do` 完成 happens-before 所有 `Do` 返回；`sync/atomic`（Go 1.19 起）是**顺序一致**语义。

**data race 检测（`-race`）**：基于 **ThreadSanitizer**，编译期插桩，运行时记录每个内存访问的向量时钟，检测到「无 happens-before 关系的并发读写」就报错。
- 用法：`go test -race ./...`、`go run -race main.go`；**CI 里应该常跑**。
- 代价：CPU 和内存各约 5~10 倍，只能发现**实际执行到**的竞争——所以要有覆盖度，不能指望它全查出来。

**逃逸分析**：
- `go build -gcflags="-m -m"` 看变量是栈还是堆。
- **逃逸到堆**的典型场景：返回局部变量指针、赋给 `interface{}`（装箱）、被闭包捕获且闭包逃逸、通过 channel 传递指针、slice/map 里的指针元素、对象过大。
- **性能含义**：栈分配几乎零成本（函数返回即回收），堆分配增加 GC 压力 → 热点路径上要减少不必要的逃逸和接口装箱。

**内存对齐 / 伪共享（false sharing）**：
- 结构体字段顺序影响大小：把大字段/8 字节字段放前面能减少 padding（`unsafe.Sizeof` 验证）。
- 未对齐访问可能跨 cache line，CPU 要两次访存。
- **伪共享**：两个无关变量落在同一条 64 字节 cache line 上，多个核分别写它们会导致 cache line 反复失效（MESI 来回弹），性能断崖。解法是 padding 到 cache line 对齐——`sync.Pool` 里的 `poolLocal` 就带 `pad [128 - unsafe.Sizeof(...)]byte`，就是这个原因。

### 1.7 常见并发陷阱（问「你踩过什么坑」就说这些）

| 陷阱 | 现象 | 正确做法 |
| --- | --- | --- |
| **goroutine 泄漏** | 内存/goroutine 数持续上涨 | 向无人接收的 channel 发送、从无人发送的 channel 接收、ctx 取消后 goroutine 没退出、HTTP body 没 close。**排查**：`runtime.NumGoroutine()`、`pprof` 的 goroutine profile、`goleak` 单测 |
| **循环变量捕获** | 所有 goroutine 都拿到最后一个元素 | Go **1.22 之前** `for i, v := range` 的 i/v 是复用的同一变量；解法是传参 `go func(i int, v T)` 或 `i, v := i, v`。**1.22 起（且 go.mod 声明 ≥1.22）每轮迭代都是新变量**，问题消失——答这题要说清版本前提 |
| **map 并发读写** | `fatal error: concurrent map read and map write` | **这是 fatal error，不是 panic，`recover` 抓不住，进程直接死**。解法：`sync.Map`、`RWMutex`、分片锁 |
| **闭包陷阱** | 捕获了大对象导致内存不释放 | 只捕获需要的字段，或提前取出值 |
| **WaitGroup 误用** | panic / 提前返回 | `Add` 放在 `go` 之前；不要复制 WaitGroup |
| **锁粒度过大** | 并发上不去，RT 长尾 | 缩小临界区（**锁内绝不做 IO/RPC**）、分段锁、读写锁、atomic 快路径 |
| **锁顺序不一致** | 死锁 | 全局约定加锁顺序，或用带超时的 `TryLock`（Go 1.18+） |
| **select 里用 `time.After`** | 每次循环新建 timer，堆积 | 用 `time.NewTimer` + `Reset`，或用带 ctx 的 ticker |

### 1.8 并发的错误处理

**一句话答案**：并发任务用 `errgroup` 管生命周期和错误，每个 goroutine 入口用 `defer recover()` 兜底，所有阻塞操作都要有超时。

**errgroup（`golang.org/x/sync/errgroup`）**
- `Group.Go(f)` 启动子任务；**第一个返回非 nil error 会取消派生 context 并记录**，`Wait()` 返回它；
- `WithContext` 拿到可取消 ctx，一个子任务失败其他都被取消（**fail-fast**）；
- `SetLimit(n)`（Go 1.20+）限制并发数，等价于带信号量的 worker pool。

**panic 恢复**
- `recover()` **只在 defer 中直接调用**才有效（`defer recover()` 是无效的，因为它不是直接调用）。
- **关键认知：goroutine 内的 panic 无法被外层 goroutine recover，未恢复的 panic 会让整个进程退出。** 所以每个「自己起的」goroutine 入口都要兜底：
  ```go
  go func() {
      defer func() {
          if r := recover(); r != nil {
              log.Errorf("panic: %v\n%s", r, debug.Stack())
          }
      }()
      // work
  }()
  ```
  （注意别用 recover 吞掉所有异常，掩盖真 bug；要打日志 + 告警。）
- `net/http` 的 server 内部对每个请求有 recover，但**崩的是那条连接**；自己起的 goroutine 不在保护范围内。

**超时控制（三层）**
1. **入口**：HTTP/RPC 层给每个请求一个超时 ctx（网关层设总超时）；
2. **每一跳**：下游调用的超时应**小于**上游剩余的 deadline（上游 1s，下游就给 800ms），否则上游已经超时了，下游还在白干；
3. **资源层**：DB 查询带 ctx、连接池设置 `ConnMaxLifetime`、HTTP client 设 `Timeout`（默认 client **没有超时**，这是经典事故源）。

### 2.1 WebSocket 长连接网关设计（本文件最重要的一节）

#### （1）连接管理

**设计思路**
- **一连接两 goroutine**：读 goroutine（循环 `ReadMessage`）+ 写 goroutine（从 per-conn 的 `chan []byte` 取消息并 `WriteMessage`）。原因：**WebSocket 连接不允许并发写**（gorilla/websocket 会 `panic: concurrent write to websocket connection`），所有写必须经过同一个 goroutine 串行化。这也是给每个连接配一个**带缓冲的发送队列**的原因——队列满说明客户端太慢，直接**踢连接**而不是无限堆积。
- **连接注册表**：本机 `map[userID]*Conn`（高并发写用分片锁或 `sync.Map`），全局在线数用 `atomic.Int64` 统计。**连接对象必须实现「幂等关闭」**（`sync.Once` 包住 close + 从注册表摘除 + 关闭发送队列）。
- **读超时 + 心跳**：服务端定期发 ping 并 `SetReadDeadline` 刷新；配合 `SetPongHandler`，收到 pong 就续期。

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| 心跳间隔 | 30s | 太短浪费流量，太长 NAT 超时断链 |
| 读超时 | 60~90s | 一般设为心跳的 2~3 倍 |
| 发送队列长度 | 64~256 | 满了就判定客户端异常，主动断开 |
| 写超时 | 10s | 避免慢客户端拖住写 goroutine |
| 连接数上限 | 按内存和 fd 算 | 见下表 |

#### （2）多实例下的连接路由（**必考，也是你「跨实例通话控制」的真实经历**）

**问题**：用户 A 连在 instance-1，用户 B 连在 instance-2。A 要给 B 发消息 / 通话控制指令要在「A 所在实例」和「B 所在实例」之间同步——**消息发到了错误的实例怎么办？**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **① 路由表 + 定向投递**（推荐） | 连接建立时写 `ws:route:{userID} = instanceID`（带 TTL，心跳续期）；发消息时查路由，本机直发，否则发到目标实例的 Redis 频道 | 只投一次，无广播浪费 | 多一次 Redis 查询；路由表与真实连接要保证一致（TTL 兜底） |
| **② Redis Pub/Sub 广播** | 所有实例订阅同一频道，收到后判断目标用户是否在本机 | 实现最简单 | N 个实例每条消息投递 N 次，实例多了浪费大 |
| **③ MQ 广播**（RabbitMQ fanout） | 每个实例一个队列绑到 fanout exchange | **可靠**（可持久化、可重放） | 延迟高于 Pub/Sub，运维成本高 |
| **④ 一致性哈希** | 接入层按 userID 哈希固定路由到某实例 | 无跨实例转发 | **扩缩容要迁移连接、实例挂掉该分片全掉线** |
| **⑤ 网关与逻辑分离** | 网关只维护连接，业务状态全在 Redis/无状态服务 | 扩展性最好（主流架构） | 架构复杂，小团队过度设计 |

> **话术（LoveSpouse 跨实例通话控制，直接背）**
> 「我们用 WebSocket 维护 App 与后端的实时链路，通话控制信令走这条链路。服务部署了多个实例后遇到一个问题：用户的连接落在 A 实例，但控制指令可能打到 B 实例。**我们的做法是把通话的状态机放 Redis**（`call:{callID}` 存参与者、状态、开始时间，带 TTL），**状态变更用 Redis 原子操作/Lua 保证并发安全**（避免两个实例同时改同一个通话状态）；实例之间的信令用 **Redis 的发布订阅**做定向投递——每个实例订阅自己的频道，投递方先查路由表知道目标连接在哪个实例，再发到对应频道。这样**扩容不需要迁移连接，加实例即可**。」

> **边界话术（被追问架构时用）**
> 「这套东西是**我们自己按 Redis + Pub/Sub 搭的轻量方案**，不是自研网关。我没有做过百万连接的网关，也没有做过服务网格那一套；我对 GMP、fd 限制、内核参数这些原理清楚，实际量级是**万级连接**。如果要上百万连接，我会先从网关层拆分、连接与逻辑分离这两步入手。」

#### （3）单机连接数上限与内核调优（能报出这些参数就够专业了）

| 层次 | 项 | 参考 |
| --- | --- | --- |
| 进程 | `ulimit -n` / systemd `LimitNOFILE` | 要调到 10 万以上 |
| TCP | `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog` | 连接建立排队 |
| 内存 | `net.core.rmem_max / wmem_max`、`net.ipv4.tcp_rmem / tcp_wmem` | 单连接缓冲区，**是内存大头** |
| Nginx | `proxy_read_timeout` **必须大于心跳间隔** | 否则代理先断开长连接 |

**单机内存估算（会算就赢了）**：每连接 ≈ goroutine 栈（2KB 起，实际几 KB）+ 读缓冲 + 写缓冲 + 连接对象 → 按 **10~30KB/连接** 估；10 万连接约 **1~3GB**。想提上去就要压小读写缓冲（`ReadBufferSize`）、减少每连接 goroutine 数。

**追问预判**
- *跨实例的信令丢了怎么办？* → Pub/Sub 不持久化，属于「尽力而为」。我们的信令是可重试的（客户端超时重发），**权威状态在 Redis**，所以丢一条不影响最终一致；**关键结果（通话结束、扣费）不走 Pub/Sub，落库或走 MQ**。
- *Redis 挂了怎么办？* → 主从 + 哨兵（我们没做 Cluster）。降级路径：新通话入口限流，通话中的用户靠**客户端心跳 + 兜底轮询接口**拉状态。
- *为什么不直接一致性哈希，省掉转发？* → 有利有弊：哈希免转发但**扩缩容要迁移连接、实例宕机会批量掉线**；我们的量级用路由表 + 定向投递更简单可控。

### 2.2 限流

**四种算法速答**

| 算法 | 原理 | 特点 |
| --- | --- | --- |
| 固定窗口计数 | 每窗口一个计数，超了拒绝 | 最简单；**临界问题**（窗口边界可打 2×） |
| 滑动窗口 | 拆小格 / ZSET 存时间戳 | 精度高，内存换精度 |
| 漏桶 | 恒定速率流出，多余丢弃或排队 | **整流**，不允许突发 |
| **令牌桶** | 恒定速率放令牌，桶容量允许突发 | 最常用；Go 用 `golang.org/x/time/rate` |

```go
lim := rate.NewLimiter(rate.Limit(100), 200) // 100 QPS，允许 200 的突发
if !lim.Allow() { /* 429 */ }
// lim.Wait(ctx) 阻塞等待，适合后台任务；Reserve 可拿到「还要等多久」
```

**单机 vs 分布式**
- 单机：`rate.Limiter` 或 atomic 计数，零网络开销，但**阈值 × 实例数 ≠ 全局阈值**（各实例独立，边界不准）。
- 分布式：**Redis + Lua**（脚本里做原子判断 + 自增 + 过期，避免 GET/SET 竞态）；注意 Redis Cluster 下同一用户的 key 要用 `hash tag`（如 `{userID}`）保证落在同一 slot。
- **go-zero 内置**（你的项目真用过，可以提）：`rest` 的 `PeriodLimit` 是基于 Redis 的固定窗口计数（默认 100 次/分钟），`TokenLimiter` 是基于 Redis + Lua 的令牌桶；另外还有**自适应限流**（基于 CPU 负载自动调节拒绝率，类似 BBR 的思路），适合保护自己不被突发打崩。

**阈值怎么定（这题要从压测讲起）**
1. 压测得出**单实例容量**（QPS + P99 可接受的最大值）；
2. 阈值 = 单机容量 × 0.7~0.8 × 实例数（留 buffer）；
3. 按接口分别定：登录/认证这类重接口单独限，读接口可以放宽；
4. 粒度：IP（防刷）→ userID（防单用户滥用）→ 接口 → 全局（兜底）；
5. 超限**返回 429 + Retry-After**，并且**要降级不要直接报错**（比如返回上次缓存的结果）。

**追问预判**
- *限流和熔断的区别？* → **限流保护自己**（入口，控流量）；**熔断保护调用方**（出口，防被下游拖死）。
- *Nginx 层也要限吗？* → 要。`limit_req`（漏桶）+ `limit_conn`（并发连接数）在最前沿挡掉明显恶意流量，成本最低。

### 2.3 熔断与降级

**熔断器三态**

| 状态 | 行为 | 转换条件 |
| --- | --- | --- |
| **Closed**（关） | 放行所有请求，统计窗口内的失败率 | 失败率超阈值 + 请求数达到最小样本量 → Open |
| **Open**（开） | **快速失败**，不发真实请求（省下超时时间） | 经过熔断时长 → Half-Open |
| **Half-Open**（半开） | 放行**少量**探测请求 | 成功数达标 → Closed；失败 → 回 Open 并重置计时 |

**参数**：统计窗口（如 10s / 最近 20 个请求）、错误率阈值（如 50%）、**最小请求数**（防样本太少误熔断）、熔断时长（如 5s）、半开探测数量。
**库**：`sony/gobreaker`（最常用）、**go-zero 内置 breaker**（基于滑动窗口的 Google SRE 自适应算法，用成功率 + K 值判断是否拒绝）、`hystrix-go`（已不活跃）。

**降级策略（按优先级）**
1. **兜底数据**：返回缓存旧值 / 默认值 / 空列表（比报错体验好）；
2. **关非核心功能**：推荐位、排行榜、AI 高级玩法先关，保核心链路；
3. **排队**：转异步，返回「处理中」；
4. **只读降级**：禁止写入，只放查询。

> **话术（挂项目）**
> 「我们对**外部依赖**都做了超时 + 熔断 + 降级。比如 LoveSpouse 的实时语音依赖外部 Live API，我们把调用包一层 timeout 和 breaker，**不可用时就降级回文本对话**，用户体验是「语音暂时不可用」而不是「App 卡死/报错」。路由器广告那边，第三方登录不可用时降级成本地手机号认证，认证本身不受影响。」

**追问预判**
- *熔断阈值怎么定？* → 先按经验给（50% 错误率、10s 窗口、最少 20 个请求），再根据线上误熔断/漏熔断的实际情况调；**最小请求数一定要设**，否则低峰期一两个失败就熔断。

### 2.4 缓存抗压

**多级缓存**：本地缓存（进程内，无网络开销，一致性问题）→ Redis（共享）→ DB。
- 本地缓存一致性两种做法：**短 TTL**（1~5s，牺牲一致性换简单）或**版本号 / MQ 广播失效**。
- 项目用法：角色配置、付费道具配置、广告位配置这类**读多写极少**的，本地缓存 + Redis 双级，改配置时发 MQ/Redis 通知各实例失效。

**热点数据（热 Key）**
- 发现：Redis 4.0+ 的 `hotkeys`、监控统计、或在客户端埋点统计。
- 解法：**本地缓存兜住**（最有效）→ key 加随机后缀打散到多个节点（读时只读一个副本）→ 从库分担读。

**缓存三兄弟（必背）**

| 问题 | 场景 | 解法 |
| --- | --- | --- |
| **穿透** | 查不存在的 key，直击 DB | 布隆过滤器 / 缓存空值（短 TTL） / 参数校验 |
| **击穿** | **单个热点 key 过期**瞬间大量请求回源 | 互斥锁重建 / 逻辑过期（不设 TTL，异步刷新） / 热点永不过期 |
| **雪崩** | 大量 key 同时过期，或 Redis 整体挂掉 | TTL 加随机抖动 / 多级缓存 / 限流降级 / Redis 主从 + 哨兵 |

**缓存与 DB 一致性**
- **Cache Aside**（主流）：写时**先更新 DB，再删缓存**（不是更新缓存）；删失败靠 MQ 重试补偿。
- **延迟双删**：更新 DB 前删一次，更新后再延迟几百 ms 删一次（对付「读请求把旧值又写回缓存」的窗口）。
- **binlog 订阅**（canal）异步失效：最可靠，但组件成本高（小团队一般不上）。
- 结论话术：*「我们接受**最终一致**，用 TTL 兜底，强一致要求的场景直接绕开缓存读主库。」*

**追问预判**
- *为什么是删缓存而不是更新缓存？* → 并发更新缓存会有乱序覆盖（后写的可能是旧值），而且很多缓存值是**聚合计算**出来的，lazy load 更划算。

### 2.5 异步化与削峰

**三种手段**
1. **消息队列削峰**：上游瞬时流量先入 MQ 缓冲，下游按自己的消费能力拉取。要点：队列积压监控、消费速率是否够、要不要动态扩容消费者。
2. **批量聚合**：攒 200 条或 200ms 触发一次批量写（batch insert / pipeline），把 N 次网络往返变成 1 次。**权衡**：延迟换吞吐。
3. **异步任务**：本地用 `goroutine + 有界队列 + 固定 worker 数`（不要无限开 G）；跨服务用 MQ。

**消息可靠性（不丢）三段论**

| 环节 | 手段 |
| --- | --- |
| 生产 | publisher confirm / 事务；发送失败重试 + 本地消息表兜底 |
| 存储 | queue durable + message persistent；broker 高可用（镜像队列 / quorum queue） |
| 消费 | **手动 ack**（`autoAck=false`），业务成功后才 ack；失败重试 + 次数上限 → **死信队列（DLX）** + 告警 + 人工/定时补偿 |

**幂等（不重复）**：MQ 是 At-least-once，**重复投递无法避免，只能幂等**。四种做法：
1. **唯一索引兜底**（最可靠）：业务唯一键（如 `产品线 + 门店 + 单据号 + 行号`）建 UNIQUE，插入冲突即忽略；
2. **Redis SETNX 去重**：处理前先占位（注意异常时别把 key 永久占了，要带 TTL）；
3. **状态机**：只有特定状态才允许流转（如「待支付 → 已支付」，重复的第二次直接忽略）；
4. **业务幂等表**：记录已处理的事件 ID。

**顺序**：同一业务实体的消息必须**进同一队列、被同一消费者串行处理**（按 key 哈希路由）；**不要追求全局有序**（吞吐会塌）。> **话术（挂 POS 数据中台，详见第三部分场景三）**
> 「POS 数据中台是典型的**异步削峰**场景：上游门店 POS 的流水、电子发票、商品档案先进 RabbitMQ，消费端做整理、加工、批量上传。我们踩过的坑就是**早期用 autoAck + 逐条写库，重启会丢消息、晚上闭店批量上报时消费跟不上**，后来改成手动 ack + 攒批处理 + 唯一键幂等，再加对账任务兜底。」

### 2.6 数据库层面的高并发

**连接池（`database/sql`）配置**
```go
db.SetMaxOpenConns(50)                 // 最大连接数（≠ 越大越好）
db.SetMaxIdleConns(20)                 // 空闲连接数，一般 ≈ MaxOpenConns
db.SetConnMaxLifetime(time.Hour)       // 短于 MySQL wait_timeout，避免用到被服务端断掉的连接
db.SetConnMaxIdleTime(10 * time.Minute)
```
- **容量约束**：`实例数 × MaxOpenConns` 必须 **< MySQL `max_connections`**（要留余量给运维、其他服务）。
- MySQL 每个连接对应一个线程，连接过多 → 上下文切换和内存暴涨，**QPS 反而下降**。经验上从 20~50 起调，配合压测找拐点。

**读写分离**：主库写、从库读；注意**主从延迟**（写后立刻读要强制走主库）。**数据量不大的话不要做**——复杂度和收益不成正比。

**分库分表的时机（说结论就够）**
1. 先做：加索引 / 优化 SQL / 缓存 / 归档历史数据 / 垂直拆表（把大字段拆出去）；
2. 单表仍到 **千万行级**且查询变慢、写入瓶颈 → 才考虑水平分表；
3. 分片键选**查询条件里最常出现的那一列**（如 `merchantID`）；痛点全在**跨分片查询、分页、聚合**；
4. **不要过早分库分表**，小体量上分片是自找麻烦。

**写优化**：批量插入（500~1000 条/批）、缩短事务、**按主键递增顺序写入**（避免 InnoDB 页分裂）、大表冷热分离（历史流水归档到归档表/数仓）。

> **话术（挂 POS 流水表）**
> 「POS 流水是典型的**只增不改、按时间查询**的数据，我们的做法是：写入用**批量 + 按主键顺序**，历史数据按时间归档，查询都带时间范围走索引。目前没有到需要分库分表的量级——**我们的判断标准是单表数据量和 P99 查询延迟，没到就不分。**」

### 2.7 压测与容量评估

**工具**：`wrk` / `wrk2`（压 HTTP 首选）、`ab`、`vegeta`、`k6`（脚本化、场景化）、`hey`；复杂链路用 Go 自己写压测脚本（能复用 client 代码，最贴近真实）。

**指标（只看 avg 是外行）**

| 指标 | 说明 |
| --- | --- |
| QPS / TPS | 吞吐，按接口/链路分别看 |
| **P95 / P99 / P999** | **长尾才是用户体验**，avg 会被大量快请求拉平 |
| 错误率 | 超时、5xx 都算失败 |
| 资源 | CPU（`us/sy/wa`）、内存、网卡带宽、磁盘 IO、**GC 频率与停顿** |
| 连接 | 并发连接数、TIME_WAIT 数量、fd 使用量 |

**定位瓶颈的方法（四步）**
1. **逐层加压**：只压网关 → 加业务逻辑 → 加 DB/Redis → 加 MQ，哪一层加上去指标塌了，瓶颈就在那；
2. **看系统层**：`top`（是否 CPU 打满、`sy` 高说明 syscall 多、`wa` 高说明 IO 等待）、`vmstat`（上下文切换 `cs`）、`ss`（连接状态）；
3. **看应用层**：`pprof` 的 cpu / heap / goroutine / **block / mutex**（锁竞争就看这两个）、火焰图、`go tool trace`；
4. **看存储层**：慢查询日志、`explain`、Redis 慢日志、连接池等待。

**容量估算（会算 = 加分）**
```
需要的实例数 = 峰值 QPS / (单机压测 QPS × 0.7)     // 0.7 是留 buffer
```
再校验三个约束：**总连接数 < DB max_connections**、**单实例内存 × 实例数 < 可用内存**、**带宽**。最后按「日常水位 + 峰值系数（如 3~5 倍）+ 冗余」定实例数，并配弹性扩缩容。

**压测注意事项**：压测机自己别成为瓶颈（多台、看压测机的 CPU/网络）；数据量要接近生产（数据少时索引全在内存，结果虚高）；压测前要**预热**（连接池、缓存）；别压生产。

> **话术（诚实版，挂路由器广告）**
> 「Portal 认证接口我用 wrk 压过，关注 QPS 和 P99。压测发现瓶颈在认证成功后的**同步写库**上，就改成了 **Redis 存认证凭据（带 TTL）+ 日志异步批量落库**，单机认证能力提升明显。**我没有做过全链路压测和影子库那一套**，量级也没到百万级。」

### 2.8 服务可扩展性

**无状态化是水平扩展的前提**
- 状态外置：session/token → Redis，文件 → 对象存储，配置 → 配置中心；
- 效果：任何实例处理任何请求结果一致 → **加实例就能扩容**，不需要迁移。

**有状态服务怎么扩（WebSocket 就是有状态，这是本岗位最相关的一题）**
1. **路由 + 转发**：连接留在原实例，消息跨实例投递（见 2.1）；
2. **一致性哈希固定路由**：无转发，但扩缩容要迁移、实例挂会批量掉线；
3. **优雅下线（发布时必做）**：先停止接收新连接 → 给客户端发「请重连」指令 → 等连接排空（connection draining）→ 再退出；K8s 里配合 `preStop` + `terminationGracePeriodSeconds`。
4. **状态与连接分离**：业务状态全在 Redis/DB，连接的实例位置只是「路由信息」，任何实例都能接管。

> **边界话术（一定要说，否则一问就露）**
> 「我们服务目前是**单实例/少量实例**，但我在写的时候**把状态都放到了 Redis**，所以**加实例只需要在网关或配置里改一下，不用改代码**。**服务的拆分和治理是团队一起做的，我主要负责业务模块和这些并发相关的设计**；链路追踪我知道要用 traceID 串起来（OpenTelemetry / Jaeger 那套），但**没有在项目里落地的经验**。」

## 第三部分：结合项目的三个高并发场景题（STAR 完整答法）

### 场景一：LoveSpouse 实时语音通话，如何支撑大量用户同时通话？跨实例通话控制怎么做？

**S（背景）**：面向智能玩具 App 的虚拟角色陪伴系统，支持实时语音通话、多角色、长期记忆和付费互动。通话是核心付费场景，**计费必须准确，不能超扣也不能漏扣**。

**T（目标）**：① 通话建立/中断延迟可控；② 多实例部署时，通话控制状态在各实例间一致；③ 金币计费准确；④ 服务能加实例扩容。

**A（做法，按四层讲）**

1. **接入层（WebSocket 长连接）**
   - 每连接**读 goroutine + 写 goroutine**，写操作通过 per-conn 的**有缓冲 channel 串行化**（WebSocket 禁止并发写，否则 panic）；
   - 心跳 30s + 读超时刷新，超时或**发送队列满**就主动断开；
   - 连接注册表放本机内存（分片锁 / `sync.Map`），全局在线数用 atomic 统计。
2. **通话状态与跨实例控制（核心）**
   - 通话状态机放 **Redis**：`call:{callID}` 存参与者、状态、开始时间、金币快照，带 TTL（**掉线时靠 TTL 兜底**）；
   - **状态迁移用 Redis 原子操作 / Lua 脚本**，避免两个实例同时改同一个通话（比如 A 实例在处理挂断、B 实例在处理超时）；
   - 实例间信令走 **Redis Pub/Sub 定向投递**：连接建立时写路由键 `ws:route:{userID} → instanceID`（心跳续期），投递方先查路由，本机直发，否则发到目标实例的频道；
   - 结果是**扩容不需要迁移连接**，加实例即可。
3. **实时语音链路**
   - 音频流走端到端 Live API，WebSocket 只承载**信令 + 文本增量**；
   - 全链路 `context.WithTimeout`，用户**打断（barge-in）时发 cancel 信令并 cancel context**，避免还在跑的推理浪费资源；
   - 外部 API 调用统一超时 + 熔断，**不可用时降级为文本对话**。
4. **计费与幂等（最容易被追问）**
   - 扣费用 **Redis Lua 脚本**一步完成「校验余额 + 扣减 + 写流水」，保证**不超扣**；
   - 通话结束、用户主动挂断、**异常掉线**三条路径都要结算：掉线靠**通话状态 TTL 过期 + 定时补偿任务**扫描未结算的通话去补单；
   - 结算本身**幂等**（`callID + 事件类型` 唯一索引），重复触发不会重复扣；
   - 对接的腾讯 IM 消息**可能重复投递**，用 msgID 做去重（SETNX / 唯一索引）。
5. **容量与保护**：入口信令限流；内部 goroutine 用 **worker pool 控并发**，不给每个请求无限开 G；对 Redis 的读写做批量/管道优化。

**R（结果）**：通话控制状态跨实例一致、计费不超扣不漏单、服务可水平扩容。
**踩坑（诚实，加分项）**：初版把连接注册表和通话状态放在**单实例内存**，扩到多实例后消息发不到目标用户；改成 **Redis 路由表 + Pub/Sub 定向投递**才解决。

**追问预判**

| 追问 | 答法 |
| --- | --- |
| Pub/Sub 消息丢了怎么办？ | Pub/Sub 不持久化，属于尽力而为。信令**可重试**（客户端超时重发），**权威状态在 Redis**，丢一条不影响最终一致；**关键结果（通话结束、扣费）不走 Pub/Sub，落库或走 MQ** |
| 两个实例同时结算同一通话？ | Lua 原子状态迁移（只有 `active` 才能转 `ended`）+ 结算幂等唯一索引，双保险 |
| Redis 挂了怎么办？ | 主从 + 哨兵；降级为新通话入口限流 + 客户端兜底轮询拉状态 |
| 单实例能撑多少连接？ | 讲 fd 限制、内存估算（10~30KB/连接）、内核参数调优；**诚实说我们实测是万级连接，没到百万** |
| 为什么不直接一致性哈希？ | 免转发但有连接迁移和单点批量掉线问题；我们量级选路由表更简单 |

### 场景二：路由器广告 Portal 认证页，公共 WiFi 大量用户同时认证，怎么保证不被打挂？

**S（背景）**：公共场所 WiFi 的广告系统，用户连上热点后**必须经过 Portal 认证页**才能上网；认证页展示广告，支持 URL Schemes 唤起浏览器 PWA 安装和第三方登录。**突发性极强**：一辆大巴/一趟地铁到站，几十秒内几百人同时连。

**T（目标）**：认证页**必须快**（它是用户上网的第一跳，也是广告曝光位），认证接口在突发下不能挂，广告素材不能拖慢首屏。

**A（四层做法）**

1. **页面与静态资源**
   - Portal 页用 **Go template 服务端渲染**，广告素材和静态资源走 CDN/本地缓存 + `Cache-Control`；
   - 首屏**尽量不依赖后端实时数据**（广告内容本地化/缓存化），页面秒开；
2. **认证接口**
   - **无状态化**：认证成功后把放行凭据写 **Redis（带 TTL）**，AC/网关侧查 Redis 即可放行，**不写 MySQL**；
   - MySQL 只承担**认证日志 + 统计**，日志**异步化**（先入内存队列或 Redis list，后台固定 worker 批量落库）；
3. **限流与防刷**
   - 按 **IP / 设备 MAC** 维度限流：同一设备短时间内重复认证，**直接返回已有凭据（幂等）**，挡掉绝大部分无效请求；
   - Nginx `limit_req` + `limit_conn` 在最前面兜底突发，超限返回**排队/重试提示而不是 500**；
4. **缓存与 DB**
   - 设备-商户映射、广告位配置放**本地缓存 + Redis**，避免每次请求打 DB；
   - 连接池按实例数 × MaxOpenConns < MySQL max_connections 配，写入批量 + 按主键顺序。

**R（结果）**：单热点几百人同时认证的突发能扛住；认证接口 P99 稳定。
**诚实边界**：*「我们量级不是百万，是通过**无状态 + Redis 凭据 + 限流 + 异步落库**把单机能力做上去的；我用 wrk 压过认证接口，看过 QPS 和 P99，也据此定位到同步写库是瓶颈。」*

**追问预判**

| 追问 | 答法 |
| --- | --- |
| 为什么用 Redis 不用 MySQL 存凭据？ | 凭据是**高频写 + 短生命周期 + 强时效**，Redis 的 TTL 天然契合；MySQL 承担持久化和统计，异步写 |
| Redis 里的凭据丢了？ | TTL 到期用户重新认证，可接受；**关键日志不丢**（异步队列有重试 + 落库失败告警） |
| AC 挂了会不会影响认证服务？ | 两边解耦，AC 侧有本地缓存/白名单，认证服务故障不清空已放行用户 |
| 怎么防同一台设备刷认证？ | 设备指纹 + 幂等（已有有效凭据直接返回） |
| 如果要做多区域？ | 服务无状态，**按区域就近部署多实例**，前置负载均衡，数据面 Redis 按区域隔离 |

### 场景三：POS 数据中台每天海量流水经 RabbitMQ 涌入，如何不丢不重复、平稳消费？

**S（背景）**：多条零售 POS 产品线的数据中台，统一接入**销售流水、商品档案、电子发票**；上游是各家门店的 POS，**网络不稳定、可能重复上报、可能补传历史数据**，峰值集中在闭店时段。

**T（目标）**：不丢、不重复、消费平稳不过载，能应对峰值。

**A（按消息生命周期讲，这条主线最容易讲清楚）**

1. **接入与生产**
   - 统一接口适配不同产品线（外部协议各异，内部收敛成统一模型）；
   - 数据先落 RabbitMQ（exchange 按业务类型 / 产品线路由）；
   - **生产端用 publisher confirm**，broker 确认收到才给上游返回成功。
2. **存储（不丢）**
   - queue **durable** + message **persistent**；broker 侧做镜像/仲裁队列保证高可用。
3. **消费（不丢 + 平稳）**
   - **手动 ack**（`autoAck=false`），**业务处理成功后才 ack**；
   - 失败重试有**次数上限**，超过进**死信队列（DLX）** + 告警 + 定时/人工补偿；
   - **不逐条写库**：攒批（如 500 条 / 200ms）批量 insert 或批量上传，减少 DB 往返；
   - 并发用**固定数量的 worker goroutine**（可控），每个 worker 独立事务。
4. **不重复（幂等）**
   - 每条消息带**业务唯一键**（产品线 + 门店 + 单据号 + 行号）；
   - 消费端靠 **DB 唯一索引**兜底（插入冲突即忽略）+ Redis 占位去重；
   - **补传的历史数据走同一套幂等逻辑**，天然安全。
5. **顺序**
   - 同一门店/同一单据的消息**按 key 哈希到同一队列**，保证局部顺序（避免「作废」比「销售」先到造成状态错乱）；**不追求全局有序**。
6. **兜底与可观测**
   - **对账任务**：按天 + 产品线比对上游单据数与落库数，发现差异走**补拉接口**；
   - 监控：队列积压深度、消费速率、失败率、死信数量。

**R（结果）**：数据不丢不重、消费平稳、峰值可控、差异可发现可修复。
**踩坑（诚实）**：早期用 **autoAck + 逐条写库**——重启会丢消息、闭店高峰消费跟不上；改成**手动 ack + 攒批 + 唯一键幂等**之后才稳。

**追问预判**

| 追问 | 答法 |
| --- | --- |
| 消息真的不丢？怎么验证？ | 三段论（生产 confirm / 存储持久化 + 镜像 / 消费手动 ack + 重试 + 死信）+ **对账任务兜底**，不靠「我觉得」 |
| 重复消费怎么彻底避免？ | 不可能避免，**只能幂等**；唯一索引是最后一道防线 |
| 消息积压怎么办？ | 先判断是**消费慢**还是**生产暴涨**：消费慢就优化（批量、并发、慢 SQL）并临时扩容消费者；生产暴涨本来就是削峰要处理的场景；**不要盲目清队列** |
| 为什么用 RabbitMQ 不用 Kafka？ | RabbitMQ 单条延迟低、路由灵活（exchange/routing key）、运维简单，**我们的体量用不到 Kafka**；Kafka 更适合高吞吐日志流（诚实：我没在生产用过 Kafka） |
| 消费失败一直重试会不会打挂 DB？ | 重试有上限 + 退避；失败进死信，不进无限重试循环 |

## 第四部分：Go 并发高频追问 TOP 15 速答表

| # | 问题 | 一句话答案 |
| --- | --- | --- |
| 1 | 为什么需要 P？ | 解耦 G 与 M、提供无锁的本地队列和 mcache、让并行度（GOMAXPROCS）可独立控制 |
| 2 | work stealing 是什么？ | P 本地队列空时从其他 P 偷**一半** G，实现负载均衡 |
| 3 | 抢占式调度什么时候变的？ | Go **1.14** 从协作式（只在函数序言检查）改为**基于 SIGURG 信号的异步抢占**，解决了 `for{}` 卡住 STW |
| 4 | goroutine 栈多大？ | 初始 **2KB**，按需翻倍扩容，64 位上限默认 1GB |
| 5 | goroutine 泄漏怎么查？ | `runtime.NumGoroutine()`、pprof goroutine profile、goleak 单测；根因通常是阻塞在无人收发的 channel 或 ctx 取消后没退出 |
| 6 | channel 关闭的三条铁律？ | 只有发送方关；不能重复关；关 nil 会 panic。多发送方用 `sync.Once` 或改用 `context.Done()` |
| 7 | nil channel 有什么用？ | 收发永久阻塞；**在 select 里把 case 置 nil 就等于动态禁用该分支** |
| 8 | select 多个 case 就绪选哪个？ | **随机**（runtime 随机洗牌），天然公平 |
| 9 | Mutex 饥饿模式？ | 等待超过 **1ms** 转入，锁直接给队首、新来的不竞争；避免长尾饿死 |
| 10 | sync.Map 适用什么场景？ | 读多写少、key 稳定（本机连接表、本地缓存）；写多用分片锁 |
| 11 | sync.Pool 能当缓存吗？ | **不能**，GC 会清空，`Get` 可能返回 nil |
| 12 | context.Value 为什么不该存业务数据？ | 无类型安全、隐藏依赖、调用方看不出要传什么、难测试；只该传取消/超时/请求域元数据 |
| 13 | map 并发读写会怎样？ | `fatal error: concurrent map read and map write`，**不是 panic、recover 抓不住，进程直接死** |
| 14 | `-race` 原理与代价？ | ThreadSanitizer 编译期插桩 + 向量时钟；CPU/内存约 5~10 倍，只能发现**实际跑到**的竞争 |
| 15 | 多实例下 WebSocket 消息怎么送到目标用户？ | **路由表（Redis，userID → instanceID，带 TTL）+ 定向投递（Pub/Sub 到目标实例频道）**；备选是一致性哈希或全量广播 |

**三个「一秒钟救场句」（卡壳时用）**
1. *「这个我在**原理层面**清楚，实践上我们项目用的是更简单的方案，我讲一下我知道的标准做法和我们的取舍？」*（把「没做过」转成「懂 + 有取舍判断」）
2. *「我们量级没到那一步，**我的判断标准是 xxx**，到了我会先做 xxx、再做 xxx。」*（展示架构判断力，比编经历安全）
3. *「这块是团队里架构组主导的，**我参与落地了 xxx 部分**，具体细节我可以讲讲我负责的那一块。」*（划清边界但仍在贡献）
